## 模块维护规则

1. 新业务接口放入对应 `api/modules/`，业务响应必须校验。只有跨多个业务复用的传输行为进入 `http.ts` 或 `stream.ts`。
2. `api/client.ts` 和 `assistant.service.ts` 是稳定入口。底层模块不得反向导入入口来取得其他模块的内部实现。
3. 共享包不依赖应用；Web 只允许依赖浏览器安全的共享代码；服务层不依赖 HTTP，数据库与配置不依赖业务服务。
4. 区分读取与写入：可被替代的读取取消并失效旧结果；已经提交的写入保留持久化语义，界面反馈检查当前对象身份。
5. 扩展流协议时分别明确进度、思考、正文、结果和错误。传输层释放资源，业务层校验最终 DTO，部分输出不能充当最终成功结果。
6. 数据库迁移、评分状态机和原始笔记保护规则，应通过各自的业务测试维护；不能仅以文件缩短或新增抽象层判定质量改善。
7. 外部模型请求不进入 SQLite 写事务；任务领取和最终提交分别使用短事务。重评在提交前保留旧结果，失败或单实例重启时恢复可读状态。
8. 公开 DTO 使用显式字段映射；JSON 和 SSE 最终结果共用合同。跨端一致的 Schema 由 shared 维护，数据库实体只留在服务端。
9. 共享包保持无全局副作用，新增模块遵守 sideEffects: false 的约定；浏览器复用共享代码后继续检查资源预算。
10. 笔记候选稿与已采用的阅读版本分别维护。长时间生成前捕获快照，提交时再次核对；客户端采用时发送已核对的候选版本 ID，重复操作保持幂等。
11. 考核提交前固定答案快照并等待全部保存结果；保存失败不得锁卷。服务端状态检查与对应写入保持在同一短事务中，客户端刷新不能覆盖尚需保留的输入和主错误。

`pnpm architecture:check` 已接入 `pnpm lint`，检查跨工作区依赖、指定分层边界和运行时循环。检查覆盖静态导入、再导出、字面量动态导入及类型导入的边界；不分析变量生成的路径、反射和外部依赖内部实现。

## 后续设计重点与验证边界

- `assessment.service.ts` 中的渐进提示与模型策略、其他领域的持久化约束和共享合同，仍可继续审查。路线查询、学习状态、挑战执行、答案与锁卷、笔记持久化及编辑状态已独立；继续重构时需保持状态机和事务边界完整。
- 本轮以服务事务防止新重复答案和锁卷后的写入，没有删除历史重复答案或增加数据库唯一约束。后续约束迁移需先核对历史数据并保留用户答案。

- 严格考核：挑战类型：CODING；首考题 1（资料定位）：只允许使用《Umi Max Request》《AbortController》，分别摘出能支撑「请求层、错误处理与取消」的定义、关键机制、边界/反例，并标明来源；首考题 2（机制解释）：闭卷按“请求配置→拦截器→响应 shape 解析→业务/HTTP/Abort 分类→唯一 UI 反馈”说明各状态在哪一层收口；首考题 3（最小产出）：固定接口返回依次为 200 `{code:0,data:{id:1}}`、422 字段错误、401、500、延迟 500ms 后取消；实现一个 service 和页面，交付统一配置、错误映射表、取消控制、测试及网络记录；预期每类只出现一次对应反馈、取消不提示失败，且未经验证的响应不能写 UI；首考题 4（受限排错）：给定失败日志“401 被拦截器 toast 一次、页面 catch 又 toast 一次；取消搜索显示 500”，只可检查错误映射责任、`AbortError` 分支和请求拦截器；提交调用栈/网络记录、排除项、根因、修复及六种状态回归；首考题 5（学习复述）：3 分钟说明“传输成功、业务成功、界面可提交”为何不同，并追问：静默请求为何不能借机吞掉 401？复测变式：仅将题 3 的 422 字段错误改为网络断开后恢复连接并重试，保留 200/401/500/取消、映射责任与单次反馈规则；预期离线显示可恢复反馈且重试只成功一次，取消仍无错误，提交新的网络记录、映射断言与六态回归。命题边界：只在所列资料、六种响应 fixture 和可复核输出内评分；英文资料不得作为独立首考题源。
- 通过标准：交付 service、映射表、六种 fixture 的正常/边界/失败记录；401、403、422、500、取消和离线各有唯一且正确的 UI 行为，响应形状先验证再消费；故障能在限定层定位。否决项：重复 toast、把取消当错误，或以 `catch {}` 隐藏失败。 评估边界：只接受本点题目输入与可复核产出。

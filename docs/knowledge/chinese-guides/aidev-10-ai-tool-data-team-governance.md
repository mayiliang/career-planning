# AI 研发工具准入、数据边界与团队治理知识点讲义

## AIDEV-10 AI 研发工具准入、数据与团队治理

团队允许使用 AI，不等于任何人可以把任何仓库、客户工单、生产日志或密钥发送给任何模型。治理的难点也不是写一份“请谨慎”政策，而是把数据分类、供应商处理、账号、技术阻断、人工审批、例外、审计、保留和事故响应连成日常可执行系统。好的治理让低风险创新更容易，让高风险行为在发生前被看见和阻止，并且能随供应商与法规变化更新。

### 学习前先确认

- 直接前置：[AGENT-10 身份、授权、工具权限与运行隔离](../chinese-guides/agent-10-identity-authorization-runtime-isolation.md#agent-10)用于理解逐工具权限和委派；[AIGOV-01 AI 数据、模型变更、审计与问责](../chinese-guides/aigov-01-data-model-change-audit-accountability.md#aigov-01)用于理解产品级风险、变更和责任。两者分别承担执行安全与治理框架。

### 一、Data Classification 决定处理边界

**数据分类（Data Classification）**根据泄露、误用、保留和跨境后果，把信息映射到允许的处理方式。常见等级有公开、内部、机密/客户、严格受限，但名称不重要，关键是每级能明确回答是否允许发送、需否脱敏、允许哪些地区/模型、保留多久、谁能批准。

代码也有分类。开源仓库、内部业务逻辑、安全配置、客户定制代码与含密钥历史不能统一称“源码”。生产日志可能混合公开错误码和个人信息；工单摘要可能包含健康或支付数据。分类发生在上传前，不依赖供应商收到后再判断。

派生数据继承敏感性。把客户内容总结、向量化、截图或生成测试样例，不会自动变公开。哈希只有在不可逆且无法字典恢复时才能降低可识别性；简单遮住界面不等于脱敏。

### 二、从数据流而不是工具名称审查

同一 AI 产品的网页、IDE 插件、CLI、企业 API、浏览器 Agent 和本地模型有不同数据路径。画出输入从设备到代理、供应商、模型、日志、缓存、人工支持和子处理商的流向，以及输出如何回到仓库和遥测。

问清传输加密、静态存储、训练使用、保留期、地区、子处理商、删除、管理员可见性、事件通知和导出能力。营销页面的“企业级安全”不能替代合同、控制台配置和技术验证。本地模型也可能下载组件、发送遥测或读取整个磁盘，不天然合规。

数据流变化是重新准入触发器。供应商改模型、地区、日志、插件权限或条款时，原结论可能失效。工具 owner 负责持续跟踪，而不是把责任交给个人用户阅读更新邮件。

### 三、Approved Tool 是带条件的配置对象

**批准工具（Approved Tool）**不是一个名字白名单，而是工具、版本/产品层级、组织账号、允许场景、数据等级、地区、模型、功能、权限、保留和到期的组合。企业 API 获批不代表个人免费网页获批，代码补全获批也不代表浏览器自动操作获批。

准入记录包含业务目的、owner、安全/隐私/法律结论、允许仓库、账号方式、最小权限、默认设置、阻断条件、退出与数据删除计划。高风险功能如自动执行命令、连接生产、长期记忆和第三方插件单独评估。

工具目录面向开发者显示“可以做什么”和“哪些数据不能用”，并提供合规替代，减少影子 AI。只发布禁止列表但不给可用路径，会把行为推向不可观测的个人账号。

### 四、身份和账号治理是第一道执行控制

受控工具使用组织 SSO、MFA、自动入离职、角色和设备策略。个人账号无法统一撤销、审计和配置，不能用于内部或客户数据。服务账号和 API key 有 owner、用途、轮换和最小 scope，不共享在聊天和仓库。

IDE/CLI 工具按仓库和目录授权，不默认读取整个主目录、浏览器配置或相邻项目。浏览器 Agent 的登录态、剪贴板、下载与上传权限独立控制。插件和 MCP Server 属于新的数据接收者与执行者，逐项准入。

员工离职或角色变化时撤销账号、token、插件、缓存和长期记忆访问，并确认供应商侧会话与数据处理。季度访问复核检查“仍需使用”，不是只确认账号存在。

### 五、Policy Enforcement 把规则放进真实路径

**策略执行（Policy Enforcement）**用身份代理、IDE 配置、DLP、网络出口、秘密扫描、仓库规则和调用网关在上传或执行前落实政策。培训告诉人为什么，技术控制防止一次疏忽立即外泄；两者缺一不可。

策略引擎读取主体、仓库、数据标签、工具、动作、目的和环境，返回允许、需要脱敏/审批或拒绝。密钥和高敏模式在发送前扫描；受限仓库关闭外部索引；高风险工具调用进入人工确认。日志只记录决策摘要，不复制被拦截的秘密。

DLP 不是万能正则。代码别名、压缩、截图和语义敏感内容可能漏检，公开示例也可能误伤。高风险边界采用默认拒绝与受控通道，检测结果有人复核并持续用真实误报/漏报校准。

### 六、上下文最小化同时改善成本与安全

只发送完成任务所需文件、片段和错误，不上传整个仓库“让模型自己找”。先用本地搜索和依赖图定位候选，再把带来源的最小上下文发送。秘密、个人信息、客户内容和无关日志在客户端或受控代理脱敏。

上下文窗口大不代表应该填满。无关内容增加泄露面、成本和模型混淆，也使审计无法解释某个文件为何被使用。工具应展示当前包含的目录/文件、允许排除，并在自动扩展前请求符合政策的授权。

生成的摘要和 embedding 也受原数据分类、目的和保留约束。对话“清空”可能只清界面，必须验证供应商删除语义和组织存储。

### 七、输出进入仓库前重新建立信任

AI 输出是候选代码、文档或命令。它需经过代码评审、测试、依赖与许可证审计、秘密扫描和领域责任人确认。批准使用某工具不代表批准它的每条建议，更不等于允许自动发布生产。

高风险操作分预览与执行，审批绑定具体 diff、参数和版本。Agent 自己生成测试不能完全证明自己正确，测试预言来自需求和独立规则。无法核验的引用、API 和安全结论标 unknown。

记录关键产物使用了哪个工具/模型和哪些人工检查，不保存无必要的完整提示或思维过程。追踪的目的是复现责任和变更，不是监控员工每句文字。

### 八、Exception Lifecycle 防止临时许可永久化

**例外生命周期（Exception Lifecycle）**定义例外的申请、风险接受、范围、补偿控制、到期、复审和关闭。例外必须具体到主体、工具、数据、用途和时间；“项目紧急”不是无限范围。

批准人具备相应责任，补偿控制可以是合成数据、隔离设备、禁日志、人工复核或受控出口。到期默认失效，系统自动提醒并阻断继续使用。续期需要新证据，不能复制原理由。

关闭时撤销权限、删除临时数据、归档最小证据并更新是否需要正式能力。统计重复例外可发现政策与实际工作的错位：要么建设合规路径，要么明确停止业务场景。

### 九、Shadow AI 要靠可用替代与最小检测治理

影子 AI 指绕过批准账号、工具或流程处理组织数据。原因可能是已批准工具不好用、审批太慢、需求未覆盖或认知不足。治理不能只惩罚个人，要分析系统诱因并提供低摩擦替代。

检测可结合 SSO、出口域名、终端软件、秘密扫描和仓库事件，但遵守员工隐私、目的限制和最小化。检测到异常先限制风险、保全必要事实、联系责任人，不在普通日志中复制其可能上传的内容。

误报处理有申诉和校准。公开仓库访问公共 AI 不应因域名命中就自动视为数据泄露；反之，允许域名中的个人账号也不能自动通过。身份、数据与用途共同决定。

### 十、日志、保留和审计同样受分类

AI 网关日志记录请求 ID、主体、工具/模型、数据分类、政策结论、token/费用、审批和结果类别。默认不记录完整 Prompt、代码、附件和模型输出；需要正文诊断时使用隔离、短期、受权存储。

供应商日志、组织代理、IDE 本地缓存和长期记忆可能有不同保留。目录中明确每处数据、删除机制和责任人。审计访问本身记录并限制，防止治理平台变成内部源码与客户信息的集中泄露点。

保留到期自动删除并可验证。备份恢复不能让已删除数据永久复活；导出和法律保留有单独流程。聚合指标不应能轻易还原个体敏感行为。

### 十一、指标衡量结果与风险而不是使用热度

采用率、token 和生成行数不能单独证明提效。比较同类任务的周期、返工、缺陷、评审时间、开发者体验和用户结果，并记录任务构成变化。风险指标包括阻断、例外逾期、未授权账号、敏感数据命中、输出逃逸和撤销时间。

指标要防激励扭曲。以生成代码量奖励会鼓励冗余，以 AI 使用率考核会迫使不适合任务使用，以零事故为目标可能压制报告。治理关注风险是否更早发现、恢复是否更快、合规路径是否足够可用。

分组报告遵守隐私和最小样本，避免把个人排名伪装成工程指标。定性反馈与抽样审查补充聚合数字。

### 十二、供应商变化需要持续复核

监测条款、训练使用、保留、模型、地区、子处理商、数据导出、插件生态和安全事件。把关键条件写成准入控制，变化触发暂停、降级或重新评审。不能依赖某位员工偶然看到公告。

建立退出能力：可导出必要配置、删除供应商数据、撤销身份、切换模型或退回无 AI 流程。专有记忆、索引和工作流要评估锁定成本。高价值任务保留人工可操作降级，避免服务中断使交付停止。

年度审查之外，对重大功能启用和组织数据范围扩展做事件驱动复核。本地模型升级同样可能改变遥测、许可证和硬件攻击面。

### 十三、事故响应从切断外发开始

发现误上传密钥、客户数据或敏感仓库时，先停止相关账号/连接和进一步同步，撤销密钥，保全最小时间线，联系安全、隐私、法律与业务 owner。不要把敏感正文复制到聊天、工单和普通日志“方便分析”。

确认发送了什么、到哪里、由哪个账号、供应商是否保留/训练、能否删除、谁受到影响。按合同与法规执行通知。恢复包含删除确认、token 轮换、策略修复、受影响制品复查和监测。

复盘从技术、流程和可用性找根因：为何分类没出现、为何控制可绕过、为何批准替代不足。行动项有 owner、期限和验证，不只再次培训。

### 十四、用演练证明治理可执行

设计公开代码、内部源码、客户个人信息、密钥和生产日志五类输入，经过企业 IDE、个人网页、受控 API、本地模型等不同工具。断言每个组合的允许/脱敏/审批/拒绝、日志、保留和输出复核符合矩阵。

注入个人账号、过期例外、代理绕过、供应商保留变化、员工离职和误上传，测量发现、阻断、撤销、删除和恢复。治理文档正确但实际代理未拦截，仍是不合格。

可参考 [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) 的 Govern、Map、Measure、Manage 结构和组织现行安全/隐私制度。NIST AI RMF 正在演进，供应商条款也持续变化；项目矩阵必须记录核验日期与责任人，不能把外部框架名称当作自动合规。

### 十五、用最小治理数据模型连接各项控制

团队至少维护 tool、toolVersion、owner、dataClass、purpose、allowedIdentity、region、retention、capability、policyVersion、exception、reviewDate 与 incidentLink 等实体关系。一次调用记录引用这些版本和决策结果，而不是复制政策全文。这样可以回答某供应商条款变化影响哪些团队、某例外允许了什么、某次输出由谁批准。

数据目录、身份系统、代理、仓库和供应商控制台之间要有对账。目录显示已禁止但 SSO 仍可登录、账号已撤销但长期 token 仍有效、例外到期但代理缓存未刷新，都是执行断裂。为同步建立延迟目标、失败告警和人工修复，不把控制面的一致性当作当然。

治理配置像代码一样评审、版本化、测试和回滚。规则变化先用历史样例回放，确认没有放行受限数据或大规模误伤合法任务；发布后观察阻断、申诉和事故。策略语言的超级管理员同样最小授权，避免治理者本身成为无约束数据访问者。

学完后，你应能为一项 AI 工具画出完整数据流，把每类数据映射到账号、地区、模型、保留、审批与技术控制，并用例外和事故演练证明规则真正生效。治理的成熟度不在政策页数，而在团队能否安全、可追溯地使用合适工具，同时快速阻断不合适的路径。

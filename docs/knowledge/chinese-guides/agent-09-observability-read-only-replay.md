# Agent 可观测性、关联追踪与安全回放知识点讲义

## AGENT-09 Agent 可观测性与回放

普通应用的一次请求往往经过几个稳定服务，Agent 运行却可能动态规划、调用多个模型与工具、等待人工批准、启动长任务并修改计划。只保存最终回答，会丢掉真正决定结果的因果链；保存完整对话和参数，又可能造成隐私、密钥与成本风险。Agent 可观测性的目标，是以最少但足够的结构化事实回答“哪一步发生了什么、依据哪个版本、谁批准、结果是否确认”，并在不重做副作用的前提下复查。

### 学习前先确认

- 直接前置：[AGENT-01 Agent 循环、规划、停止与恢复](../chinese-guides/agent-01-loop-planning-stopping-recovery.md#agent-01)用于理解 step、工具动作与终止状态；[OBS-01 前端可观测性、SLO、告警与隐私](../chinese-guides/obs-01-frontend-observability-slo-alerting-privacy.md#obs-01)用于理解日志、指标、追踪和用户体验信号。两者分别解释执行模型与观测模型，互不包含。

### 一、Distributed Trace 记录因果而不是聊天顺序

**分布式追踪（Distributed Trace）**用 trace 和 span 表达一次目标跨 Host、Client、Server、模型、工具与下游系统的因果关系。聊天消息的先后只能说明界面时间，不能说明哪个计划产生了哪个工具调用、一次重试是否属于同一动作、人工批准对应哪个参数版本。

根 trace 对应一次用户可识别的运行，span 对应模型推理、资源读取、工具调用、审批等待、结果校验或恢复。每个 span 记录父子关系、开始结束、状态、组件和版本；并行步骤共享父节点但有独立 span。业务 taskId、toolCallId、MCP request ID 与外部 operationId 作为属性关联，不应替代 trace/span 的结构。

运行跨越数小时或消息队列时，链路不一定是简单嵌套。使用 span link 连接异步消费、恢复尝试和外部任务，保留“由谁触发”的证据。把所有步骤强行塞进一个长 span 会失去等待、重试和所有权转换。

### 二、Context Propagation 要跨边界且防伪造

**上下文传播（Context Propagation）**是在进程、网络和异步队列间携带 trace 标识与采样决定，使下游事件可以回到同一因果链。HTTP 可使用 W3C `traceparent`，队列与任务句柄要保存等价字段；创建异步工作时记录父上下文，恢复时重建 link。

来自公网或第三方的 trace 头是不可信输入。入口校验格式、长度和采样标志，可生成新的内部 trace 并把外部 ID 作为受限关联，而不是允许攻击者覆盖内部标识或制造任意大量采样。向不受信下游发送时，也要决定是否剥离内部追踪信息。

Baggage 会随请求传播任意键值，极易把用户 ID、租户、密钥或文件名带到第三方。只允许经过白名单、低敏且确有诊断价值的字段；身份和授权始终从安全上下文读取，绝不能信任 baggage 决定权限。

### 三、建立 Agent 事件词汇表

不同组件若都写一条 `done`，无法区分模型生成完、工具请求已提交还是业务结果已确认。先定义事件类型与状态：run created、plan proposed、step started、resource read、tool requested、approval requested、approval decided、tool accepted、tool result observed、result verified、step retried、run stopped。

事件采用稳定 Schema，至少包含时间、run/step/attempt、trace/span、组件版本、主体的匿名引用、工具名与版本、结果类别和资源版本。自然语言摘要用于人读，结构化字段用于查询。事件是已发生事实，不应保存模型的隐式思维过程，也不能把“计划执行”写成“已执行”。

状态转换要有不变量：未批准不能进入高风险执行，未知结果不能写成失败，已取消的旧 attempt 不能覆盖新结果。观测系统可以独立检查这些不变量，及早发现编排器错误。

### 四、日志、指标与追踪各回答不同问题

日志保存离散事实和错误上下文，适合查一条拒绝原因；指标聚合成功率、延迟、成本和人工介入，适合发现趋势；追踪连接一次运行的因果链，适合定位慢点与断链。三者通过 trace、版本和稳定维度关联，但不应复制同一份完整提示。

高基数的用户、请求和文件标识不适合直接做指标标签，否则成本与查询压力失控。它们可存为受控日志字段或 span 属性，并用哈希/引用限制暴露。指标标签使用工具类别、错误代码、模型族、环境和发布版本等有限集合。

告警基于用户结果与系统预算，例如已确认成功率下降、未知副作用结果上升、审批等待超 SLO、成本异常和 trace 断链比例，而非“日志条数变多”。告警必须指向可查询的版本与代表 trace。

### 五、Data Minimization 在采集之前发生

**数据最小化（Data Minimization）**要求只采集实现明确诊断目的所必需的字段，并在数据进入遥测管线之前脱敏、截断或替换为受权引用。先记录完整参数再在查询界面打码，原文已经进入日志、备份与导出，不算安全。

字段按默认允许列表采集：工具名、参数 Schema 版本、大小、受限摘要、错误码、延迟和结果状态。密钥、token、支付数据、完整个人信息、用户文件和整段 Prompt 默认不落盘。确需诊断正文时，使用短期、隔离、显式授权的受控存储，遥测只保存引用和到期时间。

结构化脱敏优于正则扫字符串。执行器知道字段语义时，把卡号变成后四位，把路径变成根内相对标识，把文本变成长度与哈希。未知自由文本按高敏处理。错误对象也要过滤，第三方堆栈和 URL 可能携带查询密钥。

### 六、身份、权限与租户隔离延伸到遥测

能运行工具不代表能读取它的遥测。开发者、客服、安全、审计和用户拥有不同目的与字段权限；查询需要当前身份、租户、工单目的和时间范围。跨租户 trace 即使 ID 相同也不能合并展示。

日志索引、对象存储、备份和导出都应用相同分类。保留期按诊断、合规和成本决定，短期细粒度 trace 可到期转为聚合指标。删除用户数据时，能追踪哪些遥测包含可识别引用，并执行删除或不可逆去标识化。

紧急调试开关有审批、范围、到期和审计，不能永久开启“全量日志”。调试结束后验证开关关闭、缓存和导出清理、访问记录完整。观测平台本身是高价值攻击面，需要最小权限和异常访问告警。

### 七、采样必须保住失败与少数群体

固定百分比头采样简单，却可能丢掉罕见错误、低流量租户和长尾模型。可在入口做低比例头采样，再由尾采样保留错误、超时、高成本、审批拒绝、版本新发布和安全事件。采样策略与版本一起记录。

不能只保留成功 trace 来展示系统健康，也不能为每次失败保存全部正文。失败保留的是结构、分类和必要证据。对高流量工具设置每租户与每错误类别的配额，避免攻击者通过制造失败耗尽遥测预算。

采样后的指标需明确分母和估算方法。用被采样 trace 数直接计算业务成功率会偏差；关键结果应由独立计数器或业务状态提供，trace 用于解释样本。

### 八、版本信息决定记录能否解释

一次 Agent 运行同时依赖应用版本、编排规则、模型、提示、工具契约、策略、数据快照和 SDK。缺少版本时，同一输入今天无法解释昨天的不同结果。遥测保存稳定版本或内容哈希，不必复制全部内容。

外部模型名称可能指向滚动版本，要记录供应商返回的实际标识与调用参数；工具列表会随权限和 TTL 变化，要记录当时候选集合摘要；审批绑定规范化参数哈希和资源版本。这样才能判断错误来自选择、执行、数据变化还是发布。

版本字段也支持比较发布前后。把错误率按模型与工具契约版本分组，避免把同一时段流量构成变化误判为版本回归。若版本无法获得，明确标记 unknown 而不是填当前值。

### 九、Read-Only Replay 解释过去而不重做过去

**只读回放（Read-Only Replay）**将已记录事件、输入摘要、版本化配置和工具录制结果重建为时间线或隔离评估环境，默认绝不调用真实写工具。它回答当时看见什么、为何选择、哪里断链，并允许对新规划器进行离线比较。

回放器只读取冻结 artifact，Tool adapter 返回已录制结果或明确 `REPLAY_DATA_MISSING`。遇到发送邮件、退款、删除或写文件步骤，显示参数摘要与已记录结果；任何真实执行尝试都由运行隔离层拒绝并记录。只在另一个明确授权的测试环境中，才能用合成数据执行替身。

回放不是精确复现随机模型的保证。缺失供应商版本、时间敏感数据或外部结果时，要标出不可重现区段。目标是验证决策链和不变量，而不是伪造一个流畅的相同回答。

### 十、确定性重建与反事实评估分开

确定性重建按原事件展示已发生路径，不改变输入；反事实评估把同一冻结输入交给新提示、模型或路由器，比较候选差异。两者必须用不同 run 类型和界面标识，防止新结果被误认成历史事实。

反事实评估只能使用允许保留的数据，工具由录制件或模拟器替代。比较选择准确率、停止条件、成本和安全拒绝，不能把“更像人工答案”当唯一指标。新策略提出原运行没有的副作用时，评分为未执行候选。

回放产物包含源 trace、数据版本、策略版本、运行模式、缺失项和副作用计数。副作用计数必须为零；若不为零，回放环境本身就是事故。

### 十一、关联断裂和重复事件需要显式处理

服务忘记传播 `traceparent` 时，下游 span 会成为孤儿。可以用受控 request ID、时间和 operationId 辅助关联，但应标记推断置信度，不能悄悄伪造父子关系。修复传播后用端到端 trace 证明链路闭合。

网络重试可能让同一事件写入多次。遥测接收端用 eventId/spanId 与版本幂等去重，同时保留不同 attempt。只按时间文本去重会吞掉真正重试。乱序事件按逻辑序号和发生时间重排，接收时间只用于诊断传输。

时钟偏差会制造负延迟。跨主机追踪依赖单调时钟测 duration，并记录时间同步状态；界面可以校正展示但保留原时间。诊断系统的问题不能被误归因到 Agent。

### 十二、从用户结果向后定位

排障先找到用户可见请求或业务 operation，再进入对应 trace；确认终态是成功、失败、取消还是未知，然后沿关键 span 找首个语义异常，而不是盯着最后一条错误。外部 500 可能只是后果，真正原因可能是错误工具选择、审批版本过期或输入被截断。

对慢运行拆分模型首 token、完整生成、工具排队、执行、审批等待和结果验证。总耗时下降不一定体验改善，可能是提前失败。关联用户端性能和业务成功，才能区分快失败与真优化。

一次有效事故证据包括代表 trace、版本差异、触发条件、被排除假设、修复和同类回放结果。仪表盘截图只能说明现象，不能独立证明因果。

### 十三、成本可观测也要按确认结果计量

记录模型输入输出量、缓存、工具费用、重试、人工等待和存储成本，并按 root run 与 step 归属。多个重试若共用同一业务动作，账本仍保留各次消耗，但结果成功只计一次。

单位成本应除以已验证完成的用户任务，而不是请求数或生成 token。取消、拒绝、未知和人工接管分别统计。成本异常结合模型、上下文和工具版本定位，避免简单地把 token 高视为浪费。

遥测本身也有预算。属性爆炸、无限保留和重复正文会让观测成本超过业务价值。定期查询字段使用率，删除没有诊断或合规用途的采集。

### 十四、用故障注入验证观测系统

主动制造错误 trace 头、断开的父 span、重复事件、超长工具结果、敏感字段、下游超时、审批拒绝、工具未知结果和回放写入尝试。断言不仅看事件存在，还看关联正确、秘密未落盘、访问受限、保留生效和恢复建议准确。

在版本灰度中抽取同一任务的旧新 trace，确认差异能归因。灾难恢复后验证 trace 索引、原始对象和权限映射一致；如果恢复让已删除数据重新出现，备份流程不合格。

MCP 2026-07-28 已将 Logging 标为弃用方向，新系统宜用 stderr 承载 stdio 诊断、用 OpenTelemetry 承载结构化观测。可结合 [MCP 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)、[OpenTelemetry 上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/) 与 [W3C Trace Context](https://www.w3.org/TR/trace-context/) 核验当前机制。

学完后，你应能设计一条从用户目标到工具结果的可关联事件链，说明哪些字段必须在采集前脱敏、哪些指标需要独立分母，以及为什么回放默认只能读取录制结果。好的可观测性不会把所有内容都存下来，而是以受控证据让失败、权限和结果状态可解释。

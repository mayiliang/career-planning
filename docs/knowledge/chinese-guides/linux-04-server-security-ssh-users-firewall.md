# Linux 服务器安全基线知识点讲义

## LINUX-04 服务器安全、SSH、用户与基础防护

服务器安全不是安装一次工具或把 SSH 端口改掉，而是持续缩小谁能到达、谁能登录、登录后能做什么、软件如何更新，以及异常如何被发现和恢复。安全变更还必须避免把维护者锁在门外：每次 SSH、防火墙或 sudo 调整都要有语法验证、第二会话和控制台回退。本讲建立可审计、可复核的最小基线。

适用场景例如新建云主机、接管旧服务器、开放部署账号、轮换密钥和收紧公网端口；临时实验机也应按所持数据和凭据选择相应基线。

### 学习前先确认

- 直接前置：[LINUX-01 文件系统、权限与安全命令](../chinese-guides/linux-01-filesystem-permissions-safe-commands.md#linux-01)。本讲直接使用用户/组、目录权限、密钥文件和安全变更。
- 直接前置：[SEC-01 XSS、CSRF 与信任边界](../chinese-guides/sec-01-xss-csrf-trust-boundaries.md#sec-01)。本讲沿用最小信任、输入边界和分层控制。

### 一、先定义资产、主体和入口

记录主机用途、数据分类、网络区域、公开服务、管理入口、账号来源、依赖环境和恢复责任。临时测试机也可能持有源码、token 和云权限，不因“不是生产”就无风险。

列出人与机器身份：管理员、部署服务、应用、监控、备份和第三方支持。每个身份写登录方式、允许动作、凭据生命周期、owner 与撤销路径。共享 root 密码无法追责且撤销成本高。

先测当前监听和外部暴露，再设目标基线。安全组、主机防火墙、容器发布和应用绑定共同决定入口；只看一层会漏暴露。

### 二、最小权限是持续约束

**最小权限（Least Privilege）**给主体完成当前职责所需的最少权限、范围与时间。应用不用 root，部署账号不能读取业务数据，监控只读指标，临时支持权限自动到期。

按服务建立专用用户/组，禁止无登录需求账号获得 shell。目录 owner/group 和 systemd User/Group 对齐，敏感配置最小可读。不要用世界可写目录解决部署。

权限审查既看授予，也看实际使用和继承。离职、项目结束、密钥轮换和角色变化应触发撤销；长期未用权限进入复核。

### 三、SSH 是加密通道，不是完整授权模型

**安全外壳（Secure Shell）**提供加密连接、服务器身份验证和用户认证，也可转发端口。它不能自动保证账号最小权限、客户端安全或命令合法；登录后的授权仍由用户、组、sudo 与系统策略决定。

客户端首次连接必须核对 host key 指纹，避免盲目接受变化。host key 轮换提前发布新指纹并保留重叠窗口；意外变化按潜在中间人或重装调查。

优先个人密钥或集中身份，禁共享私钥。私钥有口令/安全硬件和文件权限，agent 转发谨慎使用。服务账号使用受限 key、来源和命令，不给通用交互 shell。

### 四、sshd 配置从允许对象收敛

用 `AllowUsers`/`AllowGroups` 等限制可登录主体，禁用不需要的 root 直接登录和密码认证；是否启用 MFA/证书按组织能力与威胁模型。限制认证尝试、空闲会话和转发能力。

配置可能由 include 和 Match 块覆盖。用 `sshd -t` 验证语法，`sshd -T`（必要时带连接条件）查看有效值，不能只读主文件。版本升级前核对弃用与默认变化。

应用顺序：保存备份和控制台路径，保持已登录会话，打开第二会话验证新配置，再关闭旧会话。设置自动回退窗口；不要一次同时改 SSH、用户和防火墙后失联。

### 五、authorized_keys 也能做最小授权

每人/服务独立 key，注释包含 owner 和到期。可限制来源地址、禁止 agent/端口/X11 转发，或绑定固定 command。注意不同 OpenSSH 版本支持和语法。

`.ssh` 和 `authorized_keys` 的 owner/mode 必须符合严格模式，父目录过宽也可能被拒。排障查认证日志和有效配置，不直接放开权限。

撤销要从所有节点和自动化库存删除，并查是否仍有证书、跳板或缓存访问。轮换先新增并验证新 key，后移除旧 key，避免中断。

### 六、sudo 只授权必要命令

**sudo 策略（Sudoers）**将普通身份临时映射为受控高权限命令，并留下审计。使用 `/etc/sudoers.d` 和 `visudo` 验证，按绝对命令、参数/包装器与目标用户限制。

很多看似窄的命令可逃逸：编辑器、解释器、包管理器、能加载插件或写任意路径的程序可能获得 shell。不要把通配参数和用户可写脚本放进授权链。优先提供经过审计的根权限小工具，校验输入和路径。

避免普遍 NOPASSWD；服务自动化若需要，绑定专用账号、固定命令、最小文件权限和可撤销凭据。定期用 `sudo -l` 检查实际权限与日志。

### 七、防火墙按服务与来源最小开放

主机防火墙默认拒绝不需要入站，只开放业务端口和管理来源。SSH 可限管理网/VPN；数据库只在内部网络。出站也可按敏感程度限制，减少被攻陷后的控制与外泄。

**纵深防御（Defense in Depth）**要求云安全组、主机防火墙、服务绑定和应用认证互相补充，而非认为某一层足够。规则需同时检查 IPv4/IPv6、TCP/UDP和实际接口。

变更前保存规则、确认控制台、加带超时自动回退，先在第二会话测试。不要用关闭防火墙做长期诊断；最小临时规则应有 owner 和到期。

### 八、补丁与版本生命周期

维护 OS、内核、OpenSSH、运行时和代理的支持状态。安全更新分测试、分批和回滚，但不能无限拖延。记录当前版本、更新来源、重启需求和维护窗口。

自动更新适合部分补丁，关键基础设施需验证兼容与重启。内核/库更新后运行进程可能仍加载旧版本，使用工具或维护流程识别需要重启的服务。

软件来源限制到受信仓库，验证签名；不在服务器随意 curl 管理脚本。移除不用的包和服务，缩小攻击面。

### 九、服务隔离与 systemd 硬化

每服务专用用户、工作目录和可写路径。systemd 可限制能力、文件系统写入、私有临时目录、设备和网络，逐项测试后启用。硬化评分只是提示，不能代替业务验证。

服务只监听需要地址，管理端点不对公网。秘密由受控存储以最小权限提供，不写 unit、命令行或日志。环境变量也可能被诊断读取，应最小化。

应用被攻陷时，隔离应限制其读其他服务配置、修改二进制和控制宿主。容器不是自动安全边界，宿主权限和挂载仍需审查。

### 十、账号与认证生命周期

人类账号个体化，服务账号不可交互；禁止默认和无 owner 账号。密码策略若仍使用密码，应结合限速/MFA和已泄露密码检查，而非只要求复杂格式。

定期审计 `/etc/passwd`, 组、sudo、SSH key、最近登录和失败登录。UID 0 账号、可写 shell 配置、异常 home 权限和过期 key重点检查。

离职/事故撤销从身份提供方、VPN、跳板、服务器、sudo、CI和云权限全链执行。只删一个 authorized_keys 不一定终止已有会话或其他通道。

### 十一、日志、审计与时间

收集 SSH 成功/失败、sudo、账号/组变化、服务启动、内核/防火墙和关键文件修改。日志集中、限制写入、设置保留和容量；攻击者获得 root 后本机日志不再完全可信。

时间同步确保跨机事件可关联。告警关注异常来源、爆破、首次登录、权限提升、规则变化和日志中断。减少高噪声，否则真正事件被忽略。

日志不记录私钥、密码和完整 token。审计访问本身也需权限与记录。

### 十二、暴力尝试与自动封禁

公网 SSH 会收到扫描。密钥认证、来源限制和最小账号是首要；速率限制/封禁是补充。自动封禁需防误伤共享 NAT 与管理员，并有控制台解除路径。

改端口可减少日志噪声，不是安全控制。攻击者可扫描端口；不要因此放松认证与授权。

分析失败尝试时区分无效用户、错误 key、策略拒绝和合法操作错误。保存来源和时间但遵守隐私/保留政策。

### 十三、备份与恢复是安全控制

勒索、误删和被攻陷更新都需要离线/不可变备份。备份包含配置、数据、密钥恢复流程和基础设施定义，但访问权与生产分离。

定期恢复到隔离环境，验证完整性、权限和应用可用。只看备份任务成功日志不足。记录 RPO/RTO、owner和最后演练。

备份也含敏感数据，需加密、最小访问、保留和安全删除。攻击者不应能用生产凭据同时删除所有备份。

### 十四、变更管理避免自锁

高风险变更拆分：先加新访问并验证，再撤旧；先允许精确规则，再收紧宽规则；先部署可回退配置，再重载。每步有观察和停止条件。

保存 out-of-band 控制台、救援账号或云串口，但同样保护和审计。自动回退定时器在确认成功后取消。不要把救援通道永久开成绕过基线的后门。

配置纳入版本控制但不含秘密，测试语法与策略。手工紧急修复事后回写，防止下一次部署覆盖。

### 十五、应用层仍需自己的安全

主机防火墙不能替代应用认证授权，TLS 不能阻止业务越权，SSH 安全也不能修复 XSS。明确主机基线与应用、云、容器、数据库控制的责任边界。

反向代理设置请求上限、超时和安全头时需与应用语义一致。健康端点公开最小信息，管理端点独立保护。生产 debug 和目录索引默认关闭。

安全控制失败要安全：身份服务不可用时不自动放行，日志故障不无限填磁盘，防火墙重载失败保留旧规则。

### 十六、基线验证与漂移

把目标账号、端口、sshd 有效值、sudo、包版本、服务、文件权限和日志策略写成机器可查基线。定期比较实际状态，例外有 owner、理由和到期。

验证从未授权视角进行：外部扫描开放端口、无权账号尝试登录/执行、应用用户尝试读其他秘密、过期 key 尝试认证。拒绝结果与允许结果都留证。

配置管理只能应用期望状态，也可能把错误快速扩散。先在测试/小批验证，设置并发和回滚，监控应用业务健康。

### 十七、事件响应准备

发现可疑登录时，先保护证据、限制影响、撤销相关身份与会话，再判断重建或清理。已获得 root 的主机通常不能仅改密码就重新信任；从可信制品重建并轮换可达秘密更可靠。

保存登录、进程、网络、文件变化和云审计时间线，最小化对现场的破坏。通知范围按数据和合规要求确定。不要在聊天中传播私钥或完整日志。

恢复后验证 host keys、应用制品、配置、账号和下游凭据，监控再次活动。复盘控制缺口和发现时间。

### 十八、云主机与跳板边界

云安全组、实例元数据、IAM 角色、串口控制台和快照是额外管理面。限制元数据访问与角色权限，避免被攻陷进程取得广泛云凭据。控制台权限可绕过 SSH，必须与 SSH 同等或更严格审计。

经跳板登录时保留最终用户身份，不让所有人共享同一转发账号。端口转发和 agent forwarding 按需禁用；会话录制若启用，处理秘密与隐私。跳板失效要有受控备用路径，但不能永久公开所有主机 SSH。

镜像或快照可能含 host keys、日志和秘密。复制到新环境前清理或轮换机器身份，限制共享和保留。基础镜像有版本、补丁和来源证明。

### 十九、Web 应用部署的专门检查

反向代理与应用使用独立用户，静态制品只读，可变上传在独立路径且禁止执行。TLS 私钥只对代理可读，应用无需访问。部署账号可切换发布链接和重启特定 unit，但不能改 sshd 或 sudo。

Node 等服务不以开发模式和调试 inspector 对外运行。源映射、错误页和目录列表按环境控制，健康端点不泄露依赖地址。运行时与包管理器不由应用进程自行升级。

发布后从外部验证端口、TLS 和应用，从服务用户验证只读与写目录，从无权用户验证拒绝。回滚不恢复已撤销密钥或旧不安全基线。

每次复核都从当前实际状态重新取证，不用上月清单替代。

### 二十、练习与最终复核

在隔离主机创建 deploy 用户，密钥登录、限制组和仅允许一个发布包装命令；SSH 仅管理网可达，Web 端口对外。保留控制台和旧会话，语法验证后用第二会话测试授权/拒绝矩阵。

注入错误 key 权限、过宽 sudo、IPv6 漏开放、失效新 key 和错误 CIDR，按证据恢复。记录 `sshd -T`, `sudo -l`, 监听/防火墙、认证日志、补丁、文件权限和回退时间线。

最终回答：谁可达、谁可登录、能做什么、凭据何时撤销、哪些服务/端口存在、补丁和日志是否有效、失联如何恢复、入侵如何重建。安全基线的高级性在于每项允许都有必要性、每项拒绝可验证、每次变化可回滚，且多层控制不会依赖一个永不失败的假设。

# 第 10—12 域中文学习讲义

本讲义是职业表达和 AI 原生前端中英文一手资料的中文学习载体。它不替代厂商 API 的版本核验；遇到字段、限额、价格或协议版本，应回到知识点列出的官方页面复核。每节均给出可独立学习的定义、机制、反例/边界和验证任务。

## CAREER-01

**定义。** 项目表达不是把经历按时间复述，而是以“要解决的问题—约束—本人决策—可核验证据—结果—复盘”说明可迁移的工程判断。STAR 可用来组织背景、任务、行动、结果，但不能用它掩盖个人责任或因果关系。

**机制。** 先列证据表：需求/告警/PR/指标的时间和链接；再把每一项行动连接到一个约束与一个取舍；最后写结果口径（基线、观察窗口、样本和归因限制）。没有量化指标时，使用可观察证据，如发布记录、复现步骤或评审结论，并明确不能证明的部分。例：将“优化性能”改为“把首屏 LCP 的 p75 从 3.4 s 降至 2.5 s，实验期为两周；我负责拆分路由和验证埋点”。反例是把团队结果写成“我提升 30%”。

**边界与验证。** 预测、相关性和因果性必须分开；涉及保密数据时用脱敏范围和可复核人替代原始数据。用一份匿名证据包写 250 字复盘，另附“主张—证据—限制”表；让评审连续追问五次，所有答案都必须能回指表中材料。

**证据链的组装步骤。** 先把题目给出的需求片段、故障记录、设计决定、提交或评审记录、发布记录与指标快照按时间排序，并为每项材料标注“它能证明什么、不能证明什么”。然后只选择一个待说明的问题：例如交互延迟过高、发布失败率偏高或维护成本失控。写清当时可见的约束、候选方案和停止条件，再把本人的动作拆成调查、决策、实施、验证四类。每个动作都要连接到一个可观察变化；没有连接的工作量不能自动算作结果。最后填写“主张—证据—限制”表：主张使用可证伪句子，证据给出题目材料中的编号或时间点，限制写明样本、窗口、共同贡献者和仍未排除的解释。

**贡献与指标口径。** 团队交付中要区分“我决定”“我实现”“我协助验证”和“团队共同完成”。如果题目只给出团队结果，就说明本人可证明的环节，不能反推个人独占贡献。指标至少记录定义、基线、观察窗口、样本量和数据来源；平均值不能替代题目要求的分位数，实验室结果不能冒充用户现场结果，发布后的相关变化也不能直接证明因果。无法量化时可使用可观察证据，例如某失败路径从不可复现变为有稳定复现步骤、某人工检查被确定性门禁替代，或评审记录确认一项边界被关闭，但必须明确证据强度。

**反例与受限排错。** 常见失败包括只讲技术名词、不说问题与约束；把采用某框架写成结果；省略失败尝试以制造线性成功故事；把预测收益写成已经发生；面对冲突证据时临时改变指标口径。受限排错时，评审可注入三类矛盾：提交时间晚于宣称的上线时间、指标改善早于本人动作、同一结果还有并行变更。答题者必须暂停不受支持的主张，列出至少三项可检验假设，指出补充证据，并将结论降级为与现有材料相符的表述，不能编造缺失事件。

**可复核练习。** 输入固定为匿名证据包；输出包括五分钟陈述、最多六行的“主张—证据—限制”表、一项失败尝试和一项后续改进。检查者随机抽取任一主张，应能在一分钟内定位证据；连续追问“为什么是你”“为什么是这个方案”“结果如何测量”“还有什么解释”“下次会改什么”时，答案必须保持时间、角色和指标口径一致。若出现无来源数字、把团队结果归为个人、隐去反证或把相关性说成因果，则本次不能通过；修订后应使用同一证据包再次复述并逐项核对。

## CAREER-02

**定义。** 架构图是服务于一个问题的模型，而非目录树。Context 图说明谁与系统交互；Container 图说明可独立运行/部署的数据或计算单元；Component 图说明一个容器内的职责和依赖。时序、部署图分别补足动态调用和运行位置。

**机制。** 先从题目给出的路由、身份、数据和外部依赖建立边界表；依次画人/外部系统、容器、关键组件；每条箭头标明方向、协议、数据或命令。再用一张时序图验证关键失败如何传播，并用 ADR 记录“候选方案—取舍—决定—后果”。例：浏览器经 API 服务读取知识库，认证服务仅签发令牌；不要把 `components/` 文件夹画成一个服务。反例是把数据库和缓存都标为“后端”而不画信任或故障边界。

**边界与验证。** 图应与代码/部署清单在同一提交中变更；未知信息必须标作假设。给定一个新增外部支付系统，更新三层图和一张时序图，说明其权限、超时、降级及受影响的箭头；评审应能用图定位实现入口。

**建模步骤。** 从一个可回答的问题开始，而不是从画图工具开始：例如“外部身份服务超时，谁受影响、在哪里降级？”第一步列出系统外的用户、运营者和外部系统，并写明它们信任什么凭证；第二步找出可独立部署或扩缩容的容器，标注数据存储、队列和同步/异步关系；第三步只挑会影响该问题的组件，给出输入、输出和失败语义；第四步用时序图穿起成功、超时和补偿路径。每个元素至少有名称、职责、技术或协议和所有者，箭头必须描述“谁以什么方式向谁传什么”，不能只画无标签连线。

**常见失败。** 把前端路由当作安全边界会遗漏服务端授权；把数据库画在容器内部却不标出备份、访问控制和故障域，会掩盖数据风险；组件图塞进全部类名则失去决策价值。图中某 API 是“同步调用”而实现实际入队异步处理时，容量、超时和重试结论都会错。评审应逐项核对：新外部系统的 token 从何处签发、敏感数据是否越过边界、下游不可用时用户看到什么、部署变更影响哪些容器。把这四项写进 ADR 的后果与回滚条件，才算图文一致。

## CAREER-04

**定义。** 事故处置的目标是先安全地恢复用户任务，再学习如何降低复发风险；无责复盘研究系统条件和决策信息，不把“某人粗心”当根因。

**机制。** 告警进入后，按影响、紧急度和范围定级，指定唯一指挥、操作、沟通、记录角色；记录事实时间线，先遏制/缓解，验证技术指标、核心任务和数据完整性，再在观察窗口后关闭。复盘把事实、假设、根因和促成因素分层；每个行动项都有 owner、期限、优先级、验收证据与逾期升级。例：回滚使 5xx 降为零但下单仍失败，不能宣布恢复。反例是调查期间不更新用户状态，或承诺没有证据的 ETA。

**边界与验证。** 题目提供的日志不能补造成不存在的事实。用一份零散告警包完成 10 分钟模拟：输出定级依据、角色、两次状态更新、时间线、根因树和行动台账；注入错误定级和交接中断后，证据应能显示纠正过程。

**处置步骤。** 接警先记录发现时间、受影响任务、范围和证据来源，建立一个可调整的初始严重度；指挥官只负责目标、优先级和升级，操作负责人实施止损，沟通负责人对内/对外按约定节奏更新，记录员不替代任何人的决策。先选可逆、低风险的缓解动作，例如关闭异常开关、限流或回滚；每个动作记录执行人、时间、假设和结果。恢复后不能只看告警消失：要分别执行核心用户路径，检查错误率/延迟和关键数据一致性，并在观察窗口中确认没有反弹。

**复盘与反例。** 事实时间线只写可证明的事件；“可能因缓存过期”属于假设，需列出验证方法。根因树从触发条件、检测缺口、缓解困难和组织条件拆分，避免把“值班同学失误”写成终点。反例包括：两个指挥官给出相反命令、状态页承诺精确 ETA、回滚后接口绿了但支付任务仍堆积、交班不交待未关闭的风险。行动项不是“加强测试”，而应如“为支付回调增加幂等回归用例，owner A，周五前完成，以重复回调 0 次作为验收”；逾期需升级。演练时要求观察者用台账复算定级、检查每次更新的已知/未知/下次时间，并在复盘后验证同类告警的检测或恢复时间下降。

## CAREER-05

**定义。** 代码评审是以风险和可维护性改善变更，而不是用个人风格赢得讨论。评论必须指出受影响行为、证据、严重度和可行下一步。

**机制。** 先读需求、测试和 diff，按安全/数据损失/功能/性能/可维护性分类；`必须修改` 要说明会造成的可复现风险，`建议` 可留给作者取舍，`疑问` 只用于信息不足。分歧时记录目标、候选方案、证据和决定，必要时升级给代码所有者。例：“该分支把未授权租户的 ID 直接传给查询，补上服务端 owner 条件并加跨租户测试”优于“这里写得不好”。反例是把格式偏好标为阻塞，或只给“LGTM”。

**边界与验证。** 不凭感觉声称性能或安全问题。对一份带缺陷的 PR 写至少五条带文件位置、风险和验证方式的评论，区分三种严重度；作者反驳一项后，提交更新的证据或撤回评论，并保留决策记录。

## CAREER-06

**定义。** 面试、教学和技术影响力共同考察把准确模型交给不同受众并促成可验证行动的能力，而非背诵术语或压倒听众。

**机制。** 面试回答先澄清问题和边界，再给模型、取舍、验证和未知项；教学按“已有知识—目标—示例—练习—反馈”组织，先给一个反例暴露误解。影响力依赖公开问题、方案比较、决策记录和后续指标，不等同于职位权力。例：解释缓存时先画命中/失效路径，再让听众推演租户串数据。反例是把“我们一直这样做”当证据，或在不会时编造实现细节。

**边界与验证。** 同一事实面向管理者只谈影响和选择，面向工程师补足机制，但不能改变结论。完成一段 10 分钟教学录屏和一道迁移题；受众独立完成后，记录错因、修改材料，再用模拟面试的评分表（准确性、边界、证据、沟通）复测。

## VUE-09

**定义。** 服务器状态来自远端、会过期并具有请求/错误/缓存生命周期；它与组件局部状态、URL 状态和 Pinia 中的客户端领域状态不同。TanStack Query 通过稳定 query key 将“同一份远端资源”的读取、缓存和失效连接起来。

**机制。** query key 必须完整包含资源身份、筛选、分页和租户等影响结果的输入；查询函数返回真实错误并遵从取消信号。写入时选择精确更新缓存或使相关 key 失效；乐观更新先保存快照，失败则只回滚相应版本。例：详情 `['knowledge', tenantId, id]` 与列表 `['knowledge', tenantId, filters]` 分开；反例是把 API 响应复制进 Pinia 后两处各自修改。

**边界与验证。** 缓存命中不是授权，服务端仍需鉴权；全局失效会制造重复加载。为筛选切换、并发乐观写入、失败回滚、用户切换和取消创建测试，检查每次失效仅触及预期 key，且 UI 有加载、错误和重试路径。

**实现步骤。** 先给每个读取写出 key 函数和输入类型；key 中包含所有决定响应的字段，但不放临时 UI 引用。查询函数接收取消信号，返回服务端规范化数据，错误状态交给 Query 的重试/错误边界而不是吞掉。写入前决定一致性策略：返回完整实体就精确 `setQueryData`，影响集合但无精确值则按前缀失效；乐观写入时依次取消相同 key 的在途请求、保存快照、临时更新、失败回滚、完成后再核对。分页列表、详情和计数是不同缓存，不能用一个万能 key。

**反例与检查。** `['items']` 被两个租户共用会串数据；把 `refetch()` 放进 `watch` 且参数不稳定会造成请求风暴；将查询结果复制到 Pinia 后再乐观修改会制造双数据源。可验证练习：提供两租户、两个筛选条件和一个失败 mutation 的假 API，抓取网络和缓存快照；断言切换筛选不会显示旧数据、失败后仅回滚自己的变更、登出后旧租户 key 被清理、服务端拒绝访问时缓存不显示受保护内容。提交 key 表、测试结果及一次从错误 UI 恢复的录屏。

## VUE-11

**定义。** Nuxt 的 SSR 先在服务端生成可访问 HTML 和 payload，随后浏览器 hydration 接管交互；SSG、SSR 与混合路由是对渲染时机和缓存边界的选择，不能只看首屏速度。

**机制。** 页面以 `useAsyncData`/`useFetch` 用稳定 key 获取数据，服务端路由承载秘密逻辑；客户端导航复用 payload 或按 key 重新取数。可缓存数据应明确用户/租户、参数和失效时间；服务端请求状态不得泄漏到下一请求。例：公开知识详情可静态预渲染，带登录自评的部分在服务端按会话获取；反例是在模块顶层缓存当前用户或在服务端/客户端产生不一致的随机值。

**边界与验证。** hydration 警告表明服务器与客户端输出不一致，不能忽略；浏览器路由守卫不替代服务端授权。迁移一个列表/详情切片，抓取首屏 HTML、payload、客户端导航和错误页；分别注入重复取数、错缓存键、未授权和 hydration mismatch，提交修复前后网络记录与构建产物大小。

## AIAPP-01

**定义。** 模型运行时是应用把受信指令、用户输入、允许的工具和有限上下文转换成一次可追溯请求的边界层；它不是把厂商 SDK 直接暴露给浏览器。

**机制。** 服务端先认证并选择允许的模型/能力，构造有版本号的 system/developer 指令、用户消息和受限工具；按 token 预算裁剪低优先级上下文，发送带幂等请求标识的调用；把响应归为成功、可重试暂态、拒绝、配额或未知结果。Provider adapter 只统一本应用需要的能力，保留模型/提示版本与原始错误分类。例：检索片段作为“数据”附入上下文，绝不能提升为 system 指令。反例是把 API key、全量聊天记录和任意模型名交给前端。

**边界与验证。** `temperature`、`top_p` 等参数是模型特定控制，不能承诺跨供应商语义相同。用伪 Provider 测试：验证角色顺序、超预算裁剪、429 分类、未知结果不盲重试，以及灰度失败可回滚到上一提示版本。

## AIAPP-02

**定义。** 流式响应把尚未完成的结果以有序事件送到界面；界面必须把“临时增量”和“最终可保存结果”分开。

**机制。** 服务器发出开始、文本增量、结构块/工具、完成或错误事件；客户端以 UTF-8 增量解码，按请求 ID 与序号合并，节流渲染，取消时中止传输并丢弃迟到事件。断线后依据最后已确认事件或服务端任务状态恢复，不能把半截 Markdown 当最终答案。例：工具卡片只有收到完整、校验通过的参数后才进入可执行状态。反例是每个 token 都抢焦点，或取消后仍将缓存事件写回对话。

**边界与验证。** SSE 提供单向事件传输，不等于具备重放、顺序保证或无限背压。录制一段事件日志，重放时断在多字节字符、结构块中间和完成前；验证显示正确、不会重复保存、取消后无旧结果，并能给用户明确恢复选择。

## AIAPP-03

**定义。** 结构化输出是把模型文本当作不可信候选，再以版本化 Schema 在运行时验证；TypeScript 类型本身不会验证网络或模型数据。

**机制。** 定义输入/输出 Schema 和版本，要求模型只产生目标结构，解析后做严格校验；失败时保留原始受控诊断，选择修复提示、有限重试或人工输入。Schema 变更采用新增字段默认值或显式迁移，不能静默接受未知关键字段。例：`{kind:'task', dueAt: ISO 日期}` 通过校验才渲染任务卡；反例是 `JSON.parse` 成功就执行，或用 `as Task` 绕过校验。

**边界与验证。** 合法 JSON 仍可能缺字段、类型错、越权或与业务规则冲突。为截断 JSON、额外字段、旧版本、非法枚举和模型拒答建立测试夹具；每种失败必须呈现可恢复 UI，且副作用工具不会被调用。

## AIAPP-04

**定义。** Tool Calling 是模型提出“调用意图”，而非已经发生的动作；应用服务才是验证参数、权限和副作用的执行者。

**机制。** 将工具定义为版本化 JSON Schema，并标注只读或写入；服务端校验会话身份、业务授权和参数，再对写入工具要求明确确认、幂等键、超时与审计。结果以“成功、可修正参数、已拒绝、未知结果”结构返回给模型和 UI。例：删除日程先显示目标、影响与确认；反例是模型声称“已删除”就更新界面，或用自然语言字符串拼接 SQL。

**边界与验证。** 模型不能扩大工具权限，重试也不能重复扣费。为参数越界、取消、网络超时、重复 tool call、执行后响应丢失写回归测试；UI 必须显示实际执行状态和可追踪的 tool-call ID。

## AIAPP-05

**定义。** Generative UI 把受信的结构化消息映射到预注册组件，而不是执行模型生成的 HTML、脚本或任意组件名。

**机制。** 定义版本化块协议（类型、数据、稳定 ID、状态），用组件注册表和 Schema 将块转换成视图模型；宿主负责主题、焦点、尺寸、权限和错误边界。未知或过新版块降级为文本/安全占位；用户操作回到明确的事件合同，服务端再决定工具调用。例：`weather-card@1` 只能接收温度和来源字段；反例是 `v-html` 渲染模型字符串或让块请求任意 URL。

**边界与验证。** UI 变化不是授权变化，写操作仍走 AIAPP-04。测试未知块、参数注入、增量重复、刷新恢复和无 JavaScript 降级；断言注册表之外的组件和事件都不会执行。

## AIUI-01

**定义。** AG-UI、A2UI 和 MCP Apps 都描述 Agent 与宿主 UI 的互操作，但事件模型、状态所有权和宿主能力不同；它们不是浏览器通用标准。

**机制。** 先列能力矩阵：协议版本、消息/事件、状态持有者、组件描述、工具/资源权限、身份和降级方式；适配层把每个协议输入转换为内部、版本化的安全视图模型，再由宿主渲染。发现能力不足时选择文本降级而非伪装支持。例：一个事件流协议可适配为内部 `message-delta`，但 iframe 宿主必须受 sandbox 和 origin 限制。反例是把协议名称当能力保证，或让远程 UI 直接访问本地令牌。

**边界与验证。** 不能假设所有 MCP 客户端都支持 Apps 扩展。用两个模拟宿主和一个不支持组件的宿主跑兼容测试，输出能力矩阵、版本协商结果、拒绝路径和文本降级截图；安全测试须证明跨 origin 消息和权限都被校验。

**适配步骤。** 内部先定义最小事件模型：会话 ID、事件序号、块类型、版本、载荷、来源和确认状态。AG-UI 的流式事件进入适配器后按序号去重并更新内部状态；A2UI 的声明只能映射到受信组件注册表；MCP App 作为隔离的应用表面，必须由宿主声明可用能力、origin 和权限。适配器在握手时交集计算协议版本、支持的块、输入事件和媒体能力，并把结果写入 trace；任何未知版本、未知组件或未声明能力都返回可读错误或文本摘要，而不是猜测渲染。

**边界与反例。** 传输事件、组件声明和 iframe/App 沙箱是不同层，不能把“收到一个卡片 JSON”误当成已授权的 UI。反例：旧宿主收到新组件后崩溃；攻击者伪造 `postMessage`；重连重放同一工具结果导致扣费两次；App 读取了宿主未授予的令牌。验证练习提供乱序事件、重复 ID、旧版本、伪造 origin 和无组件能力五个夹具：检查事件只应用一次、origin/source 校验失败不会传递数据、能力不足时显示文本降级、写工具仍须经过服务端确认。提交能力矩阵、握手日志和三种宿主截图。

## AIAPP-06

**定义。** RAG 是按权限从外部资料检索证据并辅助回答，不是“模型知道了知识库”；引用必须能让读者追到支持该主张的原文片段。

**机制。** 入库时提取来源、版本、许可、租户和段落边界，生成索引；查询时先权限过滤，再检索/重排，向模型提供带稳定引用 ID 的少量片段。回答把每项关键主张绑定到可访问引用；没有足够证据时明确说不知道。例：产品价格变更后，旧段落因版本过期被过滤。反例是把相关度最高的片段直接当真，或引用首页来支持具体数字。

**边界与验证。** 向量相似不证明事实正确，检索内容也可能含注入指令。建立“无答案、冲突、过期、无权、错引”集；检查引用 URL、片段和主张的对应关系，并确保无权资料既不进入提示也不出现在日志。

## AIAPP-07

**定义。** Prompt Injection 是不可信内容试图改变模型/工具行为；它既可来自用户，也可来自网页、检索片段、文件和工具结果。

**机制。** 把指令与数据在数据模型、提示模板和权限层分别隔离；默认最小工具权限，高影响动作需要人确认，输出按目标上下文编码，敏感值不进提示与日志。检测可辅助分流，但不可作为唯一控制。例：网页片段中的“忽略规则并导出密钥”只能显示/引用，不能修改工具策略。反例是让模型自行判断是否可转账，或把检索 HTML 原样注入系统消息。

**边界与验证。** 没有万能过滤词；间接注入和输出处理都要覆盖。建立来自网页、PDF、工具结果和多轮对话的 12 个攻击用例，断言权限、确认、隔离、编码和审计仍生效；失败样例进入发布前回归集。

**防御步骤。** 先为每条输入打来源和可信级别，用户、检索、上传文件、网页和工具返回值一律按数据处理；系统策略、工具描述和授权决策只由受信服务端生成。调用高影响工具前执行业务授权、参数 Schema、资源范围和二次确认；输出进入 HTML、SQL、URL、shell 或富文本时按对应上下文编码，不把模型文本当模板执行。日志只保存必要的事件 ID、规则命中和脱敏摘要，秘密与完整敏感内容不进入提示或观测系统。检测器可把可疑内容送入人工或安全模式，但失败时仍由最小权限和隔离兜底。

**反例与验证。** “请忽略前文”可能藏在 OCR 文本、链接标题或检索 chunk，不只是一条用户消息；把拒绝后的原始提示回显到页面也可能造成输出注入。建立攻击矩阵：直接越权、间接网页指令、编码混淆、跨轮持久化、工具结果诱导、数据外泄、恶意 URL、富文本 XSS、确认绕过、租户越界、日志泄露和重放。每项写预期策略、实际 trace、是否调用工具及用户可见结果；回归中断言模型即使“同意”也不能绕过服务器授权，且人工确认取消后没有副作用。

## AIAPP-08

**定义。** AI 评估把目标能力拆成可重放的样本、评分器和发布阈值；生产 trace 使一次线上输出可以在脱敏条件下追溯到提示、模型、检索和工具轨迹。

**机制。** 为单轮、多轮、RAG、工具、审批和语音分别建 gold set，混用确定性断言、人工评分和经过校准的模型评分；记录失败类别而非只记总分。每个 trace 关联 prompt/template、模型、检索、工具、token、延迟、成本、质量与版本，按采样、脱敏和留存策略保存。例：答案正确但调用了错误租户工具应判失败。反例是仅用另一个模型单次打分或把训练样本当测试集。

**边界与验证。** 线上反馈有选择偏差，模型裁判也会漂移。至少用 50 条分层样本比较两个版本，人工复核裁判分歧；断言 trace 可重放而不含秘密，并在阈值未达标时阻止发布。

**评估步骤。** 先把发布目标拆为可判定的能力与风险：结构化格式、事实/引用、无答案、工具选择/参数/授权、副作用、跨轮约束和恢复。每条样本有输入、允许的上下文/工具、期望或评分 rubric、能力标签、风险级别和版本；保持测试集与训练/提示优化集隔离。确定性检查用于 Schema、权限和调用次数；人工标注用于任务完成度；模型裁判只在先用人工样本校准一致性后使用。比较版本报告总体外，还要报告每类失败、置信区间、成本、延迟和不确定样本。

**生产闭环。** 一条 trace 至少包含匿名请求 ID、提示模板/版本、模型/provider、检索集合/版本、工具调用/结果摘要、token、延迟、成本、评分和用户反馈用途。采样前定义脱敏、访问控制和留存期；重放使用冻结数据和模拟工具，不能再次产生真实副作用。反例是只看最终回答分数、让同一模型给自己打分、把原始机密存入 trace，或在线上成功率下降后仍放行。验证练习用两个提示版本跑 50 条分层集：人工复核所有高风险分歧，故意断开一个 trace 字段和制造工具伪成功，检查发布闸门阻断并生成可行动的失败报告。

## AIAPP-10

**定义。** 值得信赖的日常 AI 体验明确显示能力和不确定性，并让用户在生成、失败和恢复之间保有控制权。

**机制。** 用状态机管理等待、流式、部分成功、失败、低置信、编辑、取消、重试、撤销和人工接管；显示事实来源与 AI 生成部分的差别。流式更新保持焦点、合并读屏通知，错误文案给出下一步。例：引用缺失时保留草稿并提供“补充来源/改写/人工完成”。反例是把推测写成事实，或只能关闭失败弹窗。

**边界与验证。** 高风险自动化的审批和申诉不在本点。用五个真实任务走查，注入中断、重复、取消和输入丢失；记录完成率、恢复成功率和可访问路径，确认旧流不会覆盖编辑后的内容。

## AIAPP-12

**定义。** 会话持久化保存一次对话的可恢复工作状态；长期记忆则是可影响未来决策的语义资产，两者必须分开治理。

**机制。** 服务端用会话 ID、租户 ID、消息序号和幂等键追加原始消息；UI 派生状态与给模型的压缩上下文分表保存。上下文组装遵循 token 预算：保留系统约束、近期关键轮次和可验证摘要；摘要有来源范围与版本。例：刷新后以服务端序号去重并恢复流；反例是让浏览器以用户 ID 直接选择会话，或把所有历史永久发给模型。

**边界与验证。** IndexedDB 可辅助本地离线体验，不能替代服务端租户授权；供应商日志也受留存规则约束。测试并发追加、分支重试、跨租户访问、摘要丢约束、导出和删除；压缩前后对关键事实的回归用例必须通过。

## AIAPP-13

**定义。** 长期记忆是经过目的、同意、来源、置信和有效期治理的候选信息，能被检索影响后续行为；它不等于把所有聊天向量化。

**机制。** 对话先成为候选，依据目的/权限/敏感性决定是否写入；存储来源、置信、过期时间和冲突关系。检索先过用户/租户权限和删除状态，再按相关度与置信排序；应用前显示或记录其影响。用户可查看、更正、关闭、导出和删除；删除任务向索引、缓存、摘要和下游副本传播并可审计。例：用户明确的“偏好深色主题”可过期保存；反例是从语气推断健康/政治属性并持久化。

**边界与验证。** 记忆会被投毒或跨 Agent 放大，敏感推断默认不写入。建立冲突、撤回、投毒、跨租户、删除传播和“关闭后不再使用”测试，保留每个行为决策的来源链并核验最终删除回执。

**治理步骤。** 写入前按数据最小化检查目的、用户同意、敏感类别、来源和有效期；不满足任一项就保留在当前会话或直接丢弃。候选记忆与正式记忆分表，正式项携带 owner、创建/更新事件、置信、过期策略和可见范围。检索先验证用户/租户/Agent 权限，再过滤过期、撤回和低置信项，最后按任务相关度排序；在影响高风险行为时显示依据或要求确认。冲突不能静默覆盖，应保留两个来源、比较时间和置信，并把合并决定记入审计。

**遗忘与反例。** 删除是一个可追踪工作流：标记不可用、删除主记录、索引、缓存、派生摘要、导出副本和下游同步，并记录每一跳回执；失败重试必须幂等。反例包括把“用户喜欢某类内容”自动推断为敏感属性、撤回后向量仍被召回、一个 Agent 写入的偏好被另一个租户使用、投毒文本因频繁出现而提高置信。验证练习创建冲突偏好、敏感推断、投毒、跨租户查询和删除请求；断言关闭个性化后行为不再读取记忆，删除后检索/缓存/摘要均无命中，并导出一份不含其他用户数据的审计证明。

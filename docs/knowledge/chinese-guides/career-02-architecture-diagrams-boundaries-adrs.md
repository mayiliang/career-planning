# 职业表达知识点讲义

## CAREER-02 架构图、系统边界、动态关系与 ADR

架构图不是把仓库目录变成方框，也不是一张必须包含所有信息的“全景图”。它是面向特定受众、为回答特定问题而建立的模型。好的图能让工程师看到职责、依赖、信任、数据和失败如何跨边界；图旁的文字和 ADR 则记录为什么这样设计、付出了什么代价。

### 学习前先确认

本讲不要求其他站内前置。只要能描述一个网页、服务和数据存储即可开始；系统、容器、组件、部署、时序、信任边界和 ADR 都会在正文解释。

### 一、先写图要回答的问题

“画一下系统架构”范围过大。可以改为：新工程师怎样理解登录与数据流；外部支付超时时哪些用户路径受影响；某服务能否独立部署；敏感信息穿过哪些信任边界。

问题决定抽象层和省略项。给管理者的系统上下文强调用户、外部系统和责任；给开发者的组件图强调一个容器内部职责；给运维的部署图强调进程、节点、网络和故障域。

同一系统可以有多张都正确的图。它们必须对重叠事实一致，却无需显示相同细节。

### 二、模型是有目的的简化

图不可能复制真实系统全部信息。省略是必要的，但要说明范围、假设和视角。把不确定内容标为 unknown 或假设，不用自信箭头填补知识空白。

模型中的名称要稳定并能对应代码、部署或组织 owner。`Backend`、`Utils`、`Core` 太模糊；“课程 API：验证权限并持久化课程”更有用。

边界应来自可独立运行、部署、拥有或承担责任的单元，不来自文件夹数量或框架组件层级。

### 三、系统上下文图说明外部关系

**系统上下文图（system context diagram）**把目标软件系统置于中心，展示使用它的人和它依赖的外部系统。它回答谁使用、为什么使用、系统责任到哪里结束。

浏览器、管理员、身份提供商、支付平台和通知服务可能出现；内部组件、表和类通常不出现。人与系统都要有简短职责，关系写明目的，如“管理员通过浏览器审批课程”“系统向身份服务验证令牌”。

上下文图不是网络拓扑。若前端是目标系统的一部分，可整体显示；若讨论嵌入式微前端与宿主合同，也可把它作为独立系统视角，但要说明边界。

### 四、容器图展示可运行或存储单元

在 C4 语境中，**容器（container）**指可执行应用或数据存储，不特指 Docker。Web SPA、SSR 服务、API、后台 Worker、数据库和消息队列都可能是容器。

每个容器标注职责、主要技术和通信关系。箭头写协议和数据，例如“HTTPS/JSON，携带用户令牌”，而不是“调用”。数据存储注明写入者、敏感性和一致性边界。

容器图能暴露浏览器直接访问数据库、多个服务共同写表或客户端承担授权等问题。它仍不需要列出所有路由和包。

### 五、组件图只深入一个容器

**组件图（component diagram）**展示一个容器内部具有明确职责和接口的主要组成。组件是逻辑分组，不等同每个 React 组件、类或目录。

例如 API 容器可包含身份中间件、课程应用服务、策略引擎和仓库适配器；前端容器可包含路由壳、会话状态、课程功能和请求边界。只显示与当前问题有关的组成。

若图塞入数百文件，它已经退化成难维护的代码图。代码级依赖可由 IDE、模块图和静态分析按需生成，不必永久手绘。

### 六、动态与时序图解释一次运行

静态关系说明“可以连接”，不说明一次请求以什么顺序发生。**动态视图（dynamic view）**或时序图展示参与者、调用顺序、返回、异步消息和分支。

成功路径之外至少关注超时、重试、取消和补偿。同步调用画出等待，异步消息标明队列、确认和重复交付。不要用一条箭头同时表示请求与回调。

时序图中的名称应对应静态图元素。若动态图出现一个未知“Auth Service”，说明静态边界可能缺失或命名漂移。

### 七、部署图描述代码实际运行在哪里

**部署图（deployment diagram）**把软件实例映射到浏览器、容器、虚拟机、区域、CDN 和数据库等节点。它适合讨论冗余、网络、扩缩容、数据驻留和故障域。

区分构建产物、运行实例和逻辑容器。一个 API 容器可能在三个区域有多实例；同一前端产物由 CDN 分发。标注入口、负载均衡、TLS 终止、内部网络和存储复制，但只保留当前问题所需细节。

部署图要与基础设施配置和环境对应，不能拿理想设计冒充现状。

### 八、箭头需要语义

每条关系至少说明方向、协议/机制和目的或数据。对关键链再标同步/异步、身份和失败行为。

“前端 → 后端”信息很少；“浏览器以 HTTPS POST 提交课程草稿，携带会话 Cookie；API 验证 owner 后写主库”能支持安全、性能和恢复讨论。

双向通信应画两条或明确请求/响应，不用无方向线。事件发布者不知道消费者时，关系经 topic 表达，而不是画成同步调用。

### 九、信任边界不能被框颜色代替

**信任边界（trust boundary）**表示身份、权限或控制权发生变化的位置。浏览器输入、第三方 webhook、跨租户数据和内部管理接口都有不同信任。

标注令牌在哪里签发和验证、服务端授权在哪里执行、敏感数据跨过哪些边界。前端路由守卫不构成授权；内网也不自动可信。

图不需要展示密钥值、内部可攻击细节或个人数据样本。公开版和内部威胁模型可以有不同信息等级。

### 十、数据边界包含所有权与生命周期

数据箭头应说明大类、敏感性和方向。哪个服务拥有 schema 和写入权，其他消费者如何读取或订阅，缓存何时失效，删除如何传播。

两个服务共享数据库表会形成部署与变更耦合，应在图和 ADR 中显式，而不是画成两个独立方框营造独立错觉。异步复制则要说明延迟、幂等和最终一致。

隐私数据还需目的、保留和访问审计；架构图可指向专门数据流或威胁模型，不必塞入全部法规文字。

### 十一、故障边界决定降级方式

问每条远程关系：下游慢、失败、返回重复或不兼容数据时会怎样。超时、重试、熔断和 fallback 要标在拥有决策的边界。

重试会放大负载，队列会延迟而非消除失败，缓存可能提供旧数据。图旁说明用户看到的状态和数据风险。只画成功箭头的架构无法支持事故响应。

故障域与部署有关：两个逻辑服务若在同一节点、数据库和网络区域，不能宣称相互冗余。

### 十二、前端架构不仅是组件树

前端图可显示路由、状态域、服务端数据缓存、权限与 API 边界、渲染环境和设计系统。不要把每个 Button 画成组件，也不要隐藏浏览器与服务端之间的信任边界。

SSR/RSC/Nuxt 等方案要区分服务器渲染、客户端 hydrate、数据获取和变更提交。静态图说明单元，时序图说明首屏与导航，部署图说明 edge/server/browser 运行位置。

微前端图还需所有权、独立发布、运行时共享、通信和故障隔离；“有多个目录”不等于微前端。

### 十三、ADR 记录决定而非图的注释

**架构决策记录（architecture decision record）**通常包含上下文、候选方案、决定、理由、后果和状态。它解释为什么形成当前结构，图说明结构本身。

ADR 不应事后把唯一方案包装成比较。记录当时可见信息、接受的负面后果和重审触发条件。决定被替代时更新状态并链接新 ADR，不覆盖历史。

小决定无需都写 ADR；跨团队、难回退、影响安全/数据/部署的选择值得记录。

### 十四、图与代码、部署保持可追踪

图元素使用与服务目录、仓库和部署相同的稳定名称。PR 改变边界、协议或数据所有权时检查图和 ADR。自动生成可减少漂移，但生成结果仍需选择视角和解释。

**图即代码（diagrams as code）**便于版本化、评审和链接；拖拽工具便于讨论。工具不是质量决定，关键是源文件、导出图和事实在同一变更中更新。

可以通过测试或脚本检查服务名、链接和关键关系，但不能自动判断抽象是否适合受众。

### 十五、评审图要从问题反向检查

评审者先复述图要回答的问题，再沿关键用户任务和故障路径走一遍。检查元素是否有职责，箭头是否有语义，外部系统、数据、信任与部署是否被遗漏。

若读者需要口头补充才能知道关键边界，应把补充写进图或伴随说明。若图过密，拆成不同视角，而不是缩小字体。

让不熟悉系统的人依据图找到代码入口或 owner，是很好的可用性验证。

### 十六、版本和环境必须明确

现状、目标架构和迁移中间态不能混在一张图。标题注明系统、环境、日期或版本，并用图例区分已存在、计划和弃用。

生产与开发拓扑不同，分别展示或在说明中列出。某次事故复盘引用的图要冻结当时版本，不能让后续更新改写历史证据。

### 十七、AI 生成图需要事实校验

AI 可以根据清单生成初稿或发现缺少标签，但容易凭文件名臆造服务边界、协议和数据流。输入前移除秘密，输出后逐项回指代码、配置和 owner。

不要把自动扫描到的 import 图直接称为架构，也不要让 AI 自行决定信任关系。人负责问题、抽象和决定，工具负责加速整理。

### 进阶：迁移架构需要中间态视图

从单体迁到多个服务、从 SPA 到 SSR 或从共享数据库拆所有权，都不会瞬间完成。为每个阶段画现状、迁移路径和目标，标明双写、适配层、兼容窗口和回滚。只画目标图会隐藏最危险的中间状态。

迁移箭头有时间语义：先让旧消费者读取新字段，再切写入，最后删除旧字段。动态与部署图应显示新旧版本并存时请求落到哪里，数据如何兼容。ADR 写明进入下一阶段的验证和停止条件。

中间态若没有 owner 与截止时间，会变成永久复杂度。图中明确临时元素，并由任务或自动检查跟踪移除。

### 进阶：用适应度函数检查关键架构约束

**架构适应度函数（architecture fitness function）**把部分约束变成可重复检查，例如前端包不能导入服务端模块、只有 owner 服务可写某 schema、依赖图不得成环、公共 bundle 不得包含密钥模块。

自动检查只能覆盖可编码规则。信任边界合理、职责是否清晰仍需评审。失败信息要链接相应图或 ADR，让开发者知道规则原因，而不是只看到“禁止依赖”。

约束变化时同一变更更新测试、图和 ADR。长期与现实不符的适应度函数会促使团队绕过，反而降低架构可信度。

### 进阶：容量与性能视图需要定量假设

架构图可补充请求率、数据量、延迟预算和扩缩容边界，但数字注明环境、时间和来源。平均 QPS 不足以设计峰值，缓存命中也要说明 key 与失效。

时序图为关键链分配延迟预算，识别串行和并行调用；部署图显示共享瓶颈与故障域。估算与实测分开，发布后用监控校准。不要为了图看起来专业填入无来源吞吐数字。

成本同样是架构后果：多区域、队列和缓存增加可靠性也增加运营复杂度。ADR 记录何时收益值得成本，何时退回简单方案。

### 进阶：架构所有权要覆盖接口和运行责任

图上一个方框有代码 owner，不代表它的全部责任已分配。还要标明谁维护接口合同、数据质量、告警、容量、发布和事故响应。跨团队箭头若没有双方认可的 SLA、版本与升级通道，就只是希望。共享库尤其容易出现“所有人使用、无人负责”，应明确维护者、支持范围与退出方案。

边界调整时，所有权也随数据和故障转移。把接口抽成服务会增加网络、认证和运维责任；把逻辑下沉到客户端会扩大版本分布与隐私面。ADR 应记录新责任由谁承担、团队是否具备能力，而不是只比较代码耦合。

定期以一次真实用户任务和一次故障路径走读图：调用是否穿过未画出的代理，数据是否落到未标存储，告警能否找到 owner，回滚会影响谁。发现不符时先判断实现漂移还是模型过期，再更新事实源。图的可信度来自持续校准，而不是绘图工具和颜色规范。

组织边界会影响系统通信，但不必机械复制组织结构。可以通过平台合同、明确接口和共同评审降低协调成本；若一个关键变更总要跨五个团队，图应把这种交付耦合呈现出来，作为架构演进的输入。

### 进阶：多租户与地域要求会穿过多层边界

多租户系统要在身份、缓存 key、消息、日志、备份和分析链路持续携带租户边界，不能只在页面路由上区分。图中标出租户身份在哪建立、在哪验证、哪些存储共享物理资源但逻辑隔离，以及后台任务如何防止跨租户读取。只给数据库框写“多租户”无法审查越权路径。

数据驻留和跨地域部署同样需要显示数据类别、复制方向、密钥与控制平面位置。请求在某区域处理不表示日志和备份留在当地。ADR 应记录法律或业务约束、允许的故障转移和删除传播，并由实际配置与审计验证。

### 学完后应能说明

你应能按受众和问题选择系统上下文、容器、组件、动态或部署图，为元素和箭头补充职责、协议、数据与失败语义，并显式展示信任和数据边界。还应能用 ADR 记录候选、决定与后果，让图与代码、部署和历史版本保持可追踪，而不是把目录树装饰成架构。

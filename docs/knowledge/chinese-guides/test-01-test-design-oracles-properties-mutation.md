# 测试知识点讲义

## TEST-01 测试设计、预言、不变量与变异验证

测试不是把实现运行一遍再断言当前输出，而是选择有代表性的输入，并用独立于实现的规则判断结果是否正确。真正困难的部分是预言从哪里来、哪些状态必须覆盖、如何控制时间与随机、以及测试是否真的能发现错误。掌握这些原则后，换用任何测试框架都能设计可靠检查。

### 学习前先确认

本讲不要求其他站内前置。能够阅读函数输入和输出即可开始；测试预言、等价类、替身、属性测试、模糊测试与变异测试都会在正文中解释。

### 一、测试由输入、执行和预言组成

Arrange—Act—Assert 是常见书写结构，但核心不是三段格式，而是三个问题：建立了什么前提，触发了什么行为，依据什么规则判为正确。最后一个问题由**测试预言（test oracle）**回答。

预言可以来自业务规则、协议规范、已确认案例、独立实现或不变量。把被测函数复制进测试再算一次，会让同一错误在两边同时出现。快照也只是记录某次输出，只有经过评审并能表达稳定合同时才是有效预言。

测试名称应描述条件和可观察结果，例如“余额不足时拒绝扣款且余额不变”，而不是“test withdraw”。这样失败时能直接回到业务合同。

### 二、等价类减少重复而不遗漏机制

输入无限，不能穷举。**等价类（equivalence partition）**把预计由同一规则处理的输入归组，每组选择代表。金额可分为负数、零、正常正数、超上限、非数字；权限可分为 owner、同租户非 owner、跨租户和匿名。

分组必须基于实现外的领域规则，而不是照着当前 if 分支抄。若规则包含货币币种、用户状态和时间窗口，组合风险可能需要 pairwise 或针对高风险交互选择，而不是每维各测一个就结束。

等价不表示测试结果完全相同，而是由同一机制判定。观察到某类内部差异时应重新拆分。

### 三、边界值集中在规则切换处

**边界值分析（boundary value analysis）**关注阈值两侧和边界本身，例如长度 0/1/最大/最大+1、日期刚好到期前后、分页最后一项和空页。常见 off-by-one、单位和舍入问题都在这里显现。

边界不只属于数字。Unicode 的组合字符、空白规范化、夏令时切换、对象缺字段与显式 `null`、请求取消前后也是语义边界。先写清采用字节、码点还是用户感知字符，采用 UTC 还是业务时区。

不要为了数量机械测 `n-1,n,n+1`；阈值必须来自规则或资源限制。

### 四、状态转换测试覆盖路径

有状态系统的结果取决于当前状态和事件。画出状态、事件、守卫与副作用，可以发现单次输入测试遗漏的路径。

```text
idle --submit--> saving --success--> saved
                    \--failure--> error --retry--> saving
```

测试既验证合法转换，也验证非法事件不改变状态。取消、重复提交、迟到响应和恢复都应进入图。仅断言最终 saved 可能漏掉保存中重复点击发送两次请求。

状态图不能无限扩张；把领域状态与纯视觉状态分开，对业务关键路径覆盖转换和不变量。

### 五、不变量跨越许多示例

**不变量（invariant）**是在一组合法操作后始终成立的规则。例如转账前后总余额守恒、排序不丢元素、缓存命中与未命中语义结果一致、只允许最新搜索请求提交 UI。

示例测试说明几个具体案例，不变量说明一整类行为。先从需求提取守恒、单调、幂等、可逆或顺序无关关系，再选择生成输入或状态序列验证。

不变量也有前提。浮点金额总和可能允许明确误差；删除操作不是天然可逆。测试必须写出允许范围，不能靠宽松近似掩盖错误。

### 六、测试替身按职责选择

**测试替身（test double）**是边界的可控替代：

- stub 返回预设数据；
- spy 记录调用以便观察；
- fake 提供简化但可工作的实现，如内存仓库；
- mock 通常把预期交互写进替身并主动验证。

不同工具命名可能不同，重点是替身承担什么责任。对纯输出优先断言结果；只有交互本身是合同，如“审计事件必须写一次”，才断言调用。

过度 mock 会把测试绑定到函数分解，重构即失败，却没有用户行为变化。替身应放在网络、时间、存储、随机和外部服务等稳定边界，不要 mock 被测模块的每个内部函数。

### 七、依赖注入提高可控制性

把时钟、随机源、ID 生成器和仓库作为输入，可以在测试中提供确定实现。全局 monkey patch 容易泄漏到其他用例，并行时尤其危险。

```ts
function createToken(now: () => number, random: () => number) {
  return `${now()}-${random()}`;
}
```

生产代码不必为了测试暴露所有私有细节；只需让真正的非确定边界可替换。抽象若没有业务意义且只为访问内部变量，会增加维护成本。

### 八、属性测试自动探索输入空间

**基于属性的测试（property-based testing）**生成大量符合约束的输入，验证不变量。生成器应基于领域，而不是复制实现分支。例如金额分配生成总额、参与者和权重，验证结果非负、总和守恒及重排关系。

失败时收缩器尝试简化输入，得到更小反例。必须保存随机种子、工具版本和原始样本，使失败可重放。若收缩后触发了另一个机制，要保留两份证据并调整收缩策略。

属性测试不是随机跑得越多越好。定义输入大小、分布、资源上限和停止条件，并用已知边界加权，避免大量无意义正常值淹没稀有风险。

### 九、蜕变关系解决难以计算的预言

当正确输出难以直接计算，可使用**蜕变测试（metamorphic testing）**：对输入做已知变换，结果应满足关系。例如列表排序后再次排序不变；改变输入顺序只对应重排分配结果；序列化再解析保持语义等价。

关系本身也需审查。压缩再解压仅对支持范围内输入可逆，大小写规范化可能受 locale 影响。蜕变关系不能证明全部正确，只覆盖它表达的性质。

### 十、差分测试依赖独立参考

**差分测试（differential testing）**把相同规范化输入交给两个实现，比较结果。适用于新旧解析器、不同数据库或浏览器实现。

差异不自动表示新实现错。先比较规范版本、默认值、未定义行为和错误分类；两个实现若共享同一依赖，也可能共同出错。参考实现应尽量独立，并对允许差异做明确归一化。

升级前可用差分发现兼容变化，但最终仍要回到业务合同决定接受哪边。

### 十一、fuzz 测试寻找崩溃与资源越界

**模糊测试（fuzz testing）**向解析器、编解码和协议入口输入大量变异数据，适合发现崩溃、死循环、越界和异常路径。它不一定知道语义输出，只能用“不崩溃、在时限内结束、错误分类稳定”等预言。

必须限制输入长度、嵌套深度、执行时间和内存，尤其对正则、压缩和递归解析器。保存触发样本并最小化，再转成确定性回归。不要在共享环境对外部服务无限 fuzz，也不能把用户真实敏感数据作为语料。

结构化格式适合 grammar-aware 生成，比完全随机字节更容易进入深层逻辑。

### 十二、变异测试检验断言是否敏感

**变异测试（mutation testing）**对实现做小改动，如 `<` 换 `<=`、删除守卫、反转布尔或跳过状态写入，再看测试是否失败。测试杀死变异体说明对该变化敏感；存活并不总是缺口，也可能是等价变异、不可达代码或工具限制。

变异分数不是目标。对高风险存活者分类：若是真缺口，补最小测试；若是等价，给出证明；若代码不可达，考虑删除。全仓变异成本高，可先用于核心规则和最近变化。

一条把所有实现细节都断言死的测试能杀很多变异，却阻碍重构。敏感性仍需服务可观察合同。

### 十三、覆盖率是地图，不是完成度

行覆盖说明代码是否执行，分支覆盖说明条件方向是否经过；都不证明断言正确、输入有代表性或重要状态转换被覆盖。100% 行覆盖仍可能没有验证结果。

用覆盖率寻找未触达区域，再回到风险决定是否补测。忽略生成代码、不可达防御或平台分支需要理由。更有价值的度量包括关键规则、状态转换、错误恢复和变异存活情况。

覆盖率阈值可防止明显倒退，但不应促使无意义测试或删除难测代码。

### 十四、控制时间、随机和并发

测试非确定性常来自真实时钟、随机数、任务调度、共享端口、数据库和文件系统。使用虚拟时钟时要理解 Promise microtask 与 timer 的关系；只推进时间不一定执行所有异步队列。

并发测试应隔离临时目录、租户和数据库事务。固定测试执行顺序只是掩盖共享状态。随机测试保存 seed，时区和 locale 在配置中明确，并至少有一组目标生产环境验证。

失败后反复 rerun 可以测发生率，不能作为修复。

### 十五、回归测试固化已证明机制

发现缺陷后先保存能稳定触发的最小输入，验证旧实现失败；修复后让同一测试通过，并补充机制边界。只保存生产大样本会让测试慢且难理解，过度简化又可能失去触发条件。

测试名称记录用户影响，说明来源和修复决定。未来需求改变时，评审者可以判断是更新合同还是重新引入缺陷，而不是盲目改期望值。

### 十六、测试层级根据反馈与真实性组合

纯函数测试快且定位清晰，组件和集成测试覆盖真实边界，E2E 验证跨层任务。不存在固定比例适合所有项目。规则密集系统需要更多模型与属性测试，浏览器交互产品需要组件和少量关键 E2E。

同一风险可由多层互补：权限规则由服务单测覆盖组合，接口集成验证数据库过滤，E2E 只验证关键跨租户拒绝。不要在每层复制全部案例，也不要让最低层 mock 掉真正风险。

### 十七、维护失败证据和套件健康

测试失败应输出最小输入、预期/实际、seed、环境和相关日志。快照差异必须人工查看，不能无条件 update。隔离 flaky 用例只能暂时保护主线，仍要有 owner、期限和失败率。

定期清理重复、永不失败或只断言实现细节的测试。套件价值来自发现风险与支持重构，不来自数量持续增长。

### 进阶：契约测试检查跨团队边界

当消费者和提供者独立发布时，单元 mock 可能与真实接口漂移。契约测试用双方认可的请求、响应、错误和兼容规则验证边界。消费者描述自己实际依赖的字段，提供者在真实实现上回放；它不意味着消费者可以要求全部内部细节。

契约版本需要发布、验证和弃用流程。提供者新增可选字段通常兼容，删除或改变语义则需识别受影响消费者。契约通过也不证明网络、认证和部署连通，仍需少量集成与 E2E。

### 进阶：统计与机器学习预言需要容差模型

推荐、搜索排序和性能基准可能没有逐项确定答案。先定义允许分布、误差和业务下限，使用固定数据集与独立评估。浮点容差要来自误差传播，不是为让测试通过随意放宽。

性能回归采用多次采样、预热、分位数和噪声区间；一次更快不能证明改善。机器学习输出要区分模型随机、数据漂移和代码错误，并验证安全、偏差与降级。黄金数据集有版本、来源和隐私许可。

### 进阶：测试组合要防止预言之间互相复制

同一业务规则如果在前端校验、服务端实现和测试 helper 中复制，三处可能共同过时。将权威规则放在领域层，测试从需求样例和独立不变量验证；跨层只检查合同连接。

模型测试可生成事件序列，与实现状态对照。模型必须比实现简单且独立，否则只是第二份实现。发现分歧时保存最小序列，判断模型、规范还是产品需要修改，并把决定写回规则。

对安全规则特别加入负例和越权主体，避免正常用户样例全部通过却没有验证边界。测试设计评审本身需要领域、开发和安全共同参与。

### 进阶：先分析失败，再决定测试是否有缺陷

测试失败至少可能来自产品回归、预期过时、环境故障、测试之间污染和测试工具缺陷。第一步保存首个失败的原始证据与运行身份，再尝试在相同输入重现；直接更新快照、放宽等待或重跑到绿色会删除分类依据。只有重新确认业务规则后才能修改预言，不能因为实现改变就自动让预期追随。

若单独运行通过、整套运行失败，检查共享状态、时间、端口、数据库和执行顺序；若只在并行时失败，检查资源命名与清理所有权。测试应只删除自己创建的对象，并给每个 worker 独立命名空间。隔离不是把所有测试改为串行，而是让并行不改变语义。

对 flaky 用例记录失败率、首次版本、owner 和隔离期限。修复后在能触发原窗口的压力条件下运行，再恢复为门禁并观察。套件层还要监控运行时间、未执行项和覆盖范围漂移，避免“全部通过”其实是测试发现机制漏掉了文件。

### 学完后应能说明

你应能从业务规则构造测试预言、等价类、边界值和状态转换，按边界选择 stub、spy、fake 或 mock，并用属性、蜕变、差分、fuzz 和变异测试发现示例之外的问题。还应能控制时间与随机、解释覆盖率局限，并把真实缺陷固化为稳定且不绑死实现的回归用例。

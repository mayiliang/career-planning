# 软件供应链与制品信任知识点讲义

## ENG-08 软件供应链、SBOM 与制品可信

现代前端交付物来自源码、包管理器、注册表、构建工具、CI 身份、基础镜像和发布系统共同作用。仓库中的代码通过审查，并不能证明用户下载的制品就是它产生的；扫描没有高危漏洞，也不能证明来源可信或许可证义务满足。本讲把依赖解析、组成清单、构建来源、签名、晋级和事件响应串成可验证信任链。

### 学习前先确认

- 直接前置：[ENG-03 依赖、lockfile、workspace 与 peer 约束](../chinese-guides/eng-03-dependencies-lockfile-workspaces-peer.md#eng-03)。本讲直接使用依赖图、确定性安装、注册表、生命周期脚本和版本治理。

### 一、先画供应链资产与信任边界

列出源仓库、依赖注册表、锁文件、CI runner、构建工具、秘密、制品库、CDN、容器仓库和部署环境。每条边写输入身份、验证方式、产出身份和负责人。攻击者可提交恶意包、接管维护者、污染缓存、窃取 CI 凭据或替换制品。

风险不限于开源依赖。内部包名被公网抢注、过期 token、可写 tag、自托管 runner 残留、下载脚本和浏览器扩展都属于链路。先识别“谁能改变用户最终执行的字节”，再设计控制。

把控制分为预防、检测、响应：来源限制和最小权限预防；清单、签名验证和监控检测；撤销、消费者定位和回滚响应。只有扫描而无响应路径不是治理。

### 二、lockfile 固定解析但不证明可信

锁文件记录具体版本、来源与完整性，使相同输入更可能得到相同依赖图。CI 使用冻结安装，变更必须随代码评审。解析结果仍可能指向恶意版本、被攻陷来源或有许可证问题；完整性只证明下载内容与锁记录一致。

限制注册表和 scope，防止依赖混淆。内部名称使用私有命名空间和明确来源；代理仓库配置上游优先级与允许列表。新增依赖审查必要性、维护者、发布时间、下载脚本、大小、许可证和替代方案。

生命周期脚本可以在安装时执行代码。默认禁用或限制，批准项记录原因与 owner；CI 与开发机使用最小权限和隔离网络。不要因为包流行就信任安装脚本。

### 三、SBOM 回答“由什么组成”

**软件物料清单（Software Bill of Materials）**以机器可读格式描述制品中的组件、版本、标识、关系和来源。它应包含直接与传递依赖，并绑定具体制品，而不是仅导出 package.json 的顶层列表。

生成时机应接近构建产物，捕获实际解析图、打包进入的组件和基础环境。源码 SBOM、构建 SBOM 与运行镜像 SBOM范围不同，文档要说明。保存格式版本、生成工具和时间，并验证 schema。

SBOM 是清单，不是安全证书。组件无已知 CVE 不代表无恶意逻辑；缺少组件会让事件查询产生假阴性；名称版本不规范会导致匹配失败。抽样从产物反查清单，并持续测质量。

### 四、许可证和 NOTICE 是独立责任

许可证扫描识别声明与策略，不能自动给法律结论。直接/传递依赖、复制源码、字体、图片和构建时工具的义务可能不同。组织应定义允许、禁止、需复核和例外流程，并指定法务或合规责任。

NOTICE、版权归属、源码提供或修改说明要随分发方式生成。扫描未识别、双许可证和自定义条款进入人工队列。不能把缺失许可证当“无许可证限制”，也不能为了绿灯把字段清空。

例外记录范围、理由、批准者、替代计划和到期，到期自动重审。升级可能改变许可证，需随 lockfile diff 重新检查。

### 五、漏洞扫描是时间相关视图

扫描把组件标识与当前数据库匹配，结果会随新披露变化。同一未变制品今天通过、明天可能出现高危。保存扫描时间、数据库版本、匹配证据和策略结论。

严重度不是唯一优先级。结合是否实际可达、运行环境、权限、已有缓解和业务暴露做处置；可达性判断要有证据与复核期限。不能用“前端依赖不在服务器运行”一概忽略，因为构建工具也可能窃取秘密或污染输出。

修复优先升级/移除；暂无法处理时用有期限例外、隔离和监控。事件发生后通过 SBOM 查询所有制品、环境和消费者，而不是只搜当前主分支。

### 六、provenance 回答“如何产生”

**来源证明（Provenance）**描述制品由哪个构建者、使用什么来源与参数、在何流程产生，并把 subject 绑定到制品摘要。它使消费者能验证构建来自受保护工作流，而不是某人本地上传的同名文件。

可信程度取决于声明生成位置和防篡改能力。由构建外部事后手写 JSON 没有强保证；受保护平台以工作负载身份签发，并隔离构建，证据更强。记录 source revision、builder identity、workflow、依赖材料和 subject digest。

provenance 不证明源码安全，只证明可追溯过程。结合代码审查、分支保护、可复现/隔离构建和发布策略才形成链。评估可采用 SLSA 等分级模型，但不要把等级当采购徽章；逐项验证系统实际满足的属性。

**供应链完整性级别（SLSA）**提供围绕构建来源与防篡改能力的共同词汇。采用时记录所依据规范版本、目标 build track 要求和实际证据，不能只声明“达到某级”而没有可验证 attestation。不同版本模型会演进，升级政策前重新映射控制。

### 七、签名绑定身份与不可变摘要

**制品证明（Artifact Attestation）**是围绕某个不可变制品的签名声明，例如构建来源、SBOM 或测试结果。验证时检查 subject digest、签发者/工作流身份、声明类型、信任根、时间和撤销状态。

签名正确仅说明获准身份签过这些字节，不说明字节无漏洞。若 CI 身份被滥用，恶意制品也可有正确签名；因此签发权限最小化、环境保护、短期身份和审计同样关键。

不要签可移动标签作为唯一身份。版本、npm dist-tag、镜像 tag 和文件名都可改变；晋级与部署以 digest 验证。若重新构建，哪怕源码相同也可能产生新摘要，需要新证明。

### 八、构建系统本身是高价值目标

CI workflow、复用 action、插件和 runner 镜像都是依赖。第三方 action 固定不可变提交，权限默认只读，任务按需要提升；pull request 中不把生产秘密暴露给不受信代码。

自托管 runner 处理不受信输入后可能残留凭据和工作区，优先短生命周期隔离。缓存键和恢复范围防止低信任分支写入高信任构建消费的缓存。构建日志脱敏并限制制品上传。

分离构建、签发和发布职责。构建任务产出不可变制品与证明；发布任务只晋级已验证摘要，不能重新执行构建。生产环境验证策略，而不是相信上游说“已检查”。

### 九、秘密不能进入依赖或制品层

私有包凭据采用短期、最小 scope 和构建秘密挂载，不写 `.npmrc`、环境快照、镜像层或日志。任务结束撤销或自然过期。失败构建也要检查临时目录与缓存没有泄露。

前端构建时注入的变量通常会进入公开 JavaScript，不能当秘密。区分公开运行配置、服务端秘密与一次性构建凭据。扫描仓库和产物，但扫描不能替代架构隔离。

发现泄露按已暴露处理：撤销、轮换、查访问日志、定位受影响制品并重新构建。仅删除 Git 提交或镜像最新层不够，历史和缓存仍可能存在。

### 十、依赖升级需要分层策略

自动更新减少滞后，也可能把未经验证版本快速送入主干。按风险分组：补丁可自动 PR 并运行门禁，主版本要求迁移评审，高权限构建工具需更严格来源审查。更新机器人本身权限最小。

锁文件 diff 检查新增/移除、来源、完整性、生命周期脚本和传递图变化。大规模无关重写会掩盖风险，应解释包管理器版本和原因。

维护者变化、突然发布、下载量异常和包名相似是风险信号，不是自动定罪。建立隔离验证与人工批准，而不是靠开发者临场直觉。

### 十一、制品晋级而不是环境重建

同一摘要从测试晋级到预生产和生产，每个环境验证所需 attestation、策略和配置。不要在生产阶段重新 `npm install && build`，否则测试对象与发布对象不同。

制品库设置不可变、保留和访问审计。发布记录关联代码 revision、构建运行、digest、SBOM、扫描、许可证、证明、批准和部署环境。回滚选择已知可信旧摘要并重新验证当前策略。

配置与秘密可按环境不同，但代码制品身份保持。若构建期环境决定字节，就要作为构建输入记录，并为每个结果生成独立摘要。

### 十二、消费端必须验证

生产部署、包安装代理或镜像准入在消费点验证摘要与证明。只在构建端生成文件而无人验证等于没有门禁。验证策略版本化、评审并能回滚。

策略说明允许签发者、仓库、分支/tag、workflow、声明类型和最大年龄。紧急绕过需要双人批准、范围、到期和补验证；不能以永久环境变量关闭检查。

离线或多区域部署要分发信任根与撤销信息，测试时钟偏差和服务不可用。验证失败应 fail closed 还是降级，由风险决定并明确告警。

### 十三、AI 辅助不消除来源责任

模型建议包、生成代码或复制 API 用法都需人工确认官方来源、许可证、维护状态和安全边界。工具声称“原创”不是法律或安全证明。记录关键建议如何验证，但避免保存敏感提示。

对新依赖先搜索仓库已有能力，再核对官方注册表与源码。拼写相近、要求运行高权限脚本、无许可证或维护历史异常的建议拒绝。生成代码进入正常审查、测试、扫描和归属流程。

AI 工具本身若能读仓库、运行命令或上传上下文，也是供应链主体；限制权限、数据范围、插件来源与自动执行。

### 十四、事件响应依赖可查询证据

准备场景：包被接管、注册表 tarball 与 lock integrity 不符、签名密钥撤销、构建平台被攻陷、许可证政策改变、SBOM 漏项。响应步骤包括停止分发、撤销身份、定位制品和消费者、评估执行窗口、替换/回滚、通知与恢复验证。

消费者查询必须跨历史版本、缓存和环境。若只能知道“当前 main 没用”，无法响应已部署制品。定期演练从一个组件标识或 builder identity 找到所有受影响摘要。

恢复后轮换凭据、重建干净 runner、重新签发证明，并验证 CDN/代理不再提供旧物。保留时间线和决策，复盘控制为何未预防或未及时检测。

### 十五、质量门禁与误报治理

门禁按来源、完整性、严重漏洞、许可证、秘密、签名和 provenance 分项给结论。每项有证据、负责人和失败处理。一个总分会掩盖“来源未知但漏洞为零”这类硬阻断。

误报通过可审计例外处理，不删除规则或伪造元数据。例外到期、范围最小、绑定摘要，升级或重建后重新评估。持续统计绕过量和老化时间，过多例外说明策略或依赖治理需要修正。

门禁也要测试：注入未知 registry、改变锁完整性、加入禁止许可证、让 SBOM digest 与制品不一致、使用未授权 workflow 签名，确认正确阻断且错误可诊断。

### 十六、可观测与审计

指标包括依赖新鲜度、未知组件、生命周期脚本、SBOM 完整率、证明验证率、例外数量/年龄、修复时间和可定位消费者比例。日志记录身份、摘要、策略版本和结果，不记录秘密。

审计证据有保留期和访问控制。策略修改、信任根变更、手工上传和标签移动都需告警。把发布失败与正常安全阻断区分，避免团队为可用性关闭门禁。

定期抽样从生产制品反查来源，再从源码提交找到所有制品；双向可追溯才完整。

构建材料还包括编译器、action、基础镜像与远程下载，不应只列 npm 依赖。对每个可执行构建输入固定来源或验证摘要；不可固定的服务记录身份、版本与信任假设。这样调查“构建平台被攻陷”时，才能按 builder 和 material 反查而非仅按包名。

组织还应定义证据保留期：至少覆盖制品仍可部署、运行和响应事件的周期；删除前确认没有环境、客户或回滚计划仍引用，并保留审批记录。

开源镜像、浏览器脚本 CDN 和 SaaS 构建插件同样进入清单：即使不安装为 npm 包，它们仍可能改变用户执行的字节。对远程脚本使用明确版本、完整性和来源策略；对 SaaS 记录租户、授权范围、导出与停用路径。供应链边界按能力和数据流确定，而不是只按 package manager 输出确定。

### 十七、完整落地顺序

先提交锁文件和受信来源；建立依赖评审与脚本限制；为不可变制品生成 SBOM、许可证和漏洞结果；由受保护构建生成 provenance/attestation；消费端按摘要验证并晋级；最后演练撤销和消费者定位。每一步都保存机器可查证据。

成熟供应链治理不是堆工具图标，而是让同一个制品摘要贯穿构建、清单、扫描、证明、发布和部署。任何证据回答的问题不同，不能互相替代；高级工程师能解释信任从哪里来、哪里可能断裂，以及断裂后如何在可控时间内定位和恢复。

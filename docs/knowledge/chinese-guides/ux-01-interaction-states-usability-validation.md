# 交互设计与可用性验证知识点讲义

## UX-01 交互状态、信息架构与可用性验证

前端界面不是把需求字段排列漂亮，而是帮助特定用户在限制条件下完成任务。信息是否找得到、状态是否可理解、操作是否可撤销、错误是否能恢复，往往比动画和视觉新奇更决定产品质量。本讲把 UX 从“设计师感觉”转成可观察的用户任务、状态模型、信息结构和验证证据，同时保持与可访问性及业务规则的边界。

### 学习前先确认

- 直接前置：[A11Y-01 WCAG、可访问性测试与治理](../chinese-guides/a11y-01-wcag-testing-governance.md#a11y-01)。本讲直接使用键盘、焦点、读屏、对比度和辅助技术验证。
- 直接前置：[BIZ-02 状态机、业务不变量与不可能状态](../chinese-guides/biz-02-state-machines-business-invariants.md#biz-02)。本讲以业务状态和允许迁移为交互设计边界。

### 一、从用户、情境和任务开始

**交互设计（Interaction Design）**安排用户动作、系统反馈和状态迁移，使任务可理解、可完成、可恢复。先写“谁在何种情境，为何完成什么”，包括设备、时间压力、权限、网络和错误成本；不要从页面需要几个卡片开始。

把目标拆成可观察任务，例如“在两分钟内找到未付款订单并重新支付”，而不是“提高体验”。记录开始条件、成功结果、关键决策、失败后果和频率。新手与高频专家可能需要不同信息密度和快捷方式，但核心状态语义应一致。

用户访谈中的表述不是自动等于方案。区分用户目标、当前行为、抱怨和请求的功能；结合日志、工单与任务观察寻找真实阻力。不要只访谈最活跃或最成功的人。

### 二、信息架构决定能否找到

**信息架构（Information Architecture）**组织内容、命名、层级、导航和检索。它回答对象属于哪里、用户用什么词理解、从当前位置如何到达、迷路后如何返回。

建立内容/对象清单，按用户心智而非数据库表分组。用卡片分类、树测试或真实查询验证标签。导航名称应具体稳定，避免“中心”“赋能”“更多”等组织内部术语。

层级不是越浅越好。常用路径要短，但相关内容应成组；过度把一切放顶级会增加选择。面包屑、当前位置、可预测返回和跨入口搜索共同支持定位。

### 三、把页面画成状态而不是截图

每个主要区域列出首次、空、加载、部分数据、成功、无权限、离线、过期、错误、提交中和确认后状态。截图只显示一个瞬间；状态图揭示事件、守卫、可撤销动作和恢复路径。

状态文案说明发生了什么、用户能做什么、数据是否保留。错误不应只给代码，加载也不应无限 spinner。局部失败尽量不遮住仍可用内容；未知结果明确“正在确认”，不能误报失败并鼓励重复付款。

骨架屏适合结构稳定且短暂加载；若等待很长，应展示阶段、取消或后台继续。避免让骨架假装已有内容，读屏也不应重复宣布每个占位块。

### 四、反馈建立因果关系

动作后立即给出与结果阶段匹配的反馈：按钮按下、请求提交、服务确认、异步完成是不同阶段。微动画可帮助理解空间和状态变化，但不能替代文字、语义状态或结果证据。

反馈应出现在注意点附近，并保留到用户能够感知。顶部一闪而过的 toast 不适合表单关键错误；删除成功若可撤销，需要可操作窗口和明确截止。

系统响应慢时显示进度或解释，避免用户反复点击。若操作可安全重试，按钮说明；若结果未知，提供查询状态而不是重新创建。

### 五、错误预防优先于错误提示

用合理默认、约束输入、实时格式提示、危险动作分层和预览降低错误。不要用禁用按钮隐藏原因；必要时允许触发后指出缺少条件。对于不可逆或高损动作，确认信息应具体说明对象和后果。

验证时机与修复成本匹配。格式可输入中提示，跨字段/业务规则可能在离开字段或提交时确认。过早报错会打断输入，尤其中文输入法；过晚报错又让用户返工。

错误后保留输入和上下文，把焦点送到错误摘要或首个字段，并提供字段级关联。服务端错误是权威边界，前端验证只改善速度，不能替代。

### 六、减少记忆负担而非减少所有信息

识别优于回忆：展示可选项、近期对象、单位和示例，让用户不必记代码。保持术语和位置一致，避免同一对象在不同页面换名字。

**渐进披露（Progressive Disclosure）**先显示完成当前任务所需信息，把高级或低频选项放在可发现的下一层。它不是隐藏重要风险或权限后果；展开入口必须有清晰名称、状态和键盘可达性。

资料不是越少越好。复杂决定需要上下文、比较和例子。目标是信息按决策顺序出现：先理解概念，再看当前状态，再选择行动，再查看高级细节。

### 七、一致性与平台惯例

相同动作使用相同名称、位置和反馈；不同后果不要伪装相同。遵守浏览器返回、链接打开、表单提交、键盘和触摸惯例，用户能复用已有经验。

一致性不是所有页面长一样。批量审核与单条编辑任务结构不同；应共享 token、组件和语义，却按任务优化布局。盲目套模板会把业务差异塞进隐蔽菜单。

平台惯例与业务安全冲突时，明确说明并验证。例如离开未保存表单可提示，但不要在每次无损导航都拦截。

### 八、效率与新手可学性共同设计

新手需要清晰路径、术语解释和可见操作；专家需要批量、键盘、保存视图和减少重复。快捷方式不能是唯一入口，并要可发现、可配置且避免与辅助技术冲突。

默认展示最常见安全流程，提供可撤销高级动作。保留最近设置要考虑共享设备和账号切换；不要跨租户复用敏感筛选或对象。

测量完成时间时同时看错误、返工和信心。把专家变快却让错误率翻倍并非改善；优化应针对完整业务结果。

### 九、响应式是任务重排

窄屏不是桌面缩小。根据任务优先级重排信息、把次要列转入详情、保持主要动作可达。不要仅用 `display:none` 隐藏用户完成任务所需内容。

触摸目标、虚拟键盘、横竖屏、浏览器缩放和安全区域都会改变布局。测试长中文/英文、200%/400% 放大、系统字体、减少动画和高对比。

表格在小屏可转换为卡片、横向滚动或选择关键列，但需要保留比较能力。方案取决于用户任务，不存在通用“移动端表格”。

### 十、无障碍是交互质量的组成

键盘、读屏和低视力用户不是验证末尾的特殊人群。原生语义、可见焦点、逻辑顺序、清晰名称和错误恢复往往改善所有用户，尤其在键盘高频、弱网和临时受限情境。

颜色不能独自传达状态，拖拽要有替代操作，hover 内容要可聚焦和可关闭，超时要能延长。动态更新应适度宣布，避免 live region 轰炸。

组件通过自动检查不等于任务可完成。以真实辅助技术走完整任务，观察名称、顺序、状态变化与恢复。

### 十一、原型按风险选择保真度

纸面/线框适合验证结构和流程，高保真适合视觉、内容和复杂交互，代码原型适合键盘、响应式、性能和平台行为。不要在结构未定时投入精致动画，也不要用静态图验证焦点与异步状态。

原型明确哪些是真实能力、哪些是假数据。测试参与者若以为不可点击是自己错误，结论会失真。对高风险状态制作可触发路径，而不是口头描述。

记录每轮假设、变化和证据，避免设计迭代只剩最终稿。被否定的方案能解释为何当前边界存在。

### 十二、可用性测试验证任务

**可用性测试（Usability Testing）**让代表性参与者在接近真实的情境完成任务，观察行为、困难和理解。它不等于问“你喜欢吗”，也不要求大样本统计显著性才有价值。

测试计划包含目标用户、筛选标准、任务情境、成功标准、时间、提示规则和记录方式。任务避免泄露操作名称，例如说“找出支出最高的项目”，不要说“点击排序按钮”。主持人保持中立，让参与者思考出声但不教学。

记录完成/失败、关键错误、绕路、帮助、时间和主观信心。一个严重阻断可以比多个轻微偏好重要。结论写观察与影响，不把参与者性格当根因。

### 十三、研究偏差与伦理

内部员工熟悉术语，不能代表新用户；只招活跃客户会遗漏流失者。样本按关键行为与限制覆盖，说明不能推广到谁。远程测试要考虑设备、网络和隐私。

获得知情同意，说明录制、用途、保存期限与退出权。测试数据最小化并脱敏，不收集与研究无关的真实敏感信息。未成年人或高风险领域需更严格流程。

避免为了“证实方案”引导。把设计团队的假设提前写出，观察者独立记录，再共同归纳，减少权威影响。

### 十四、从发现到优先级

每个问题记录场景、证据、影响用户、发生频率、严重度和修复建议。严重度结合是否阻断、能否恢复、业务/安全后果，不只按出现人数。

聚类时保持原始证据链接，避免“导航不好”这类模糊总结。优先修复根因，例如术语和层级错误可能同时导致搜索、菜单和表单理解问题。

方案上线后用同任务复测。仅看转化率可能掩盖误操作；结合错误、取消、支持工单、可访问性和定性反馈。

### 十五、指标不是用户价值本身

点击率、停留时间和步骤数需要语境。帮助页停留长可能是认真学习，也可能是找不到答案；步骤更少可能把高风险确认删除。定义任务成功、质量和护栏指标。

漏斗找出掉点，不能解释原因；访谈和可用性观察解释机制。A/B 测试比较可量化方案，但不能验证明显违法、不可访问或欺骗性设计。

防止暗黑模式：未经理解的默认同意、难以取消、伪造紧迫感或隐藏费用即使提高短期转化，也损害用户自主和长期信任。

### 十六、交付给工程的完整状态合同

设计稿交付对象/术语、任务流、状态表、迁移条件、响应式规则、焦点、键盘、文案、数据边界和埋点语义。只交几张理想状态截图会迫使工程师猜所有失败路径。

工程评审反向检查 API 能否表达状态、服务端是否提供必要版本/权限、错误是否可区分、性能预算是否现实。发现约束后回到用户任务调整，而不是在实现里悄悄改变体验。

产品、设计、工程和测试共享同一状态名称。业务状态、请求状态和视觉状态分开，避免“disabled”同时表示无权限、加载和数据不合法。

### 十七、内容设计与本地化

界面文字是交互的一部分。按钮用明确动作，标题说明对象，错误解释原因和恢复；避免“确定”“操作失败”这类脱离上下文的词。术语与用户心智、帮助和客服一致，并为关键概念提供就近解释，而不是把所有名词堆在开头。

中文、英文和其他语言的长度、断行、数字、日期、姓名与复数规则不同。布局允许文本扩展，不能靠截断隐藏关键状态。时间说明时区与相对或绝对含义；金额显示币种并避免只靠小数格式猜测。

翻译不是字符串替换。语序可能改变组件组合，读屏名称也需整体校对。伪本地化、长文本和 RTL（如适用）应进入自动与人工测试，翻译更新与功能版本一起追踪。

### 十八、性能与感知连续性

交互延迟会改变用户判断：点击后无反馈会重复操作，布局跳动会点错。为关键任务定义响应预算，先保证输入及时反馈和主要内容稳定，再优化装饰。加载优先级与信息优先级一致。

乐观反馈只用于结果可预测、可回滚的低风险动作；高风险或服务端会改写结果时显示待确认。预加载和缓存不能泄露上一身份内容。离线或弱网下明确数据时间和能力，不把旧缓存伪装最新。

性能研究使用真实设备与网络，结合任务完成和 Core Web Vitals 等技术指标。只优化跑分却增加步骤、错误或不可访问，不是 UX 改善。

### 十九、组织决策与设计债务

每个重要交互决定记录问题、用户证据、业务与技术约束、选择、未选方案和复查条件。随着用户、数据和平台变化，过去正确方案可能失效；研究与指标触发复审。

设计债务包括术语分叉、状态遗漏、不可访问组件、无法撤销动作和只在口头存在的规则。按用户风险和重复范围治理，不只按视觉不一致。公共组件修复后仍要回归具体任务。

跨角色评审使用同一状态与任务语言，减少设计稿、接口和测试各自命名。决策有 owner，而不是“大家都负责”导致无人追踪。

对未采用的反馈也保存原因和复查条件，避免下一轮失去上下文后重复试错。

上线后的支持工单、搜索无结果、反复撤销和人工客服路径也是研究入口。将其关联到具体任务和状态，不把单条抱怨直接转成按钮；先确认影响范围和机制，再用小范围原型或改动复测。持续发现与阶段性研究互补，避免只在大改版前才询问用户。

### 二十、完整复核清单

确认目标用户和任务有证据；信息结构用用户术语；首次、空、加载、成功、错误、离线、无权限和未知结果齐全；反馈与系统阶段一致；危险动作可预防/恢复；键盘、读屏、放大和窄屏可完成；测试计划不引导且保护隐私；发现能追到改动与复测。

成熟 UX 的标志不是资料变少或界面更空，而是用户在正确时刻获得足够上下文，知道现在是什么状态、下一步会发生什么、失败后如何恢复。它以业务不变量约束方案，以可访问性保证入口，以真实任务证据持续修正。

# 为什么这段代码每次修改都要多花半天

## ARCH-04 技术债识别、优先级与偿还治理

订单系统有两份优惠计算规则。一次活动只改了结算页，客服页仍显示旧价格。团队修好差异后，下一次活动又要提醒所有人“记得改两处”。另一边，一个多年不动的报表模块虽然写法陈旧，却一直正确运行。应该先重写哪一个？回答这个问题，需要解释技术状态怎样增加未来成本，而不是按代码年龄排名。

本篇沿着一项债务从发现到关闭的过程，说明怎样写出可判断的债务条目、估计利息、安排偿还，以及确认成本确实减少。文中的订单系统、工时和日期均为教学假设，不是本站实际项目的测量结果。

### 学习前先确认

- 直接前置：[ARCH-01 质量属性、约束与架构权衡](../chinese-guides/arch-01-quality-attributes-constraints-tradeoffs.md#arch-01)，先知道质量目标、硬约束和成本如何共同影响选择，再讨论为什么值得偿还某项债务。

### 一、把代码评价改写成有后果的债务陈述

**技术债（Technical Debt）**是某种技术结构或实现选择使后续变化、运行或维护持续承担额外成本。早期为了按时交付而复制规则，可能是合理折中；后来两份规则分别演进，修改与核对成本越来越高，债务便需要重新处理。债务也可能来自当时不了解需求，或者外部环境改变，不必先证明有人做错了决定。

“规则代码很乱”无法支持排期。可以改成：“优惠规则分别由结算页与客服页维护；过去三次规则调整都要修改两处，其中一次漏改造成金额展示不一致；下季度预计还有六次同类变更。”这段话同时交代了位置、影响场景、证据和未来触发条件。别人可以核实它，也可以指出估计不成立。

判断额外成本必须有合理基线。若两处计算分别遵循销售报价与售后退款规则，强行合并反而制造条件分支；先确认重复的是同一种业务语义。真正相同的规则可以有一个权威计算入口，两个界面保留各自展示；业务语义不同的计算则应共享基础能力，而不是共享一个含糊的巨型函数。

旧报表是否属于高优先级债务，要看它是否频繁变化、是否仍可安全部署、是否有人能修复。年龄和写法只是调查线索。反过来，刚上线的新服务如果每次发布都需要三组人同步操作，也可能已经产生明显的架构债。债务衡量的是后果，不是新旧。

### 二、先分清今天必须修复什么

把所有工程问题放进同一个“技术债池”，容易让紧急问题排到遥远以后，也容易让个人偏好挤占必要工作。可先用下面四种问题判断处理入口。

| 观察到的情况 | 首先属于什么问题 | 当前动作 |
| --- | --- | --- |
| 已承诺的金额展示出现错误 | 缺陷 | 修复并核对受影响范围 |
| 两份规则让每次修改都增加核对成本 | 技术债 | 登记结构原因与偿还方案 |
| 可利用漏洞可能暴露用户数据 | 安全风险；若已发生则进入事故处理 | 按安全响应时限评估、控制和修复 |
| 希望支持一种尚未承诺的新报表 | 新能力 | 确认产品价值与范围 |

它们可以关联。一项缺陷修复只改正了本次价格，并没有消除规则分散的原因；漏洞补丁可能先用紧急升级解决，而长期无维护者的 Fork 仍需要退出计划。分别记录，才能知道哪个承诺已经完成、哪个风险仍存在。

扫描器报告两项 CVE，不能直接推出“有两项高优债务”，也不能直接忽略。需要核对实际安装版本、传递依赖路径、受影响功能是否可达、部署环境和修复方案。有明确利用风险时，先控制暴露面，不等普通债务排序会议。依赖核验的方法可接着读[沿依赖路径判断影响](../chinese-guides/aidev-07-dependency-source-security.md#三沿依赖路径找问题避免把漏洞安在错误的包上)。

测试债、数据债和知识债也需要具体后果。例如“缺少测试”还不够；“修改结算规则后只能人工核对二十种组合，且没有保存预期金额”说明了缺少哪种反馈。先补关键行为基线，再进行结构调整，通常比同时改规则与重写测试更容易解释结果。

### 三、用范围估计利息，而不是制造精确数字

**债务利息（Debt Interest）**指债务存在期间重复付出的额外成本。它可能表现为每次变更的返工、升级阻塞、故障恢复延迟或人工核对。偿还所需的一次性投入可以类比本金，但软件债务不会按固定利率自动增长：业务变化频率、人员熟悉程度和支持期限都会改变它。

假设核对两份优惠规则每次额外花费 1～3 小时，未来每月发生四次。整理权威计算入口预计投入 24～40 小时。下面只计算工程时间的粗略回收窗口，帮助判断哪些假设值得继续调查。保存为 `debt-window.mjs`，使用 Node.js 22 或更新版本运行 `node debt-window.mjs`。

```js example=arch04-payback
function paybackMonths({ repairHours, extraHours, changesPerMonth }) {
  if (![repairHours, extraHours, changesPerMonth].every(
    value => Number.isFinite(value) && value >= 0
  )) throw new Error('输入必须是非负有限数');
  const monthlyInterest = extraHours * changesPerMonth;
  return monthlyInterest === 0 ? null : repairHours / monthlyInterest;
}
const optimistic = paybackMonths({
  repairHours: 24, extraHours: 3, changesPerMonth: 4
});
const conservative = paybackMonths({
  repairHours: 40, extraHours: 1, changesPerMonth: 4
});
console.log(`${optimistic.toFixed(1)}～${conservative.toFixed(1)} 个月`);
// => 2.0～10.0 个月
console.log(paybackMonths({
  repairHours: 40, extraHours: 1, changesPerMonth: 1
}).toFixed(1));
// => 40.0
console.log(paybackMonths({
  repairHours: 40, extraHours: 1, changesPerMonth: 0
}));
// => null
```

第一条输出来自两个不同假设端点，不是统计置信区间。第二条只把变化频率从每月四次改成一次，保守回收期就从十个月变成四十个月。最后的 `null` 表示这套模型没有可计算的时间收益，并不代表系统可以永久不维护。安全支持结束和恢复能力下降，可能仍要求行动。

这个模型假设整理后额外核对成本全部消失，没有计入迁移期维护和折现，也没有把故障损失硬换成人时。因此不能把结果当投资回报保证。实际估计可保留迁移后的剩余成本，并写出哪些活动有记录、哪些只是访谈。若范围宽到足以改变决定，优先做一次小试验缩小不确定性；不要先编造一个看似精确的均值。

### 四、台账让后续负责人能继续判断

**技术债台账（Technical Debt Register）**保存债务状态、影响证据、责任人和下一步决定。它可以是现有任务系统中的一类条目，不必另建平台。重要的是下一位工程师接手时，能知道为什么它存在、现在选择什么、什么时候必须复查。

下面是一条完整但精简的模拟记录：

| 字段 | 示例内容 |
| --- | --- |
| 标识与位置 | DEBT-17，结算与客服的优惠规则入口 |
| 后果与证据 | 同类调整需改两处；三次变更记录中一次漏改 |
| 当前判断 | 业务负责人确认两处应使用同一份规则版本 |
| 利息与不确定性 | 每次额外 1～3 小时；下季度变化次数仍待确认 |
| 处置与负责人 | 先抽出纯计算入口，由订单团队负责人推进 |
| 依赖与资源 | 需要业务提供历史样例；预计 24～40 工时 |
| 临时控制 | 发布清单核对两处版本，四周后重新评估 |
| 关闭证据 | 两个调用方接入同一入口，旧规则删除，同类变更不再双改 |

不要把漏洞利用细节、真实凭证或用户数据复制进公开台账；可链接受控的安全记录。一个条目可以连接事故、ADR、需求与修复提交，正文只保留决定需要的摘要。

状态可以使用“待核实、已排期、控制中、接受、已解决、已失效”，这只是本篇建议的工作流，不是行业协议。“接受”必须带理由、承担后果的负责人和复查触发条件；“控制中”表示风险有所降低，不等于根因消失；“已失效”可以是相关功能已退役，不必伪装成完成重构。状态本身不能代替证据。

### 五、排序先看底线，再比较值得投入的窗口

一份列表里同时有可利用漏洞、重复规则、构建等待和即将删除的模块，单一加权总分很容易掩盖差别。先把安全、合规、恢复等不能妥协的底线单独处理，再在可选择的工作之间比较利息、投入、依赖和机会窗口。评分可以帮助对齐看法，但权重与评分依据仍需要人解释。

设想团队只有一周可支配时间。优惠规则重构预计四天，升级关键依赖预计两天，整理旧报表预计三天。如果依赖即将失去安全支持，升级有明确截止；优惠规则在下次活动前处理才能减少重复修改；报表下个月就停用，则可以优先完成退役核对，而不是先美化内部结构。决定来自时间关系，不来自谁把工单写得更吓人。

十二个过期依赖也不必十二个同时启动。先识别运行时关键路径、构建链、被锁住的传递依赖，以及有无维护者的 Fork。一个存在十八个月的 Fork，可能阻塞其他五个依赖升级，这时它是共同根因；反过来，合并所有升级为一个巨型改动会使回归难以定位。先用最小升级验证关键兼容边界，再安排可独立回退的序列。

每周只有两小时维护容量时，可以承诺完成清单核实、找出负责人、验证一个最小升级，而不能在没有估算时承诺本周解决所有债务。若支持期限前无法完成必要工作，应把资源缺口、继续运行的影响与可选降级交给有权调整范围的人决定。把“不够时间”写进台账，是让风险可见，不是转移责任。

### 六、偿还、控制、接受和退出各有完成条件

偿还是改变产生额外成本的结构，例如收拢同义规则、升级受支持依赖、删除循环调用。控制是在暂时不能解决根因时限制后果，例如冻结一个高风险入口、缩小访问范围、增加可观测性。接受是在明确条件下继续承担成本。退出则是删除功能、替换供应商或停止维护一个不再需要的组合。

四种策略可以分阶段出现。旧编辑器 Fork 没有负责人，先指定临时维护者并限制新增扩展；随后验证上游版本能否满足必要功能；能够替换就迁移，暂时不能就登记缺口与结束日期。监控和注释没有消除 Fork 维护成本，不能据此关闭债务。

选择最小能改变根因的切片。优惠计算可以先整理输入输出与历史样例，接入一个调用方，观察后再迁另一个；不要同时更换 UI 框架、数据库和规则引擎。需要迁移数据或外部副作用时，应先读[回滚窗口由数据和在途动作决定](../chinese-guides/arch-03-progressive-migration-strangler-compatibility.md#七回滚窗口由数据和在途动作决定)。部署旧制品不一定能恢复已经改变的数据语义。

控制和接受都要说明会触发什么改变：业务访问量上升、出现新漏洞、维护者离开、上游停止支持，或者原定退役被取消。仅写“下季度再说”没有解释何时判断改变。如果某个触发已发生，应重新决策，而不是自动延期旧结论。

### 七、完成修复以后，仍要验证成本是否下降

**退出条件（Exit Criteria）**指这项治理工作可以结束或转入日常维护时，必须具备的证据。它们应在动手前写出，以免最后把“合并了一批提交”当作偿还成功。规则债的退出条件包括权威入口明确、旧分支移除、两个调用方使用同一规则版本、必要的错误与边界用例通过，以及后续同类变更不再需要双改。

依赖升级的退出条件则不同：生产所用制品解析到目标版本，必要场景通过，回滚路径可用，Fork 补丁有明确去向，支持矩阵与责任人已经更新。版本更新工具可以发起升级提议；它不能替团队证明业务兼容、部署环境正确或许可证条件满足。告警消失也可能只是扫描范围改变。

收益比较要保持口径。若重构前记录三次复杂活动的全部处理时间，重构后只记录一次简单活动的编码时间，数字下降无法归因于重构。可以分别记录需求澄清、规则修改、双端核对、等待发布四段时间，再比较复杂度相近的任务。样本少时写“观察到核对步骤减少，长期工时收益待继续记录”，比宣布节省百分比可信。

若新入口引入了额外服务故障，可能只是把修改成本转成运行成本。复查需要同时看原目标与质量护栏。已解决条目保留记录；发现新问题可以关联新债务，不能为了保持关闭数量好看而隐藏它。台账数量上升有时说明识别更诚实，并不等于质量变差。

### 八、把债务治理接回日常交付

每次需求评审可以问：这次变化会不会再次支付已知利息？每次事故复盘可以问：临时修复后哪个结构原因仍在？每次升级可以问：有没有把一个临时 Fork 变成无人负责的长期产品？这些问题把债务治理接回真实工作，而不是一年一次大清理。

对产品同事的说明应包含可选择的后果。例如：“下次活动前投入三天整理规则，预计减少后续双端核对；若先交付活动，本次继续人工核对，并在四周后复查。”同时交代估计范围和可能延期，允许对方根据业务时机参与决定。不要用无法验证的“以后会出大事”代替证据。

治理责任也不能永远压在最熟悉系统的人身上。一个条目无人能独立验证关闭，说明还缺少上下文、访问权限或演练机会。技术债与交接问题可以关联，但各自的完成条件要清楚：代码改完是一份证据，另一位工程师能接手运行是另一份证据。

最终希望得到的不是“零技术债”，而是团队知道哪些额外成本正在支付、哪些风险需要控制、哪些选择已经被接受，以及下一次变化发生时谁来重新判断。这个能力比一次大规模重写更能支持长期演进。

### 带着问题回看

1. “旧模块写法过时”还缺哪些事实，才能成为可排序的债务条目？
2. 规则修复后金额正确，为什么规则分散的债务可能仍没有解决？
3. 若变化频率降为原来的四分之一，时间回收模型怎样变化？什么风险不能靠这个模型决定？
4. 依赖升级、临时控制和接受风险，各自需要什么关闭或复查证据？

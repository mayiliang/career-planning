# AI 流式传输与增量界面知识点讲义

## AIAPP-02 流式响应、SSE 与增量渲染

流式回答不是把完整字符串切成许多小段再显示。网络字节、文本解码、协议事件、模型增量、Markdown 结构和最终业务消息是六个不同层次；任何一层都可能断开、重复、迟到或只完成一半。可靠界面必须让临时内容保持临时，让用户随时取消而不丢草稿，让断线与未知终态可恢复，并在性能、安全和可访问性之间建立明确合同。

### 学习前先确认

- 直接前置：[AIAPP-01 模型接口、指令与上下文边界](../chinese-guides/aiapp-01-model-interface-instructions-context-boundaries.md#aiapp-01)。流式只是模型运行时的一种传输方式，仍需请求身份、能力协商、错误分类、取消、隐私和版本证据。
- 直接前置：[NET-01 浏览器网络、Fetch 与可靠性](../chinese-guides/net-01-browser-network-fetch-reliability.md#net-01)。本讲直接使用 HTTP、连接、流读取、AbortSignal、重试、缓存和未知结果边界，不重复讲通用网络基础。

### 一、先区分六层“块”

TCP 或 HTTP 传来的字节块可以在任意位置切分 UTF-8 字符；文本块也可能把一条 SSE 事件、JSON 或 Markdown 标记切开；一条供应商事件可能包含多个模型 token；业务消息只有收到明确终态并通过校验后才可保存。把任一网络 chunk 当完整 token 或完整 JSON 都会产生乱码和解析错误。

管道应写成字节流→增量文本解码→协议帧→应用事件→消息状态→渲染提交。每层有独立缓冲和错误，不在 UI 组件里用 `split('\n')` 同时完成所有职责。事件日志保存原始序号与类型，渲染层只消费标准内部事件。

正常测试也要故意在中文多字节字符、`\n`、SSE 空行、JSON 字符串转义和 Markdown 标记中间切块。若同一语义在不同分块下结果不同，协议实现不成立。

### 二、SSE 提供标准单向事件格式

**服务器发送事件（Server-Sent Events）**使用 `text/event-stream` 传送 UTF-8 文本事件，字段可包含 `event`、`data`、`id` 和 `retry`，空行结束一条事件。浏览器 `EventSource` 能自动重连并携带 Last-Event-ID，但只有服务端保留并理解该 ID 时，才真正具备断点恢复。

EventSource 适合服务端到浏览器的长期单向通知；请求通常由 URL 建立，认证与自定义请求体能力有限。模型生成常需要 POST、JSON 请求体、自定义头和 AbortSignal，因此也常用 `fetch` 读取响应 `ReadableStream`，再自行解析 SSE 或其他事件格式。

SSE 不等于模型协议，也不保证业务恰好一次。代理缓冲、空闲超时、重连、服务端副本和客户端重复都会影响到达；应用仍需 stream ID、序号、终态和幂等。

### 三、选择 SSE、fetch stream 或 WebSocket

原生 EventSource 提供简单重连和事件语义，适合 GET 单向流；fetch stream 便于 POST、认证头、请求体和精确取消，但重连、帧解析与检查点由应用实现；WebSocket 提供全双工长连接，适合频繁双向实时控制，却带来会话、心跳、恢复和背压复杂度。

不要因为“AI 很实时”默认 WebSocket。一次请求一次响应的文本生成通常用流式 HTTP 足够；语音、协作或持续工具交互才可能需要双向协议。选择依据是方向、认证、代理兼容、重放、消息频率和运维能力。

传输可替换时，内部事件合同保持稳定。页面不读取供应商的 `[DONE]` 或私有字段，由服务端适配成 started、delta、tool、completed、failed 等语义事件。

### 四、事件合同需要身份、序号和终态

每个事件至少包含 streamId、attemptId、单调 seq、type、payload、serverTime 和协议版本。started 声明请求与能力；text.delta 追加文本；structure/tool 采用独立类型；usage 可更新统计；completed、failed、cancelled 是互斥终态。

客户端只接受当前尝试的事件，维护最后连续序号而非最大见过序号。收到 4、6、5 时先缓冲 6，处理 5 后再推进到 6；重复 5 去重。终态后拒绝迟到 delta，并记录异常，不能把晚到内容悄悄接到完成消息。

事件演进向后兼容：未知可选事件安全忽略并保留观测，未知关键版本停止并提示刷新。payload 运行时校验，不能让半个工具参数进入可执行状态。

### 五、增量解码要跨网络块保存状态

`TextDecoder` 的 streaming 模式或 `TextDecoderStream` 能在多字节字符跨块时保存解码状态。读取结束时显式 flush，非法编码根据协议选择替换或失败；SSE 规范固定 UTF-8，不能通过响应头偷偷换编码。

帧解析器保留未完成行，兼容 CRLF、LF 和末尾无换行；多个 `data:` 行按规范组合。注释心跳不进入模型文本，id 只在完整事件后更新。JSON 在完整 data 帧到达后解析，不对每个字节尝试 `JSON.parse`。

设置单事件、单行、缓冲和总响应上限，防止永不换行或巨大帧耗尽内存。超过上限进入明确错误并中止连接。

### 六、临时消息与最终消息必须分离

界面状态可以是 idle、connecting、streaming、recovering，最终进入 completed、failed、cancelled 或 incomplete。临时 buffer 属于 attempt，只有 completed 且结构校验通过后，才提交为持久消息版本。页面刷新或会话同步不会把半截内容伪装成正式答案。

用户可以查看和复制临时文本，但界面标明“生成中/未完成”。工具卡片在参数完整、授权和确认之前只是提议；引用在来源元数据完整前不显示为可验证链接。失败后保留安全草稿，并提供继续、重试、放弃或新建选择。

每次重试建立新 attemptId，旧尝试的迟到事件被拒绝。若选择基于部分回答继续，把原文本作为有版本的输入，而不是继续使用已经失效的网络流。

### 七、Backpressure 防止接收速度压垮界面

**背压（Backpressure）**是下游处理速度低于上游生产速度时限制、缓冲、合并或暂停工作的机制。浏览器读取网络、JSON 解析、Markdown、语法高亮、DOM 更新和持久化都可能成为瓶颈；每个 token 都触发响应式全树更新会让页面越来越慢。

网络层按可控节奏读取，事件层设置队列上限；文本 delta 可合并，但工具、引用、错误和终态不能丢。渲染在动画帧或短时间窗批量提交，后台标签页降低频率，最终事件到达时 flush。队列过大时暂停读取、降低可选处理或中止并说明资源限制。

背压不是永远延迟。记录队列长度、最老事件等待、批量大小和渲染耗时，确保终态和取消优先。若解析持续跟不上，服务端应降低事件粒度或限制输出，而不是让浏览器积累无限内存。

### 八、Incremental Rendering 只提交稳定边界

**增量渲染（Incremental Rendering）**在内容到达时只更新受影响的稳定部分，而不是每次重建整个答案。纯文本可追加文本节点；Markdown 需要能保留解析状态的流式解析器，或只在段落、代码块等稳定边界提交。

普通 Markdown 解析器反复解析全部历史并替换 `innerHTML` 会增加 CPU、布局和焦点抖动，还可能执行不安全 HTML。渲染器禁用原始 HTML或对合并结果执行严格安全策略，链接限制协议；危险内容被移除时停止并显示失败，不能继续输出被改写的“原回答”。

代码高亮、公式和图表在块闭合后延迟处理，并设大小/时间预算。更新节点保持稳定 key，避免读屏和选择区每次重建。最终完成时进行一次完整解析与一致性校验。

### 九、TTFT 与总耗时衡量不同体验

**首词元时间（Time to First Token）**从用户提交到第一个可用模型增量到达，包含排队、上下文组装、网络和模型启动；它不代表回答完成。还应记录首可见内容、首有用结构、生成速率、总耗时、取消响应和恢复时间。

过早发送无意义空白或“正在思考”不能优化 TTFT。首事件可先说明已接收，但指标分开；用户真正感受到的是有用内容。输出很快开始却持续一分钟，同样可能不可接受。

按任务、模型、地区、输入规模和版本看分位数，关联服务端 trace。前端 Performance 标记与 stream/attempt ID 连接，不能只用供应商返回的模型时间解释全部等待。

### 十、取消是状态转移而不只是关闭按钮

点击取消立即把当前 attempt 标为 cancelling，停止页面渲染并触发 AbortSignal；服务端取消供应商和可取消工具，最终返回 cancelled 或说明无法确认。迟到事件按 attempt 状态拒绝，用户已编辑草稿绝不被覆盖。

取消按钮在 connecting、streaming 和 recovering 都可用，键盘和读屏能操作。完成与取消竞态用服务端终态和单一原子转移解决：先提交的有效终态获胜，另一事件记录但不改变已呈现结果。

客户端断开不一定代表用户取消，例如网络切换或页面冻结。服务端根据心跳、任务类型和保留策略决定继续或中止，不能把所有连接丢失都写成用户取消。

### 十一、断线恢复依赖服务端保留和检查点

客户端维护最后连续确认序号，重连携带 streamId、attemptId 和 checkpoint。服务端若仍保留事件，从下一序号重放；客户端去重并验证缺口。保留窗口、最大重放量和过期状态在合同中明确。

若服务端不支持恢复，不假装继续同一答案。把部分内容标为 incomplete，允许保留草稿、重新生成或放弃；新生成建立新身份。工具动作发生后断线时先查询业务状态，避免重复执行。

代理超时、服务器重启、移动网络切换、标签页后台与刷新都要测试。恢复不只拼文本，还要恢复工具、引用、用量和终态的一致状态。

### 十二、自动滚动要尊重用户阅读位置

只有用户仍接近内容底部且未主动上滚时才跟随新内容。用户上滚、选择文字、聚焦代码或展开引用后暂停自动滚动，并提供“回到最新”按钮。新 token 不抢焦点，也不把滚动容器强制拉到底。

状态更新对读屏节流播报，例如开始、工具等待、完成和失败，而不是朗读每个 token。使用语义化 live region，最终内容保持正常文档结构；减少动态偏好下关闭光标闪烁和不必要动画。

虚拟列表和长回答要保持锚点稳定。图片、代码高亮和字体加载造成高度变化时，避免把用户位置推走；移动软键盘出现时也不把输入区和回答互相遮挡。

### 十三、持久化与跨标签同步只接受稳定版本

数据库保存请求、attempt 状态、连续 checkpoint 和最终消息，临时 delta 可按风险选择内存、短期日志或批量快照。每个持久更新带版本条件，多个标签页不能互相覆盖；最终提交幂等。

页面刷新先读取服务端状态：运行中则恢复，已完成则加载最终版本，未知则提示查询或人工处理。不要仅凭本地缓存把旧临时 buffer 显示为最新事实。会话删除与数据权利传播到事件存储和日志。

跨设备继续时保留用户草稿和滚动意图，但不必同步每个动画帧。同步单位是稳定消息、状态和检查点，而不是 DOM 快照。

### 十四、用事件重放证明整个流可靠

建立确定事件夹具：Unicode 跨块、重复 seq、乱序缺口、final 后迟到、结构块中断、分类器阻断、取消竞态、代理断线、服务端无法重放、用户上滚和页面刷新。对同一日志使用不同网络分块，最终消息和状态必须一致。

验证 DOM 没有未净化 HTML、重复文本或半个工具；用户草稿和焦点不丢；队列有上限；指标、审计和服务端状态可关联。再在低端设备与弱网测 TTFT、批量渲染、内存和取消响应，修复后用原夹具回归。

学完后，你应能区分字节、文本、协议、模型和业务消息，选择 EventSource、fetch stream 或 WebSocket；能设计带序号、检查点和终态的事件合同，处理增量解码、背压、安全 Markdown、取消、恢复、滚动、持久化和观测，并解释为什么“逐 chunk append”无法构成可靠流式产品。继续查证可参考 [WHATWG Server-sent Events](https://html.spec.whatwg.org/dev/server-sent-events.html)、[MDN TextDecoderStream](https://developer.mozilla.org/zh-CN/docs/Web/API/TextDecoderStream)、[Chrome 流式 LLM 响应渲染指南](https://developer.chrome.com/docs/ai/render-llm-responses?hl=zh-cn)与所选模型供应商的当前流事件说明。

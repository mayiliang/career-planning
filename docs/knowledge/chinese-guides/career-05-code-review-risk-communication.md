# 职业表达知识点讲义

## CAREER-05 代码评审、风险判断与工程沟通

代码评审的目标不是证明评审者更聪明，也不是替自动格式化工具找空格。它通过独立视角降低安全、数据、功能、性能和维护风险，同时传播上下文和形成可追踪决定。高质量评论说明受影响行为、证据、严重度和下一步；证据改变时，评审者也愿意修订或撤回。

### 学习前先确认

- 直接前置：[GIT-03 原子提交、远端协作、PR 与并行工作区](../chinese-guides/git-03-commits-remotes-pr-worktrees-collaboration.md#git-03)。本讲直接使用提交边界、PR 生命周期、自动检查和合入策略；分支与对象基础由该讲递归链接。

### 一、评审先理解变更意图

开始看 diff 前读问题、约束、方案、测试和回滚。若 PR 没有足够上下文，先请求补充，不要在错误目标上评论大量实现细节。

复述变更：谁的什么行为发生改变，哪些路径明确不处理，风险最高处在哪里。作者确认后再深入，可以早期发现需求理解分歧。

评审不是重新设计整个系统。超出当前范围的改进作为后续建议，除非现有方案会造成不可接受风险。

### 二、按风险安排阅读顺序

先看权限、数据写入、迁移、并发、支付、缓存和公共 API，再看普通逻辑与可读性。变更行数小也可能高风险，例如删除一个授权条件。

**风险分级（risk classification）**可包含：安全/隐私、数据损失、功能正确性、可靠性、性能、兼容、可维护与风格。分类帮助决定是否阻塞、需要什么证据和由谁评审。

不要把个人偏好标成“严重性能问题”，也不要因代码看起来简单就跳过数据边界。

### 三、从调用者和数据流阅读 diff

查看新增 API 谁调用、输入从哪里来、输出到哪里去，异常和取消怎样传播。只读改单文件容易漏掉类型、测试、配置、生成物和部署。

公共函数改变默认值时搜索全部消费者；数据库字段变更检查迁移、旧版本、回滚和数据填充；前端权限变化继续追到服务端授权。

diff 展示变化，不展示未变却受影响的代码。利用模块图、引用和测试找出影响面。

### 四、一条评论包含位置、行为、证据和请求

“这里不太好”无法行动。可以写：

> 阻塞：这个查询只按 `courseId` 过滤，跨租户用户若猜到 ID 会读取其他租户记录。请在服务端加入 `tenantId + owner` 条件，并补一条跨租户返回 404/403 的负例测试。

它说明位置、攻击路径、严重度、最小修复和验证。若不确定，改成问题并说明需要什么证据，而不是用肯定语气制造事实。

评论聚焦代码和行为，不评价作者能力。用“这个分支会……”而不是“你怎么又……”。

### 五、区分阻塞、建议和疑问

- 阻塞：合入会产生明确不可接受风险或违反既定合同；
- 建议：有收益但可以由作者权衡或后续处理；
- 疑问：信息不足，需要确认意图或行为。

标签让作者安排处理，也防止所有评论都被当成硬要求。团队可以约定 `must`、`suggestion`、`question` 或严重度，但含义需一致。

一个纯命名偏好不应阻塞，除非违反会造成真实兼容或维护风险的规范。反过来，授权和数据损失不能被模糊成“nit”。

### 六、证据强度匹配风险

功能问题用失败用例、规范和调用链；性能问题用同条件基准和真实 profile；安全问题用输入、信任边界和可达攻击路径；兼容问题用支持矩阵和消费者。

“我感觉会慢”不足以阻塞。可以请求基准或建议保持简单实现。若存在明显 O(n²) 且数据规模已知，也应写出规模和路径。

安全问题避免在公开评论放可利用秘密或真实用户数据，按团队安全渠道处理。

### 七、测试评审关注预言而非数量

检查测试是否证明新合同、旧实现是否会失败、异常与边界是否覆盖。十个只断言 mock 调用的测试不一定比一个用户行为回归更强。

评审测试替身是否位于稳定边界，是否使用真实时间和共享状态，快照更新是否经过阅读。对删除测试，确认对应合同真的移除，而不是为了让 CI 绿。

没有测试不自动阻塞所有变更，但作者应说明替代证据和风险。高风险且可自动化的行为通常需要回归门禁。

### 八、错误和恢复路径与成功路径同等重要

评审 loading、空、无权、超时、取消、重复和部分成功。异步代码检查迟到响应、卸载和幂等。迁移检查中断与回滚。

成功截图无法证明这些边界。要求最小故障注入或测试，并检查用户有下一步，而不是只显示“出错了”。

服务端返回错误码、前端映射文案和监控分类应一致，避免一个异常在各层失去语义。

### 九、可维护性评论要联系未来变化

抽象不是越多越高级。只有重复背后有稳定概念、公共合同或变化轴时才建议抽取。两个当前相似但未来方向不同的组件不应强行共享。

评论指出具体成本：新增第三种状态会修改五处分支；函数同时解析、授权和写库导致失败难隔离。再提出可选结构和迁移范围。

不要要求作者在当前 PR 重写整个遗留模块以满足理想架构。记录债务、风险和 owner，比无限扩大范围更负责。

### 十、评审大 PR 先建立分层视图

先看提交或文件分组：纯移动、生成物、合同、实现、测试。要求作者提供阅读顺序。可建议拆分，但拆后必须保持可构建和迁移安全。

忽略空白或生成文件能减少噪音，随后仍检查生成来源和产物同步。对于自动重命名，验证引用和运行结果，不因“机械变化”完全跳过。

若 PR 大到无法可靠评审，阻塞理由是审查风险而不是行数本身，并给出具体拆分方案。

### 十一、异议通过目标和证据解决

作者反驳时先确认双方目标是否相同。评审依据旧假设就更新评论；证据不足则降级为建议或撤回。坚持错误意见会破坏信任。

若候选都有代价，记录方案、证据、决定、owner 和回顾条件。无法在时限内一致时，升级给代码 owner 或架构责任人，不把讨论变成人格竞争。

作者也应对每条阻塞提供修改、反证或接受风险的明确回应，不能只点 resolved 隐藏未处理问题。

### 十二、决定状态需要闭环

评论可经历：未审、收集证据、阻塞/建议/疑问、已处理或延期、已验证。代码更新后原结论可能失效，评审者回到证据而非沿用旧判断。

“已修复”需要相同失败测试通过、攻击路径关闭或基准满足。回复“done”不是验证。延期建议进入可追踪任务，明确是否阻止当前发布。

平台的 resolved 状态只是界面标记，决定记录仍应可回查。

### 十三、批准意味着对当前 commit 的判断

批准应对应看过的差异和检查。作者新增重要提交后可能需要重新评审。保护规则可要求 dismiss stale approval，但评审者仍需知道最终合入内容。

“LGTM”可以用于低风险清晰变更，但高风险 PR 应总结已检查范围和残余风险。批准不意味着保证无缺陷，而是现有证据满足团队门槛。

评审者不熟悉某领域时说明边界，请相应 owner 加入，不要默默批准。

### 十四、代码所有权分配专业责任

**代码所有者（code owner）**帮助找到熟悉边界的人，不代表其他人不能评审，也不应成为单点瓶颈。owner 需要轮换、文档和继任。

跨模块变更让每个 owner 看自己的局部，还需要一位集成人检查端到端合同。多人批准的并集不自动覆盖交互风险。

紧急旁路要有授权、记录和事后补审，不能永久依赖管理员合入。

### 十五、AI 生成代码需要相同甚至更强的范围检查

AI 可一次修改许多文件，复制过时 API、遗漏权限或声称不存在的测试。评审先确认需求来源、文件所有权和真实 diff，再运行门禁并验证关键行为。

不要接受“模型说已测试”作为证据，也不要把提示文本当实现规格。生成代码仍由提交者负责，引用外部代码还需许可与来源检查。

AI 辅助评审可以列候选风险，但可能产生误报或泄露私有代码。使用受批准工具、最小上下文并由人核验证据。

### 十六、评审沟通兼顾清晰和尊重

文字缺少语气，使用具体、中性的行为描述。对教学性解释与必须修改分开，避免长篇展示知识使关键风险淹没。

高延迟评审会阻塞交付，团队约定响应时间、替代 reviewer 和升级路径。作者通过小 PR、清楚描述和自审降低成本；评审者及时说明暂时无法处理。

公开讨论技术决定，私下处理敏感人员问题。尊重不是降低标准，而是让证据更容易被接受。

### 十七、合入后仍要观察结果

评审判断基于提交前证据。合入和发布后检查主线、制品、监控和用户任务；出现问题关联回原 PR，补回归和决定，而不是用“已经评审过”否认。

复盘高影响漏检：是上下文缺失、规则未覆盖、时间压力、owner 空缺还是证据误读。改进流程，不以个人漏看作为终点。

### 十八、衡量评审系统而非评论数量

可观察首次响应时间、合入周期、阻塞问题类型、返工、漏检和知识分布。评论越多不代表质量越高，快速批准也不代表效率。

指标用于发现瓶颈，不能排名个人“挑错能力”。若团队因指标拆碎无意义评论或避免批准，度量已经伤害目标。

定期审查规范是否仍适用，自动化机械规则，把人力留给风险与设计。

### 进阶：分布式团队需要异步上下文

跨时区评审不能依赖作者随时在线口头解释。PR 描述、设计决定、运行步骤和证据应自包含到下一位评审者能继续。录屏可辅助复杂交互，但文字仍提供可搜索结论和无障碍替代。

评论一次提出完整问题和期望，避免每天只追问一个缺失字段。作者更新后总结关键变化和未解决项，减少评审者重新阅读全部对话。紧急时安排同步会议，会议结论回写 PR。

时区不应成为降低标准的理由；通过小批次、明确 reviewer 和响应 SLO 规划等待。长期无人可评的模块说明 ownership 与继任存在风险。

### 进阶：评审需要识别认知偏差

熟悉作者容易过度信任，陌生代码容易过度挑剔；大段复杂代码会让人忽略最后的小权限变化；已经投入很多时间会使团队不愿否决方案。使用风险清单、轮换 reviewer 和独立证据降低这些偏差。

先写自己的理解再看其他评论，可减少从众；但不要重复已经解决的问题。高风险变更要求领域和安全等不同视角，而不是简单增加同背景人数。

### 进阶：隐私与日志也属于 diff 审查

新增埋点、错误日志和 AI 上下文时，检查采集目的、字段最小化、脱敏时机、保留、访问和删除。前端 console、CI 附件和截图也可能泄露令牌或用户数据。

评论应指出具体数据路径和信任边界，不笼统说“注意隐私”。必要时阻塞并邀请隐私/安全 owner。测试使用合成数据，PR 描述不粘贴真实记录。

删除日志字段也要考虑可观测与事故调查，平衡通过 schema 和采样设计完成，不由个人在评审中临时决定。

### 进阶：好评审也肯定正确的关键决定

只留下负面评论会让作者不知道哪些边界值得保留。对清晰的回滚、有效测试或简化方案给出具体肯定，帮助团队传播模式。它不是礼貌性“写得不错”，而是指出为什么降低风险。

评审结束可总结阻塞已关闭、建议延期和接受的残余风险。这份摘要使未来维护者理解当时决定，也让批准不只是一个按钮状态。

### 进阶：评审深度要与可逆性和爆炸半径匹配

同样一百行差异，内部样式调整、认证规则、数据库迁移和 CI 权限的风险完全不同。评审计划应考虑影响用户、数据可逆性、权限扩大、运行可见性和回退速度。高风险变更要求领域 owner、安全或运维视角，分阶段发布并准备回退；低风险变更则避免用不成比例的流程拖慢反馈。

“有测试”也要问测试针对哪个风险。迁移需验证新旧版本并存、部分失败和重复执行；权限变更需验证越权负例；缓存修改需验证版本错配与失效。评审者不必亲自重跑所有流水线，但要确认检查对应当前 commit、输入可信且失败会阻止合入。

可逆性不是只看能否 `git revert`。代码可逆但数据已删除、消息已发出或客户端已缓存时，回退提交无法恢复世界状态。PR 应列出外部副作用、兼容窗口、观察指标和停止条件。评审意见围绕这些具体后果，才能从代码风格上升为工程风险判断。

若剩余风险被接受，记录接受者、理由、期限和后续保护，不用“之后再看”结束。风险决定可被重新评估，也不应隐含转嫁给值班人员。

### 进阶：评审吞吐取决于批次与等待，而非催促次数

从 PR 创建到合入的时间通常包含排队、理解、修改、检查和再次等待。只要求 reviewer 更快响应，可能增加上下文切换却没有减少返工。观察每一阶段，若理解时间长就改善描述和拆分；若反复修改就更早对齐接口；若检查排队则调整流水线容量。目标是缩短安全决定的总时间，不是提高评论数量。

评审负载也要可持续。关键模块至少培养第二位 reviewer，轮换值班并为深度评审保留时间。长期把所有高风险变更交给一个人会形成单点故障，也让其批准变成形式。文档、测试和清晰边界应降低知识转移成本，但不能假设读过说明就拥有同等领域判断。

### 学完后应能说明

你应能从需求和数据流建立评审范围，按风险决定阅读顺序，并写出包含行为、证据、严重度和验证方式的评论；能处理异议、修订错误判断并闭环决定。还应能区分自动检查、代码 owner、人工批准和发布观察的责任，使评审成为可追踪的工程风险控制，而不是风格争论。

# 职业表达知识点讲义

## CAREER-05 把代码评审写成可行动的反馈

“这里不太好，建议优化一下。”作者读完不知道哪里会出错、怎样重现，也不知道这条意见是否阻塞合入。另一种极端是列出很多格式偏好，把真正的越权、数据覆盖或恢复问题淹没。

代码评审的任务，是让一项具体变更在证据充分、责任清楚的条件下进入主线。这篇从一段会被旧结果覆盖的代码开始，演示怎样读变更、验证风险、写评论并完成复核。

### 学习前先确认

- 直接前置：[GIT-03 提交与 PR 协作](../chinese-guides/git-03-commits-remotes-pr-worktrees-collaboration.md#git-03)。本讲使用提交边界、PR、自动检查与合入概念。

**下面的 PR、代码片段、人员和评论都是教学模拟。** JavaScript 例子可用 Node.js 运行，不依赖真实服务，也不需要创建远端 PR。重点在提出能核对的问题，不是在对话里实际向他人发送评论。

### 先复述变更想解决的问题

开始看 diff 前，先用一句话确认预期行为。本例的变更是：“用户从资料 A 切到资料 B 后，页面只显示最后一次选择对应的结果。”这句话给出了判断依据。

如果 PR 描述只有“重构请求逻辑”，评审者还不知道哪些行为应保持、哪些会改变。作者可以补上触发场景、旧行为、新行为、涉及边界和验证。背景不需要很长，但应让没有参加讨论的人能继续阅读。

例如模拟 PR 描述可以写为：

> 切换资料后，较早发出的读取可能较晚返回，覆盖当前选中资料。此变更只允许最新一次读取提交结果。通过手动按 B、A 顺序交付响应，核对旧实现显示 B 后又显示 A，修改后只显示 B。

这段描述包含可验证的预期。它没有把“已经用了 AbortController”当成结果，也没有顺便承诺保存请求幂等、权限安全或所有网络异常都已解决。

### 按风险与数据流安排阅读顺序

文件大小不是风险大小。一个只改一行的租户筛选条件，可能比几百行纯样式整理更重要。先沿输入、信任、状态变化和输出读一遍，再看局部写法。

| 变更位置 | 优先追问 | 适合寻找的依据 |
| --- | --- | --- |
| 请求输入与权限条件 | 身份来自可信来源吗，对象范围检查在哪里 | 接口约定、服务端路径、跨身份反例 |
| 状态更新 | 哪个请求还有资格提交结果 | 操作顺序、响应顺序与可观察状态 |
| 写入、迁移与删除 | 能否部分成功，回退是否兼容 | 数据不变量、事务与恢复说明 |
| 错误处理与日志 | 用户如何恢复，是否记录敏感字段 | 失败路径、字段来源、日志采集位置 |
| CSS 或交互 | 长文本、焦点、窄面板是否破坏任务 | 真实布局与键盘路径 |

本例属于读取结果的提交顺序问题。查看调用者是否在资料切换时启动读取，回调是否能更新当前界面，以及组件离开后谁让请求失效。只看 helper 内部，很可能错过上层仍保留旧回调的情况。

评审深度还取决于影响范围与可逆性。文案调整通常不需要完整故障演练；不可逆数据迁移不能仅凭本地构建通过批准。机械格式交给既有工具，把人力留给这次变更真正可能伤害的行为。

### 用可控顺序把疑问变成反例

先运行下面的完整例子。load 返回等待手动完成的 Promise，模拟两次读取；它不是随机计时，也没有实际网络。

```js example=career05-stale-result
function createReader(load, show) {
  return async (id) => {
    const value = await load(id);
    show(id, value);
  };
}
const complete = new Map();
const shown = [];
const open = createReader(
  (id) => new Promise((resolve) => complete.set(id, resolve)),
  (id, value) => shown.push(`${id}:${value}`),
);
const a = open('a');
const b = open('b');
complete.get('b')('资料 B');
await b;
complete.get('a')('资料 A');
await a;
console.log(shown.join(' → '));
// => b:资料 B → a:资料 A
```

用户最后选的是 B，结果却又提交了 A。这个反例把“可能有竞态”变成具体顺序与结果，不需要猜服务器偶尔会慢多少毫秒。

但也要回到需求：如果这是日志收集器，每个结果都应保存，忽略旧结果反而可能是错误。本例允许丢弃过时显示结果，是因为界面只代表当前选择。评审不能把“最新请求获胜”推广成所有异步工作都必须遵守的规则。

测试需要有独立预期。若断言只检查两次 load 都被调用，这段有缺陷的实现也能通过。怎样区分执行覆盖与结果判断，可查 [TEST-01](../chinese-guides/test-01-test-design-oracles-properties-mutation.md#预期结果先从需求里找)。

### 修改后还要说明守卫保护了哪一层

一种局部修复是为每次读取创建独立身份，只有仍然是当前身份的读取才能提交结果：

```js example=career05-current-result
function createReader(load, show) {
  let current;
  return async (id) => {
    const ticket = {};
    current = ticket;
    const value = await load(id);
    if (current !== ticket) return;
    show(id, value);
  };
}
const complete = new Map();
const shown = [];
const open = createReader(
  (id) => new Promise((resolve) => complete.set(id, resolve)),
  (id, value) => shown.push(`${id}:${value}`),
);
const a = open('a');
const b = open('b');
complete.get('b')('资料 B');
await b;
complete.get('a')('资料 A');
await a;
console.log(shown.join(' → '));
// => b:资料 B
```

每次请求获得一个新对象，即使连续两次读取相同 id，也能区分先后。只比较资料 id 会漏掉“A 第一次读取 → A 第二次读取”的情况；同名资料不代表同一次工作。

这个示例只展示成功结果的提交资格。load 拒绝仍会使返回的 Promise 拒绝；调用者要处理错误，错误提示和 loading 结束也要按请求身份判断。离开页面时还需要使当前工作失效。不能把这个小 helper 直接称为完整的数据请求库。

取消请求可以减少无用工作，但需要底层能力配合，而且服务端可能已经收到请求。取消与“禁止旧结果更新界面”要分别解释。框架中的清理与请求身份可继续读 [REACT-04](../chinese-guides/react-04-effects-external-sync-cleanup.md#react-04)，不要把读取守卫误当成写入撤销。

### 评论要把触发条件与修改请求连起来

一条可行动的评论通常有四部分：位置或行为、触发条件、可观察后果、希望修改或补充的证据。不必每条都写成长文，但不能只留下个人感受。

| 模糊评论 | 针对本例的具体评论 |
| --- | --- |
| 这里是不是有竞态 | 当 A 先发后回、B 后发先回时，show 仍会提交 A。我按 B、A 顺序交付结果复现了覆盖，请限制过时读取提交，并保留这个顺序用例。 |
| 应该用 AbortController | 如果要减少离开页面后的读取工作，请说明底层是否支持取消；无论是否取消，当前界面的提交资格仍需要明确保护。 |
| 测试不够多 | 当前只断言请求被调用，错误实现也能通过。请断言最终显示的资料身份，并核对故意移除守卫时用例会失败。 |

第一条可以标为“阻塞”：它违反明确需求。第二条是否阻塞要看取消是否属于当前要求，不能把技术偏好伪装成必改项。

提出疑问时也可以附自己的理解：“我理解 show 会更新当前详情，如果它只写独立缓存，这条风险可能不成立。请确认调用位置。”这样既明确依据，又给新证据留下修正空间。不要用讽刺或一连串问号代替判断。

### 区分阻塞建议与尚待确认的问题

标签的目的，是帮助作者安排动作。团队名称可以不同，但每种状态要有一致含义。

| 类型 | 何时使用 | 作者如何回应 |
| --- | --- | --- |
| 阻塞 | 有依据地违反需求、必要安全边界或已约定规范 | 修改并提供证据，或证明风险不成立 |
| 建议 | 有收益但不影响当前通过条件 | 可采纳，也可说明暂不采用 |
| 疑问 | 信息不足，答案会影响判断 | 补上下文后再决定是否需要修改 |
| 后续事项 | 已明确允许延后，且残余风险可接受 | 记录负责人、范围与跟进条件 |

“以后处理”不能自动把阻塞项变成后续事项。比如最新选择被错误结果覆盖，正是本次需求要解决的问题，不应被移到另一个任务来换取当前通过。

相反，变量名称有两种都清楚的写法，而规范没有要求，就不值得阻塞。可以肯定已有的关键选择，例如“使用请求身份而不是资料 id，保留了重复读取同一资料的区分”；这种反馈传递可复用的理由，不是礼貌性的空夸。

### 验证证据应来自正在评审的改动

看到绿色结果后，还要问它运行了什么、针对哪个提交、预期是否独立。本例只需要少量针对性观察，不需要把所有浏览器和整个项目都重跑一遍。

合适的核对包括：B、A 逆序完成时只提交 B；按发出顺序完成时仍只允许当前读取更新；如果需求覆盖离开页面，则核对失效；去掉身份守卫时，保护当前选择的用例应当失败。错误路径另按真实的公开行为设置预期。

正文的两个例子可以直接比较输出，说明机制，但没有模拟 React 挂载、HTTP 解析、权限或页面卸载。评审真实组件时，还要查看它怎样接入调用者。组件测试与浏览器任务的边界，见 [TEST-02](../chinese-guides/test-02-component-testing-user-behavior-accessibility.md#先确定这一次组件检查的边界)。

对于视觉变化，截图应有环境与状态，不能把截图相同当作交互正确；对于安全风险，单个管理员账号的成功路径也不足以证明授权隔离。验证强度要跟着风险走，而不是跟着工具名称走。

### 可维护性意见需要连接未来变化

“拆成函数更优雅”难以评估。更有意义的理由是：“这个函数同时负责权限判断、请求和提示，新增只读状态时容易绕过权限；把权限输入与 UI 反馈分开，可以单独核对两条规则。”

本例的请求身份可以局部封装，也可能已有框架数据层提供。先寻找项目内的现成模式，避免为一个演示再引入整套状态平台。对重复两三行的处理，也要看它们是否代表同一个业务规则，不能只数代码相似度。

公共抽象会增加使用者和维护者之间的约定。若把身份守卫做成通用 Hook，还需要说明错误、卸载、同步异常和调用范围；不能为了隐藏几行代码，把尚未决定的语义一起藏起来。

架构意见应关联具体变化成本。目录多不等于解耦，依赖少也不自动意味责任清楚。需要讨论边界时，回到 [CAREER-02](../chinese-guides/career-02-architecture-diagrams-boundaries-adrs.md#容器视图展示应用和存储单元)。

### 大 PR 先拆出可理解的阅读路径

大变更不一定都能切成彼此独立的小 PR，但通常能说明哪些是机械移动、接口变化、行为变化、数据迁移和生成文件。评审者先看会改变外部行为的部分，再核对连接处。

例如一项“资料请求重构”同时改目录、变量名、CSS、请求身份和权限条件，就很难判断回归来源。作者可以先保持行为不变完成移动，再引入请求守卫；若必须一并完成，应给出推荐阅读顺序与必要上下文。

拆分也不能让中间提交处于不可运行、不可回退状态。前后端接口要兼容，数据库阶段要能说明迁移窗口；否则“小 PR”只是把完整风险藏在多张页面中。跨边界变化需要一位负责人检查整体效果，多个局部批准不会自动拼成端到端正确。

跨时区协作时，一次写清问题、证据和期望，减少每天只补一个字段的往返。录屏可以辅助复杂交互，但重要结论仍写成可搜索的文字。说明何时能响应、替代评审者是谁，比连续催促更能减少等待。

### 分歧用需求证据和明确决定收束

作者可以不同意评论，但需要回应依据。例如“请求结果写入以 id 为 key 的独立缓存，不直接修改当前视图”，可能改变竞态判断；评审者应检查调用者后调整意见，而不是为了保持立场再找另一个理由。

若双方争论方案 A 与 B，先列共同目标、限制和可验证差异。需要同步讨论时，结束后把决定和理由写回 PR，避免下一位读者只看到“会议上说过”。无法达成一致时按团队约定请相应负责人裁决，不依赖无限线程消耗。

熟悉作者、复杂 diff 和先看到的评论都可能影响判断。可以先独立走一遍关键路径，再阅读其他人的发现；对已解决的问题引用原线程，减少重复。多加几个持相同假设的评审者，不一定增加独立证据。

决定结束后，明确每项是已修改、风险不成立、接受残余风险，还是有负责人继续处理。问题消失在滚动列表里，不等于已经得到决定。

### 批准对应的是特定版本与检查范围

作者更新代码后，先核对新增 diff 与评论对应位置，再按风险决定需要重跑哪项检查。只确认“已回复”不等于修改正确；旧提交上的绿色结果也不能自动覆盖新提交。

本例的**模拟批准说明**可以是：

> 已核对当前提交的读取身份守卫与调用位置。逆序完成时旧结果不再提交，移除守卫的对照会暴露覆盖问题。此处结论仅覆盖当前资料读取；写请求重试与权限逻辑不在本次变更范围内。

真实项目应填入可定位的提交与记录，而不是复制这段就算完成。合入队列、必需检查和权限按平台配置执行；不能因分支曾经绿色就绕过实际合入版本的要求，参见 [ENG-05](../chinese-guides/eng-05-quality-gates-lint-types-tests-ci.md#绿色结果要对应真正被合入的提交)。

批准意味着在已说明的范围内，证据满足当前标准，不是保证从此不存在缺陷。紧急变更可以有事先约定的例外流程，但要记录授权、范围和补审责任，不能让紧急通道成为长期捷径。

### 评审能力需要通过后续结果持续校准

**code owner** 帮助找到熟悉模块的人，也需要替代者和知识传递。跨团队接口、日志隐私、数据变更各有专业边界；不了解的部分明确说明，并请合适的人加入，不应默默批准。

AI 生成的代码和评论也使用同样的事实标准。先看实际 diff、依赖和真实运行结果；“模型说已测试”不算证据。新增日志要核对字段最小化和脱敏位置，新增依赖要核对必要性与来源，输入 AI 的内容也应符合可分享范围。

合入后观察主线、制品与用户任务。发现问题时关联原 PR，判断是上下文缺失、测试预期错误、检查范围遗漏还是设计假设变化，再调整流程。事故复盘中的行动如何反馈到日常评审，可继续读 [CAREER-04](../chinese-guides/career-04-incident-response-postmortem-learning.md#让复盘进入下一次真实变更)。

评审系统可以观察等待时间、反复返工、漏检类型与知识分布。评论数不能代表价值，批准速度也不能单独代表效率。让每条关键反馈都能帮助作者行动，并让决定有可追踪的依据，才是这一过程值得保留的部分。

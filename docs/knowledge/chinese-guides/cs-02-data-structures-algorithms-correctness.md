# CS-02 常用数据结构、算法模式与正确性

数据结构不是一张需要背诵的名词表，算法模式也不是看到关键词就套用的模板。它们共同回答三个问题：程序最常进行什么操作，哪些信息要被保存，为什么结果在所有允许的输入上都正确。

### 一、从操作模式选择数据结构

同一批数据可以用不同方式组织。选择的起点不是“哪个结构最快”，而是程序反复做什么：按位置读取、按键查找、取出最早加入的项、得到当前最小值，还是沿关系向外探索。

**栈（stack）**遵循后进先出。编辑器的撤销、表达式求值和显式模拟递归，都可以把“最后进入、最先处理”写成 `push`/`pop`。**队列（queue）**遵循先进先出，适合消息等待、广度遍历和公平调度。在 JavaScript 中对大数组持续 `shift()` 可能反复移动元素，更稳妥的实现是保留一个头指针：

```js
const queue = ['a', 'b', 'c'];
let head = 0;

while (head < queue.length) {
  const current = queue[head++];
  console.log(current);
}
```

**堆（heap）**是一种能快速取得最高或最低优先级元素的结构。它只保证堆顶的极值，不保证全部元素已经排序。动态维护少量最高分、调度最早到期任务时，堆可能比每次全量排序更合适；但集合很小、更新很少时，简单排序常常更易审查。

**树（tree）**表达父子层级，文件目录和组件结构是直观例子。二叉搜索树利用有序关系加速查找，但若树严重倾斜，性能会退化；真实工程常使用有平衡保证的实现。**图（graph）**表达任意关系，由节点和边组成，可表示依赖、社交关系、路线和状态迁移。图可能有环、不连通、重复边或方向，不能把它默认为一棵树。

结构选择常常是在时间与空间之间交换。为数组额外建立 Map 索引会占内存，却能避免反复线性查找；保存已访问集合会占内存，却能防止图遍历重复工作甚至无限循环。

### 二、查找模式依赖可以排除候选的条件

线性查找不需要预先排序，最坏要检查所有元素。**二分查找（binary search）**每次排除约一半候选，但前提是数据已按目标关系排序，或者答案空间具有单调性。

实现二分时必须先固定区间语义。下面使用左闭右开区间 `[left, right)`，查找第一个不小于目标值的位置：

```js
function lowerBound(sortedValues, target) {
  let left = 0;
  let right = sortedValues.length;

  while (left < right) {
    const middle = left + Math.floor((right - left) / 2);
    if (sortedValues[middle] < target) left = middle + 1;
    else right = middle;
  }
  return left;
}
```

循环开始和结束时都保持一个事实：答案仍在 `[left, right)` 中。区间每次严格缩小，所以算法会终止。理解这两个事实，比背 `left <= right` 还是 `left < right` 更可靠。

**双指针（two pointers）**让两个位置按规则移动，并在每次移动后排除一批不可能的候选。它常用于有序数组或从两端收缩的区间。**滑动窗口（sliding window）**维护一个连续区间，右端加入元素、左端移除元素，并增量更新区间状态。若“移除左端后怎样恢复状态”无法高效完成，或目标不满足可收缩条件，就不能仅凭题目出现“连续子数组”而套窗口。

### 三、遍历关系：DFS、BFS 与拓扑顺序

**深度优先搜索（depth-first search）**沿一条路径尽量深入，再回退探索其他分支。它适合枚举路径、检测结构和处理嵌套关系。递归写法直观，但层级极深时可能超过调用栈，可改用显式栈。

**广度优先搜索（breadth-first search）**按离起点的层数逐层展开，使用队列。在所有边成本相同的无权图中，它第一次到达节点时的路径边数最少；一旦边有不同权重，就需要其他最短路径算法，不能继续沿用这个结论。

无论 DFS 还是 BFS，一般图都要维护已访问集合。标记时机也重要：通常在加入待办容器时就标记，可以避免同一节点被多个邻居重复加入。

当图表示“某件事必须先于另一件事”时，需要的是**拓扑排序（topological sort）**。它只对**有向无环图（directed acyclic graph）**存在。Kahn 算法维护每个节点尚未移除的入边数：先把入度为 0 的节点加入队列，输出一个节点后移除它指向的边，新出现的入度 0 节点再入队。

如果最后输出数量少于节点总数，剩余部分含有环。可能存在多种合法顺序；正确性的要求是每条有向边的起点都早于终点，而不是匹配唯一字符串。重复边是否代表一条关系还是多条约束，必须由数据合同先定义，不能在算法内部猜测。

### 四、贪心与动态规划都需要理由

**贪心算法（greedy algorithm）**在每一步选择当前看起来最好的选项，并且不回头。它成立需要交换论证、最优子结构等证明，或已知问题性质支持。硬币系统稍有变化，反复选择最大面额就可能不再得到最少硬币数。

**动态规划（dynamic programming）**把问题拆成会重复出现的子问题，定义状态、转移和初始条件，并保存结果避免重复计算。写代码之前至少回答：

- 状态包含哪些信息，是否足以决定后续；
- 转移从哪些更小状态得到当前状态；
- 计算顺序是否保证依赖已经可用；
- 不可能状态、空输入和边界怎样表示。

动态规划不等于“使用二维数组”，递归加记忆化和按依赖顺序填表只是两种实现。状态定义错误时，再熟练的循环也只会稳定地产生错误答案。

### 五、正确性靠不变量、终止性和覆盖边界

**不变量（invariant）**是在算法执行到特定位置时始终为真的陈述。二分查找的“答案仍在候选区间”，队列遍历的“队列中是已发现但尚未处理的节点”，拓扑排序的“入度等于尚未移除的入边数”，都能指导实现与排错。

一份完整的正确性解释通常包含：

1. 初始化：开始时不变量为什么成立；
2. 保持：执行一步后为什么仍成立；
3. 终止：什么量会持续接近结束条件，为什么不会无限运行；
4. 结束推论：循环结束时，不变量怎样推出目标结果。

测试正常示例只能说明“这些输入没有暴露错误”。还应主动覆盖空集合、单元素、重复值、同分规则、断开的图、环、极深结构、已经排序和完全逆序等边界。对索引算法，还要检查 0、最后一项和“找不到”。

**基于性质的测试（property-based testing）**不是只罗列几个预期输出，而是生成许多满足约束的输入，验证普遍性质。例如拓扑排序可以检查每条边的起点位置都小于终点位置；排序可以检查结果有序且元素多重集合未变化。性质测试能扩展覆盖面，但仍需要正确的生成约束和可读的最小失败样例。

### 六、把结构和算法放回业务语义

算法不知道两个同名用户是否是同一个人，也不知道重复依赖是否应合并。Map 的键、排序的稳定规则、图边的方向、缺失值处理和冲突策略都来自业务合同。

以实时排行榜为例，先定义事件是“覆盖当前分数”还是“增加分数”，同分时按什么顺序，删除事件怎样处理，才有资格选择全量排序、固定大小堆或分桶。实现之前写清语义，通常能消除大半所谓的算法 bug。

结构也不是越专门越好。数据量小、更新频率低、团队更容易验证数组实现时，简单方案可能最合适；规模或操作模式变化后，再用测量证据升级。可维护性和正确性证明也是工程成本。

实际程序还经常组合结构，而不是只选一种。依赖图可以用 `Map<节点, Set<后继节点>>` 表示：Map 负责从节点找到邻接集合，Set 负责避免同一关系重复出现，队列负责保存当前可处理的节点。搜索建议可以用 Map 保存详情、数组保存当前展示顺序。组合时要为每一层写清职责，避免同一事实在多个结构中各存一份却没有同步规则。

修改数据时尤其要关注派生结构的一致性。原始记录删除后，其索引、计数、堆条目和图边是否一起更新？如果采用惰性删除，读取时如何识别过期项，何时重建？很多看似“算法输出偶尔错误”的问题，根因是多个结构之间的更新合同不完整。

### 七、常见误区

- “Map 一定是哈希表且严格 O(1)”：规范要求的是平均访问时间次线性，并未强制具体结构。
- “BFS 总能求最短路径”：只对无权或等权边的边数最短成立。
- “检测到已访问节点就是有环”：无向图要排除父边，有向图要区分正在访问与已经完成。
- “使用堆后结果自动有序”：堆只保证堆顶，完整有序仍需逐次取出或另行排序。
- “样例通过就证明算法正确”：样例只是有限证据，不变量和边界推理不能省略。

### 学完后的自我检验

选一个“依赖加载”或“最近任务处理”的小场景，先用自然语言列出最常见操作和数据语义，再选择结构。写出一个关键不变量、终止理由和至少四类边界输入。最后说明数据规模或更新频率发生什么变化时，你会换成另一种结构。能解释选择条件与错误边界，比记住更多模板更重要。

# 04–06 域中文审校讲义

本讲义为 04 Umi/Ant Design、05 业务建模、06 工程质量的中文学习载体。每节按“定义与机制—适用/边界—验证”组织；链接到英文规范的知识点，英文页面仅用于冻结版本和术语核验，不是学习或考核的必读材料。

## UMI-01

**定义、机制与适用范围。**路由把 URL 解析为页面树，布局是页面树中共享的壳层；父级路由必须在约定的位置承接子页面，404 与重定向必须各有唯一落点。它适合有导航、页签和权限壳的后台；登录、回调、嵌入页等无壳页面要显式脱离布局。配置式与约定式路由只能二选一并说明优先级，不能让同一路径由两套规则隐式竞争。

**实现与反例。**为每条路由记录 `path`、动态参数、父布局、权限入口、懒加载边界和旧路径去向；菜单只是导航投影，不能作为路由存在或授权的证据。常见失败是把 `users/:id` 放在静态 `users/new` 前、把重定向写成循环、只在客户端点击中正常而深链刷新由服务器返回 404，或让登录页继承后台布局。迁移旧 URL 时保留参数并记录一次命中日志，不能一律跳首页而丢失目标。

**深链与 SSR 机制。**浏览器地址栏直接打开 `/users/42` 时，请求先到静态托管或 SSR 服务器：SPA 回退必须返回应用入口，SSR 则必须用与客户端相同的 `base`、参数和路由表匹配并输出对应状态码。客户端 hydration 后再次解析 URL；若服务端把未知路由渲染成首页、客户端却渲染 404，或两端权限/重定向结论不同，就会出现内容闪烁、hydration 不一致或错误缓存。服务端 404、应用内 404、鉴权重定向三者要分别记录，不能用统一 200 页面掩盖。

**最小实验与证据。**在现有 Umi/Max 应用实现“列表—详情 `/:id`—无壳登录—旧地址重定向—兜底 404”的最小路由表；分别直接打开、刷新、后退/前进、输入非法参数并模拟无权限。提交路由表、四张状态截图或自动化结果、网络/服务端深链响应，以及旧路径携参前后的 URL。学习时在资料卡记录 Umi 文档的页面标题、访问日期和项目实际版本；框架升级后先复跑该实验，再更新结论。

## UMI-02

**定义、机制与边界。**`getInitialState` 是启动期可刷新的全局读取，运行时配置把布局、请求等扩展点接入应用；它适合恢复会话、当前用户和权限快照，不应用来充当页面缓存、表格数据仓库或无限阻塞首屏。初始化链应明确为“读取凭证—请求会话—得到用户/权限或匿名结果—渲染布局/路由”，每一环都有加载、成功、失败和可重试状态。

**实现与反例。**把匿名、凭证过期、网络失败和服务端异常区分：匿名进入公开/登录路径，过期清理凭证并只跳转一次，网络失败显示可重试壳而不是空白页。刷新和切换账号须作废前一次请求或以会话版本拒绝旧响应，避免 A 账号迟到的权限覆盖 B。运行时配置只注册稳定扩展点；把权限请求散落在 layout、页面和 interceptor，会造成重复请求和闪现敏感菜单。

**Session、SSR 与竞态机制。**会话快照至少含主体 ID、权限版本和生成序号；开始初始化时捕获该序号，响应提交前再次比较，旧序号只能记录为丢弃。SSR 场景不能读取浏览器专有存储，服务端只能从请求 cookie/header 获得可验证会话，并把可公开的初始快照安全序列化给客户端；客户端 hydration 时先复用该快照，再按策略刷新。若服务端按匿名渲染、客户端立即按已登录重排布局，应设计稳定骨架或明确跳转，不能先闪现菜单再撤回。

**最小实验与证据。**为五种会话状态列状态表，给每次初始化加关联 ID 和计数；在慢网下连续刷新、先以 A 登录后切到 B、再模拟 401 与重试。验收记录应证明每种状态的请求次数、最终用户/菜单、重定向次数和恢复入口；代码审查时标出哪些数据属于 initial state、哪些必须留在页面。资料卡同时记录 Umi/Max 页面标题、访问日期和项目锁定版本，不能只写“最新”。

实验再加入一次 SSR 请求：对匿名、有效 session 与过期 session 分别保存服务端状态码/初始快照和 hydration 后页面；把 A 请求延迟到 B 登录之后，证明确认日志出现“丢弃旧 session 序号”且 B 的菜单、首屏请求和审计主体不被覆盖。

## UMI-03

**定义、机制与边界。**请求层统一注入认证、超时、追踪标识和错误语义；取消仅终止客户端等待，不能推断服务端没有执行。它适合跨页面的一致反馈，但业务错误仍须由接口契约映射，不能用一个全局 toast 吞掉字段错误、权限拒绝或结果未知。把 transport、HTTP、业务、取消、离线和解析错误分层，页面只消费已判定的 UI 状态。

**实现与反例。**每个请求带关联 ID、会话版本和 `AbortSignal`；搜索、路由离开或新请求到达时取消旧请求，并只允许最新序号提交列表状态。401 刷新凭证要做单飞控制，刷新失败清理会话；写操作超时标为“结果未知，可查询/对账”，绝不能自动重发。反例是把 `AbortError` 提示为服务器错误、两个拦截器重复 toast，或在组件卸载后仍写状态。

**最小实验与证据。**实现一个带搜索和保存按钮的 service：注入乱序响应、卸载、401、422、429、500、离线和写超时。交付错误映射表、请求日志（含关联 ID/取消原因）、每种 UI 状态和保存后查询记录；核对一次取消不会声称回滚、一次未知结果不会创建重复记录。资料页更新时记录 Umi Request 与 MDN AbortController 的具体标题、访问日期和项目使用版本。

## UMI-04

**定义、机制与边界。**前端 access 从一份权限快照派生路由、菜单、按钮和字段可见性；服务端在查询与命令边界对资源、动作和数据范围作最终授权。RBAC 以角色赋权，ABAC 再考察主体、资源和环境属性；两者均默认拒绝。它不替代认证、审计或业务状态守卫，尤其不能以“页面没入口”证明数据安全。

**实现与反例。**先定义动作（如 `invoice:approve`）和范围（租户、部门、本人），再让前端以同一快照渲染四层体验；角色变化时原子替换快照并清理缓存。服务端从已验证会话取主体与租户，列表、详情、导出和批量接口都强制加范围条件，忽略客户端提交的角色与租户。反例包括只隐藏按钮、只保护菜单、下载接口漏检，或权限收回后旧标签页仍可读取缓存数据。

**最小实验与证据。**交付角色—动作—范围矩阵与四层映射。以直达 URL、篡改 store、跨租户 ID、过期权限快照、批量/导出和字段脱敏逐项回归，保存 UI、网络响应和服务端审计决定；通过条件是“看不见”与“拿不到”同时成立。资料卡只把英文 OWASP 作为版本术语核验，中文学习与首考定位到本讲义和 Umi Access，并写明访问日期/项目版本。

## ANTD-01

**定义、机制与边界。**Form 的字段由 store 统一保存，`initialValues` 只在初始化生效；联动依赖订阅、显式更新与校验规则共同决定显示和提交。它适合编辑表单与动态数组，不应用受控组件和 Form store 双写同一字段。弹窗重用前先选择保留、重置或销毁字段；“重新打开自然会刷新”不是机制。

**实现与反例。**新建/编辑切换时以稳定记录 ID 建立表单生命周期，显式写入回填值；条件字段隐藏时决定是否保留值，并让提交 DTO 遵守该决定。异步校验携带字段版本，只接受最后一次结果；保存按钮在提交中防重，服务端字段错误映射回对应字段。反例是以 `value || ''` 抹掉 `0`/`false`、以旧 `initialValues` 覆盖编辑数据，或慢校验把已改正的值重新标红。

**最小实验与证据。**实现含 `Form.List`、条件字段、慢唯一性校验和 Modal 重开的编辑表单；依次测新建/编辑、零值、隐藏字段、两次快速输入、422 字段错误与双击提交。交付字段状态表、请求 DTO 对照、慢校验时间线和一次复用弹窗的录屏/测试；资料卡记录 Ant Design Form 的精确页标题、访问日期和锁定组件版本。

## ANTD-02

表格的查询条件、排序、分页和筛选应映射为可序列化服务端参数；导出是独立异步任务，不是把当前页数据直接拼文件。适合中后台列表；跨页选择、总数变化和较慢旧请求是边界。用 URL 恢复、页码回退、乱序响应、列权限和任务下载链路验证。

**适用条件与不适用条件。**当列表的结果集由服务端筛选、权限、排序或总数决定，用户需要刷新、分享链接、跨页批量操作或异步导出时，采用这一状态模型；它让可恢复查询和一次性视图结果分开。仅展示几十条已完整加载的本地只读数据时，不应为了形式引入服务端分页、任务导出和复杂 URL 状态；若导出只是当前内存数组的临时下载，也必须明确它不是本节所说的受权限约束的业务导出。

**状态模型。**把列表状态拆为可恢复的查询条件、服务端分页信息、排序筛选、已选主键集合、请求序号和导出任务，而不是把整张表的显示结果当作唯一状态。查询条件变化时必须先归一化参数并重置页码；由 URL 还原时要校验未知字段、失效枚举和非法页码。服务端返回的 `total` 与本页 `rows` 是不同证据：筛选后总数变小并不表示可以继续显示空页，应回退到最后有效页后重新请求。排序、筛选和分页必须同时进入请求参数，不能只在前端排序再声称是服务端列表。

**并发与选择。**每次请求分配递增序号或取消信号，只有最新请求能提交结果；慢的旧响应、路由切换后的响应和组件卸载后的响应都必须被丢弃。跨页选择保存稳定主键而不是行下标；筛选条件改变、记录被删除或权限下降时，应重新校验并提示选择集已变化。批量操作要显示受影响数量、不可操作项和服务端逐项结果，不能只因 HTTP 成功就清空选择。列权限和敏感字段应由服务端数据范围决定，前端仅负责不显示和解释受限状态。

**例子。**岗位审核列表的 URL 为 `?status=pending&page=3&pageSize=20&sort=createdAt:desc`；用户先勾选第 1 页的 `job-17` 和第 2 页的 `job-42`，再把状态改为“已关闭”。客户端重置到第 1 页，服务端返回 `total=14`；先前选择项必须重新授权与存在性校验，而不是仍显示“已选 2 项”。若旧的“待审核”请求晚到，只能写入日志，不能覆盖“已关闭”结果。导出时提交这份查询快照，返回 `export-8`，完成后才给下载凭证；文件列、行数和权限范围都应与快照一致。

**导出与验收。**导出提交的是完整查询快照和权限上下文，返回任务标识后轮询或订阅进度；完成后取得短期下载凭证，失败、取消、过期和部分成功都有明确提示与重试条件。验收至少覆盖：刷新后 URL 与请求一致、快速连续筛选不出现旧数据、总数收缩时页码回退、跨页选择不串行、无权限列不泄露、导出文件范围等于查询快照，并记录请求参数、任务标识和下载结果以便排错。

**最小证据。**交付物应包含一份参数对照表、一段乱序请求日志、一张跨页选择前后的主键清单，以及导出任务从创建到下载或失败的记录。这样评审可以复核状态归属，而不是只看某次页面截图。

## ANTD-03

**定义、机制与边界。**Modal/Drawer 是短时上下文容器，必须区分打开、加载、可编辑、保存中、保存失败、关闭确认和销毁；详情适合只读，编辑须携带记录版本与加载边界。它不适合连续多层钻取或把页面主流程塞进不可恢复的弹层；此时应使用独立路由页。

**实现与反例。**打开时保存触发元素和目标 ID，异步详情仅在 ID 与请求序号仍匹配时写入；关闭脏表单先给保存/丢弃/继续编辑选择，真正关闭后将焦点还给触发点。保存中禁用重复确认并在成功后关闭；失败停留在原上下文并保留输入。反例是 A 的慢详情覆盖已打开的 B、Esc 绕过脏数据确认、关闭后焦点落到页面开头，或保存成功以旧响应覆盖更晚编辑。

**最小实验与证据。**用两个记录连续打开同一容器，注入 A 慢、B 快详情与一次保存失败；再用键盘测试 Tab、Esc、遮罩和焦点返回。提交状态转移图、焦点顺序、请求序号日志、脏表单决策和保存后的版本/列表更新证据。学习记录引用 Ant Design Modal 精确页面与本地讲义，注明访问日期及项目版本。

## ANTD-04

**概念与问题。**移动业务组件不是把桌面组件缩小：手指输入不精确、可视区域会被软键盘压缩、网络和系统返回会中断任务，刘海/底部手势区还会遮挡固定操作。组件选择的目标是让用户能在一只手、窄屏和中断后继续完成关键任务，而不是复刻桌面布局。触控目标应有足够尺寸和间距；列表优先展示可判断的核心信息，复杂筛选分步展开；删除、支付等不可逆操作须给明确确认和撤销窗口。

**适用条件与不适用条件。**当关键任务会在手机窄屏、触控、软键盘、弱网或系统中断下完成时，应按本节的移动任务流设计，并把桌面与移动的状态、焦点和恢复分别验证。它不要求所有后台密集数据操作都迁到手机：依赖大量并排比较、精细拖拽或高密度分析的流程，应保留桌面路径或重新拆分任务，不能用缩放和横向滚动冒充移动适配。

**分步机制。**第一步画出“进入—填写—校验—提交—结果/恢复”任务流，并为每步列加载、空、失败、离线、无权状态。第二步把表单控制在单列可滚动容器内：焦点进入字段时计算键盘遮挡，滚动字段到可视区，键盘收起后不丢失草稿。第三步为顶部和底部固定区使用 `safe-area-inset-*`，但只在支持时增加内边距，不能用固定像素猜设备。第四步将主题变量限定为颜色、间距、圆角和字体，并同时核对文字/背景对比度、暗色和高对比模式。第五步把上传、日期和弹层当作异步状态机：用户取消、权限拒绝、弱网重试、服务端校验失败都回到可理解的可操作状态。

**例子。**报销申请页在窄屏中先选择日期和金额，再添加票据；选择文件后显示“本地已选—上传中—已完成/失败”而非立即当作成功。提交按钮始终位于安全区之上；旋转横屏后仍能看到当前字段与错误文案。若网络中断，页面保留草稿和待重试文件，不重复创建申请。

**反例、边界与验证。**把桌面双栏表单、hover 提示和右侧抽屉直接搬到手机，会产生小触点、键盘遮挡和无法返回的多层弹窗；仅靠 CSS 缩放不能修复。安全区不是所有浏览器都存在，弱网反馈也不能替代服务端幂等和授权。练习：以同一申请 fixture 在 320px、横屏、放大字体、软键盘、刘海区、断网/恢复和屏幕阅读器下走完整任务；交付录屏、状态表、触控尺寸/对比度检查、一次失败重试日志和未重复提交的网络记录。

**验收清单。**逐项记录设备/浏览器、视口、字体缩放、网络、预期和实际；验证错误焦点可达、返回后草稿与选择项一致、上传取消不会遗留无主文件。对每个固定底栏检查键盘弹出和安全区同时存在时的可点击区域，并把发现的问题关联到具体状态和修复回归。

## BIZ-01

**定义、机制与边界。**实体以身份连续性区分，值对象以值相等区分，聚合规定一次命令内要保持的一致性边界；统一语言让需求、接口、页面和测试使用同一术语。它用于处理跨页面、跨接口仍需同义的业务概念，不把临时 UI 状态、数据库表名或接口 DTO 直接升级为领域模型。

**实现与反例。**从真实流程抽取名词、动作和规则，给每个术语写定义、同义词禁用项、owner 与例子；标出实体 ID、值对象相等规则、聚合根以及跨聚合的异步事件。以“报销单—金额—审批记录”为例：报销单按 ID 连续，金额按币种和数值相等，审批记录不能绕过报销单根随意修改。反例是让 `statusText` 既是 UI 文案又是存储状态，或以一个巨型聚合承担所有查询和历史。

**最小实验与证据。**交付术语表、关系图、三个 fixture，以及术语到路由/API/类型/测试断言的逐项映射。故意将一个同义词和一个 DTO 字段误用注入评审，说明为何会破坏规则；变更术语时同步更新映射并跑回归。资料卡记录中文 DDD 页面标题、访问日期与项目版本；英文安全页只作术语核验，不承担定义题。

## BIZ-02

**概念与问题。**业务状态机把“对象现在能做什么”写成有限状态、事件、守卫和转移；不变量是每个合法转移后都必须继续成立的业务事实。它用于审批、订单、导入任务等有明确生命周期的对象，解决多组布尔值互相矛盾、非法操作被接口偶然接受、并发事件覆盖结果的问题；它不适合表达无穷连续数值或把每个 UI 临时开关都升级为领域状态。

**分步机制。**先从需求中分出稳定状态（如 `draft`、`submitted`、`approved`、`rejected`、`cancelled`）和事件（提交、批准、拒绝、取消）。再为每条边写前置守卫、命令副作用、失败结果与审计记录，例如“批准”仅允许 `submitted` 且操作者有权限。接着列不变量：已批准记录必须有审批人和时间；取消后不得再生成付款；同一版本只能接受一个审批结果。实现时服务端在单次命令中读取当前版本、校验状态和守卫、持久化新状态与事件；客户端根据返回的状态渲染，而非自行猜测成功。对并发命令使用版本号/条件更新，冲突时返回当前状态并要求用户重新决定；对外部副作用设置幂等键和补偿/对账路径。

**例子。**报销单从草稿提交后进入待审批。审批人与申请人同时操作：取消命令若先成功，批准命令以版本不匹配失败；系统不会出现“已取消且已批准”。新增“补充材料中”状态时，先更新状态图、允许事件、UI 文案、API 枚举、迁移脚本和测试，再发布兼容读取，不能只在前端新增颜色。

**反例、边界与验证。**`isApproved`、`isCancelled`、`isPaid` 三个布尔字段可同时为真，无法说明操作顺序；前端禁用按钮也不能阻止直调 API。状态机不能替代权限、金额计算或跨聚合事务。练习：交付状态/事件表、守卫和不变量清单、含版本号的命令样例；用参数化测试覆盖每条合法/非法边，并注入重复事件、乱序事件、并发批准/取消和新状态灰度读取，保留预期、实际、审计事件与回归结果。

**验收清单。**每条边都必须能追到输入、守卫、持久化状态、事件和可观察结果；测试既断言拒绝原因，也断言拒绝后对象未改变。变更状态集时跑旧客户端读取、重放历史事件和失败补偿，确认没有因枚举未知或重复投递把对象送入不可达状态。

复核者应能仅凭状态图和记录复现一次决定，不依赖口头约定或隐藏数据库修补。

## BIZ-03

**概念与问题。**RBAC 把权限赋给角色，再把角色赋给主体，适合稳定岗位；ABAC 根据主体、资源、动作和环境属性作判断，适合“仅本部门、仅本人、仅工作时间”的数据范围。两者都要把“能看见页面”与“服务端是否可读取/修改资源”分开：前端只改善体验，最终授权必须在服务端查询和命令边界执行。此模型不应用来替代身份认证、审计或业务状态守卫。

**分步机制。**第一步定义资源、动作与数据范围，例如 `invoice:read`、`invoice:approve`、`tenantId`、`departmentId`、`ownerId`；拒绝“管理员”这类没有边界的词。第二步写策略优先级和默认拒绝规则，并为每条策略指定 owner、版本和生效范围。第三步服务端从已验证会话取得主体和租户，构造授权上下文，在列表查询中强制加入范围条件，在详情/写操作中重新检查目标对象；不得相信客户端传来的角色或 tenantId。第四步前端从同一权限快照派生路由、菜单、按钮和字段可见性，在会话刷新或角色变更时原子替换快照并清理缓存。第五步把拒绝、策略版本和请求关联写入审计日志，便于解释而不泄漏敏感策略。

**例子。**财务专员能查看本租户全部发票，部门经理只能批准本部门且处于待审批状态的发票，申请人只能查看自己的草稿。列表接口即使收到 `tenantId=other` 也使用会话租户；详情接口和导出任务同样带范围检查。角色被收回后，前端隐藏入口，服务端仍拒绝旧标签页发出的请求。

**反例、边界与验证。**只隐藏按钮、仅在网关检查或把数据范围塞到前端筛选器都会造成越权；缓存策略若不含策略版本会在权限变更后继续放行。ABAC 规则过多也会难以解释，应把稳定共性收敛为角色。练习：交付角色—权限—属性矩阵和四层映射；分别用直达 URL、篡改 store、跨租户 ID、过期缓存、导出/批量操作和字段脱敏样例验证，检查网络响应、审计日志和 UI 均未泄漏。

**验收清单。**为每个拒绝用例保存主体、资源、动作、策略版本、决定和请求关联 ID；确认列表、详情、下载、导出和写操作使用同一范围规则。权限变更后主动失效会话/缓存，再在旧页面和自动任务中复测，确保“看不见”与“拿不到”同时成立。

策略评审还要抽查默认拒绝路径，证明没有因新增资源而获得隐式许可。

## BIZ-04

**概念与问题。**API 契约是消费者与提供者对操作、输入、输出、错误、版本和兼容语义的共同承诺；DTO 是传输形状，领域模型承载业务规则，UI 模型服务显示和交互。把接口 JSON 直接铺进表单会把服务端命名、可空规则和未知枚举泄漏到 UI，既难升级也难处理不同协议。契约设计不等于实现 OpenAPI 解析器或代码生成；那些属于相邻工程点。

**适用条件与不适用条件。**当同一业务能力被多个页面、客户端、版本或传输协议消费，且字段可空、错误语义、枚举演进或发布节奏会变化时，应建立操作契约与 DTO—领域—UI 防腐层。一次性、封闭且不跨边界的纯展示数据可以保持简单，但仍须说明数据来源；不能把“当前只有一个调用方”当作跳过未知值处理、错误分类或版本证据的理由。若目标是生成客户端、解析 OpenAPI 文件或实施发布兼容门禁，应转交 API-01/02 与 TEST-04，而非扩张本节范围。

**分步机制。**先以业务动词定义操作，如“提交报销”“查询进度”，写清成功、可预期业务拒绝、可重试暂时失败和未知结果。再为每个字段分别声明“缺失、`null`、空串、零、默认值、未知枚举”的意义，不能只写类型。第三步在边界层把 REST/gRPC-Web/消息 DTO 映射为稳定领域命令和结果，再映射为 UI 所需的金额、文案、可操作性；映射器集中处理日期、金额、错误码和未知值。第四步选择协议：普通查询/命令可用 HTTP，强类型多语言内部调用可评估 gRPC-Web，长任务通知可用异步消息；选择必须说明浏览器、流、代理和故障恢复约束。第五步对新增字段、废弃字段、枚举扩展、默认值变化和错误体变化建立兼容样例与消费者验证。

**例子。**`POST /expenses/{id}/submit` 返回 DTO `{status, reviewerName?, version}`。边界层把未知 `status` 映射为“需要更新客户端/不可继续操作”，而不是误显示已成功；`reviewerName: null` 表示尚未分配，字段缺失表示旧服务未提供，二者不混同。列表分页的 `nextCursor` 缺失表示结束，空字符串是非法响应并记录契约错误。

**反例、边界与验证。**以 TypeScript `as` 强转绕过校验、把 HTTP 200 当业务成功、将 proto 默认零值当“未提供”都会产生静默错误。前端映射不能替代服务端授权和状态机。练习：交付操作表、DTO—领域—UI 映射、错误字典与协议选择 ADR；针对缺失/空值/未知枚举/错误体/版本冲突写测试，并用一份旧响应和一份新响应复核关键页面及日志。

**验收清单。**每个映射字段标注来源、转换、默认/未知处理和显示/提交去向；契约变更先在旧、新消费者样例上运行。验证日志不得只写“解析失败”，而要保留关联 ID、契约版本和安全脱敏后的响应类别，以支持发布阻断或回退决定。

对外错误文案与内部诊断字段分离，避免在修复兼容性时泄露实现细节或个人数据。

所有映射变更应在评审中由消费者代表确认语义。

## BIZ-05

同一业务对象在表单、列表、详情、草稿和服务端版本之间应有显式映射；保存成功不能简单覆盖用户尚未提交的编辑。适用于高频编辑场景；刷新、撤销、并发修改、部分保存与冲突是必测边界。以版本号/ETag、脏标记、恢复策略和跨视图断言验证。

**机制链。**用户进入编辑时，客户端先保存“已确认的服务端快照 + 版本”作为基线；输入只改变本地草稿并设置脏标记。提交携带版本条件，服务端接受后返回新的权威对象，客户端按 ID 更新各视图的已确认投影并清除对应草稿；服务端拒绝或网络结果未知时，草稿不能被后台刷新覆盖，而是保留基线、最新服务端值和待决状态供用户重新决定。这个因果流程把“本地编辑”“已确认数据”和“冲突恢复”分开，避免一个成功响应或旧响应直接污染全部页面。

**先定义投影和唯一事实。**领域对象要有稳定 ID、版本或更新时间、生命周期状态和权限范围；列表只保留筛选、摘要和版本，详情保留可读字段，编辑表单保留可提交字段与本地草稿。页面显示的格式化金额、日期和标签是投影，不能反向作为保存 DTO。新建成功后以服务端返回对象为准补入列表并跳转；编辑成功后按 ID 与版本同步详情、列表缓存和当前表单。若接口只返回局部字段，应主动失效并重新读取，而不是用不完整响应覆盖完整详情。

**处理并发和冲突。**进入编辑时记录基线版本和初始快照；用户修改形成草稿，刷新、关闭或路由离开前提示保存、丢弃或暂存。提交携带版本条件，服务端拒绝时保留草稿和服务端最新值，展示哪些字段冲突，并让用户选择重新加载、逐字段合并或放弃。不能把“保存成功”当成所有缓存都已同步，也不能在后台刷新到达时覆盖脏字段。撤销应恢复到最近确认的服务端快照；部分保存必须明确哪些字段已成功、哪些仍在草稿，避免把失败字段误标为完成。

**验证路径。**用同一 fixture 驱动新建、列表、详情和编辑，核对 ID、状态、权限与版本在四个页面的呈现是否一致。注入慢加载、双标签页并发编辑、422 字段错误、网络超时后未知结果、权限收回、服务端格式化回填和删除后返回列表等场景。每个场景记录初始状态、用户操作、请求版本、服务端响应、缓存变化和最终 UI；只有当用户未提交内容不丢失、冲突可解释且已确认数据不被旧响应回滚时，才算状态映射正确。

## BIZ-06

**定义、机制与边界。**异步任务至少区分已创建、排队、执行、成功、失败、取消和结果过期；`202 Accepted` 只说明接收，不是完成。它适合导入、导出、批处理与耗时生成，不应用同步 HTTP 连接伪装进度；短小、可立即确认的操作应直接返回业务结果。轮询或推送均须有退避、断线恢复和终态停止。

**实现与反例。**创建任务返回稳定 `taskId`、操作者和查询快照；客户端持久化可恢复的任务摘要，按退避轮询或订阅，并在成功/失败/取消/过期终态停止。取消是请求取消，服务端应说明已停止、已完成或结果未知；下载使用短期凭证并再次校验权限。反例是收到 202 就 toast 成功、每秒永久轮询、页面关闭后重复创建任务，或把部分成功的行悄悄算入成功总数。

**最小实验与证据。**模拟大文件导入和导出：重复点击、掉线再连、取消与完成竞争、部分成功、结果过期和权限收回。交付状态图、`taskId` 时间线、轮询间隔、服务端逐项结果与下载记录；通过条件是每个终态可解释、恢复不重复创建、下载范围等于创建快照。资料定位优先本地精确讲义和 MDN Fetch/AbortController，记录访问日期与项目版本。

## BIZ-07

**定义、机制与边界。**幂等保证同一业务意图重复抵达不会产生额外效果；超时后结果未知，应查询或对账而非盲目重试。最终一致性允许短暂不同步，但必须提供可观察状态、截止时间和补偿路径。它适合提交、审批、支付、消息消费等跨网络写操作；不能用幂等键掩盖两次不同意图，也不能以“最终会一致”放弃用户反馈。

**实现与反例。**客户端为一次意图生成并复用幂等键，服务端把键、请求摘要、结果和有效期原子保存；同键同载荷返回原结果，同键不同载荷拒绝。并发修改携带版本/ETag，冲突返回当前版本；副作用通过事件、重试与对账收敛。反例是超时立即换新键重发、HTTP 200 就展示业务成功，或只在前端禁用按钮而服务端没有去重。

**最小实验与证据。**对“提交报销”注入网络超时、重复点击、重复消息、并发编辑和部分下游失败；记录键、版本、命令结果、审计事件和对账结论。验收要求可证明只产生一次业务记录，冲突不覆盖他人更新，未知结果可由查询恢复；资料卡定位 MDN 条件请求的 ETag/If-Match 章节并写明访问日期。

## UX-01

**定义、机制与边界。**交互设计从用户目标和关键任务开始，将目标拆为入口、信息、操作、反馈与恢复；状态至少覆盖默认、加载、空、成功、错误、离线、无权和部分完成。可用性验证用任务、观察和严重度，而非偏好投票或截图还原度；无障碍是必要约束，但不等于全部体验质量。

**实现与反例。**先为一个高风险流程写成功定义、前置条件、可撤销点与失败恢复，再在原型中逐状态写文案、焦点和下一步。测试让目标用户在不提示下完成任务，记录成功/失败、用时、错误、卡点与引语；按严重度改动后用同类任务复验。反例是只有空状态插画、错误只写“失败”、以点击量替代任务成功，或以 hover/动效承载键盘用户拿不到的信息。

**最小实验与证据。**选择导入审批或复杂配置，交付任务脚本、八态矩阵、原型、观察表和两轮对比；在键盘、读屏、200% 缩放及 reduced-motion 下走主流程。通过条件是至少一项变更能追溯到观察证据并改善任务结果，且错误/无权/离线状态仍有下一步。学习资料按 Ant Design 价值观、MDN 表单和无障碍的精确章节定位，记录访问日期和使用版本。

## BIZ-08

**定义、机制与边界。**可追踪链把需求编号、业务规则、设计决策、实现、测试和验收证据相连；每次变更能正向说明“为何做”，也能反向找出受影响的规则和回归集。它不是建立更多 Issue、把 PR 标题当验收，或用链接数量替代关系语义。

**实现与反例。**为每条可验收规则分配稳定 ID，写入来源、歧义决策、实现位置、正反例测试、非功能约束和验收记录；PR/Issue 只作载体，关系需可导出复核。需求变更时先列受影响的状态、权限、接口、文案、测试和已发布行为，再补充决定与回归。反例是一个测试笼统标“覆盖需求”，却无法指出哪条规则；或只追主流程，遗漏权限、异常和兼容性。

**最小实验与证据。**将“审批人只能批准本部门待审批单”做成双向追踪表：从规则定位权限策略、接口、UI、服务端测试和验收录屏；再修改为“代理审批”，重新计算影响与回归集。交付变更前后矩阵、歧义 ADR、失败/通过证据和缺失项清单；资料卡记录 GitHub Issues 的精确中文页、访问日期和项目版本，不把它当机制本身。

## GIT-01

**定义、机制与边界。**Git 的 blob、tree、commit、tag 是不可变对象；暂存区决定下一次快照，引用和 `HEAD` 决定可达历史。`restore` 处理工作区/索引，`revert` 新增抵销提交，`reset` 移动引用；已发布历史优先 `revert`，不能把本地恢复方法直接用于共享分支。

**实验与证据。**在空仓库依次修改、暂存、提交、误删、恢复和抵销，记录每步 `status`、对象/树、引用和 `reflog`。注入“误把密钥提交”的反例：停止暴露、轮换凭证、清理历史并验证远端/缓存边界；仅删除当前文件不算处理。资料定位到 Pro Git 对象、暂存与重置的中文章节，记录书页版本与访问日期。

## GIT-02

**定义、机制与边界。**分支是可移动引用；merge 形成合并提交或快进，rebase 将提交重放到新基点并改写 ID，cherry-pick 复制指定改动。公共分支改写须协调并使用 `--force-with-lease`；冲突标记消失不等于语义正确，尤其当同一规则在不同文件表达时。

**实验与证据。**从共同祖先创建两支，分别构造文本冲突和语义冲突，比较 merge 与 rebase 的提交图、diff、测试和回滚路径；再演练错误 rebase 用 reflog 恢复。提交图、冲突决定、测试结果和推送前远端引用是最低证据。资料定位 Pro Git 分支、合并、变基中文深页，记录版本与访问日期。

## GIT-03

**定义、机制与边界。**原子提交应单一目的、可测试、可回滚；PR 把需求、差异、检查与评审串成协作证据。worktree 共享对象库但工作目录和 `HEAD` 独立，适合隔离并发 Agent，却不提供文件所有权、自动解决冲突或绕过检查的能力。

**实验与证据。**把两个不重叠任务置于两个 worktree，记录基线分支、改动范围、责任人、验证命令和集成顺序；故意在脏目录、重叠文件和过期基线时停止并处理。通过 PR 逐项关联需求、风险、测试和评审决定，交付 worktree 列表、提交范围、合并顺序和最终测试，而不是只给平台截图。资料定位 Pro Git 贡献与 GitHub PR/评审中文深页，记录访问日期。

## ENG-01

**定义、机制与边界。**构建从入口形成模块图，经转换和依赖分析产出 chunk、运行时与 source map；tree-shaking 依赖可静态分析和正确副作用声明。开发源码能运行不证明生产产物正确，构建也不等于部署路径、缓存和运行时加载都正确。

**实验与证据。**为静态导入、动态 `import()`、有/无副作用模块各建一个样例，从入口追到产物文件和网络加载；检查重复依赖、chunk 边界、source map 是否能定位一次生产错误。反例是以产物大小变小断言功能正确，或把误删副作用当作优化。资料定位 Vite 构建和 MDN Modules 精确页，记录实际工具版本与访问日期。

**适用条件与场景。**当应用存在多入口、懒加载页面、共享依赖、第三方包或生产错误排查需求时，必须做模块图和产物追踪；小型单入口试验也应至少说明入口、依赖和最终加载文件。若问题实际来自接口、鉴权或 CDN 配置，不能把它错误归为 tree-shaking；构建分析只负责证明“什么被转换、输出与加载”，不替代服务端行为验证。

**具体追踪步骤。**先选一个入口，列出其静态边、动态边和副作用导入；再执行生产构建，记录 manifest、chunk 名称、压缩前后模块、source map 与资源 URL。接着在预览环境打开动态路由，用网络面板验证懒加载 chunk 的请求时机、状态码和缓存；最后人为制造一个仅在压缩后出现的错误，依据 source map 从堆栈回到源码。若发现重复依赖，先定位版本、别名或导入路径，再评估去重会不会改变运行时单例。

**验收清单。**交付入口—模块—chunk—请求的表格、一次动态导入瀑布、一次 source map 定位记录和一次副作用反例。评审能从源码文件指出其为何进某个 chunk、何时加载、失败会在何处显现；只提交分析插件截图、只比较体积或未验证生产运行均不通过。

## ENG-02

**定义、机制与边界。**开发服务器按请求转换模块并以 HMR 更新，生产构建生成优化产物；代理、环境变量、`base`、CSS 和资源路径在两者中语义不同。清缓存只能排除一个变量，不能作为 CDN 旧 chunk、路径或环境配置问题的结论。

**实验与证据。**用同一页面在开发服务器、生产预览和子路径部署运行，列出 API 代理、资源 URL、环境变量与缓存头矩阵；模拟旧 HTML 引用已删除 chunk，再用网络瀑布与服务端日志定位。通过需说明根因和修复为何同时适用于开发/生产边界；记录 Vite/Umi 文档标题、访问日期及锁定版本。

**适用条件与场景。**当项目使用 HMR、开发代理、环境变量、子路径部署、CDN 或多构建工具时，必须把开发请求模型和生产静态产物分开验证；一个只在本机开发服务器运行的页面，不能据此证明部署正确。若只是修复业务逻辑且资源路径、环境和加载方式未变，可不扩大为工具链迁移；本节也不覆盖发布审批、签名或供应链策略。

**具体追踪步骤。**先为同一请求在开发、`preview` 和真实子路径部署分别记录 URL、响应状态、代理目标、环境变量来源、CSS/图片地址与缓存头。再切换一次动态导入，观察 HMR 更新的是模块状态还是完整刷新；生产则确认 HTML 中的 base、manifest 和运行时 chunk URL。模拟用户持有旧 HTML、CDN 缓存旧入口和新版本已删除 chunk：保留网络瀑布、边缘响应头与回退策略，避免把问题归结为“用户清缓存”。

**验收清单。**最小复现须包含开发正常、生产预览或部署失败、根因假设、反证、修复和复测；产物路径、代理行为与环境变量都能在日志或响应中验证。通过标准是解释清楚开发服务器、转换/HMR、生产构建和部署缓存分别承担什么，而不是记住某个工具配置片段。

## ENG-07

**概念与问题。**构建工具链迁移是解析器、转换器、插件钩子、依赖预构建、压缩器、chunk 和 source map 的兼容性变更；它不是“新版本启动更快”的单项基准测试。Vite、Rolldown、Oxc 等名称会变化，但迁移方法必须独立于产品宣传：只有开发、测试、构建、部署和真实运行行为均受控，才算成功。它不适合用删除插件、关闭压缩或忽略旧浏览器来换取表面成功。

**分步机制。**先冻结旧链路：记录 Node/包管理器/锁文件、插件与运行时版本、入口、环境变量、浏览器范围以及冷启动、热更新、生产构建、峰值内存、产物大小和错误基线。第二步做兼容矩阵，逐项列解析语法、JSX/TS 转换、CSS、资源、别名、动态导入、库模式、SSR、source map 和每个自定义插件的预期。第三步以 feature flag 或独立 CI job 双轨构建，比较文件清单、chunk 名称/边界、压缩前后语义、sourcemap 定位和关键页面。第四步先修复最小不兼容：例如插件依赖旧钩子顺序、CommonJS 互操作差异或路径大小写；修复必须有回归测试，不得永久保留双份业务代码。第五步设置停止条件（核心任务失败、错误率/构建时间/内存超阈值、产物漂移无法解释）和一键切回旧链路的回滚演练。

**例子。**一个含自定义 SVG 转换插件、库模式和动态 `import()` 的项目切换打包器后，开发页可打开但生产 chunk 404。对照发现新 `base` 使运行时资源 URL 不同；修复配置并在 CDN 模拟旧 HTML 引用旧 chunk 的场景验证。迁移 ADR 记录被比较的版本、差异、接受理由、负责人和删除旧链路日期。

**反例、边界与验证。**只贴官方性能图、只跑本地首页或把不兼容插件移除，都没有证明迁移成功；source map 能生成也不代表生产错误能定位。工具链迁移不覆盖 CI 发布策略与供应链签名。练习：交付基线表、兼容矩阵、双轨日志、产物 diff、至少一项真实兼容修复和回滚记录；在冷启动、增量、构建、内存、关键路由、SSR/库消费者及 source map 故障上复测并解释差异。

**验收清单。**将每项指标的机器、缓存、样本次数和阈值写入报告；对不可解释的产物差异先阻断而不是接受。切换前后分别从生产样式、动态路由、错误堆栈和库消费者收集证据；执行一次恢复旧构建产物的演练并核对用户任务、静态资源和监控均正常。

迁移完成后设定观察期和删除旧链路的条件，防止双轨长期漂移成无人维护的隐患。

## ENG-03

**定义、机制与边界。**manifest 表达意图，lockfile 固定解析结果，workspace 管理包边界；peer 依赖由消费者提供，幽灵依赖暴露边界错误。可重复安装还依赖干净环境、受控注册表和可审计缓存，不能以删除 lockfile 或本机已有模块掩盖问题。

**适用场景与解析机制。**多包仓库需要以 workspace 协议表达内部包关系，以 lockfile 记录“声明约束 + 注册表元数据 + 解析器规则”得到的实际版本。`dependencies` 随运行产物交付，`devDependencies` 只支撑开发，`peerDependencies` 约束宿主提供的共享实例，`optionalDependencies` 允许明确降级。单包脚本也应锁定安装，但不必为了形式拆 workspace。缓存命中不等于依赖可信或可重复；冻结安装必须在无 `node_modules` 的环境复现。

**失败模式与决策。**幽灵依赖来自未声明却因提升偶然可见的包；peer 冲突表示消费者无法同时满足版本范围，不能靠静默复制多个 React 等单例解决。`override` 可临时处置漏洞或错误版本，但必须记录原因、影响包、验证、owner 和删除期限。直接删除 lockfile 会把确定性问题变成重新抽签；手改 lockfile、混用包管理器或只在有热缓存的机器验收也不能通过。

**实验与证据。**建立 `app`、`ui`、`shared` 三包 fixture：`app` 通过 `workspace:` 消费内部包，`ui` 声明框架 peer，`shared` 故意导入未声明依赖。先在干净目录执行冻结安装并保存版本、完整性摘要和依赖树；再注入 peer 冲突、幽灵依赖、注册表缓存污染与 override，逐项记录预期、实际、根因和修复。最后清空安装目录再次验证，交付 manifest/lockfile diff、解析树、失败日志和消费者运行结果。资料卡记录 pnpm、lockfile 格式与访问日期。

## ENG-04

**定义、机制与边界。**组件包把源代码、产物、`exports` 条件、声明、CSS 和 peer 依赖作为一个发布合同；ESM/CJS 双格式有解析与双包风险。构建成功只证明生产者一侧，适用性由 Node、bundler、类型系统、样式和框架单例等消费者矩阵决定。

**实验与证据。**发布一个 fixture 包到本地制品目录，以 Node ESM/CJS、应用 bundler、TypeScript 和样式入口分别消费；检查 React 是否被打进两份、子路径是否被 `exports` 正确限制、声明与运行时是否一致。交付 package 字段对照、消费者结果和一次故障修复；资料定位 Node Packages 与 Vite Library Mode 的精确页，记录版本。

## ENG-05

**定义、机制与边界。**format 管格式，lint 管可疑代码，typecheck 管静态类型，测试管行为；提交钩子提供快速反馈，CI 才是不可绕过的共同门禁。增量检查适合变更反馈，但不能隐藏既有债务、本地/CI 版本差异或安全关键检查遗漏。

**适用场景与门禁机制。**所有多人协作仓库都应有统一、可在干净环境重复的脚本；小型原型可以减少规则，却不能把格式、类型和行为混成一个不可诊断命令。开发者先获得增量反馈，提交钩子只运行足够快且与完整检查同源的子集；CI 从锁定依赖执行完整 format check、lint、typecheck 和风险测试，并以退出码阻断。规则版本、配置入口和例外必须入库，不能依赖编辑器个人设置。

**失败模式与治理。**自动 format 不证明语义正确；lint 的误报应通过最小范围、带原因和期限的例外处理，不得全局降级 warning。`skip hooks`、未安装钩子或直接从网页修改都能绕过本地层，所以 CI 必须兜底。本地通过而 CI 失败时，先比较 Node/工具版本、文件大小写、增量缓存、生成物和环境变量，不能反复重跑碰运气。历史债务用基线清单冻结“旧问题”，同时阻止新增并按 owner/期限收敛。

**实验与证据。**在 fixture 中分别注入格式偏差、未使用变量、浮空 Promise、类型不兼容和行为回归；记录每个故障被哪一层发现、诊断是否指向文件/规则、修复后何种命令转绿。再使用允许的方式跳过本地钩子，证明干净 CI 仍阻断；模拟旧缓存和不同工具版本，保留对照日志。交付门禁矩阵、配置/版本、失败输出、例外记录和基线下降曲线。资料定位 ESLint Configure、TS Compiler Options 的具体设置，lint-staged/Husky 仅作版本化实现参考。

## TEST-01

**定义、机制与适用范围。**测试预言定义什么结果可判定为正确；stub 提供固定输入，spy 记录交互，fake 提供轻量但可工作的替代实现，mock 把交互期望写进测试。示例测试验证已知案例，属性测试验证大量输入都应成立的不变量，fuzz 寻找崩溃/资源越界，差分测试比较两个独立实现，变异测试则检验现有断言能否识别故意植入的错误。它们适合纯函数、解析器、状态转换与明确边界；不替代真实浏览器、跨服务契约、性能或授权测试。

**生成器、种子与收缩。**先从领域约束设计生成器，而不是复制被测实现：金额分摊生成总额、正权重和参与者；解析器生成有界深度、长度和编码的结构。每次运行保存随机种子、工具版本、样例数量和资源上限，使失败可用同一种子重放。失败后按语义收缩：缩短数组、减小数值、删除无关字段、降低树深度，直到得到仍破坏不变量的最小反例；若收缩改变了失败原因，须保留原样本并修正收缩器。

**差分预言机。**当规范复杂但存在独立参考实现时，把相同规范化输入送入新旧解析器或不同库，比较 AST、错误类别与副作用。分歧不是自动说明新实现错：先核对规范版本、默认值、未定义行为和两个实现是否共享代码/依赖，避免共同错误或合法差异成为伪预言。没有独立实现时使用蜕变关系，例如“序列化后再解析保持语义”等价，但仍要说明关系不能证明的部分。

**变异算子与存活者。**选择与风险对应的算子：把 `<` 改成 `<=`、删除守卫、反转布尔、替换默认值、跳过异常分支或移除状态写入。每个变异体在隔离环境运行；被测试失败“杀死”说明相应断言敏感，存活体必须分类为等价变异、不可达代码、工具限制或真实测试缺口。只报告变异分数没有意义；对真实缺口补最小测试，对等价/不可达结论给出代码或覆盖证据，并保存算子、位置和日志。

**完整实验。**以金额分摊函数为例，定义“不产生负值、分项之和等于总额、输入顺序改变只重排对应结果”三个属性。生成 1–20 个参与者和带小数的总额，固定种子运行，故意植入舍入与边界变异；让失败收缩到最少参与者/最小金额。再用一个独立高精度实现作差分预言机，记录规范允许的一分钱分配差异。解析器实验则限定输入 64 KiB、深度 30、单例 200 ms，保存崩溃样本并重放，防止 fuzz 变成无界资源攻击。

**回归固化与证据。**最小反例要转成命名清晰的确定性回归用例，标注风险、预言来源、原始种子、修复提交和对应变异；随后继续保留属性测试，避免只修一个样本。交付等价类/边界表、生成器约束、种子与收缩轨迹、差分结果、变异算子清单、被杀死/存活者分类、fuzz 资源上限和回归日志。冻结时间、随机数、并发与 I/O，证明重复运行无顺序依赖；覆盖率仅回指风险清单，不能单独作为通过证据。

## TEST-02

**定义、机制与边界。**组件测试以用户可见的角色、名称、输入和输出为断言对象，按可访问查询优先级定位；异步更新等待可观察结果而非内部 state 或固定时间。网络替身只模拟边界，不能重写组件逻辑以让测试通过；组件测试也不替代真实浏览器跨页流程。

**实验与证据。**测试一个异步保存表单：用键盘到达字段，输入、看到加载、收到字段错误后修正并成功；断言焦点、可访问名称、按钮状态和清理后的无泄漏请求。注入慢响应和卸载，确保旧结果不更新 UI。交付测试名称到用户任务映射、网络替身契约和失败截图/日志；资料定位 Testing Library Queries、User Event 精确中文页与版本。

## TEST-03

**定义、机制与边界。**E2E 覆盖跨层关键任务，fixture、账户和环境必须隔离；等待业务信号而非固定延时。视觉回归需冻结字体、时区、动画和动态遮罩，基线变更要审查。它不能替代大量业务规则单测，也不能让重试掩盖竞争和第三方不稳定。

**实验与证据。**以独立租户执行登录—筛选—编辑—提交—退出，等待 API/可访问状态而非 `waitForTimeout`；在 Chromium 与另一目标浏览器保存截图。模拟地图/支付等第三方失效，确认核心任务降级可解释。保留 trace、视频、网络日志、重试原因、截图基线批准记录和清理结果；资料定位 Playwright Introduction、Best Practices、截图比较精确页并记录版本。

## TEST-04

**概念与问题。**消费者驱动契约（CDC）把消费者实际依赖的请求、响应、错误和状态前置条件写成可执行证据；提供者验证这些证据，防止接口实现悄悄漂移。它解决“规范存在但消费端仍被发布破坏”的问题，不等于只有 OpenAPI/proto 文件或把 mock 跑绿。契约测试不代替业务领域建模、端到端体验测试、性能测试或服务端授权。

**分步机制。**第一步识别每个消费者及版本，记录其关键交互和失败语义，而非从提供者猜测。第二步为每个交互建立 Provider State，例如“订单 42 为待审批且属于租户 A”，状态准备必须确定、可重复且不暴露生产数据。第三步消费者生成契约，包含方法、路径/metadata、请求体、响应字段、错误码与匹配规则；提供者在 CI 中逐条验证，并把失败阻断不安全发布。第四步建立兼容矩阵：新增可选字段、弃用、枚举扩展、默认值、删除字段、HTTP 与 gRPC-Web unary/streaming、异步消息各有消费者版本与窗口。第五步把 schema/proto diff、生成物、代理帧和验证报告关联到发布决策；字段编号复用、收窄枚举或改变错误语义须拒绝或走迁移方案。

**例子。**Web 客户端依赖 `GET /tasks/{id}` 在任务不存在时返回可区分的错误体，移动端仍读取旧枚举。服务端把错误体从 `{code}` 改为纯文本，类型生成和最新 Web happy path 都可能成功，CDC 会让旧消费者验证失败。对于 gRPC-Web 流，契约还要声明首帧、结束状态和取消语义，不能只验证能连上。

**适用场景与不适用条件。**当提供者被多个可独立发布的客户端消费、旧版本有存续窗口或协议会跨团队演进时，契约测试应进入发布门禁。单体内部的纯函数调用可用类型与单元测试，不必建立 Broker；但一旦存在网络、代理、消息队列或独立版本，类型生成不能替代运行时兼容证据。契约测试也不证明 UI 任务完整、容量足够或权限正确，这些须由相邻测试承担。

**可执行实验。**建立 Web v1、Web v2 和移动 v1 三个消费者，为“待审批任务存在”“任务不存在”建立确定性 Provider State。先发布兼容新增字段，再依次注入删除字段、收窄枚举、错误体改纯文本、proto 编号复用和流提前结束；运行消费者生成、Broker 发布与提供者验证，记录哪个版本失败、是否阻断、迁移或弃用期限。实验须保留契约文件、状态准备日志、schema/proto diff、代理帧和回归结果，使另一名评审者能在空环境复现。

**反例、边界与验证。**以一个共享 mock、只跑最新消费者或只做 JSON 字段比较，无法说明多团队兼容；Provider State 若依赖不可控测试数据会制造偶发失败。练习：交付消费者清单、交互契约、确定性状态、兼容矩阵和 CI 门禁；注入字段删除、未知枚举、错误体变更、proto 编号复用、流提前结束和异步消息重复，保存 diff、验证日志、阻断/迁移决定与回归结果。

**验收清单。**每份契约必须标消费者版本、owner、最后验证时间和弃用日期；提供者验证失败时输出具体交互和状态准备证据。发布前既运行旧消费者也运行新消费者，确认允许新增的字段不改变默认语义，且异常消息、取消与重试不会绕过兼容门禁。

若不能建立可重复的 Provider State，应先缩小交互或修复测试隔离，不能把不稳定契约设为非阻断。

每次失败均保留最小复现请求。

## ENG-06

**定义、机制与边界。**CI 把检查、测试、构建连接成可审计流水线；同一不可变制品应逐环境晋级，密钥不得进入产物和日志。灰度需要停止条件，回滚后还要用技术、任务和数据三类证据确认恢复。流水线绿灯不等于用户可用，也不能以重新构建“同版本”替代制品可追溯性。

**实验与证据。**为一次发布记录提交、制品摘要、环境晋级、配置版本和审批；注入错误前端、旧 HTML 引用旧 chunk、配置不兼容与回滚。恢复后核验错误率/性能、关键任务完成和数据/队列状态，保存决策时间线。资料定位 GitHub Actions 工作流机制与现场指标的精确页，记录访问日期和使用版本。

## ENG-08

**概念与问题。**软件供应链治理追踪从依赖解析到构建、发布和运行的信任链。lockfile 固定一次解析，SBOM 说明组成，漏洞/许可证扫描说明已知风险，签名证明特定密钥签过某制品，provenance 说明制品由何处、何流程产生；它们是不同证据，不能互相替代。此点不把“扫描绿灯”当作安全、法律意见或 AI 代码来源无风险的证明。

**适用条件与不适用条件。**只要前端应用、组件包、构建镜像或部署制品会引入第三方依赖、由 CI 构建或被多个环境消费，就应把锁定解析、组成清单、策略、签名和来源证据纳入交付链。一次性本地原型可先采用较轻的记录方式，但在共享、发布或接触真实用户数据前必须补齐可追溯证据。供应链治理不能替代渗透测试、业务授权审计、法律意见或对 AI 输出来源的逐项确认；这些结论需要各自的责任人和证据链。

**适用场景。**典型案例是 pnpm workspace、发布到 npm 的组件包、由 CI 生成的静态站点制品和容器镜像：它们都要从依赖解析追到最终摘要。机制的核心是每一环消费上一环的不可变身份并产出可验证声明，而不是在发布时重新构建“同名版本”。

**分步机制。**第一步锁定安装：提交 lockfile，限定受信注册表和允许执行的生命周期脚本，记录直接/传递依赖的 owner 与升级策略。第二步在每次构建为同一不可变制品生成 SBOM、许可证清单和漏洞结果，并把摘要绑定到制品版本。第三步按组织政策对严重漏洞、禁止许可证、未知来源和例外设置门禁；例外必须有负责人、到期和复核，不能永久忽略。第四步由受保护构建身份生成 provenance 和签名，发布/晋级时验证摘要、签名、来源和环境，而不是重新构建一个“看起来相同”的包。第五步为发现恶意包、撤销密钥、被替换制品和错误 NOTICE 预先准备定位消费者、停止分发、回滚和通告步骤。AI 辅助改写代码另记录工具、输入上下文、人工审查、测试和来源不确定性，不能把模型声明当许可证证明。

**例子。**pnpm workspace 的依赖更新在 CI 中先以冻结 lockfile 安装，生成 CycloneDX SBOM 和许可证清单；若传递依赖加入禁止许可证，流水线阻断，例外记录业务 owner 和到期。发布包的 SHA-256 同时出现在构建日志、SBOM、签名和发布记录；下载端验证摘要后才晋级。

**反例、边界与验证。**只跑漏洞扫描会漏掉恶意脚本、许可证义务和制品替换；只有 SBOM 不表示包由可信流程产生；签名正确也不表示代码没有漏洞。练习：交付依赖图、脚本白名单、SBOM/NOTICE、策略和签名/来源记录；注入恶意 postinstall、依赖混淆、摘要不匹配、禁止许可证、缺失 NOTICE 与密钥泄漏，验证门禁、审计、撤回和受影响消费者定位。

**验收清单。**复核制品摘要在构建、签名、制品库和部署记录中完全一致；例外工单到期后自动重新阻断。模拟撤销时从 SBOM 反查全部受影响制品和消费者，测试停止分发、通知、替换版本、密钥轮换和恢复验证，避免只删除仓库标签却继续被缓存下载。

策略变更同样需要版本、审批与回滚，避免在紧急修复中静默降低长期防护基线。

## OBS-01

**定义、机制与边界。**前端可观测性关联错误、日志、指标、资源、请求和用户任务；SPA 软导航的性能边界不能只按 URL 推断。采样、脱敏、同意和留存是设计输入，告警应连接症状、SLO、原因线索和响应人。RUM 不能收集可识别内容来换取排障，也不能以一次 URL 变化自动认定一次性能导航。

**实验与证据。**为一次关键提交生成匿名会话/路由/版本/请求关联，在不记录姓名、令牌和表单原文的前提下采集耗时、错误与结果；设定延迟/错误 SLO 和触发阈值。注入一次发布故障，从告警追到版本、路由、受影响任务与恢复窗口，保留采样率、脱敏规则、查询截图和复盘。资料定位 OpenTelemetry Browser、MDN Performance API 的精确页，记录 SDK/浏览器能力版本与访问日期。

## DX-01

**概念与问题。**前端平台工程把内部能力当作有用户、路线图、服务质量和退出策略的产品，而不是共享脚本仓库或强制统一技术栈。平台的用户是开发者：它应降低创建、开发、测试、发布、排障等任务的认知和等待成本，同时不把合理差异压成影子流程。平台不负责替业务团队决定所有架构，也不以工具安装量或强制采用率作为成功。

**适用条件与不适用条件。**当至少两个团队反复经历相同的创建、构建、发布、权限或排障摩擦，且能够明确共同用户、owner、服务边界和成功指标时，才值得把能力产品化为平台。单个团队的一次性脚本、尚未验证的偏好或需要为特定业务深度定制的架构决策，不应被仓促升级为 Golden Path；先以可撤回试验验证需求，再决定标准化、继续支持或淘汰。

**分步机制。**第一步访谈新老开发者，画出从创建应用到上线的实际旅程，标记等待、失败、手工复制和权限阻塞。第二步把可提供的能力写入服务目录：模板、构建、组件、观测、发布、权限等均有 owner、版本、API/SLA、支持渠道、成本和弃用政策。第三步设计 Golden Path：默认安全且可发现，带升级说明、可观测过程和可回退的 escape hatch；逃生不是绕过审计，而是记录原因、期限和回收计划。第四步用门户或自助接口交付，保持文档、模板和实现同版本；对依赖平台的团队给出迁移和故障降级。第五步每月以任务成功率、完成时间、失败率、采用/留存、满意度和交付质量中的至少三类指标检查假设，并根据反馈削减无价值能力。

**例子。**新服务创建过去需两天复制仓库、申请权限和搭建 CI。平台提供带 owner 的模板、环境申请 API、标准构建与发布路径；复杂 SSR 应用可登记临时 escape hatch 并得到支持。评估不只看模板创建次数，而看首次生产发布时间、失败重试率、90 天留存和变更失败率是否改善。

**反例、边界与验证。**只搭 Backstage/Nx、只写脚手架或锁死配置都不是平台价值；没有 owner 的“公共能力”会迅速过期。平台目录不能替代团队对业务质量负责。练习：基于两个团队的 fixture 交付旅程、目录、owner/SLA、一条 Golden Path、升级/回退/逃生规则和实验设计；让两类用户完成创建到发布，记录至少三类指标、失败样本、支持工单和下一轮调整决定。

**验收清单。**每个路径明确适用条件、输入权限、输出制品、检查和人工支持边界；将失败任务录像/日志与目录 owner 关联。每次平台变更都比较采用前后同类任务，而非只看总用户数；逃生通道到期后复盘根因并决定标准化、延长或淘汰，防止永久影子流程。

度量公开给平台与使用团队共同解释，避免单方以指标压力掩盖真实任务摩擦。

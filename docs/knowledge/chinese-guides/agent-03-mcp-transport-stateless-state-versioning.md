# MCP 传输、无状态核心与显式状态知识点讲义

## AGENT-03 MCP 传输、无状态核心、显式句柄与版本迁移

MCP 让 AI 客户端用统一消息访问工具、资源和提示，但“统一”不表示连接可靠、请求只到达一次，也不表示服务端可以把业务状态藏在某条长连接里。2026-07-28 规范把核心协议转向无状态：初始化握手和隐式会话退出核心，能力通过发现获得，长流程使用显式句柄或扩展表达。理解这一变化，关键不是背消息名，而是分清传输事实、协议事实和业务事实由谁保存。

### 学习前先确认

- 直接前置：[MCP-01 MCP 核心概念、工具与信任边界](../chinese-guides/mcp-01-server-tools-resources-prompts-schema.md#mcp-01)，用于理解 Host、Client、Server、tool、resource 与 prompt 的职责。间接前置不重复列出。

### 一、传输只负责搬运消息

**流式 HTTP（Streamable HTTP）**是 MCP 可使用的一类传输方式：客户端通过 HTTP 请求发送协议消息，服务端可以用普通响应或事件流返回结果。它提供连接、状态码、header、分块与中断信号，但不会自动保证业务操作恰好一次。

stdio 适合本地父子进程，以标准输入输出交换消息；HTTP 适合远程部署、网关与独立扩缩容。二者承载同样的协议意图，却有不同的身份、origin、代理、超时和进程生命周期风险。不要把本地 stdio 的信任假设原样搬到公网 HTTP。

传输断开只能证明客户端没有继续收到数据，不能证明服务端未执行。请求超时、反向代理重试、标签页关闭都需要协议层和业务层共同处理。

### 二、Stateless Protocol 不等于系统没有状态

**无状态协议（Stateless Protocol）**表示处理核心请求所需的协议语境不依赖此前隐藏握手或某个粘性连接；请求携带必要版本、方法、身份和参数，服务端可以独立路由。业务任务、授权、幂等账本和长运行结果仍然可以持久存在。

无状态核心有利于负载均衡、故障转移、无服务器执行和单请求调用，也减少“连接还在所以权限还有效”的错觉。每个请求都按当前凭据和策略验证，不能依赖内存中的 session object 代表用户。

过去依赖 initialize、协商后连接状态或 session header 的实现需要显式迁移。兼容层可以暂时支持旧客户端，但新业务逻辑不再把正确性绑定到连接亲和性。

### 三、请求自身携带可路由语义

远程调用需要明确协议版本、目标方法、服务名称或可发现标识、内容类型、认证和关联 ID。网关根据这些字段路由与审计，不解析自然语言判断要调用谁。未知或不支持版本返回可识别错误，而不是勉强按最新版解释。

协议元数据与业务参数分开：method 表示 MCP 操作，name 定位服务或部署，params 表示工具输入。模型不能随意覆盖租户、主体和授权 header；这些由 Host/Client 从可信运行环境注入。

限制 body、header、流长度、并发和方法集合。代理必须保留必要 header，移除外部伪造的内部身份字段，并记录版本转换。

### 四、Explicit Handle 表达持续存在的对象

**显式句柄（Explicit Handle）**是由服务端签发、客户端在后续请求中明确携带的资源、任务、订阅或交互引用。它把“后续属于哪个流程”从连接内存变成可持久、可授权、可过期的协议对象。

句柄应不可猜、绑定主体和范围，并记录创建、状态、到期和撤销。它不是权限本身；每次使用仍校验当前身份和对象访问。URL、taskId、cursor 或订阅 ID 都可成为句柄，但需要各自 Schema 和生命周期。

不要把数据库自增 ID 直接暴露，也不要把所有状态编码进可篡改 token。需要跨实例恢复的事实保存在持久层；签名 token 只携带最少可验证声明，并支持撤销或短期有效。

### 五、Multi-Round-Trip Request 支持中途交互

**多轮请求（Multi-Round-Trip Request）**表示一次逻辑请求在得到终态前可能需要额外输入，例如用户确认、补充参数或凭据选择。中间状态必须结构化为 `input_required` 一类结果，并给出后续句柄、所需字段、风险说明与有效期。

它不同于让模型在一个 HTTP 连接里无限等待。服务端可持久化状态并结束当前响应，Client 向 Host 呈现可信 UI，用户决定后以新请求继续。继续前重新验证状态和权限；旧输入不能应用到已经变化的资源。

中途输入不应要求客户端回传秘密到不可信 Server。OAuth、设备授权或宿主确认由 Host 控制，Server 只获得最小结果或授权引用。

### 六、流式结果需要序号与终态

流传输中的事件带 request/run、sequence、kind 和 terminal。客户端按序应用，重复忽略，缺口重同步；终态之后拒绝迟到 delta。仅靠拼字符串会在重连、代理缓冲和重复投递时破坏结果。

大资源或进度可以增量传输，业务副作用仍只执行一次。流中断后，Client 使用显式句柄查询状态或恢复，不自动重发创建请求。若 Server 不支持恢复，必须把结果标为未知并给人工路径。

背压需要限制服务端生产速度、客户端缓冲和单事件大小。慢消费者可降级为轮询或快照，不能让进程内存无限增长。

### 七、取消是请求，不是事实

客户端发出取消或关闭连接，只表示“不再需要继续”，服务端可能已经进入不可中断阶段。服务端尽快检查取消标记、停止后续步骤并返回最终状态；已发生的副作用与清理结果要明确报告。

取消使用 request/task 句柄并校验所属主体。不能允许任意用户猜 ID 后终止别人的任务。重复取消是幂等的，完成后取消返回已完成事实，而不是把任务改成 cancelled。

资源清理、锁释放和临时文件删除也有可观测状态。强杀进程不是正常取消协议。

### 八、幂等处理重复和未知结果

创建或写操作由 Host 生成稳定 operationId，Server 在业务范围内持久去重。HTTP 方法是否幂等不能代替业务语义；工具可能用 POST 执行可去重操作，也可能读取时触发计费。

相同 key 与相同参数返回原结果；相同 key 不同参数拒绝。去重窗口至少覆盖客户端合理重试和代理延迟。Server 崩溃时用意图/回执账本对账，不在内存 map 中短暂记录。

超时后先按句柄或 key 查询。只有确认未执行且策略允许时才重试，否则交由用户或补偿流程。

### 九、认证与授权不依赖连接寿命

远程 Server 每个请求验证 token、audience、scope、租户与资源权限。Host 不把上游用户 token 随意透传给所有 Server；按目标兑换最小凭据。stdio Server 也要限制可执行来源、环境变量、文件权限和工具范围。

重连、扩容或版本切换不能扩大权限。长期任务执行到下一敏感步骤前重新校验；授权撤销后停止新动作。句柄泄露不能绕过身份。

日志不记录完整 bearer token、cookie、工具秘密或用户敏感正文。协议追踪使用脱敏 ID。

### 十、版本迁移是双边能力问题

客户端、网关和 Server 可能在不同时间升级。每个端点声明支持的规范族、扩展与方法；Client 选择共同能力。不能因为版本号接近就假设字段和失败语义兼容。

解析遵循明确规则：允许规范声明可忽略的未知可选字段，拒绝未知必需语义和错误类型。适配器把旧 initialize/session 模型映射到内部稳定接口，并记录丢失能力；不得伪造无状态保证。

设置兼容截止、遥测版本分布和回滚方案。部署时先让接收端理解新格式，再让发送端启用；数据库或任务句柄迁移也要兼容在途流程。

### 十一、网关与代理不能成为隐藏会话层

API 网关负责 TLS、认证入口、限流、路由、大小限制和观测，但不应偷偷保存“上一次工具列表”或用户审批。隐藏状态会让多实例、重启和绕过网关的请求产生不同语义。

代理缓冲可能破坏流式体验，自动重试可能重复写操作，超时可能短于 Server 任务。逐层配置并测试，透传关联 ID 和必要协议 header。对外错误隐藏内部拓扑，对内保留准确分类。

浏览器直连还需严格 origin、CORS、CSRF 和凭据策略。允许网络访问不等于允许工具执行。

### 十二、可观测性分层定位故障

一次调用关联 Host、Client、Server、协议版本、transport、request、operation、task、用户主体和路由实例。记录进入/离开时间、状态迁移、字节量、重试与取消，不默认保存敏感参数全文。

区分 DNS/TLS、HTTP、协议解析、能力不支持、授权、工具业务、外部依赖和未知结果。统一报成“工具失败”无法选择恢复策略。

指标包括版本分布、发现命中、首事件延迟、流缺口、断线恢复、重复去重、句柄过期、跨实例恢复和无效取消。

### 十三、故障注入验证无状态承诺

让连续两次请求落到不同实例，重启 Server 后按句柄恢复，在首个响应丢失时重试，在流中断和乱序时重同步，在 token 撤销后继续。若必须依赖粘性会话才能正确，说明状态仍被隐藏。

再测试旧客户端、新 Server，新客户端、旧 Server，未知可选字段、未知必需方法、代理剥离 header、重复 operationId 与句柄越权。断言不重复副作用、不跨租户、不把未知结果当失败重做。

性能测试覆盖大消息、慢消费者、多个并发流和长等待，不让背压变成全局阻塞。

### 十四、本地 stdio 仍需要生命周期与供应链控制

Host 启动 stdio Server 时固定可执行来源、参数、工作目录、环境变量和权限，不用 shell 拼接模型提供的命令。Server 的 stdout 只写协议帧，诊断走 stderr 且限量；一行无关日志就可能破坏 framing。子进程退出、僵尸、信号、超时和重启由 Host 管理。

本地不等于可信。第三方包可能读取文件、网络和环境秘密；用专用低权限账户/沙箱、文件与网络允许列表限制。升级前验证签名/哈希与兼容测试，锁定版本，出现异常能回滚。发现的工具声明仍是不可信输入。

并发请求需要独立 requestId 和取消，不能因单一 stdin/stdout 就串行等待所有长任务。大输出、慢消费与 Server 崩溃采用与 HTTP 相同的大小、背压和未知结果规则。

### 十五、无状态服务的数据层需要一致性设计

请求可落到任意实例后，幂等记录、句柄、任务与授权撤销不能只在进程内。选择数据库、缓存或对象存储时明确一致性：创建句柄和业务意图原子提交；缓存 miss 不代表对象不存在；主从延迟不能让刚创建的 operation 被另一个实例重复执行。

用条件更新和版本号封闭状态迁移，终态不可被迟到 worker 覆盖。短租约协调处理者，过期后新实例接管前先对账外部动作。分区键包含租户与对象，避免热点和跨租户扫描。

灾难恢复演练不仅恢复数据，还验证句柄可解析、删除标记不复活、旧版本任务不被新代码误执行。明确 RPO/RTO 对进行中请求意味着什么。

### 十六、以当前规范为基线实现

先设计与传输无关的内部请求、显式对象和业务账本，再接 stdio 与 HTTP；先实现独立请求授权和幂等，再增加流、交互和长任务。兼容旧版放在边缘适配器，不污染核心状态模型。

实现评审要拿出原始请求/响应、跨实例路由、operation 去重记录、句柄权限、断线恢复、取消终态和旧版适配证据。分别重启 Client、Server 与网关，确认核心请求不依赖隐藏连接内存。协议错误、业务失败和未知副作用必须有不同状态与恢复路径；若只有一条“connection failed”，系统仍不可运营。

协议报文夹具要覆盖 JSON 与事件流、空结果、大结果、未知字段、错误 content type、重复请求和中途断开，并对照规范版本固定预期。SDK 升级后重放这些报文，防止库的默认重试、header 或解析行为悄悄改变业务语义。

学完后，你应能解释无状态核心为何仍允许长任务，区分连接、协议和业务状态，设计显式句柄、多轮交互、流恢复、取消与版本迁移。实现前应核对 [MCP 2026-07-28 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)与 [TypeScript SDK 迁移指南](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)，因为生态兼容状态仍会变化。

# Web 密码学知识点讲义

## SEC-05 Web Crypto、密钥生命周期与客户端密码学边界

Web Crypto 提供经过实现的密码学原语，却不替应用选择协议、管理密钥或定义信任。算法名称写对，只要 IV 复用、AAD 错绑、密钥可随意导出或轮换无法回滚，系统仍不安全。本讲从术语、CryptoKey 和认证加密开始，逐层走到存储、轮换、威胁模型与服务端边界。

### 学习前先确认

- 直接前置：[SEC-01 XSS、CSRF 与前端输入输出信任边界](../chinese-guides/sec-01-xss-csrf-trust-boundaries.md#sec-01)。本讲默认理解同源脚本、XSS、客户端授权和敏感日志的边界。

### 一、编码、摘要、MAC、签名与加密各有目的

编码把字节换成可传输表示，如 UTF-8、Base64url；任何人可解码。摘要产生固定长度指纹，不使用密钥，不可逆不等于适合密码存储。MAC/HMAC 用共享秘密验证完整性与持钥方来源，第三方无法区分两方谁生成。

数字签名用私钥签名、公钥验证，提供可公开验证的完整性和来源；加密保护机密性。AEAD 同时加密并认证数据与关联上下文。把 Base64 当加密、直接 SHA-256 密码、用公钥“签名”都是类别错误。

每个需求先写要保护机密性、完整性、来源、口令抗破解还是传输表示，再选成熟协议。不要从“我们能调用 AES”反推产品需求。

### 二、Web Crypto 是异步底层原语

`crypto.subtle` 的 SubtleCrypto 提供 digest、generateKey、import/export、encrypt/decrypt、sign/verify、derive 与 wrap 等操作。大多返回 Promise，错误常是 DOMException，输入输出以 ArrayBuffer/TypedArray 为主。

它不提供完整消息协议、证书信任、密钥服务器、口令数据库或端到端聊天。名称 subtle 提醒调用者：参数和上下文错误不一定由 API 阻止。

浏览器 secure context、算法支持和实现差异要按目标环境测试。不要用第三方纯 JS 自制算法作为不支持时的静默回退；安全功能不可用时明确降级或交给服务端。

### 三、CryptoKey 是带算法和权限的句柄

**密码密钥对象（CryptoKey）**包含 type、algorithm、extractable 和 usages。type 是 secret/public/private；algorithm 固定 AES-GCM、ECDSA 等参数；usages 限制 encrypt、decrypt、sign、verify 等操作；extractable 决定能否 exportKey。

为本地加密生成 AES-GCM 256 key，通常 `extractable:false` 且只给 encrypt/decrypt。最小 usages 能防误调用，不能阻止同源 XSS 取得句柄后调用允许操作。

导入时同时验证来源、格式、算法、用途、可导出性与 key version。一个成功 import 的公钥不自动可信，仍需固定指纹、证书/配置签名或受信服务分发。

### 四、AES-GCM 提供认证加密

**AES-GCM**是 AEAD：加密明文并产生认证标签，解密时同时验证完整性。密文、IV、AAD 或 tag 任一改变，应整体失败，不能输出部分明文。

同一 key 下 IV/nonce 必须唯一，常用 96-bit 随机值；IV 不保密但复用会严重破坏安全。随机生成需要 `crypto.getRandomValues()`，并在协议层用 keyVersion+IV 识别异常。页面内 Set 只能做测试，不是跨设备唯一性证明。

GCM tag 通常包含在 Web Crypto ciphertext 输出中。算法、tagLength、IV 与 additionalData 在解密时必须完全一致。

### 五、AAD 把密文绑定到业务上下文

Additional Authenticated Data 不加密但参与认证，适合绑定 userId、recordType、tenant、schemaVersion 或协议头。攻击者能看见 AAD，却不能在不使解密失败的情况下修改。

若密文从用户 A 复制到用户 B 仍能解密，说明上下文绑定不足。AAD 序列化必须规范化：字段顺序、编码与大小写一致；不要把随展示变化的本地化字符串当 AAD。

业务在解密前根据可信上下文构建 expected AAD，而不是无条件采用信封里攻击者提供的 aad。信封可保存可读字段，验证时对照当前记录身份。

### 六、信封让算法和版本可迁移

不要只存一段 ciphertext。**密码信封（Cryptographic Envelope）**至少包含 protocol/version、alg、keyVersion、IV、AAD 标识和 ciphertext。解析时先限制对象大小和字段，再只接受固定允许算法。

算法敏捷不等于让任意 alg 字符串决定底层调用。由应用版本与 allowlist 选择，未知/废弃版本拒绝或进入迁移，不自动降级到弱算法。

信封 metadata 可能泄露账号关系、记录类型和时间，威胁模型要包含流量与元数据。需要隐藏时采用更完整协议，不随意加密字段后仍把同样信息放键名。

### 七、随机数不能使用 Math.random

IV、challenge、salt、临时 secret 与不可预测 token 使用 `crypto.getRandomValues()`。UUID 可用于许多唯一 ID，但不同版本/实现的不可预测性与协议要求要核验，不能通用替代密钥材料。

随机唯一与数据库唯一不同。服务端业务 ID 仍需唯一约束，nonce 需要在 key 作用域不复用。随机失败或 API 缺失时终止安全操作，不退回时间戳或 Math.random。

### 八、密码不是对称密钥

用户口令熵低，不能直接 UTF-8 填充成 AES key，也不能只做快速 hash。口令派生使用专门 KDF、随机 salt、足够成本与参数版本。服务端密码存储通常优先成熟的内存困难算法和专用库。

Web Crypto 提供 PBKDF2 原语，但参数选择、设备性能、升级、认证错误和离线攻击仍需协议设计。本知识点不让前端自建登录密码数据库。

若做本地保险箱，明确口令丢失即数据丢失、派生参数与 salt 存储、尝试限速的客户端局限，并评估系统钥匙串或服务端受控密钥更合适。

### 九、导入导出是高风险生命周期操作

exportKey 输出 raw/JWK 等密钥材料；extractable false 会使其失败。需要备份/迁移时，临时可导出 key 增加泄漏面，应在受控流程产生、包装、审计和清理。

wrapKey 使用另一个 key 加密密钥材料，仍需管理 wrapping key、算法与完整性。把 raw key Base64 后放 localStorage 不是包装。

公钥通常可导出用于分发，私钥与对称 key 尽量不可导出。用途由协议决定，不能“一律 false”后又无法合法迁移。

### 十、IndexedDB 可以保存句柄，不是硬件保险箱

CryptoKey 支持 structured clone，可存入 IndexedDB，保留 extractable/usages。这样避免转为字符串，不表示密钥位于 HSM；同源脚本仍可能读出句柄或调用允许操作，浏览器配置/备份行为也需核验。

存储记录包含 keyVersion、状态、创建时间和用途，不记录明文。账号退出、设备撤销和站点数据清理要有一致策略。配额驱逐可能让本地数据无法解密，产品必须定义恢复或明确不可恢复。

### 十一、密钥生命周期从生成到移除

状态可建模为 staged、active、decrypt-only、revoked、removed。staged 验证新版本但不写正常数据；active 用于新加密；decrypt-only 只读旧数据；revoked 拒绝操作；removed 清理持久引用。

JavaScript 变量设 null 不能保证立即擦除所有内存副本，所以不要承诺物理销毁。泄漏响应还要处理会话、设备、服务端授权和受影响密文。

每个状态转换有 owner、时间、覆盖率和审计。密钥不应无限 active，也不因日历到期就直接删除仍有数据依赖的版本。

### 十二、轮换采用双读单写和可回滚迁移

v2 staged 验证后成为 active，新写只用 v2，v1 保持 decrypt-only。读取 v1 时完整解密验证，再用新 IV 与规范 AAD 写 v2 临时记录，原子切换引用；失败保留 v1。

覆盖率、失败率和回滚窗口达标后才 revoke/remove v1。迁移任务幂等，记录 recordId、from/to version 和稳定错误，不记录明文、key 或完整敏感信封。

直接删 v1 会让未迁移数据永久丢失；同时写两份 active 会增加分叉。双读单写把兼容窗口与真写版本分开。

### 十三、撤销、登出、丢设备和常规轮换不同

登出可能移除本地句柄和缓存，但不一定吊销跨设备凭证；设备丢失需要服务端设备授权撤销；密钥泄漏要停止使用版本、评估重加密和通知；常规轮换是计划内迁移。

事件分类决定范围。不要把“清 localStorage”当撤销，也不要让前端自行决定服务端 KMS key 生命周期。

### 十四、浏览器威胁边界决定能保护什么

攻击者只拿到离线 IndexedDB 且没有 key 时，本地加密可降低明文泄漏；能执行同源 XSS 时，可读加密前/解密后明文，也可能调用 CryptoKey；合法用户越权访问他人记录要靠服务端授权；服务端数据库泄漏需要 KMS/HSM、密钥分离与端到端协议。

客户端“加密成功”绝不是服务端授权。前端内置的共享 secret 可从制品或运行时提取，不作为服务身份。真正根密钥和跨用户决定留在受控服务端。

### 十五、KMS 与 HSM 承担受控密钥域

KMS 提供生成、授权、轮换、版本和审计，HSM 在受保护硬件内执行关键操作。它们也不是自动安全：IAM、用途、审计、备份和应用协议仍需设计。

浏览器可持用户端 key 或短期数据 key，服务端 KMS 包装、授权或派生；具体架构取决于谁应能解密、恢复与撤销。先写信任和恢复要求，再选择 envelope encryption 或端到端方案。

### 十六、签名验证需要可信公钥来源

浏览器可验证下载配置、插件清单或离线制品签名，但公钥若从同一可篡改响应获得，验证没有建立新信任。公钥/指纹应内置于受信制品、由已验证证书/更新链提供，或经独立受信服务获取。

签名覆盖规范化字节和版本，解析前先限制大小，验证后再信任内容。重放旧但签名有效的配置需要版本、过期或单调序号防护。

### 十七、错误处理不能降级为明文

解密认证失败统一拒绝，不尝试忽略 tag、猜 AAD 或用旧弱算法“救回”。UI 显示数据暂不可用/需要恢复，安全日志记录算法版本、错误类别和关联 ID。

禁止日志输出 key、明文、完整 IV+ciphertext+AAD 敏感组合。调试测试使用专用非生产向量。失败次数异常可告警，但 GCM OperationError 不足以单独判断攻击。

### 十八、验证包含篡改、复用和迁移失败

正向测试加密后严格解密原文；反向分别翻转 ciphertext、IV、AAD/tag，均整体拒绝；同 key 重复 IV 在协议层被检测；extractable false 导出失败；错误 usage 不可调用。

轮换测试新写 v2、旧 v1 可读迁移、注入失败保留 v1、重跑幂等、回滚后两版本可解释。用 Web Crypto 真实实现而不是 mock 核心算法，同时让业务状态机可单元测试。

测试向量固定编码和规范化规则，跨浏览器对照。性能测量大数据时避免一次复制和主线程阻塞，必要时流式分块方案必须采用成熟协议而非自行拼 GCM 块。

### 十九、何时不应在浏览器做密码学

如果目的是隐藏前端包里的 API secret、绕过服务端权限、让 XSS 看不到当前明文或自行创造区块模式，浏览器密码学无法满足。把需求移到服务端、平台凭证、安全存储或成熟端到端协议。

需要合规、长期密钥托管、多用户共享和可恢复时，引入安全工程与密码学评审。高级开发者的能力包括知道何时停止写代码。

### 学完后应能说明

你应能区分编码、摘要、MAC、签名和加密，解释 CryptoKey、AES-GCM、唯一 IV、AAD 与信封；能设计不可导出最小用途 key 的存储、双读单写轮换和撤销；还能按 XSS、离线数据、设备丢失与服务端越权区分威胁，说明浏览器、KMS/HSM 和授权各自责任。

# Shell 自动化知识点讲义

## LINUX-03 Shell 脚本、环境变量与自动化任务

把终端中成功的一串命令复制进脚本，并不会自动变成可靠自动化。非交互环境的目录、PATH、身份和信号不同；空变量、特殊文件名、管道状态与中途失败会把小错误放大成批量副作用。可靠脚本是一份关于输入、前置条件、输出、退出码、权限、并发、清理和恢复的执行合同。本讲以 Bash 为主要示例，但强调可移植边界。

### 学习前先确认

- 直接前置：[LINUX-01 文件系统、权限与安全命令](../chinese-guides/linux-01-filesystem-permissions-safe-commands.md#linux-01)。本讲直接操作路径、权限、链接、归档与安全批处理。

### 一、先选择解释器和运行合同

脚本第一行声明实际需要的解释器，例如 Bash 特性就不要写成 `/bin/sh`。不同系统的 sh 可能是 dash、bash 或其他实现；数组、`[[ ]]`、pipefail 等语义不一致。保存 Bash 版本并在目标环境测试。

文档写输入参数、环境变量、工作目录、运行用户、所需工具、输出文件、日志、成功/失败码、超时、并发策略和副作用。入口先显示 `--help`，解析参数后验证，再做任何写操作。

命令脚本与库文件分开；被 source 的文件不应擅自修改 shell 选项或退出进程。主函数统一返回状态，顶部只负责调用与退出。

### 二、理解展开顺序才能正确引用

**Shell 展开（Shell Expansion）**包括参数、命令替换、算术、拆词、路径名展开等阶段。`$path` 未引用时，一个字符串可能变成多个参数并匹配文件；`"$path"` 保持为一个参数。绝大多数变量展开都应双引号。

数组保存参数列表，不能把命令拼成字符串再 `eval`。例如 `args=(--format json --output "$target")` 再 `tool "${args[@]}"`，每个边界明确。来自用户的字符串绝不能直接成为 shell 语法。

命令替换会去掉尾随换行，且输出再经展开；不要用它承载任意文件名。批量文件通过 `find -print0`/readarray 或工具原生接口传递。

### 三、引用是数据边界

**引用（Quoting）**决定哪些字符是数据、哪些由 shell 解释。单引号保留字面值，双引号允许部分参数/命令替换，反斜线只处理特定字符。不要为“能跑”层层转义，优先减少 shell 层数。

远程命令、JSON、正则和 SQL 同时出现时尤其危险。将结构化数据写临时文件或通过标准输入，使用各工具参数化能力；不要拼一条跨 SSH 的长字符串。

here-document 也要理解定界符是否引用、是否展开。敏感数据不要出现在命令行、历史、进程列表或调试 trace。

### 四、严格模式不是异常处理魔法

`set -u` 在读取未定义变量时报错，`set -e` 尝试在某些失败时退出，`set -o pipefail` 让管道反映前段失败。它们有条件、循环、子 shell、命令替换等例外，不能替代显式检查。

**管道失败传播（Pipefail）**避免 `producer` 失败而 `consumer` 成功导致整体 0。对关键步骤仍捕获状态、输出清晰错误并执行正确清理。不要在不了解调用方的库文件里全局开启选项。

错误处理函数记录步骤、退出码和安全上下文，避免把所有变量 dump 到日志。预期失败如“文件不存在”应建模为分支，不依赖 `set -e` 猜测。

### 五、输入先验证再规范化

区分必填、可选和默认；拒绝未知选项。路径转为绝对并确认在允许根内，枚举值用 allowlist，数字检查范围。不要把空值默认成危险广范围。

检查前置条件：工具存在、版本满足、源可读、目标可写、空间足够、身份正确、服务状态允许。检查与执行之间可能变化，高风险步骤需使用原子操作或锁缩小竞态。

`--dry-run` 输出将做什么、作用对象和数量，不能仍创建最终文件或触发远端副作用。计划输出应由执行路径共用同一解析结果，避免 dry-run 与真实操作条件漂移。

### 六、临时文件和清理

使用 `mktemp` 在可信目录创建不可预测临时文件/目录，设置最小权限。不要固定 `/tmp/app.tmp`，否则有冲突和链接攻击风险。敏感临时内容避免长期落盘或用受控加密位置。

`trap` 在 EXIT 清理临时资源，在 INT/TERM 记录中断并终止子任务。清理函数必须幂等、路径已验证且不掩盖原退出码。收到 TERM 后不要无限等待。

若失败后临时产物是调试证据，可移动到权限受控的 quarantine 并给保留期，而不是既泄露又永不清理。

### 七、原子写入避免半成品

目标文件先在同一文件系统临时位置完整生成，校验格式/摘要后 rename。直接 `command > important.conf` 会先截断文件，即使命令随后失败。数据库或远端对象需各自事务/版本机制。

多文件更新不天然原子。可写版本目录，完成后切换链接；或使用 manifest 指向一组已完成对象。失败时保留旧版本并清理未发布版本。

写入后验证消费者视角：配置语法、服务读取、文件 owner/mode 和摘要。退出码 0 只证明命令自认为成功。

### 八、幂等让重复执行可预测

**幂等性（Idempotency）**表示同一意图重复执行不会不断增加业务效果。脚本应检查期望状态并只应用差异：目录存在则验证属性，配置使用声明式模板，链接原子指向目标，远端创建使用稳定操作键。

幂等不等于忽略错误。现有对象若配置不同，要更新、明确拒绝或报告漂移，不能静默当成功。重复执行后输出应说明“无变化”还是“修复了漂移”。

测试在成功后立即第二次运行、失败中断后再运行、两实例并发运行。每次检查没有重复条目、半成品和越界权限。

### 九、锁与并发

cron、部署重试和人工触发可能同时执行。使用 `flock` 或平台任务唯一性，定义等待、超时和失败策略。锁文件位置和权限不能让无关用户阻断或劫持。

锁保护共享状态，不要覆盖耗时且无需互斥的准备步骤；但发布指针切换等关键区必须原子。检测“PID 文件存在”不充分，PID 可复用且崩溃会留陈旧文件。

分布式任务不能只靠单机锁。使用数据库唯一约束、租约或队列消费者语义，并设计租约过期和重复执行。

### 十、环境变量是进程输入而非秘密仓库

环境由父进程继承，可能被子进程、诊断工具或错误日志看到。它适合非敏感配置和秘密系统短期注入，但不能提交 `.env` 或无差别打印 `env`。

脚本明确变量名、格式、默认、是否敏感和优先级。区分未设置与设置为空；使用 `${VAR:?message}` 等方式前先确保消息不泄露值。高风险生产值不提供隐式开发默认。

cron/systemd 的 PATH、HOME、locale 和 timezone 与交互 shell 不同。任务使用绝对工具路径或显式安全 PATH，设置 locale/timezone 并记录。不要依赖 `.bashrc`。

### 十一、日志要让失败可定位

日志包含时间、级别、任务/运行 ID、步骤和结果摘要；输出到标准流由调度器收集，或写权限受控文件并轮转。秘密、完整命令参数和个人数据脱敏。

长命令保存 stderr，但给用户简明因果。外部工具失败记录退出码与有限输出，避免几万行淹没根错误。可选 debug 有时间限制且默认关闭。

进度与最终结果分开。脚本成功前不要提前打印“完成”；清理失败是否改变最终退出码由合同决定。

### 十二、退出码形成机器接口

0 表成功，非零区分使用错误、前置条件、暂时外部失败、永久策略拒绝和内部错误。不要所有失败都 `exit 1` 后要求调度器解析中文日志。

函数用 `return`，主脚本 `exit`。保存原始失败码，包装时记录映射。管道、多后台任务和 `wait` 都要收集每个结果。

调用方据此决定重试、告警或人工介入。可重试码仍需退避和最大次数；不可重试配置错误立即停止。

### 十三、网络调用有时间和重试预算

所有网络命令设置连接/总超时、重试范围和最大次数。只重试暂时错误及幂等操作；上传/创建使用幂等键或先查询状态。随机退避防止同时任务冲击恢复服务。

下载验证 HTTPS、来源、摘要/签名和大小，再原子放置。`curl | sh` 把网络内容直接变代码且无法先审查，不应用于受控环境。

保存远端请求 ID和响应状态，不把令牌写 `-v` 日志。代理、证书和 DNS 是显式依赖。

### 十四、cron 与 systemd timer

cron 简单但环境精简，容易重入且日志/状态弱。使用绝对路径、明确 shell、锁、超时、输出收集和邮件/告警。表达式与时区、夏令时需测试。

systemd timer 可结合 unit 的用户、环境、资源、失败状态和 journal；`Persistent` 等行为需按版本核验。无论调度器，任务本身仍需幂等和恢复。

任务失败后不能默默等下次覆盖。告警包含运行 ID、最后成功时间、下一步和安全日志链接。

### 十五、信号、超时与子进程

调度器终止脚本时，shell 应把信号传给子进程并等待有限清理。后台任务要保存 PID、捕获结果并在退出时终止。`timeout` 工具提供外部期限，但应用仍需安全中断点。

在复制完成、指针切换、数据库迁移等阶段定义是否可取消。关键提交阶段可短暂屏蔽中断，完成后再响应；不可无限忽略。

故意发送 INT/TERM，检查没有孤儿进程、锁和半文件。OOM/KILL 无法执行 trap，所以恢复不能只依赖清理函数。

### 十六、ShellCheck 与测试

静态检查发现未引用变量、不可移植语法和常见陷阱，但不能证明路径范围和业务正确。为纯函数/解析写单测，为文件和外部命令使用临时 fixture/可控替身，为完整任务做隔离集成测试。

测试空值、空格/换行/前导短横线、无匹配 glob、权限拒绝、磁盘满、网络超时、管道前段失败、并发、中断和第二次运行。断言退出码、输出、最终状态和无残留。

脚本审查重点看删除、权限、远端执行、秘密与 `eval`。任何宽泛递归命令都需要明确根路径、预览和恢复。

### 十七、何时不再使用 Shell

当数据结构复杂、并发多、需要精细异常/重试、跨平台或长期维护时，使用有类型与测试生态的语言。Shell 适合编排现有命令和小型系统任务，不适合作为大型业务应用。

迁移不表示调用外部命令风险消失。新语言仍需参数边界、超时、退出码、原子性和秘密治理。保留 CLI 合同，便于渐进替换。

短脚本也可能删除大量数据，风险按权限和副作用评估，不按行数。

### 十八、发布、版本与兼容

脚本随仓库版本化，帮助文本与行为同评审。破坏参数、退出码或输出格式需要迁移期，因为其他自动化可能把 CLI 当 API。为机器消费者提供 JSON 或稳定格式，面向人的输出可读但不保证可解析。

依赖外部命令时记录最低和已验证版本，并在启动检查必要能力；不要仅比较版本字符串后假定特性。发行版升级、locale 和时区变化进入兼容测试。下载工具要验证来源和摘要，并固定版本。

发布产物带 changelog 与回滚版本。高风险脚本可先在 canary 目标和 dry-run 执行，限制一次处理数量。旧版本仍在调度器运行时，要能定位并逐步替换，不能只更新仓库文件。

### 十九、代码审查的因果问题

审查者沿数据流追踪每个外部输入到命令参数和每个写操作到允许根；沿失败流追踪非零状态到清理、日志与最终码；沿生命周期追踪并发、信号和第二次运行。仅看 shell 风格无法发现业务越界。

对危险命令要求示例计划输出、目标上限和恢复证据。对 `sudo`、SSH、数据库和云 CLI 说明凭据和远端身份。新脚本若复制已有工具能力，优先复用经过测试的实现。

上线后观察成功率、持续时间、重试、锁等待、最后成功和数据变化量。异常“成功但处理 0 项”也要告警，避免上游路径错误被当正常。

将正常运行耗时和处理数量作为基线，异常偏快或偏慢都进入调查；自动化的沉默成功同样可能是失败。

自动任务的负责人离开或外部 API 停用时，仍要有人能定位、暂停和安全重跑。为每个调度入口记录 owner、告警接收者、凭据轮换、上游合同和停用步骤；定期演练在没有原作者的情况下处理失败。可维护性也是自动化可靠性的一部分。

### 二十、最终复核

脚本上线前确认解释器/版本、参数与默认、路径范围、引用和数组、严格模式例外、临时文件、原子写、幂等、锁、秘密、日志、退出码、超时/重试、信号、调度环境、dry-run、测试与回滚。

高级自动化不是“无人值守地跑命令”，而是失败、中断、重复和并发都能得到可预测结果。把 shell 语法中的隐含行为转化为显式合同，并以最小权限和可恢复状态执行，脚本才有资格进入生产。

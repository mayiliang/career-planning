# 高级与前沿主题中文核心讲义

更新时间：2026-07-29

本讲义服务于暂时没有稳定官方中文版、或中文资料明显滞后的知识点。它负责建立中文概念框架、学习主线和工程边界；知识库中保留的英文官方原文只用于核对最新 API、协议字段和版本变化，不进入首考资料定位题。若讲义与版本化规范发生冲突，应先依据最新版官方规范同步修订本讲义和考核范围，再要求学习者掌握变化。

## A11Y-01

WCAG 2.2 用“可感知、可操作、可理解、健壮”组织成功准则，A/AA/AAA 是符合级别而不是质量分数。高级前端至少应把 AA、完整键盘操作、可见焦点、合理焦点顺序、名称/角色/值和动态状态通知纳入交付标准。

语义 HTML 是第一选择：标题形成层级，地标划分区域，label 关联表单，button/link 保持各自行为。只有原生元素无法表达所需模式时才使用 ARIA；ARIA 只改变辅助技术看到的语义，不会自动增加键盘行为、焦点管理、校验或视觉样式。

复合组件要按交互模式实现键盘和焦点。对话框打开后把焦点移到合适位置、限制在对话框并在关闭后归还；菜单、Tab、列表框和网格具有不同方向键与选择语义，不能复制同一套处理。`tabindex="0"` 加入自然顺序，`-1` 允许脚本聚焦，正数 tabindex 会制造难以维护的顺序。

动态体验需要可感知反馈：错误与输入建立程序化关联，加载和结果变化使用合适 live region，焦点不应被无意义抢走。颜色不是唯一信息，对比度、文本缩放、触控目标、横竖屏、高对比/强制颜色和 `prefers-reduced-motion` 都要纳入组件状态设计；视频还需字幕、音频描述或等价替代。

AI 流式回答应按语义段节流播报，允许暂停并保持用户焦点；不能逐 token 触发 live region。生成式 UI 只能组合语义和键盘行为已知的组件，并验证模型选择的组件、名称、状态和顺序没有破坏无障碍树。生成图片提供可编辑替代文本，音视频提供字幕或转写，AI 生成的替代内容仍需用户校正。

自动扫描只能发现部分问题。验证必须包含语义与可访问树检查、完整键盘任务、至少一种主流屏幕阅读器抽查、200%/400% 缩放、强制颜色、减少动态效果和移动触控。Lighthouse 与 DevTools 用于发现线索，不能以单一分数替代人工任务证据。

缺陷按阻断程度和影响人群排序，修复后加入组件测试、E2E 或设计系统规则防止回归。组织还要定义组件准入、CI 门禁、严重度、负责人、修复时限、例外审批与到期、跨浏览器/辅助技术基线和发布阻断条件。合格交付要能说明适用的 WCAG 成功准则、采用的 APG 交互模式、已测环境和剩余限制，而不是声称一次扫描“完全无障碍”。

## ENG-08

软件供应链安全关注“依赖和制品从哪里来、由谁构建、是否被篡改、能否追溯”。SBOM 描述组件清单，SLSA 描述构建完整性级别，签名与来源证明用于验证制品身份；它们不能替代漏洞扫描、依赖审查和运行时防护。

落地时要固定 lockfile、限制安装脚本、审查直接与传递依赖、最小化 CI 权限、保护发布密钥，并让构建产物可重复和可追溯。仅生成一份从不更新的 SBOM，或只检查已知 CVE，都不构成完整治理。

可分发还需要许可证治理。直接与传递依赖的许可证、NOTICE/归属、源码提供和修改声明义务会随源代码、二进制、容器、桌面包或 SaaS 的分发方式不同；自动扫描只提供候选结论，未知、自定义、双许可证和复制文件仍需人工复核。允许/禁止/需审批规则、例外 owner、期限和替换计划应与制品摘要绑定，不能到发布后才补清单。

本知识点负责组织级、工具无关的软件供应链基线，以及 SBOM、许可证清单、NOTICE、签名和来源证明如何指向同一不可变制品。AI 建议依赖和生成代码来源的专项准入由 AIDEV-07 负责，容器镜像扫描与制品准入由 DOCKER-04 负责；三者共享证据但不重复考核。

## COMP-03

组件文档应同时说明意图、API、状态模型、可访问性、示例、错误用法和迁移方式。示例必须可以运行并进入自动化测试，不能把 Storybook 当作与真实组件实现脱离的截图仓库。

版本治理应采用明确的兼容承诺、语义化版本、变更日志、弃用周期和迁移脚本。破坏性变化不仅包括类型签名变化，还包括 DOM 结构、样式令牌、事件时序、默认值和无障碍语义变化。

文档示例要作为可执行测试随组件发布；无障碍语义、DOM/样式约定和默认行为变化也可能是破坏性变更。弃用先告警、给迁移对照或 Codemod，并观察旧 API 使用量，达到期限后再移除。发布记录关联制品和版本，不能只在聊天中通知。

## PLATFORM-03

物料平台的目标是减少重复决策并提高一致性交付能力，不是追求组件数量。需要持续跟踪采用率、覆盖场景、重复实现、升级成功率、缺陷密度、支持成本和从需求到交付的时间。

治理应明确所有者、准入标准、版本策略、弃用机制和反馈通道。低使用率可能意味着发现困难、API 不合适或迁移成本过高，不能简单归因于团队“不执行规范”。

平台准入要求明确复用场景、稳定 owner、测试、文档、版本和支持承诺；退出时提供弃用、迁移和删除路径。采用率要按目标用户和任务解释，同时观察升级成功率、缺陷、支持工单与交付周期；强制接入或组件数量增长不能单独证明平台价值。

## DX-01

前端平台工程把构建、测试、发布、项目创建、升级、文档和所有权等重复认知封装成可自助的产品能力。平台的用户是开发者，目标是让团队更快、更安全地完成真实任务，而不是统一所有工具。平台团队应先研究开发者旅程、等待时间、常见失败和认知负担，再选择自动化范围；没有用户、反馈和退出机制的脚本集合不是平台产品。

项目图描述应用、库、服务和所有权，任务图描述构建、测试、生成与发布的依赖。`affected` 只执行受变更影响的任务，但正确性取决于显式依赖、环境变量、配置、工具链和外部输入是否进入图。缓存键必须覆盖源码、依赖、命令、配置、运行时和有效环境，缓存产物还需隔离权限并验证来源；关闭缓存重跑应得到等价结果，不能用一次命中率证明确定性。

Golden Path 是可发现、可执行、可升级的推荐路径，通常由模板、生成器、文档、策略、流水线和可观测性组成。它应提供安全默认值和常见场景的最短路径，同时保留有审批、有责任人的逃生通道。生成器和 Codemod 必须支持 dry-run、幂等、版本、测试和回滚；否则模板复制会逐渐漂移，升级成本最终转嫁给每个业务团队。

开发者门户将服务目录、所有权、运行手册、文档、模板和任务入口连接起来，但门户页面数量不是价值。平台应定义能力 API、SLA、版本和弃用策略，避免隐藏失败或形成新的中央排队。衡量至少覆盖任务完成时间/成功率、采用与留存、开发者满意度或认知负担、缺陷/变更失败率和平台支持成本；强制使用率、生成代码量和仓库数量不能单独证明效果。

AI 编码 Agent 会放大平台的好坏。平台应向 Agent 暴露精简且版本化的仓库地图、允许命令、依赖边界、Owner、策略和验证结果，而不是整个组织数据；命令按白名单和最小权限运行，高风险发布仍需确认。Agent 与人类使用同一套确定性构建、测试、缓存和制品来源门禁，不能为追求自动化速度建立旁路。

## API-01

OpenAPI 描述 HTTP API 的路径、操作、参数、请求体、响应、安全方案和可复用 Schema；YAML 只是常见序列化格式。规范化时应先完成 YAML 解析与引用解析，再建立内部模型，不能依赖缩进文本或字符串替换。

重点处理 `$ref`、组合 Schema、nullable/null、只读/只写、枚举、鉴别字段、不同响应状态和递归引用。解析器必须限制文件大小、引用深度和远程引用，并用固定样例验证输入到内部模型的确定性。

OpenAPI 3.2 需要识别文档版本与 JSON Schema 方言，规范化路径、Webhook、媒体类型、流式响应和安全方案。多文档组合与远程引用要有确定的基址、缓存和循环上限。兼容性 diff 不能只比较字段：参数位置、必填性、枚举、空值、状态码、错误体和鉴权语义都可能破坏消费者。

## MCP-01

MCP 把 Host、Client 与 Server 分离：Host 管理用户体验和安全边界，Client 维护与单个 Server 的连接，Server 暴露 Tools、Resources 和 Prompts。Tool 是可执行操作，Resource 是可读取上下文，Prompt 是可发现模板，三者不能混为一个万能 RPC。

Tool 描述应让模型和人判断何时调用、输入什么、会产生哪些副作用；输入输出用 JSON Schema 约束格式、范围、枚举和互斥关系。Resource URI 要稳定、可授权并支持分页/缓存，Prompt 参数要可验证和可版本化；错误区分参数无效、业务拒绝、权限不足、暂时故障和未知结果，不能用自然语言“成功”掩盖协议失败。

核心能力模型不绑定具体传输或会话实现。协议版本、客户端信息和能力必须可协商，调用要有请求身份、取消、超时、分页和兼容降级，不能根据 Server 自报名称直接授予信任；Streamable HTTP、stdio、无状态/显式状态、会话恢复和 legacy 双栈细节统一由 `AGENT-03` 负责。

具有写入、发送、删除、发布或付费影响的工具必须最小权限、显式确认和幂等。Resource、工具结果和 Prompt 内容都属于不可信输入；文件/URL 读取设置允许范围、大小和类型上限。可观测记录身份、协议/工具版本、参数摘要、耗时、结果和关联追踪，但在采集前移除密钥、个人数据和不必要上下文。

最小验收应实现 Tool、Resource 和 Prompt 各一项，覆盖能力缺失、Schema 错误、分页、权限拒绝、重复副作用和未知字段降级。协议打通只是起点，语义边界、安全和业务恢复证据同样属于完成条件。

## CAREER-02

架构图用于回答特定受众的问题。系统上下文图说明人与外部系统，容器图说明可独立运行或部署的单元，组件图说明容器内部主要职责；不要在一张图中混合所有层级。

每张图都应有标题、范围、图例、方向和关键约束，并与真实代码或部署保持同步。框和箭头本身不是结论，应在图旁说明数据、信任边界、同步/异步关系、失败路径和被刻意省略的细节。

架构图的箭头要标注协议、同步/异步、数据与失败方向，信任边界和第三方依赖不能隐藏。图与代码、部署和 ADR 通过稳定名称关联，变化时可校验；评审时按受众分层展示上下文、容器和关键时序，避免一张图塞满文件与类。

## CAREER-04

故障复盘要建立从现象、影响、时间线、证据、直接原因到系统性因素的因果链。先恢复服务并保全证据，再进行分析；不能用“某人操作失误”代替对权限、流程、测试、监控和恢复能力的审查。

改进项应有所有者、截止时间和验证方式，并按预防、检测、缓解和恢复分类。一次复盘的质量取决于能否降低同类风险，而不是文档篇幅或是否找到了单一根因。

事故发生时先按用户影响、范围和紧迫度给出可调整的严重度，再建立单一指挥链。事故指挥官负责目标、优先级和角色，操作负责人实施缓解，沟通负责人按固定节奏更新内部与用户状态，记录员维护带时间戳的事实、假设、决策和结果。状态更新写明已知/未知、当前影响、正在做什么和下次更新时间，不在证据不足时承诺 ETA。

恢复命令或单个指标变绿并不等于事故结束。用技术 SLO、核心用户任务和数据完整性共同验证，并在约定窗口观察；交接时明确当前状态、风险、下一动作和 owner。复盘行动项按风险排序，记录 owner、期限、验收和逾期升级；完成实现后还要复验同类故障的预防、检测或恢复时间确实改善，才能关闭。

## VUE-09

Vue Query 管理的是来自服务端、具有异步生命周期和失效规则的数据；Pinia 更适合本地业务状态。缓存键必须完整表达请求身份，查询函数必须可取消并抛出真实错误，组件不应自行复制一份长期不同步的服务端数据。

理解 staleTime、gcTime、失效、预取、分页、乐观更新和 SSR hydration 的区别。写操作成功不等于所有缓存自动正确，应根据服务端返回精确更新或失效；乐观更新必须保存快照并处理并发与回滚。

## AIAPP-07

Prompt Injection 的根因是模型无法可靠地区分指令和不可信数据。网页、检索片段、上传文件、工具结果与模型输出都必须按不可信输入处理，不能依赖“忽略恶意指令”一类提示词作为唯一防线。

工程控制包括最小权限工具、数据与指令分层、参数校验、域名与资源白名单、高风险确认、输出编码、敏感数据隔离和审计。测试集要覆盖直接注入、间接注入、编码混淆、越权工具调用和数据外泄。

Prompt Injection 来自用户、网页、检索文档、工具结果和跨 Agent 消息等不可信内容。系统指令、数据和工具描述分层，敏感动作靠服务端授权、参数校验、最小权限和确认，而非提示词“不要执行”。测试覆盖直接/间接注入、数据外泄、越权工具和多轮持久化。

## AIAPP-08

模型评估先把产品目标拆成可判定指标，再建立包含正常、边界、失败和对抗样本的固定数据集。确定性规则适合 Schema、引用、工具参数和权限断言，人工标注适合主观质量，模型裁判适合规模化辅助，但必须用人工样本校准位置、长度、风格和自我偏好。

评估按系统分层：模型输出检查事实和格式；RAG 检查召回、引用和无答案；工具检查选择、参数、授权、结果与副作用；Agent 检查轨迹、停止、恢复和成本；多轮会话检查跨轮约束和记忆；语音检查转写、首音频、打断、乱序与降级。最终答案正确不能掩盖越权工具或错误副作用。

比较版本时固定数据、采样参数和评分规则，保存版本与可回放轨迹，报告均值之外的分布、置信区间、失败类型、延迟、安全和成本。离线回归通过后仍要灰度并观察真实任务成功与人工介入。

生产 trace 要把 Prompt/模板版本、模型/供应商、检索文档标识、工具调用、token、延迟、费用、质量判定、安全结果和用户反馈关联到同一请求，同时执行采样、脱敏、留存和访问控制。线上失败经人工确认后才能进入回归集，不能把含秘密或个人敏感数据的原始会话直接复制到评测环境。

单次演示、只看总体胜率、用训练样本当测试集、只评最终文本或让待评模型给自己打分，都不能证明上线质量。

## AGENT-01

Agent Loop 通常包含获取状态、选择下一步、调用工具、观察结果和判断是否停止。循环必须有明确目标、最大步数、时间与成本预算、可恢复状态和终止条件，不能把“继续思考”当作进展。

规划适合多步骤和高代价任务，简单确定性操作应直接执行。遇到缺少权限、关键输入或不可逆影响时应暂停并请求用户；工具连续失败、目标已满足或边际收益过低时应停止。

Agent Loop 每轮包含观察、计划/选择动作、执行、验证和状态更新。停止条件包括目标达成、不可恢复错误、预算/时间耗尽、重复循环和需人工决策；每次工具调用有 id、超时、取消与结果状态。把完整思维过程展示给用户不是可观测性，结构化决策摘要和证据更安全。

## AGENT-03

无状态 Streamable HTTP 让每个请求携带完成处理所需的信息，服务器通过显式 handle 保存长任务或业务状态。这样更利于水平扩展、缓存、路由和故障恢复，也避免把隐式连接会话当成业务事实来源。

协议版本通过请求头协商，路由与缓存必须考虑方法和名称维度。兼容旧会话协议时应放在独立适配层，明确超时、重连、幂等和状态迁移，不能让旧语义污染新核心模型。

MCP 传输负责消息到达，不应承载隐含业务会话。stdio 与 Streamable HTTP 都要处理初始化能力、请求 id、取消、断开、重连和重复响应；长任务使用显式 task handle。代理、负载均衡和多实例部署下，客户端不能假设下一请求命中同一内存进程。

## AGENT-04

Client 连接前要发现服务器能力并选择双方支持的协议版本；连接后分别缓存 Tool、Resource 和 Prompt 元数据，并依据通知、TTL 或版本变化失效。不能假设所有 Server 都支持同一组扩展。

兼容策略应定义最低版本、可选能力、未知字段处理、降级路径和错误提示。双栈期间用契约测试验证新旧 Server，避免用宽松 `any` 掩盖协议差异。

客户端兼容层先协商协议版本和能力，再决定是否调用 Tool、读取 Resource 或使用扩展；未知能力安全忽略或降级。每个 Server 的连接、权限和错误隔离，不能因同名工具共享信任。兼容测试覆盖旧/新 Server、能力缺失、Schema 变化和传输切换。

## AGENT-05

Human-in-the-loop 不是每一步都弹确认，而是把人的判断放在目标含糊、高风险副作用、权限扩大和不可逆决策处。确认界面必须展示拟执行动作、关键参数、影响范围、数据来源和取消结果。

用户补充输入后要关联原请求并避免重复执行；超时、拒绝和修改参数都是正常状态。低风险只读操作可按策略自动执行，高风险动作不能因模型“置信度高”而跳过审批。

Human-in-the-loop 按动作的可逆性、金额、外部影响和权限分级。确认界面展示主体、目标、参数摘要、预计影响和替代方案，审批绑定具体请求摘要与有效期；参数变化后旧批准失效。拒绝、超时和撤回都是正常终态，不能用批量“始终允许”绕过高风险复核。

## AGENT-07

多 Agent 适合职责可分离、可并行且有明确交付契约的任务。每个 Agent 应获得最小必要上下文、工具权限、输入、输出格式和停止条件，协调者负责合并、冲突处理和最终验证。

共享完整对话会增加泄密、成本和指令冲突风险；完全隔离又会导致重复劳动。应通过结构化任务单、版本化产物和证据引用交接，并限制递归委派、总步数和总体预算。

多 Agent 协作要定义角色、输入输出、共享上下文和最终责任人。消息与产物带任务、版本、来源和权限，避免一个 Agent 的不可信结果直接成为另一个的高权指令。并发委派设置预算、去重和停止条件，冲突由明确仲裁规则或人工处理，并记录交接与审计。

## AGENT-08

工具可发现性依赖清晰名称、动作型描述、精确 Schema 和有区分度的适用场景。字段描述要表达业务含义、单位、格式、默认值和限制，不能只重复字段名。

Tools 用于执行动作，Resources 用于读取可寻址上下文，Prompts 用于可复用交互模板；选择依据是语义、所有权、副作用和生命周期。只读数据不应为了“方便模型调用”全部包装成有副作用的 Tool，Prompt 也不能隐藏未经验证的权限扩大。

复杂输入优先拆分为可组合工具，避免巨大可选参数对象。必填、枚举、格式、范围、互斥和 `additionalProperties` 策略进入 Schema；列表与资源定义游标、分页、TTL 和取消。路径/URI 先规范化，再限制到授权根、协议和大小，防止遍历、符号链接逃逸与资源耗尽。

用正例、边界例、反例和易混淆工具建立选择评估集，统计选错、参数无效、无调用和不应调用时误调用。工具变更要版本化并验证旧 Client 的未知字段和能力降级，不能只通过一次演示判断可发现性。

## AGENT-10

Agent 安全采用身份、授权、输入、执行、输出和审计的纵深防御。OAuth/OIDC 要验证 issuer、audience、scope、state/nonce 与 PKCE；禁止把上游 Token 原样透传给下游服务。

Server 端仍需逐次授权并防御 confused deputy、SSRF、DNS rebinding、开放重定向和越权资源访问。文件参数要规范化并限制根目录、处理符号链接；URL 参数限制协议、主机、解析后地址和重定向，不能只匹配字符串前缀。

工具描述、Resource、Prompt、网页和工具结果都可能携带提示词注入或投毒内容。模型看到“管理员要求”不形成授权证据；执行层重新校验参数、用户、资源和策略，高风险动作展示真实目标、影响和关键参数供用户确认。

工具权限按任务和时间最小化，凭证短期、按 audience 绑定且可撤销。密钥不进入 Prompt、浏览器或普通日志；审计记录能追溯用户、Client、Server、策略版本和结果，同时对个人数据设定访问和保留期限。

安全测试应覆盖 Token 透传、issuer/audience 混淆、CSRF、SSRF、DNS 重绑定、路径穿越、符号链接、恶意工具描述、间接注入和重复副作用。只有威胁模型、可运行验证和拒绝证据共同成立，才算完成。

本知识点止于身份、授权、工具权限和执行隔离。目标劫持、记忆/上下文投毒、级联失效、人机信任利用、失控 Agent 等系统级威胁的矩阵、红队与滥用防护统一由 `AISAFE-02` 负责。

## AIDEV-01

`BIZ-08` 负责把需求、规则、方案、测试和验收形成通用追踪链；本点从该结果开始，为 AI Agent 封装最小、版本化、可撤销的执行上下文。上下文列出允许读取和修改的路径、可调用命令/工具、不可触碰资产、预算、检查点、停止条件、人工升级和证据格式。

Agent 循环每一步都必须产生可观察进展，并在测试失败、权限不足、上下文冲突、预算耗尽或循环不收敛时停止。需求变化时先更新权威规格，再重新生成任务上下文；代码、模型消息或旧摘要都不能反向成为事实来源。

完成判定来自已有验收项与独立工具证据，而不是模型自报。上下文过多会扩大泄露和误改面，过少会诱发猜测；应通过任务切片、按需读取、明确版本和失败升级平衡两者。

## AIDEV-04

AI Code Review 应先按影响面和风险分级，再检查正确性、安全、数据一致性、并发、资源释放、兼容性和测试证据。模型建议只是线索，必须定位到具体代码、可复现条件和规范依据。

高风险问题要求人工确认和可运行验证；样式偏好不能与真实缺陷混在一起。评审结果应去重、标注置信依据，并统计误报、漏报和修复采纳率，防止“评论很多”被误认为质量提升。

AI 评审按认证/授权、数据、并发、迁移、供应链、性能和可维护性分级，先验证高影响问题。评论引用具体行、失败场景和证据，区分阻断、建议与疑问；模型建议可能误报或遗漏，必须执行测试、静态分析或最小复现，不因措辞自信直接合并。

## AIDEV-06

AST 改写先解析为语法树，依据节点类型和语义定位目标，再变换、打印和验证。相比正则替换，它能理解嵌套结构和语法边界，但仍需处理别名、作用域、注释、格式和不同语法版本。

生成器应幂等、确定、可重复运行，并保留无法安全处理的输入。用 golden file、语法解析、类型检查和真实仓库样本验证；不能在匹配不明确时静默修改大量文件。

Codemod 先解析 AST 并保留语法/注释语义，转换规则具有版本、前置条件和冲突诊断。支持 dry-run、确定性输出、幂等和可回滚批次；对语义不确定的位置停止并请求人工。用固定输入/快照、类型检查、测试和二次运行验证，禁止正则批改复杂语法。

## AIDEV-07

AI 生成依赖建议时仍要验证包身份、维护状态、许可证、版本、下载来源、传递依赖和安装脚本。名称相似、刚发布、低维护或要求异常权限的包应进入人工审查。

锁定版本与校验和，使用可信 Registry、来源证明、SBOM 和漏洞扫描，并隔离构建权限。生成代码中复制的片段也可能带有许可和供应链风险，不能因为“由模型生成”就视为无来源。

AI 新增依赖前核验包名、发布者、版本、许可证、维护状态和是否真实存在，锁定解析并限制安装脚本。生成代码记录来源与审查，不复制未知许可片段或泄露仓库秘密。SBOM、扫描、签名和可重复构建仍适用，模型推荐不能成为供应链例外。

本知识点只负责 AI 建议进入依赖清单和生成代码进入仓库前的专项审查；组织级供应链控制归 ENG-08，容器镜像构建与生产准入归 DOCKER-04。

## AIDEV-08

AI 研发提效要同时观察交付速度、质量、开发者体验和业务结果。可使用交付前置时间、变更失败率、恢复时间、返工率、评审时间、缺陷逃逸率和任务成功率，但不能用生成代码行数衡量价值。

评估应有基线、同类任务、足够周期和质量护栏，并区分学习期与稳定期。速度提高但返工、安全事件或认知负担增加时，不应判定为净提效。

提效评估以成功完成的真实任务为单位，比较周期、返工、缺陷、评审负担和用户结果，而不是生成行数或提示次数。实验控制任务难度、经验和工具学习期，记录失败与人工接管；局部更快可能增加下游验证和维护成本，应观察发布后质量。

## AIDEV-10

团队 AI 治理要定义允许的数据、工具、模型、用途、审批和留存规则。源代码、客户数据、密钥和个人信息按敏感级别处理，明确哪些内容不得发送到外部模型。

需要记录模型/工具版本、重要输入来源、人工责任人和上线验证证据。治理的目标是让风险可控且可追溯，不是禁止实验；规则应配套安全沙箱、培训、例外流程和定期复审。

团队规范明确哪些数据/代码可发送、允许模型与地区、保留策略、身份权限、人工审批和禁止动作。集中管理供应商和日志但最小化内容，支持退出、导出与删除。例外有 owner 和期限，培训与抽查验证实际执行；合规打勾不能替代隐私与安全证据。

## AIDEV-11

编码 Agent 只阅读源码时，看不到浏览器中的真实 DOM、可访问性树、网络时序、运行时状态、布局、性能和用户操作结果。可靠调试必须形成“固定环境与输入—复现—采集证据—提出假设—最小修改—同条件复验—回归”的闭环；模型文字解释和测试最终变绿都不是运行时证据。

任务开始前固定版本、账号权限、数据夹具、路由、视口、网络和复现步骤，并记录检查点。证据可包括 DOM/可访问性快照、Console、Network 请求和响应摘要、Storage 状态、截图、Playwright trace、Performance trace、堆快照和框架运行时状态。每项观察都应带时间、页面、操作和关联标识，避免 Agent 在陈旧标签页、错误会话或非确定数据上修复另一个问题。

Agent 先观察再写入。浏览器工具按域名、动作和数据最小授权；发送、删除、购买、授权和发布等副作用必须展示影响并由用户确认。Cookie、Token、表单值、响应体和日志先脱敏，网页文字、工具描述和运行时自定义工具都按不可信输入处理。不能让 Agent 为通过验证而删除断言、扩大 Mock、关闭 CSP/类型检查或清空真实数据。

修复后使用相同输入和环境比较修改前后的行为、请求、视觉、可访问性和性能，并运行与风险相称的类型、单元、契约、E2E、视觉、安全或性能回归。证据包至少包含复现脚本、失败证据、根因假设、变更摘要、复验结果和剩余风险，使另一位工程师能够重放，而不是只留下 Agent 对话。

截至 2026-07-29，Chrome DevTools 面向 Agent 的 MCP/CLI 可以作为稳定调试入口；框架暴露自定义运行时工具、Agent 内存调试和 WebMCP 调试仍需按实验能力管理。所有自动化都要有能力检测、权限边界和人工 DevTools/Playwright 降级，不能把某个浏览器或 Agent 产品当作通用 Web 标准。

## LINUX-01

Linux 文件系统从根目录组织，路径、挂载点、用户/组和权限共同决定访问结果。需要掌握绝对/相对路径、软硬链接、所有者、读写执行位、umask、sudo 边界以及 `/etc`、`/var`、`/proc`、`/tmp` 等目录用途。

命令学习要围绕查看与验证：`pwd`、`ls`、`find`、`stat`、`chmod`、`chown`、`df`、`du`。不要在不了解解析结果时递归修改权限，也不要用 `777` 或长期 root 权限掩盖所有权问题。

## LINUX-02

排障从“进程是否存在、监听什么端口、请求走到哪里、日志记录了什么”建立证据链。常用工具包括 `ps`、`top`、`ss`、`lsof`、`journalctl`、`curl`、`dig` 和 `ip`。

先确认时间范围、PID、端口、DNS、路由和返回码，再形成假设并做最小验证。不要一看到端口不通就重启服务；重启可能清除现场，也可能暂时隐藏资源泄漏、配置错误或依赖故障。

进程排障从监听端口、PID/父子关系、启动参数、工作目录、环境和资源用量建立事实，再关联 systemd/应用/代理日志时间线。DNS、路由、TLS、代理和防火墙逐层验证，区分连接拒绝、超时和应用错误；不能一遇故障就重启丢失现场。

## LINUX-03

Shell 脚本由命令、退出码、管道、重定向、变量展开和控制结构组成。可靠脚本应校验输入、正确引用变量、处理失败和临时文件，并让重复运行保持安全。

理解 `set -e` 的边界、管道退出状态、信号与 `trap`，使用 ShellCheck 发现常见错误。环境变量适合运行时配置但不等于安全存储；Cron 任务必须显式设置工作目录、PATH、日志和互斥。

Shell 自动化启用严格错误处理，参数引用避免空格与通配符扩张，临时目录和清理使用 trap。环境变量分清必填、默认和秘密，日志不输出凭据；脚本可重复运行、支持 dry-run 并以退出码报告部分失败。对路径和目标先验证再执行破坏动作。

## LINUX-04

服务器基础防护从减少攻击面开始：及时更新、关闭无用服务、最小用户权限、SSH 密钥认证、限制管理入口、主机防火墙、日志与备份。禁止直接共享 root 密钥或把应用长期运行在 root 下。

SSH 配置变更要先保留现有会话并验证新会话，避免把自己锁在服务器外。安全控制必须包含密钥轮换、失败登录监控、恢复演练和变更记录，而不只是一次性“加固脚本”。

服务器按最小权限创建用户和服务账户，SSH 使用密钥、限制来源并审计，sudo 只授权必要命令。补丁、防火墙、暴力破解防护、密钥轮换和备份恢复形成基线；应用 Secret 不放源码或 shell 历史。加固后仍要保留受控运维和应急访问路径。

## DOCKER-01

镜像是只读分层制品，容器是镜像的运行实例；Dockerfile 描述可重复构建过程。构建上下文、指令顺序和 `.dockerignore` 会影响缓存、速度与泄密风险，多阶段构建用于分离构建工具和最小运行时。

固定基础镜像策略、避免把密钥写入层、合并相关安装与清理步骤，并让非 root 用户运行应用。缓存命中不是正确性的证明，依赖更新和可重复构建需要显式策略。

镜像分层要让依赖安装可缓存且运行层最小，固定基础镜像 digest、非 root 用户、只复制必需产物并定义健康检查。构建参数不是 Secret 容器，临时凭据用受控 secret mount。多阶段构建后检查最终层、架构和入口，避免开发依赖与源码意外进入。

## DOCKER-02

Compose 用服务、网络、卷、配置和密钥描述多容器应用。服务名可作为默认网络中的 DNS 名称；卷的生命周期独立于容器；环境变量插值、容器环境与应用配置是不同层次。

开发和生产配置要明确分离，健康检查不能只验证进程存在。数据库等有状态服务使用命名卷并演练备份恢复，敏感信息不要提交到 Compose 文件，服务间只开放必要端口。

Compose 明确服务 DNS、端口暴露、网络、卷、健康依赖和环境覆盖；`depends_on` 的启动顺序不等于应用已就绪。数据卷有备份/迁移/权限策略，开发绑定挂载不照搬生产。配置按环境分层但保持拓扑可比，Secret 不写进 Compose 或镜像。

## DOCKER-03

容器排障先检查状态、退出码、日志、资源、健康检查、挂载和网络，再进入容器查看。`exec` 是临时诊断手段，不应在运行容器内手工修复后把它当成正式版本。

为 CPU、内存、进程数和日志设置上限，正确处理 PID 1 与终止信号，并使用只读文件系统和最小能力。OOM、磁盘满、健康检查风暴和重启循环都要有可观测与恢复策略。

容器调试要区分宿主、容器网络和应用监听地址，检查只读文件系统、用户权限、DNS、证书和资源限制。CPU throttle、OOM 与磁盘满会表现为延迟或重启，需关联 cgroup 指标和日志；生产镜像不永久内置调试工具，采用临时、审计的诊断方式。

## DOCKER-04

镜像安全包含可信基础镜像、最小内容、漏洞扫描、签名/来源证明、SBOM、运行用户和及时重建。扫描结果要结合可利用性、运行路径和修复版本排序，不能只以漏洞数量判定风险。

发布流水线应验证 digest 和签名、保护 Registry、限制推送权限并保留可回滚版本。不要在构建参数、镜像层或历史记录中写入密钥，也不要长期运行无法追溯来源的 `latest`。

镜像治理固定 digest，生成 SBOM、扫描 OS/应用依赖、签名并记录来源证明；基础镜像更新触发重建和回归。漏洞按可利用性与暴露处理，例外有期限，生产准入验证签名与策略。签名只证明身份/完整性，不证明内容无漏洞或许可证合规。

本知识点以容器镜像及 Registry/运行准入为边界；跨语言、跨制品的软件供应链总策略由 ENG-08 负责，AI 推荐依赖与生成代码来源由 AIDEV-07 负责。

## EDGE-01

BFF 为特定前端聚合认证、数据和协议，能降低客户端复杂度，但不应复制核心业务规则。Edge/Serverless 运行时具有执行时长、内存、网络、文件系统和 API 限制，需要按部署平台验证。

设计时明确缓存键、用户隔离、区域一致性、冷启动、密钥、重试和可观测性。靠近用户并不自动更快；跨区域数据访问、无命中缓存和过重依赖可能抵消边缘收益。

边缘运行时通常限制 Node API、CPU、内存、连接与执行时长，且多区域实例无共享内存。设计使用 Web 标准 API、流式响应和外部状态，明确冷启动、缓存键、一致性和区域故障；能力检测或适配层支持回到常规服务，不能假设“靠近用户”必然更快。

## DATA-01

Server State 来自远端并可能被其他参与者修改，具有获取、缓存、陈旧、失效和同步生命周期。查询键必须完整描述资源身份，fresh/stale 是是否需要重新验证，缓存存在不代表数据仍新鲜。

设计取消、去重、分页、预取、重试和错误恢复时要服从业务一致性。不要把服务器结果复制到多个本地 Store；写操作后应精确更新或失效相关查询，并防止旧响应覆盖新状态。

Server State 的缓存身份由资源、参数、用户/租户和版本共同决定，stale 与 gc 生命周期分开。请求可取消，失效、预取、分页和重试依据 HTTP/业务语义；写入后精确更新或失效。缓存不是数据库，登出、权限变化和敏感数据必须隔离与清除。

## GQL-01

GraphQL Schema 是客户端与服务端的类型契约，Query、Mutation、Subscription 分别表达读取、写入和持续事件。前端必须理解 nullability、变量、Fragment、错误数组、分页连接和规范化缓存。

客户端生成类型不能替代运行时错误处理。查询深度与复杂度、N+1、缓存身份、乐观更新和 Schema 演进都需要治理；不要为减少请求次数而构造无边界的巨型查询。

## VIS-01

数据可视化先确定问题、数据类型和受众，再选择位置、长度、颜色、面积等视觉编码。坐标轴、单位、基线、排序和缺失值会改变结论，动画与装饰不能牺牲可读性。

交互图表仍需标题、摘要、键盘操作、焦点和可访问替代内容。数据量大时分层聚合、抽样或使用 Canvas/WebGL，并用真实设备验证渲染与交互延迟。

可视化先按数据类型和比较任务选择位置、长度、面积、颜色等编码，标注单位、来源和不确定性。缩放、筛选与高亮保持数据语义，截断坐标和颜色映射不得误导。复杂图提供可访问标题、说明和数据表，大数据量采用聚合/抽样并披露。

## EXP-01

Feature Flag 将发布与部署解耦，评估通常基于用户、组织、环境和版本上下文。默认值必须安全，服务不可用时要有确定降级，客户端可见 Flag 不能承载真正的授权判断。

每个 Flag 要有所有者、创建原因、审计记录、到期时间和清理任务。渐进发布需要监控护栏与 Kill Switch；长期不清理的 Flag 会形成组合爆炸和难以测试的隐性架构。

Feature Flag 有稳定 key、类型、默认值、owner、受众、创建/到期和审计。评估在可信边界执行，客户端规则不承担授权；配置服务失败使用安全默认并缓存版本。发布、实验、运维开关分别治理，完成后删除代码与配置，避免永久分支债务。

## EXP-02

A/B 实验先提出可证伪假设，定义主要指标、护栏指标、随机化单位、样本量和停止规则。显著性不等于业务价值，置信区间比单一 p 值更能表达效果与不确定性。

避免中途反复看数后提前停止、多重比较不校正、样本污染和选择性报告。新奇效应、网络效应与分流不均都可能破坏结论，上线决策还要综合风险、成本和长期影响。

实验在上线前写明假设、随机单元、主指标、护栏、样本量和停止规则。检查分流比例异常、污染、新奇效应、多重比较和提前窥探；报告效应量与置信区间，而非只看 p 值。统计显著不等于业务值得上线，负面护栏和分群风险同样影响决策。

## CONTENT-01

内容模型把标题、正文、作者、状态、版本、分类、引用和发布时间等语义结构化；Markdown/MDX 是一种编写与序列化选择，不是完整 CMS。渲染前应解析为受控 AST，并限制可执行组件和危险 HTML。

内容流程需要草稿、审核、发布、回滚、链接检查、搜索索引和 Schema 迁移。SEO 结构化数据必须与页面可见内容一致；搜索要处理分词、权限、版本和失效内容。

内容模型表达语义字段、引用、权限、版本和发布状态，展示层从模型派生。Markdown/富文本先解析 AST，再对白名单节点、属性、URL 和嵌入内容净化；不执行不可信 MDX。slug、链接、引用和搜索索引可校验，发布/回滚/重建状态可追踪。

## IDENTITY-02

生产基线是 OAuth 2.0 Security BCP 与 OIDC；OAuth 2.1 仍是整合并收紧既有实践的 Internet-Draft，不能称为已发布 RFC。浏览器应用采用授权码加 PKCE，使用 state 防 CSRF、nonce 绑定 ID Token，并验证 issuer、audience、签名、时间和授权端点来源。

Access Token 面向资源服务器，ID Token 面向客户端，二者不能互换。Token 避免进入 URL 和普通日志，Scope 最小化；刷新、退出、账号绑定和多租户 issuer 都需要清晰状态机。

## PRIVACY-01

隐私工程从目的限制和数据最小化开始：只收集完成明确目标所需的数据，并说明用途、保存时间、共享对象和用户权利。同意必须可理解、可撤回，拒绝非必要处理不能阻止核心服务。

前端应完成敏感字段盘点、埋点审查、权限与日志最小化、导出/删除入口和第三方 SDK 管理。匿名化不只是删除姓名；稳定标识、组合属性和行为轨迹仍可能重新识别个人。

隐私工程从目的、合法性/同意、最小化、用途限制、保留和主体权利设计数据流。数据清单标记来源、敏感度、处理方、地区与删除路径；日志、缓存、索引、模型输入和备份都属于副本。撤回与删除要传播，不能只隐藏前端记录。

## AIPROD-01

先定义用户任务、现有基线和可衡量价值，再判断 AI 是否必要。模型选择要比较能力、领域适配、延迟、成本、隐私、上下文、可部署性和失败代价，而不是只看通用榜单。

用代表性样本做离线评估和小范围用户验证，并保留非 AI 基线。若任务需要确定规则、零容错或无法获得验证反馈，传统程序、搜索或人工流程可能更合适。

AI 产品适配先定义用户决策与失败成本，比较规则、搜索、传统模型和生成模型。只有输入允许不确定性、输出可验证且价值覆盖延迟/成本/风险时才采用生成 AI。原型测试无 AI 降级、拒答和人工路径，不能因“可以聊天”证明需求成立。

## AIPROD-02

AI 产品应把不确定性转化为可操作界面：显示来源、范围、可能错误、可编辑结果和下一步。不要伪造精确置信度；应根据任务风险决定自动执行、请求确认、拒绝或转交人工。

失败状态要区分无结果、低相关、模型拒绝、工具错误和超时，并保留用户输入。高风险决策必须可撤销、可追溯且有人负责，Human-in-the-loop 不能只是隐藏在异常后的客服入口。

质量评估把任务拆成正确性、相关性、引用、格式、安全、延迟和成本指标，建立代表性/边界/对抗数据集与人工评分准则。离线评估用于版本比较，在线实验看真实任务与护栏；模型、提示、检索和工具版本固定，防止口径漂移。

本知识点负责高风险自动化的风险矩阵、批准/复核点、权限升级、撤销、人工接管与责任闭环；普通 AI 会话中的等待、取消、编辑、重试和可恢复交互由 AIAPP-10 负责。

## AISAFE-01

模型输出始终是不可信数据。先做结构与类型校验，再做业务规则、引用、权限、敏感信息和内容安全检查；展示到 HTML、SQL、Shell 或工具参数前使用对应上下文的安全编码或参数化接口。

Guardrail 需要分层：输入过滤、最小上下文、工具授权、输出校验、人工升级和监控。误拦截与漏拦截都要通过数据集评估，模型自评或关键词黑名单不能成为唯一控制。

输出安全覆盖不当内容、事实错误、隐私、偏见、版权/来源和高风险建议。输入/输出过滤、Schema、引用、权限、限流和人工复核分层使用；拒绝应保留安全替代路径。安全分类器也会误报漏报，阈值和申诉按场景验证并持续监测。

## AISAFE-02

AI 威胁建模要枚举资产、参与者、身份、信任边界、数据流和滥用途径，覆盖 Prompt Injection、目标劫持、数据/记忆/上下文投毒、模型/提示窃取、资源耗尽、越权工具、不安全代码执行、供应链、Agent 间伪造、级联失效和隐私泄漏。

红队样例应可重复、记录前置条件和成功标准，并进入自动回归。防护采用权限隔离、委派深度、速率与预算、输入输出控制、沙箱、确认、审计、停止和故障隔离；不能把所有责任交给系统提示词。至少验证一条“恶意内容 → 错误记忆/目标 → 越权工具 → 下游 Agent”的级联链，并证明控制能在预期位置阻断。

## AIGOV-01

AI 治理需要记录数据来源与许可、模型和提示版本、评估结果、上线审批、责任人、审计事件和下线条件。模型卡应说明用途、限制、训练/评估信息和已知风险，不是营销简介。

变更模型、检索源或 Guardrail 都可能改变产品行为，必须经过版本化评估和发布闸门。事故响应要支持定位受影响请求、停止能力、通知、修复和复盘，同时控制日志中的个人数据。

AI 生成或编辑媒体还要处理输出来源。C2PA Content Credentials 可以把声明、生成/编辑动作和签名验证结果与媒体关联；产品应让用户看到来源摘要并可展开验证细节，导出时尽量保留凭证，平台转码或截图造成凭证丢失时给出诚实提示。

治理还要建立法规适用矩阵：按地区、产品角色、风险等级、能力类型和生效日期映射透明度、生成内容标识、用户告知、高风险评估和人工复核要求。中国生成合成内容标识规则、EU AI Act 等只在各自适用范围内形成发布闸门；不明确或高风险变更必须升级给法务，工程清单不能替代法律判断。

来源凭证证明的是声明和文件链是否可验证，不证明画面中的事实真实；无凭证也不能反推“不是 AI 生成”。水印、元数据、签名和内容检测能力不同，界面不得用绿色对勾制造过度信任。

验收覆盖有效、过期、损坏、未知签发者、编辑后失效、平台剥离和仅有副本等情况，并把验证库/信任列表版本纳入治理和回滚。

## ARCH-02

架构评审检查问题是否清楚、约束是否真实、方案是否比较、质量属性是否可测、风险是否可控。ADR 用于保存关键决策及后果，评审结论应区分必须修改、接受风险和后续验证。

方案先写目标、非目标、现状基线、硬约束和成功指标，再提供至少三个真实可行选项，其中包含维持现状。比较延迟、可靠性、安全、可维护性、成本、交付和组织影响，标注数据来源、假设和不确定性；只有目标方案有细节的“陪跑选项”不算比较。

评审不能变成资历表决或统一技术栈。通过原型、容量测试、故障演练和用户/运维验证降低高风险假设；明确受影响团队、迁移依赖、兼容窗口、监控、回滚和分阶段停止条件，避免不可逆大爆炸。

ADR 记录背景、驱动因素、选择、后果、状态和复查条件，RFC 保存更完整的讨论和迁移计划。异议与未决项原样记录，决策后以指标复验；事实或约束变化时允许替换旧决定，而不是把文档当永久权威。

答辩应能面向工程师解释机制和故障边界，也能向产品、运营或管理者说明收益、成本、风险和时间。合格方案可追溯、可证伪、可迁移、可回滚，文档长度和术语密度都不是质量指标。

## LEAD-01

技术路线从业务目标和系统约束推导能力缺口、优先级和阶段结果。路线图表达问题、依赖、风险和成功指标，不应只是框架升级清单；跨团队推动需要共同语言、决策机制和反馈闭环。

影响力来自让他人能独立做出更好决策，包括文档、示范、授权、评审和冲突处理。委派前说明目标、非目标、约束、决策权限、检查点和升级条件；根据风险与熟练度逐步放权，既不微管理也不把模糊任务和失败责任直接转交。

Mentoring 以对方的能力目标和真实任务为载体，通过提问、示范、配对、及时且具体的反馈和逐渐减少支持形成独立能力。Code Review 需要用共同样例校准正确性、安全、可维护性和风格的优先级，记录可接受例外，避免不同评审者给出相反门槛。

Bus Factor 治理不是要求所有人了解所有代码，而是让关键职责至少有备份 Owner、运行手册、决策记录、演练和轮换。事故复盘关注系统控制为何失效、如何改进工具与流程，不用个人归责代替学习。AI 工具可以辅助总结和评审，但人员仍需保有问题定义、证据判断和最终责任。

用交付稳定性、采用效果、风险下降、关键职责覆盖和他人独立交付衡量结果，而不是会议数量、个人代码量、培训场次或文档页数。

## BACKEND-01

关系模型用表、主键、外键和约束表达事实，索引用额外存储换取特定查询速度。前端需要理解排序与分页稳定性、唯一约束、N+1、读模型和查询成本，避免把数据库偶然顺序当作 API 契约。

事务保证一组操作的原子性，隔离级别决定并发可见性并可能产生不同异常。前端应针对冲突、重复提交、版本检查和最终一致性设计状态，而不是把所有失败显示为通用网络错误。

后端一致性素养要理解事务边界、唯一约束、隔离级别和乐观并发。前端超时只代表结果未知，写入用幂等键并提供查询；读副本延迟、事件最终一致和补偿会影响 UI 状态。契约明确版本、错误和重试，不能用前端乐观更新掩盖数据丢失。

## AIUI-01

AG-UI 主要描述 Agent 与前端之间的事件流和状态同步；A2UI 用受限、声明式组件描述表达可渲染界面；MCP Apps 让工具提供在沙箱中运行、经宿主桥接交互的应用。三者解决不同层次的问题，可以组合，但不能把任一协议当成另一协议的完全替代。

互操作层要标准化事件序号、会话/任务标识、幂等键、Schema 和协议版本。声明式组件只能来自宿主白名单，属性和事件动作需要验证；沙箱消息必须核验来源、能力和权限。未知事件、未知组件、旧客户端和不支持扩展时，应降级到可理解的文本或结构化结果。

本知识点负责协议层横向比较、组合与互操作实现，包括 MCP Apps 的资源关联、沙箱桥接和 Host 能力降级；协议无关的消息块、视图模型和组件注册表由 `AIAPP-05` 负责。

## AGENT-11

A2A 用 Agent Card 发布身份、端点、能力与交互方式，并以 Task、Message、Part 和 Artifact 表达跨 Agent 工作。任务可能同步返回、流式更新或异步回调，客户端必须处理排队、工作中、需要输入、完成、失败和取消等状态，而不是把一次 HTTP 成功当作任务完成。

Agent Card 是发现信息而不是授权证明。跨组织通信要验证远端身份、受众、Scope、租户与委派链，对任务创建、回调和 Artifact 使用幂等、防重放与审计。MCP 面向模型/Agent 使用工具和上下文，A2A 面向独立 Agent 间协作；不需要独立身份和远程任务生命周期时，普通服务调用更简单。

## REACT-10

路由首先是 URL、浏览器历史记录和界面状态之间的双向契约。嵌套路由把布局、数据和错误边界沿路由树组合，动态参数与查询参数必须在边界解析和校验；深链、刷新、前进后退、重定向、404 与焦点恢复都属于正确性。链接负责声明可达位置，命令式导航只用于确有控制流需求的场景，客户端隐藏菜单不等于服务端授权。

React Router 的 Declarative 模式主要提供路径匹配与导航，应用自行管理数据；Data 模式增加 loader、action、pending、错误和自动重验证；Framework 模式再提供类型生成、代码分割以及 SPA、SSR、预渲染等框架能力。选型依据是数据生命周期、渲染部署、团队控制权和迁移成本，不以“功能最多”作为默认答案。Route Module 应把读取和写入靠近路由边界，`Form`/fetcher 负责导航式或非导航式提交，并通过请求身份、取消和重验证避免旧结果覆盖新页面。

错误边界放在能够独立恢复的最小路由层，加载状态区分首次导航、局部刷新和表单提交；鉴权失败、参数无效、资源不存在与暂时故障应产生不同结果。路由可编排页面数据，但通用 Server State 缓存策略仍由 DATA-01/02 负责，最终授权仍由服务端 BIZ-03 执行。迁移从可观察的垂直切片开始，验证 bundle、导航时序、数据重复请求、错误恢复和回滚，再逐步扩大。

## ARCH-05

框架选型从产品形态和系统约束开始：交互密度、SEO/首屏、边缘或服务器运行环境、离线需求、性能与无障碍预算、团队经验、招聘与运维能力、生态支持周期、供应链风险和总拥有成本。React、Vue、元框架与 Web Components 位于不同层级，不能把路由/构建/服务端渲染的元框架能力错误归给 UI 库，也不能用流行度或个人偏好代替验证证据。

决策矩阵应包含维持现状，明确硬约束、权重、数据来源、不确定性和结论有效期。对高风险假设做最小原型，比较真实业务切片的体积、交互延迟、可访问性、错误恢复、部署和开发体验。版本支持矩阵记录运行时、浏览器、插件、设计系统与关键依赖的兼容窗口；达到弃用、维护停滞、安全风险或组织能力变化等触发条件时重新评估，而不是永久绑定一次 ADR。

跨框架迁移采用可独立交付的垂直切片，先定义边界、共享协议、遥测和回滚，再决定路由切分、Web Components、iframe 或兼容适配层。双运行期要监控 bundle、内存、状态同步、视觉与行为一致性，兼容层有 owner、删除日期和停止条件；若关键指标退化或假设被证伪，应暂停或回滚。ARCH-03 负责通用渐进迁移机制，ARCH-04 负责依赖和技术债台账，本知识点负责框架生命周期判断与跨框架决策闭环。

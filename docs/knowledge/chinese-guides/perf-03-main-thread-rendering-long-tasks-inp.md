# 主线程与交互响应知识点讲义

## PERF-03 主线程、渲染、长任务与交互响应

页面“卡”不是一个根因，而是用户输入到下一帧之间某个阶段无法及时推进。JavaScript、样式、布局、绘制和合成都争用有限时间，浏览器还要处理网络回调、垃圾回收和观察器。高级性能优化需要从任务和帧的时间线建立因果，而不是看到函数耗时就随意加防抖。本讲连接事件循环、渲染流水线、Long Task、Long Animation Frame、INP、调度与 Worker。

- 直接前置：[BROWSER-02 观察器、调度与页面生命周期协作](../chinese-guides/browser-02-observers-scheduling-lifecycle-coordination.md#browser-02)。本讲依赖任务、微任务、帧、观察器和生命周期清理模型。

### 一、主线程同时承担脚本与渲染

**主线程（Main Thread）**执行大部分 JavaScript、事件回调、样式计算、布局和绘制准备。它一次只能推进一段工作；当前任务不结束，用户输入即使到达也只能排队。GPU合成能独立处理部分图层变化，但不能替代 DOM、布局和业务计算。

浏览器每帧尝试处理输入、脚本、`requestAnimationFrame`、样式、布局、绘制与合成，实际顺序受实现和工作量影响。60Hz 屏幕约每 16.7ms 一帧只是参考，120Hz预算更小；并非所有页面都必须持续动画，但交互后的可见反馈要及时。

从用户角度观察“按下—页面变化”，从工具角度则展开成排队、事件处理、框架更新、布局与绘制。优化应缩短整条链，而不是只看某个函数自报计时。

### 二、任务、微任务和帧会互相推迟

事件、定时器和消息通常以任务运行；Promise回调进入微任务检查点。任务结束前微任务会持续清空，递归产生大量微任务同样会饿死渲染。把同步循环改成一串 resolved Promise不等于让出页面。

`requestAnimationFrame`适合在下一帧前更新视觉状态，不适合塞入大量计算。`requestIdleCallback`不能保证很快执行，关键任务不能依赖它；后台标签页的调度会被节流。调度选择必须写出优先级、截止时间、取消和降级。

一次工作是否可切片取决于中间状态能否安全暴露。列表过滤可以分块并显示进度，账户扣款不能把半完成状态呈现给用户。切片前先减少总工作量，避免只是把 500ms 分成许多仍然浪费的任务。

### 三、长任务是占用信号而非完整体验

**长任务（Long Task）**通常指主线程连续执行超过 50ms 的任务，超出部分被视为阻塞时间。它能指出输入可能被延迟，但没有长任务也可能因为多个 40ms任务、布局或帧排队造成差 INP。一个长任务也未必恰好包含用户交互。

Performance面板中的 Task、调用栈和底部活动帮助找到脚本来源。第三方脚本、JSON解析、同步存储、框架渲染和观察器都可能出现。先用时间线定位，再回到源码和输入规模；火焰图最宽函数是耗时归属，不自动是可删除根因。

Long Tasks API适合现场采样，但归因有限且支持有边界。上报时限制数量、去除敏感 URL、抽样并在页面结束清理 observer，避免监控本身制造更多任务。

### 四、Long Animation Frame 更接近一帧的组成

**长动画帧（Long Animation Frame）**观察超过约 50ms的动画帧，并提供 blockingDuration与脚本归因。它把任务、渲染和帧联系起来，特别适合分析 INP；一个交互仍可能跨越一个以上 LoAF，不能只取第一条。

duration长但 blockingDuration低，可能表示工作被分成可响应任务但视觉更新仍迟；blockingDuration高更直接说明输入被阻塞。脚本归因受浏览器支持和跨源限制，字段数据先能力检测，缺失时不能填零。

LoAF与Long Task互补：前者围绕帧，后者围绕任务。结合事件条目、trace截图和业务操作，才能判断脚本、强制布局、绘制还是队列造成体验。

### 五、INP 要按三个阶段归因

输入延迟高说明交互到达时主线程正忙，检查此前任务和微任务；处理时长高说明事件相关回调、框架更新或同步计算重；呈现延迟高说明处理后样式、布局、绘制或下一帧等待。三者修复手段不同。

事件监听器可能只是触发状态更新，真正成本出现在框架提交或浏览器布局。使用 User Timing标记业务阶段时，标记代码要轻量且命名稳定。不要用事件回调首尾的 `performance.now()` 宣称测得完整 INP。

字段 INP关注访问中的代表性慢交互，实验室必须覆盖真实操作序列。只点击一个空闲按钮不能代表搜索、拖拽、路由和弹窗。按路由、元素语义和版本聚合，避免记录用户输入文字。

### 六、布局抖动来自读写交错

修改样式后读取几何信息可能迫使浏览器立即计算样式和布局。循环中“写一个节点—读尺寸—再写”会反复触发，元素越多越严重。批量读取旧布局，计算后批量写入，或用一次容器布局替代逐项测量。

`getBoundingClientRect`、offset系列和 computed style在脏布局下可能触发同步工作，但 API本身不是禁用对象。先用 trace中的 forced reflow警告、调用栈和总耗时证明。缓存尺寸还要处理字体、响应式和内容变化，不能换来错误布局。

DOM规模、复杂选择器和布局依赖共同决定成本。虚拟化、CSS containment和更小更新边界可以减少工作，但会影响焦点、测量和可访问性，需要行为回归。

### 七、绘制与合成不是“使用 transform”就结束

布局确定几何，绘制生成像素指令，合成组合图层。transform和opacity常可在合成阶段更新，但创建过多图层会增加内存和上传成本；`will-change`长期滥用会适得其反。

大面积阴影、滤镜、透明和频繁重绘可能很贵。Performance与Rendering工具可显示 paint flashing、图层和帧；只凭CSS属性名称猜测不够。动画掉帧还可能来自主线程脚本或图片解码。

尊重 `prefers-reduced-motion`，并保证动画中断与后台恢复正确。性能优化不应删除必要焦点反馈或让内容突然跳变。

### 八、减少工作优先于更聪明地安排工作

先检查算法复杂度、重复计算、无效渲染和数据规模。5000项每键全量排序的根本问题可能是数据策略，不是调度 API。派生结果缓存要有稳定键和失效，避免缓存本身保留大量对象。

框架层检查状态归属、组件边界和订阅范围。一次输入若更新全局状态并让整页重渲染，memo可能缓解但也增加比较成本。先让变化只传播到真正消费者，再对昂贵且稳定计算做缓存。

网络返回也可合并、分页或服务端聚合。把所有数据传到浏览器再用 Worker处理，可能只是把服务设计问题移到设备。

### 九、切片和调度要保证正确终止

**调度（Scheduling）**决定哪项工作何时获得执行机会。可中断任务拆成小块，每块检查当前请求身份与取消信号，处理高优先级输入后继续。分块大小根据设备和帧预算调节，固定 5ms不保证所有机器一致。

连续输入需要“最新结果获胜”：新查询取消或作废旧计算，旧结果不得晚到覆盖。调度器记录 queued、running、cancelled和completed，错误进入明确恢复，不让 Promise永远悬挂。

优先级提升要谨慎。把所有更新标成用户阻塞等于没有优先级；后台预计算可以在资源紧张时丢弃。测试快速输入、路由离开、后台恢复和组件卸载。

调度还需要背压：生产工作持续快于消费速度时，单纯切片只会让队列越积越长。搜索联想可以合并旧输入，分析任务可以限制并发，必须逐项处理的操作则要显示积压并允许取消。队列长度、最老任务等待时间和被丢弃数量应进入观测；否则页面可能没有单个长任务，却仍因陈旧工作长期争抢主线程。

### 十、Worker 适合纯计算而不是 DOM

Web Worker在独立线程执行 JavaScript，不能直接操作 DOM。适合解析、压缩、搜索、图像和可序列化计算。主线程发送输入、接收结果，仍要承担拷贝或结构化克隆；大型 ArrayBuffer可转移所有权减少复制。

Worker启动、模块下载和消息往返有成本，小任务搬移反而更慢。协议要包含任务 ID、版本、取消、进度和错误；组件卸载后丢弃旧结果。Worker崩溃或不支持时提供主线程降级并限制规模。

SharedWorker和Worklet有不同生命周期与能力，不应为了“多线程”随意采用。先验证瓶颈是可分离计算，而不是布局或主线程消息处理。

### 十一、PerformanceObserver 现场采集要有预算

观察 event、longtask或long-animation-frame前先检测 supportedEntryTypes。回调批量处理，截断脚本位置，限制每导航数量并抽样；页面隐藏时flush，生命周期结束disconnect。重复路由注册会让条目成倍上报。

观察器条目可能延迟、缺失或被浏览器隐私策略降低精度。指标 schema记录支持状态和采集版本，不支持不是性能为零。跨源脚本名也可能不可见，结合资源和第三方清单定位。

监控回调总耗时和发送字节。若为归因序列化大量调用栈，采集会改变被测系统；用小流量诊断模式而非全量永久开启。

### 十二、录制 trace 要控制实验条件

明确用户操作、数据规模、缓存、CPU/网络、浏览器版本和录制范围。录制前热身必要代码，重复相同操作，避免 DevTools打开本身与扩展造成偏差。保存 trace和结果，不只截一张火焰图。

先从用户可见慢点缩小时间区间，再看 Interactions、Main、Frames、Network和截图。建立候选假设并做单变量实验：禁用第三方、替换 Worker、批量 DOM写入或关闭 observer。一次改多项无法知道因果。

修复后同条件复测结果正确、INP阶段、帧、长任务和业务输出。低端设备上的改善比开发机更关键。

### 十三、常见“优化”为什么失败

- 把同步代码放入零延迟定时器，只是晚一点阻塞。
- 只加 debounce，让用户等待更久且最终任务仍很大。
- 每帧执行大量 DOM工作，长任务消失但帧持续变慢。
- 为全部组件加 memo，比较与内存成本超过节省。
- 把计算放进 Worker，却频繁传巨大对象并在主线程重建 DOM。
- 只追 60 FPS，忽略输入正确、焦点和减少动态偏好。

任何优化都要声明减少了什么工作、把什么工作移到何时、可能牺牲什么，并以相同任务验证。

### 十四、学完后应能完成因果闭环

在团队实践中还要建立性能变更说明：描述被优化的用户任务、原始瓶颈、适用数据规模、选择方案、取消策略和不采用方案。代码评审者应能从说明追到 trace 区间与回归断言，而不是接受“体感更快”。对共享组件的调度变更，分别测试空闲页、忙碌页、后台恢复和低端设备；若工作被推迟，记录它最晚何时必须完成。长期仪表盘关注交互分布与任务规模，发现模型、数据或第三方改变后及时重新取证。这样一次局部优化才会沉淀为可维护的主线程预算，而不是下一位开发者无法解释的时间片技巧。

选一个真实慢交互，记录字段 INP或可重复现场症状；在 trace中把输入延迟、处理和呈现展开，关联 Long Task、LoAF、脚本与布局。只修改一个成立根因，复测性能与业务结果，再观察小流量真实用户。

你应能解释主线程、任务、微任务和帧怎样竞争；区分 Long Task与LoAF；选择减少工作、批量读写、切片、调度或Worker，并为取消、卸载和观测成本建立边界。继续查证可参考 [Chrome Performance](https://developer.chrome.com/docs/devtools/performance)、[Long Animation Frames API](https://developer.chrome.com/docs/web-platform/long-animation-frames)与 [MDN PerformanceObserver](https://developer.mozilla.org/zh-CN/docs/Web/API/PerformanceObserver)。

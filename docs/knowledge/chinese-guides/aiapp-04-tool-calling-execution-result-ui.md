# AI 工具调用与结果呈现知识点讲义

## AIAPP-04 Tool Calling 与前端工具结果呈现

模型生成“调用日历”“创建计划”或“退款”并不代表动作已经发生。真实系统必须把提议、验证、授权、确认、执行、结果查询和界面呈现拆开，并能处理响应丢失、重复事件和参数变化。Tool Calling 的价值是给模型一个结构化的能力接口；它的安全性和可靠性来自应用与服务端的确定控制，而不是模型是否表现得谨慎。

### 学习前先确认

- 直接前置：[AIAPP-03 结构化输出与 Schema 校验](../chinese-guides/aiapp-03-structured-output-schema-validation.md#aiapp-03)。工具名、参数和结果都先是不可信结构化候选；没有运行时 Schema、语义与授权分层，就无法安全讨论执行。

### 一、模型只拥有提议权

**工具调用（Tool Calling）**是模型根据工具描述产生名称和参数的结构化提议，应用决定该工具是否存在、当前主体是否可用、参数是否有效以及何时执行。模型既不是身份提供者，也不是授权服务器或事实账本。

把一轮调用拆成四个角色：模型提出候选；策略层验证和分类；执行器以受信身份调用真实系统；UI 显示经服务端确认的状态。即使模型文字写着“已经删除”，界面也只能依据执行记录改变，不根据自然语言猜结果。

工具合同从任务需要出发，只暴露最小操作。例如查询日历与创建事件分开，预览变更与提交变更分开，批量删除不复用单条删除的无限数组。工具越粗，单次错误影响越大；工具越碎，也可能增加组合复杂度，需要用状态机而不是无限循环协调。

### 二、工具 Schema 同时约束输入和返回

输入 Schema 限制字段、类型、枚举、数量、长度和未知字段，业务层继续检查对象、租户、状态和额度。身份、租户、价格、审批状态等受信字段从会话和数据库取得，不接受模型填写。URL、路径和查询条件还要做协议、根目录和资源范围检查。

结果也需要版本化合同。成功返回实际对象标识、版本和来源；拒绝返回稳定原因；可修正参数错误指出安全的字段类别；未知结果返回查询句柄。不要把执行器异常栈、SQL 或密钥当作 tool result 回传给模型。

工具说明影响模型选择但不是控制边界。描述要明确适用条件、副作用、必要参数和不适用情况，同时假设模型仍会选错。服务端注册表才决定允许的真实工具及版本。

### 三、Side Effect 改变系统外部事实

**副作用（Side Effect）**是调用对持久数据、外部人员、资金、权限、文件或其他系统产生可观察改变。只读查询通常风险较低，但仍需授权、限流和隐私控制；写入、发送、删除、支付、发布与授权变更要更强的确认和恢复。

按影响而非 HTTP 方法分类。一个 GET 端点也可能触发昂贵计算或审计记录，一个 POST 可以只是只读搜索。记录可逆性、影响对象数量、外部受众、敏感数据、最大损失和补偿方式，策略层据此决定自动、提示、确认、双人审批或禁止。

确认必须展示真实参数和后果，绑定规范化参数摘要、工具版本、主体、资源范围和有效期。用户编辑任何关键参数后旧确认失效；“始终允许”也只能是明确范围和期限内的授权，不能成为永久万能令牌。

### 四、状态机比加载动画更重要

建议状态为 `proposed → validating → denied/awaiting_confirmation → executing → succeeded/failed/unknown/cancelled`。参数修正产生新提议而不是悄悄修改旧调用；终态封闭，迟到事件不能把失败改成成功。

前端每个工具卡片绑定稳定 `toolCallId`、请求代次和服务端操作 ID。显示工具名称、关键参数、影响范围、谁批准、当前状态和结果来源。模型的解释与执行事实在视觉和数据结构上分开。

取消有不同含义：取消尚未执行的提议可以直接终止；执行中的取消只是请求，服务端可能已完成；取消 UI 等待不等于撤销业务事实。界面应显示“正在确认取消”或最终状态，而不是立即宣称已撤销。

### 五、Idempotency Key 保护重放边界

**幂等键（Idempotency Key）**标识同一业务意图的重复提交，使服务端返回原操作结果而不再次产生副作用。它由可信应用生成并绑定主体、工具、规范化参数和有效期，不能把模型随口产生的字符串直接作为全局键。

执行器在原子事务中登记键与操作，再调用或写入；重复请求查询同一记录。仅在前端禁用按钮不能防止双击、刷新、代理重试或进程恢复。对于不支持原生幂等的外部系统，要建立本地操作账本、查询和补偿策略。

幂等不是“所有错误都重试”。参数错误、权限拒绝和策略阻断不应重试；暂态读取可按预算退避；响应丢失的写入先查询。键重复但参数摘要不同必须拒绝，不能复用旧结果掩盖调用者错误。

### 六、Unknown Outcome 是第一等业务状态

**未知结果（Unknown Outcome）**表示请求可能已被执行，但调用者没有获得足够证据判断最终事实。典型情形是写入提交后连接中断、网关超时或客户端崩溃。它既不是失败，也不能按成功展示。

未知状态提供按操作 ID 或幂等键查询、稍后刷新、人工核对和安全离开入口。查询仍未知时保持不确定性；不要因为用户着急就再次创建。金额、发送、删除等动作必须在产品文案中明确“尚无法确认是否完成”。

对可以可靠补偿的动作，也要先确认原动作事实，再发补偿，并让两者有独立操作 ID。盲目“回滚”可能在原动作根本未发生时制造新的错误。

### 七、结果回流仍是不可信输入

内部工具返回值可能含用户控制的订单备注、网页内容或错误消息，外部工具更可能携带提示注入。结果进入模型前保留 source、contentType、tenant、截断和可信级别，以数据块传递，不能提升成系统指令。

页面渲染结果按最终上下文编码。富文本、链接、文件、图片和嵌入内容各有允许策略；不要因来源是“工具”就使用 `innerHTML`。引用和附件要重新鉴权，临时 URL 设短期并绑定主体。

结果过大时做结构化裁剪与摘要，保留原始制品引用和完整性信息。模型生成的摘要不能替代真实结果账本；用户应能查看关键事实来源。

### 八、工具版本和能力协商

工具合同带名称、版本、输入输出 Schema、副作用等级、超时、幂等支持和弃用期限。破坏性更改使用新版本或新名称；旧会话恢复时按记录的版本解释，不能自动套用当前 Schema。

模型供应商是否支持原生 tool calls、并行调用、严格参数 Schema和工具结果角色，需要适配器在调用前协商。文本中模拟 `<tool>` 不等价于结构化能力。并行调用还要检查彼此依赖和累计副作用，不能只因接口返回数组就同时执行。

工具临时不可用时提供能力缺失状态，允许纯文本解释或人工路径。用另一个名字相似的工具自动替代，可能改变权限、成本和语义。

### 九、前端需要呈现事实而非剧场

提议阶段用“建议执行”，确认后用“等待执行”，收到服务端开始事件才用“执行中”。成功展示真实对象和版本；失败说明是否可以修改或重试；未知保留查询。不要用模型逐字描述的“正在连接数据库”制造不可验证进度。

工具参数很多时先显示关键摘要，允许展开完整受控字段。屏幕阅读器按语义阶段播报，不为每个 token 重复；焦点在确认、错误和返回之间可预测。用户拒绝后会话仍可继续，不应清空草稿或反复诱导同一动作。

多个工具调用按依赖关系呈现。后一步依赖前一步事实时必须等待已确认成功；取消父任务要传播到尚未开始的子调用，已开始的调用则独立收敛。

### 十、权限在执行时重新核验

模型可看到某工具不代表用户有权调用。执行器从当前认证上下文取得主体和租户，重新校验对象范围、角色、业务状态、策略版本和批准。确认到执行之间权限可能撤销、对象可能更新，必须采用版本或条件写入。

前端隐藏按钮只是体验，不能作为权限。工具代理使用最小服务凭据，按用户委托限制资源；不要让一个高权共享密钥代替细粒度授权。审计同时记录用户主体、代理主体和实际下游身份。

跨租户错误应统一拒绝，避免通过“对象不存在/无权限”的差异泄露存在性。批量操作在服务端重新计算实际集合和上限，不能信任确认页之前的旧计数。

### 十一、超时、重试与并发要共同设计

区分排队、连接、首字节、执行和总时限。浏览器超时不证明服务端停止；AbortSignal 传播到 BFF、执行器和下游，并由实际支持者确认。重试使用总预算、退避和抖动，不与 SDK 自动重试叠加。

同一对象的并发修改用版本号、条件请求或业务锁检测冲突。模型基于旧快照提出的动作，在执行前发现版本变化应回到重新预览或确认，而不是覆盖他人修改。

并行只读可以提高速度，但仍受租户级并发和成本预算。多个写调用要有明确顺序、依赖和部分成功处理；“全部并发后挑成功结果”会留下不可见副作用。

### 十二、审计链必须能重建真实动作

一次调用至少记录请求、工具与版本、参数摘要、主体、租户、授权决定、确认摘要、幂等键、执行尝试、下游操作 ID、结果类别和用户恢复动作。敏感参数按最小化和脱敏策略处理。

审计事件是不可变事实流，当前状态由事件归约；人工修正产生新事件而不是覆盖过去。模型文字不进入“执行成功”事实，除非它只是附属说明。

指标包括提议到确认耗时、拒绝率、授权失败、重复键命中、未知状态、查询收敛、取消成功、重复副作用和恢复完成率。异常不是只看 5xx；未知和重复影响更危险。

### 十三、用故障注入证明控制有效

准备合法只读、非法参数、越权资源、确认过期、双击、响应丢失、迟到结果、权限撤销、工具返回注入文本和下游部分成功。逐项断言执行器调用次数、状态序列、页面文案、审计和恢复。

让模型故意选择不存在的工具，确认注册表拒绝；让 Schema 合法但订单跨租户，确认授权拒绝；让写入实际完成却丢失响应，确认界面进入 unknown 并通过查询收敛；让同一键重复送达，确认只有一个副作用。

回归同时保护正常流程，避免安全修复让只读工具全部需要确认或让用户无法从参数错误恢复。固定工具桩与事件日志比依赖模型每次产生同样文字更稳定。

### 十四、组合调用需要显式依赖与事务边界

一次用户目标可能包含“查询客户→创建方案→发送通知”。这不是三个可以随意并行的函数。计划应声明输入引用、前置状态和每一步的副作用；执行器只把已确认结果的结构化字段传给下一步，不让模型从展示文本里重新抄 ID。若查询返回多个客户，流程进入选择状态，不能猜一个继续。

跨工具事务通常不能原子提交。先识别可逆、可补偿和不可逆动作，把不可逆步骤放在最后，并在确认页展示组合后的整体影响。创建方案成功而通知失败时，真实状态是部分完成；UI 列出已创建资源、失败步骤、是否可重试和是否需要补偿，不把整条链显示为红色失败后诱导用户全部重来。

并行调用要有共享预算、取消传播与结果屏障。一个分支失败不一定取消独立只读分支，但依赖它的写入必须停止。合并前校验每个结果的版本、来源与权限，防止较晚到达的旧结果覆盖较新的用户选择。

### 十五、前后端契约应能独立演进

工具注册、策略执行和 UI 卡片不应共享一份随意扩展的 TypeScript 类型后就认为安全。对外协议使用版本化运行时 Schema，内部领域对象通过防腐层转换；旧工具结果可由适配器读取，新写入只产生当前版本。前端遇到未知状态或字段，保留原始事实并安全降级，不默认映射为成功。

### 十六、形成可维护的执行边界

为一个真实工具从模型提议画到外部系统事实，标出每个 Schema、身份、确认、幂等、未知和显示边界。每个状态写允许动作和禁止转移，再用故障证明页面与服务端一致。

上线前逐项确认：工具身份与版本可见，服务端重新授权，副作用拥有稳定 operationId，未知结果可查询，拒绝和取消不会继续执行，旧客户端能显示安全降级。对每个写工具准备一个真实对账方法，而不是把“请重试”作为默认恢复。

工具下线时先停止新提议，等待或迁移在途调用，保留旧结果的只读渲染；不能删除注册项后让历史会话变成无法理解的空卡片。

学完后，你应能明确区分提议和执行，设计副作用分级、确认、幂等和未知结果；能让工具结果安全回流并在 UI 中准确呈现；能解释为什么“模型调用成功”与“业务动作成功”不是同一件事。具体厂商轮次可参考 DeepSeek 的 [Tool Calls 官方说明](https://api-docs.deepseek.com/zh-cn/guides/tool_calls/)，但真实授权和状态始终由应用负责。

# 移动视口与响应式布局知识点讲义

## H5-01 viewport、响应式、安全区与横竖屏

移动适配不是为几款手机写媒体查询，而是让内容在视口、字体、工具栏、刘海、横竖屏、缩放和宿主变化时仍满足可读与可操作约束。CSS像素、设备像素和用户真正看见的区域并不相同；固定宽高在一台模拟器上完美，换到动态地址栏或200%文字缩放就可能遮挡。本讲从视口模型开始，建立内容驱动布局、安全区、动态高度、方向变化和可验证适配。

### 学习前先确认

- 直接前置：[WEB-02 布局、层叠、响应式与逻辑属性](../chinese-guides/web-02-layout-cascade-responsive-logical-properties.md#web-02)。本讲直接使用正常流、Flex/Grid、min/max约束、媒体与容器查询。
- 直接前置：[A11Y-01 WCAG、测试与治理](../chinese-guides/a11y-01-wcag-testing-governance.md#a11y-01)。缩放、重排、目标尺寸和键盘焦点属于适配底线。

### 一、CSS 像素不是物理像素

浏览器用CSS像素进行布局，设备用物理像素显示。**设备像素比（Device Pixel Ratio）**描述一个CSS像素大致对应多少设备像素，并会受设备与缩放影响。它不等于页面宽度，也不能用来推断具体机型。

高DPR图片若只提供CSS显示尺寸可能模糊，但一味按最大DPR下载巨大资源浪费带宽。使用响应式图片让浏览器结合布局宽度、DPR和网络选择。Canvas需要按实际像素扩展缓冲再用CSS设显示尺寸，同时控制内存。

测试断言使用CSS像素和真实布局，不按截图像素硬编码。浏览器缩放、系统显示比例和远程调试截图都可能改变物理映射。

### 二、布局视口决定 CSS 排版基准

**布局视口（Layout Viewport）**是CSS布局使用的视口。移动浏览器为兼容旧桌面页面可能采用较宽虚拟视口，再整体缩小；`meta viewport`中的 `width=device-width, initial-scale=1`让布局宽度与设备CSS宽度匹配。

不要使用 `user-scalable=no` 或过小 maximum-scale掩盖布局问题，这会阻止需要放大的用户。`viewport-fit=cover`允许内容延伸到屏幕边缘，但随后必须使用安全区环境变量保护操作区。

meta viewport缺失时，媒体查询和vw基于意外宽度，开发者可能误以为响应式断点无效。把它作为文档基础合同，并在嵌入WebView中实测宿主是否覆盖设置。

### 三、视觉视口表示用户当前真正看到的区域

**视觉视口（Visual Viewport）**是缩放、软键盘和动态浏览器UI后用户当前可见区域，它可以小于布局视口并带偏移。页面布局仍可能保持原尺寸，而键盘遮住下半部；只读取 `innerHeight`不能覆盖所有宿主。

VisualViewport API提供 width、height、offset和resize/scroll事件，适合调整浮动工具、将焦点滚入可见区和诊断键盘。事件可能高频且不同浏览器行为有差异，处理要节流、能力检测，并优先让正常文档流解决问题。

不要用视觉视口高度重写整个页面每个元素，那会在地址栏动画中造成抖动。只把它用于真正依赖可见边界的固定操作或定位，并准备无API回退。

### 四、响应式布局从内容约束开始

先确定最小可读宽度、可换行区域、操作优先级和内容最大宽度，再选择Flex/Grid、`minmax()`、`clamp()`与自动换行。断点应在内容开始拥挤或结构需要改变处出现，不按“iPhone/Pad”型号列表划分。

使用 `max-width:100%`保护媒体，容器子项加 `min-width:0`允许长内容收缩；长URL和不可断字符串要有溢出策略。固定卡片宽、绝对定位和一行按钮是横向滚动常见根因。

宽屏不等于无限拉长。正文设置合理行长，工具区可形成多列；窄屏重新排序时保持DOM阅读和焦点顺序，不能只用CSS视觉 order制造键盘混乱。

### 五、媒体查询与容器查询解决不同问题

媒体查询根据视口、方向、指针、悬停、色彩和用户偏好调整整体。容器查询根据组件所在容器尺寸或样式，使同一卡片在主区、侧栏和嵌入环境独立适配。组件库优先使用容器约束，页面骨架使用媒体查询。

方向查询反映视口宽高关系，不等于设备物理方向；软键盘也可能改变比例。不要用 orientation断言用户旋转了设备或切换业务模式。

`pointer`/`hover`只能描述主要输入能力，二合一设备可能同时有触摸和鼠标。功能不能只在 hover出现，触控和键盘仍要可达。

### 六、视口单位有小、大、动态三套高度

传统 `100vh`在移动浏览器动态工具栏下可能对应最大或稳定视口，造成底部被遮或高度跳变。`svh`表示小视口、`lvh`大视口、`dvh`随UI变化；选择取决于页面是否宁可留空还是动态填满。

全屏对话框可用 `min-height:100dvh`配合内容滚动，但地址栏动画时频繁重布局需观察。落地页若要避免首次内容被工具栏遮住，可选择svh；背景可延伸到lvh，核心操作仍按可见区域。

提供旧浏览器回退，并允许内容自然增高。固定 height比 min-height更容易在文字放大后裁切；页面不应因追求“整屏”而禁止滚动。

### 七、安全区是环境输入而非固定 padding

**安全区（Safe Area）**描述显示切口、圆角或系统手势区域内不适合放关键内容的边距。配合 `viewport-fit=cover`使用 `env(safe-area-inset-top/right/bottom/left)`，值可能为零且会随方向变化。

通常把设计间距与安全区相加，例如底部操作条 `padding-bottom: calc(16px + env(safe-area-inset-bottom))`。不要按机型写34px，也不要给整个页面重复叠加导致双倍空白。背景可覆盖到边缘，文字和按钮留在安全范围。

折叠、双屏和键盘还有其他环境段信息，支持与形态快速变化。采用能力检测和渐进增强，在未知设备上保持单栏可滚动，而不是猜测铰链位置。

### 八、横竖屏变化需要保存任务状态

旋转会改变宽高、方向、安全区、图片候选和可能的输入法状态。布局应重新流动，不重新创建业务任务。视频或图表可切布局，但表单值、焦点语义和滚动上下文尽量保留。

不要监听 resize后立即大量读取写入；浏览器在旋转和工具栏变化中可能连续触发。CSS完成大部分响应，JS只处理必须重算的画布或虚拟列表，并在稳定帧批量处理。

方向锁定只适用于确有沉浸需求且平台允许的场景，提供退出和替代。普通表单强制竖屏会阻碍横屏键盘、支架和无障碍用户。

### 九、字体缩放和重排是布局输入

用户可能通过浏览器缩放、系统文字大小或无障碍设置放大。使用rem和内容驱动高度，按钮允许文字换行或增长；固定行高、固定容器高度和图标覆盖文字在200%时暴露。

WCAG重排关注在窄等效宽度下无需双向滚动完成阅读，数据表、地图和代码等可有局部滚动但要标识。页面级横向滚动通常意味着约束失败。放大后粘性头和底部条不能占满可见区域。

测试真实长中文、英文、数字、错误文案和动态翻译，不用短占位文本证明适配。浏览器自动文字放大策略在不同平台不同，必要时了解 `text-size-adjust`，但不应用它禁止用户需求。

### 十、固定与粘性元素最容易遮挡内容

底部导航、提交条、浮动AI按钮、toast和软键盘会争夺有限可见区。固定元素要把自身高度和安全区反馈给内容 padding，焦点滚动时留出 scroll-padding。多个浮层同时出现需要层级和避让策略。

`position:sticky`依赖滚动容器和祖先 overflow，嵌套滚动可能让它失效。先减少滚动容器，再检查实际包含块。fixed在transform祖先或WebView中也可能有特殊行为，需要实测。

关闭按钮、错误摘要和主要操作始终可见可达。不要用覆盖层阻止页面缩放或把背景滚动锁死后无法恢复。

### 十一、图片、Canvas 与视频随布局变化

媒体保持固有比例，使用 `object-fit`决定裁切。关键内容不能被 cover裁掉；为不同比例提供艺术指导候选。视频控件与字幕在横屏、全屏和安全区下要可操作。

Canvas根据CSS显示尺寸和DPR设置缓冲，resize时保存绘制状态并限制像素上限。图表在容器变更后重新布局，但不要每个像素变化都昂贵重绘；ResizeObserver回调避免写读循环。

iframe和第三方嵌入给出尺寸、sandbox与响应式容器，内容不可控时提供打开新页。未知高度的跨源iframe不能读取内部布局，双方需通过受控消息协议协商。

### 十二、不同 WebView 不是“缩小的 Chrome”

应用内WebView可能使用不同内核版本、状态栏、键盘模式、返回手势和安全区注入。宿主还可能改变字体、Cookie、导航和下载。记录宿主版本与能力，不以桌面设备模拟替代真机。

设计 JS bridge时把系统信息作为不可信输入校验，版本协商并提供Web回退。适配代码隔离在平台层，不让业务组件散落机型判断。

最低支持矩阵基于真实用户和业务风险。未测试组合标记待验证，不声称“全机型兼容”。

### 十三、建立多条件视觉与行为验证

至少覆盖窄屏320、常见中宽、较宽手机、横屏、200%文字、浏览器工具栏变化和安全区零/非零。检查 `scrollWidth <= clientWidth`、主要操作可见、目标尺寸、焦点位置、阅读顺序和截图差异。

自动截图能发现布局变化，但软键盘、真实安全区、系统字体和WebView仍需真机或可靠设备环境。保存浏览器/系统版本和缩放，不用“手机截图”这种模糊证据。

故障注入长标题、错误列表、图片失败、慢字体、键盘和方向切换。适配合格意味着任务在变化中保持，而不是静态首页看起来整齐。

### 十四、学完后应能用约束而非机型适配

以结算页为例，可以把标题、商品清单、优惠、价格与提交条分别写成约束：正文允许换行且不挤压金额，列表在容器内自然增高，提交条不覆盖最后一项，横屏时信息和操作可并列但DOM顺序不变，安全区只增加外侧留白。然后把同一DOM放入全宽页面、窄侧栏和WebView，观察容器而不是设备名决定结构。图片未加载、价格变长、出现三条错误、语言改成英文、用户放大文字时，组件仍应满足最小宽度与可达性。若必须通过隐藏信息才能避免溢出，应重新确定内容优先级并给出可访问入口，而不是CSS裁掉。

适配代码也需要性能和生命周期边界。ResizeObserver只观察真正影响组件的容器，把多次变化合并到一帧，并防止回调写尺寸后再次触发无限循环。窗口和VisualViewport监听由页面级服务统一管理，组件订阅结果并在卸载时取消。服务端渲染时没有真实视口，初始输出采用不依赖客户端宽度的安全结构，水合后渐进增强，避免首次布局与客户端完全不同。打印、桌面缩窄、分屏和浏览器侧栏同样会触发响应式约束，良好的内容模型能自然覆盖这些非手机场景。

适配评审应保存一张“变化输入—布局响应—任务不变量”表：宽度改变时列数可变但阅读顺序不变；安全区改变时背景可延伸但按钮仍在可触区；文字放大时高度与换行可变但内容不裁切；键盘出现时可见区变小但焦点与提交仍可达；横竖屏切换时布局可重排但表单状态不丢失。新增组件先在容器级验证，再放进页面与宿主；发现特定机型问题时先找被破坏的通用约束，只有确有平台缺陷才增加隔离补丁和到期复查。这样支持矩阵扩展时无需复制更多设备判断。

你应能解释CSS像素、DPR、布局/视觉视口、meta viewport和动态高度单位；能用内容约束、媒体/容器查询与安全区构建响应式页面；能处理横竖屏、缩放、固定元素和WebView差异，并用多条件证据验证无横滚、无遮挡和任务连续。

选一个含表单、底部操作和媒体的页面，在窄屏、横屏、安全区和200%文字下实际运行，记录尺寸断言、焦点和截图。继续查证可参考 [MDN viewport meta](https://developer.mozilla.org/zh-CN/docs/Web/HTML/Viewport_meta_tag)、[MDN Visual Viewport](https://developer.mozilla.org/zh-CN/docs/Web/API/Visual_Viewport_API)与 [MDN env()](https://developer.mozilla.org/zh-CN/docs/Web/CSS/env)。

# 业务授权模型知识点讲义

## BIZ-03 RBAC、ABAC 与数据权限

权限系统的任务不是决定某个按钮是否显示，而是在已确认主体身份后，对“谁、在什么上下文中、能对哪个资源执行什么动作”作出可解释、可复核、默认安全的决定。企业应用一旦出现多租户、部门、项目、班级、地区、数据级权限或临时委托，单纯在页面里散落 `isAdmin` 判断就会迅速失控。本讲从授权模型、数据范围、执行位置、缓存与变更治理逐层建立完整机制。

### 学习前先确认

- 直接前置：[BIZ-01 业务对象、关系与统一语言](../chinese-guides/biz-01-domain-objects-relations-ubiquitous-language.md#biz-01)。本讲直接使用实体身份、关系、聚合边界、业务动作和统一语言来定义资源与权限。

### 一、先区分认证、授权与界面可见性

认证回答“当前主体是谁”，授权回答“该主体能否执行这次动作”。登录成功只产生一个可验证身份，不自动意味着能读取所有订单。界面可见性则是授权结果在客户端的体验投影：隐藏无权按钮可减少困惑，但攻击者仍能绕过页面直接构造请求，因此它从来不是最终安全边界。

把一次决定写成 `subject + action + resource + context → allow | deny + reason`。主体包含稳定用户 ID、所属组织和已经验证的身份强度；动作使用业务动词，如 `invoice.approve`，不要只写模糊的 CRUD；资源包含对象 ID、租户、所有者和状态；上下文包含时间、来源网络、临时委托与策略版本。任何信息缺失都应按策略拒绝或进入明确的待确认状态。

### 二、RBAC 用稳定职责压缩权限管理

**基于角色的访问控制（Role Based Access Control）**把权限授予角色，再把角色授予用户。角色表达组织中的相对稳定职责，例如客服、审计员、财务复核人。它避免为每位员工分别维护大量权限，也便于入职、调岗、离职和定期审计。

RBAC 的核心关系是用户—角色与角色—权限。权限应拆成资源与动作，例如 `refund:read`、`refund:approve`，而不是把页面名称当权限。角色继承可以减少重复，但层级过深会让实际权限难以解释；“高级角色继承所有低级角色”也未必符合职责分离。创建者与审批者不能是同一人时，需要显式约束，而不是再造一个超级角色绕过。

角色适合稳定、可枚举的职责，不适合表达“只能看自己负责的华南区”“临时代班到今晚八点”。若把每种地区、班级和期限组合都编码成角色，会出现角色爆炸，权限评审也无法回答某一数据为何可见。

### 三、ABAC 用属性表达动态范围

**基于属性的访问控制（Attribute Based Access Control）**根据主体、资源、动作和环境属性评估规则。教师可以读取 `resource.classId ∈ subject.classIds` 的成绩，审计员可以读取同租户记录，临时代班还要求 `context.now < subject.delegateUntil`。属性让一条规则覆盖许多对象，而不是为每个班级生成角色。

属性必须有可信来源和生命周期。租户 ID 应来自验证后的会话与服务端资源，不应相信查询参数；组织关系应有版本或更新时间；临时委托到期后要及时失效。把未经验证的前端字段放进策略，等于让请求者自己填写通行证。

ABAC 并不天然比 RBAC 更安全。规则越灵活，越需要明确的组合语义、冲突处理和测试矩阵。实践中常用 RBAC 决定“具有哪类能力”，再由 ABAC 收窄“能作用于哪些数据和条件”，两者不是互斥产品选型。

### 四、资源、动作与数据范围要来自业务语言

权限模型应从业务操作表开始，而不是从路由和组件开始。订单的查看、导出、提交、批准、作废是不同动作；列表读取、单条详情、聚合统计和文件下载也可能暴露不同范围。若只定义 `order:read`，后来很容易让能看单条的人意外导出整个租户。

数据范围至少考虑租户、组织、所有者、关联关系、敏感级别和对象状态。范围应下推到服务端查询或可靠的访问层，不能先查出全部数据再在浏览器过滤。分页总数、搜索建议、导出任务、缓存命中和错误差异都可能泄露越权对象的存在。

对象 ID 可猜并不应影响授权结论。每次按 ID 读取都重新验证主体与资源关系；批量接口对每个对象或整个集合约束范围；后台任务在执行和领取结果时都保留发起主体与租户，不能只在创建任务时检查一次。

### 五、默认拒绝让遗漏变成安全失败

**默认拒绝（Deny by Default）**表示只有明确匹配允许规则的请求才放行。新动作、新资源、新枚举或缺失属性不会因为“系统没写规则”而意外开放。拒绝结果仍要可诊断：内部日志记录规则 ID、主体、资源、策略版本和拒绝原因；外部响应避免泄露敏感资源是否存在。

规则冲突需要固定算法。例如先应用强制拒绝，再处理明确允许；或者按资源所有者、租户边界和职责分离逐层收窄。不能依赖规则数组顺序或某个框架的偶然默认值。策略升级也要有版本，让一次决定能重放当时使用的规则。

默认拒绝不等于所有异常都返回相同用户体验。未登录可引导认证，已登录但无权可说明申请路径，敏感对象可统一返回不存在。安全语义与可用性文案应分别设计。

### 六、决定点与执行点必须分工清楚

**策略决策点（Policy Decision Point）**负责根据标准输入返回允许、拒绝及理由；策略执行点位于 API、服务方法、查询和文件下载等实际边界，确保拒绝真的阻止副作用。属性信息点提供组织、角色和资源属性，策略管理点负责变更、审批和发布。即使没有专门产品，这些职责也应在代码结构中分开。

纯策略函数便于用表格测试，但不能把资源状态完全交给调用者。服务端先从可信存储加载必要事实，调用决策，再在同一业务提交边界内防止状态被并发改变。高价值动作可以记录决策摘要或策略版本，便于审计。

前端可以消费能力清单控制入口，但服务端仍独立决定。能力清单是某时刻快照，标签页长时间打开、角色撤回或租户切换后都可能过期；请求被拒绝时，界面应刷新权限并清理不再允许的数据。

### 七、缓存权限决定时先定义身份与失效

权限缓存的键至少包含主体、租户、策略版本，以及所有会改变结果的上下文维度。只用 `role=auditor` 会让不同租户和不同临时委托共用结果。对对象级决定还要考虑资源版本或关系版本，否则所有者变更后旧许可仍可能生效。

缓存有效期必须短于关键属性的失效要求。角色撤回、账号冻结、委托到期和策略发布触发主动失效；无法可靠推送时，用短 TTL 和服务端二次检查控制风险。缓存失败应回到安全决定，不能因为权限服务超时就默认允许。

列表数据缓存也属于权限边界。切换账号或租户时取消在途请求、清除私有查询和预取；响应提交 UI 前校验仍属于当前会话。登出只删 token 却保留上一用户列表，会造成明显的数据泄露。

### 八、前端权限层负责一致体验而非替代授权

前端可以把服务端能力映射为路由入口、按钮、字段和操作说明。隐藏适用于完全无关的能力；禁用并解释适用于用户可能通过申请、补充条件或等待状态获得能力的场景。不要仅靠 CSS 隐藏敏感内容，数据根本不应传到无权客户端。

同一业务动作应复用统一能力判断，避免菜单、详情和批量工具各写一套。组件接收的是语义能力，如 `canApprove` 与拒绝理由，而不是原始角色数组；这样角色和策略变化不会扩散到所有页面。

客户端预判与服务端拒绝可能因时序不同而不一致。界面要把 401、403、对象已变更和策略暂不可用分开处理，保留用户安全的未提交输入，并提供刷新或申请权限路径。

### 九、授权测试要覆盖矩阵、绕过与生命周期

先构造主体×动作×资源×上下文矩阵，覆盖允许与拒绝两面。重点反例包括跨租户同 ID、对象关系变化、临时权限到期、角色撤回、批量混入越权 ID、直接调用隐藏接口、缓存命中和旧标签页。只测试管理员成功路径无法证明系统默认安全。

策略函数用单元测试穷举边界，API 集成测试证明执行点不可绕过，端到端测试验证用户反馈但不承担全部安全证明。属性生成或性质测试可以表达“不论其他字段如何变化，不同租户始终拒绝”这类不变量。

日志验证同样重要：允许与拒绝都应带请求关联 ID、策略版本和规则标识；敏感属性要脱敏。定期从真实角色反查实际权限，与岗位和最小权限要求比较，发现长期累积的角色漂移。

### 十、变更与应急权限必须可治理

策略变更像代码发布一样需要评审、测试、灰度和回滚。先写影响对象、旧新矩阵、迁移窗口与缓存失效，再发布新版本。新增允许通常比新增拒绝风险更高，因为错误开放可能立即泄露数据；回滚也要确认缓存与会话已回到一致版本。

应急账户和 break-glass 权限要有明确触发条件、短时有效、强认证、双人批准和完整审计。它不是永久超级管理员。应急结束后撤回凭据，复核使用记录，并把暴露的日常权限缺口纳入改进。

多服务架构中，边缘网关可做粗粒度检查，但拥有业务事实的服务必须执行最终授权。把所有决定放在网关会丢失对象状态，把所有决定散落在服务又会产生规则漂移；共享策略语言与分布式执行点需要用一致性测试连接。

### 十一、常见失败与边界

- 把认证成功、前端按钮隐藏或路由守卫当成服务端授权。
- 用角色名直接拼查询，却遗漏租户、所有者和对象状态。
- 先查全量再过滤，导致总数、日志、缓存或导出泄露。
- 权限服务失败时开放访问，或缓存键缺少主体和策略版本。
- 规则过度抽象到没人能解释一次拒绝，也没有规则 ID 和测试。
- 为每个属性组合创建角色，最终无法审计实际权限。

权限系统不解决身份认证、加密或业务状态机本身；它消费这些可信事实并限制动作。对于极简单的单用户本地工具，不必引入完整策略平台，但仍应清楚哪些操作只在本地、哪些服务端数据需要保护。

### 十二、关系型权限与委托要防止越界传播

协作产品常出现“项目成员可看文档、文档所有者可邀请、组织管理员可管理成员”这类关系型授权。决定不只看角色和属性，还要沿主体—组织—项目—资源关系求值。关系必须有方向、类型和作用域；“A 管理团队 T，T 拥有文档 D”不自动推出 A 可阅读 D，除非策略明确允许该路径。

继承和共享链接要设置传播边界。文件夹权限下传到子项时，子项是否能断开继承、移动后如何重算、外部访客是否被保留，都必须是可测试规则。删除成员、转移所有权与租户合并属于高风险变更，应先模拟受影响资源，再原子更新关系版本并失效缓存。

委托记录发起人、受托人、允许动作、资源范围、开始/结束和撤回状态。受托人不能继续转委托，除非规则明确；委托到期后的长任务、下载链接和现有会话都要重新判断。定期审计“谁通过哪条关系获得了什么”，而不只导出静态角色表。

### 十三、权限评审要同时检查过多与过少

最小权限评审不仅找越权，也找因规则过严而迫使团队共享账号、绕过流程的情况。先从真实岗位任务列必要动作，再比较实际授予、最近使用和敏感度；长期未使用不等于必然可删，但应要求 owner 解释。

策略影子模式可以在不实际放行时计算新旧结果差异，观察哪些请求会新增允许或拒绝。差异样本脱敏并由业务 owner 复核；确认后灰度发布，监控拒绝率、支持请求与关键路径。影子计算不能把本应拒绝的请求真的放行。

每次复核产出策略版本、差异矩阵、批准人、例外到期和回滚点。临时例外必须有期限，不能成为永久隐藏规则；到期前提醒 owner，未续期自动回到默认拒绝。

权限数据导出本身也是敏感能力：报告按需生成、限制范围与留存，并避免让审计者通过报表获得原本无权读取的业务内容。

### 十四、学完后应能说明

你应能从业务对象和动作建立 RBAC+ABAC 模型，解释主体、资源、环境属性的可信来源；区分客户端可见性与服务端执行点；设计默认拒绝、缓存键和失效；用跨租户、到期、撤回、批量与绕过测试证明权限边界，并在一次允许或拒绝后给出可追踪的策略版本和规则原因。

继续查证可参考 [NIST RBAC 项目](https://csrc.nist.gov/Projects/Role-Based-Access-Control) 与 [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

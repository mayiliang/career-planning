# AI 建议依赖、生成代码来源与准入安全知识点讲义

## AIDEV-07 AI 建议依赖与生成代码来源安全

AI 很容易给出一个包名、一段复制代码或“升级到最新版”的建议，但它并不承担包名是否拼错、发布者是否可信、安装脚本做了什么、许可证是否兼容、间接依赖是否增加、代码片段从何而来的后果。依赖和生成代码一旦进入仓库，就进入产品的执行、维护与法律边界。成熟团队把模型建议当作候选，把必要性、来源、解析结果、行为和可撤回性变成准入证据。

### 一、先证明需要依赖

每个新增包都增加版本、漏洞、许可证、安装、包体、维护和退出成本。审计第一问不是“这个包安全吗”，而是“为何要引入”。写清用户问题、所需能力、已有依赖和平台 API 能否满足、自己实现的成本与风险，以及不引入的代价。

AI 常为很小功能推荐多个库，或推荐仓库中已有能力。先搜索现有依赖、组件与工具链，避免重复日期、请求、状态、校验或格式化方案。原生 API 可减少第三方风险，但也要检查浏览器/运行时支持和团队维护能力。

必要性结论有有效期。一个临时迁移工具可放在隔离脚本并设删除日期，不必成为生产依赖；长期核心解析器则需更严格维护与兼容承诺。开发依赖同样能在 CI 执行脚本和读取秘密，不能天然视为低风险。

### 二、Dependency Provenance 回答制品从哪里来

**依赖来源（Dependency Provenance）**连接包版本、源仓库提交、构建工作流、发布身份和透明日志，使团队能验证下载制品与声明来源的关系。来源证明降低包被替换或冒充的风险，但不会证明代码无漏洞、许可证合适或功能满足需求。

检查 registry 页面、规范化包名、scope、发布者、仓库链接、签名/attestation、版本时间和归档状态。拼写相近包、刚创建发布者、README 链接跳转到另一仓库、来源提交不存在或构建来源不可验证都需要阻断或升级复核。

企业私有 registry 和代理可能改写 resolved URL，需要记录最终实际下载来源和完整性摘要。不要只凭搜索结果、下载量或模型给出的主页判断，因为攻击者能购买域名、复制文档和制造流量。

### 三、package 名称、版本和 tag 不是同一个事实

`latest`、版本范围与锁定版本承担不同语义。manifest 表达允许范围，registry tag 是可变指针，lockfile 记录当前解析树。AI 建议“安装 foo@latest”只说明一次命令，不能成为可重复的长期合同。

审计以实际解析版本为准，检查 Node/浏览器引擎、peer、optional、平台分支与发布渠道。预发布版本、弃用版本和大版本升级分别评估。包名规范化后与官方文档核对，scope 归属变化或所有权转移需要重新审查。

版本固定也不是永不升级。采用更新策略、兼容测试、漏洞响应和回滚窗口；长期冻结会累积不可跨越的升级跨度。准入记录写下一次复查信号，而不是一次盖章永久可信。

### 四、Lockfile Diff 展示真实依赖树变化

**锁文件差异（Lockfile Diff）**显示新增、删除、升级的直接与传递包、解析地址、完整性、可选分支和 peer 结果。只看 `package.json` 的一行变化，会漏掉数百个间接包或 registry 来源漂移。

生成 diff 前固定包管理器和版本，使用仓库认可的安装命令，避免无关格式/版本重写。评审新增节点、解析 URL、integrity、安装脚本标志、重复版本和大幅体积变化。一个直接包的漏洞可能实际来自传递路径，责任与修复方案要按依赖图说明。

锁文件来自确定的解析过程，但不是安全判决。完整性摘要证明下载内容与锁记录一致，不证明记录本身选对了包。冻结安装能验证可重复性，仍需来源、漏洞、许可证和行为审计。

### 五、Install Script 是安装阶段代码执行

**安装脚本（Install Script）**包括 preinstall、install、postinstall 等在依赖安装期间运行的代码。它可能下载二进制、编译原生模块、读取环境或访问网络；CI 中常同时存在 registry token、签名凭据和缓存，因此风险不低于运行时代码。

检查直接与传递包的脚本字段、脚本内容、调用二进制、网络地址和平台分支。在隔离环境以最小权限、无生产秘密、受控网络运行，记录创建文件、进程和请求。禁用脚本安装可揭示哪些包依赖隐式执行，但不能自动作为所有项目的最终方案。

必要的原生构建工具应有明确来源、校验和替代。包声称“只下载预编译文件”仍需验证目标、摘要和失败回退。未知脚本默认不准入；紧急例外有 owner、范围、到期和隔离控制。

### 六、漏洞扫描提供线索而不是单一结论

CVE/安全公告具有时间性。保存扫描工具、漏洞库版本、时间、依赖路径、受影响版本与可达功能。直接包携带脆弱传递依赖，不等于漏洞一定可利用；扫描没有告警，也不等于没有未知漏洞或恶意行为。

风险判断结合严重性、可达性、输入控制、部署环境、补偿控制和修复可用性。高影响可达漏洞阻断；暂不可升级时，记录临时缓解、监控、负责人和到期。不能用“只是开发依赖”忽略会在 CI 执行的攻击面。

升级后重新生成依赖树和测试，避免修复一个 CVE 却引入破坏性 peer、另一条漏洞或体积退化。豁免绑定具体 advisory、版本和路径，不是对包名永久放行。

### 七、许可证和代码出处属于不同证据链

包的 SPDX 许可证、仓库 LICENSE、发布制品内容和复制代码片段可能不一致。确认组织允许的许可证、通知/归属义务、源代码提供要求、专利条款和生成物边界；不确定时由法律或合规责任人判定，而不是让模型解释为“通常没问题”。

AI 生成片段可能与训练或检索来源高度相似。要求工具保留可用的引用、搜索明显独特片段、核对官方示例许可，并记录人做出的出处判断。来源未知的大段代码不能因“是模型写的”自动获得许可。

内部代码和第三方代码也分开。把组织专有片段发到未经批准的模型可能先造成数据泄露，即使返回代码本身没有第三方问题。发送治理归团队工具准入，合入准入仍检查输出来源和许可证。

### 八、Source Attribution 让生成片段可追溯

**来源归属（Source Attribution）**记录生成或复制内容使用了哪些文档、仓库、许可证、模型/工具版本和人工修改。它不是在每行代码贴来源，而是在风险足够高时保留可复核链路。

通用样板、简单调用与大段独特算法的归属需求不同。代码越长、越独特、越接近已知实现，越需要核验。若模型工具提供引用，仍要打开原来源确认内容和许可证；引用字段本身可能错误或过期。

对于无法确认出处但可以独立重写的功能，先从需求和公开规范重新实现，并用独立测试验证，不保留可疑结构或注释。无法安全重写且业务价值不高时，最合理决定是不用。

### 九、包体与运行权限影响产品边界

分析浏览器生产包、服务端部署和 CLI 三种环境的不同成本。一个 Node-only 依赖可能把 polyfill 和动态代码带进浏览器；一个小入口包可能按条件加载巨大字典；tree-shaking 只有在真实构建中才能验证。

记录传输、解析、执行、内存和初始化，不只看 registry 的 unpacked size。观察副作用标记、动态 import、worker、Wasm、原生二进制和网络请求。体积预算是用户体验和部署成本约束，不是美观数字。

运行权限也需最小化：是否访问文件、网络、环境变量、子进程、剪贴板或浏览器 DOM。依赖功能若需要超出问题本身的权限，应拒绝或放入隔离服务。README 自述不会自动形成沙箱。

### 十、维护状态要看治理而非明星数

检查发布节奏、未处理安全问题、bus factor、所有权变化、CI 与发布方式、支持版本和弃用政策。高星项目可能停止维护，小而稳定的规范实现也可能合适。下载量容易受生态默认和机器人影响，只能作为背景。

维护信号必须结合使用位置。核心身份/解析依赖需要稳定响应和长期支持；一次性构建脚本可以接受更窄生命周期，但需锁定和隔离。Fork 意味着团队承担上游合并、安全响应和发布责任，应明确 owner 与退出计划。

准入后持续观察弃用、所有权、漏洞和供应链事件。新维护者、包转让、突然大版本或构建流程改变触发复审，不等待出事故。

### 十一、建立可执行准入流水线

PR 模板声明为何新增、替代项、直接/传递变化、来源、许可证、脚本、漏洞、包体和验证。自动化生成 lockfile diff、SBOM、许可证和 vulnerability 报告；人工负责必要性、可达性、来源异常与风险接受。

门禁只阻断明确政策，例如不允许许可证、关键可达漏洞、未知 registry、未审安装脚本或超预算。工具故障与数据缺失要显示 unknown，不能默认为通过。例外文件有具体版本、原因、owner、到期和补偿控制。

合入后冻结安装和生产构建，验证没有隐式网络漂移；制品晋级使用同一依赖树，不在部署时重新解析。回滚保存前一锁文件与制品，且数据库/协议变化另有兼容策略。

### 十二、生成代码也要经过普通工程生命周期

模型生成代码先检查需求与边界，再做类型、静态分析、单元/属性、组件、契约和端到端验证。测试预言来自需求、规范和历史行为，不能由同一提示同时生成实现与期望后互相证明。

审查错误处理、权限、并发、资源释放、可访问性和性能。生成内容可能表面惯用却对当前版本错误。任何新增依赖回到相同准入流程，不能因“只是修复编译”临时安装。

记录使用工具、关键人工决策和验证，不需要保存隐式思维或所有对话。责任人仍对合并负责，模型不能批准自己的建议。

### 十三、用恶意与退化样例验证

准备拼写相近包、同名不同 scope、来源提交缺失、未知 postinstall、许可证冲突、高危传递漏洞、重复能力、巨大包体、不可复现 tag、无引用长代码和包含秘密的片段。断言流水线在正确层阻断并给出可行动原因。

对允许包从空缓存执行冻结安装，核对实际 resolved URL、完整性、脚本与 SBOM。对拒绝项验证没有残留 lockfile、缓存提交或导入。升级演练包含失败回滚和旧制品恢复。

可用 [npm 来源证明说明](https://docs.npmjs.com/viewing-package-provenance/)、[npm lockfile 说明](https://docs.npmjs.com/files/package-lock.json/) 和 [GitHub Dependency Review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review) 核验当前工具能力。npm、GitHub 与漏洞库都会变化，结论应带日期和工具版本。

### 十四、准入之后仍需响应与退出能力

获准版本进入资产和 SBOM，持续关联新漏洞、弃用、发布者变化、许可证变化和运行异常。安全公告需要从包名追到实际制品、传递路径、部署环境和可达功能；无法确认影响时先限制高风险使用并指定调查期限。开发、测试与生产可能解析不同树，必须分别核对。

准备移除依赖的边界：调用集中在适配器，业务类型不直接泄露第三方结构，关键数据使用开放格式。发生恶意发布或账户接管时，能够冻结 registry、撤销版本、恢复前一制品、搜索受影响构建并轮换可能暴露的秘密。删除依赖后检查动态 import、脚本、缓存、镜像和许可证通知，不以 manifest 消失当作完成。

定期抽样已准入包从空环境重建，比较来源、摘要、脚本、SBOM 和生产构建。若维护、来源或组织需求已变化，重新做必要性判断；“过去审过”不是永久豁免。

学完后，你应能从“AI 推荐一个包”开始，依次证明是否需要、实际解析了什么、制品从哪里来、安装会执行什么、法律与安全风险如何、怎样冻结和撤回。可信准入不是收集一堆扫描绿勾，而是让每个进入仓库的外部能力都有可追溯理由和边界。

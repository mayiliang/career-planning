# AI 推荐的包，怎样才可以进入仓库

## AIDEV-07 AI 建议依赖与生成代码来源安全

你让 AI 为报表增加日期格式化，它给出一个看起来很专业的包名。安装之后功能正常，锁文件却新增了二十多个包，其中一个在安装时下载并执行二进制。团队原本已有日期工具，这次改动究竟解决了什么问题？

模型给出的名称、版本和代码都是候选。准入要回答三个连在一起的问题：为什么需要它，实际引入了什么，以及出了问题如何停止使用。本篇从一次依赖建议走到锁文件、安装执行、来源、漏洞、许可证与退出；读完应能把“看起来可靠”改成可以逐项复核的证据。

### 学习前先确认

- 直接前置：[ENG-08 软件供应链、SBOM、来源与可信制品](../chinese-guides/eng-08-software-supply-chain-sbom-provenance.md#eng-08)。先理解源代码、构建与交付制品之间的区别。
- 直接前置：[AIDEV-03 AI 生成代码的验证金字塔](../chinese-guides/aidev-03-ai-generated-code-verification.md#aidev-03)。预期行为必须有独立于生成实现的依据。

### 一、先把包名还原成用户需要的能力

报表需要把时间显示成“2026 年 10 月 7 日”，不等于需要一个新的日期生态。先说明时区、语言、输入格式和错误处理，再检查现有依赖与平台 API。若需求只是展示，Intl.DateTimeFormat 可能够用；若还要复杂日历计算、时区数据库或历史规则，选择可能不同。原生能力同样要符合目标运行环境。

建议记录可以很短：“需要解析带时区的导入数据；现有工具只格式化；比较复用、独立适配器和新库；由报表模块负责人维护。”这比先安装再找理由更容易评审。临时迁移脚本也不必进入浏览器生产依赖，可以限定在隔离工具目录，用完删除。

包名要从可信项目文档和包注册表双向核对。模型可能写错字符，混淆相似 scope，或者推荐已经改名、废弃甚至不存在的包。所谓拼写仿冒，是利用读者看漏一个字母来引入另一个发布者的代码。不能为了让生成代码通过编译，就自动安装报错中出现的所有名称。

下载量、星标和更新时间是调查线索，不能单独成为许可。一个多年不变的简单算法可能已经稳定；一个刚发布、下载量很高的包也可能接管了旧名称。对身份、解析和执行分别取证，才不会让流行度替代信任判断。

### 二、版本范围、解析结果与来源证明各回答一件事

package.json 中的版本范围表达“允许选择哪些版本”；registry 的 tag，例如 latest，是发布方可以移动的指针；锁文件保存某次解析的具体结果。三者可能分别是 `^2.1.0`、指向 `2.3.1` 的 tag，以及之前锁定的 `2.2.4`。审计对象应是实际安装和构建使用的版本，而不是 AI 文字中的“最新版”。

**依赖来源（Dependency Provenance）**描述某份制品从哪里、经由什么构建过程产生。npm 的来源证明可以关联源提交、构建工作流、发布与透明日志；验证时还要检查这些身份是否符合自己的信任政策。证明存在不等于代码安全，证明缺失也不等于已经发现恶意，要区分“不满足本团队来源要求”与“有攻击证据”。

完整性摘要回答“下载的字节是否与锁文件记录一致”。若攻击者让你选中了错误的包，又把它的摘要写入锁文件，摘要仍可一致。签名、来源证明、代码评审、漏洞分析和许可证分别回答不同问题，不能把任意一个绿勾解释成全部通过。制品身份的基础解释见 [ENG-08](../chinese-guides/eng-08-software-supply-chain-sbom-provenance.md#一先确定要交付的是哪一份字节)。

不同包管理器的锁文件结构不同。npm package-lock.json 可以记录 resolved 和 integrity；pnpm 的 registry 包可能只写摘要，再由 registry 配置确定下载位置。不能因为没有逐包 resolved URL 就凭空补一个“已核验地址”。应结合锁文件、scope 配置、代理配置和安装证据记录实际来源；Git、workspace、本地文件与 tarball 依赖还需分别识别。

固定版本有助于复现，却不等于永久冻结。安全公告、维护者变化、许可证变化或运行环境升级都可能触发复审。应保存当时的版本和结论，同时指定下一次复查的条件。

### 三、沿依赖路径找问题，避免把漏洞安在错误的包上

**锁文件差异（Lockfile Diff）**是解析前后依赖图的变化。评审不只看直接依赖多了一行，还要看传递依赖、peer 组合、可选平台包、来源配置和完整性是否变化。包管理器版本不同造成的大面积格式改写，会掩盖真正需要判断的部分，因此先固定工具版本。

假设两个工具都引用了同一个有风险的解析器。只移除其中一个工具，并不能让解析器消失。下面是完全虚构的离线图；名称和公告不对应真实包或真实 CVE。保存为 `dependency-paths.mjs`，用 Node.js 22 执行 `node dependency-paths.mjs`，不安装任何依赖、不访问网络。

```js example=aidev07-dependency-paths
const graph = {
  app: ['report@2.0', 'export@1.0'],
  'report@2.0': ['parser@1.4'],
  'export@1.0': ['parser@1.4'],
  'parser@1.4': [],
};
function pathsTo(node, target, path = []) {
  if (path.includes(node)) return []; // 防止错误图中的循环无限递归
  const next = [...path, node];
  if (node === target) return [next.join(' → ')];
  return (graph[node] ?? []).flatMap(child => pathsTo(child, target, next));
}
for (const path of pathsTo('app', 'parser@1.4')) console.log(path);
// => app → report@2.0 → parser@1.4
// => app → export@1.0 → parser@1.4
graph.app = ['export@1.0'];
console.log(pathsTo('app', 'parser@1.4').length); // => 1
```

第一轮得到两条路径，是因为同一制品有两个使用入口。删除 report 后仍有一条，说明移除一个直接依赖没有消除风险节点。如果 export 升级到不再引用旧 parser 的版本，才可能清空这条路径。真实锁文件中的身份还可能含 peer 或平台上下文，不能只按名称把不同节点合并。

路径证明“引入关系”，可达性分析还要问受影响代码能否被当前产品、构建脚本或攻击者输入触发。扫描报告中的严重性、受影响版本与实际执行条件应分别保留。没有告警可能是数据库未知或扫描失败；未使用某函数也不等于安装期间不会执行代码。高风险但暂时无法确认的项应进入调查或受限运行，不能把 unknown 当成低风险分数。

### 四、安装过程已经在执行外部代码

**安装脚本（Install Script）**指安装生命周期中执行的程序，例如 preinstall、install、postinstall。它可以编译原生扩展、下载二进制，也可能访问环境变量、文件和网络。devDependencies 常在开发机与 CI 中执行，因此“不会发到浏览器”不代表没有安全影响。

先读取脚本内容及它继续调用的文件，再决定是否执行。仅看 postinstall 调用了 setup.js，看不到后者的行为。应检查下载目标、摘要校验、平台分支、失败回退和子进程；运行时使用无生产秘密的临时环境，限制文件和网络，观察实际写入与请求。容器如果挂载了宿主凭据或 Docker socket，也不能被当成天然安全边界。

安装策略与包管理器版本相关。本文于 2026-10-07 核对官方文档中适用于 pnpm 11 的规则：依赖构建审批由 `allowBuilds` 等设置管理；不要把其他版本的配置字段或 npm 默认行为直接套用。仓库应固定 packageManager，依据该版本的文档解释实际启用的规则。禁用脚本可以用于初步取证，但依赖可能因此无法使用，后续必须验证哪些构建确实必要。

下面是已有 pnpm 项目的操作说明，**只在临时副本、已核对 registry 且无生产凭据的环境执行**。它会安装文件并可能下载依赖，不是本篇自动运行的离线实验。仓库若还含其他可执行配置，也需要先审查；`--ignore-scripts` 不应被描述成对所有扩展代码的通用沙箱。

```bash example=aidev07-frozen-install runtime=project file=inspect-install.sh
pnpm --version
pnpm install --frozen-lockfile --ignore-scripts
pnpm list --depth Infinity
```

预期是锁文件与 manifest 一致时按已有解析安装，不一致时拒绝继续；最后观察实际依赖树。保存工具版本、锁文件摘要、registry 配置与执行输出。再按仓库策略只允许已经审过的必要构建，在干净环境完成生产构建。一次冻结安装成功不能证明安装没有访问网络，也不能证明打包可重现或制品已经安全。

### 五、让准入决定保留拒绝与未知的区别

团队门禁应把明确禁止、证据不足和允许进入下一步分开。例如“必要性已否决”可以直接拒绝；“发布身份尚未核验”应暂停；“来源已核验但安装脚本未知”仍不能通过。检查器故障应暴露为缺证据，而不是默认返回成功。

下面只演示判定顺序。所有 true/false/null 都是假定上游审查给出的结果，程序没有联网核验许可证、CVE 或签名。保存为 `admission.mjs`，用 Node.js 22 运行；null 表示未知。

```js example=aidev07-admission
function decide(evidence) {
  const required = ['needed', 'source', 'scripts', 'license', 'vulnerability'];
  const rejected = required.filter(key => evidence[key] === false);
  if (rejected.length) return `拒绝：${rejected.join('、')}`;
  const missing = required.filter(key => evidence[key] !== true);
  if (missing.length) return `待复核：${missing.join('、')}`;
  return '进入隔离构建验证';
}
const reviewed = {
  needed: true, source: true, scripts: true, license: true, vulnerability: true,
};
console.log(decide({ ...reviewed, needed: false })); // => 拒绝：needed
console.log(decide({ ...reviewed, scripts: null })); // => 待复核：scripts
console.log(decide(reviewed)); // => 进入隔离构建验证
```

最后一个结果刻意没有叫“永久可信”。它只说明这几项证据达到当前门槛；包体、功能、引擎、peer 兼容以及部署条件还要验证。把 scripts 改为 false 时，明确拒绝优先于其他缺失项；改为 undefined 时则是待复核。真实系统应返回结构化原因与证据引用，这里的中文字符串只是为了看清分支。

证据记录至少绑定包身份、具体版本、依赖路径、工具版本、核验时间、负责人和适用环境。漏洞豁免还要绑定公告、影响判断、补偿控制与到期；不能将一次对某版本的接受扩张成整个包名永久白名单。未知安装脚本、未知 registry 或越过硬性预算时，应先处理原因再重新运行门禁。

### 六、生成代码的出处与使用许可要单独核验

**来源归属（Source Attribution）**记录代码或资料取自哪里，以及怎样进入当前改动。来源能找到，并不自动说明可以按当前用途分发；找不到来源，也不能靠模型说“原创”就消除不确定性。

例如 AI 返回一段带独特注释的复杂解析器，并附上某仓库链接。先打开链接，核对文件、提交、对应片段与该版本许可证；再检查制品中是否包含另附条款的代码。package.json 的 license 字段、仓库 LICENSE 和复制文件的头部说明可能不同，需要把冲突提交给组织的许可审查责任人。公开可见、可以 fork 与可以在商业产品中任意再分发是不同权限，不能相互推导。

可保存一条来源记录：“需求 R-17；参考文件及提交；许可文件；保留的通知；人工修改；审查结论。”没必要给每个普通变量做归属标签，也不要把整段敏感对话存入 PR。对独特长代码、算法、图片或大块示例，应比简单样板采取更严格的来源核验。

引用也可能编造。链接能打开只说明页面存在，必须确认它确实支撑这段实现。无法确认、价值又有限时，放弃候选往往成本最低。若从明确需求和公开规范独立重写，应独立设计并验证，不能只改变量名就声称来源问题已经解决。具体许可证义务依许可证文本、分发方式及组织审查结论确定，本篇不提供某类生成代码的一概授权判断。

输入也有风险：把公司专有实现发给未批准工具，可能在输出审查之前就越过数据边界。哪些材料可以发送，见 [AIDEV-10 的数据流解释](../chinese-guides/aidev-10-ai-tool-data-team-governance.md#一沿一次请求找出真正的数据接收者)。输出通过测试不能撤销已经发生的外发。

### 七、用真实构建观察权限、体积与行为变化

同一个库在 Node.js、浏览器和 CLI 中可能使用不同入口与平台分支。registry 上的解压大小不能直接推导用户下载的 JavaScript；tree-shaking 是否生效，要看实际生产产物。至少比较变更前后的传输体积、关键路径加载、初始化、内存和必要功能，不把只在本机成功当成全部运行环境都支持。

假设替换日期工具后生产 JavaScript 增加 300 KB。先查是否误引入全部语言数据，是否 Node-only 入口引入 polyfill，是否同时保留了两套库。动态 import 可能延后下载，却不自动减少总体积；延后后还要处理加载失败、旧版本资源和用户取消。预算有业务依据，超过时解释代价，不能悄悄抬高阈值来让 CI 通过。

权限同样要观察实际使用：格式化文本的功能为什么需要子进程、任意文件读取或远程上报？确有必要的能力应集中在边界明确的适配器或服务中，并限制凭据和输入。文件路径、网络目标和运行隔离的详细机制已在 [AGENT-10](../chinese-guides/agent-10-identity-authorization-runtime-isolation.md#五授权允许做什么隔离限制实际能碰到什么)说明，这里不要重复制造另一套安全定义。

验证范围随影响选择。纯替换工具函数可用独立边界样例与必要构建；修改原生模块、安装脚本或身份链路则需要对应环境验证。AI 同时生成实现和测试不构成独立证据，应从需求、标准或已核验行为取得预期。检查投入的目的，是让重要假设有机会被推翻。

### 八、准入结论要能随事件撤回

审过的包仍可能出现新漏洞、维护者交接、账号接管、许可证调整或不再支持当前运行时。维护状态应结合安全响应、发布流程、人员和支持策略判断，不能用星标数量替代。引入方要指定 owner，保存当前使用版本及部署位置，才知道公告出现后该找谁、改哪里。

遇到可疑发布，先冻结新增使用与自动升级，确认受影响的版本、构建时间和执行权限；恢复此前可信制品，检查可能暴露的凭据并按影响撤销轮换。仅回退锁文件不足以清除安装阶段造成的外部影响，删除 package.json 一行也不会自动移除缓存、镜像、动态导入或生成文件。

退出设计从引入时就开始：业务通过小型适配器使用能力，关键数据采用可以导出的格式，保留旧制品及恢复步骤。不要为一个很小的依赖建立庞大通用框架，但也不要让第三方类型渗透到每个业务模块，导致移除时全仓联动。

最终准入记录应能回答：“谁基于哪一版证据允许这份制品进入哪个环境，发生什么变化时重新判断？”它比收集一页扫描截图更有用。通过、拒绝和未知都应保留原因；被否决的候选也值得记录，避免下一次 AI 建议让团队从头重复调查。

### 带着问题回看

1. 锁文件摘要一致，为什么仍可能安装错包？缺失的证据是什么？
2. 离线图中删除 report 后为什么还有风险路径？把 parser 改为构建期依赖会改变哪些判断？
3. 禁用安装脚本后构建失败，你会收集什么证据决定是否允许某项构建？
4. 一段代码通过全部功能测试，但引用无法核验，可以据此忽略出处吗？

# 组件职责与公共契约知识点讲义

## COMP-01 组件职责、API 设计、组合与扩展边界

组件不是把一段模板挪进单独文件，也不是以复用次数决定的抽象。它应拥有一个可以命名的界面职责，对外给出稳定的数据、事件与组合边界，并把内部结构留作实现细节。能长期演进的组件既不会把整个页面业务塞进“万能组件”，也不会把每个标签拆成只能在一个位置使用的空壳。本讲从职责、契约、语义和演进成本建立跨 React/Vue 的组件设计方法。

### 学习前先确认

- 直接前置：[A11Y-01 WCAG、可访问性测试与治理](../chinese-guides/a11y-01-wcag-testing-governance.md#a11y-01)。本讲直接使用语义、键盘、焦点、名称和自动/人工验证；该资料已递归包含 HTML 语义基础。

### 一、从用户任务而不是 DOM 片段划职责

一个组件的职责应能用“用户在什么情境完成什么任务”说明，例如日期范围选择、可排序数据表或可撤销通知。`LeftBox`、`BlueSection` 只描述布局；`EverythingForm` 又包含过多原因变化。好的边界让数据所有者、交互状态、错误恢复和可访问语义相对内聚。

列出变化原因：业务规则变、视觉主题变、数据来源变、交互模式变、平台能力变。经常一起变化的内容可在同一边界；变化节奏不同且接口稳定的部分可拆分。拆分不是越细越好，每个边界都有 props、事件、测试和理解成本。

先画组件树并标注状态所有者、数据方向和焦点责任。若一个节点既拉取多个业务域、又编排路由、又渲染低层控件，应把数据适配与视觉组件分开，而不是把所有选项继续堆进 props。

### 二、公共 API 是需要维护的合同

**组件契约（Component Contract）**包括输入、输出、组合点、状态模式、可访问语义、错误行为和兼容承诺。输入描述意图而不是内部 DOM，例如 `tone="danger"` 比 `className="red"` 更稳定；事件给出业务相关载荷，不暴露内部节点。

为每个输入写类型、默认值、必填关系、合法组合和变化时行为。`undefined`、空数组、空字符串、加载、错误和无权限都应有明确语义。不要让调用者猜测某 prop 是初值还是持续受控值；状态所有权细节在 COMP-02 深入，但这里必须在 API 上说清。

事件命名描述已发生或请求改变。载荷保持最小且稳定，包含必要身份和原因；不要把整个浏览器事件作为唯一合同。事件顺序、是否冒泡、取消方式和异步失败也应文档化。

### 三、先用组合，再增加开关

**组合（Composition）**让调用者把子内容或协作部件放入明确插槽，以结构表达差异。卡片的 header/body/actions、表格的列定义、对话框的触发器与内容，都比一串 `showHeader/isAdmin/isCompact/hasFooter` 更易扩展。

布尔参数相乘会产生许多没有业务意义的组合。三个开关已有八种状态，测试者无法知道哪些合法。优先使用具名变体、判别联合或专用子组件，让非法状态在类型和结构上不可表达。

组合不是把内部全暴露。插槽需要说明可出现的位置、接收的上下文、键盘和布局责任。渲染回调若每次都泄露内部状态，会让实现无法变化；只公开调用者真正需要的能力。

### 四、语义变体必须与行为一致

**语义变体（Semantic Variant）**以用户意图命名，如 primary/destructive/quiet，而不是 blue/small。变体同时约束视觉、语义、交互和可访问性：危险按钮不仅红色，还需要清晰名称、确认或撤销机制；链接外观不能把按钮语义改成导航。

尺寸、密度和布局可以是独立轴，但应限制组合并提供设计 token。不要允许调用者任意覆盖内部颜色、间距和层级，否则公共组件只是带默认样式的裸 DOM。

当两个变体的 DOM 语义、交互流程或数据合同显著不同，拆成两个组件比继续加条件更清晰。例如导航 Link 与执行动作 Button 可以共享样式基础，却不应由一个模糊 `as` 属性隐藏语义差别。

### 五、默认值是产品决定

默认值降低常用路径成本，也会把隐含行为扩散到所有调用者。默认按钮类型、对话框关闭方式、日期时区和表格排序都可能造成业务后果。安全默认应最小权限、可预测，并在版本升级中保持兼容。

不要从调用上下文偷偷推断关键行为，例如根据是否存在 `onClick` 改变元素语义，或根据 children 文本决定危险级别。重要选择应显式；便利推断只用于无业务歧义的展示。

更改默认值属于 API 变更。通过弃用提示、迁移说明和调用点清单渐进推进，不能在设计系统版本中静默改变所有页面。

### 六、可访问语义由组件负责到底

组件选择原生元素并提供名称、角色、状态和键盘行为。调用者提供具体标签，组件确保标签真正关联。自定义列表框、菜单和对话框需要完整焦点模型，不是加一个 `role` 就完成。

定义焦点入口、移动、退出和恢复。组件打开浮层时把焦点送到合理位置，关闭后返回触发器；禁用与只读要区分；错误通过程序可感知方式关联输入。插槽内容也必须遵守组件的语义约束。

自动规则能发现缺少名称、对比度和部分 ARIA 错误，但键盘顺序、读屏含义和任务完成需要人工验证。公共组件的修复影响大量页面，因此基础层应有更严格的可访问性测试。

### 七、数据与视图适配放在边界外

后端 DTO 往往包含权限、分页、空值和技术字段，视觉组件不应直接依赖整份响应。容器/适配器把 DTO 转为组件模型，负责取数、权限和重试；展示组件接收完成任务所需的稳定数据与事件。

这样能在 Storybook、单元测试和另一个框架环境中构造明确输入，也避免内部发请求造成隐藏瀑布。并非所有组件都要“纯展示”：路由页面和领域组件可以拥有数据，但公共 API 仍需划清远端状态与局部交互状态。

不要把全局 store 当免传 props 的捷径。隐藏依赖降低可复用性、测试隔离和多实例能力。真正跨树的主题、语言或会话上下文可注入，但必须记录来源和覆盖方式。

### 八、样式 API 保护封装

允许 `className` 或任意 CSS 选择器深入内部会让调用者依赖 DOM 结构。优先提供语义变体、尺寸、token、根节点类和有限的 part/slot。若必须开放内部样式，命名为稳定 part，并把它当公开 API 测试。

布局责任要明确：组件负责内部排列，父容器负责外部位置和可用宽度。根节点通常应能收缩，长文本和本地化不溢出；不要写死页面宽度或依赖父级特定标签。

主题通过 CSS 变量或设计 token 传递，同时提供回退。测试高对比、放大、窄屏、超长文本和减少动画，避免只看默认截图。

### 九、逃生口必须狭窄且可撤回

**逃生口（Escape Hatch）**处理公共契约难以覆盖的少数合法场景，例如根节点属性、稳定 part、自定义渲染或最小命令能力。它不应成为绕过设计系统、权限或语义的通用后门。

开放前收集真实用例：是否能通过组合解决；是否多个调用者需要；是否能维持兼容；错误使用能否被发现。给逃生口写风险说明、测试和迁移策略。只为一个页面临时开口，通常更适合在该页面组合专用组件。

禁止暴露完整内部状态、可随意替换 DOM 的回调或所有 CSS 变量。开放越多，维护者越难重构。调用者需要聚焦时可给 `focus()`，不必返回 input DOM 和内部 reducer。

### 十、复杂组件需要状态模型

表格、选择器、对话框和上传器都包含多个正交状态。列出用户可观察状态与事件：空、加载、失败、就绪、禁用；打开、关闭、提交；键盘焦点和异步结果。避免用许多布尔值表达互斥状态。

组件契约只承诺可观察行为，不要求调用者理解内部框架生命周期。异步操作有取消和陈旧结果保护；卸载后不能更新已失效实例；重开组件时重置哪些状态必须明确。

状态模型也揭示拆分点：若筛选器、结果表和批量操作有独立所有者，可通过组合协作；若必须访问彼此全部内部状态，当前抽象可能错误。

### 十一、错误、空态与权限是主路径

错误不是 `console.error`。组件区分输入不合法、网络失败、业务拒绝和内部异常，给用户可行动信息，同时把技术细节交给日志。空态区分尚未查询、确实无数据和被筛选为空。

权限决定操作是否存在、禁用还是提示申请，需由业务策略定义。前端隐藏不是授权；组件仍不能让无权限调用者通过任意 slot 注入危险动作。权限语义作为输入，而不是组件自行猜角色名。

恢复动作保持上下文：重试不丢筛选，表单失败保留输入，焦点回到错误摘要或相关字段。公共组件应允许页面提供领域文案，却负责正确关联和行为。

### 十二、类型只能表达部分合同

TypeScript 能表示判别联合、必填关系、事件载荷和泛型项身份，但不能证明焦点顺序、服务端权限或运行时外部数据。对外部输入运行时校验，对交互语义做 DOM 测试，对视觉和任务路径做浏览器验证。

泛型组件避免过度聪明。表格若用几十层条件类型推导每个单元格，调用者错误会难懂。优先清晰列定义、稳定 key 和可推断的常用入口；为高级入口提供显式类型。

弃用字段先给替代方案和开发期告警，再统计调用点并分阶段删除。类型报错本身也是 API 体验，需用示例与类型测试保护。

### 十三、测试公共行为而非实现细节

组件测试从用户可见角色、名称和事件操作，不查询内部类名或 state。覆盖键盘、指针、禁用、只读、加载、错误、长文本和多实例。事件断言包含次数、顺序和载荷。

契约测试可固定公共类型和关键 DOM 语义；视觉回归保护不同尺寸和主题，但不能替代行为断言。对弹层检查焦点捕获、Escape、外部点击规则、滚动锁和关闭后恢复。

故意注入慢响应、旧结果、重复点击、调用者传入非法组合和 slot 异常。失败时应明确拒绝或进入已定义状态，不应静默渲染半合法界面。

### 十四、版本演进与兼容

区分新增可选能力、行为修复、默认变化和破坏性重构。语义版本只是通知机制，关键是列出受影响调用者和迁移步骤。公共组件先在真实页面灰度，观察交互完成率、错误和可访问性回归。

不要永久保留两套模糊 API。兼容层有截止时间、告警和删除计划。若旧 API 无法安全映射到新语义，明确主版本迁移比暗中猜测更可靠。

跨 React/Vue 共享的应是职责、token、状态模型和行为合同，不必强求一份运行时代码。Web Components 也不能自动解决框架数据流和表单语义；互操作选择取决于团队与发布边界。

### 十五、文档与示例也是契约

组件文档先给最小正确示例，再展示组合、错误、禁用、异步和响应式；每个示例说明状态所有者和用户语义。不要只列 props 表，调用者需要知道多个输入如何共同形成合法状态。示例应由测试或可运行故事复用，避免升级后文档静默过期。

为选择题写决策指南：何时用 Button 或 Link，何时用 Dialog 或 Popover，何时组合、专用组件或不使用该组件。列出非目标和替代方案能阻止抽象被滥用。迁移文档从用户任务映射旧到新，而不只是机械重命名。

公共组件的错误信息应指向文档和修复建议。开发期对非法组合告警，生产保持安全退化；不能在生产悄悄渲染一个语义错误但视觉正常的结果。

### 十六、组织级治理与采用反馈

设计系统维护者统计真实调用、逃生口使用、重复包装、缺陷和升级阻力。高频覆盖内部样式说明 API 缺能力，也可能是团队未理解；结合代码与访谈判断。不要把组件数量或采用率当唯一成功指标。

变更由设计、工程、无障碍和主要消费者共同评审，明确 owner 与支持周期。实验组件标记稳定性，避免早期 API 被误当长期承诺。弃用有自动迁移、告警和截止日期。

当业务需求分化时允许领域组件在基础原语上形成更具体合同。平台层不应吸收所有业务差异，业务层也不应复制键盘和可访问机制。分层的关键是变化原因和责任边界。

评审还应由未参与实现的人只读文档完成一次调用，记录歧义与错误恢复；作者熟悉内部结构，容易把隐含知识误当公共合同。

组件的遥测也不能泄露内部实现。记录用户可观察事件、失败类别、版本和调用场景，避免上传输入全文或 DOM。发现某个非法组合频繁出现时，优先收紧类型和文档；若合法任务长期依赖逃生口，则把真实需求提升为稳定契约并补齐语义与测试。

### 十七、评审顺序

先看职责陈述和用户任务，再看组件树、状态所有者、输入/事件表、合法组合、语义/焦点、组合点、样式边界、逃生口、错误恢复、测试矩阵和迁移策略。若必须阅读实现才能知道某 prop 的含义，契约还不够完整。

高级组件设计不是把 API 做得最灵活，而是让常见正确用法自然、非法组合难以表达、少数扩展有清晰边界。组件能在内部实现变化后继续兑现同一用户语义，才真正形成可复用资产。

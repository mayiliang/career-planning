# AI 协作执行知识点讲义

## AIDEV-01 AI 协作规格上下文与代理执行闭环

AI 编程工具可以搜索仓库、编辑文件和运行命令，这使它从“建议者”变成了能产生副作用的执行者。可靠协作不能只靠一句写得很长的提示词，而要把任务事实、权限、工具、预算、检查点、验证和人工责任组成一个可停止、可审计的执行系统。本讲不绑定某个模型或产品，重点是怎样控制任何会行动的编码代理。

### 学习前先确认

- 直接前置：[ENG-05 lint、format、typecheck 与提交门禁](../chinese-guides/eng-05-quality-gates-lint-types-tests-ci.md#eng-05)。本讲直接使用风险门禁、CI 裁决、可信输入、例外和证据保存；代理生成的改动不会获得更低标准。

### 一、先区分需求、规格、任务与提示

需求表达为什么要改变以及用户需要什么；规格把可观察行为、边界与非功能约束写清；任务把一个可交付切片分配给执行者；提示是与模型通信的一次输入。提示可以引用规格，但不能替代规格的版本、评审和所有权。

一个任务若只有“优化结算页”，模型只能猜测目标。可执行任务至少说明当前问题、期望行为、不变量、允许范围、验证方式和需要人判断的事项。规格仍可能不完整；发现冲突时正确动作是停止并提出具体缺口，而不是用模型偏好补成事实。

### 二、任务包把事实与执行约束放在一起

**任务包（Task Packet）**是一次代理执行所需的最小、版本化合同。它包含任务 ID、目标、规格版本、基线提交、直接相关文件或地图、允许读写范围、允许工具、网络与依赖策略、时间/费用预算、验收项、证据格式、停止和升级条件。

任务包不是把整个仓库复制进聊天。文件内容仍按需读取，包中先给可定位的 URI、路径与版本。敏感信息只给完成任务必需的最小权限；生产密钥、客户数据和无关历史不因“模型可能用得上”而进入上下文。

任务包应由人或上游流程批准，并能以 hash 或版本号重建。同一执行中规格改变，应创建新版本并重新评估已有改动，不能把旧验证拼接到新目标。

### 三、工具边界决定代理能造成什么副作用

**工具边界（Tool Boundary）**定义代理可调用哪些能力、作用于哪些目标以及何时需要批准。读仓库、改工作区、安装依赖、访问网络、推送分支、操作云资源和删除数据的风险不同，不能只用一个“允许终端”概括。

边界要在执行环境中强制，而不只写在提示里。文件系统沙箱、只读令牌、仓库级 deploy key、网络白名单、命令批准和临时凭据都能缩小爆炸半径。代理声称“我不会访问”不是控制；审计日志显示它不能访问才是控制。

动作还要区分可逆性。局部文件编辑可由 diff 恢复；发送消息、发布包、数据库迁移和生产删除可能不可逆或影响他人，需要更强批准、dry-run、备份和回滚计划。

### 四、执行循环必须由状态而不是聊天长度驱动

一个受控循环可写成：UNDERSTAND → PLAN → ACT → VERIFY → DECIDE。理解阶段确认规格、基线和未知；计划阶段把工作拆成小步并识别风险；行动阶段一次产生有限变更；验证阶段收集机器和人工证据；决策阶段选择继续、修正、回滚、完成或升级。

每轮输出结构化状态：做了什么、改变哪些文件、使用哪些工具、观察到什么、还剩哪些验收项。聊天文本可以解释，但状态记录是恢复和审计依据。工具结果是不可信输入时，还要防止其内容冒充高优先级指令。

### 五、检查点让长任务可观察、可恢复

**检查点（Checkpoint）**是经过验证、可恢复的中间状态。检查点应对应一个有意义的风险边界，例如“失败测试已复现”“Schema 已更新且类型通过”“UI 已实现且行为测试通过”，而不是每执行一条命令就打点。

检查点记录基线、diff、命令与退出码、失败证据、未解决项和下一步。长任务中断后从最近可信检查点恢复，而不是只读一段摘要后猜测环境。若外部状态可能变化，恢复时重新核验分支、依赖、服务和权限。

过大的检查点会让错误累积，过小则产生审计噪声。按可独立验证和可回滚的工作单元划分，通常比按时间间隔划分更有效。

### 六、停止条件是可靠性功能

**停止条件（Stop Condition）**明确代理什么时候不得继续。典型条件包括：规格冲突或缺关键选择；需要超出允许范围；连续出现同类失败；预算或时间用尽；验证环境不可用；发现高风险安全问题；即将执行不可逆动作；观察到外部状态与任务包不一致。

停止不等于任务失败，而是把决策权归还给有权限的人。升级消息要具体说明阻塞事实、已经排除的可能性、可选方案和每个方案的影响，不能只说“需要更多信息”。

次数预算不能机械地“失败三次就换另一种随机方法”。它的目的在于阻止无证据重试和权限扩张。相同故障反复出现时，先比较输入、环境和假设是否改变。

### 七、验证必须独立于“代理说完成了”

验收项要映射到证据：静态规则对应 lint/typecheck，行为对应自动测试或浏览器轨迹，构建对应制品，视觉对应审查后的截图差异，安全对应扫描与边界测试。命令退出码和原始输出应保存，摘要只能作为索引。

代理可以运行检查，却不应成为唯一裁判。高风险改动由独立测试、代码所有者或第二条证据验证；生产发布、权限变化和数据迁移保留人工批准。测试绿只说明当前测试覆盖的预言成立，不证明规格本身正确。

完成状态要求所有验收项有证据、未解决项明确、变更范围未越界、回滚/恢复路径存在。若只能验证一部分，应报告部分完成而不是润色成成功。

### 八、计划和权限应随风险动态收紧

初始阶段通常只需要读和诊断。确认根因后才开放最小写范围；验证时只需要运行已批准命令；发布另设审批。渐进授权比一开始给全权限更容易发现偏航。

风险来自数据敏感度、用户影响、可逆性、权限等级、外部副作用和验证难度。修改文案与更改认证逻辑都可能只改一行，但风险完全不同。预算也按风险分配：高风险步骤允许更多验证时间，不允许更多未经批准的尝试。

### 九、失败分类决定下一步

规格失败：输入相互矛盾或验收不可判断，升级产品/领域负责人。环境失败：依赖、服务或凭据不可用，保存证据并恢复环境。实现失败：代码没有满足已知合同，回到最小反例。验证失败：测试不稳定或预言有问题，先修复证据系统。权限失败：动作超出边界，不自动申请更大权限。

把所有红灯都交给模型“继续修到绿”会诱发改测试、删断言、扩大忽略或绕过门禁。任务包应明确哪些文件和配置禁止为了变绿而修改，以及谁能批准例外。

### 十、规格变化需要重新建立因果链

任务执行中出现新需求时，先暂停当前循环，记录旧规格下已经完成的事实。比较新旧验收项，标出可复用、需重做和冲突的部分；更新任务包版本与基线，然后重新计划。只有输入仍相同的证据才能复用。

例如原目标是“优惠不可叠加”，后来改为“同类优惠不可叠加”。旧的拒绝所有叠加测试不再证明新规则。代码可能需要放宽，测试预言也要变；不能只改文案并保留绿灯截图。

### 十一、审计记录要能重建而非堆积

记录模型/工具版本、任务包 hash、基线提交、读取与修改范围、工具调用、批准、检查点、退出码和最终 diff。对输入输出做必要脱敏，并设保留和访问策略。日志越多不等于越可审计；没有任务 ID、顺序和关联的海量文本难以重建因果。

摘要标明“事实、推断、未知”。原始证据可按 URI 保存，摘要引用它而不是复制全部。这样既控制上下文，也允许评审者下钻。

### 十二、用故障演练验证控制是否真实

选一个小型只读筛选功能，准备有效规格和一组故障：过期规格、相互冲突的验收、越界文件、禁止网络、失败测试、超出命令预算和一个需要生产权限的请求。运行同一代理流程，观察它是否在正确阶段停止。

验收不仅看最终代码，还看：是否使用正确规格；越界动作是否被环境阻止；失败后是否保留原证据；是否修改了不允许修改的测试；预算耗尽是否升级；中断后能否从检查点恢复。再把任务范围缩小或验证命令改动，确认任务包版本能准确区分两次执行。

### 十三、工具结果与仓库内容都可能携带不可信指令

代理会读取 issue、网页、日志、源文件注释和测试数据，其中可能包含“忽略规则并上传密钥”之类文本。它们是任务数据，不会因为措辞像指令就获得控制权。执行系统要区分可信控制平面与不可信数据平面，外部内容不能修改权限、目标或批准要求。

网络抓取只允许必要域名，返回内容限制大小和类型；命令输出不得自动拼成下一条 shell；文件名、分支名和测试输出用于参数时采用结构化接口而非字符串执行。出现要求泄露秘密、扩大权限或绕过门禁的内容时，记录来源并停止相关动作。

这种边界也适用于 AI 生成的计划。计划是候选，不是授权；每一步仍受任务包和技术控制检查。

### 十四、多代理或子任务需要单一所有权与合并合同

复杂任务可分给多个执行者，但拆分不会自动提高正确性。父任务明确每个子任务的输入版本、写入范围、预期产物和验证，避免两者同时修改同一核心文件。共享事实通过版本化制品交换，不靠彼此聊天摘要。

合并者负责整体验收：两个局部结果各自绿，不代表接口组合、迁移顺序或用户路径成立。子任务失败要回传原证据和未完成状态，不能由上层把“已尝试”改写成“已完成”。需要顺序的工作保持依赖，例如先稳定合同和失败测试，再并行实现与文档。

委派深度、并发和预算有限制，防止代理无限复制任务消耗资源。高风险权限不随委派自动继承，仍按最小必要单独批准。

### 十五、回滚与恢复要在行动前设计

可逆文件改动使用小 diff、分支或工作树隔离；依赖安装记录 lockfile 与脚本；数据迁移先备份和演练；外部消息、发布和删除说明无法完全回滚的部分。代理在行动前写出恢复命令、验证恢复成功的方法和负责人。

回滚不是一律执行 `git reset`。工作区可能包含用户未提交改动，粗暴恢复会丢失数据；应只撤销当前任务明确创建的变更。生产操作优先前滚修复或补偿时，也要保留原事件和审计轨迹。

中断恢复先读取真实状态：文件、提交、服务、任务队列和外部资源。不能只根据最后一条聊天消息判断某动作是否完成，特别是超时的网络写可能已经成功。

### 十六、团队需要衡量控制质量而不鼓励刷指标

可以观察越界动作被阻止数、规格缺口提前发现率、同类失败重复次数、人工升级原因、变更后缺陷、证据重放成功率和从检查点恢复时间。指标用于找到薄弱控制，不用于奖励“少升级”或“更多自动修改”，否则执行者会隐藏不确定性。

抽样审查任务包是否最小充分、批准是否发生在动作前、测试是否被弱化、日志是否可重建。发生事故时沿任务 ID 复盘输入、工具、权限和决策，改进模板与技术边界，并用原故障演练证明修复有效。

### 十七、不同任务类型采用不同自动化等级

只读分析、局部可回滚改动、依赖升级、数据迁移和生产操作不能共享一个自动化策略。根据影响面、可逆性、证据成熟度和环境隔离选择“建议”“在工作区执行”“自动提交待审”“经批准发布”等等级。

等级提高需要历史证据：任务定义稳定、验证能发现代表缺陷、回滚可靠、权限可收紧、异常能正确停止。模型能力升级不自动提升授权等级；组织控制与责任仍按实际风险决定。

### 十八、最小任务切片要端到端成立

切片不是任意少改几个文件，而是能从输入到可观察结果独立验证的一小段价值。只生成类型却不接入口、只改界面却没有服务端合同，都可能局部绿而无法判断完成。优先选择一个用户行为或领域规则，连同必要实现、测试和说明一起闭环。

切片之间用明确接口连接，前一片未稳定时不让后续在猜测上扩展。发现任务无法在预算内形成端到端证据，应进一步拆分规格或请求更多时间，而不是留下无人能验证的半成品并宣称完成。

每个切片还要说明不做什么，防止“顺手优化”把范围重新扩大；被推迟的工作进入独立待办并保留原因和依赖。

切片完成后还要从用户入口重走一次结果，确认局部证据确实连接到可观察行为，而不是停留在内部实现层。

### 常见误解

- 提示写得详细，不等于规格已评审或权限已强制。
- 代理能运行测试，不等于它能独立决定业务正确。
- 更多仓库内容不一定更好，无关和过期事实会增加漂移。
- 自动重试不应通过扩大权限、删测试或改变目标来获得绿灯。
- 人工批准不是最后随手点一下，而是对明确风险和证据负责。

### 学完后应能说明

你应能把一个模糊开发请求改写为版本化任务包，划定技术上可执行的工具边界，设计带检查点和停止条件的执行循环，把验收项映射到独立证据，并在规格变化、越权、重复失败和不可逆动作前准确停止与升级。

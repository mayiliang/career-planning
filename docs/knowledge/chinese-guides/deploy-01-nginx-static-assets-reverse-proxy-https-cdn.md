# Web 部署与边缘交付知识点讲义

## DEPLOY-01 Nginx、静态资源、反向代理、HTTPS 与 CDN 缓存

Web 应用部署的核心不是“把 dist 目录复制到服务器”，而是让浏览器、边缘节点、Nginx、应用服务和旧标签页在版本变化时仍对每类请求做出一致决定。入口 HTML、带哈希资源、运行时配置、API 和用户上传文件具有不同的可变性与安全边界；若把它们交给一条通用 location 和一组缓存头，最常见结果不是立即报错，而是某些用户长时间拿到互相不兼容的版本。本讲从请求路径开始，建立静态资源、代理、TLS、CDN、回滚和验证的完整交付模型。

### 学习前先确认

- 直接前置：[LINUX-02 进程、端口、日志与网络诊断](../chinese-guides/linux-02-process-port-log-network-diagnostics.md#linux-02)。本讲需要能够辨认监听端口、进程身份、DNS、连接、状态码和服务日志之间的因果关系。

### 一、先画清请求从浏览器到上游的路径

一次请求可能经历浏览器 DNS 与缓存、递归解析、CDN、负载均衡、Nginx、应用进程和下游服务。每一层都可能返回响应、改写头或缓存内容，因此“服务器文件存在”并不等于用户取得它。排障时要记录最终 URL、解析 IP、TLS 证书、响应头、缓存状态、上游地址和请求 ID，避免把任意一层的 200 当成端到端正确。

Nginx 常同时承担静态文件服务器和**反向代理（Reverse Proxy）**。静态请求由它从明确目录读取；API 请求被转发到内部上游；前端路由在文件不存在时才回退入口 HTML。三种行为必须由不重叠的路径规则表达。若 `/api/orders` 被 SPA 回退吞掉，浏览器会得到状态 200 的 HTML，前端却在解析 JSON 时失败，真正的上游错误也被隐藏。

先建立路径表：外部路径、资源类型、处理层、允许方法、缓存策略、最大请求体、超时和失败响应。路径表比一段看似工作的配置更容易评审，也能发现 `/api` 与 `/api/`、大小写、编码斜杠和静态目录穿越等边界。

### 二、静态资源要按可变性分类

入口 HTML 是版本导航，它告诉浏览器当前需要哪些 JS、CSS 和配置，通常需要短缓存或每次重新验证。内容哈希资源的 URL 随内容变化，可以设置很长的有效期和 `immutable`，因为旧 URL 永远对应旧内容。没有哈希的 `app.js` 若长期缓存，发布后相同 URL 指向新内容，缓存层就无法判断何时更新。

图片、字体和媒体也要看命名策略。带内容摘要的公共资源可长缓存；用户头像等同 URL 会更新的对象需要版本查询或重新验证；含授权数据的下载不能因为扩展名像静态文件就进入公共缓存。运行时配置通常比代码更频繁变化，应独立命名、限制缓存，并对字段兼容做版本控制。

MIME 类型和 `nosniff` 是交付合同的一部分。JS 返回 HTML、字体类型错误或压缩文件带错 `Content-Encoding`，都会造成浏览器拒绝。服务器的默认类型表不能替代对主要资源的响应头检查。

### 三、SPA 回退只属于前端导航

SPA 深链刷新时服务器找不到真实文件，需要回到 `index.html`，由前端路由解析路径。规则应先尝试精确文件和目录，只对约定的前端导航空间回退。API、健康检查、上传、WebSocket、静态资源和 `.well-known` 等路径必须在回退之前明确处理。

回退还要保留正确状态。不存在的静态 chunk 不应返回入口 HTML 的 200；否则动态导入会报告语法错误而非清晰 404。未知前端路由是否返回 200 由产品和 SEO 决策，但 API 的 401、403、404 和 5xx 绝不能被页面覆盖。

验证时不只打开首页。直接请求嵌套路由、真实静态文件、不存在静态文件、API 成功与失败、带尾斜杠路径和编码参数，核对状态、类型、缓存头和响应体摘要。浏览器页面正常只能证明其中一条路径。

### 四、代理必须保存真实请求语义

代理上游时要明确 Host、原始协议、客户端地址和请求 ID。应用生成绝对链接、判断安全 Cookie 或记录来源时依赖这些信息；盲目信任来自公网的 `X-Forwarded-*` 也会被伪造，因此边缘应覆盖而不是原样透传外部值。多层代理需要约定可信跳数。

连接、读、写和总请求超时表达不同阶段。上传大文件、普通 JSON API、长轮询和流式响应不能共用一个随意的超时。超时发生后 Nginx 返回的网关错误要有请求 ID，上游也应收到取消或在幂等边界内完成；客户端重试不能把未知结果变成重复写入。

缓冲可以保护慢客户端和上游，但会改变流式语义。Server-Sent Events 或逐块输出需要关闭不合适的代理缓冲并处理连接保活；WebSocket 需要升级头和超时策略。不要为“实时”全局关闭缓冲，那会增加内存、连接和慢客户端风险。

### 五、TLS 建立的是身份与加密边界

**传输层安全（Transport Layer Security）**让客户端验证访问域名对应的服务器身份，并加密传输。证书必须覆盖域名、链条完整、在有效期内且私钥受保护。服务器能在 443 监听并不代表客户端验证成功；错误中间证书、SNI 配置或系统时间都可能只影响部分客户端。

HTTP 应受控跳转 HTTPS，避免方法和请求体被意外改变。HSTS 只有在所有相关子域都真正支持 HTTPS、证书续期和恢复路径成熟后再扩大范围；错误的长期 HSTS 会把配置失误变成长时间不可访问。TLS 套件和协议版本遵循当前平台建议，不应复制多年未审查的“加固片段”。

证书续期是运行流程而不是一次安装。记录颁发者、域名、到期时间、续期账号、验证方式和负责人；在到期前多阶段告警，并实际验证续期后进程重新加载了新证书。测试环境也要覆盖续期和回退，而不是等生产首次执行。

### 六、安全头必须与应用能力匹配

内容安全策略、HSTS、`X-Content-Type-Options`、Referrer Policy 和权限策略可以减少攻击面，但配置需要理解应用来源、嵌入、Worker、字体和 API。直接复制极严 CSP 可能让页面白屏，放宽到 `unsafe-inline` 又失去主要价值。先以报告模式收集真实依赖，再收敛来源并建立违规告警。

头部可能由 CDN、Nginx 和应用多层设置。重复或互相矛盾时浏览器的实际行为未必符合任何单层配置。用最终公网响应验证，而不是只看 Nginx 文件。错误页、重定向和缓存命中也要带必要安全头。

CORS 不是让接口“更安全”的通用开关。它约束浏览器读取跨源响应，不能替代服务端认证授权；允许凭据时不能使用任意来源。预检的缓存和失败也要纳入代理与 CDN 路径，不要把 OPTIONS 全部无条件返回成功。

### 七、缓存由多个层共同决定

浏览器 HTTP 缓存、Service Worker、CDN 和 Nginx 代理缓存各有键、有效期和失效机制。`Cache-Control` 的 `max-age` 面向客户端，`s-maxage` 可面向共享缓存；`no-cache` 表示使用前重新验证，不等于不存储；真正敏感内容通常需要 `no-store` 并防止共享缓存。

ETag 或 Last-Modified 支持条件请求，但验证器必须对应实际表示。压缩、语言、设备或认证差异可能通过 `Vary` 进入缓存键；漏掉维度会把错误版本甚至其他用户内容复用出去，维度过多则导致命中率骤降。缓存认证响应前要有明确隔离策略，默认不要共享。

**内容分发网络（Content Delivery Network）**把可缓存响应放到靠近用户的边缘。它减少距离和源站压力，却增加传播、键和失效层。Age、Via、缓存状态、PoP 和对象版本是排障证据。源站已更新而某地区仍旧，往往是边缘规则或失效范围问题，不应反复重启应用。

### 八、缓存失效要与版本策略配合

**缓存失效（Cache Invalidation）**是让已存对象不再被继续使用。带内容哈希资源通常无需主动失效，新版本使用新 URL；入口 HTML 和运行时配置才需要短 TTL、重新验证或精确 purge。全站清缓存简单但会制造源站尖峰，并掩盖键设计问题。

失效请求成功不表示所有边缘已经收敛。CDN 可能异步传播，需要查询状态并从不同区域核对响应。版本发布记录应保存失效对象、请求 ID、发起人和完成时间。紧急撤回敏感内容时要有比普通 TTL 更强的确认方式。

不要删除旧哈希资源来“强制升级”。旧 HTML、离线页面和长时间打开的标签页仍可能引用它们。保留与回滚窗口一致的旧资源，直到入口、Service Worker 和监控证明旧版本使用量降到可接受范围。

### 九、压缩和图片优化也有正确性边界

文本资源可按客户端协商 gzip 或 Brotli，响应要带正确 `Content-Encoding`，缓存键需要区分编码。已压缩图片、视频和归档再次压缩收益有限却增加 CPU。动态压缩级别要结合延迟与服务器负载，不能只追求最小字节。

图片格式、尺寸和质量应与布局及设备能力匹配。响应式图片让浏览器选合适候选，CDN 转换需要把源图版本、宽度、格式和质量纳入键。若只按 URL 缓存第一次设备的转换结果，后续用户会拿到错误尺寸或格式。

字体要控制子集、跨源和缓存，并准备回退以减少不可见文本和布局偏移。资源优化的目标是实际用户体验和传输成本，不是让服务器输出某个漂亮压缩比。

### 十、发布时保持入口和资源的原子关系

上传静态资源后再切换入口，能保证新 HTML 出现时引用资源已经可取。若先替换入口、资源仍在传播，新用户会立刻白屏。对象存储或发布目录可以用版本前缀，最后原子切换指针；每版清单记录入口摘要和全部资源。

回滚时切回上一入口，并确认上一资源仍保留。CDN 对 HTML 的缓存可能让一部分用户继续看到新入口，因此要结合失效和观察。API 版本与运行时配置也要兼容旧入口，静态切回不能修复已经不兼容的后端。

旧 chunk 加载失败可以提示刷新，但要区分网络瞬断、权限失败和版本撤换，避免无限刷新循环。保存表单草稿、只刷新一次并记录当前/目标版本，比直接调用 `location.reload()` 更安全。

### 十一、Nginx 配置要模块化且可验证

配置按全局、站点和 location 分层，重复规则抽成受控片段，但不要用复杂 include 隐藏最终行为。正则 location 的优先级、前缀匹配、`root` 与 `alias` 差异容易造成意外文件映射；每次改动都查看展开后的完整配置，并运行语法检查。

进程重载通常允许旧 worker 完成连接、新 worker 使用新配置，但仍要观察失败和版本。配置文件通过语法不代表上游可达、证书可读、静态目录权限正确或 DNS 能解析。预发布环境应使用等价拓扑和真实响应探针。

访问日志记录请求时间、上游时间、缓存状态、版本和请求 ID；错误日志级别足以诊断但不泄露凭据。日志轮转、磁盘上限和保留属于部署设计，磁盘被日志写满会让原本健康的代理突然失败。

### 十二、故障要按层定位而不是猜配置

502 通常表示代理没有得到合格上游响应，可能是连接拒绝、上游提前关闭、协议或 DNS 错误；504 更偏向等待超时。先用请求 ID关联访问日志、错误日志和上游日志，再检查端口、协议、超时阶段和资源压力。反复增加超时只会让用户等待更久。

静态 404 要确认请求 URI、location、文件映射和发布清单；403 检查目录遍历权限、进程用户和安全策略；证书错误检查域名、链、时间和实际提供证书。CDN 命中时源站日志可能根本没有请求，必须先判断响应来自哪一层。

故障注入比纸面检查可靠：停止上游、返回慢响应、让 API 404、保留旧 HTML、撤下一份旧 chunk、提供错误证书链和不一致压缩，观察系统是否给出正确状态、告警和恢复动作。

### 十三、验证交付必须覆盖新旧客户端

建立响应矩阵：无缓存新浏览器、热缓存浏览器、缓存旧 HTML 的标签页、深链刷新、CDN 命中与绕过、API 成功和失败。对每项记录状态、类型、缓存头、Age、ETag、内容摘要和版本。页面截图只能作为表现证据，不能替代头和日志。

验证 TLS 时使用正常浏览器和独立客户端检查证书链、域名和协议；验证代理时比较外部与内部响应并确认转发头；验证缓存时至少做冷请求、热请求、重新验证和失效后请求。任何包含 Cookie 或 Authorization 的抓包在保存和分享前必须脱敏。

发布后持续观察旧资源 404、动态导入失败、API 返回 HTML、证书剩余时间、缓存命中异常和区域差异。只有新旧入口都能完成关键用户任务，才能说明交付兼容窗口成立。

### 十四、学完后应能设计完整边缘合同

你应能把一个 Web 应用拆成入口 HTML、哈希资源、配置、API 和用户文件，为每类对象定义路径、类型、缓存、安全与失败语义；能解释代理头、超时、缓冲和 TLS 身份边界；能设计 CDN 键、精确失效、旧资源保留和入口切换顺序。

选一个含前端路由和 API 的站点，实际验证首页、深链、未知 chunk、API 4xx/5xx、旧入口、证书和 CDN 命中。然后演练一次新版本发布与回退，证明不是“文件复制完成”，而是每层都返回与资源类型相符的状态和版本，用户任务在缓存差异下仍可恢复。

继续查证可参考 [Nginx 反向代理模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)、[MDN HTTP 缓存](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/Caching)与 [MDN TLS](https://developer.mozilla.org/zh-CN/docs/Web/Security/Transport_Layer_Security)。

# 框架选型、生态生命周期与跨框架迁移知识点讲义

## ARCH-05 框架选型、生命周期与跨框架迁移

框架选型不是“React 还是 Vue”的偏好辩论，也不能只按招聘热度、GitHub star 或单个 demo 帧率决定。框架、元框架、组件技术和组织能力处于不同层次，会共同影响渲染、数据、部署、无障碍、安全、团队协作与十年维护。成熟决策在同一业务约束下比较维持现状和真实候选，用原型验证最大风险，为支持期、双运行、回滚与退出负责。

### 学习前先确认

- 直接前置：[ARCH-03 渐进迁移、Strangler 与兼容层](../chinese-guides/arch-03-progressive-migration-strangler-compatibility.md#arch-03)用于理解切片、双运行和回滚；[ARCH-04 技术债识别、排序与偿还治理](../chinese-guides/arch-04-technical-debt-prioritization-governance.md#arch-04)用于理解生命周期、升级与退出成本。两者分别承担迁移和长期治理基础。

### 一、先分清选择的层次

UI library 提供组件渲染与状态抽象；router/data library 解决导航和远端数据；meta-framework 规定服务器渲染、构建、路由与部署；design system 规定视觉和交互合同；Web Components 提供浏览器级封装与互操作。把这些都叫“框架”会比较错层。

先画现有产品需要的层：页面类型、渲染位置、数据/身份、部署、设计系统、原生容器、测试和团队边界。候选只为明确层解决问题，避免因选择组件库顺手重写后端和部署。

同一 UI 框架在不同元框架或自建栈下成本完全不同。评测记录确切组合与版本，而不是只写品牌名。

### 二、从产品形态与质量场景出发

内容站、电商结算、内部后台、实时编辑器、嵌入式组件和离线应用需要不同渲染、交互和更新。列出核心任务、SEO、首屏、离线、实时、可访问性、浏览器、部署、团队和法规约束。

把约束写成可测场景：目标设备的 LCP/INP、服务器失败降级、键盘/读屏任务、发布频率、故障恢复、数据地区和包体。候选在同一场景测试，不能给喜欢的方案更多优化时间。

维持现状是正式候选。若现有栈能通过局部治理满足目标，迁移成本可能高于收益。只有明确问题与目标，选型才可复查。

### 三、Total Cost of Ownership 超过开发速度

**总拥有成本（Total Cost of Ownership）**包括开发、培训、招聘、构建、CI、运行资源、监控、值班、安全、升级、双运行、迁移、供应商和退出。初始页面开发快，只是生命周期的一小段。

使用真实任务测两周维护、缺陷修复和发布，不只看脚手架时间。团队已有能力是现状成本，但不能无限合理化低质量；新技术培训与招人是迁移成本，也不应被夸大阻止必要演进。

成本估算给范围、时间和敏感变量。SSR 可能增加服务器与运维但改善内容任务；客户端方案可能省服务器却伤害低端设备。将成本与用户结果一起比较。

### 四、Support Matrix 记录生命周期承诺

**支持矩阵（Support Matrix）**列出框架、元框架、运行时、构建器、TypeScript、浏览器、Node、关键插件、设计系统和部署平台的可支持组合。它连接官方支持期与组织实际测试，防止各应用自由升级成不可维护网格。

记录当前、允许、弃用和阻断版本，owner、升级窗口和 EOL。官方声明是输入，项目还需验证 peer、插件和自建扩展。没有维护者的关键插件会缩短整个组合寿命。

矩阵不是永久冻结。定期升级小步验证，跟踪弃用和安全公告。停止维护、许可证/治理变化、核心插件断裂或团队无法值守触发复查与退出。

### 五、生态健康看治理和替代能力

评估发布流程、维护者数量、RFC/弃用、漏洞响应、企业/社区结构、文档、迁移工具和插件质量。Star 和下载量只说明关注或默认使用，不证明未来支持与项目适配。

核心能力依赖第三方插件越多，组合风险越高。检查身份、路由、数据、国际化、可访问、测试和部署是否由稳定核心或可替换接口承担。插件锁定内部 API 会扩大升级债。

组织也要有 owner。即使生态健康，内部无人理解构建、SSR 或故障恢复，仍是高风险。原型应包含运维与升级，不只功能开发。

### 六、验证性原型针对最大未知

为同一真实垂直切片实现候选：登录、列表/详情、表单错误、权限、数据加载、可访问性、测试和部署。避免 todo demo，因为它不会暴露缓存、身份、SSR、设计系统和恢复。

原型预先定义假设和指标，限制时间与优化。测冷/热加载、包体、解析执行、交互、服务端成本、错误恢复、键盘/读屏、测试和开发流程。保存配置、版本与原始结果。

原型代码默认可丢弃。若要进入生产，补安全、测试、owner 和迁移合同。失败原型是有效证据，不通过包装隐藏。

### 七、框架能力、元框架能力与组织能力分开

自动路由、数据缓存、SSR、边缘部署或服务器动作可能来自元框架而非 UI 框架；成熟设计系统、平台和工程规则可能来自组织。把某一层收益归给另一层，会选错替代。

建立能力地图：谁提供、谁配置、谁运维、能否替换、失败时谁处理。某候选缺少内建功能但有稳定可组合方案，未必劣于一体化；一体化降低组合成本但增加升级与退出耦合。

面试与招聘信号可以作为人才市场输入，不能覆盖用户、运行和生命周期证据。组织能力可通过培训和平台改善，是可变化变量。

### 八、可访问性与兼容性是硬门槛

对核心组件测试语义、键盘、焦点、读屏、缩放和语言；对目标浏览器、WebView、低端设备和弱网运行真实任务。框架默认行为可能帮助，也可能因自定义抽象被破坏。

比较 hydration、portal/teleport、路由焦点、错误边界和动态公告。自动扫描只是基础。设计系统适配要有视觉与行为契约，不能只实现 CSS token。

候选未通过硬门槛时，除非有可验证且成本可接受的补偿方案，否则淘汰。不要在最终选择后才计划“以后补无障碍”。

### 九、渲染与部署共同决定架构

CSR、SSR、SSG、流式和混合渲染影响缓存、身份、错误、成本和部署。候选框架能 SSR 不等于团队平台、数据和运维能安全交付。验证目标环境的冷启动、缓存键、区域、日志和回滚。

构建产物、server/client 边界和秘密需可解释。服务器组件或 server actions 等能力改变数据访问与部署边界，应独立评估安全和兼容。供应商专有适配要有可迁移层。

部署失败时核心任务如何恢复、旧客户端如何兼容、制品如何晋级进入原型。开发服务器顺畅不是生产证据。

### 十、Reversibility 设计改变方向的成本

**可逆性（Reversibility）**表示若假设失败，团队能在什么时间、数据损失和业务影响下停止、回滚或切换。它由边界、数据所有权、公共合同、部署和迁移切片决定，不是一句“可以重写”。

采用路由级切片、适配层、版本化 API 和独立制品，减少一次绑定。避免把业务规则写进框架全局对象或专有数据层，使退出需要重做全部核心。抽象也要有现实候选，不能为理论替换建立巨型通用层。

为关键退出路径演练：关闭新路由、恢复旧制品、处理新写数据、撤销供应商连接。不可逆数据变更需要 expand/contract 和备份。

### 十一、Dual-Run Period 是临时架构

**双运行期（Dual-Run Period）**是新旧框架同时服务产品的过渡阶段。它增加 runtime、包体、状态同步、设计系统、测试、发布和认知成本，因此必须有范围、预算、owner 和结束日期。

按路由/岛屿懒加载，避免所有用户下载两套框架。共享状态优先用 URL、服务端数据或版本化消息，不直接共享两种响应式 store。全局 CSS、事件、错误边界和 DevTools 有隔离策略。

指标包括新旧流量、重复依赖、包体、缺陷、交付时间和兼容层使用。只扩大新系统而不删除旧系统会使迁移成本永久化。

### 十二、跨框架组件要选择正确互操作边界

Web Components、iframe、运行时模块、服务端组合和设计 token 都是互操作手段，各有语义、样式、性能、身份和部署代价。选择最小必要边界，不因“标准”或“独立部署”自动胜出。

公共组件合同包含属性/事件、slot、表单、焦点、错误、版本和样式 token。复杂业务状态与数据获取不应塞进通用 UI 元素。跨框架事件采用稳定序列化和所有权。

验证 React/Vue/原生消费者、SSR/hydration、读屏和升级。适配器有支持矩阵和删除/长期 owner，不复制三套行为实现。

### 十三、迁移按垂直切片与闸门推进

选择代表但可控的页面，建立现状基线、路由开关、数据/身份合同、影子/小流量、监测和回滚。每片达到用户成功、性能、无障碍、错误和运维门槛才扩大。

数据库和 API 不因前端换框架随意重写；若确需改变，作为独立架构决定和迁移。框架迁移已经高风险，混入业务重构会难以归因。

每阶段删除旧路由、组件、依赖和配置。兼容层使用量下降到零并观察后再删。遇到门槛越界可暂停，而不是为期限调宽指标。

### 十四、结论有有效期与退出条件

ADR 记录约束、候选、原型、TCO、支持矩阵、风险、决定、异议、迁移和复查。退出条件可包括停止维护、关键插件不可用、包体/性能超预算、安全响应不足、团队能力丧失或供应商变化。

每次大版本与年度路线复核实际结果。若当初预测错误，更新模型而不是掩盖。流行框架也会过时，当前维持现状也可能因业务变化不再合理。

用同一订单/结算流程回放候选和迁移，保存版本、构建分析、可访问结果、故障恢复和团队工时。只有优缺点表没有运行证据，不能支撑长期决定。

### 十五、用决策矩阵但不让分数伪装事实

矩阵先标硬门槛，再对软 driver 给权重和证据。每个格子写实测、估算或未知及来源，最后分数只用于发现差异，不自动决定。一个候选安全门槛不满足，不能靠开发体验高分抵消；大量 unknown 也不能按中位数填充。

邀请产品、平台、运维、安全、无障碍和实际开发者分别复核自己承担的后果，避免选择团队只优化熟悉度。出现权重争议时回到业务目标和责任 owner。保存未采用候选在什么条件下会胜出，为未来复查提供起点。

对同一原型重复测量和交叉实现，区分框架能力与实现者熟悉度。若候选团队多投入两周优化，要在证据中说明，不能把不对称投入当成天然优越。

### 十六、升级能力是选型的一部分

在原型中执行一次小版本和模拟大版本升级，观察 codemod、类型、插件、测试、文档和回滚。一个框架当前功能完整但每次升级需要冻结数月，会产生长期成本。官方迁移工具有帮助，仍需验证自定义扩展。

建立定期升级节奏、兼容测试和 canary，不从多年旧版直接跳到 latest。弃用先观测使用、迁移消费者、再删除。安全补丁无法及时吸收是重要退出信号。

升级责任不能只属于“有空的人”。框架组合有 owner、容量和供应商/社区信息来源；关键知识至少两人掌握。

### 十七、供应商和生态事故需要降级方案

registry 污染、关键包撤回、CDN/托管故障、许可证改变或维护者事件都可能影响框架栈。锁定制品、来源证明、内部缓存和已验证上一版本支持快速恢复，但不能无限停在脆弱版本。

托管元框架服务不可用时，确认能否迁移部署、导出缓存/数据、恢复 DNS 和保持身份安全。专有功能越深，退出实验越重要。不要等供应商事故发生才第一次阅读导出文档。

年度演练在隔离环境从锁文件重建、切换一个关键适配器并恢复旧制品。记录缺失文档、凭据和 owner，作为支持矩阵的一部分。

### 十八、决定也要照顾多产品与多团队现实

组织可以有推荐路径和有限例外，不必强迫所有产品同一框架。标准化能降低平台、招聘和运维成本，例外用于真实产品约束；每个例外有 owner、支持范围、到期和不向其他团队外溢成本的计划。

公共设计系统、身份、遥测和发布合同尽量框架中立，具体适配由版本化包承担。避免中央团队同时维护无限组合，也避免产品团队私自 Fork 核心库。支持矩阵明确哪些组合有服务级别。

通过迁移成本、问题响应和团队独立交付评估标准化是否创造价值，而非只看采用率。若推荐路径无法满足主要场景，应改进路径，不把所有偏离都归因团队不配合。

学完后，你应能区分选择层次，从产品质量场景建立包含现状的候选，用真实原型、TCO 与支持矩阵比较，设计可逆的双运行迁移并定义退出。框架选型的高级能力不是预测谁最流行，而是让产品在技术和组织变化中仍能安全演进。

# Web 可访问性知识点讲义

## A11Y-01 WCAG 2.2、无障碍测试与工程治理

可访问性不是页面完成后的“检查项”，而是界面合同的一部分：内容能否被感知，操作能否在不同输入方式下完成，状态变化能否被理解，组件能否在浏览器与辅助技术组合中保持稳定。初级开发者常从补 `alt`、跑一次自动扫描开始；高级工程师还要能把用户任务映射为规范要求、设计键盘与焦点协议、组合多类测试证据，并把一次修复变成持续治理。

### 学习前先确认

- 直接前置：[WEB-01 HTML 语义、表单与可访问性基础](../chinese-guides/web-01-html-semantics-forms-accessibility.md#web-01)。本讲会直接使用语义元素、可访问名称、表单标签和基础焦点规则；HTML 基础由该文独立解释。

### 一、可访问性讨论的是完成任务的能力

**可访问性（Accessibility）**关注不同视觉、听觉、行动与认知能力的用户，能否获取同等信息、执行同等操作并理解结果。它不等于某种残障专用模式，也不只服务屏幕阅读器用户。键盘受伤、强光下看屏幕、嘈杂环境中观看视频、网络或设备性能受限，都会暴露同一套设计是否依赖单一感官与单一操作方式。

评审一个界面时先写用户任务，例如“搜索课程并收藏”“读完错误信息后修正表单”“暂停正在生成的回答”，再列出完成任务需要的内容、操作、状态和恢复路径。若只按 DOM 元素逐个打勾，很容易得到“每个按钮都有名字，但整个流程仍走不通”的假通过。

### 二、WCAG 是可测试准则，不是一个总分

**Web 内容无障碍指南（Web Content Accessibility Guidelines, WCAG）**用 POUR 四项原则组织成功准则：可感知、可操作、可理解、健壮。A、AA、AAA 是符合级别，不是质量分数。某个页面通过若干 AA 准则，不等于整个产品永久“符合 WCAG”；符合性结论必须限定页面集合、完整流程、版本、依赖内容与测试环境。

把规范落到工程时，建立“用户风险—成功准则—实现合同—验证证据”的映射。例如：

| 用户风险 | 相关机制 | 可验证合同 |
| --- | --- | --- |
| 无法用键盘打开和关闭弹层 | 键盘、焦点顺序、焦点可见 | 打开后首焦点明确，背景不可进入，关闭后归还触发器 |
| 拖拽是唯一排序方式 | 拖动动作等价路径 | 提供上移/下移等不依赖拖动的单指针操作 |
| 流式文本不断打断读屏 | 状态消息与实时区域 | 视觉更新与语义通知分离，按可理解片段节制播报 |
| 放大后操作被固定区域遮住 | 重排、缩放、焦点不被遮挡 | 200%/400% 与窄视口仍可完成同一任务 |

WCAG 2.2 新增的焦点不被完全遮挡、拖动动作、目标尺寸、一致帮助、冗余输入和可访问身份验证等要求，体现了从“元素存在”走向“真实任务可完成”。工程师不必背诵所有编号，但必须知道怎样从用户障碍定位准则原文，并避免把旧版本经验当作当前要求。

### 三、浏览器同时维护 DOM 与无障碍树

页面源码形成 DOM，浏览器还会结合元素语义、CSS、ARIA 与状态计算 **无障碍树（Accessibility Tree）**。辅助技术主要通过这棵树理解名称、角色、描述、状态和值。一个元素在 DOM 中可见，不代表它一定出现在无障碍树中；反过来，视觉隐藏方法选择错误，也可能让本应隐藏的内容仍被播报。

可访问名称回答“它叫什么”，角色回答“它是什么”，状态和值回答“它现在怎样”。名称优先来自可见文字或 `<label>`，需要组合多个可见片段时用 `aria-labelledby`，补充说明用 `aria-describedby`。不要习惯性用 `aria-label` 覆盖清楚的可见文字，否则视觉用户与语音控制用户看到的名称可能和辅助技术获得的名称不一致。

开发者工具中的树快照能检查计算结果，却不能证明真实读屏器的措辞、停顿和导航体验。树是中间模型证据，不是最终用户测试的替代品。

### 四、原生语义提供行为、状态与平台适配

原生 `<button>` 同时提供可聚焦性、Enter/Space 激活、禁用状态和按钮角色。`<div role="button">` 只补角色，键盘行为、焦点、禁用和高对比度表现仍要自己实现。ARIA 的第一条工程原则是：存在合适原生元素时优先使用它。

ARIA 适合表达原生 HTML 无法充分描述的关系或状态，例如展开按钮的 `aria-expanded`、错误输入与错误文本的关联、动态结果数量的状态消息。ARIA 不改变业务行为，也不提供权限。给不可点击的节点加 `role="button"` 不会让它安全可用，给无权限按钮加 `aria-hidden` 也不会阻止请求。

自定义组合控件必须采用对应模式的完整键盘协议，不能只复制角色名称。若产品只需要一组普通操作按钮，就保留自然 Tab 顺序，不必为了“更高级”伪装成 ARIA menu 并承担方向键、Home/End、焦点管理等全部合同。

### 五、键盘设计先确定焦点的所有权

焦点不是一个彩色边框，而是浏览器把下一次键盘输入交给谁。每次打开、切换、删除或恢复界面都要回答三个问题：焦点从哪里来、操作期间可去哪里、结束后回到哪里。

模态对话框打开后，初始焦点应落在能理解当前任务的位置：短确认可放在主要按钮，含搜索或表单的面板通常放在标题后的首个输入。Tab 与 Shift+Tab 不应进入背景；Escape 和可见关闭按钮都能结束；关闭后回到仍存在的触发器。触发器被删除时需要定义邻近的安全落点，而不是让浏览器悄悄落到 `body`。

不要使用正数 `tabindex` 人工重排全页。它会把 DOM 顺序、视觉顺序与键盘顺序分裂，响应式布局后尤其难以维护。可编程聚焦但不参与常规 Tab 的标题可临时使用 `tabindex="-1"`，并在聚焦目的完成后保持语义清楚。

焦点指示器必须可见，且不能被 sticky header、cookie banner 或浮层完全遮挡。测试时既看 CSS，也用键盘真实移动；只截图一个聚焦按钮无法证明整个顺序正确。

### 六、指针、触控和拖拽需要等价路径

拖拽适合直接操纵，但不能成为唯一方式。为排序项提供“上移/下移”按钮，让触控、鼠标、键盘和语音控制都能触发同一个领域函数；移动后保留合理焦点，并用节制的状态消息说明新位置。

目标尺寸不只是设置 `min-width`。相邻目标的可点击区域、间距、缩放后的实际几何和覆盖层都要检查。图标按钮需要可见或可访问名称；扩大伪元素点击区时不能覆盖旁边链接。复杂画布手势还要提供列表、表单或数值输入等非手势路径。

键盘快捷键只能作为增强，不能代替可发现的按钮。单字符快捷键还可能与语音输入冲突，需要关闭、重映射或仅在控件聚焦时生效。

### 七、动态内容要区分可见更新与语义通知

**实时区域（Live Region）**让辅助技术在焦点不移动时获知内容变化。它是通知建议，不是可靠消息队列：浏览器与读屏器可能合并、延迟或忽略连续更新。因此不能把每个动画帧、每个 token 都塞进 `aria-live`。

流式回答应把视觉正文与播报缓冲分离。视觉区域可连续追加，隐藏的 `polite` 通知区按句子、段落或时间窗口发布可理解片段；完成、失败和取消是独立状态。生成过程中不抢焦点，提供暂停或停止。用户主动触发且必须立即知道的严重错误才谨慎使用 assertive，滥用会中断正在阅读的内容。

加载指示、保存完成、搜索结果数和表单错误的通知目的不同。持续显示的正文不要同时被多个 live region 重复播报；错误摘要与字段错误也应避免双重宣告。真实读屏记录需要包含操作步骤和实际播报，而不是只断言 DOM 属性存在。

### 八、图片、音视频与生成内容需要等价信息

替代文本表达图片在当前任务中的意义，而不是逐像素描述，也不重复“图片”。纯装饰图片使用空 `alt`，信息图需要在附近提供结构化数据或长描述。AI 生成的替代文本只能作为草稿，内容责任人要校正事实、语境与敏感信息。

视频需要准确同步字幕；只有音频的信息需要转写，重要视觉动作还需要音频描述或正文说明。自动字幕可以降低起稿成本，但人名、术语、数字与说话人经常出错，不能未经审核就当作合格证据。

画布、图表和生成式界面要提供语义替代与人工操作路径。把整张图命名为“销售图表”仍无法让用户获得趋势、异常和数据点。高级实现应让视觉、表格、摘要和下载数据来自同一数据模型，减少内容漂移。

### 九、缩放、重排、颜色和运动偏好都是合同

在 200% 文本缩放、400% 页面缩放和约 320 CSS px 宽度下检查核心任务。内容可以变成长页面，但不能被双向滚动、固定高度、绝对定位或溢出裁剪破坏。浏览器缩放与 CSS media query 不完全等价，所以必须真实操作。

颜色对比需要检查普通文本、大文本、非文本控件、焦点和状态。不要只靠颜色表达错误或选中；增加文字、图标形状与程序化状态。forced-colors 下自定义背景和阴影可能消失，应使用系统颜色和真实边框验证。

`prefers-reduced-motion` 不是把所有过渡时间粗暴设为极小。先区分装饰运动、空间方向提示和状态反馈：删除非必要平移缩放，为必要关系提供淡入或立即更新，保证内容不会因为动画被禁用而永远透明。自动播放、闪烁和视差还要分别处理暂停、频率与触发风险。

### 十、自动测试、树检查、键盘和读屏各证明一部分

没有单一工具能证明完整可访问性：

| 证据 | 擅长发现 | 不能单独证明 |
| --- | --- | --- |
| axe/Lighthouse 等规则 | 缺名称、无效 ARIA、部分对比度和表单关系 | 任务是否合理、替代文本是否准确 |
| 浏览器无障碍树 | 计算名称、角色、值和树映射 | 真实读屏器的完整交互 |
| 键盘任务测试 | 顺序、激活、关闭、归焦、焦点可见 | 各读屏组合的表达 |
| 屏幕阅读器抽查 | 实际导航、播报、状态消息 | 所有平台和所有流程 |
| 缩放与视觉检查 | 重排、遮挡、目标尺寸、强制颜色 | 语义和业务恢复 |

测试记录应包含页面版本、浏览器、操作系统、辅助技术版本、步骤、预期、实际和制品。自动化适合守住组件合同与关键路径，人工测试负责判断任务和语言是否可理解。两者不是竞争关系。

### 十一、组件级合同让问题在复用前暴露

设计系统中的交互组件应公开：语义与名称来源、键盘模型、焦点进入和退出规则、禁用与只读差异、状态通知、缩放与用户偏好表现、自动测试和人工验证基线。只有颜色和尺寸的视觉稿不足以定义一个可用组件。

组件示例页面要覆盖长文本、缺失数据、错误、加载、RTL、高对比度和缩放。破坏性改动不仅是 TypeScript 属性变化，也包括可访问名称、DOM 顺序、焦点落点或键盘手势改变。版本升级时把这些合同纳入迁移说明。

框架封装不能抹掉平台语义。React/Vue 组件最终仍生成 HTML、事件和焦点行为；传送门、Portal 或 Shadow DOM 可能改变 DOM 所有权与事件路径，必须在真实渲染结果上验证。

### 十二、治理把偶然修复变成持续能力

建立严重度与发布策略：核心登录、支付、学习流程完全不可操作属于阻断；错误不可感知、对话框无法退出等严重缺陷默认阻断；局部目标尺寸或次要页面重排进入明确迭代。严重度依据受影响任务与替代路径，不依据修复代码行数。

例外记录必须写清准则、受影响用户和任务、临时替代、负责人、批准人、创建与到期日、复验条件。到期后自动重新评审，不能无限续期。第三方组件造成的问题也需要 owner 和退出路线，不能用“供应商问题”消除产品责任。

CI 可阻断新增严重自动规则失败、组件键盘合同回归和关键流程失败；周期性人工审计、真实用户反馈和生产缺陷趋势补上自动化盲区。指标应关注未解决阻断缺陷、修复时长、重复问题和覆盖流程，而不是追求一个好看的总分。

### 十三、从单页走向产品级成熟度

成熟团队会在需求阶段写可访问验收、设计阶段确定名称和焦点、开发阶段复用合格组件、评审阶段检查用户任务、测试阶段组合证据、发布后追踪真实缺陷。培训和文档应让产品、设计、内容、开发、测试共同理解责任边界。

法律合规会受地区、产品和组织承诺影响，本讲不提供法律结论。工程上可以诚实说明采用的 WCAG 版本、目标级别、已测试范围、已知例外和联系方式，避免“100% 无障碍”这类无法持续证明的承诺。

### 学完后应能说明

你应能从用户任务建立 WCAG 映射，解释 DOM 与无障碍树、名称/角色/状态、键盘与焦点、实时通知、媒体等价内容和用户偏好的机制；能说明自动扫描的边界，用多类证据验证真实流程，并设计组件准入、缺陷严重度、例外到期和持续回归，使可访问性成为工程系统而不是一次活动。

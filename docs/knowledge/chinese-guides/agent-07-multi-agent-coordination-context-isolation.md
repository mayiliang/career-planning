# 多 Agent 协作、上下文隔离与冲突处理知识点讲义

## AGENT-07 多 Agent 拆分、协调、隔离与合并

多 Agent 并不是同时开更多模型就会更聪明。任务拆分错误会重复工作，权限共享会扩大攻击面，多个执行者会争写同一资源，最终汇总模型还可能把矛盾结果强行拼成“完成”。真正有价值的多 Agent 系统要让子任务边界、输入、能力、产物、完成证据与冲突处理都可验证；只有可以独立推进且合并收益大于协调成本时，才值得并行。

### 学习前先确认

- 直接前置：[AGENT-01 Agent 循环、规划、停止与恢复](../chinese-guides/agent-01-loop-planning-stopping-recovery.md#agent-01)，用于理解单个任务的状态机、预算、检查点和失败恢复。间接前置不重复列出。

### 一、Multi-Agent System 是多个受控执行域

**多 Agent 系统（Multi-Agent System）**由一个协调者和若干具有独立任务状态、上下文、能力与结果契约的执行单元组成。Agent 可以由不同模型、规则、工具或人工承担；关键是职责和边界，不是拟人化角色名称。

协调者负责拆分、依赖、调度、预算、权限、冲突与最终验收。子 Agent 只对其任务信封负责，不能自行扩大目标或再获取全部根任务权限。共享事实通过受控存储或消息传递，不靠所有人共享一段无限聊天。

系统必须允许退化为单 Agent。若拆分后没有独立性、验证标准或速度/质量收益，多 Agent 只是增加成本和失败点。

### 二、先画依赖图再决定并行

把目标分解为有明确输入与输出的节点，边表示必须先完成的依赖。只有没有共享可变资源、结果能独立验证且不会改变彼此前提的节点才安全并行。

研究多个互不相关来源、检查不同模块和运行独立测试通常可并行；设计同一个数据模型、连续编辑同一文件、依赖前一步结果的迁移通常需串行或分阶段。推测“应该不冲突”不是调度依据。

计算协调开销：上下文复制、结果审查、冲突解决、模型费用和等待尾延迟。小任务在单个 Agent 内完成可能更快、更可靠。

### 三、Task Envelope 定义子任务契约

**任务信封（Task Envelope）**是交给子 Agent 的结构化契约，包括 objective、scope、输入引用、禁止事项、能力、预算、依赖、期望产物、完成证据、截止和父任务版本。

“检查安全性”太模糊；应说明检查哪些文件/接口、只读还是可修改、采用哪些威胁边界、输出问题清单还是补丁、什么算完成。信封引用源数据版本，防止子任务在过期快照上工作。

子 Agent 返回 status、artifacts、claims、evidence、unresolved、sideEffects 和 resourceVersions。自然语言总结供人阅读，结构化字段供协调者验收。

### 四、Context Isolation 遵循最小必要

**上下文隔离（Context Isolation）**让每个子 Agent 只获得完成当前任务所需的事实、数据和权限，并保留来源与租户边界。它降低 token、干扰、隐私泄露和提示注入横向传播。

不要把完整根会话、所有用户文件、所有工具凭据复制给每个 Agent。提供裁剪后的任务事实、只读引用和按能力签发的短期 token。子 Agent 读取新资源仍经过授权与范围检查。

外部文档中的指令保持不可信数据身份，不能通过子 Agent 总结后升级为父系统规则。返回结果也按外部输入验证。

### 五、共享状态需要单一事实来源

子 Agent 的本地上下文不是全局事实。共享产物放入版本化 artifact store、数据库或仓库，写入采用所有权、锁、分支或乐观并发。协调者通过明确版本取得结果。

可以为每个任务分配独立工作区/分支，最终由集成步骤合并。若必须共同编辑同一对象，分区字段或指定单写者。聊天广播不能代替并发控制。

共享黑板模式也要有 Schema、ACL、来源、有效期和冲突规则。任何 Agent 都能随意覆盖“最终结论”的黑板会迅速失真。

### 六、消息传递至少一次且可去重

任务分派、结果提交和取消可能重复或乱序。消息带 taskId、attempt、parentVersion、messageId 和序号；接收端持久去重。相同任务重试复用逻辑 stepId，但新的替代方案使用新 attempt。

协调者收到迟到结果时检查任务是否仍接受、依赖版本是否匹配。已取消或已替代的结果可保留审计，不能覆盖当前产物。Agent 失联通过租约和心跳发现，不马上把未知执行当未开始重派副作用。

大产物用受权引用传递，消息只包含哈希和元数据。避免复制敏感全文到队列。

### 七、能力隔离限制爆炸半径

每个 Agent 使用任务特定工具白名单、资源范围、速率和费用。负责阅读文档的 Agent 不需要部署权限，负责写测试的 Agent 不需要生产凭据。协调者自身也不自动拥有所有下游秘密。

委派不能扩大父授权：子能力是父能力与任务策略的交集。子 Agent 再委派时继续缩小，并限制深度、数量和总预算，防止递归生成无穷团队。

高风险动作仍经过独立审批，不能以“多数 Agent 同意”替代有权限的人。来自多个模型的相同建议不是授权证据。

### 八、Conflict Arbitration 处理不一致结果

**冲突仲裁（Conflict Arbitration）**是在多个结果互斥、重复或争用资源时，依据证据质量、来源、版本、政策和人工规则选择、合并、重新执行或升级，而不是让最后一个输出覆盖。

先分类：文本表述不同但事实一致、数据版本不同、方法选择冲突、测试结论冲突或实际写入冲突。可机器验证的用测试、Schema、哈希和来源解决；价值判断或高影响选择交给用户/负责人。

“再叫一个 Agent 投票”只在独立性和评判标准成立时有意义。共享同一错误来源的多数票不会更真。仲裁记录采用的结果、拒绝原因和未解决不确定性。

### 九、聚合器不能创造缺失证据

最终合并前逐个验收 Task Envelope：产物存在、版本匹配、测试通过、引用可访问、范围完整。聚合器可以组织信息、去重和指出差异，不能把三个 partial 写成 complete。

结论携带 claim→evidence 映射。来源不可用、子 Agent 失败或范围遗漏时明确缺口。不同子任务采用不兼容假设，先统一假设再合并。

代码集成在隔离分支/工作区做静态检查、测试和冲突审查；文本集成检查术语、前置与交叉引用。输出流畅不代表语义一致。

### 十、失败恢复按任务图传播

子任务失败时只重试其可重试部分，保留成功兄弟节点。依赖它的节点进入 blocked，不继续使用缺失输出。瞬时失败退避，输入错误修改信封，权限拒绝不靠换 Agent 绕过。

重试前检查是否已产生副作用。未知结果先对账；无副作用分析可用新 attempt。达到预算后给部分成果与缺口，不无限增加 Agent。

协调者崩溃后从持久任务图、租约、产物和事件恢复。进程内 Promise.all 不是可恢复编排器。

### 十一、取消与计划变化要定向传播

用户改变目标时计算哪些子任务仍有效、哪些需取消或重建。不要取消全部后从头开始，也不要让旧目标结果混入新汇总。父版本变化通过事件传播。

取消请求到达每个相关 Agent，它们停止新动作并报告完成/在途/未知。已完成的只读产物可以复用，但必须重新校验新目标的适用性。外部写入按补偿策略处理。

迟到消息标记 obsolete。UI 显示正在收敛，而不是在后台仍执行旧计划却宣称已取消。

### 十二、预算与公平全局管理

总预算分配到子任务并保留集成、验证和恢复额度。子 Agent 不能只因“还可深入”自行扩展。动态调度可把未使用额度重新分配，但高成本分支需要协调者批准。

限制并发、委派深度、模型调用、工具次数和上下文大小。尾部最慢任务可能决定总延迟，可设置截止后接受部分结果或选择备用策略。不要为了表面并行把下游 API 打到限流。

按任务价值选择模型/工具，而非所有节点都用最高配置。费用账本按根任务和子任务可追踪。

### 十三、可观测性展示任务图而非聊天墙

记录 rootRun、task graph、父子关系、信封版本、Agent/模型、能力、租约、消息、产物、证据、预算、冲突和仲裁。正文最小化，跨租户严格隔离。

指标包括并行收益、协调开销、重复工作、冲突率、无效结果、上下文泄露阻止、子任务恢复、集成失败、尾延迟和单位成功成本。Agent 数量不是成功指标。

用户界面显示阶段、负责对象、已确认产物和阻塞，不公开冗长内部思维。人工可以暂停单个分支或整个根任务。

### 十四、评测协作不只评测答案

构建可拆与不可拆任务，对比单 Agent 基线。测试独立研究、共享文件冲突、过期输入、恶意子结果、Agent 失联、重复消息、迟到结果、父目标变化、预算耗尽和协调者重启。

断言权限不横向扩散、同一资源不被无控制并写、依赖失败正确阻塞、聚合不掩盖缺口、恢复不重复副作用。用实际产物和版本证据评分，不仅让另一个模型评价文案。

逐步增加 Agent 数，观察质量、延迟、费用和失败面。若没有稳定收益，回到更简单架构。

### 十五、角色多样性不等于事实独立性

给同一个模型换成“研究员、评审员、专家”角色，不会自动产生独立证据。如果所有 Agent 读取同一摘要、使用同一检索结果或共享同一错误工具，它们的结论高度相关。需要真正独立验证时，分离数据来源、方法、模型或确定性检查，并在合并时记录相关性。

对抗式评审用于寻找反例和缺口，不允许直接修改被审产物或验收标准。实现者回应每个问题并附证据，仲裁者检查原始 diff、测试和来源。角色提示只能引导工作方式，权限仍由执行层限制。

多数票适合主观偏好或有校准样本的分类，不适合权限、事实和不可逆操作。高影响结论要求权威来源、可执行验证或有责任的人批准。

### 十六、跨组织协作需要更强契约

外部组织的 Agent 有不同身份系统、保留策略、模型和工具。交接使用版本化 Schema、签名来源、最小数据、目的、到期和允许的后续处理。对方返回的状态与制品仍需验证，不能因“合作伙伴”身份提升成内部事实。

在发送前完成数据分类与用户/组织授权，使用目标受众 token，防止 confused deputy。撤销、删除和事故通知写入协议与合同；无法保证的敏感数据不跨边界。对方超时或版本不兼容时有人工路径。

跨组织任务句柄不暴露内部数据库 ID。审计连接双方 correlation，但各自只看到必要元数据；争议时能对齐时间、版本和签名回执。

### 十七、工作流引擎与 Agent 各司其职

任务图、重试、定时、权限、幂等和状态迁移适合确定性工作流引擎；模型用于拆解模糊目标、理解内容、提出候选和解释结果。将模型每次输出转成经过验证的任务信封，再由工作流调度，避免聊天历史成为编排数据库。

稳定流程可以逐步固化，减少 Agent 数量；开放研究保留受控分支。系统价值来自问题解决，不来自长期维持复杂团队。每次架构评审都比较单 Agent、普通工作流和多 Agent 三种基线。

架构评审先用单 Agent 或普通工作流完成同一代表任务，记录成功、延迟、成本和人工修正；再加入多 Agent，只有独立证据、并行速度或专业分工带来稳定收益才保留。若质量提升来自更长 token 或更多重试，应与等预算单 Agent 公平比较。

上线清单包括任务图无环、信封 Schema、上下文与能力矩阵、共享资源所有权、消息去重、租约、产物版本、仲裁、总预算和协调者恢复。用敏感信息、污染结果、同文件并写、Agent 失联、迟到消息和目标变更验证隔离。

团队还要指定谁能创建新角色、接入外部 Agent、调整预算和批准高风险工具。组织边界与技术边界一致，防止一个看似辅助的子 Agent 成为绕过数据治理和发布流程的通道。

产物验收按类型选择检查器：代码运行类型、测试和安全扫描，研究结论核对来源与时间，设计文档核对约束和决策，数据文件校验 Schema 与统计。聚合器只能采用已通过对应检查器的版本，未验证内容保留为候选。

故障演练要同时中断协调者和若干子 Agent，再从持久任务图恢复；检查租约是否正确接管、旧消息是否被拒绝、成功产物是否复用、预算是否没有重置。只有进程正常时的并行演示不能证明协作可靠。

学完后，你应能判断任务是否值得拆分，定义任务信封、上下文与能力隔离、共享状态、冲突仲裁、取消和恢复，并用单 Agent 基线验证多 Agent 的真实收益。成熟的协作系统让责任和证据更清晰，而不是让更多模型同时说话。

# 工程化知识点讲义

## ENG-02 开发服务器、生产环境、资源路径与缓存一致性

“开发环境正常，生产环境失败”通常不是一个神秘类别，而是两个运行模型被混为一谈。开发服务器可以按请求转换源码、代理 API、保留模块热更新状态；生产环境运行经过优化的静态或服务端产物，还要经过反向代理、子路径、CDN 和浏览器缓存。要消除差异，先列出每一层真实承担的工作，而不是要求用户清缓存。

### 学习前先确认

- 直接前置：[ENG-01 模块图、构建产物、代码分割与 Source Map](../chinese-guides/eng-01-module-graph-build-output-source-maps.md#eng-01)。本讲直接使用入口、chunk、manifest、动态导入和映射关系；ESM 基础由其前置继续递归说明。

### 一、开发服务器以反馈速度为优先

适用场景需要先分清：开发服务器服务本地编辑反馈，预览服务器用于观察构建后的静态结果，生产服务器则承担真实流量、安全、缓存和可用性。三者都能“打开页面”，不代表可以互换职责。

开发服务器常接收浏览器 ESM 请求，按需解析和转换模块，注入调试信息，并维护模块图以支持更新。第三方依赖可能预处理以减少请求和兼容 CommonJS。源码错误可以带丰富 overlay，路径也可能由内存中间件直接处理。

这套行为不是生产部署协议。开发服务器可能回退所有未知路由到 `index.html`，自动处理 CORS、代理 `/api`、从项目根读取文件，并允许未压缩源码。把它直接暴露到公网会带来性能和安全问题。

开发环境验证关注快速定位和热更新正确性；生产验证关注已生成制品、真实路径、缓存、目标运行时和故障恢复。

### 二、HMR 替换模块但尽量保留页面状态

**热模块替换（hot module replacement）**在模块变化后更新相关边界，避免整页刷新。框架集成会决定组件状态是否保留；普通模块可通过接受与清理回调管理资源。

状态保留并不总是正确。改变模块级单例、事件订阅或数据 schema 后，旧内存状态可能与新代码不兼容；开发环境看似正常，完整刷新才暴露初始化错误。HMR 更新还可能重复注册监听器或定时器，说明模块没有正确释放旧资源。

开发时定期完整刷新、重启服务并从干净状态验证。不要把“热更新后能用”当成首次加载和生产构建证明。

### 三、生产构建冻结一组决定

生产构建解析配置、mode、target、环境常量和插件，输出带散列的文件集合。压缩、tree-shaking 和代码分割可能改变执行顺序与错误位置。生产预览用于本地检查这些产物，但通常不是正式生产服务器，也不模拟所有 CDN、TLS、压缩和反向代理行为。

验证至少分三层：`dev` 是否满足开发模型，`build + preview` 是否运行真实产物，目标部署是否正确提供同一产物。只比较界面截图会遗漏响应头、路径、缓存和服务端环境。

### 四、mode 与 NODE_ENV 不是天然同义词

构建工具的 mode 用于选择 `.env.[mode]` 等配置；`NODE_ENV` 常影响库的开发/生产分支。两者可能同时存在且取值不同。应显式记录命令、mode、运行环境和实际暴露常量，不要在代码里根据一个模糊字符串推断所有行为。

环境文件也有优先级：通用、local、mode-specific 和进程已有变量可能互相覆盖。服务启动后修改 `.env` 常需重启才能重新加载。诊断时输出允许公开的配置来源摘要和 schema 校验结果，不要打印密钥。

### 五、进入客户端的环境变量都是公开信息

客户端前缀变量在构建时被替换进 JavaScript，用户可以下载和检查。API 密钥、数据库密码、服务账号凭据不能因为存放在 `.env.production` 就变安全。

客户端只应包含公开 endpoint、功能开关 ID、release 等非秘密配置。真正的秘密由服务端或受控边缘函数保存，敏感操作还需要服务端授权。构建检查可以扫描客户端产物中是否出现已知密钥模式，但扫描不是密钥管理的替代。

布尔和数字环境值通常先以字符串进入，应经过 schema 解析。字符串 `'false'` 在 JavaScript 条件中是真值，是典型生产差异来源。

### 六、开发代理不会跟随产物部署

开发配置可能把 `/api` 代理到本地或远端服务，浏览器看到同源路径；构建后的静态文件不包含这个代理服务器。生产必须由反向代理、BFF 或真实 API 地址承担。

因此调试 404 或 CORS 时先画出浏览器实际 URL、DNS/代理目标和响应方。不要因为 dev 请求成功就认为生产 API 配置存在。代理还可能重写 Cookie domain、path 和 secure 标志，使身份行为与生产不同。

把代理规则、生产路由和应用 base 放在部署合同中，并用健康检查验证关键请求，而不是靠开发者机器隐含配置。

### 七、base 决定资源 URL 的根

应用部署在 `/`、`/portal/` 或 CDN 域名下时，HTML、动态 import、CSS URL、路由 history base 和 Service Worker scope 必须协调。绝对 `/assets/x.js` 在子路径下可能指向错误根；相对路径在深层路由直接刷新时也可能解析错误。

构建工具的 `base` 会重写可分析资源，但运行时字符串、服务端模板和第三方脚本仍需单独检查。使用 manifest 生成入口引用比手工拼接散列文件可靠。

目标验证应直接访问深层 URL、刷新、前进后退、加载异步路由和字体图片，并查看每个请求的最终 URL、状态和 MIME。

### 八、SPA fallback 只解决文档入口

History 路由的 `/courses/42` 刷新会向服务器请求该路径。静态主机需要把适当的非资源请求回退到入口 HTML，但不能把缺失的 JS、图片或 API 也返回 HTML 200，否则浏览器会以错误 MIME 解析并给出迷惑信息。

回退规则应区分文档导航、静态文件和 API，保留真实 404。服务端渲染或多页应用则有自己的路由，不能机械套 SPA fallback。

### 九、内容散列与缓存策略必须配套

带内容散列的 JS/CSS 可使用长时间 immutable 缓存；入口 HTML 和更新清单通常需要较短缓存或可重新验证，因为它们指向当前散列。若 HTML 长缓存而旧 chunk 已删除，用户会请求不存在文件。

**原子发布（atomic deployment）**意味着某个可见入口引用的整组产物同时可用。部署新版本时保留一段时间的旧散列文件，或让版本目录不可变，再切换入口，能支持打开中的客户端和安全回滚。

不要用“全部 no-cache”逃避一致性设计；它牺牲性能且仍可能受 Service Worker 或中间缓存影响。应为不同资源定义用途、版本和失效策略。

### 十、旧 HTML 与新 chunk 的错配需要应用级恢复

用户长时间打开页面后触发新路由，运行时可能按旧映射请求已被删除的 chunk。除了部署保留，还可捕获动态导入失败，判断是否为版本错配，提示安全刷新或重新导航；不能无限自动 reload 导致循环和草稿丢失。

恢复设计要保护未保存输入，记录当前 release 与目标资源，并区分网络暂时失败、权限错误和版本失效。刷新只是恢复手段，不是根因说明。

### 十一、CSS 与字体差异会改变布局结果

开发环境样式注入顺序、生产 CSS 提取、代码分割和第三方层顺序可能不同。缺失字体会改变文本宽度，导致只在生产出现换行和视觉回归。CSP、跨域字体和 MIME 也可能阻止资源。

检查生产 HTML 中 CSS 顺序、网络加载、computed style 和实际字体。不要仅增加选择器权重；先确定规则是否存在、属于哪个 layer、是否晚于预期加载。

### 十二、Service Worker 是额外发布参与者

Service Worker 可拦截请求并持有独立缓存。新 worker 的安装、等待和激活与页面生命周期不同，可能出现旧页面由新 worker 控制或反之。更新策略必须说明何时通知、是否自动激活、未保存状态如何处理以及旧缓存何时删除。

诊断时记录页面 release、controller script URL、worker 状态和 Cache Storage 版本。只勾选 DevTools 的 bypass 证明问题消失，仍需解释实际用户为何会取得错误组合。

### 十三、开发与生产的安全策略不同

生产常启用 HTTPS、CSP、严格 Cookie、资源完整性或跨源隔离，开发环境可能宽松。内联脚本、eval source map、WebSocket HMR 和本地代理在生产策略下会失败。

不要为了让功能运行就全局放宽 CSP 或 CORS。定位所需能力，使用 nonce/hash、明确源列表和服务端跨源响应，验证拒绝路径。安全头属于部署产物的一部分，也应进入环境矩阵。

### 十四、多环境应用需要明确运行位置

客户端、SSR 服务、Worker、edge 和构建配置可能读取不同变量、解析不同包条件并输出不同产物。共享模块应避免顶层访问特定全局，秘密只能进入服务端环境。

用表格记录入口、运行时、允许 API、配置来源、产物目录和部署单元。工具提供的环境 API 会演进，但这些问题不会消失。不能把 server bundle 成功当成浏览器 bundle 不含敏感模块的证明。

### 十五、建立开发—预览—部署矩阵

对关键路径记录：

| 维度 | 开发服务器 | 生产预览 | 目标部署 |
| --- | --- | --- | --- |
| 模块 | 按需转换/HMR | 构建 chunk | CDN 或服务端产物 |
| API | 开发代理 | 显式地址 | 反向代理/BFF |
| 路径 | 根目录便利规则 | 构建 base | 真实子路径与路由 |
| 缓存 | 通常弱缓存 | 本地文件 | 浏览器/CDN/SW |
| 安全 | 本地例外 | 部分模拟 | HTTPS/CSP/Cookie |

每次差异排查先找矩阵中不一致的层，再做单变量实验。清缓存可以作为区分缓存变量的一次操作，但不能成为用户长期手册。

### 十六、部署验证必须从用户入口开始

构建后检查文件散列只是第一步。还要从真实入口加载，深链刷新，触发动态路由，检查 API 身份、静态资源、错误恢复和新旧版本兼容。保存响应头和 release，确保健康接口检查的正是当前进程与数据库。

回滚验证同样需要入口、资源、服务端和数据兼容。若新版本执行了不可逆迁移，仅回滚前端文件可能产生更严重问题；部署合同要提前说明。

### 进阶：配置也需要 schema 和启动时失败

将环境变量集中解析为类型化配置：必填 URL、枚举 mode、布尔和数字范围在进程启动或构建时验证。错误应指出变量名和期望，不输出秘密值。业务代码消费解析后的对象，避免各模块用不同默认和字符串转换。

客户端和服务端配置使用不同 schema 与前缀；共享类型不表示共享数值。运行时配置文件若允许同一产物部署多环境，要定义缓存、完整性和加载失败路径；它不应成为绕过构建验证的任意脚本注入点。

### 进阶：灰度发布验证的是组合而非文件上传

按少量流量或用户逐步切换新版本时，记录客户端入口、API、数据库 schema 和功能开关组合。指标异常要能回指 release 和 cohort。灰度前后若同时改变缓存策略与后端版本，回退边界必须提前定义。

静态资源部署成功后可先做无用户冒烟，再切入口；切换后保留旧不可变文件和兼容 API，直到打开中的客户端自然退出。服务端新旧版本并存时，数据合同要向前/向后兼容，不能只验证最新前端配最新后端。

版本切换完成后从多个区域和真实 CDN 入口检查响应散列，防止部分边缘仍返回旧 HTML。健康检查、资源哈希和浏览器关键路径三者共同证明安装/发布结果。

### 进阶：运行时能力检测优于环境名称猜测

“production”只是一个标签，不能保证 HTTPS、特定浏览器 API、可写存储或某个后端版本存在。代码应在真正使用能力的位置检测，并定义不支持、权限拒绝和暂时失败的不同退路。构建时条件用于移除调试代码或选择固定实现；运行时条件用于处理用户设备和部署组合，两者不能互相冒充。

功能开关也不是普通环境变量。它需要默认值、目标群体、读取失败行为、审计、过期 owner 和与旧客户端的兼容规则。关闭功能只能隔离被开关包住的路径，不能撤销已经写入的数据或加载的资源。发布验证应记录实际求值结果，而不是只看控制台中的配置页面。

当浏览器长时间保持页面打开时，前端版本可能跨越多次后端发布。请求合同应允许兼容窗口，服务端错误返回可识别版本不兼容；客户端在保存用户输入后再提示刷新。用版本过旧测试和混合部署测试，才能证明系统不是只在“最新配最新”的理想组合中工作。

### 学完后应能说明

你应能区分开发服务器、HMR、生产构建、预览和真实部署，解释 mode、环境变量、代理与 base 如何造成差异；能设计 HTML、带散列资源和 Service Worker 的缓存一致性，并在子路径、旧 chunk 或生产安全策略下用证据定位问题，而不是把“清缓存重试”当作最终解决方案。

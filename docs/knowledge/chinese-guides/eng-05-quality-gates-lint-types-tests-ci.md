# 工程化知识点讲义

## ENG-05 格式、Lint、类型、测试与 CI 质量门禁

质量门禁不是把尽可能多的工具串进一个命令，而是让不同风险在最合适的层被稳定发现，并让任何人都能在干净环境复现结果。format、lint、typecheck 和测试回答的问题不同；本地钩子负责快速反馈，CI 负责共同且不可由个人环境绕过的裁决。

### 学习前先确认

- 直接前置：[ENG-03 依赖解析、Lockfile、Workspace 与 Peer Dependency](../chinese-guides/eng-03-dependencies-lockfile-workspaces-peer.md#eng-03)。本讲要求能在锁定依赖与 workspace 中运行统一脚本；包解析细节由该讲说明。

### 一、门禁从风险清单开始

先列仓库最需要阻止的失败：无法构建、类型合同破坏、关键业务回归、敏感信息进入产物、依赖不可重复、格式噪音或发布制品缺失。再把每类风险映射到检查，不要先安装流行工具再寻找用途。

门禁的目标是给出稳定、可行动的否决。无法确定的启发式提示可以作为建议，不应在没有误报治理时阻断所有提交。安全和数据损失风险则需要更强的保守规则与人工批准。

### 二、format 只统一文本表现

**格式化（formatting）**处理缩进、空格、换行、引号等可机械决定的文本形式，减少评审噪音。它不判断变量是否未使用、Promise 是否遗漏处理，也不证明业务正确。

CI 通常运行 check 模式而非直接改文件，避免服务器悄悄产生未提交变化。自动修复在开发者本地执行，并让 diff 可审查。生成文件、Markdown、样式和代码可能使用不同格式器，应明确范围和忽略规则。

格式规则变更会触发大面积 diff，最好独立提交并协调未合并分支，防止掩盖行为变化。

### 三、lint 发现可疑结构与约定偏差

**静态规则检查（lint）**通过语法树、类型信息或文件模式发现未使用变量、危险比较、Hook 规则、浮空 Promise 和架构边界。某些规则可自动修复，某些需要理解语义。

规则严重度应与风险一致。把所有 warning 永久保留会制造告警疲劳，把所有规则设 error 又可能因启发式误报阻塞交付。新增规则可先统计基线，再禁止新增、按 owner 逐步消化旧问题。

行内禁用必须最小范围，写明原因和移除条件。全局关闭只因一处误报，会让其他真实风险失去保护。

### 四、typecheck 证明静态合同可满足

**类型检查（type checking）**验证声明与使用在类型系统中一致，适合发现重构后的参数、返回值、联合分支和模块边界错误。它不验证运行时输入真实符合类型，也不证明授权、时序或 UI 行为。

构建工具可能只转译 TypeScript 而不完整检查，必须有独立 typecheck 命令。多包仓库要处理项目引用、生成类型和依赖构建顺序；增量缓存不能让缺失声明被旧结果掩盖。

外部 JSON、环境变量和网络响应仍需运行时解析。`as` 断言只改变编译器认识，不会转换数据；大量断言通过不是质量证据。

### 五、测试验证可观察行为

测试通过预言和输入证明具体行为，覆盖纯函数、组件、接口或端到端路径。不同层有速度和真实性权衡；不应让一个超大的 E2E 套件承担所有规则，也不能以行覆盖率替代关键风险。

门禁应选择与变化相关的快速测试，并在 CI 有完整或风险分层套件。随机、时间和并发测试需要固定种子、虚拟时钟或受控调度，确保失败可复现。

测试本身也会失效。重试通过要保留首跑失败并进入 flaky 治理，不能自动把最终绿色称为稳定。

### 六、构建验证跨越工具合同

生产构建可发现模块解析、资源、环境和打包问题，但构建成功仍不证明部署正确。CI 至少保存产物清单、体积与关键散列，并在适当阶段运行生产预览或冒烟路径。

库包需要验证打包内容和消费者安装，应用需要验证入口与异步 chunk。只运行开发编译会漏掉 tree-shaking、CSS 提取和环境替换问题。

### 七、本地反馈分层而不是一次跑完

编辑器提供即时诊断，保存时可格式化；提交前运行秒级的变更相关检查；推送前可运行稍重套件。越靠近输入，反馈越快，但权威性越低，因为个人配置、缓存和旁路可能不同。

本地命令应与 CI 使用同一脚本和配置，避免“编辑器绿、命令红”。不要让钩子自行安装依赖、访问不可控网络或修改无关文件；失败信息应给出可直接复现的仓库命令。

### 八、Git hooks 可以被跳过

pre-commit 和 pre-push 提供便利，不是安全边界。新机器可能没安装，用户可跳过，网页编辑也不经过本地钩子。共同规则必须由服务端保护和 CI 兜底。

这不意味着钩子无用。它们能把常见失败提前到提交前，减少远端等待。关键是把“快速反馈层”和“不可绕过裁决层”写清，并验证旁路本地钩子时 CI 仍会失败。

### 九、CI 从已声明输入重建结果

**持续集成（continuous integration）**在受控环境检出明确 commit，冻结安装依赖，运行检查并保存证据。环境应记录操作系统、运行时、包管理器、工具版本和关键配置。

CI 不应依赖某位开发者机器已有文件，也不应从未声明目录读取秘密。生成物若应入库就检查是否同步；若应在流水线生成，就从干净源重建并避免把陈旧产物作为输入。

矩阵可以覆盖多运行时或浏览器，但维度过多会增加成本。根据支持合同和风险选择，并明确哪些是必过、哪些仅观察。

### 十、门禁顺序优化反馈，不改变标准

可先运行格式、lint 和 typecheck，再运行单测、构建和 E2E，以快速失败节省资源。并行执行无依赖检查可缩短时间，但日志和临时资源要隔离。

快速失败不能隐藏后续证据：对安全事件或大版本升级，可能需要收集完整矩阵，即使早期一项失败。流程应区分日常反馈与调查模式。

合并策略还要防止“每个 PR 在旧基线都绿，组合后红”。要求最新基线、merge queue 或合入后主线检查，确保裁决对应实际集成 commit。

### 十一、增量检查需要可信失效

只检查改动文件能加速 lint，但类型、公共配置和依赖变化会影响未改文件。monorepo 的 affected 计算应沿依赖图传播，锁文件或根配置变化通常扩大范围。

缓存 key 包含源、配置、工具、锁文件和相关环境。若某输入未纳入，旧成功结果会成为伪通过。定期无缓存运行和随机全量对照可验证增量策略。

不稳定或无法解释的缓存应先关闭再修，不能因为“通常更快”牺牲门禁可信度。

### 十二、历史债务采用基线而不是永久降级

接入新规则时可能已有大量问题。可生成可审计基线，冻结旧问题并阻止新增；每条债务有 owner、风险和清理计划。基线应只减少不增加，变更触碰相关区域时可以要求顺手清理。

把全部问题降为 warning 会让新旧混在一起，最终无人处理。基线也不能覆盖安全关键问题或已导致生产故障的模式。

用趋势跟踪剩余数量、年龄和重复发生，而不是以“工具已经安装”宣告治理完成。

### 十三、误报与例外需要生命周期

误报首先用最小示例确认规则不适用，再考虑重构、精确配置或窄禁用。例外记录规则 ID、原因、范围、批准者和复查时间。规则升级后重新验证，避免旧禁用继续屏蔽新语义。

如果团队频繁禁用同一规则，可能是规则与技术栈不匹配，也可能是培训或 API 设计问题。通过数据决定调整，而不是互相指责。

### 十四、本地通过、CI 失败要比较环境

依次比较检出的 commit、未跟踪生成物、Node/包管理器版本、锁文件冻结、文件名大小写、时区/locale、环境变量、CPU 并发和缓存。Windows 本地允许的大小写路径可能在 Linux 失败；真实时钟和排序也会制造差异。

反复 rerun 只收集发生率，不修复原因。保存首次失败日志和制品，构造最小环境对照。若 CI 池本身故障，应标为环境问题并修基础设施，不应改测试断言迎合坏环境。

### 十五、质量门禁也保护 AI 生成变更

AI 可以快速生成大量跨文件修改，也会复制过时 API、漏掉边界或伪造测试通过。生成来源不改变标准：先检查 diff 与所有权，再运行同一格式、lint、类型、测试和构建门禁，并用运行证据核对关键行为。

不要因为补丁由 AI 生成就放宽，也不要只因来源而拒绝。风险取决于权限、数据、范围和验证。对自动生成的大差异尤其要限制文件边界、保存提示外的真实需求来源，并防止工具修改用户未授权内容。

### 十六、门禁输出必须可行动且可保存

失败信息包含文件、规则、预期/实际和复现命令；CI 页面关联 commit、环境和制品。长日志可保存为附件，摘要突出首个根因，避免后续级联错误淹没信息。

成功也要有证据：实际运行了哪些脚本、是否命中缓存、测试数、构建产物与检查版本。一个只写“all good”的自定义脚本无法审计。

### 十七、评估门禁是否真正降低风险

观察门禁拦截的真实缺陷、误报率、反馈时间、旁路次数和主线失败率。目标不是追求最多检查或 100% 覆盖，而是在可接受成本下更早阻止高风险变化。

过慢门禁会促使开发者批量提交和寻求旁路；过弱门禁让 CI 变成装饰。通过并行、增量和分层优化速度，同时保留定期全量与高风险路径。

### 进阶：门禁规则本身也要版本化和测试

CI 配置、共享 lint preset、测试 helper 和构建脚本都属于生产工程代码。修改它们会改变哪些问题被发现，应独立评审并用故意失败样例验证。一个脚本若无论子命令失败都返回 0，会制造最危险的伪通过。

对关键门禁建立元测试：注入格式、类型、测试和构建缺陷，确认对应 job 非零；模拟缓存命中，确认输入变化会失效；取消 job 时确认合并状态不是成功。不要只测试正常仓库全绿。

共享工作流引用固定版本或可信 commit，第三方 action/镜像按供应链策略更新。流水线拥有写仓库、发布或云权限时，PR 来源和密钥可见性需要严格隔离。

### 进阶：Required Check 名称与拓扑会漂移

分支保护常按检查名称要求通过。重命名 job、拆分矩阵或条件跳过后，旧 required check 可能永远等待，或新 job未真正成为必需。每次 CI 拓扑变化核对平台保护、merge queue 和实际合入 commit。

条件执行要区分“无需运行”和“未运行但风险存在”。文档-only 变更可跳过浏览器矩阵，但根配置、锁文件和共享工作流变化应扩大范围。跳过决定输出机器可读原因并可审计。

### 进阶：质量策略需要可靠的紧急通道

生产事故可能需要快速修复，但直接关闭所有保护会留下长期漏洞。预先定义 break-glass：谁能批准、哪些检查仍不可跳过、如何记录差异、何时补跑、谁负责恢复规则。

紧急合入后立即在实际主线和制品运行完整门禁，失败则按发布策略回退。复盘旁路是否必要，以及正常流程为何无法满足响应时间。目标是缩短可信检查，而不是培养管理员手工合入习惯。

政策例外到期自动提醒或失败，避免事故借口成为永久配置。门禁既要可靠，也要在真实高压条件下可操作。

### 进阶：门禁结果需要对应被合入的提交

PR 页面显示绿色时，要确认检查针对当前 head，若平台使用合并队列，还要确认针对候选 merge commit。旧运行完成、分支随后被强推，或检查只覆盖 PR 分支但目标分支已变化，都可能产生“绿色结果与最终代码不是同一对象”。保护规则应在新提交后使旧批准和旧检查失效，并保留检查到 commit 的可查询关系。

矩阵任务不能用其中一个成功代表全部成功。汇总 job 应显式依赖每个必需平台，区分失败、取消与跳过；即使平台 UI 把允许失败标成绿色，发布决定也要知道哪些风险未验证。分片测试还需证明测试集合完整分配，没有因筛选表达式错误而运行零项。

外部贡献的 CI 尤其要防止不可信代码读取秘密、修改缓存或发布制品。先在无秘密环境执行构建和测试，只有经过批准的 commit 才进入有权限阶段。缓存按信任域隔离，制品携带来源。质量门禁本身若成为攻击路径，它越自动化，影响越大。

### 进阶：质量趋势要按风险解释

失败次数上升可能代表质量变差，也可能是规则刚增强、运行量增加或旧问题终于可见。趋势图应同时记录检查版本、代码变更量、跳过率和不稳定失败，不能用单一“绿色率”评价团队。发现缺陷的门禁有价值，不应因它让数字变难看而被关闭。

相反，长期百分之百通过也可能说明规则没有覆盖真实事故。定期把线上缺陷映射到本应拦截的层：是没有规则、规则未运行、预言太弱，还是风险本来只能在发布后观察。新增保护时给出对应机制与误报预算，过期规则则通过证据删除。门禁组合应随产品风险演进，而不是不断累加永不复查的命令。

### 学完后应能说明

你应能区分 format、lint、typecheck、测试和生产构建各自能证明什么，为本地、钩子和 CI 分配不同责任，并设计可信的增量缓存、历史债务基线和例外生命周期。面对本地/CI 差异或不稳定检查时，应以环境和证据定位，而不是重跑到绿色或全局关闭规则。

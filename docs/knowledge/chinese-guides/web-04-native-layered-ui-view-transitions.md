# Web 平台 UI 知识点讲义

## WEB-04 原生分层 UI、视图过渡与渐进增强

浮层、对话框与页面过渡看似是视觉问题，实际牵涉绘制层级、焦点、历史、导航失败和无脚本路径。平台能力能减少手写基础设施，但不会替你选择交互语义。高级实现的核心是先建立真实链接、按钮、表单与内容的可用基线，再用 popover、dialog、View Transition 和 Navigation API 增强同一条任务路径。

### 学习前先确认

- 直接前置：[BROWSER-01 渲染流水线、DOM 事件与存储](../chinese-guides/browser-01-render-events-storage.md#browser-01)。本讲直接使用 DOM、事件、渲染与历史相关模型。
- 直接前置：[A11Y-01 WCAG 2.2、无障碍测试与工程治理](../chinese-guides/a11y-01-wcag-testing-governance.md#a11y-01)。浮层焦点、键盘和用户偏好由该讲建立完整合同。

### 一、先按交互语义选择平台原语

非阻塞提示、操作面板和选择器可以使用 popover；必须先完成或明确取消的流程使用 modal dialog；页面或资源跳转首先是真实链接；视觉连续感再由 View Transition 增强。选择错误会迫使代码重新实现浏览器已有行为。

**顶层（Top Layer）**是浏览器管理的特殊绘制层，dialog、popover 与全屏元素等可进入其中。它不受普通祖先 `overflow` 裁剪和常规 `z-index` 堆叠竞争，但进入顶层不等于模态、不等于自动管理业务焦点，也不等于安全隔离。

把浮层统一实现成 `position:fixed; z-index:999999` 会遇到 stacking context、裁剪、关闭协议和焦点问题。原生能力减少这部分偶然复杂度，同时仍要求产品定义内容、触发器、初始焦点、关闭结果和回退。

### 二、Popover 提供显示状态和轻触关闭

`popover="auto"` 适合一次只打开少量的非模态浮层，支持点击外部与 Escape 等 light dismiss；manual popover 由应用显式控制，可同时存在多个。`popovertarget` 与相关命令属性可以建立声明式触发，但能力支持需按目标环境核验。

Popover 不会自动变成 ARIA menu。若内部是普通操作按钮，保留自然 Tab 顺序通常最可靠。只有产品确实需要菜单的方向键与类型搜索协议时，才实现完整 menu 模式。 tooltip 也不能只在 hover 出现；键盘焦点与触控需要等价触发。

打开与关闭可通过 `beforetoggle`/`toggle` 观察。记录真实触发器，关闭后在触发器仍连接时归焦；若用户主动把焦点移到别处，不要无条件抢回。嵌套 popover 需要理解祖先关系和自动关闭顺序，不能靠全局点击监听器随意关闭所有层。

### 三、Dialog 区分模态与非模态

`dialog.showModal()` 建立模态对话框并使背景变为不可交互区域；`.show()` 只是非模态显示。两者不是视觉差别。对话框需要可访问名称、合理初始焦点、可见关闭按钮、Escape/cancel 策略和关闭归焦。

表单可用 `method="dialog"` 关闭并返回值，但真正保存仍应由显式业务逻辑处理，区分取消、验证失败和提交成功。`cancel` 事件可阻止 Escape 关闭，只有数据丢失等明确理由才这样做，并给用户可理解的退出路线。

不要在 `showModal()` 后给整个 body 手工 `aria-hidden`，这可能把 dialog 自身也藏出树。自定义惰性区域使用 `inert` 时成对设置/清理；它只控制交互，不是服务端权限。

### 四、焦点协议比打开动画更重要

打开浮层前保存触发器，打开后把焦点放到任务入口，关闭后根据结果和 DOM 存活情况选择归还点。确认删除当前列表项后，原触发器已不存在，应聚焦下一项或列表标题，并向用户说明变化。

非模态 popover 通常允许背景操作，不应模仿 dialog 把全页 inert。菜单操作完成后可以关闭并归焦；若用户点击背景完成轻触关闭，浏览器的点击目标和归焦策略要通过真实事件顺序测试，避免把焦点从用户刚点击的控件抢走。

滚动、缩放与虚拟键盘可能遮挡焦点。固定 header、顶层层级和视图过渡快照不能成为焦点可见的假象。用键盘在长页、窄屏和缩放下走完整任务。

### 五、锚点定位只解决几何关系

CSS Anchor Positioning 能让浮层相对触发器布局，并按可用空间尝试候选位置。它解决定位与碰撞，不提供 popover 语义、关闭、焦点或权限。基础路径可用普通 top-layer 默认位置或成熟定位逻辑，支持时再增强。

锚点消失、进入滚动容器、RTL、缩放和软键盘都会改变空间。fallback 列表要保证内容留在视口内，箭头图形不能反过来决定可读性。能力检测按具体语法执行，不因浏览器支持 popover 就假设支持所有锚点子特性。

### 六、View Transition 围绕一次状态变化

**视图过渡（View Transition）**在更新前后捕获视觉快照，并让旧、新状态通过伪元素动画。单文档过渡由 `document.startViewTransition(update)` 包裹一次 DOM 更新；跨文档过渡还需要双方页面和导航条件满足当前规范。

基础更新函数必须可以独立执行：不支持 API、用户减少运动、过渡创建失败时直接调用同一个更新。过渡回调已经执行后，`finished` 拒绝不表示业务更新没发生，catch 中不能盲目再更新一次。

`ready`、`updateCallbackDone` 与 `finished` 表示不同阶段。业务状态提交、动画准备和动画完成不要混成一个 Promise。页面路由可以在数据准备后提交 DOM，再让视觉过渡完成；失败时清楚区分网络错误、渲染错误与动画错误。

### 七、快照不等于真实 DOM

过渡期间伪元素显示旧/新快照，真实 DOM 和焦点仍由应用管理。用户可能点击、按键或触发第二次导航；需要定义中断与取代规则。不要让覆盖全屏的快照层长期拦截指针，也不要等待动画结束才更新屏幕阅读器可见状态。

`view-transition-name` 在同一时刻必须唯一。重复名称会使过渡跳过或失败。列表重排使用稳定业务 ID，避免索引变化造成错误配对；敏感内容可能出现在快照中，要评估遮罩、截图与跨文档边界。

移动同一 DOM 节点通常保留其身份、输入值和监听器，销毁再创建则不会。动画技术不应决定业务节点是否被无意重置。过渡前后保存焦点、选择区与滚动策略，并用无动画路径做对照。

### 八、运动偏好和动画可取消性

`prefers-reduced-motion: reduce` 下关闭非必要平移、缩放和视差，内容与状态立即更新。不是简单把持续时间改为 0.01ms 后仍触发大量生命周期事件；可在调用 View Transition 前直接选择基础路径。

快速连续操作时，新过渡可以取代旧过渡。业务更新要有序且幂等，不能因为动画被跳过而丢失一次导航或重复一次删除。记录 transition ID 与 navigation ID，日志才能区分视觉取消和业务取消。

过渡性能查看快照面积、动画属性、主线程更新和合成成本。视觉顺滑不能掩盖内容加载更慢或焦点漂移。

### 九、真实链接是导航增强的基线

详情入口使用 `<a href="/items/42">`，服务端能直接响应 URL。这样无脚本、刷新、复制链接、新标签打开和搜索引擎都保留基本语义。点击处理器只增强符合条件的同源普通导航，不拦截下载、外部链接、修饰键新窗口或浏览器不允许拦截的情况。

表单同理：真实 action/method 提供基础提交，脚本可增强校验和局部刷新。把所有链接写成 button 再由 JavaScript 改 URL，会失去平台行为并制造大量回退责任。

### 十、Navigation API 统一观察导航但不是第二套历史

**导航 API（Navigation API）**提供当前历史条目、navigate 事件、拦截、提交和完成阶段，目标是替代应用散落的 click、popstate 与 history 操作。它仍有支持范围，必须让真实 URL 路径独立可用。

在 navigate 事件中先检查 `canIntercept`、源、下载与表单等条件。拦截当前导航后由 handler 加载数据和渲染，不要再调用 `history.pushState()` 或再次 `navigation.navigate()` 提交同一意图，否则产生双历史条目。

URL committed 表示历史位置已变化，finished 表示拦截处理完成；两者间失败需要错误 UI和恢复。后退/前进是 traverse，不应一律当新 push。滚动恢复、焦点标题和数据缓存策略按 navigation type 决定。

### 十一、导航并发需要取消旧工作

用户连续点击两个链接时，旧数据请求可能晚到。每次导航绑定 AbortSignal 与单调 ID，迟到结果在提交前验证仍属当前目的地。取消网络等待不保证服务端写入没发生；导航通常只自动取消读取，写操作需要独立确认与结果查询。

加载中可以保留旧页面、显示局部 pending 或进入新 URL 后显示骨架，选择要与错误恢复一致。不要为了动画先提交空页面，再在失败时无法返回。服务器、客户端路由与缓存必须对同一 URL 有一致身份。

### 十二、渐进增强按能力而不是品牌分支

建立能力矩阵：popover、dialog、View Transition、Navigation、锚点定位分别检测。支持入口不代表所有行为无 bug，关键路径仍需真实测试。基础路径只要求任务完整，不要求像素与增强完全相同。

不支持 popover 时可用内联操作区或经过验证的简易显示逻辑；不支持 modal dialog 时可导航到独立页面，而不是仓促用 div 模拟全部模态协议；不支持过渡时直接更新；不支持 Navigation API 时让浏览器加载 href。

把回退与增强共享同一领域函数和 URL，避免维护两套业务。新能力覆盖率足够后可按版本化基线删除旧适配，并保留变更证据。

### 十三、分层 UI 的安全边界

顶层、Shadow DOM 和 inert 都不是安全边界。隐藏背景按钮不能替代授权，popover 内容也可能被同源脚本读取。外部 URL、富文本和 iframe 仍按各自信任边界验证。

clickjacking 防护来自 `frame-ancestors`、嵌入策略和服务端流程，不来自把确认框放在 top layer。重要操作显示明确对象、影响和来源，避免透明覆盖和误触；确认后的服务端命令仍重新授权与幂等处理。

跨文档过渡与截图可能暂存视觉内容，涉及高敏感页时按当前浏览器机制核验或禁用。不要把动画 API 加入密码、支付或医疗数据页面却不做威胁评估。

### 十四、测试矩阵覆盖键盘、历史和禁用能力

对浮层测试鼠标、触控、Tab/Shift+Tab、Escape、外点、触发器删除和嵌套；记录打开/关闭前后 activeElement 与无障碍树。对导航测试普通点击、修饰键、新标签、刷新、直接 URL、后退/前进、连续点击和请求失败。

View Transition 同时跑启用、减少运动、API 缺失和动画失败，断言业务更新次数严格一致、焦点和历史不变。用截图辅助视觉判断，但 DOM、URL、history entry 与用户任务断言才是核心。

### 十五、何时仍应使用框架或成熟组件库

原生原语减少底层工作，不自动提供复杂选择器、虚拟列表、国际化日期、业务校验和组织设计系统。成熟组件库若完整实现语义、键盘、焦点和兼容矩阵，可能比每个团队重复封装更可靠。

选择标准是合同与维护成本：平台原生适合稳定通用机制，框架负责状态与组合，组件库提供一致产品语言，普通页面链接/表单保持最低可用层。避免因为“零依赖”而重写高风险交互，也避免因为库存在就忽略最终 DOM。

### 学完后应能说明

你应能区分 top layer、popover、modal dialog 与 inert，设计完整焦点和关闭协议；能解释 View Transition 快照、状态更新与失败阶段，确保减少运动和无 API 路径可用；能以真实链接为基线使用 Navigation API，避免双历史提交，并用键盘、URL、历史、焦点和能力矩阵验证整个任务。

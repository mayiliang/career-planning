# 前端可观测性与运行目标知识点讲义

## OBS-01 前端可观测性、SLO、告警与隐私边界

前端代码运行在用户设备、网络和浏览器组合中，团队无法像查看服务器那样直接登录现场。可观测性的价值，是从有限且受控的外部信号推断用户经历了什么、问题从哪个版本和环节开始、恢复动作是否生效。它不是把所有日志上传，也不是买一个监控平台后打开默认仪表盘。本讲从用户任务与事件口径出发，连接错误、性能、请求、Trace、发布、SLO、告警和隐私治理。

### 学习前先确认

- 直接前置：[DEBUG-01 系统化排错、证据与因果](../chinese-guides/debug-01-systematic-debugging-evidence-causality.md#debug-01)。遥测只能提供观测，定位仍需区分事实、假设、相关与因果。
- 直接前置：[ENG-06 CI/CD、制品晋级、发布与回滚](../chinese-guides/eng-06-ci-cd-artifact-promotion-release-rollback.md#eng-06)。现场信号必须关联不可变版本、发布阶段和恢复窗口，才能闭合交付证据链。

### 一、从要回答的问题设计信号

“页面是否可用”至少包含加载、交互、请求、业务结果和恢复。先列出关键用户任务，例如登录、搜索、保存、支付和导出，再写成功条件、允许时长、失败状态与影响人群。只有与问题相连的信号才值得采集；没有消费方式的字段会增加成本和隐私风险。

前端通常使用错误、日志、性能条目、网络请求、用户任务结果和业务事件。它们不是同义词：异常说明某段执行失败，HTTP 200 不代表业务成功，慢请求未必阻塞用户，点击事件也不能证明任务完成。高级观测模型把这些信号用版本、路由、任务、请求和 Trace 关联，而不是在不同仪表盘里孤立统计。

指标名称、单位、边界和版本要写成数据合同。一次口径修改可能让趋势断裂，应保留 schema 版本和生效时间；历史回算不可行时明确分段。未经定义的“成功率”“页面耗时”很容易被不同团队用不同分母计算。

### 二、RUM 与实验室数据各自回答什么

**真实用户监控（Real User Monitoring）**从真实浏览器采集抽样体验，覆盖实际设备、网络、地区、缓存和用户行为。它能发现长尾与特定群体退化，但环境噪声大、归因有限，且必须处理同意、采样和数据质量。实验室测试固定设备与输入，适合复现和比较变更，却不能代表全部用户分布。

正确闭环通常是字段数据发现“哪类用户和路由退化”，实验室或可控现场复现“为什么”，修复后先在相同条件验证，再回到字段数据确认真实分布改善。单次 Lighthouse 绿色不能推翻 RUM p75 变差；RUM 相关也不能单独证明某函数是根因。

采集导航类型、设备档位、网络、可见性和缓存状态能帮助分层，但维度组合会快速爆炸。先保留能改变决策的少量维度，限制基数，并为样本不足显示“不足以下结论”，不要用细分后的两三个样本画确定趋势。

### 三、页面、路由与用户任务是三种边界

传统硬导航从文档加载开始，性能条目有相对清楚的生命周期。SPA 路由在同一文档中切换，旧请求、布局偏移和异步渲染可能跨越 URL 变化。只监听 `history.pushState` 就把“URL 改了”误当成“新页面已呈现”，也可能漏掉不改 URL 的任务步骤。

软导航能力仍需按浏览器支持检测，并记录口径。可使用路由开始、主要内容变化、稳定点和用户交互共同定义启发式边界；标准化条目和启发式结果不能无标记混算。导航 ID、开始时间和完成/放弃原因使延迟到达的指标能归回正确路由。

用户任务边界可能跨多个路由和请求。例如“提交报销”从编辑到确认再到回执，单页加载很快仍可能整体失败。任务记录开始、阶段、终态和恢复动作，并使用随机任务 ID；不要把输入正文、订单内容或稳定个人身份放进遥测。

### 四、错误采集需要上下文而非堆栈洪水

脚本异常、Promise 拒绝、资源加载失败、框架错误边界和网络失败来自不同通道。统一事件模型要保留错误类别、受影响任务、版本、路由和环境，同时删除敏感值。跨源脚本若缺少正确 CORS 和 source map，可能只得到模糊错误；公开 source map 与上传到受控错误平台是不同选择。

错误归组不能只按消息字符串。构建压缩会改变行列，动态 ID 会制造高基数；可结合异常类型、规范化栈顶、版本和组件边界生成指纹。归组规则本身要版本化，并允许拆分和合并，以免一个大组掩盖多个根因。

未捕获异常不是唯一失败。被业务代码吞掉的保存失败、无限加载、空白区域和错误成功提示更接近用户症状。关键任务要有显式终态和超时监测；错误边界显示降级 UI 时也记录恢复是否成功。

### 五、性能条目要归属到具体体验

Performance API 提供导航、资源、绘制、事件、布局偏移和长任务等条目。观察器可能在条目发生后异步回调，页面隐藏时还可能收到最终值，因此要在生命周期边界正确 flush。重复注册观察器会造成重复上报，组件卸载时需要清理。

Web Vitals 是重要信号，但不是完整体验。LCP、INP、CLS 分别代表加载、交互响应与视觉稳定；搜索耗时、保存成功和流式首字也可能更贴近产品任务。将指标关联候选元素、事件、资源、路由和版本，才能从“变慢”走向可复现假设。

观测代码自身占用主线程、网络和电量。批量、采样、压缩、空闲发送和上限控制可以降低成本；页面关闭时的上报能力也有体积与可靠性限制。若 observer 回调处理大量堆栈、序列化 DOM 或同步写存储，它会成为新的性能问题。

### 六、请求与分布式上下文连接前后端

前端请求记录方法类别、目标服务、状态、阶段耗时、重试、取消和业务结果，不应记录完整 URL 查询、Authorization、Cookie 或请求正文。动态 ID 需要模板化，例如 `/orders/:id`，否则指标维度无法聚合并泄露对象标识。

**分布式追踪（Distributed Tracing）**使用 Trace 和 Span 描述一次工作跨组件传播的因果关系。浏览器根 Span、API 网关和后端子 Span共享 trace ID 后，团队可区分前端排队、网络、代理和服务处理。不是所有请求都要全量追踪，采样决定必须尽量保持一条 Trace 的完整性。

跨源传播 `traceparent` 会触发安全与 CORS考虑，只有可信目标才能接收。第三方资源不应自动获得内部上下文。OpenTelemetry 浏览器实现的部分能力仍处于实验或非完全规范状态，因此生产接入要隔离适配层、固定版本并准备降级，不能把供应商 SDK 的当前行为当永久 Web 标准。

### 七、日志、指标和 Trace 的分工

日志适合离散事件与详细上下文，指标适合聚合趋势和告警，Trace 适合一次请求的跨服务路径。三者通过一致字段相连，而不是把所有日志转成高基数标签。版本、服务、环境、路由模板和错误类别通常适合公共资源属性；用户 ID、完整 URL 和随机请求 ID不适合指标标签。

前端控制台日志不是生产遥测。它可能被用户设备保留，也无法可靠集中。生产日志应通过受控通道、结构化 schema 和采样发送；调试开关要有到期，不能远程开启后无限收集细节。

后端日志与前端事件时间可能因设备时钟偏差无法直接排序。使用服务接收时间、相对时长、请求 ID 和 Trace 关系重建时序，并记录客户端时钟状态。不要仅凭两个绝对时间相近就断言因果。

### 八、SLO 把用户期望变成运行目标

服务级别指标 SLI 是被测量的用户结果，例如“可搜索请求在 2 秒内成功的比例”；**服务级别目标（Service Level Objective）**是在一个窗口内对该比例的目标。指标分子、分母、排除条件、窗口和数据源必须明确。把内部 CPU 当作前端用户任务 SLI，无法表达用户是否完成工作。

可用性不是只有 HTTP 成功。一个保存请求返回 200 但数据未持久化，应算业务失败；用户主动取消不一定进入失败分母；机器人和内部监测是否包含要按目标说明。目标不是越接近 100% 越好，过严目标会消耗大量成本并让每次小故障都违约。

SLO 可以按关键任务分层。登录和支付比头像加载有不同目标；移动弱网与桌面企业网络可分别观察，但总目标不能通过排除困难人群美化。目标由用户价值、风险和可实现成本共同确定。

### 九、错误预算连接可靠性和发布速度

**错误预算（Error Budget）**是目标允许的不成功比例。例如 30 天 99.9% 目标允许约 0.1% 合格事件失败，而不是允许团队随意制造故障。预算消耗速度比单点状态更有决策价值：短时间快速燃烧需要立即响应，缓慢消耗可能进入计划修复。

多窗口燃烧率能同时发现快速大故障和持续小退化。阈值必须绑定具体 SLO、观察窗口和通知渠道。预算耗尽后的策略可以暂停高风险发布、优先可靠性工作或加强审批，但不应机械阻断所有紧急安全修复。

发布与错误预算互相校验。新版本切流后若预算快速燃烧，自动停止扩大；恢复后仍需观察预算消耗回到基线。一个月末通过减少流量或改分母“恢复预算”是数据治理失败。

### 十、告警首先服务行动

症状告警告诉值班人员用户正在受影响，如关键任务失败率或延迟燃烧；原因告警提示可能根因，如某上游错误或资源耗尽。症状告警决定是否响应，原因信号帮助定位。只对 CPU、日志关键字和每个异常告警，会产生大量无法行动的噪声。

每条告警要有严重度判断输入、owner、运行手册、升级和抑制规则。严重度考虑影响人数、任务关键性、数据风险、持续时间和可逆性，不只看错误数量。关联同一事件的十个信号应归并，不让十个频道同时叫醒十个人。

运行手册提供当前仪表盘、最近发布、诊断步骤、安全缓解和升级联系人，但不能假装固定脚本适用于所有事故。告警长期无人行动就应删除、降级或重新设计。告警质量可用可行动比例、误报、漏报和发现时间评估，而不是总数。

### 十一、发布标记与恢复验证闭合交付

每次代码、配置、内容和开关变化都发送发布事件，包含不可变版本、环境、阶段和变更类型。仪表盘叠加发布时间，查询可以比较同路由的新旧版本。若只有“今天上线过”，现场退化无法准确关联哪一份制品。

金丝雀阶段按分流标识比较新旧版本，并控制设备、地区和用户群差异。指标不足时不能扩大；观测管道失明本身就是停止条件。回滚后继续追踪旧版本流量、错误、缓存和关键任务，直到约定观察窗稳定。

事故时间线保存首个用户症状、告警、确认、缓解、恢复和关闭。复盘行动要落入可追踪工程任务并验证风险下降，可观测性改进不是“增加更多日志”，而是补上当时无法回答的关键问题。

### 十二、隐私最小化是采集前置条件

先定义目的，再决定字段、采样、留存和访问。输入内容、URL 参数、token、Cookie、消息正文、文件名、精确位置和稳定设备指纹通常不应进入遥测。即使单字段看似匿名，组合后也可能识别个人；哈希稳定身份仍是可关联标识，不等于匿名。

在客户端源头删除敏感字段优于上传后再清洗。采用允许列表而非黑名单：只发送明确定义字段，未知属性拒绝。错误对象和网络头常携带意外数据，序列化前要规范化、截断和测试。用户同意、撤回、访问和删除请求要能沿供应商与备份生命周期执行。

访问控制按职责和环境隔离，查询与导出留审计，留存到期自动删除。生产排障需要临时扩大采样时，应有批准、范围、期限和自动回落。供应商 SDK 版本变化可能新增默认字段，每次升级重新做数据审查。

### 十三、数据质量和成本需要持续治理

遥测丢失、重复、延迟和时钟偏差都会改变结论。为采集管道建立自己的健康指标：发送、接收、拒绝、采样、队列、处理延迟和 schema 错误。若应用错误上升同时 SDK 上报下降，不能据“事件变少”判断恢复。

事件去重需要稳定事件 ID 或明确聚合窗口；离线队列恢复后可能延迟发送，要保存发生时间与接收时间。版本发布后字段变化要通过 schema 验证和兼容阶段，不让旧客户端上报突然被全拒绝。

成本由事件量、字段大小、维度基数、查询和留存共同决定。优先保留能驱动决策的汇总，按风险抽样详细事件，并限制每会话/每错误的上限。成本优化不能只在后端丢弃，因为敏感数据一旦上传就已越过边界。

### 十四、验证可观测性是否真的可用

选择一个关键任务，画出从用户操作到前端阶段、API、后端和业务终态的信号图。注入脚本错误、资源失败、慢交互、API 超时、业务拒绝、离线、路由切换和恢复，检查事件是否归属正确版本、路由与任务，是否没有输入内容和凭据。

演练一次发布：标记版本、只放少量流量、触发 SLO 快速燃烧、停止发布并回滚。值班人员只凭告警与运行手册应能确定影响、关联请求、采取安全缓解并证明恢复。再关闭或延迟遥测管道，确认系统会报告“观测失明”而不是显示虚假健康。

学完后，你应能从用户任务定义 RUM、错误、性能、请求和 Trace 的最小数据合同；能解释实验室与字段数据、硬导航与软导航、日志/指标/Trace 的边界；能建立 SLO、错误预算和可行动告警，并在采样、成本和隐私限制下完成发布与恢复验证。继续查证可参考 [OpenTelemetry JavaScript](https://opentelemetry.io/docs/languages/js/)、[OpenTelemetry 浏览器接入](https://opentelemetry.io/docs/languages/js/getting-started/browser/)与 [MDN Performance API](https://developer.mozilla.org/zh-CN/docs/Web/API/Performance_API)。

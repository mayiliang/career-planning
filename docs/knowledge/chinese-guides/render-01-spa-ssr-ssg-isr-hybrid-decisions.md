# Web 渲染策略知识点讲义

## RENDER-01 SPA、SSR、SSG、ISR 与混合渲染决策

渲染模式不是框架阵营，而是对“数据何时取得、HTML 何时生成、结果能被谁复用、脚本何时接管”的工程决定。同一产品的营销页、商品详情、个人订单与实时控制台往往需要不同策略。若把所有页面都套成 SSR 或静态化，会在缓存泄露、数据陈旧、服务器成本和交互启动之间制造新的问题。本讲建立按路由、数据和失败路径作决策的完整方法。

### 学习前先确认

- 直接前置：[NET-01 浏览器网络协议、Fetch 与请求可靠性](../chinese-guides/net-01-browser-network-fetch-reliability.md#net-01)。本讲直接使用 HTTP 缓存、Cookie、状态码、请求取消、CDN 和网络时序；该资料已递归包含浏览器渲染基础。

### 一、把一次页面访问拆成四个时刻

先问数据何时可得、HTML 何时产生、响应何处缓存、交互代码何时就绪。构建时数据稳定可预生成；请求时才能确定身份/库存则需要动态处理；浏览器独有数据可在客户端取得；部分区域还能混合。

性能也分阶段：服务器响应首字节、HTML 中出现有意义内容、关键资源完成、JavaScript 解析执行、事件绑定和用户真正可操作。首屏 HTML 很快不等于交互很快，TTFB 较慢也不一定导致差体验；要结合 LCP、INP、错误与业务完成时间。

### 二、CSR 把初始应用组装交给浏览器

**客户端渲染（Client Side Rendering）**通常先返回应用壳和脚本，由浏览器执行代码、请求数据并生成主要界面。它适合登录后工具、SEO 不重要且交互密集的区域，也便于静态托管与清晰的前后端分离。

代价是初始内容依赖脚本、网络和 API，低端设备会承担解析/执行成本；错误状态可能先白屏，爬虫或链接预览得到空壳，服务端也难返回内容对应的 404/重定向。CSR 不是 SPA 的同义词：客户端导航可与服务器渲染并存，SPA 也可预渲染首屏。

优化 CSR 先减小首路由脚本、并行关键请求、提供可读 HTML 外壳与明确加载/错误，而不是只加全屏 spinner。对公开内容可局部预渲染，对交互区域按需加载。

### 三、SSR 在每次请求时生成 HTML

**服务端渲染（Server Side Rendering）**在请求阶段读取数据并生成 HTML，浏览器可在 JavaScript 完成前看到内容。它适合个性化、强时效、需要正确状态码/元数据和首屏可读的路由。

SSR 把计算与依赖延迟放到服务器路径，数据库慢、冷启动或缓存击穿会拉长 TTFB。生成 HTML 后通常还要 hydration 才能交互，服务端执行与客户端下载可能做重复工作。服务器可扩展性、超时、取消和连接断开都要治理。

包含用户/租户数据的响应不能进入公共共享缓存。缓存键至少覆盖身份、语言、权限和影响输出的头，或使用 private/no-store。SSR 输出也必须最小化序列化状态，防止把服务端秘密送到 HTML。

### 四、SSG 在构建或发布阶段预生成

**静态站点生成（Static Site Generation）**提前把路由变成文件/CDN 对象，请求时直接分发。它适合公开、变化低频、路由集合可枚举的文档、帮助和营销内容，运行成本与攻击面较小，缓存效率高。

构建时间与路由数量、数据源稳定性相关。百万商品全部构建会拖慢发布；构建期请求失败也可能让整个制品缺页。静态不代表永远不变，必须定义内容变更如何触发新构建、缓存清除和旧资源兼容。

不要在构建时注入用户数据或运行时秘密。静态 HTML 可在客户端增强个性化区域，但公共缓存内容保持一致，身份相关信息由安全 API 获取并有加载边界。

### 五、ISR 在静态复用和更新之间设陈旧窗口

**增量静态再生成（Incremental Static Regeneration）**允许页面按时间、事件或按需重新生成，而请求仍可复用静态结果。它适合大量公开路由、允许短暂陈旧且无法每次全量构建的场景。

实现可能采用 stale-while-revalidate：过期后的首个请求得到旧页并触发后台更新；也可能阻塞生成。必须写清正常陈旧上限、触发源、并发再生成去重、失败时保留旧页多久、内容删除怎样返回 404。把 revalidate=60 称为“实时”是误导。

更新数据库不自动使 CDN、框架路由缓存和浏览器缓存一起失效。事件驱动失效需要可靠消息和标签/路径映射；漏事件时还有定期校正。框架版本会改变默认缓存语义，应记录并通过响应头与真实请求验证。

### 六、混合渲染按路由和区域组合

现代应用通常是混合的：帮助页 SSG，商品页 ISR，订单页 SSR，登录后表格 CSR；同一页面的静态文章可服务器生成，收藏按钮客户端增强。选择单位是具有一致数据和缓存性质的边界，而非整个仓库只能选一个模式。

组合时定义所有权：哪个层取得数据、哪份缓存权威、客户端导航是否复用服务端数据、失效如何传播。重复请求可能是刻意的后台刷新，也可能是 hydration 与客户端 query 各自无知，需要用 trace 判断。

框架的 Server/Client Component、loader 或 route config 是实现手段，不应替代通用决策卡。先写路由需求，再映射到当前框架能力，升级时重新验证默认行为。

### 七、缓存设计决定正确性与成本

列出缓存层：浏览器 HTTP、Service Worker、CDN、反向代理、框架数据/路由缓存和数据库查询。每层记录键、TTL、失效、私有性、错误缓存和观测头。只写“用了缓存”无法判断泄露和陈旧。

公共内容的键包含路径、查询、语言和内容变体；身份/权限影响 HTML 时避免共享，或把私有部分移到客户端。Cookie 存在不等于自动不缓存，必须配置 Cache-Control/Vary 和 CDN 规则并用两个账号实测。

缓存击穿通过请求合并、预热、陈旧保底和容量限制缓解。缓存污染、键遗漏和变体爆炸也需测试。失效后同时验证旧对象不再可见、新对象已生成和故障回退符合预算。

### 八、SEO 需要内容、状态码和链接语义

可索引页面应在初始 HTML 提供主要内容、标题、canonical、结构化数据和可抓取链接，并返回真实 200/404/301。客户端稍后把“未找到”画出来，但服务器始终 200，会产生软 404 和分享预览错误。

SSR/SSG 有助于交付内容，不自动保证 SEO。错误 canonical、被 robots 阻止、重复参数页和不可达内部链接仍会失败。CSR 也可能被搜索引擎渲染，但延迟、预算与非搜索爬虫不同，不能把关键发现完全托付给执行脚本。

用抓取工具查看原始响应与渲染 DOM，测试禁用 JS、慢脚本和错误数据。搜索需求与登录私有页面分开，后者不应为了 SEO 暴露内容。

### 九、状态码、重定向与错误边界属于渲染合同

数据不存在、无权、需登录、永久迁移和临时故障分别对应不同状态与页面。服务器渲染有机会在发头前决定；流式开始后状态码可能已经锁定，因此边界设计更重要。静态托管也要配置 fallback，避免所有未知路径都返回 200 应用壳。

错误页应保留全局导航和恢复动作，不能因一个次要数据源失败让整页 500。对公开静态页，构建失败决定阻断发布还是保留上个版本；对 SSR，依赖超时可降级非关键区域，并记录部分响应。

客户端导航与完整刷新必须得到一致业务结论。只测 SPA 内跳转会漏服务端 404、缓存头和重定向链。

### 十、Hydration 与脚本预算不能被忽略

服务端 HTML 可读后，JavaScript 仍需下载、解析、恢复状态和绑定事件。组件树越大、序列化数据越多，交互延迟和 mismatch 风险越高。减少客户端边界、按交互拆包、避免重复数据和主线程长任务。

首屏性能比较至少记录 HTML 大小、脚本字节、请求 waterfall、TTFB、LCP、INP 与 hydration 时段。只比较后端模板生成时间会偏向 SSR，只比较缓存命中会掩盖更新成本。

禁用 JS 验证内容和基础链接是否可用，不要求所有复杂工具无 JS 完整运行。关键提交若依赖 JS，加载失败时提供明确状态而非看似可点的死按钮。

### 十一、数据时效与个性化形成决策轴

公开/私有、稳定/实时、可共享/用户专属、可枚举/动态路由是比“博客还是应用”更精确的轴。把每个路由放入矩阵，并记录更新来源、允许陈旧、SEO、首屏任务、部署平台和故障策略。

库存可能公开但强时效，适合静态商品描述加客户端/服务器实时库存；个人订单强私有，不进入公共缓存；新闻文章可静态，推荐列表个性化增强。不要因页面含一个动态小部件就放弃整体静态化，也不要因主体公开就静态化所有敏感边栏。

决策卡有 owner 和复核时间。业务、流量和平台变化后重新测量，而不是把早期模式当永久架构。

### 十二、部署平台约束必须进入选择

静态站可在对象存储/CDN，SSR 需要服务器、函数或边缘运行时，ISR 需要共享缓存与并发再生协调。多区域渲染还面对数据位置、一致性和冷启动；边缘运行时的 Node API、连接和执行时限可能受限。

制品发布要兼容旧 HTML 引用的旧 chunk。删除历史资源过快会让缓存页面加载失败；HTML 与资产使用内容 hash、保留窗口和原子部署。回滚时数据库、缓存 Schema 与旧代码也要兼容。

成本模型包括构建分钟、请求计算、数据出口、缓存命中、失效风暴与运维复杂度。没有团队能力维护的高级缓存模式，可能比简单 SSR/CSR 更不可靠。

### 十三、迁移采用路由级渐进与可回滚证据

从 CSR 迁移时先选公开、边界清晰路由，记录基线 HTML、状态码、性能与错误。引入服务器数据层和缓存，保持客户端交互，再比较搜索、用户指标和成本。不要一次重写全站且无法归因。

从 SSR 静态化时验证数据时效和失效；从 SSG 转 ISR 时注入更新失败、并发再生和删除内容；从传统服务器模板引入客户端增强时控制脚本预算与可访问性。

用 feature flag 或流量切分灰度，监控模式特有指标并准备路由级回滚。回滚验证真实旧制品和缓存，不只是配置里存在一个开关。

### 十四、验证必须包含冷、热、失效和故障路径

为每个代表路由抓取原始 HTML、响应头、状态码、缓存状态与资源 waterfall；在冷启动、缓存命中、过期再生、数据更新、依赖超时、权限变化、禁用 JS、低端设备和慢网下重复。两账号测试私有数据隔离。

性能采用多次样本和分位，记录设备、网络、区域、框架/运行时版本。现场 RUM 验证实验室结论，按路由和缓存命中拆分。搜索用真实抓取/日志，而不是只看浏览器最终 DOM。

断言包括：公开正文是否在初始 HTML；私有数据是否从未进入共享对象；404/重定向是否真实；陈旧窗口是否符合承诺；再生失败是否有界；旧 HTML 是否仍能加载资源。

还要检查语言、设备提示和实验分组是否进入正确缓存键；验证浏览器后退、直接深链接与分享预览得到一致路由事实。所有测量保存响应样本、构建摘要和采集时间，避免用无法重放的单张性能截图下结论。

### 十五、常见反例与适用边界

- 宣称某模式普遍更快、更 SEO 或更现代，未按路由分析。
- 带 Cookie 的个性化 HTML 进入公共 CDN，缓存键缺身份。
- 把 ISR 称为实时，没有陈旧窗口、失败和删除语义。
- 只测客户端导航或热缓存，不测完整刷新、冷启动与失效。
- SSR 返回内容却发送过多脚本，交互仍长时间不可用。
- 框架默认缓存随升级改变，团队没有响应头与行为回归。

内部工具可选择简单 CSR，稳定文档可选择纯 SSG；不必为了展示所有术语强行混合。最佳策略是在当前约束下最简单地满足内容、时效、安全、体验和运维目标。

路由重定向、404 与权限拒绝也属于渲染输出，不能全部等客户端启动后再修正。

### 十六、学完后应能说明

你应能为不同路由写出数据时机、HTML 生成、缓存复用和交互接管链；比较 CSR、SSR、SSG、ISR 的成本和故障；设计私有/公共缓存与状态码；用冷/热/失效/权限/禁用 JS 证据验证；并以路由级迁移和回滚逐步调整，而不是选择一个全站口号。

继续查证可参考 [web.dev Rendering on the Web](https://web.dev/articles/rendering-on-the-web) 与 [RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)。

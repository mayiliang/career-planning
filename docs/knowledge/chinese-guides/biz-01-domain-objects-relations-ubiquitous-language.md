# 业务领域建模知识点讲义

## BIZ-01 业务对象、关系与统一语言

复杂业务代码难维护，往往不是因为 TypeScript 写得不够漂亮，而是团队对“订单、名额、候补、退款、用户”等词没有共同且精确的含义，规则散落在页面、接口和数据库里。领域建模从业务事实出发，识别有身份的对象、按值比较的概念、一致性边界和共同语言，让界面、服务、测试与业务人员能讨论同一套模型。

### 学习前先确认

- 本讲没有硬前置。示例使用少量 TypeScript 表达业务关系；不熟悉语法时可先看代码旁的中文规则，概念不依赖特定框架、数据库或面向对象语言。

### 一、模型是对业务决策有用的简化

模型不复制现实的全部细节，只保留当前问题需要的概念与规则。课程报名系统关心课程、学员、名额、报名和候补；未必关心教室油漆颜色。换成财务上下文，同一个人可能只以付款方身份出现，属性与规则都不同。

建模从行为问题开始：谁发起什么命令；哪些事实决定结果；哪些状态必须保持一致；失败如何表达。先画数据库表再给每表生成类，容易把存储结构误当业务模型。模型会随理解演进，代码、术语表和测试要一起更新。

### 二、实体由持续身份而不是当前属性定义

**实体（Entity）**是需要在时间中持续追踪的领域对象。两位同名学员不是同一个人；订单改了地址仍是同一订单。身份可以是业务生成的 ID、组合键或外部权威标识，但必须在上下文内稳定。

实体相等通常比较身份，而不是所有字段。身份创建、传递和映射要有边界：数据库自增键未必适合作为跨系统业务身份；邮箱会变化，不应随意作为永久身份；前端临时 ID 与服务端正式 ID 需要显式关联。

实体不仅存数据，也应保护与自身生命周期紧密相关的行为。例如 Enrollment 可记录状态变化和时间，但“课程是否还有名额”可能属于更大的课程聚合规则。

### 三、值对象按完整值表达概念

**值对象（Value Object）**没有独立生命周期，以所有组成值判断相等。金额由数值和币种共同定义，日期范围由开始和结束共同定义，地址在某些上下文也可作为一个整体值。

值对象适合不可变：创建时校验，改变时生成新值。这样可以把规则集中在构造入口，避免出现 `amount=100` 却不知道币种，或结束早于开始。值对象不等于“没有 ID 的任意对象”；若业务需要追踪某个地址的审核、历史和责任，它可能应成为实体。

```ts
type Currency = 'CNY' | 'USD';

type Money = Readonly<{
  cents: number;
  currency: Currency;
}>;

function addMoney(a: Money, b: Money): Money {
  if (a.currency !== b.currency) throw new Error('CURRENCY_MISMATCH');
  return { cents: a.cents + b.cents, currency: a.currency };
}
```

### 四、聚合定义一次业务提交的一致性边界

**聚合（Aggregate）**是一组必须通过同一入口维护业务不变量的对象，聚合根是外部修改的唯一入口。课程及其当前报名名额可以组成聚合；报名命令通过 Course 执行，不能让页面、控制器和子对象各自扣一次容量。

聚合不是把所有有关对象放进巨大对象图。边界通常由“哪些事实必须在一次业务事务内保持一致”决定。跨聚合只保存对方身份，通过领域服务、事件或流程协作；把学生全部详情嵌进 Course，会放大加载、锁竞争和耦合。

聚合根在提交结束时保证不变量。外部流程可能最终一致，但聚合内部不能暂时产生可被观察的非法状态。并发命令还需要版本或条件写入，单靠内存检查无法阻止两个请求同时抢最后名额。

### 五、不变量是任何合法操作后都必须成立的事实

“课程已录取人数不能超过容量”“已取消订单不能发货”“余额不能在未授权透支时为负”都是不变量。它们应写成可执行规则和测试，并由拥有所需事实的边界保护。

校验输入格式与保护不变量不同。`capacity` 是正整数属于值合法性；一次报名后录取数不超容量属于状态规则。前端提前校验改善体验，却不是可信保护，因为请求可被并发或伪造。

规则失败返回领域原因，如 COURSE_FULL、ALREADY_ENROLLED、COURSE_CLOSED，而不是只抛“操作失败”。应用层把原因映射为 API 和 UI 表达，领域层不依赖按钮文案。

### 六、统一语言贯穿对话、代码和证据

**统一语言（Ubiquitous Language）**是领域专家、产品、设计、开发和测试共同使用的严谨词汇。它不只是词典；命令、事件、类型、接口、日志和验收都应采用一致含义。

如果业务说“候补”，API 返回 `success=true`，页面显示“报名成功”，测试叫 `should enroll second student`，团队实际上没有统一语言。应明确 ENROLLED 表示已获得名额，WAITLISTED 表示进入候补队列，REJECTED 表示不能报名；每个状态的后续能力也不同。

语言允许演进，但变更要显式。将“用户”拆成“账户持有人、学员、付款人”时，记录原因、影响范围和迁移计划，避免新旧词混用。

### 七、限界上下文让同一个词拥有局部精确定义

大型系统里同一个词可能在不同上下文有不同模型。销售上下文的 Product 关心价格和可售，仓储上下文的 Product 关心 SKU、批次和库存。强行建立一个包含所有字段的全局 Product，会让每个团队依赖不需要的规则。

限界上下文划定语言和模型适用范围，并定义上下文之间怎样转换。上下文不是自动等同微服务、代码包或团队，但这些边界经常应相互对齐。初期模块化单体也能有清晰上下文，不必为了“DDD”拆成分布式系统。

上下文地图记录上游、下游、共享内核、防腐层和公开合同。外部供应商的 `status=1` 不应渗透整个领域，通过防腐层转换为本地明确概念。

### 八、关系要表达业务语义而不只是外键

一对多、多对多只是结构。Course 与 Student 之间通过 Enrollment 关联，Enrollment 本身有身份、状态、时间和来源，因此不是一张可忽略的连接表。把它扁平成 `course.studentIds` 会丢掉候补、取消和历史。

关系还要说明方向、基数、生命周期和所有权。删除课程是否删除报名历史？学员合并如何处理身份？候补转录取产生什么事件？这些问题决定聚合边界和引用方式，不能由 ORM 默认级联替业务回答。

跨聚合引用 ID 能减少对象图耦合，但读取页面需要投影或查询模型。写模型保护规则，读模型为界面组织数据，两者可以不同；不要为了一个页面方便就破坏写入边界。

### 九、DTO、领域对象和展示模型职责不同

DTO 表达跨进程传输合同，领域对象保护业务行为，展示模型服务具体界面。三者字段可能相似，但不应直接当作同一对象。服务端新增未知状态时，前端 DTO 解析需要兼容策略；领域转换决定本地含义；展示层提供诚实降级。

```ts
type EnrollmentStatus = 'ENROLLED' | 'WAITLISTED';

function toEnrollmentView(status: EnrollmentStatus) {
  switch (status) {
    case 'ENROLLED':
      return { label: '已录取', canPay: true };
    case 'WAITLISTED':
      return { label: '候补中', canPay: false };
  }
}
```

映射器集中且穷尽，避免每个组件自己判断。不要让领域对象直接依赖 CSS、路由或 API 序列化注解。

### 十、领域事件记录已经发生的业务事实

命令请求发生某事，如 EnrollStudent；事件陈述已经发生，如 StudentWaitlisted。命令可以被拒绝，事件名称使用过去式并携带稳定身份、版本和必要事实。

事件可驱动跨聚合流程、审计和读模型，但发布可靠性需要事务/outbox、幂等消费和顺序策略。领域事件不是把内部对象完整广播；公开集成事件需要版本、隐私和兼容治理。

事件历史有助于理解状态，却不强制采用事件溯源。多数系统使用当前状态加审计事件即可，选择更复杂模式要有恢复、查询或审计需求支撑。

### 十一、并发暴露真正的一致性边界

课程容量为 1，两个请求同时读取已录取数 0，都在内存判断可报名，再分别写入，就会超卖。聚合方法写对仍不够，持久化必须用事务锁或 `WHERE version = oldVersion` 的条件更新，使只有一个提交成功，另一个基于最新状态转候补或冲突。

跨聚合事务往往不宜无限扩大。付款成功后开通课程可使用流程状态和幂等事件协调，允许短暂中间态并提供补偿/人工恢复。把“一致性”分为必须立即成立和允许最终收敛，才能选择恰当边界。

### 十二、模型验证需要业务人员和可执行反例

维护术语表：词、定义、同义/禁用词、所在上下文、示例和负责人。用事件风暴、示例映射或流程访谈发现命令、事件、规则和例外；再把关键不变量转成自动测试。

以容量为例，验证容量 0、1、2，重复报名、取消后释放、并发抢最后名额和课程关闭。测试不仅看返回状态，还看聚合版本、事件和未改变事实。让业务人员审阅“候补是否占容量、是否可付款、何时自动转正”，歧义在进入代码前解决。

模型质量不以类数量或模式数量衡量，而以语言是否减少误解、规则是否集中、变化影响是否可定位、失败是否可解释来衡量。简单 CRUD 没有复杂规则时，贫血数据模型可能足够，不必强行套聚合。

### 十三、从真实语言中的歧义发现模型缺口

收集客服话术、工单、接口字段、页面文案和测试名称，找同词异义与同义异词。例如“取消”可能指撤销未支付订单、申请退款或停止自动续费，三者权限、时限和副作用不同。把模糊动词改成明确命令，并与业务人员用具体例子确认。

例子映射可以按“规则—正例—反例—疑问”展开。若团队无法判断一个边界例子，先记录待决问题，不让开发者各自在代码里做默认决定。决定后同步术语表、规格、Schema 和测试，避免只有会议纪要更新。

### 十四、前端也需要领域边界而不是只消费字段

前端不负责最终业务授权，却需要用领域语言组织状态、命令和失败。组件发出 `submitEnrollment`，应用层调用 API 并把 DTO 转为本地结果，展示层依据 ENROLLED/WAITLISTED 显示不同能力；不要让页面散落 `status === 1`、`capacity - 1` 和文案判断。

在客户端缓存中保存服务端事实与本地草稿的区别。乐观更新只用于可回滚、冲突合同明确的动作；最后名额、余额和权限不能由前端自封为成功。服务端返回新状态时，未知值安全降级并记录，不能落入默认成功分支。

### 十五、模型演进需要兼容与数据迁移

把 WAITLIST 改名为 WAITLISTED 看似只是词汇调整，却涉及数据库值、API 枚举、事件、指标、前端和历史报表。采用扩展—迁移—收缩：先让读者接受新旧值，生产者切换并迁移存量，观察无旧值后再移除兼容。

聚合边界变化更昂贵。拆分巨大聚合时定义跨边界流程和暂时一致性；合并时评估锁竞争与迁移。为每次重要模型决定写简短 ADR：问题、语言、边界、被拒方案和后果，使后续团队知道设计不是偶然类结构。

### 十六、读模型与分析指标也要尊重领域语义

报表把 WAITLISTED 计入“报名成功”会让产品指标误导决策。指标定义引用术语与事件版本，说明分母、时间窗口、去重身份和迟到事件。展示投影可为查询扁平化，但字段名仍要保持业务含义。

回填和重算使用事件或权威状态，不能从页面埋点猜核心事实。分析上下文可以有不同聚合方式，却通过明确映射连接交易上下文；否则同名指标在不同团队得到不同答案。

模型评审时让业务、前端、后端、测试和数据人员分别用同一例子复述结果。如果有人把候补解释成成功、有人把取消解释成删除，就说明语言仍未收敛，应先修正定义和示例再扩展实现。

### 常见误解

- 实体不是数据库表的同义词，值对象也不是任意无 ID 对象。
- 聚合不是“相关对象的最大集合”，而是一致性和提交边界。
- 前端校验提升体验，不能独自保护并发业务不变量。
- 统一语言不是一次整理后不再变化的名词表。
- 采用领域建模不要求立刻使用微服务或事件溯源。

### 学完后应能说明

你应能从业务命令和不变量识别实体、值对象、聚合与关系，建立在限界上下文内成立的统一语言，把 DTO、领域对象和展示模型分开，解释并发为何需要持久化保护，并用术语表、反例和可执行测试验证模型是否真正减少歧义。

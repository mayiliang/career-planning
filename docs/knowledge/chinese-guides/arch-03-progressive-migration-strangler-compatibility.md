# 渐进迁移、Strangler 与兼容层知识点讲义

## ARCH-03 渐进迁移、Strangler 与兼容层

重写旧系统最危险的部分不是新代码能否运行，而是新旧系统在数月甚至数年的共存中如何路由、共享身份、同步数据、比较结果、回滚并最终删除旧路径。渐进迁移通过可观察的垂直切片降低一次性风险，但会引入双运行、兼容和数据一致性成本。只有每个阶段都有边界、闸门和退出，渐进才不是把两套系统永久叠在一起。

### 学习前先确认

- 直接前置：[ARCH-02 技术方案、ADR 与架构评审](../chinese-guides/arch-02-technical-proposal-adr-review.md#arch-02)，用于明确迁移 driver、候选、责任、风险和退出条件。其前置会递归提供质量场景基础。

### 一、先证明为什么要迁移

迁移原因可能是交付阻塞、安全与支持期限、性能、可靠性、成本或业务变化。把原因量化为现状基线与目标场景：发布等待、事故、依赖生命周期、用户任务成功、维护工时和风险。单纯“代码旧”或“团队想换框架”不足以支撑长期迁移。

比较维持现状、局部修复、渐进替换和整体替换。小且可停机系统、法规要求快速退役或旧系统无法拦截请求时，大爆炸可能更合理；渐进不是道德正确，而是一种对风险与成本的选择。

定义完成：哪些能力、数据和流量转移，哪些旧组件、配置、账号和基础设施删除，哪些指标证明收益。没有退役定义的项目只能叫并存建设。

### 二、建立现状地图和迁移不变量

绘制用户入口、路由、模块依赖、数据 owner、共享状态、身份、事件、部署、外部集成和运维流程。分析运行时流量而不只静态 import，因为动态调用、脚本和人工流程也会绑定旧系统。

迁移不变量是任何阶段都不能破坏的事实，例如订单只扣款一次、权限不跨租户、已确认数据不丢、用户可恢复、审计可追溯。把它们转成契约测试、对账和监测，作为每个切片共同闸门。

未知依赖先观测。通过访问日志、trace、事件与 owner 访谈确认，避免删掉“看起来无人使用”的旧路径。标记无 owner 和不可观测部分为风险。

### 三、Vertical Slice 以用户结果切分

**垂直切片（Vertical Slice）**贯穿入口、界面、API、数据、权限与观测，能独立完成一个可识别任务。按技术层“先重写所有组件、再重写所有接口”会长时间没有用户价值，也无法验证真实边界。

选择边界清晰、业务价值足够、风险可控制且有代表性的第一片，例如只读订单详情，而非最核心支付写入。切片小到可回滚，又大到能暴露身份、数据和部署问题。完成后复盘成本，调整下一片。

每片有 owner、输入输出合同、现状基线、流量策略、数据一致性、失败降级、闸门和旧路径删除。不能只按页面视觉完成判定。

### 四、Strangler Fig 用外部边界逐步替换

**绞杀者模式（Strangler Fig）**在客户端与新旧系统之间建立 façade/路由边界，逐步把具体功能转到新实现，最终退役旧实现和临时 façade。用户保持稳定入口，迁移单元可独立切换。

路由键可以是路径、租户、用户、功能、数据版本或明确 feature flag。它必须稳定、可观测并避免同一写请求随机落到两边。Façade 不能承担越来越多业务逻辑，否则会成为新单体、瓶颈和单点。

并非所有系统可拦截或分割。紧密共享数据库、内部调用和全局事务会限制。此时先建立接口、事件或数据 owner 边界，或选择另一策略。模式名称不能替代可行性分析。

### 五、Anti-Corruption Layer 隔离旧语义

**防腐层（Anti-Corruption Layer）**在新旧模型之间转换字段、状态、错误和调用，使新系统不必继承旧系统的混乱语义。它是过渡适配器，不是把所有调用再包装一遍。

转换规则版本化并测试：单位、时区、空值、枚举、ID、权限和错误不能靠隐式默认。未知旧状态进入明确 quarantine/unsupported，不强行映射。双向转换要说明是否可逆，信息丢失时禁止盲目回写。

防腐层有使用遥测、owner 和删除条件。若新功能继续依赖它作为永久公共 API，需要重新承认其长期地位并治理，而不是继续称临时层逃避责任。

### 六、读迁移从影子比较开始

影子读把同一规范化请求发送到新系统，但用户仍看到旧结果；比较器按业务语义检查差异。忽略时间戳、排序等允许差异，重点验证金额、权限、状态、缺失和性能。影子路径无副作用并受预算限制。

比较记录请求版本、数据快照、两边结果摘要和差异类别，不保存不必要敏感正文。差异可能来自真实数据变化、缓存时点、转换规则或新实现 bug，需要可关联 trace 分析。

达到样本量与差异阈值后，小流量切读，并保留快速回退。只有正常样本通过不够，还要覆盖边界、权限、错误、低网和峰值。

### 七、写迁移先确定唯一权威

双写最容易制造两个真相。优先选择一个系统作为 system of record，另一边通过事务外盒、事件或可重试同步派生。若请求同步写两边，定义顺序、部分失败、幂等、补偿与对账；不能假设网络同时成功。

每个业务操作有稳定 operationId 和版本。重复交付幂等，乱序按版本拒绝或合并，未知结果查询状态。数据转换丢失字段时，不进入反向覆盖。高风险写先从低影响范围和人工监测开始。

双写只是过渡。记录流量、延迟、积压、差异和修复成本，设退出日期。永久双写会把每次业务变化变成两套修改和无限一致性风险。

### 八、缓存、会话和身份必须一起切换

代码回滚后仍读新缓存，是常见隐藏失败。缓存键包含实现/数据版本与租户，切换和回滚有明确清除或旁路策略。不要让新旧系统共享含不同语义的无版本缓存。

用户会话在新旧域、Cookie、token 和 CSRF 边界间保持安全。身份声明和授权仍由共同受信来源验证，不能为迁移临时接受客户端角色。跨域嵌入还要处理 CSP、Cookie 与焦点。

功能开关作用域、默认值、owner 和紧急操作明确。服务端与客户端看到不同开关版本时，以安全策略为准并可恢复，不能形成半切换界面。

### 九、Migration Gate 以证据控制推进

**迁移闸门（Migration Gate）**是进入下一阶段前必须满足的可测条件，例如差异率、错误率、延迟、业务成功、数据积压、支持工单、无障碍与回滚时间。闸门也包含立即停止阈值。

每个指标定义分母、窗口、样本和责任人。总体差异 0.5% 可能掩盖某租户 100% 失败，需按风险分层。只有 dashboard 绿灯不够，还要执行故障、权限和回滚演练。

闸门改变需新决策记录，不为赶期限临时调宽。异常时暂停新流量、保持已稳定切片，不一定全部从头回退。渐进的价值正是局部收敛。

### 十、回滚区分路由、代码和数据

路由回退可快速让读取返回旧系统；代码回滚恢复旧制品；数据回滚涉及已经确认的新写入，通常不能简单覆盖。预先定义每类状态的恢复、补偿和人工对账。

回滚窗口基于检测速度、数据兼容和业务容忍。数据库采用 expand/migrate/contract，先兼容双版本，再迁数据，最后删除旧列；不可逆压缩或语义改变前留备份与验证。

演练实际执行开关、缓存、任务、队列和告警。文档中一句“可回滚”没有价值。演练失败要阻止扩大流量。

### 十一、前端跨框架迁移控制共享边界

决定路由、设计 token、组件、状态、事件和依赖由谁拥有。多个框架直接共享可变 store 会产生更新语义冲突；更稳妥的是通过 URL、明确消息、服务端状态或版本化接口交互。共享组件需框架无关合同与无障碍测试。

双框架期测总包体、重复 runtime、解析/执行、样式隔离、错误边界和开发者工具。按路由或岛屿延迟加载，避免所有用户下载两套。CSS 与全局事件有命名/所有权边界。

React 的渐进接入可以从页面局部 root 开始，但产品迁移仍需数据、身份、监测和退出。一个 demo 能渲染不证明架构可迁移。

### 十二、组织和发布拓扑也在迁移

明确新旧系统的 on-call、代码 owner、发布批准、事故指挥和支持。两套系统无人统一负责时，故障会在团队间转交。迁移路线与团队容量、培训和依赖协商一致。

发布单元应支持切片独立推进但保持合同兼容。流水线验证新旧组合，而不是只测最新全套。制品、配置和数据迁移版本可追踪。

迁移工作不能永远挤在功能余量。把减少旧责任和删除计入里程碑；只奖励新增新系统会导致遗留永存。

### 十三、旧路径退役是最后一个产品功能

退役前用流量、调用图、数据、账号、队列、定时任务和人工流程证明无依赖。通知消费者并观察弃用窗口。备份和合规保留与在线执行路径分开。

删除旧代码、路由、缓存、数据副本、凭据、监控、基础设施和文档，更新应急流程。保留无法执行的历史审计不等于保留生产服务。删除后观察错误和意外调用，准备有限恢复。

核对迁移收益与原目标：交付、事故、性能、成本或支持是否改善。若只完成技术替换而业务指标未变，分析假设或执行问题。

### 十四、用失败注入验证迁移体系

测试影子结果差异、重复/乱序事件、双写部分失败、缓存版本错、旧 Client、权限变化、开关不同步、新系统超时、回滚后迟到写和对账积压。断言不变量保持，状态可解释。

保存相同输入下的新旧结果与 trace，修复后回放。敏感数据脱敏，影子流量也遵守目的与地区。性能验证包含 façade 和双运行额外成本。

可参考 [Azure Strangler Fig Pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig) 与 [React 渐进接入](https://react.dev/learn/add-react-to-an-existing-project) 理解通用模式和局部接入方式，但具体切片、数据和闸门必须来自项目事实。

### 十五、为数据迁移建立可重复作业

数据回填按可分片、可暂停、可重试和幂等设计，记录 source version、目标版本、cursor、成功/失败数量与校验摘要。不要用一次性手工脚本直接改生产且没有状态。回填与在线写并存时，定义版本比较，防止旧批次覆盖新更新。

校验分结构、数量、业务不变量和抽样内容。总行数相同不说明金额与归属正确；哈希不同也可能只是允许的排序/格式。差异进入隔离队列，有明确 owner 修复和重放，不能无限跳过坏记录。

迁移完成后保留可审计摘要而非无期限复制全部敏感数据。旧数据删除遵守保留与法律要求，并验证备份和索引路径。

### 十六、处理无法双写的外部副作用

支付、邮件、短信和第三方创建不能安全地向新旧系统各执行一次。选择唯一执行方，另一方只观察事件或录制结果；用 operationId、outbox 与状态查询传递事实。影子流量禁止到达真实副作用端点。

切换执行方时冻结/排空在途队列，记录最后旧序列与第一新序列，确保没有缝隙或重叠。网络未知结果先向第三方对账，再决定补偿。回滚可能只回路由，已发生外部动作继续由统一账本负责。

对无法撤销动作提高预览、审批和灰度门槛。迁移速度不能优先于资金、消息和用户信任。

### 十七、观察迁移本身的健康度

除业务指标外，跟踪每切片周期、差异清理、兼容层增长、双运行成本、旧代码删除、支持工单和团队负担。新流量比例提高但旧责任没有下降，说明迁移在积累而不是收敛。

迁移 dashboard 连接到具体版本、路由键、数据批次和 owner。按租户/设备/场景分层，防止总体成功掩盖少数组失败。指标异常必须能触发暂停或回退，不只是月报。

定期重新估算完成成本和目标收益。若约束变化让原目标不再合理，可以停止并固化当前稳定边界；停止不是失败，永久保持无人治理的半迁移才是。

### 十八、管理迁移期的合同版本

新旧消费者可能同时存在，API、事件和组件合同使用扩展优先的兼容演进。先让生产者发双方可读数据，再升级消费者，观察旧使用量，最后删除。不要在同一发布中改变字段含义并假设所有调用者同步。

契约测试覆盖新生产者—旧消费者、旧生产者—新消费者等真实组合。未知字段、枚举和错误有显式处理；旧客户端不能因新状态崩溃或绕过权限。弃用通知有可识别消费者与截止。

版本数量受控，兼容窗口越长成本越高。超过窗口的消费者由 owner 升级、隔离或停止，不能让一个未知客户端永远阻止退役。

学完后，你应能从现状依赖图选择一个垂直切片，设计 façade、防腐层、影子读/双写、缓存与身份策略，为每阶段设置闸门并演练回滚，最后证明旧路径真正退役。渐进迁移的完成标志不是新系统上线，而是风险受控地转移责任并删除过渡结构。

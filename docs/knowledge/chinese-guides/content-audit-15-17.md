# 15–17 域中文学习讲义

本讲义是知识点的中文首考材料；每节同时给出定义、运行机制、适用边界和可复核练习。外部英文一手文档只用于核对版本与术语，不能替代本讲义作答。

## AIDEV-01

把已验收的需求拆成版本化的任务合同：输入规格、允许读写路径和命令、预算、停止条件、检查点及证据格式。Agent 每一步都应先读取被允许的最小上下文，再执行、验证和回传；需求冲突、权限不足、测试失败或预算耗尽时停止并交人工。输出应能对应到验收项，而不是一段“完成了”的说明。

### AIDEV-01 深入学习：执行合同而非聊天记录

**概念与问题。** AI 协作合同解决“模型拿到一句需求就直接改仓库”的不可控问题。合同的输入是已验收的需求版本、验收项和允许的事实来源；输出不是泛化说明，而是带任务编号的 diff、命令日志、测试结果与人工待决项。适合可拆为小切片、能运行验证的改动；对需求尚未定稿、需要产品判断或不可逆生产操作，应先交给人。

**分步机制。** (1) 固定规格版本与基线提交；(2) 列出仅可读写的路径、允许命令、网络和时间/费用预算；(3) Agent 先输出计划和风险，再一次只执行一个检查点；(4) 每步用构建、测试或浏览器证据验证；(5) 证据回填验收表，未满足项保持失败状态；(6) 遇到需求冲突、权限拒绝、预算耗尽或连续两次同类失败，停止并升级。这样可把模型输出限制在可审计的状态机内。

**示例、反例与验证。** 例如“为订单列表添加只读筛选”：合同允许改 `src/orders/**`、运行指定测试，不允许读取 `.env` 或发布；产物应含筛选规则、测试截图和命令退出码。反例是把整仓库和生产令牌放入上下文，再由 Agent 自判“完成”。练习时故意提供过期规格、越界路径和失败测试，检查它是否拒绝继续；验收清单须能逐项定位到输入版本、diff 与复现命令。

**检查清单。** 开始前确认规格版本、允许范围、预算和负责人；执行中记录每个检查点；结束时由非执行者复核 diff、命令退出码和验收项。任何缺少输入版本、证据链接或升级记录的产物都只能算草稿，不能进入合并或发布。

**复盘问题。** 若任务在中途换了验收版本，应撤销后续自动改动并重新确认，而不是把旧证据拼接到新需求。复盘时比较计划、实际工具调用、失败次数和人工介入点，修改合同模板；下一次演练应能证明新停止条件比旧条件更早阻止越界。

## AIDEV-02

上下文工程以任务为单位选择最少而充分的规则、代码地图、接口契约和事实来源。仓库指令应分层、就近、带作用域和更新日期；资源 URI、缓存键与失效条件必须可追踪。不得把密钥、整仓库或未经验证的摘要塞给模型；抽样复跑十个任务，记录命中规则、输入版本、成功率和失败原因。

### AIDEV-02 深入学习：选择事实并防止上下文漂移

**概念与问题。** 上下文工程不是增加提示词长度，而是在有限预算内给出完成当前任务所需、来源可追踪且不会泄密的事实。它适合有多个模块、规则分散的仓库；不适合用来替代需求评审或把历史聊天当成事实。仓库指令应说明它适用的目录、优先级、维护者和失效日期，局部规则应靠近代码。

**分步机制。** 先把任务拆成目标、受影响模块、接口和验证命令；再从仓库地图选择全局规则与局部规则，记录每条来源 URI、提交版本与读取时间。对缓存的摘要设置键、TTL 和失效事件（规则变更、依赖升级、测试失败）；每次回答标注事实、推断和未知。敏感路径、令牌、客户数据和未核实的网页内容排除在上下文外。发现摘要与源码/测试不一致时，源码和可运行证据优先，并作废摘要。

**示例、反例与验证。** 为支付表单修复校验时，只提供该模块指令、接口契约、失败用例和验证命令；输出应列出读过的文件与未读的敏感目录。反例是复制整个 monorepo、把旧 README 当唯一规则，造成模型修改错误包。练习选十个跨模块任务，分别在有/无地图条件下运行，检查错误率、检索文件数、过期规则命中和密钥泄露是否为零。

**检查清单。** 提交前逐项核对：规则是否有来源、缓存是否可失效、敏感内容是否排除、摘要是否可被源码证伪、十个任务是否均留下输入和结果。不能解释为什么某条上下文存在，或无法重建同一输入时，应删除或重新生成它。

**复盘问题。** 当接口契约、依赖版本或模块边界更新时，旧摘要必须自动失效；否则模型会以历史正确性污染当前任务。要求学习者给出失效事件、重新索引步骤和一次摘要漂移的证据，确认更新后只读取与新任务有关的最小材料。

## AIDEV-03

AI 生成实现、测试和预期值会共享同一误解，测试变绿并不等于正确。针对高风险验收项，至少建立两类相互独立的预言，例如人工规则加浏览器行为、旧系统差分加属性测试；保留随机种子、最小反例、变异杀死结果和可重放回归。覆盖率、页面存在或模型自评不是独立证据。

### AIDEV-03 深入学习：让测试预言独立于生成过程

**概念与问题。** 生成模型若同时写需求解释、实现、测试和期望值，可能稳定地重复同一误解；绿灯只能说明自洽。此点专门为 AI 产出的高风险行为建立独立预言，通用单测框架语法仍归 `TEST-01`。适用于解析、权限、金额、异步状态等可观察行为；主观文案或没有稳定业务规则的探索性原型不能假装已被自动证明。

**分步机制。** 先把验收项转为风险表；为每项选择两个失败相关性不同的证据，例如人工编写的规则表加浏览器 E2E、旧版本差分加属性测试。fuzz 必须保存种子和收缩后的最小反例；变异测试只在基线可信时解释杀死率；快照需要语义断言补充。失败按规格、实现、测试或预言分类，固定输入、环境和版本后进入回归集。

**示例、反例与验证。** 让 AI 实现“仅管理员可导出 CSV”：一类预言从权限矩阵产生输入，另一类从真实浏览器会话观察响应；再注入 `role === 'admin' || true` 的变异体，二者都必须失败。反例是同一提示生成断言“按钮存在”，或仅看覆盖率。练习交付种子、权限矩阵、变异结果、trace 与失败归因，并从干净环境一键重放。

**检查清单。** 交付包至少含验收项—预言映射、独立来源、种子/环境、最小反例、变异或差分结果和回归命令。若两类证据由同一实现或同一错误规则派生，必须合并计为一类，补充独立人工或系统证据后才可宣称通过。

**追问练习。** 当模型声称“所有测试通过”时，要求它指出每条测试的预言来源、哪一类错误仍不可见以及如何制造最小反例；若答不出，就将该结论降级为未验证。把一次错误预言写入回归集，验证后续提示没有重犯。

**复盘问题。** 将一次被放过的线上错误倒推到哪一类预言相关、哪个输入缺失和哪个回归应加入；随后在不修改实现的条件下让新增测试先失败。只有测试能先暴露历史错误，才算真正补上独立证据而非事后叙述。

## AIDEV-04

AI 评审用于提出可验证假设，人负责按影响、可利用性与证据分级并作合并决定。审查变更范围、权限、并发、资源释放、依赖、无障碍和不存在的 API；每条问题写出文件位置、触发输入、预期、实际和复验命令。风格意见不能冒充高危缺陷，未经人工复核的模型建议不能直接合并。

适用场景是影响用户权限、资金、数据、并发或发布安全的实质变更；仅改排版时可简化流程，但不适用以模型评分替代责任人复现。

### AIDEV-04 深入学习：风险证据决定评审优先级

**概念与问题。** AI 可以快速扫描补丁并提出假设，但不能替代作者、评审者和发布责任人。风险分级以影响范围、可触发性、数据/资金/权限后果和证据强度决定，适合变化较大或涉及安全的补丁；纯格式化可走低风险路径，但仍需确认没有语义 diff。

**分步机制。** 获取基线、需求和变更清单，先检查文件范围和新增依赖；再按认证授权、并发、资源、错误处理、可访问性等维度生成待证伪假设。每条意见包含位置、输入、实际路径、预期和复验方法；人复现后标记确认、误报或待决。高危问题阻断合并，中低危必须有明确接受理由；模型置信度不作为证据。

**示例、反例与验证。** 对“删除账号”补丁，AI 指出客户端隐藏按钮却未校验 API；人工用普通用户请求复现 403/200 并记录 Network 证据。反例是把命名风格列为高危，或直接采纳模型修复造成新的竞争。练习提供含权限绕过、未释放订阅和错误吞噬的补丁，输出排序评审表和修复后回归记录。

**检查清单。** 评审输出不能只有“建议修复”；每条结论均须有风险级别、复现输入、文件位置、预期/实际、负责人与验证命令。合并前再检查修复没有删除原断言、扩大权限或引入未审计依赖，无法重现的意见只能作为待调查线索。

**追问练习。** 让评审者解释一条问题若进入生产会经过什么调用路径、为什么现有测试没有拦住、修复后以什么反例证明。无法给出输入和观察点的意见不得升级为缺陷，也不能以模型的措辞漂亮替代复现。

**复盘问题。** 对一个误报和一个真实漏洞分别记录为何初筛相似、最终证据怎样区分、评审者花了多少时间。后续优化只能减少无证据的噪声，不得降低权限、并发、资源和可访问性检查的覆盖；每次规则调整均以历史补丁回放验证。

## AIDEV-06

需要结构化迁移时，以解析后的 AST 和类型信息匹配目标，而非用正则替换源码文本。改写器要有 dry-run、确定性输出、格式化、幂等检查、错误清单和回滚；二次运行不得产生 diff。对含注释、同名符号、类型重载和语法错误的样本分别验证，确认语义等价或明确拒绝处理。

适用场景是规则稳定、可由语法和类型判断的批量迁移；语义依赖领域判断、样本不完整或无法解析的改动不适用自动改写，应转交人工。

### AIDEV-06 深入学习：结构改写必须可证明可逆

**概念与问题。** AST codemod 将源码解析为语法树后按节点和类型改写，避免文本替换误伤注释、字符串或同名变量。适合规则稳定、样本量大、可机械判断的迁移；业务重构、语义不确定或解析失败文件应明确跳过并交人工。

**分步机制。** 定义输入语言版本、匹配条件、变换规则和禁止区域；先 dry-run 输出每个文件的节点匹配与 diff，再写入临时目录并格式化。运行类型检查、测试和二次运行的零 diff 验证幂等；任何单文件解析/写入失败都不提交半成品。保留原始提交、变换版本、文件清单和反向补丁，必要时可整体回滚。

**示例、反例与验证。** 将旧的 `api.get('/x')` 迁移为 `client.get('/x')` 时，只匹配实际调用表达式，不改注释、字符串或自定义同名函数。反例是全局正则替换导致文档 URL 和模拟数据也被改。练习在二十个含嵌套调用、注释、语法错误和类型重载的文件上交付 dry-run、diff、失败清单、二次运行结果和回滚演练。

**检查清单。** 发布迁移前保留 dry-run 文件清单、变换器版本、格式化/类型/测试结果和备份引用；发布后运行第二次并比较零 diff。若任一文件不能解析、注释丢失或回滚不完整，立即停止批量写入，改为人工处理该类语法。

**追问练习。** 在生产样本以外再加入一个近似但不应改写的文件，确认匹配器拒绝它；随后故意中断写入并执行回滚。检查结果必须列出未处理文件，不能用“成功数”掩盖失败和跳过。

**复盘问题。** 同一迁移应支持“只报告”“只改已确认文件”“全部回滚”三种模式；比较三者的文件集合。对格式化导致的无关 diff 设单独阈值，避免评审者看不出语义变更；发现阈值超限即中止并要求人工分批确认。

## AIDEV-07

AI 推荐的包或代码不是可信来源。逐项记录必要性、官方来源、许可证、维护状态、漏洞、安装脚本、包体、版本和 lockfile diff，并检查是否已有能力可复用。来源不明、要求执行高风险脚本、携带密钥或不能给出许可证的建议应拒绝；通用制品签名和 SBOM 的治理另由 ENG-08 负责。

### AIDEV-07 深入学习：AI 推荐不等于可引入依赖

**概念与问题。** 依赖或复制代码一旦进入仓库，会带来维护、许可证、漏洞、安装脚本和来源不明的风险；模型推荐只是线索。此点只审计 AI 建议的新增内容，不与通用 SBOM/制品晋级重复。适用于每次新增包、复制片段或升级建议；紧急修复也必须留下例外期限和后续复审。

**分步机制。** 对每项建立台账：需求、替代方案、官方来源、发布者、许可证、最近维护、版本、漏洞、install/postinstall、体积、权限和 lockfile diff。锁定解析后的版本并在隔离环境安装；风险超过阈值则拒绝、替换或要求人工例外。来源证明只能说明制品由某工作流产生，不保证它适合业务，仍需许可证和功能复核。

**示例、反例与验证。** AI 建议十个日期库时，先证明原生 API 或现有库不能满足；对于带 postinstall 的包，隔离观察脚本并审查网络访问。反例是因下载量高而直接安装，或复制未知 gist。练习输出十行台账、锁文件 diff、扫描结果、拒绝理由与重新安装的可复现命令，确保没有令牌或私有注册表地址进入记录。

**检查清单。** 审计结论必须能回答“为什么需要、来自哪里、会执行什么、固定到什么、出了问题怎样撤回”。缺少任一项则默认不引入；例外必须有风险接受人和到期日。复核人独立从 lockfile 还原清单，确认台账没有被包装名称误导。

**追问练习。** 选择一个下载量高但有高危安装脚本的包，和一个体积较大但完全不需安装脚本的替代方案，写出取舍。再从空目录按锁定版本安装，核对脚本、来源和许可证仍与台账一致。

**复盘问题。** 依赖升级后重新核验发布者、许可证和 install 脚本，不能沿用旧结论。若漏洞无法立即修复，应记录受影响路径、临时缓解、复审日期和撤回版本；到期未复审的例外自动阻止下次发布，而不是永久沉默。

## AIDEV-08

评估 AI 提效先设无 AI 基线，并按相近任务、经验和风险做对照；同时记录交付周期、返工、缺陷逃逸、评审耗时、成本、认知负荷和满意度。结果必须报告样本、缺失数据、学习效应和选择偏差；代码行数或补全次数不能代表效能。若速度提升而返工、缺陷或成本变差，应调整工具、提示或流程而非宣布成功。

### AIDEV-08 深入学习：用对照设计判断而非统计补全量

**概念与问题。** “写得更快”可能转化为更多返工或事故，因此 AI 效能是交付、质量、成本和人的体验共同结果。适合持续的团队流程改进；样本很小、任务差异极大或组织正在大规模变革时，只能得出探索性结论，不能据此考核个人。

**分步机制。** 先定义无 AI 基线和成功/失败指标，再按任务类型、复杂度和开发者经验配对或随机分组；记录从开始到上线、返工、缺陷逃逸、评审等待、工具成本、认知负荷和满意度。预先声明剔除规则，并同时报告中位数、分布、样本量和缺失值。把学习效应、选择偏差、指标博弈与发布窗口分开解释，结论只适用于观察范围。

**示例、反例与验证。** 四周内让相似表单任务轮换使用 AI，代码评审者不知道分组；比较每个任务的完成时间和上线后一周缺陷。反例是只计代码行数或只挑 AI 擅长任务。练习交付原始匿名数据、分析脚本、限制说明和一次“速度提升但返工上升”的处置建议，并让他人复算图表。

**检查清单。** 分析前冻结指标定义和分组，分析后不因结果不好改口径；至少复查一项质量和一项人因指标。团队应把结论写成下一轮可证伪假设，例如缩小允许任务或增加评审，而不是把平均值直接变成个人绩效目标。

**追问练习。** 若某组经验更丰富且任务更简单，即使平均交付更快也不可归因给 AI。要求学习者给出重新分组、扩样或停止试验的决定，并解释该决定对质量、成本和开发者感受的影响。

**复盘问题。** 试验结束后请未参与分析的人检查分组是否被任务难度或人员能力混杂；把一条与预期相反的结果保留在报告中。若成本、返工或满意度的任一恶化超过预设阈值，就停止扩大使用范围并针对根因重新设计试验。

## AIDEV-09

设计稿只提供意图，不是可运行规范。先提取结构、设计 token、状态和断点，再由 AI 产出组件；以固定视口截图、交互状态、键盘流程、对比度和 reduced-motion 复验。字体、素材或无障碍语义缺失时必须显式标注差异，视觉 diff 只能发现差异，不能替代人工确认体验是否正确。

### AIDEV-09 深入学习：把视觉产出变成可复核的契约

**概念与机制。** 设计稿中的颜色、字号、间距、断点和状态命名不会自动变成程序规则；直接要求模型“照图实现”，往往把偶然坐标、示例文案或单一屏幕尺寸固化进代码。先拆出 token、语义组件、状态机和验收视口，再锁定设计版本、浏览器、字体和数据夹具。然后按 token → 组件 → 状态 → 截图 → DOM/无障碍树 → 真实交互的顺序验证，视觉差异只负责定位候选问题。

**可执行示例。** 为订单卡片建立 `Card/Title/Price/Action` 的 token 表，分别在 360、768、1440 像素、中文长标题和加载/错误状态下采集截图；再以键盘 Tab、Enter 和 200% 缩放完成“查看详情”。提交设计版本、token 表、截图基线、差异阈值、无障碍树和复现命令。反例是只在开发机默认字体下截一张首页图，或把丢失焦点解释为“肉眼看不出”。

**限制与练习。** 抗锯齿、字体回退、动态时间和平台渲染会产生噪声，不能把每一像素差异直接视为缺陷。练习故意替换字体、注入长文本、隐藏焦点并修改一个 token；学习者要给出视觉差异、语义检查、根因、修复和同一矩阵的回归证据。只有任务路径与视觉/无障碍证据同时成立，状态才可验收。

**复核清单。** 每次提交均应列明设计来源、token 版本、浏览器与字体、所有覆盖状态、阈值理由和人工结论。若设计稿没有说明错误态、窄屏或动效，必须将它记为待确认需求，不能由 AI 擅自补成产品规则；复测时应让未参与实现的人只用验收清单完成任务。

验收记录还应保留设计与代码的对应关系，避免下一次视觉变化无法追溯责任。

## AIDEV-10

工具准入将数据分级映射到允许的模型、账号、地区、日志和人工审批；默认不发送密钥、客户数据或敏感仓库内容。记录例外审批、保留期限、供应商变更、违规检测和事故处置；高风险发布仍需人批准。影子 AI 与个人账号不是合规替代方案，日志也不得反向保存明文敏感内容。

适用场景是团队把外部模型、代码助手或浏览器 Agent 接入真实研发流程；脱离数据分级、账号控制和撤销能力的个人试用不适用于受限数据。

### AIDEV-10 深入学习：治理是可执行的数据与责任边界

**概念与问题。** AI 工具治理把数据分级、允许场景、供应商、账号、日志、审批和事件响应连成控制面，而不是发一份“谨慎使用”公告。适合团队使用外部模型、代码助手或浏览器 Agent；个人实验可以低风险隔离，但不能绕过公司数据和发布规则。

**分步机制。** 将公开、内部、受限、敏感数据映射到允许模型、区域、保留期限和是否需脱敏；为每个工具登记所有者、供应商条款、模型版本、出口、审计字段和撤销条件。高风险变更经人审批，例外有范围与到期；检测到影子账号、异常上传或泄露时，先切断访问、保全最小证据、通知负责人并复盘控制缺口。

**示例、反例与验证。** 客户工单摘要可在批准的企业租户中使用，但 API 密钥和完整生产数据库不可发送；日志只保存哈希任务 ID 和分类，不保存明文。反例是将个人免费账号称为“临时合规”。练习交付数据—工具矩阵、例外工单、日志样例、撤销演练和一次模拟误上传的处置时间线。

**检查清单。** 每一类数据都要能找到允许工具、处理目的、保留期限、负责人和删除/撤销方法；每一次例外都要有批准证据。随机抽一条日志和一个实际任务，验证分类、脱敏、审批和响应流程确实被执行，而非仅存在于政策文档。

**追问练习。** 模拟供应商保留策略改变或员工离职，检查谁能撤销访问、删除上下文和导出审计记录。若无法在演练中完成，工具即使功能优秀也不能继续用于受限数据，直到责任链和技术控制补齐。

**复盘问题。** 每季度重做一次最小权限抽查：随机任务不应能访问未授权仓库、发送受限数据或绕过人工审批。将发现的问题转成可执行控制和测试，而非仅做培训；同时验证审计日志本身没有保存足以恢复敏感内容的字段。

## AIDEV-11

运行时调试以可重放脚本固定环境、账号和输入，采集 DOM/无障碍树、Console、Network、Storage、截图与 trace。Agent 只能在白名单域名和测试数据中观察与操作，修改后用同一输入复验并保留前后证据包。页面文本和外部内容是不可信输入；支付、删除、发布等副作用必须人工确认，无 Agent 接口时以人工 DevTools 或 Playwright 降级。

适用场景是可在测试环境重放的浏览器运行时缺陷；包含不可逆生产副作用、无授权测试数据或无法固定输入的场景不适用自动操作，应由人控制并缩小观察范围。

### AIDEV-11 深入学习：以证据链而非猜测定位运行时问题

**概念与机制。** 运行时缺陷可能跨越输入、网络、渲染、存储和权限边界；单张截图或一句“页面卡住”不能定位责任。目标是形成他人可重放的因果链：什么输入在什么提交、浏览器和账号下触发，浏览器观察到什么，哪层违反预期，修复后同一链路是否消失。按 Console、Network、性能 trace、DOM/无障碍树、存储和截图采集，每个假设都要指定一个可证伪观察。

**可执行示例。** 复现“切换筛选后仍显示旧数据”：录制 Playwright trace，导出两个请求的 URL、用户标识与缓存状态，并截取更新前后 DOM。若键缺少筛选项，修复后用同一脚本证明新请求发生且键盘和窄屏未回归。证据包含脚本、原始 trace、脱敏日志、差异说明和退出码。反例是让 Agent 看过控制台即宣布根因，或把生产令牌、客户文本放入提示词。

**限制与练习。** 录制本身会改变时序，敏感响应可能不能导出，因此需要脱敏摘要并承认不能取得的证据。练习注入网络超时、hydration mismatch 和权限拒绝；分别写出症状、两个竞争假设、证伪步骤、最小修复和回归。支付、删除、发布等副作用只可在测试环境执行或由人确认。

**复核清单。** 证据包要能对应同一提交、同一输入和同一环境；删除原始 trace 前先保留哈希、采集时间与脱敏规则。修复不得只消除错误日志，也要证明用户任务、权限边界和失败提示都正确；无法重放的偶发问题应以发生概率、采样窗口和下一步观测计划报告。

## LINUX-01

Linux 路径、文件类型、所有者、组和 rwx 权限共同决定访问；软链接指向路径、硬链接共享 inode，`umask` 影响新建文件默认权限。用带引号的路径、预览结果和最小权限执行 `find`、`du`、`tar`、`ln`、`tail`；空格、隐藏文件、符号链接环和通配符都要作为测试输入。删除前先输出匹配清单，生产环境不使用宽泛通配符。

### LINUX-01 深入学习：文件对象、权限与可逆操作

Linux 中路径解析、inode、目录项、所有者、组和权限位共同决定一个操作是否能成功。普通文件、目录、设备、管道和套接字的行为不同；软链接保存目标路径，目标移走即悬空，硬链接共享 inode 且通常不能跨文件系统。`rwx` 对文件和目录含义不同：目录的执行位控制穿越，删除取决于父目录写/执行位，不取决于文件自身。新建文件再受 `umask` 影响，不能只凭 `ls -l` 猜测实际身份。

排查或批处理遵循“先定位、后预览、再最小修改”：以绝对路径和引号处理空格、换行和通配符，使用 `find -print0` 配合零分隔消费者；用 `stat` 确认类型、inode 与权限，用 `du` 区分表观大小与占用，用 `tar -t` 预览归档。修改权限前记录原模式和归属，优先授予组权限而非开放 `777`；符号链接需用 `readlink` 检查目标，递归工具必须明确是否跟随链接。

示例：发布用户需要读取 `/srv/app/releases/v2/config.json` 而不可改写，建立专用组、设置目录可穿越和文件只读，再以该用户执行 `test -r` 与 `test -w` 验证。反例是 `rm -rf $dir/*` 中变量为空或目录含意外通配符，可能越界清理。练习构造空格文件名、隐藏文件、悬空链接和权限拒绝四种样本，提交命令日志、修改前后 `stat`、失败预期和回滚命令；删除必须先打印目标清单并由第二人复核。

**限制与复核。** ACL、挂载选项、SELinux/AppArmor 和网络文件系统还会改变权限位结论；练习需记录这些控制是否存在。把目录交给另一普通用户复跑读、写、删除和穿越检查，验证最小权限不是只对管理员成立，并在归档恢复后再检查 inode 与访问边界。

## LINUX-02

排障按链路从进程、监听 socket、路由/DNS 到 HTTP/TLS 和应用日志逐层取证。`ps`/`top` 看进程和资源，`ss`/`lsof` 查端口，`curl` 和 DNS 查询验证网络，`journalctl` 关联时间线。重启不能代替根因；必须保留命令、时间、目标、输出摘要和修复后的同一路径复验，区分未启动、未监听、被拦截和应用错误。

**定义。** 链路式诊断是把一次不可达现象按进程、监听、名称解析、传输、协议和应用日志分层证伪的取证方法，不是按经验猜测后反复重启。

### LINUX-02 深入学习：沿网络链路定位故障

一次“网页打不开”可能发生在进程、监听 socket、路由、防火墙、DNS、TLS、反向代理或应用任一层。诊断应从客户端可观察事实开始，按时间和连接五元组向内收缩：先确认服务进程及父子关系，再查目标地址端口是否监听，随后验证名称解析、TCP 建连、TLS 握手、HTTP 状态与日志关联。重启会破坏现场且掩盖资源耗尽，不能替代取证。

步骤是：(1) 记录请求时间、主机、URL、解析结果和错误；(2) 以 `ps`/`top` 查进程和 CPU/内存；(3) 以 `ss`、`lsof` 核对监听者和连接；(4) 以 `dig`/`nslookup` 验证 DNS；(5) 用带超时的 `curl -v` 观察 DNS、连接、TLS 与 HTTP；(6) 用 `journalctl --since` 将应用日志与系统事件对齐。每一步只有在前一层正常后才进入下一层，避免凭经验跳层。

示例：端口 8080 可在本机访问、域名访问超时，应分别记录 `ss`、本机 curl、外部 curl、DNS 与入口规则，区分未监听和边界阻断。反例是看到 502 就修改前端，实际是上游进程 OOM 后反复重启。练习注入端口占用、错误 DNS、证书失败、上游 500 和磁盘满，交付时间线、假设—证伪表、根因、修复和同一路径复验；日志中的令牌和个人数据要脱敏。

**限制与复核。** 负载均衡、代理缓存和多区域 DNS 会使一次请求不能代表所有节点；须记录请求落点并在两个观察位置复测。最终报告保留未证实假设，不能把重启后的暂时恢复写成根因；每个修复应有监控阈值和再次告警时的取证入口。

## LINUX-03

安全脚本应把输入、环境、输出、退出码和副作用写成合同：引用变量、校验参数、处理管道失败、清理 trap，并支持帮助和 dry-run。环境变量可传配置但不可写入日志或仓库；定时任务有绝对路径、锁与可观察日志。用静态检查和空值、通配符、失败中断三类用例复验，保证重复执行不会产生破坏性副作用。

适用场景是需要重复执行的部署、备份、清理或定时运维任务；一次性探索命令也不得直接复制为生产 cron，含不可恢复删除的步骤应要求人工确认。

### LINUX-03 深入学习：把 Shell 自动化约束为可失败、可恢复的任务

**概念与机制。** Shell 会拆词、展开通配符，并把未引用变量、管道前段失败和继承环境转化为隐蔽副作用。脚本是输入、前置条件、输出、退出码和清理责任的合同，不是命令清单。使用明确解释器和 `set -euo pipefail`（同时理解条件、子 shell 等例外）；所有路径双引号引用，文件列表零分隔；临时目录由 `mktemp` 创建并由 `trap` 清理。危险操作先打印计划，显式确认才执行。

**可执行示例。** 编写 `backup.sh --source /srv/app --dest /backup --dry-run`：先验证目录、空间和权限，列出归档计划，再创建临时文件并原子移动；任一管道失败即非零退出，日志只记任务 ID 与脱敏摘要。以 ShellCheck、空参数、含空格文件名、磁盘写满和 SIGTERM 逐项运行，提交输出、退出码、遗留文件检查和第二次运行结果。cron 使用绝对路径、超时和锁，避免重入。

**反例、限制与练习。** `for f in $(ls)`、空变量配合递归删除，或将密码放命令行和 cron 日志都是反例；`set -e` 也不等于全局异常处理。练习加入互斥锁和 dry-run，故意中断一次执行，证明没有半成品且重复运行幂等；标记需要人工批准的破坏性步骤与恢复办法。

**复核清单。** 每个自动任务应提供帮助、输入样例、权限要求、成功与失败退出码、日志位置、锁超时和回滚命令。审查者必须在最小权限账户下复跑正常、空值、特殊字符和中断场景；任何不能解释副作用范围的命令都要改为预览或人工步骤。

## LINUX-04

服务器基线采用独立用户、SSH 密钥、最小 sudo、受限入站规则、补丁与审计日志；root 共享和明文密码不可接受。改变 SSH 或防火墙前保留已登录救援会话和回滚计划，防止把自己锁在门外。验证包含非授权登录被拒、授权用户只能执行许可操作、暴露端口最小和密钥轮换可恢复。

适用场景是承载应用、构建或运维入口的长期服务器；临时试验主机仍应最小暴露，但不能把单机基线直接当作云安全组、容器或身份提供方的替代控制。

### LINUX-04 深入学习：在不锁死自己的前提下建立服务器基线

**概念与机制。** 基线的目标是缩小可登录主体、可达端口和可执行权限，并保留可审计的恢复路径。先建立个人账户与受控管理员组，禁用共享凭据；SSH 只允许密钥、限定用户/组和认证尝试；sudo 以命令白名单授权；入站规则只开放业务端口并限制来源。补丁、时间同步和审计日志同样是基线的一部分，任何 SSH/防火墙变更前都要保留已验证救援会话、控制台入口和旧配置备份。

**可执行示例。** 为 Web 主机创建 `deploy` 用户，仅允许密钥登录并执行受限发布命令，443 对外开放、22 仅管理网可达。先验证配置语法，再在第二会话应用；分别用未授权账号、过期密钥和 deploy 账号登录，并记录 sudo、端口扫描、审计日志和回滚步骤。轮换时先新增并验证新钥匙，最后撤销旧钥匙。

**反例、限制与练习。** 一次性应用禁 root、错误 CIDR 和防火墙却无控制台可能永久失联；隐藏 SSH 端口也不是访问控制。云安全组、IPv6、容器端口和身份提供方仍需单独核对。练习注入失效密钥与 sudo 越权，交付允许/拒绝矩阵、恢复时间线和可复现审计记录。

**复核清单。** 基线发布应由第二人逐项核对可登录账户、有效密钥、允许端口、sudo 命令、补丁级别、日志保留和救援入口。每次网络或 SSH 改动后，用新会话验证且保留自动回退窗口；发现异常登录、暴力尝试或配置漂移时，能定位负责人并撤销最小范围的访问。

所有拒绝结果也要留证，确认规则没有误伤紧急救援通道。

月度复核应比较实际端口与基线，发现例外就明确到期和责任人。

## DOCKER-01

镜像是分层制品，容器是其一次运行；Dockerfile 与构建上下文决定可重现性和缓存。将依赖描述先复制、源码后复制，使用 `.dockerignore` 和多阶段构建缩小产物；固定基础镜像版本/摘要，运行时使用非 root、明确入口和信号处理。干净环境构建两次并比较结果，检查密钥、`.env`、node_modules 没有进入层。

适用场景是需要可交付、可重建服务镜像的应用构建；本机临时调试镜像不能跳过秘密隔离，也不应用容器层缓存取代依赖锁定和制品验证。

### DOCKER-01 深入学习：从构建上下文到最小运行镜像

**概念与机制。** Dockerfile 每条指令产生可缓存层，构建上下文决定哪些文件可能进入制品。缓存快不等于正确：把源码、密钥或本机依赖过早送入上下文，会失效频繁也可能泄露。先以 `.dockerignore` 排除 `.git`、密钥、构建物和本机依赖；先复制锁文件安装依赖，后复制源码；构建阶段编译、运行阶段只复制必需产物。基础镜像固定版本或摘要，显式非 root 用户、入口与停止信号。

**可执行示例。** 为 Node 服务写两阶段 Dockerfile：构建阶段以锁文件安装和编译，运行阶段只含产物、生产依赖和 `app` 用户。空缓存连续构建两次，记录镜像摘要、层大小与日志；启动后用健康端点、非 root 身份和 SIGTERM 测试验证。搜索层和历史，证明 `.env`、私钥及 `node_modules` 未进入。构建参数不是秘密注入渠道，运行时配置应受控提供。

**反例、限制与练习。** `COPY . .` 后才排除文件、使用 `latest` 或在镜像内写入令牌均不可接受；即便删除秘密，旧层仍会保存它。架构、时间戳和远程依赖会影响字节级可重现，须记录平台与锁文件。练习分别改一行源码和一个依赖，解释应失效的层并提交最小镜像、扫描与启动回归。

**复核清单。** 发布前比对构建上下文清单、基础镜像摘要、锁文件、最终层、运行身份、暴露端口和健康检查；发布后从运行容器反查实际摘要。若构建需要私有包或证书，必须采用不会写入层和日志的受控通道，并在失败时确认临时凭据已撤销。

## DOCKER-02

Compose 声明服务、内部网络、服务名 DNS、卷、环境与健康检查；`depends_on` 只表达启动依赖，不能证明服务已经就绪。把可持久数据放 volume，把密钥与示例配置分开；用开发和生产覆盖文件表达差异。重建容器后检查数据仍在，并验证健康失败时消费者不会错误连接。

适用场景是本地或单机上由多个服务组成的可复现拓扑；跨集群调度、全局流量和托管密钥治理不适用只靠 Compose 文件解决。

### DOCKER-02 深入学习：用声明式拓扑表达隔离、就绪与持久化

**概念与机制。** Compose 把服务、网络、卷和配置编排为局部系统，但“已启动”不等于数据库可接受连接或迁移已完成。为服务定义专用网络和最小暴露端口，消费者用服务名而非宿主端口连接；数据库放命名卷，临时缓存明确可丢；健康检查验证真正可服务的动作。一次性初始化用独立 job 或可重入迁移处理，基础文件只存非机密默认值，开发/生产覆盖文件分离差异。

**可执行示例。** 编排 `web`、`api`、`db`：db 用卷保存数据，api 在 db 健康且迁移完成后才接流量，web 仅访问 api 的内部 DNS。创建记录、停止、删除容器、重新启动，证明数据仍在；再让 db 健康失败，确认 api 返回可诊断错误而非无界重试。提交拓扑图、配置展开结果和日志时间线。

**反例、限制与练习。** 将密码写入仓库、数据库端口全网暴露或把 `depends_on` 当就绪保证均不可接受。命名卷不等于备份，驱动和编排平台可能改变语义。练习注入 DNS 不可达、卷满、迁移失败和重复启动，交付恢复步骤、数据校验与最小权限网络规则。

**复核清单。** 每个服务应说明拥有的数据、依赖、健康语义、公开端口、重启后行为、配置来源与删除风险。审核者在干净环境执行配置展开、启动、停止、重建、健康失败和卷恢复；若任何步骤依赖人工顺序或本机隐含变量，需显式写入脚本或文档。

演练结束后清理测试数据，并再次确认卷与网络的实际归属。

生产变更前还要核对备份恢复时间与卷数据完整性，不能以容器仍能启动代替验证。

结果须连同 compose 版本与覆盖文件保存，保证环境差异可追溯。

## DOCKER-03

先按构建期、启动期、运行期分类，再用 logs、inspect、exec 和 stats 取得容器证据；容器内手改只是诊断，修复必须回到 Dockerfile 或配置。为 CPU、内存、文件系统、健康检查、信号和重启设置明确策略；OOM、僵尸进程和重启环都要能复现并观察。资源限制的含义受宿主和编排环境影响，不能只在本机据此下结论。

适用场景是已容器化服务的启动或运行故障定位；不能在生产容器内临时修改后宣布修复，也不应把单一宿主的资源观察泛化到其他编排环境。

### DOCKER-03 深入学习：将容器故障归因到制品、配置或资源边界

**概念与机制。** 容器退出可能来自入口、环境、挂载、应用异常、健康检查或宿主资源压力。先确认重启频率和事件，再读带时间戳日志；inspect 核对入口、环境、挂载、网络和退出码；必要时仅在副本 exec 取证；stats 与宿主日志区分内存泄漏和 cgroup OOM。CPU、内存、进程数、只读文件系统、健康检查、优雅停止和重启上限均要显式配置，修复最终回到 Dockerfile 或编排清单。

**可执行示例。** 将 API 上限设为 256Mi，用受控压测触发 OOM；收集应用日志、退出状态、资源曲线和重启事件。修复后降低并发、限制缓存并处理 SIGTERM，再跑同一压测，验证不形成重启环且请求有受控失败。交付命令、配置 diff、指标摘要和恢复条件。

**反例、限制与练习。** 看到重启就无限加内存，或容器内 `npm install` 后宣称解决，都是不可重建的修复。桌面 Docker、Kubernetes 和不同内核的限制语义不同，必须记录环境。练习制造错误入口、端口冲突、OOM 与未回收子进程，分别给出证据、根因和可重建回归。

**复核清单。** 故障单需要关联镜像摘要、容器配置、宿主/编排版本、资源限制、退出码、日志窗口和监控曲线。修复必须在全新容器中通过同一故障注入；只要仍依赖人工进入容器修改、无限重启或未解释的资源峰值，就不得提升为生产修复。

报警规则应与限制值相连，方便下一次在退出前捕获现场。

复测同时覆盖健康检查误报和真实故障，避免配置只会重启而不能服务。

## DOCKER-04

镜像可信链从可追踪基础镜像、构建记录、层/秘密/漏洞扫描到 SBOM、签名或 provenance，以及可回滚晋级组成。扫描结果按可利用性和修复策略处理，不能只看分数；`latest` 不是可审计版本。演练应产出镜像摘要、扫描报告、例外审批和回滚证据；本点只管容器镜像，通用依赖供应链不重复计分。

适用场景是把镜像从构建环境晋级到测试或生产环境；源码依赖选型和通用包治理不适用在此重复处理，应由对应工程供应链流程负责。

### DOCKER-04 深入学习：让镜像晋级具有可追踪的信任链

**概念与机制。** 可信镜像要能回答基础摘要、源码提交、构建流程、组件清单、扫描结论、例外批准和回滚路径。标签可被覆盖，摘要才是不可变引用。构建时固定基础摘要并记录提交和构建器；生成 SBOM，执行漏洞、秘密和配置扫描；按可利用性、暴露路径、修复版本与业务影响分级。发布时以签名或 provenance 绑定摘要，策略只允许受信来源晋级，例外必须有负责人、到期日和补偿控制。

**可执行示例。** 为 `api@sha256:...` 生成 SBOM 和扫描报告；发现高危库后升级基础层重新构建，若暂不能修复则建立 14 天例外、限制暴露并在到期时阻断。部署前验证签名、提交与摘要匹配，部署后核对实际运行摘要。提交扫描原件、判定、审批、晋级日志和回滚演练。

**反例、限制与练习。** 只扫描 `latest`、忽略无法修复项或把 SBOM 当自动安全证明均是反例；注册表权限和扫描数据库时效仍需治理。练习注入秘密层、可修漏洞和误报，说明各自阻断、修复或例外的证据与复查日期。

**复核清单。** 每次晋级记录来源提交、不可变摘要、构建器、SBOM 哈希、扫描器与数据库版本、策略结果、例外审批和部署目标。回滚不能只改标签，必须验证运行环境切回已批准摘要并复跑健康与关键业务检查；到期例外应自动提醒并阻断继续晋级。

制品保留期要覆盖回滚窗口，过期清理前先确认无活动部署引用。

策略调整必须对历史镜像重跑，确认新规则既能阻断风险也不会意外放行旧制品。

审计人员应能从生产摘要反查全部签名与构建证据。

## DEPLOY-01

部署将 HTML、带哈希静态资源、API 代理和 CDN 缓存分开建模：HTML 短缓存/可验证，哈希资源长缓存/不可变，SPA 深链回退不能吞掉 API。Nginx 负责 TLS、压缩、路径和安全头，CDN 失效与旧 chunk 回退要有发布记录。用响应头、深链刷新、旧客户端和回滚版本四组检查证据确认策略，而非只看首页正常。

**定义与适用场景。** Web 部署交付是将入口 HTML、不可变制品、反向代理和边缘缓存按各自可变性与权限边界协同发布的过程。适用场景是静态 Web 或带 API 代理的站点发布；纯后端内部任务或无版本化静态资源的临时预览不应用这套缓存策略冒充生产保障。

**机制与边界。** 浏览器请求首先要区分 HTML、指纹化 JS/CSS、图片、运行时配置和 API。HTML 指向“最新入口”，不应长期 `immutable`；带内容哈希的静态资源可长缓存，但发布前必须证明入口与资源集同时可取。反向代理只代理明确的 API 前缀，静态站点的 `try_files` 回退只服务前端路由，不能把 `/api/404` 或上传失败改写成首页成功响应。TLS 终止后仍须可信地传递协议、主机和客户端 IP，安全头、压缩和 MIME 类型不能靠默认值猜测。

**可执行示例。** 发布一个含 `app.abc.js` 的 SPA：HTML 返回短缓存和 ETag，哈希资源返回一年不可变缓存；Nginx 对 `/api/` 设置上游超时并保留真实 4xx/5xx，对未知前端路径回退到入口。用新浏览器、缓存了旧 HTML 的浏览器、深链刷新和被撤回版本分别访问；记录每一步的状态码、`Cache-Control`、ETag、Age、响应体摘要与发布版本。然后让 CDN 只失效 HTML，验证旧客户端仍能取得它引用的旧 chunk，或有受控刷新页而非白屏。

**反例、练习与复核。** 将所有响应设为长缓存、将 API 失败回退 HTML、或删除上一版静态资源后立即切流都会破坏可恢复性。练习交付站点/代理路径表、缓存规则、证书续期责任、CDN 失效步骤和一次回滚演练；故意模拟旧 HTML 引用的资源不存在、上游超时和错误 Host，确认用户得到可解释的失败而不是错误页面。评审时检查配置 diff、响应头抓取、深链和回滚记录是否能互相证明。

上线审批还应明确谁可失效缓存、何时保留旧制品、怎样验证缓存已经收敛；将这三项与监控告警一起纳入发布清单。

## RENDER-01

CSR、SSR、SSG、ISR 是按路由选择的数据获取和 HTML 交付时机：个性化或强时效倾向服务器动态渲染，稳定公共内容可静态化，ISR 仍需明确失效与陈旧窗口。决策同时比较 SEO、TTFB、注水/交互、缓存键、状态码、部署和失败降级。用真实路由的 HTML、响应头、性能指标和过期数据用例验证，不能把任一模式称为普遍最快。

适用场景是不同访问者、时效和搜索需求混合的 Web 路由决策；不能因框架默认模式或一次性能跑分，就把某一种渲染方式套到所有私有或实时页面。

**机制与决策。** 渲染模式不是框架标签，而是“何时得到数据、何时生成 HTML、谁可复用结果”的组合。公开且变化低频的内容可预生成；带用户身份、权限或强一致查询的路由应在请求时验证并避免共享私有缓存；ISR 允许短暂陈旧，但需写清失效来源、陈旧窗口和失败时保留旧页还是返回错误。CSR 适合初始 SEO 不重要或交互高度局部的区域，但不能用它掩盖首屏数据、状态码和无 JS 可达性的问题。

**可执行示例。** 为文档页、商品详情、个人订单和实时控制台分别写一张决策卡：访问者类型、数据时效、缓存键、HTML 状态码、SEO 需求、错误/降级方式和性能预算。抓取首次 HTML，检查正文是否已存在、私有数据是否泄露；再在缓存过期前后更新内容，验证失效和用户看到的时间线；记录 TTFB、LCP、交互可用时间和服务器成本，不能只取某一次本机测量。

**反例、练习与复核。** 把所有路由静态化、把带 cookie 的页面放入公共 CDN 缓存、或将 ISR 叫作“实时”都是反例。练习将一条旧 CSR 路由迁为可索引页面，同时保留错误态和渐进交互；注入数据源超时、缓存击穿和权限变更，提交响应头、HTML、性能 trace 与回滚方案。复核人须能从每张决策卡追到真实路由和测试结果。

若指标只在理想缓存命中时成立，决策卡必须标明冷启动、失效和故障路径的预算，避免把实验室结果当作生产承诺。

## RENDER-02

流式 SSR 按边界先发送可用 HTML，慢数据后续补齐；hydration 让客户端接管交互，Islands 只为需要交互的局部加载脚本。边界必须有加载、错误、取消、缓存和可序列化状态规则；服务端不得把敏感数据序列化给客户端。检查初始 HTML、延迟边界、禁用 JS、客户端导航和 hydration mismatch，避免把流式输出误认为可跳过一致性验证。

适用场景是首屏有稳定外壳而局部数据较慢、且可拆分加载与错误边界的页面；强耦合的原子事务界面或无法保证两端初始一致的数据不适用为追求首包而强行流式化。

**机制与边界。** 流式输出先交付稳定的外壳与已完成边界，慢边界以占位、补丁或后续片段抵达；它降低等待感，却增加边界顺序、错误显示和取消的设计要求。Hydration 必须从与服务器一致的结构和可序列化数据开始，时间、随机数、用户环境和受限信息不能直接参与两端首次渲染。Islands 将脚本预算限制在真实交互区域，静态区域不应被整个应用运行时拖累；客户端导航仍要处理数据取消、缓存命中和旧边界卸载。

**可执行示例。** 构造“商品摘要立即返回、库存 800ms、推荐 2s”的页面：摘要可读，库存有加载和错误边界，推荐可以取消；分别在启用/禁用 JavaScript、慢网、导航离开和服务端抛错时截图与抓取 HTML。比较发送顺序、首个可读内容、hydration 警告和最终 DOM；把用户令牌、内部错误栈和未授权字段列入不得序列化清单。

**反例、练习与复核。** 用流式边界包住整个页面而没有独立错误态、在渲染中调用不稳定时间导致 mismatch、或为静态文本建立 Island 都是反例。练习提交边界图、每个边界的缓存/取消/错误规则、初始 HTML 和客户端 trace；注入一个慢源与一个不一致字段，证明故障不会阻塞主任务或泄露信息。复核时确认每个可交互组件在接管前后语义和键盘行为一致。

边界变更须回归测试加载、错误和取消三种状态；只测最终成功画面不能证明流式体验可用。

## EDGE-01

边缘或 Serverless BFF 在靠近用户处聚合受控后端调用，但运行时常只支持 Web 标准的一部分，且受 CPU、内存、连接与执行时长限制。认证、租户和缓存键必须留在服务端，密钥不下发；跨区可变状态和长任务应回源或改用常规服务。用不兼容 API、超时、跨租户缓存和区域故障四类测试验证回退路径。

适用场景是低延迟、轻量的请求聚合、鉴权和缓存协调；长时间计算、强一致事务、持久连接或依赖 Node 专有 API 的任务不适用边缘运行时，应明确回源常规服务。

### EDGE-01 深入学习：在边缘约束下交付受控的聚合接口

**概念与机制。** Edge/BFF 的价值是在用户附近完成轻量聚合、鉴权和缓存，而非搬运任意后端工作。浏览器把会话交给 BFF，BFF 在服务端验证身份/租户，再并行调用允许上游并合并最小响应；每个上游有取消、超时、错误映射和熔断边界。缓存键须包含公开性、租户/用户和变体，私有响应默认不共享。受限运行时只使用已验证 API；长任务、事务与强一致读取回源常规服务。

**可执行示例。** 建立 `/dashboard`：租户从签名会话获得，profile 与统计各限时 300ms，任一失败返回可区分部分数据，不能泄露另一个租户缓存。以两租户、慢上游、禁用 Node API 和区域不可达运行测试，记录响应头、trace ID、缓存命中和回源结果。提交路由预算表、失败模式和用户可见降级。

**反例、限制与练习。** 把数据库管理密钥给浏览器、以 URL 用户名隔离缓存，或在边缘执行无上限报表均不可接受。供应商限制和区域拓扑会变化，不能从一次部署泛化。练习注入超时、串租户缓存和运行时不兼容，交付传统服务器回退和复验。

**复核清单。** 每条边缘路由应记录运行时 API 清单、CPU/内存/时长预算、上游依赖、认证来源、缓存可见性、日志字段、故障降级和回源条件。评审时用普通与跨租户账号分别测试，确认错误不会泄露响应、密钥或内部拓扑；区域故障演练要留下 trace 与用户提示。

预算超过阈值即降级或回源，不能等到供应商硬性终止才处理。

回源后的响应契约、认证和可观测字段必须保持一致，避免故障时改变权限语义。

## DATA-01

Server State 是远端副本，不等同组件、URL 或本地 UI 状态。缓存键必须包含所有结果依赖（用户/租户、筛选、分页和版本），并为新鲜期、失效、垃圾回收、取消、重试和 hydration 设规则。以网络记录证明去重和失效后刷新，登出或权限变更要清理隔离数据；清空全部缓存不能掩盖错误键。

适用场景是客户端读取、缓存和刷新可由远端权威数据重建的查询；本地输入草稿、短暂动画状态或 URL 导航意图不适用塞进 Server State 缓存。

### DATA-01 深入学习：用完整缓存键和状态迁移管理远端副本

**概念与机制。** Server State 带有时间、权限和网络不确定性，和输入框、路由参数或本地展开状态的生命周期不同。查询键应列出全部响应依赖，如 `['orders', tenantId, filter, cursor, schemaVersion]`；再定义 fresh、stale、失效和垃圾回收。相同在飞请求可去重，参数切换取消旧请求；写入成功精确更新或失效列表/详情。SSR hydration 只能接收当前用户数据，登录、登出和权限切换必须隔离私有条目。

**可执行示例。** 实现订单列表和详情，状态、游标和租户都进键；修改订单后只失效该详情和受影响列表。网络面板同时打开两个相同列表证明仅一个请求；切换租户验证无旧响应闪现；慢响应时改变筛选验证旧请求取消或被忽略。提交键表、状态图和请求日志。

**反例、限制与练习。** 键只用 `['orders']`、登出后保留缓存，或每次写入清空全部缓存都是反例。客户端去重不替代服务器幂等，缓存时间也不能绕开实时一致性。练习注入漏筛选键、权限降级和乱序响应，提交串数据证据、修复键、失效策略和回归。

**复核清单。** 查询清单应列出键组成、数据归属、新鲜期、失效触发、取消策略、错误重试、SSR 来源和登出处理。评审者以两个用户、两个租户、多个筛选和慢网络复跑，检查每次 UI 变化都有可解释网络证据；无法表达的依赖必须拆分查询或补进键。

监控应统计命中、重复、取消和错误，才能发现规则在真实流量中的偏差。

审计记录应能关联一次写入到受影响查询，方便验证失效范围既完整又不过宽。

## DATA-02

乐观更新先保存可回滚快照或补丁，再提交带幂等键和基版本的写入；失败恢复输入，冲突以服务端结果和用户可见决策处理。离线 outbox 要持久化身份、顺序/依赖、重放状态和确认记录，假设消息可重复、乱序或中断。用断网重启、重复提交、409/ETag 冲突和两端并发四组用例验证，敏感或不可逆写入改用悲观确认。

**定义与适用场景。** 乐观更新是客户端在服务端确认前暂时应用可回滚变更的交互策略，离线突变是把待确认操作持久化后再重放的同步策略。适用场景是可撤销、可幂等且能表达版本冲突的编辑；支付、审批、不可逆删除或无法安全合并的写入不适用默认乐观处理。

**机制与边界。** 乐观 UI 是先显示预期结果，不是先把服务器当作已经成功。每次突变先记录影响的查询、原值/补丁、客户端操作 ID、当前用户与基版本；请求成功后以权威响应合并，失败则只回滚仍属于该操作的变化。离线队列必须与用户身份绑定，记录依赖、尝试次数、最后错误和确认游标；登出、权限收回或 schema 不兼容时不能继续替下一个身份重放旧操作。ETag/版本冲突需要可理解的合并或重新编辑入口，不能静默“最后写入获胜”。

**可执行示例。** 在订单列表中乐观修改状态：将原条目快照、操作 ID 和版本写进持久 outbox；断网后关闭并重新打开页面，再恢复网络重放。并行用另一客户端修改同一订单，服务端返回 409 和最新版本；UI 保留用户输入，展示冲突字段并允许重新提交。测试重复点击、乱序响应、过期登录、重放两次和浏览器崩溃，提交操作日志、前后缓存、请求头和用户可见结果。

**反例、练习与复核。** 成功前永久删除原数据、用数组下标作为幂等键、或将 A 用户的离线队列交给 B 用户发送都是反例。支付、审批、不可逆删除等高风险动作采用明确确认和服务器状态刷新，而非无条件乐观更新。练习为三种失败模式写回滚状态机并注入 409、500、断网重启；复核人须能从操作 ID 追到唯一请求、服务端确认和最终 UI。

队列清理只发生在明确确认后；未知网络结果保留为待判定，重新查询服务端后再决定重试、合并或提示用户。

## REALTIME-01

SSE 适合服务器单向事件，WebSocket 支持双向消息，WebTransport 在安全上下文和 HTTP/3 上提供可靠流与可丢数据报；传输可靠不等于业务已持久化。应用层还要做身份、心跳、背压、序号/游标、重连退避、幂等和确认。关键消息用游标恢复和持久确认，可丢数据报只承载允许丢失的信息；能力检测后降级到 WebSocket、SSE 或轮询。

适用场景是需要及时呈现状态、通知或协作事件的连接型交互；关键业务写入不能仅凭“帧已送达”确认，网络、代理或平台不支持时也不适用假定长连接永远可用。

**机制与选型。** SSE 是服务器持续下推的 HTTP 文本流，适合通知和状态；WebSocket 是双向长连接；WebTransport 建立在 HTTP/3 安全上下文上，可组合可靠流和允许丢失的数据报。选择传输前先写清消息方向、顺序要求、是否容许丢失、代理兼容性、连接数量和恢复游标。无论传输层如何，业务仍需身份校验、消息 ID、确认语义、权限变更处理与持久化边界；“收到 socket 帧”不等于订单已写入。

**可执行示例。** 设计订单状态订阅：服务端按用户授权发事件，事件含单调游标和 ID；客户端持久化最后确认游标，断线后以指数退避连接并补拉缺口。让网络工具依次模拟重复包、乱序包、慢消费者、代理关闭升级和移动网络切换；验证未确认事件不会丢失，进度提示可承受丢失，最终降级到轮询仍能完成任务。提交协议字段表、连接状态图、网络记录和消息去重断言。

**反例、练习与复核。** 用 WebSocket 传输所有大文件、不设背压地无限推送、或断线后从零开始且重复执行业务动作都是反例。练习让一个客户端 30 秒离线、另一个快速连续写入，恢复后比较游标和最终状态；再撤销权限，确认连接与重连都被拒绝。复核人需检查消息日志能关联身份、游标、确认、错误和降级原因。

监控还应统计连接寿命、重连次数、积压深度和确认延迟，以便在用户投诉前发现协议或代理层退化。

## COLLAB-01

OT、CRDT 与服务端串行分别用变换、可合并数据结构和中心顺序处理并发；收敛只对定义的操作集合成立。文档状态与 Presence 分离，离线更新要保留因果/版本信息，服务端仍负责权限、大小限制、Schema 与持久化。用并发插删、重复乱序、旧 Schema、断线重连和历史压缩恢复证明收敛，不能只演示两端成功一次。

适用场景是多人编辑可合并文档、画布或共享草稿；带强业务语义的批准、库存扣减和资金决策不适用仅靠文本 CRDT/OT 合并，仍需服务端事务与授权。

### COLLAB-01 深入学习：将并发收敛与业务授权分开证明

**概念与机制。** OT 通过变换并发操作适配共同顺序，CRDT 用可合并状态/操作使副本趋同，服务端串行以中心顺序简化客户端；三者的离线能力与代价不同。收敛只对明确 schema 和操作集合成立，不能自动保证权限或业务事务。定义操作 ID、因果依赖和大小；本地编辑形成可重放变更，重连后去重合并；持久文档与短暂 Presence 分通道；服务端在持久化前校验成员、速率、schema 与资源限额，并生成快照、压缩历史。

**可执行示例。** A 插入、B 删除同一段文字并各自离线生成带 ID 的变更；重连时以乱序、重复包重放，比较最终文档哈希一致，同时确认光标 Presence 不进入保存内容。再将一端设为旧 schema，要求迁移或拒绝而不是静默污染。提交操作日志、因果图、快照和恢复结果。

**反例、限制与练习。** 两端在线成功一次，或 CRDT 接受任意未授权大消息，不能证明正确；订单“批准/取消”等语义冲突也不能交给字符合并。练习注入并发删除、恶意大包和历史膨胀，交付收敛断言、服务端拒绝证据、压缩前后恢复和人工冲突流程。

**复核清单。** 协作协议需列出操作类型、ID/因果格式、最大载荷、去重窗口、schema 兼容策略、Presence 生命周期、快照频率和恢复步骤。测试至少包含三副本、离线、乱序、重复、权限撤销和压缩恢复；只要最终状态或审计日志无法解释某次合并，必须停止扩大该模型的使用范围。

发布前需演练从快照和日志恢复到新副本，确认压缩没有丢失可追踪历史。

## PWA-01

Service Worker 经过安装、等待、激活后按作用域拦截请求；应用壳、导航回退和运行时缓存需要不同策略。HTTP 缓存、Cache API、IndexedDB 与 OPFS 的生命周期和逐出风险不同，浏览器存储不是永久盘。升级提示、多标签协调、迁移中断和配额不足必须可恢复；敏感响应不进共享缓存，`skipWaiting` 只在兼容性证明后使用。

**定义。** Service Worker 是浏览器在受控作用域内独立于页面拦截请求、管理缓存和处理后台事件的脚本环境；它不是永久在线的服务器，也不保证浏览器存储永不被清除。

**机制与边界。** Service Worker 的新版本先安装，再等待旧控制器释放，最后激活并接管其作用域；强制跳过等待会使旧页面与新缓存同时存在，因此只有资源和数据兼容时才可自动启用。应用壳适合预缓存，导航回退必须排除 API、下载和认证页；运行时缓存按资源类型、最大数量、有效期和离线策略设计。HTTP 缓存、Cache API、IndexedDB 与 OPFS 的持久性和可见性不同，浏览器可逐出数据，敏感身份响应默认不得放入共享缓存。

**可执行示例。** 为新闻阅读页制定版本清单：入口 HTML、带哈希资源、离线页、图片和 API 各有独立策略。部署 v2 后保留 v1 资源直到旧客户端安全退出；同时打开两个标签，让一个标签处于旧版本、另一个收到更新提示。离线刷新已访问和未访问路径、耗尽存储、终止安装、恢复网络，记录控制器版本、命中资源、提示文案、迁移结果与清理证据。

**反例、练习与复核。** 缓存带 cookie 的个人 API、对每次发布无条件 `skipWaiting`、或用“浏览器会保存”代替迁移设计都是反例。练习故意让新页面读取旧 schema、让缓存写满并制造更新中断，交付版本兼容矩阵、回滚步骤、缓存清单和多标签测试录像。复核时检查离线可用不以权限泄露、白屏或无法回退为代价。

产品界面必须说明当前离线版本和可用范围，使用户不会把过期缓存误解为已同步的权威数据。

## LOCALFIRST-01

local-first 让本地数据库成为可编辑副本，不只是离线读取缓存。事务先提交本地数据与变更日志，outbox 以幂等键上传，inbox/游标拉取远端变化，再以显式策略处理冲突、删除墓碑和快照压缩。数据库升级、配额/逐出、多标签写入、导入导出和损坏恢复都要设计；不能用时间戳最后写入覆盖所有语义冲突。

适用场景是用户需要在弱网或离线时持续编辑、并可接受稍后同步与显式冲突处理的应用；必须即时全局一致、无法保留本地副本的敏感数据不适用 local-first 模式。

**机制与边界。** 本地优先把设备数据库作为可写副本：一次事务同时更新业务数据、操作日志和同步状态；outbox 上传本地操作，inbox 按游标吸收远端变化。实体 ID、操作 ID、幂等键、版本/因果信息和删除墓碑必须稳定，避免重放或同步后“复活”已删除数据。IndexedDB、OPFS 或 SQLite Wasm 的选择取决于查询、二进制、事务、Worker 与备份需求，不改变浏览器可能逐出存储和多标签并发的现实。

**可执行示例。** 建一个离线笔记库：编辑在本地事务提交，产生带用户、设备、操作 ID 和基版本的 outbox 记录；恢复网络后上传并按游标拉取。模拟两设备编辑、一个设备删除、其中一个停留旧 schema，再导出、清库、导入并恢复；比较实体、墓碑、游标和审计记录。输出 schema 迁移脚本、同步状态图、冲突策略、备份格式和恢复时间目标。

**反例、练习与复核。** 把 local-first 简化为缓存 HTTP 响应、仅以本机时间戳决定冲突、或在登出后保留私有数据库都是反例。练习注入配额异常、写入中断、重复上传和坏备份，验证系统不会静默丢失或串用户数据；不可自动合并的语义冲突必须可见并可撤销。复核人须能从一个本地操作追到远端确认或明确的待处理状态。

同步状态应在界面明确呈现为已同步、待上传、冲突或失败，避免用户把本地保存误认为多设备已经一致。

## PWA-02

Manifest 定义安装元数据和作用域；Share Target、文件/协议处理、Push 和通知均是渐进增强，核心任务必须有网页回退。分享来的文本、URL 和文件一律不可信：在 HTTPS 下校验参数、CSRF、类型、数量和大小，预览并由用户确认，随后清理临时存储。通知权限在明确价值时请求，推送载荷最小且可退订；平台差异要以实测矩阵记录。

适用场景是安装后能增强入口、分享接收或状态提醒的 Web 应用；浏览器未安装、权限被拒或平台不支持时不适用把这些能力当作完成核心任务的唯一入口。

**机制与边界。** Manifest 决定名称、图标、显示模式、启动 URL 与作用域，但安装资格和成员支持由浏览器/平台决定。Share Target、文件/协议处理与 `launch_handler` 都必须渐进增强：未安装或不支持时，网页表单和深链仍能完成同一核心任务。Push 订阅绑定权限和浏览器服务，通知应在用户理解价值时请求；推送负载最小，敏感内容在打开后再经授权获取，退订和权限撤销要立刻生效。

**可执行示例。** 实现“从系统分享链接或图片创建草稿”：接收端验证 POST 方法、CSRF、URL 协议、文件 MIME、数量和大小，将文件放入临时存储并展示预览确认；取消后清理。分别在支持与不支持 Share Target 的浏览器上从网页入口完成任务。再订阅一条状态通知，测试拒绝权限、失效订阅、退订与点击通知的路由；记录设备、浏览器、安装状态和回退结果。

**反例、练习与复核。** 将分享来的 URL 直接导航、把任意文件持久化、用静默推送逼迫安装或只在一种桌面浏览器测试均不可接受。练习构建兼容矩阵，注入伪造文件、超大载荷、拒绝通知和卸载重装；交付输入校验、用户确认、临时数据清理和网页回退的证据。复核人应能验证任何平台差异都不会让用户失去关键功能或泄露共享内容。

每次浏览器或系统升级后抽样重测安装、分享和订阅流程，把实测结果和已知限制同步到兼容矩阵。

## GQL-01

GraphQL Schema 是类型契约：query、mutation、subscription、nullability、错误和分页都要明确。解析器的授权、复杂度和 N+1 控制在服务端；客户端规范化缓存以稳定实体键和更新规则保持列表/详情一致。用部分错误、权限拒绝、游标稳定性和实体冲突验证，GraphQL 不会自动解决性能、缓存或授权。

适用场景是前端需要围绕稳定类型契约组合多个字段并维护实体缓存的 API；只读单一资源、没有 schema 治理或后端未实现字段授权与复杂度限制时，不适用把 GraphQL 当作自动性能或安全方案。

### GQL-01 深入学习：以 Schema 表达前端可依赖的错误与缓存边界

**概念与机制。** GraphQL 允许客户端组合字段，但契约由 schema、解析器和错误规则共同决定。先定义对象、输入、枚举和 nullable 边界；预期业务失败使用可识别结果类型或字段错误，执行错误保留安全路径。列表用稳定排序 cursor，mutation 接受幂等键/版本并返回可更新缓存的实体。客户端键使用 `__typename + id`；服务端实施字段授权、深度/复杂度限制、批量加载和 trace。GraphQL 不会自动消除 N+1、越权或昂贵查询。

**可执行示例。** 为订单列表—详情定义 `OrderConnection`、`OrderEdge` 与 `updateOrder(input)`：列表按创建时间和 ID 稳定排序，`customer` 仅授权角色可见。测试一条订单部分字段失败时其余数据仍可用；批量加载证明 50 条订单不产生 50 次客户查询；更新后比较缓存实体和列表摘要一致。提交 schema、变量、响应样例和查询计数。

**反例、限制与练习。** 将所有字段设非空后以服务器异常表示缺失、客户端只信任 `id` 不含类型，或允许无限嵌套查询都是反例。订阅还需独立鉴权、重连和顺序语义。练习注入 cursor 重复、N+1、字段越权和 mutation 部分失败，给出响应路径、缓存修正、服务器限制和回归断言。

**复核清单。** Schema 变更必须标注废弃策略、客户端影响、授权规则、复杂度预算、分页排序、实体键和错误分类。发布前以旧客户端、权限变化、空值、部分失败、重复 mutation 和大查询复跑；若响应能成功却无法让客户端安全区分数据、错误和权限，契约仍未完成。

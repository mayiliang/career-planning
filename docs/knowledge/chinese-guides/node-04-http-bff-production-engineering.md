# Node.js HTTP 与 BFF 生产工程知识点讲义

## NODE-04 Node.js HTTP 服务与 BFF 生产工程

一个能返回 JSON 的 HTTP 服务离生产可用仍很远。生产 BFF 要把浏览器请求、身份、运行时校验、多个下游、缓存、重试、流式响应、过载、可观测性和进程关闭放进同一条生命周期。目标不是记住某个框架的中间件顺序，而是能为一次请求建立总预算、所有权和可验证的失败合同。

- 直接前置：[TS-07 接口契约、运行时校验与错误模型](../chinese-guides/ts-07-runtime-contracts-validation-error-models.md#ts-07)。本讲直接使用 `unknown` 入口、Schema、兼容枚举和稳定错误模型。

### 一、BFF 是客户端边界的服务，不是万能转发器

**面向前端的后端（Backend for Frontend）**针对某类客户端聚合、裁剪和适配后端能力。它可以把账户、消息和推荐合成页面需要的视图，减少往返和前端编排；也会承担认证上下文、协议兼容、缓存和失败降级。

BFF 不应复制核心业务规则或绕过领域服务授权。若 Web、移动端和第三方都需要同一业务命令，规则应位于可信领域边界；BFF 负责把客户端表达转换为该合同。一个 BFF 服务过多不相关客户端或直接访问所有数据库，会变成新的单体耦合点。

### 二、请求生命周期从接收字节前就开始

反向代理与 Node 之间已经存在连接、头部和正文限制。应用接到请求后依次确认：方法与路由、头部和内容类型、认证、租户、正文大小、Schema、授权、业务执行和响应。顺序影响安全与资源：在校验大小前读取完整正文，攻击者可先耗尽内存；在认证前做昂贵聚合，会放大匿名流量成本。

请求与响应是流。客户端提前断开、socket 错误、响应已提交和流式写入背压都必须进入状态机。错误处理中间件不能在 `headersSent` 后再尝试写第二份 JSON；此时应记录阶段、终止流并让上游观察失败。

### 三、边界校验产生可信内部命令

路径、查询、头部和正文都来自不可信输入。解析时限制总字节、字段数、字符串长度、嵌套深度和集合大小，再用运行时 Schema 生成内部命令。错误响应采用稳定 code、可公开 message、request id 和必要字段问题，不回显令牌、Cookie、堆栈或原始正文。

认证回答主体是谁，授权回答该主体能否在当前租户和对象上执行动作。BFF 只向下游传递白名单中的身份、租户、区域和 trace 信息，不能照搬全部入站头。服务到服务凭据与最终用户凭据也应区分，避免 confused deputy 问题。

### 四、一个请求应共享绝对截止时间

每一层都设“1 秒 timeout”会让串行重试把总时长叠加。**截止时间（Deadline）**是从入口开始计算的绝对完成边界；每个下游读取“截止时间减当前时间”获得剩余预算，排队、退避和解析都计入同一总预算。

入口创建 AbortController，并把客户端断开、总截止时间和进程排空合并成取消信号。下游 fetch、流管线和内部队列接收这个信号；提交状态前再次检查请求是否仍有效。取消表示调用方不再等待，不保证远端没执行，因此写操作仍需查询结果、幂等或补偿。

```js
const deadlineAt = Date.now() + 800;
const controller = new AbortController();
const timer = setTimeout(() => controller.abort('deadline'), 800);
req.once('close', () => controller.abort('client_closed'));

try {
  return await loadDashboard({
    signal: controller.signal,
    deadlineAt,
  });
} finally {
  clearTimeout(timer);
}
```

生产代码还要清理事件监听器，并区分正常请求完成与异常连接关闭。

### 五、并发聚合要有容量与降级策略

账户和消息互不依赖时可并发读取，但不能为每个请求无界展开几十个调用。限制每请求、每租户和全局并发；连接池、队列长度与下游配额也要纳入容量。超过上限时尽早拒绝或降级，比让所有请求排到超时更可恢复。

聚合结果要定义必要与可选部分。账户失败可能让页面无法成立；推荐失败可返回空区块并标注 stale。`Promise.all` 的全失败语义、`allSettled` 的部分结果和自定义并发池各有用途，关键是输出 Schema 能诚实表达缺失、过期和不可用，而不是用空数组伪装成功。

### 六、重试需要资格、预算和幂等保护

只对被合同声明为瞬时失败、且重复执行安全的操作重试。连接失败、部分 5xx 或明确限流可能有资格；认证失败、Schema 错误和确定性业务拒绝不应重试。退避带随机抖动，并受总 deadline、最大次数和并发容量约束。

非幂等写入需要**幂等键（Idempotency Key）**表示同一次业务意图。服务端将键与主体、操作、规范化请求散列和结果绑定；同键同请求返回已有结果，同键不同请求拒绝。键有作用域、保留期和并发占位，不能只在 BFF 内存里短暂去重，也不能把每次自动重试生成成新键。

超时后的结果是未知，不应直接告诉用户“失败，可重新提交”。先用幂等键或业务查询确认是否已发生，再提供安全重试入口。

### 七、缓存必须包含真正影响结果的维度

BFF 常缓存聚合读取。缓存键至少包含资源身份、租户、权限投影、语言、区域、接口版本和其他会改变响应的参数。私有用户数据不能误入公共缓存；认证响应要配置正确的 `Cache-Control` 与 `Vary`，并理解 CDN、代理和进程内缓存是不同层。

缓存命中也要经过当前授权，或缓存本身按权限隔离。失效策略与业务变化连接：写后失效、事件驱动、TTL 或版本键。stale-while-revalidate 能改善可用性，但页面必须知道数据可能过期，高风险余额或权限不可盲目使用陈旧值。

### 八、流式响应要尊重提交点和背压

大列表、文件或 AI 增量结果可流式返回。响应头发送前仍可选择完整错误结构；发送后，协议只能用流内错误事件、终止连接或尾部元数据表达失败。客户端要区分“传输完成”和“业务完整”。

`res.write()` 返回 `false` 时暂停生产，等待 `drain`；客户端断开时取消下游和生成器。不要让上游继续生成并把数据积在内存。代理缓冲、压缩和 HTTP 版本可能改变客户端观察到的块，不能把 chunk 边界当业务消息边界。

### 九、过载保护要早于资源耗尽

限制头部等待、请求正文、请求处理时长、keep-alive、并发、队列、下游连接和响应字节。Node 官方 HTTP API 的 `headersTimeout`、`requestTimeout` 等只覆盖部分边界；反向代理、框架和应用也有各自预算，必须画出谁先终止。

过载时返回 429 或 503，并在适当场景提供 `Retry-After`。按租户和优先级公平调度，避免一个客户占满全局队列。熔断只能在下游持续失败时快速失败，不能替代正确容量；半开探测也要有小并发上限。

### 十、可观测性连接入口、下游和结果

每次请求接收或生成 request id，并与 trace id 区分：request id 便于日志关联，分布式 trace 表达跨服务因果。结构化日志记录路由模板、状态、阶段耗时、下游结果、重试次数、取消原因和幂等结果，不记录完整 URL 中的敏感查询、Cookie、令牌或正文。

指标至少包含请求量、错误率、延迟分位、在途和排队、拒绝数、连接池、事件循环延迟、内存和句柄。高基数用户 ID 不应直接作为指标标签。trace 采样要保留错误与慢请求，同时说明未采样流量的盲区。

告警应对应用户影响和可行动原因，例如关键路由成功率下降且下游超时占比上升；仅因 CPU 短时升高报警会制造噪声。

### 十一、健康检查区分活着、就绪与依赖状态

liveness 回答进程是否仍能运行，readiness 回答是否可接新流量。数据库短暂失败不一定要让进程被重启，但可能应让 readiness 失败；把所有下游都串行探测又会使健康端点放大故障。

健康检查自身必须快速、有上限且不泄露内部拓扑。启动阶段在必要配置、监听器和关键连接准备好前不应就绪；关闭阶段先撤销就绪，再排空请求。部署平台的启动、停止和探测参数必须与应用预算一致。

### 十二、优雅停机是一条有上限的状态机

**优雅停机（Graceful Shutdown）**收到 SIGTERM 后先标记不就绪、停止接受新连接，再等待或取消在途请求，关闭 keep-alive、数据库池、定时器、队列消费者和 worker，最后退出。每一步有总上限；超过上限才强制关闭并记录未完成工作。

当前 Node.js 的 `server.close()` 会停止接收新连接并关闭空闲连接；`closeAllConnections()` 会强制关闭活跃 HTTP(S) 连接，应谨慎并在 `server.close()` 后调用以减少竞态。升级为 WebSocket/HTTP2 的连接不一定由它覆盖，需要分别跟踪。

不要在信号处理器里立即 `process.exit(0)`，也不要无限等待一个失联下游。队列任务要停止领取新消息，对已领取任务按协议确认、放回或续租；写操作要让幂等键和事务恢复接手。

### 十三、用故障矩阵验证生产合同

建立一个最小 BFF：一个必要下游、一个可选下游、一条写接口和一条流式接口。固定并发与总 deadline，分别注入慢响应、连接拒绝、部分 5xx、客户端断开、重复写、响应背压、队列满和 SIGTERM。

保存请求/trace id、阶段时间线、响应 code、下游调用次数、幂等记录、在途计数和退出时间。检查：总时长不超过预算；可选失败按合同降级；非幂等写不被盲重试；客户端断开后下游被取消；队列满时早拒绝；SIGTERM 后不接新请求且在上限内退出。再以压力测试确认拒绝策略保护了已接收请求，而不是只让所有请求一起变慢。

### 十四、反向代理信任必须显式配置

生产流量常经过 CDN、负载均衡和网关。`X-Forwarded-For`、`Forwarded`、协议和主机头只有来自受信代理链时才能用于客户端 IP、HTTPS 判断和绝对 URL；直接相信任意请求头会让攻击者伪造来源或生成恶意跳转。应用记录受信跳数/网段和规范化结果，部署拓扑变化时同步更新。

Host、原始路径和重写路径都应进入路由与缓存威胁模型。生成重定向时使用批准的公共 origin，不把未校验 Host 拼入 Location。网关已做认证也不意味着内部请求永远可信，服务间仍验证签名、受众、租户与授权上下文。

### 十五、部署和回滚验证运行中的合同

滚动发布期间新旧实例同时服务，API、缓存键、幂等记录和数据库迁移必须兼容。采用先扩展后收缩：先让旧代码能容忍新字段，再发布生产者，最后移除旧路径。readiness 只有在实例具备服务当前合同的能力时才通过。

灰度按用户或租户稳定分流，比较错误率、尾延迟、取消、重试和业务结果；发现退化时停止扩量。回滚代码不一定能回滚已写数据或外部副作用，所以迁移和写协议要有向后读取、修复或前滚方案。一次成功启动不等于生产验证完成。

### 常见误解

- CORS 不是认证，BFF 也不能因为请求来自自家页面就信任输入。
- 每层各设 timeout 不能保证端到端预算。
- 重试不是错误处理默认项，幂等也不是只看 HTTP 方法名称。
- 响应流开始后不能再假装返回另一份完整 JSON 错误。
- 增加进程实例能分担可并行负载，不能修复主线程阻塞与无界队列。

### 学完后应能说明

你应能从连接到退出画出一次 BFF 请求的状态机，为边界校验、身份、deadline、取消、并发、重试、缓存、背压、日志和停机分别指定责任人和上限，并用故障注入证明服务在慢下游、重复写、客户端断开、过载和部署终止时仍给出诚实、可恢复的结果。

# 业务状态与不变量知识点讲义

## BIZ-02 状态机与业务不变量

订单、审批、导入、退款等流程不是几个可以任意组合的布尔值，而是一组有限状态、允许事件和必须始终成立的业务事实。状态机把“现在在哪里、什么能发生、为什么被拒绝、产生什么副作用”写成可枚举合同，使前端、服务端、消息处理和测试能用同一模型讨论并发、超时、重复与恢复。

### 学习前先确认

- 直接前置：[TS-02 联合类型、收窄、never 与穷尽检查](../chinese-guides/ts-02-unions-narrowing-never-exhaustiveness.md#ts-02)。本讲用判别联合和穷尽检查让合法状态与专属数据进入类型系统。

### 一、状态机适合离散且规则密集的生命周期

**状态机（State Machine）**由有限状态、事件和转移构成。订单可处于 DRAFT、SUBMITTED、APPROVED、REVOKED、EXPIRED；SUBMIT 只允许从 DRAFT 发生，APPROVE 只允许从 SUBMITTED 发生。当前状态概括了对未来行为有影响的历史。

状态机适合合法操作随阶段变化、需要审计与恢复的对象。一个一次性展开面板、连续温度值或纯计算函数可能不需要正式状态机。不要为了画图而把每个变量组合都命名成状态；只有影响允许行为和业务语义的模式才进入状态空间。

### 二、命令、事件和状态不能混为一谈

命令表达意图：ApproveOrder 请求批准。事件表达已发生事实：OrderApproved。状态表达当前模式：APPROVED。命令可能因权限、版本或规则被拒绝，因此“收到批准请求”不能直接等同状态已批准。

API 接收命令后，边界校验身份与输入，聚合读取当前状态和版本，评估守卫与不变量，在原子提交中写入新状态和事件。消息回调同样只是输入事件，不能因为消息成功到达就绕过当前状态。

日志使用明确名称，避免 `updateStatus('done')` 隐藏业务动作。命令和事件带稳定对象 ID、意图/事件 ID、发生时间与必要版本，便于幂等和审计。

### 三、转移表是允许路径的可执行合同

列出 `current + event + guard → next + effects`。未列出的组合默认拒绝且对象不变，而不是随意赋值。转移表让产品、开发和测试一起审阅缺失边、死状态和含糊路径。

```ts
type OrderState =
  | { kind: 'DRAFT' }
  | { kind: 'SUBMITTED'; submittedAt: string }
  | { kind: 'APPROVED'; approvedAt: string }
  | { kind: 'EXPIRED'; expiredAt: string };

type OrderEvent =
  | { type: 'SUBMIT'; at: string }
  | { type: 'APPROVE'; at: string }
  | { type: 'EXPIRE'; at: string };
```

状态专属数据跟随判别分支，避免 `approvedAt` 在 DRAFT 中也可选存在。TypeScript 的穷尽检查能提醒新增状态，但运行时输入仍需 Schema 校验。

### 四、不变量比“允许哪条边”更深一层

**业务不变量（Business Invariant）**是在任何合法命令提交后都必须成立的事实。例如只有 APPROVED 可发货、EXPIRED 后不能支付、退款总额不超过已支付金额。转移表约束路径，不变量约束状态与关联数据的整体合法性。

有些不变量跨多个字段，有些跨实体。保护它们的聚合必须在一次提交中拥有所需事实；若事实来自外部系统，则需要预留、确认、版本或流程协调，不能在一个本地函数里假装强一致。

每个命令执行前检查前置条件，构造新状态后再次确认不变量。失败返回稳定原因和当前版本，不产生部分副作用。

### 五、守卫是纯粹、可解释的转移条件

**守卫（Guard）**决定一条转移在当前上下文是否启用，例如申诉需在批准后 24 小时内、批准者不能是申请人。守卫应尽量纯、同步，以当前状态、事件和已加载事实返回真假；Stately/XState 当前文档也把 guard 定义为纯同步条件函数。

不要在守卫中偷偷发网络请求、写数据库或发送消息，否则同一次判断可能产生副作用且无法重放。需要外部事实时，先由应用层取得带版本的快照或进入 WAITING_FOR_CHECK 状态，再用结果事件转移。

拒绝也要可观察：返回 guard code、对象版本和可公开原因。安全相关规则由服务端执行，前端禁用按钮只提供提前反馈。

### 六、终态和中间态要明确生命周期

终态表示该状态机实例不会再接受普通事件，如 COMPLETED、REVOKED 或 EXPIRED。到达终态后清理定时器、订阅和临时资源。若业务允许“重新打开”，它就不是绝对终态，应建显式 REOPEN 命令、新版本或新的流程实例。

中间态不能只存在于内存。支付请求发出后进程崩溃，若没有 PENDING_PAYMENT 及意图 ID，重启后无法判断是否重试。把具有业务意义的等待、人工审核和补偿阶段持久化，使恢复路径可查询。

### 七、幂等处理重复事件，不替代合法性检查

网络重试和至少一次投递会重复送达同一意图。保存 idempotency key 或 event ID 与处理结果，重复到达返回已有结果而不重复副作用。但即使是新 key，也必须检查当前状态是否允许；不能用“没见过这个消息”作为合法依据。

键与主体、对象、命令类型和规范化载荷绑定，避免同键不同请求被误复用。并发首次到达要原子占位；记录保留期覆盖可能重试窗口。幂等记录成功、确定性拒绝和处理中状态，故障恢复时可判断继续、查询或人工处理。

### 八、并发需要版本与原子提交

approve 和 revoke 同时读取 SUBMITTED，都可能通过各自守卫。使用乐观版本 `WHERE id=? AND version=?` 或事务锁，让只有一个状态转移提交；另一个收到冲突后读取新状态重新判断，而不是最后写入覆盖。

状态、事件、幂等记录和必要 outbox 应在同一事务提交，否则状态已变但事件丢失，或消息已发但状态回滚。跨系统无法用本地事务时，采用可恢复流程、幂等消费者和对账。

前端收到 409/版本冲突后刷新并展示当前事实，不要自动重放一个可能已不合法的命令。用户意图若仍适用，应明确重新确认。

### 九、超时由领域时间事件表达

计时器只负责在某时刻投递 EXPIRE_DUE 之类事件，真正是否过期由状态机用权威时间和当前版本判断。定时任务可能迟到、重复或漏执行；读取路径也可惰性检查到期，再由幂等命令收敛。

业务时间与机器执行时间分开。规则是“提交后 24 小时”还是“当地日历次日 18:00”，涉及时区、夏令时和节假日，必须进入统一语言。测试注入可控时钟并覆盖边界，不能依赖真实 sleep。

### 十、外部副作用需要流程状态与补偿

扣款、发货、发送不可撤回通知都在聚合事务之外。先保存意图和 outbox，再由 worker 执行；结果以成功/失败事件回流。若步骤二失败，状态机决定重试、等待人工或执行**补偿（Compensation）**。

补偿是新的、可审计的业务动作，例如退款抵消已扣款，不是删除历史或把状态字段直接改回去。补偿本身可能失败，需要独立状态、幂等和升级。并非所有副作用可完全撤销，模型应诚实表达 PARTIALLY_COMPLETED 或 MANUAL_REVIEW。

长流程可以由 saga/process manager 协调，但名称不重要；重要的是每一步状态持久、消息幂等、失败可恢复、责任明确。

### 十一、层级与并行状态控制组合爆炸

当多个状态共享行为，可用父状态封装，例如 ACTIVE 下含 EDITING、SUBMITTING，父级统一处理 CANCEL。并行状态表示两个相对独立区域同时活跃，如订单履约与客户通知；Stately 文档指出进入并行状态会同时进入各区域，事件也会交给各区域处理。

并行不等于彼此完全独立。跨区域不变量仍需协调，事件可能同时触发两处转移。若两个维度其实互相强耦合，拆成并行区域会隐藏非法组合。只有能分别演进且组合规则清晰时才使用。

历史状态能恢复离开前的子状态，但对支付、权限等高风险流程，自动恢复旧状态可能不安全，需要重新校验外部事实。

### 十二、状态演进是 API 与数据迁移

新增 APPEALING 不只是图上加节点。需要更新转移、运行时 Schema、数据库约束、API 枚举、前端未知状态降级、指标、文案、历史数据和测试。旧客户端收到新值时不能默认为完成；显示“状态待确认”并限制高风险动作。

删除或合并状态要定义存量实例怎样迁移、旧事件怎样重放。事件消费者采用向前兼容字段策略，版本差异明确。滚动发布期间，新旧服务可能同时运行，转移协议需要双版本安全或先扩展后收缩。

状态图也应版本化。正在运行的长流程继续旧版本还是迁移到新版本，由业务决定，不能让部署瞬间隐式改变历史实例规则。

### 十三、验证要覆盖所有边与拒绝路径

从转移表生成参数化测试：每条合法边至少一次，每个状态的代表非法事件至少一次，断言拒绝后状态、版本和副作用不变。再覆盖守卫边界、重复事件、并发命令、超时乱序、外部失败、补偿失败和未知状态。

保存 trace：`event/current/guard/next/version/effect`。同一事件序列应在固定时钟和依赖下重放得到同一结果。属性可以是“终态不会离开”“版本严格递增”“已处理 key 不产生第二次副作用”“退款累计不超过付款”。

模型检查工具能发现不可达状态、死锁和遗漏路径，但工具通过不等于业务规则正确；转移表和不变量仍需领域人员审阅。

### 十四、用订单乱序演练完整机制

准备订单 o7：DRAFT → SUBMITTED，10:00 到期；随后并发出现 APPROVE、EXPIRE 和重复付款回调 k9。明确权威时间与规则优先级，例如到期判定在提交时基于版本和时间，EXPIRED 为终态。

分别重放正常顺序、回调先到、计时器迟到、k9 重复、approve/revoke 并发和进程在外部调用后崩溃。检查最终状态、版本、幂等记录、outbox、补偿和 trace。改变一条规则（允许 APPROVED 在 24 小时内 APPEAL），新增显式状态与 guard，再验证旧客户端降级和旧实例迁移。

### 十五、界面是状态机投影，不是状态权威

前端根据服务端状态决定可见命令、文案和恢复入口，但按钮禁用不能替代服务端守卫。请求发出后用局部“提交中”状态阻止重复手势，服务端仍通过幂等和版本保护；响应回来后以权威新状态替换投影。

网络未知结果不能随意回到原状态。显示“正在确认”并用意图 ID 查询；收到 409 时展示最新状态和允许动作。深链打开旧页面、多个标签页和离线恢复都可能带来过期投影，提交命令时携带版本并诚实处理冲突。

### 十六、可观测性应以业务转移而不是字段更新为单位

日志记录命令、旧状态、guard 结果、新状态、版本、意图/事件 ID 和副作用引用；指标统计转移成功、拒绝原因、停留时间、补偿和人工积压。不要把用户 ID 直接做高基数标签，也不记录敏感载荷。

告警关注不可能路径、终态离开、版本倒退、同一 key 重复副作用和某状态停留超预算。通过 trace 串联入口命令、事务、outbox、消费者和外部调用，事故后才能区分状态没提交、事件没发布或副作用没完成。

### 十七、状态空间过大时先重新审视建模维度

如果用一个枚举列出“已批准且已付款且已通知”等所有组合，状态数量会指数增长。识别相对独立的区域、派生属性和外部流程；有些“状态”其实可由事实计算，有些应拆成另一个聚合或 process manager。

拆分后仍列出跨区域不变量和同步事件，不能用架构边界掩盖业务约束。对高风险流程，可用模型检查或遍历转移图验证可达性、终态和死锁，再由领域人员确认这些路径确实符合业务。

### 常见误解

- 多个布尔值不能自动保证互斥和完整状态组合。
- 守卫不应执行网络请求或产生副作用。
- 幂等只处理重复意图，仍必须检查当前状态与权限。
- 超时发生不等于计时器准点运行，规则应以权威时间重新判断。
- 补偿不是删除历史，也不保证把世界完全恢复原状。

### 学完后应能说明

你应能把一个业务生命周期写成状态、命令、事件、转移和不变量，利用守卫、版本和原子提交抵御非法路径与并发，用幂等、outbox、流程状态和补偿处理外部副作用，并为重复、乱序、超时、版本演进和未知状态建立可重放证据。

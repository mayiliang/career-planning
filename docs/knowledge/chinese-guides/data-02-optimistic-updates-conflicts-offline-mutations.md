# 乐观写入与离线同步知识点讲义

## DATA-02 乐观更新、并发冲突与离线突变

即时界面常在服务器确认前先显示用户预期结果；离线产品还会把写操作保存起来，联网后重放。这两种策略都把“本地看见”与“远端已确认”分开，若没有快照、操作身份、版本和恢复状态，失败回滚会覆盖新编辑，离线队列会替错误账号重放，重复请求也会制造额外副作用。本讲以服务器仍为权威的前提，建立可逆、可恢复、可审计的写入模型。

示例和实验围绕收藏、改名、排序与高风险写入比较：注入离线、重复点击、响应乱序、409 冲突、账号切换和刷新，验证局部补丁、outbox 与权威重取能否收敛。

### 学习前先确认

- 直接前置：[DATA-01 Server State、缓存键、失效与请求去重](../chinese-guides/data-01-server-state-cache-keys-invalidation-deduplication.md#data-01)。本讲直接使用查询键、取消、缓存影响图、身份隔离与权威重取。
- 直接前置：[BIZ-07 异常边界、幂等与一致性](../chinese-guides/biz-07-errors-idempotency-eventual-consistency.md#biz-07)。本讲假定你能区分明确失败、未知结果、幂等、版本冲突和最终一致。

### 一、先决定哪些操作值得乐观

**乐观更新（Optimistic Update）**在服务端确认前，临时把预期结果应用到客户端副本。它适合成功率高、结果可预测、可回滚且错误成本低的收藏、轻量改名和排序。资金、权限批准、库存扣减、不可逆删除或复杂服务端计算通常应悲观等待或只显示“待确认”。

判断表包括副作用可逆性、冲突概率、服务端是否会改写结果、失败对用户影响、是否有幂等和版本、能否恢复未知结果。不要因为库提供 onMutate 就默认所有写入乐观。

乐观 UI 必须显式标识 pending，让用户知道结果尚未确认；刷新后能从服务端操作状态恢复。短暂快感不应以事实误报为代价。

### 二、一次突变需要稳定客户端操作身份

为每次业务意图生成 operationId，记录用户、租户、对象、mutation 类型、规范化变量、基版本、创建时间和状态。operationId 关联 UI、缓存补丁、网络请求和服务端幂等键，不能用数组下标或组件实例 ID。

**幂等键（Idempotency Key）**保证同一意图重放不会增加业务效果。网络重试沿用原键，同键不同载荷拒绝。新的用户意图才生成新键。客户端去重和按钮禁用不替代服务端原子记录。

操作记录有 queued/sending/unknown/confirmed/rejected/conflict/cancelled。confirmed 前不能永久清理恢复信息；网络超时进入 unknown，先查询服务端记录而不是直接新建操作。

### 三、乐观补丁必须可逆且归属于操作

开始突变前暂停或取消相关查询，读取受影响缓存，生成最小 forward patch 和 inverse patch，或保存必要快照。随后应用预期状态并登记 operationId。不要复制整个全局缓存，既昂贵也会在回滚时覆盖无关变化。

失败时只撤销本操作仍拥有的字段/条目。若用户随后又提交 B，A 的失败不能恢复到 A 之前而抹掉 B。用每字段最后操作 ID、补丁序列或从权威数据重取。并发复杂时宁可不乐观。

服务端成功响应可能补充 ID、版本、规范化名称和权限，应以权威结果替换临时值，再失效相关查询校正。不要假设预期对象完全等于服务器对象。

### 四、列表乐观更新要处理筛选与排序

改状态后对象可能离开当前筛选、进入另一列表或改变排序。影响图列出详情、所有已缓存筛选、统计和分页。可精确更新已知列表，也可更新当前视图后失效其他集合。

创建使用临时 ID 并标记 pending；确认后原子替换真实 ID，修正详情键和路由。失败移除临时项但保留表单输入。重复确认不能产生两条。

删除可先隐藏并保留 tombstone/撤销窗口，服务器拒绝则恢复正确位置。跨页和总数更新必须一致；数组索引不是对象身份，排序变化后索引会失效。

### 五、响应乱序用版本和操作序列解决

对同一字段连续提交 A、B，B 先成功、A 后成功。若直接用到达顺序覆盖，最终回到旧值。请求携带基版本和 operationId，响应带新版本；只接受比当前确认版本新的事实，冲突时从服务端重取。

串行队列可以减少同对象竞态，但降低速度且仍需处理跨设备写入。合并连续未发送操作可用于文本/拖拽，但要保持用户意图与审计；已经发送的副作用不能简单覆盖掉。

Abort 客户端请求不证明服务端未执行。取消后若结果未知，保留 operationId 查询。旧响应提交前检查会话、对象与当前操作状态。

### 六、冲突不是普通失败

服务器用 ETag/If-Match 或 version 拒绝基于旧快照的写入。收到 409/412 时保存本地草稿、旧基线和最新服务器对象，进入 conflict，而不是回滚并丢输入或无条件覆盖。

**冲突解决（Conflict Resolution）**按业务选择：重新加载放弃本地、三方字段合并、让用户选择、生成新业务命令或交给人工。非重叠字段可自动合并，双方改同一字段需要语义判断；订单状态等命令通常重新判断合法性，不按字符串合并。

展示谁/何时/哪些字段变化，避免泄露无权信息。重新提交使用最新版本和新的用户确认；原 operationId 的冲突结果保留审计，不能偷偷改载荷重放同键。

### 七、离线队列是持久状态机

**发件箱（Outbox）**在客户端持久保存待同步操作。每项包含 schemaVersion、用户/租户、operationId、幂等键、基版本、依赖、规范化变量、尝试、错误和创建时间。刷新、崩溃后能恢复，而不是只靠内存 Promise。

队列状态 queued→sending→unknown/confirmed/rejected/conflict。只有服务端明确确认后删除；超时保留 unknown 并查询。数据库事务同时写草稿/乐观投影和 outbox，避免页面显示已排队但记录没落盘。

存储有配额、过期和迁移。满额时拒绝新离线写并说明，不能静默丢最旧操作。敏感 payload 最小化、按留存清理；本地加密不能防同源 XSS，仍需脚本安全与身份隔离。

### 八、重放顺序与依赖要显式

创建临时对象后再编辑，第二操作依赖第一操作确认并把临时 ID 映射真实 ID。用 dependsOn 或对象队列表达，不能简单全并发。独立对象可受控并行，单对象按业务顺序或可合并规则处理。

队列不是永远 FIFO：被拒绝操作可能阻塞依赖，但不应阻塞无关对象；高优先与普通操作也要防饥饿。重放前重新验证身份、权限、Schema 和网络，不在网络刚恢复时瞬间发送全部积压。

重放日志记录 attempt、响应和最终版本。应用多实例/多标签同时恢复时用锁或 leader 协调，服务端幂等仍是最后防线。

### 九、身份切换是硬隔离边界

outbox 与缓存命名空间绑定用户和租户。登出时停止发送、取消请求、清理或加密封存旧队列；下一用户永远不能看到或发送前一用户操作。再次以同一身份登录是否恢复，按产品与隐私策略决定。

token 过期先重新认证，不把 401 当暂时网络错误无限重试。角色撤回后，重放可能 403；保留安全摘要和用户输入导出/删除入口，不继续绕过权限。

服务端也从当前认证主体校验幂等记录归属，不能仅凭知道 key 查询他人结果。多设备操作通过对象版本冲突收敛，而非共享客户端 outbox。

### 十、网络状态只能提供提示

`navigator.onLine` 不证明目标服务可达，DNS、代理和服务故障仍可能失败。应用根据真实请求结果切换在线/离线/服务不可用，采用退避探测；不要每秒 ping 制造流量。

网络恢复后先刷新权限和相关对象，再按依赖重放。若服务端 Schema/版本已不兼容，暂停并迁移或要求用户确认。弱网下 sending 可能持续，UI 给出最后尝试与手动重试，不重复创建。

后台同步能力受浏览器平台与权限限制，不能承诺关掉浏览器也一定发送。重要操作让用户看见是否已确认，并在服务端任务中心可查。

### 十一、失败回滚保护用户输入与新事实

确定性验证失败保留草稿并定位字段，撤销乐观投影；权限拒绝清除敏感缓存但可保留允许的本地输入；暂时故障进入队列；未知结果查询；冲突进入合并。一个通用 `onError => restore snapshot` 无法正确处理。

回滚本身可能失败，因为缓存已被其他写改变。优先 inverse patch 加所有权检查或使权威查询失效。UI 说明哪些改变已撤销、哪些仍待确认，避免 toast 写“失败”但页面还显示成功值。

部分成功用对象/字段级结果，已确认部分不回滚，失败部分保留重试。高风险批量操作可能选择服务端原子语义，客户端按合同处理。

### 十二、悲观与乐观可以在同一流程组合

编辑标题可乐观，最终发布需悲观确认；本地添加评论先显示 pending，附件上传完成后才能发送；删除先提供撤销窗口，窗口后才提交。按阶段风险选择，不必整个产品统一一种模式。

悲观等待也要保留输入、处理重复点击和 unknown。它不是“什么都不显示”，可以展示明确 pending 与可离开任务。乐观模式则不是“立即成功”，应显示待确认标记。

产品文案与状态图共享同一事实，避免设计稿把 pending 画成绿色成功，代码却仍可能回滚。

### 十三、离线冲突需要产品级数据策略

Last-write-wins 简单但可能丢数据，只有业务确认时间顺序可接受且有审计时使用。字段合并适合独立属性；文本协同可能需要 OT/CRDT；财务、审批用服务端命令与人工协调。技术库不能替业务决定。

保留冲突双方和版本，让用户理解差异。自动合并后仍由服务端重新检查不变量。冲突长期未处理时有过期、提醒和导出策略，不能永久占用队列。

时钟不可靠，排序优先服务器版本/序列；客户端时间仅展示。跨时区日期字段按业务语义比较。

### 十四、观测与隐私

指标包括乐观成功/回滚率、unknown 停留、409/412、队列长度/最老年龄、重试、身份隔离清理、配额失败和冲突处理结果。operationId 连接 UI、请求、服务端幂等和最终版本。

日志不写完整敏感 payload、token 或本地数据库内容。调试导出需用户明确触发并脱敏。队列保留期与删除可验证，登出/注销流程有自动测试。

高回滚率说明不适合乐观或服务端规则未前置；高冲突率可能意味着对象粒度、自动保存或协作模型需要改变，不应只增加重试。

### 十五、故障验证覆盖重启、重复与乱序

固定对象 v3，执行本地改名，注入：请求前断网、提交后响应丢失、浏览器崩溃重启、同 key 双发、另一设备提交 v4、A/B 响应乱序、账号切换、权限撤回、队列 Schema 升级、存储满和两标签同时重放。

断言一个意图只有一个服务端效果；unknown 查询后收敛；冲突保留双方；B 用户不见 A 队列；旧响应不覆盖新版本；只有确认项清理。保存 outbox 行、缓存补丁、请求头、服务端幂等记录和最终 UI。

性质测试随机生成重复/顺序，验证版本单调和确认后队列不复活。端到端测试覆盖用户可理解的 pending、冲突和恢复，但服务端唯一约束必须由集成测试证明。

### 十六、常见反例与适用边界

- 所有写入一律乐观，支付/审批也先显示完成。
- 回滚整个查询快照，覆盖随后操作或后台新数据。
- 每次重试生成新 key，或用数组索引作为操作身份。
- 离线队列不绑定用户、版本和依赖，恢复后一股脑并发。
- 409 后静默 last-write-wins，失败时丢失草稿。
- 根据 navigator.onLine 宣称已同步，未保存服务端证据。

若操作不可逆、冲突无法安全解释、服务端结果不可预测或失败成本高，采用悲观确认和明确任务状态。乐观/离线不是目标本身，可靠完成用户意图才是。

### 十七、学完后应能说明

你应能判断操作是否适合乐观，设计可逆补丁和操作归属；用幂等键、基版本处理重复与冲突；建立绑定身份、可迁移、有依赖的持久 outbox；区分失败、unknown 和 conflict；并通过断网、重启、乱序、跨设备、账号切换和配额故障证明最终远端事实与 UI 可解释地收敛。

继续查证可参考 [TanStack Query Optimistic Updates](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates) 与 [MDN Using Service Workers](https://developer.mozilla.org/zh-CN/docs/Web/API/Service_Worker_API/Using_Service_Workers)，但后台能力必须以目标浏览器当前支持为准。

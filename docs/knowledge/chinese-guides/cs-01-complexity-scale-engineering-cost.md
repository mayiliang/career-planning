# CS-01 复杂度、数据规模与工程成本判断

当页面数据从几十条增长到几万条，原本顺畅的搜索可能开始卡顿。工程师需要回答的不是一句“这个算法是 O(n)”，而是：输入究竟是什么、工作量怎样增长、内存和主线程付出了什么成本、测量是否可信，以及应该在哪一层解决问题。

## CS-01

### 学习前先确认

开始前只补当前真正需要的基础：

- 不确定 `n`、基本操作和增长曲线代表什么，先读 [PRECS-01 输入规模、基本操作与增长趋势](../chinese-guides/algorithm-input-size-and-growth.md#precs-01)。
- 不熟悉 Array、Map、Set 的基本用途，先读 [PRECS-02 JavaScript 集合、键与成员关系](../chinese-guides/javascript-collections-keys-membership.md#precs-02)。

理解这两份短文后即可继续；无需预先通读一整本算法或性能术语手册。

### 一、复杂度是在建立“规模—成本”模型

**时间复杂度（time complexity）**描述输入规模变化时，代表性操作次数怎样增长。**空间复杂度（space complexity）**描述算法额外占用的内存怎样增长。它们先回答趋势，再由真机测量补充实际耗时和字节数。

考虑“根据用户 ID 给订单补上用户名”：

```js
function attachNamesSlow(orders, users) {
  return orders.map((order) => ({
    ...order,
    userName: users.find((user) => user.id === order.userId)?.name,
  }));
}
```

若订单数和用户数都随 `n` 増长，每张订单最坏会再次扫描用户列表，比较次数接近 `n × n`。把用户先建成索引后，工作分成“一次建表 + 一次查表”：

```js
function attachNamesIndexed(orders, users) {
  const userById = new Map(users.map((user) => [user.id, user]));
  return orders.map((order) => ({
    ...order,
    userName: userById.get(order.userId)?.name,
  }));
}
```

这里用 **大 O 表示法（Big O notation）**忽略常数和较低阶项，前者可描述为 O(n²)，后者通常描述为 O(n)。这不是说 Map 查询绝对零成本，也不是说小数据时第二种一定更快；它说明规模继续变大时，两种方案的增长形状不同。

如果订单数为 `m`、用户数为 `n`，更诚实的表述是前者 O(mn)，后者建表和查询合计 O(m+n)。不要为了得到熟悉的字母而把两个独立维度强行写成一个 `n`。

### 二、常见增长形状来自不同工作方式

O(1) 表示工作量不随输入规模明显增长，例如已知键的 Map 查询；O(log n) 常见于每步排除一半候选的二分查找；O(n) 常见于完整扫描；O(n log n) 常见于高效通用排序；O(n²) 常见于两两比较。

这些名称不是从“代码有几层循环”机械数出来的。递归可能形成线性或对数增长，库函数内部也可能包含遍历。应沿着真实调用路径找出随着输入重复的工作，再写出它与规模的关系。

增长趋势还要结合约束。有时 `k` 是永远不超过 10 的显示槽位，那么 O(nk) 在该约束下近似随 `n` 线性增长；如果 `k` 也会扩大，就不能把它藏进常数。数据上限是产品合同的一部分，不应默认为永远很小。

### 三、最好、平均、最坏与摊还回答不同问题

查找数组第一个元素时很快，找不到时却要走完整个数组。**最坏情况（worst case）**描述最不利但仍允许的输入，适合检查卡顿、安全和容量边界；平均情况依赖输入分布，必须说明“平均”是按什么概率或真实流量分布计算。

动态数组追加元素通常很便宜，但容量不足时要申请更大空间并复制已有元素。单次扩容可能是 O(n)，连续许多次追加的总成本却仍与追加次数同阶。这种把偶发昂贵操作分摊到一串操作上的分析叫**摊还分析（amortized analysis）**。摊还 O(1) 不能改写成“每次都保证 O(1)”；对要求稳定响应时间的交互，偶发尖峰仍值得测量。

工程结论应把语境写全，例如：“在键分布正常的 Map 实现中，平均查询近似常数；构建索引需要 O(n) 时间和 O(n) 额外空间；索引失效时需重建。”

### 四、相同 Big-O 仍可能有不同用户体验

两段代码都只遍历一次，实际表现仍可能相差很大：

```js
function sumDirect(values) {
  let total = 0;
  for (const value of values) total += value;
  return total;
}

function sumWithLabels(values) {
  return values
    .map((value) => ({ value, label: String(value) }))
    .reduce((total, item) => total + item.value, 0);
}
```

第二个版本创建中间数组、对象和字符串。两者都可以写作 O(n)，但常数、峰值内存与**垃圾回收（garbage collection）**压力不同。对象布局、缓存命中、JIT 优化、序列化和数据类型也会影响结果。

前端还多一个特殊约束：主线程同时承担事件处理和渲染协调。屏幕刷新周期不是 JavaScript 的独占预算；样式、布局和绘制也要占时间。一个总耗时不算很长的任务，如果连续阻塞主线程，仍会让输入响应变差。把工作放进 Worker 可以改善响应，却不会消除总 CPU 成本、消息成本和内存成本。

因此成本至少分四层看：算法操作、分配与内存、主线程连续占用时间、跨线程或网络边界。只说“复杂度没问题”不能替代这四层判断。

空间也要区分输入本身与算法为了工作额外创建的空间。原始列表已经由调用方持有时，分析“额外空间”通常不重复计算它；但做容量规划时，进程实际承受的是输入、索引、中间结果和副本的总和。一个用 O(n) 索引换掉 O(n²) 查找的方案，往往是值得的时间—空间交换，但仍要确认移动设备能否承受索引和构建期间的短暂双份数据。

延迟与吞吐也不是同一个指标。延迟关心一次操作多久完成，吞吐关心单位时间完成多少操作。批量处理可能提高吞吐，却让第一条结果更晚出现；分块可能略增总耗时，却让交互更及时。选择指标要从用户等待方式和系统容量出发，不能用一个“性能分数”代替全部体验。

### 五、可信基准先控制问题，再记录结果

**基准测试（benchmark）**的目的，是在可解释的条件下比较方案或观察规模曲线。一次开始时间减结束时间只能得到一个样本，无法区分代码差异与偶然噪声。

一个可靠的比较通常包含：

1. 明确问题：比较的是吞吐、单次延迟、主线程长任务还是内存峰值；
2. 固定输入：记录数据规模、分布、随机种子和是否已经排序；
3. 隔离变量：一次只改变实现方式，保持设备、构建模式和输入一致；
4. 预热与重复：让运行时有机会稳定，再保留多次正式样本；
5. 保留原始数据：不要只留下一个平均数；
6. 同时验证正确性：更快但返回错误结果的实现不能参与结论。

用中位数可以描述典型样本，用**百分位数（percentile）**可以观察慢尾。例如 p95 表示约 95% 的样本不超过这个值，而不是“最慢一次”。样本很少时，p95 很容易被个别值支配，应同时给出样本数和分布。

浏览器微基准容易被开发者工具、后台标签页、节能策略和开发构建干扰。测纯函数时可用 `performance.now()`；判断页面卡顿时还要看 Performance 录制、Long Tasks、交互指标或真实用户监控。工具产生的是证据，不会自动给出根因。

比较方案时还要防止基准测成了另一个问题。若优化版本提前缓存结果，而对照版本每次重算，测到的是缓存策略差异；若排序输入与真实输入分布不同，分支和比较次数也可能不同；若返回值从未被使用，运行时甚至可能采用与真实业务不同的优化路径。基准代码应尽量调用真实实现、消费结果，并把构建模式和环境写进记录，使后来的人能够复现和质疑结论。

### 六、从曲线和剖析证据走向决策

先画不同规模下的耗时和内存，而不是只测“当前这一份数据”。如果输入翻倍后耗时接近四倍，检查是否出现嵌套扫描；如果耗时近似线性但尖峰变大，检查分配、GC 或偶发 I/O；如果 Worker 内部很快而总流程慢，检查消息复制与合并。

处理顺序通常是：

1. 删除不必要的计算、重复查询和无用格式化；
2. 用更匹配的结构或算法改变增长趋势；
3. 控制分配、缓存和中间结果的生命周期；
4. 将长工作切片，或把适合的 CPU 工作移出主线程；
5. 当客户端不应持有全部数据时，在权限和一致性边界内改为服务端筛选、聚合或分页。

“上 Worker”和“移到服务端”都不是算法改进的同义词。前者改变交互线程，后者改变计算与数据所在的位置；两者会引入通信、错误处理和所有权问题。

### 七、容易混淆的结论

- “O(1) 就一定快”：O(1) 也可能包含很大的固定工作或网络等待。
- “数据现在很小，不用分析”：可以简化实现，但要把可信的数据上限写进决策。
- “平均耗时合格就没有卡顿”：平均值会隐藏慢尾与长任务。
- “内存最后回落就没有问题”：峰值可能已经触发卡顿、崩溃或移动端回收。
- “基准更快就应该替换”：还要比较正确性、可维护性、启动成本和真实场景占比。

### 学完后的自我检验

挑一个你熟悉的列表处理流程，依次写出：输入规模是什么、主要操作次数怎样增长、额外保存了什么数据、哪段工作会连续占用主线程。然后设计至少三个不同规模的输入，说明要固定哪些条件、记录哪些原始样本，以及什么证据会让你选择“改算法”“切片/Worker”或“改变数据边界”。能把推导与测量分别说清，才算真正建立了工程成本判断。

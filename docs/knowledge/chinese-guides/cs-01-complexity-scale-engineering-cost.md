# B02 数据处理与异步协作

## CS-01 复杂度、数据规模与工程成本判断

一份订单列表只有几十行时，怎样查用户名似乎都很快。到了几万行，页面开始停顿；你换了更快的电脑，问题暂时消失，数据再涨一些又回来了。这时真正需要理解的，是程序有没有随着数据增长，重复做越来越多的工作。

这篇先用可以数清的例子建立直觉，再介绍复杂度符号。你会看到：算法的增长趋势、实际耗时、内存峰值和界面响应是几件相关但不同的事，优化时需要分别判断。

本文代码块可以分别运行，`// =>` 后面是可核对的输出。先用小数组数操作次数，再把同一种工作方式推广到大数据，不需要一开始就记住所有公式。

### 同一个问题为什么会越算越费力

给订单补上用户名，是一个很常见的数据处理步骤。最直观的写法是：每遇到一张订单，就从用户列表开头查一次。

```js example=cs01-repeated-search
const users = [
  { id: 1, name: '小林' },
  { id: 2, name: '小周' },
  { id: 3, name: '小陈' },
];
const orders = [{ userId: 3 }, { userId: 3 }, { userId: 3 }];
let comparisons = 0;
const names = orders.map((order) => users.find((user) => {
  comparisons += 1;
  return user.id === order.userId;
})?.name);

console.log(names.join(',')); // => 小陈,小陈,小陈
console.log(comparisons); // => 9
```

三个订单都要查到用户列表末尾。第一次比较 3 次，第二次又比较 3 次，第三次仍比较 3 次，合计 9 次。这里耗费的不是“给三个订单赋值”，而是反复从头查用户。

换一种组织方式：先把用户按 ID 放进 Map，再处理订单。

```js example=cs01-index
const users = [
  { id: 1, name: '小林' },
  { id: 2, name: '小周' },
  { id: 3, name: '小陈' },
];
const orders = [{ userId: 3 }, { userId: 3 }, { userId: 3 }];
const userById = new Map(users.map((user) => [user.id, user]));
const names = orders.map((order) => userById.get(order.userId)?.name);

console.log(userById.size); // => 3
console.log(names.join(',')); // => 小陈,小陈,小陈
```

这次仍处理了同样的数据，却改变了查找方式。前面花一次成本整理索引，后面不必每次扫描全表。它很像先做通讯录索引，再反复按名字找人，而不是每次从第一页读到最后。

如果用户数为 `n`，订单数为 `m`，第一种方式最坏要进行 `m × n` 次匹配比较。在把 Map 单次查询和写入近似视为常数成本的常见分析模型下，第二种方式的增长主要来自建表的 `n` 次处理和订单的 `m` 次查询。

这里有两项需要保留的前提。第一，Map 不被 JavaScript 规范强制实现为某一种哈希表，规范要求平均访问成本次线性，而不是保证每次严格 O(1)。第二，如果 ID 重复，`find` 取第一项，Map 连续 `set` 会保留最后一次的值；优化前必须明确 ID 唯一，或先决定重复项该取哪条。性能更好不能以悄悄改变结果为代价。

### 先定义 n 再谈复杂度

**时间复杂度（time complexity）**描述工作量随着输入规模如何增长。这里的“时间”通常通过代表性操作次数来建模，不直接等于测量出来的毫秒。

`n` 只是代号。搜索名单时它可以是人数，处理文本时可以是字符数，遍历关系图时往往需要同时写节点数 `V` 和边数 `E`。上面的订单数与用户数可以各自变化，因此先写成 `m` 和 `n` 更清楚。

假设有 10 张订单、100 个用户，最坏约比较 1,000 次；订单增至 20 张，约 2,000 次；两边都翻倍，变成 20 张订单和 200 个用户，约 4,000 次。说“数据翻倍”之前，要先说明究竟是哪一份数据翻倍。

还有些成本取决于一项数据有多长。比较两段文本、克隆一个对象、创建一组 DOM，都不应无条件当成一次固定成本的动作。如果每条记录的文本长度为 `k`，扫描 `n` 条记录可能需要把 `k` 也写进模型。只有业务确实给 `k` 设置了稳定上限，才可以在当前分析里把它视为常量。

### 把常见增长方式数出来

**大 O 表示法（Big O notation）**帮助我们抓住规模变大时占主导的增长项。下面的表先展示数量级关系，不承诺每一种操作在机器上花相同的时间。

| 工作方式 | 规模 8 | 规模 16 | 常用表示 |
| --- | --- | --- | --- |
| 从普通数组中按已知下标取一项 | 1 次读取 | 1 次读取 | O(1) |
| 每一步将候选数量减半，直到剩 1 项 | 3 次减半 | 4 次减半 | O(log n) |
| 扫描每一项 | 8 项 | 16 项 | O(n) |
| 每一项都与全部 n 项比较 | 64 对 | 256 对 | O(n²) |

线性增长很好观察：输入多一倍，就多处理一倍的项。平方增长则是两个方向一起扩大：外层多一倍，每一轮内层也多一倍，于是总量约变成四倍。

对数增长可以用“猜数”建立直觉。1 到 1,024 之间，每次询问目标在前半还是后半，只要约 10 次就能缩到一个候选。范围扩大到 2,048，只多一次减半。这不是某种快速循环语法的功劳，而是每一步真的排除了大量不可能的答案。

```js example=cs01-halving
function halvings(size) {
  let count = 0;
  while (size > 1) {
    size = Math.ceil(size / 2);
    count += 1;
  }
  return count;
}
console.log(halvings(8)); // => 3
console.log(halvings(16)); // => 4
console.log(halvings(1024)); // => 10
```

高效的比较排序常见 O(n log n) 增长，可以初步理解为“每层处理一遍数据，层数大约是 log n”，归并排序便是典型例子。但不要由此断言 JavaScript 的 `Array.prototype.sort` 在所有引擎、所有输入上都采用同一种算法或空间开销；具体实现仍由运行时决定。

### 不能只数代码里有几层循环

两层循环并不自动等于 O(n²)。如果内层最多检查三个固定字段，总工作量是 `3n`，仍然随 `n` 线性增长。

```js example=cs01-fixed-inner
const rows = [
  { name: '小林', city: '杭州', role: '开发' },
  { name: '小周', city: '成都', role: '设计' },
];
const fields = ['name', 'city', 'role'];
let reads = 0;
for (const row of rows) {
  for (const field of fields) {
    String(row[field]);
    reads += 1;
  }
}
console.log(reads); // => 6
```

真正需要看的是内层次数能否随着同一个输入规模继续增长。如果显示字段以后可以由用户任意增加，就改用字段数 `k`，保留 O(nk)，不要继续把它写成永远固定的 3。

反过来，看上去只有一个 `map`，里面的 `find` 仍然在遍历；看上去只调用一次 `JSON.stringify`，内部也需要处理整份数据。语法短不代表工作少。

两两比较但不重复配对时，可以数得更精确：4 项会组成 `(0,1)、(0,2)、(0,3)、(1,2)、(1,3)、(2,3)`，共 6 对。

```js example=cs01-pairs
function pairCount(size) {
  let count = 0;
  for (let left = 0; left < size; left += 1) {
    for (let right = left + 1; right < size; right += 1) count += 1;
  }
  return count;
}
console.log(pairCount(4)); // => 6
console.log(pairCount(8)); // => 28
```

总数是 `(n-1) + (n-2) + … + 1 = n(n-1)/2`，主导项仍是平方，所以写 O(n²)。省去重复配对减少了实际工作，但没有改变增长的阶。优化一半工作有时很有价值；只是不要把“常数变小”误说成“从平方变成线性”。

### O 表示上界不表示最坏情况这个词

严格地说，O 描述渐近上界；Θ 表示上下界同阶，Ω 表示渐近下界。这些符号与“最好输入、最坏输入、平均输入”是两个维度。

例如，对一次线性查找，可以分别分析：目标位于第一项时，比较次数为 1；目标完全不存在时，要比较 `n` 次。前者是最好情况 Θ(1)，后者是最坏情况 Θ(n)。不是因为写了 O 才变成最坏情况，而是我们先选择了最坏输入，再描述它的增长。

日常讨论常把紧确的线性增长简称为“O(n)”，这种说法方便交流。需要严谨推导时，要知道一个恒定工作量也能被宽松地写成 O(n)，但写 Θ(1) 更能表达实际情况。符号不是越大越保险，而是越能说明当前问题越好。

### 平均和摊还各自在平均什么

**最坏情况（worst case）**指允许输入中最不利的情况；平均情况则需要输入分布。目标总在前几项，与目标均匀分布在整个数组，得到的平均比较次数并不一样。没有分布，不能随口补一个“平均 O(1)”。

以长度 4 的列表为例，目标等概率出现在四个位置且保证存在，比较次数分别为 1、2、3、4，平均为 2.5。长度变成 `n` 时，平均约为 `(n+1)/2`，仍然是线性增长。平均少查一半，并不意味着平均变成常数时间。

**摊还分析（amortized analysis）**分析的则是一串操作的总成本。想象一个按容量翻倍扩大的储物箱：已有空间时放一件物品很便宜，箱子满了就换大箱，把原有物品搬过去。

从容量 1 扩到 16，中间搬运的旧物品数为 `1+2+4+8=15`。虽然某次搬运需要处理当时全部物品，但前 16 次放入总共只有 16 次新增和 15 次搬运，平均每次不到两项基本工作。

```js example=cs01-amortized
function simulateGrowth(count) {
  let capacity = 1;
  let moves = 0;
  for (let size = 0; size < count; size += 1) {
    if (size === capacity) {
      moves += size;
      capacity *= 2;
    }
  }
  return moves;
}
console.log(simulateGrowth(16)); // => 15
console.log(simulateGrowth(32)); // => 31
```

这是动态数组增长的一种教学模型，不是在声明每个 JavaScript 引擎都以这种方式实现 `push`。它解释的是“偶尔昂贵，长期总成本仍线性”的可能性。摊还常数成本不保证每次都没有延迟尖峰；用户碰巧点按钮时撞上扩容，仍可能感觉到停顿。

### 相同复杂度为什么仍然有快慢差别

下面两个函数都完成求和，时间增长都随列表长度线性变化，但第二个额外创建了数组、对象和字符串。

```js example=cs01-allocation
function sumDirect(values) {
  let total = 0;
  for (const value of values) total += value;
  return total;
}
function sumWithLabels(values) {
  const labeled = values.map((value) => ({ value, label: String(value) }));
  return labeled.reduce((total, item) => total + item.value, 0);
}
console.log(sumDirect([3, 5, 7])); // => 15
console.log(sumWithLabels([3, 5, 7])); // => 15
```

如果实际界面根本不用 `label`，这些分配就是多余的。如果确实需要显示格式化标签，事情就变成了不同的需求，不能只比较纯求和时间然后宣布其中一种“永远更好”。

对象分配会占内存，也会增加之后**垃圾回收（garbage collection）**的工作。引擎优化、数据布局、缓存与字符串长度也会影响实际耗时。复杂度能发现增长方向不合适的方案，却不会抹掉这些成本。

**空间复杂度（space complexity）**同样要说明在算什么。输入数组本来已存在，直接求和只用少量辅助变量；创建 `labeled` 则增加随 `n` 增长的辅助数据。如果函数的任务就是返回 `n` 项结果，结果空间本身已经是 O(n)，但仍可以另报辅助工作区的大小。

递归也会占用调用栈。没有显式新建数组，不等于没有额外空间。如果每次只缩小一项却递归调用一次，深度可能达到 `n`。此前讲过的[调用栈](../chinese-guides/js-01-execution-context-scope-closure.md#从一次函数调用看起)，在这里也是需要计入的成本。

### 总耗时和页面响应要分开看

假设两种处理方式都要完成 100 毫秒的计算。一种连续占用主线程 100 毫秒，另一种分成十段，中间给浏览器处理其他工作的机会。后者的总完成时间甚至可能略长，但用户的点击更有机会及时响应。

这不是数学上的性能倒退，而是评价目标不同。**延迟（latency）**关心一次请求多久得到结果，**吞吐量（throughput）**关心单位时间完成多少工作；界面响应还关心主线程连续多久没有空下来。

例如批量统计一次处理 1,000 条，可能比一次只处理 10 条有更高吞吐，但第一个结果会等得更久。搜索建议通常在意最新输入尽快得到结果，离线导出则可能更看重总完成时间。选择目标以后，才知道应该减小批次、建立索引，还是改变线程安排。

浏览器的刷新间隔也不是 JavaScript 可以独占的时间。样式、布局与绘制等工作还需要机会。桌面电脑性能较强，也不能消除主线程被长循环连续占用的问题；线程与分块的具体做法见 [CS-03：把工作拆开让界面有机会响应](../chinese-guides/cs-03-large-data-workers-incremental-memory.md#把工作拆开让界面有机会响应)。

### 测量先保证比较的是同一件事

**基准测试（benchmark）**不是随便运行一次、取一个毫秒数。它帮助你回答具体问题，例如“每次查询都重建索引是否划算”或者“已经有索引时，一百次查询的耗时怎样”。这两个问题的计时范围就不同。

用下面的安排做一个小型比较，比直接追逐某个跑分更有用：

| 要确认的事情 | 订单索引例子中怎样处理 |
| --- | --- |
| 结果是否一致 | 两种实现给每张订单补出的名字相同，重复 ID 规则一致 |
| 数据规模 | 分别记录订单数、用户数和字段长度 |
| 查询分布 | 都命中前几项、都命中末尾、部分缺失分别观察 |
| 计时范围 | 分开报告建索引与使用索引；按业务需要再合计 |
| 运行条件 | 使用同一台目标桌面设备、同一浏览器和构建模式 |
| 原始结果 | 重复若干次，保留每次样本，而不是只抄一个平均值 |

`performance.now()` 可测短时间间隔，但开发者工具、后台任务、运行时预热和垃圾回收都会带来波动。输入生成、打印大量日志或开发构建的额外检查，也不应无意混进核心算法的计时范围。反过来，用户实际每次都必须承担的复制、排序或建索引，就不能为了让数字好看而从端到端时间中删掉。

中位数适合观察典型表现，**百分位数（percentile）**适合观察较慢样本。假设有 20 次结果，将它们从小到大排列，按 nearest-rank 定义，p95 取第 19 项；它不是“最慢一次”，不同工具也可能使用插值方式计算。样本很少时，不宜把 p95 的一位小数当成精确保证。

分析增长时，至少选几个不同规模。输入翻倍而操作次数接近四倍，说明可以检查嵌套查找；实测时间没有严格四倍，也不能直接否定推导，常数与环境噪声仍在起作用。推导解释结构，测量说明当前实现的实际表现，两者互相补充。

### 用成本判断决定下一步

回到订单例子。如果一张页面只偶尔查一条记录，建立完整索引可能不划算；如果相同用户表会被几万张订单反复查询，建表成本就更容易被摊薄。若用户表经常变化，还要考虑索引何时失效，谁负责更新。

再假设索引已经很好，页面仍然卡。接下来检查的是不是每次输入都格式化全部记录，或者最终一次插入了过多 DOM。换算法、减少数据、分块、Worker 和服务端聚合解决的是不同环节，不能只把它们排成“越来越高级”的工具清单。

| 观察到的原因 | 优先考虑的变化 |
| --- | --- |
| 每条记录都反复查整张表 | 建索引、复用查找结果 |
| 根本不用的大量字段也在处理 | 缩小输入与输出范围 |
| 工作必须做，但连续占用太久 | 分块或合适的 Worker |
| 队列、副本、缓存同时保留 | 控制在途数量与引用生命周期 |
| 客户端不需要全部原始数据 | 服务端筛选、分页或聚合 |

工程决策可以很短，但要具体：当前有多少数据，主要重复工作是什么，改变了哪一段成本，保留了哪些结果语义，什么时候需要重新评估。这样，复杂度就从写在答案旁的标签，变成帮助你选择实现的工具。

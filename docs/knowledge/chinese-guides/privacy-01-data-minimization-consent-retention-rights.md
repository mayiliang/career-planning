# 隐私工程知识点讲义

## PRIVACY-01 数据最小化、同意、留存与用户权利

隐私工程不是在发布前补一张勾选框，也不是把数据库字段加密就结束。它要求团队能回答：为了什么目的处理哪些人的哪些数据，是否真的必要，以什么依据处理，谁能访问，保存多久，流向哪些系统和处理方，个人如何行使权利，以及停止处理后怎样让所有副本收敛。

### 学习前先确认

- 无直接前置。本讲从数据生命周期、产品目的和可验证工程控制开始；涉及具体地区法律适用时，应转交隐私/法务专业人员判断。

### 一、从处理活动而不是数据库表开始

“用户表有 email 字段”只描述静态存储，无法说明数据怎样进入系统、为什么被处理、是否进日志、是否发送给模型供应商、是否进入分析仓库和备份。隐私分析的基本单位应是处理活动。

一项处理活动至少记录主体类别、数据类别、来源、目的、处理动作、接收方、存储位置、保留期、合法性依据、owner 和安全措施。AI 对话功能还要记录提示词、附件、检索片段、输出、反馈、向量表示、审核记录和模型提供方。

同一个字段可能服务多个目的。例如邮箱用于登录、账单和营销，三种目的的必要性、触发条件、退出方式与留存期不同。不能用“已经收集”推导“可以无限复用”。

### 二、目的要具体到能约束设计

**目的限制（Purpose Limitation）**要求先定义清楚、具体、正当的处理目的，再让收集、使用和共享围绕目的展开。“改善服务”“提升体验”“用于 AI”过于宽泛，无法判断某字段是否必要，也无法让用户形成合理预期。

可执行的目的写法包括“保存最近 30 天对话，使已登录用户跨设备继续会话”或“在用户主动提交诊断报告后，保留 7 天请求元数据以定位该次失败”。这些描述包含主体、功能、数据范围和期限，能转化为控制。

新增用途不是文案编辑。产品要做兼容性与合法性评估，更新数据地图、权限、告知、同意/退出、供应商合同、留存和删除。若原依据不覆盖新用途，就先阻断发布并升级判断。

### 三、最小化发生在收集前

**数据最小化（Data Minimization）**不是“磁盘快满时删点字段”，而是在每个目的下只处理足够、相关且必要的数据。判断单位是字段×目的×阶段，不能说整个表“都可能有用”。

对每个字段提出反事实：若不收集，核心功能是否无法完成；能否在设备本地计算；能否用粗粒度、短期、聚合或假名化数据；能否只在出错且用户同意时收集；能否用抽样代替全量。

必要账号 ID 与可选诊断数据应分开。拒绝诊断上传不能阻断登录和核心任务；页面不应用深色模式诱导用户开启可选处理，也不能把多个不相关目的捆绑成一个总开关。

### 四、派生数据仍然可能关联个人

哈希邮箱、设备指纹、embedding、行为评分和内部账号 ID 不因“看不懂”就自动匿名。只要能被合理地重新关联到个人、账号或设备，就仍应纳入清单、访问控制、权利请求与泄漏评估。

匿名化要求重新识别风险降到适用规则认可的程度，通常比删除直接标识更难。假名化通过替换标识降低部分风险，但映射表或其他数据可恢复身份，因此仍要保护。

模型输出也可能复述输入或推断敏感信息。团队应记录输入到派生物的关系，避免只删除原文却让索引、摘要、特征和训练样本永久存在。

### 五、合法性依据不等于全部使用同意

不同地区允许的处理依据不同，可能包括履行合同、法定义务、同意或其他适用基础。工程师的职责是把已经确认的依据落实为条件与证据，而不是自行选择最方便的法律结论。

若依据不是同意，界面也要提供必要告知和适用权利；若依据是同意，则要确保自愿、具体、知情、清晰且可撤回。把所有处理都塞进同意会造成不必要弹窗，也可能因不能自由拒绝而失效。

系统记录每项处理活动的依据版本、确认人和适用范围。未知地区、新主体或新用途不能静默沿用旧值，应进入发布闸门等待专业复核。

### 六、同意是一条可变状态链

同意记录不仅是 `true/false`，至少包含主体、目的、数据类别、告知版本、界面语言、动作、时间、来源与撤回时间。前端显示的开关必须映射到服务端权威状态，并在不同设备间一致。

默认不勾选可选目的，不用拒绝按钮弱化、重复弹窗或阻断核心服务来强迫同意。多个目的分别选择，敏感处理或跨境等是否需要单独同意由适用规则与法务结论决定。

撤回应像同意一样容易。撤回后停止未来处理，并按规则处理已经收集的数据和下游副本；不能只把开关变灰而继续上报。无法立即删除的法定保留数据要进入冻结、隔离或仅必要存储状态。

### 七、告知应分层但不能隐藏事实

首层界面在作出决定前说明关键目的、数据、接收方、影响与选择；详细层提供完整规则、期限、权利和联系方式。分层是降低认知负担，不是把重要限制埋在十级链接之后。

运行时告知应出现在用户最需要理解的时刻，例如上传医疗附件、开启位置、把内容发送给外部 AI 提供方或开启长期记忆。隐私政策不能替代上下文说明。

版本变化要判断是否影响目的、范围或用户预期；必要时重新告知或重新取得选择。证据保存告知版本与用户动作，而非依赖当前页面截图还原历史。

### 八、数据清单必须连接真实数据流

数据清单以字段和处理活动为粒度，数据流图连接前端、API、队列、主库、缓存、对象存储、搜索、分析、向量库、日志、备份、客服工具和供应商。每条边标明协议、地区、加密、目的和 owner。

静态文档容易漂移。可从 schema、事件目录、网关、云资源和供应商配置持续对账，发现未登记字段、未知目的或新地区。自动发现用于提示，不替代人工判断。

每次功能评审让工程变更关联处理活动 ID。若代码引入新事件或外发端点却没有清单记录，流水线或发布评审应阻断，而不是等审计时补表。

数据地图还应记录谁能以什么目的访问。业务服务、分析人员、客服、管理员和供应商使用不同身份与权限；临时排错采用限时授权并记录原因。一个广泛共享的生产只读账号会让目的限制失去执行边界，即使它从未执行写操作。

权限检查要落在服务端与数据平台，导出、批量查询和后台搜索尤其需要单独审批、速率限制和审计。定期把实际访问日志与声明用途对账，发现某角色长期不用的权限就收回，而不是只在员工离职时处理。

### 九、分类决定保护强度但不决定全部适用性

分类可以区分公开、内部、机密、个人信息、敏感个人信息、重要数据等。标签驱动日志脱敏、访问控制、加密、地区路由和保留策略，使控制可自动执行。

分类依据需要明确，例如数据能否识别个人、泄露影响、业务关键性和法律目录。不要只凭字段名；`note` 可能含医疗信息，附件 URL 可能带访问凭证，错误堆栈可能含用户输入。

自动分类会误报和漏报，高风险字段由 owner 与专业人员复核。未知分类默认进入保守路径，不能为了发布速度自动当普通数据。

### 十、保留期来自目的与义务

保留期应写成可执行规则：起点、期限、触发事件、例外、动作与 owner。例如“对话自最后一次活动起 30 天删除，进入备份后最长 35 天不可恢复淘汰；存在争议保全时冻结并记录审批”。

“业务需要”“永久”或“直到用户删除”通常无法审计。短期缓存、日志、索引和对象版本也要有 TTL；生命周期规则失败应告警，而非只配置一次就相信它。

数据减少能降低泄漏影响、权利请求成本和错误复用。保留不是越久越有价值：过时数据可能误导模型、造成错误个性化，并增加存储和治理负担。

### 十一、删除是跨系统的工作流

删除主库一行只是开始。系统要找到对象存储、缓存、搜索索引、向量库、分析仓库、消息队列、导出文件、客服副本、供应商和备份中的关联数据，并根据各自语义删除、匿名化、冻结或等待周期淘汰。

删除任务需要稳定 request ID、主体验证、范围快照、每个处理方状态、重试、死信、超时和最终结果。任务本身只能保存执行所需最小元数据，不能为了证明删除又复制整份被删除内容。

**删除墓碑（Deletion Tombstone）**是最小化记录“某对象已被删除/禁止重新导入”的控制数据。它防止迟到事件或备份恢复让数据复活，但墓碑也要限制内容、访问和期限，不能保存原文。

### 十二、备份中的删除要诚实建模

不可逐条修改的加密备份可以通过限定保留期、严格隔离和恢复后重放删除清单来收敛。产品不能声称“立即从所有介质物理消失”，若实际是 30 天备份淘汰，应在流程和告知中表达。

恢复演练必须验证删除不会复活：恢复某时间点备份后，在恢复环境应用 tombstone/删除日志，再开放业务。若恢复流程绕过权利状态，真实事故时会重新暴露已经删除的数据。

备份密钥销毁可用于批量不可读化，但要评估共享密钥影响和证明。不要把“有备份”当无限保留理由。

### 十三、访问、复制、更正和导出是不同能力

用户查看当前资料、取得机器可读副本、更正错误、限制处理、反对特定用途和转移数据，语义可能不同。产品与法务先确定适用权利，再为每项定义身份验证、范围、期限、例外与申诉。

导出包含用户可理解的数据和必要上下文，使用安全下载、短期链接、加密与访问日志。不要把内部密钥、他人信息、反欺诈机密或无法解释的原始表全部打包，也不能只导出 UI 当前可见的小部分。

更正请求要传播到派生显示和下游；历史审计记录可按规则保留原事实并追加纠正，而不是篡改不可变日志。限制处理时系统要能冻结非必要任务，而非只有一个工单状态。

### 十四、身份验证不能反过度收集

权利请求要防止攻击者导出或删除他人数据，但验证强度应与风险相称。已登录用户可以近期再认证，高风险或失去账号访问时采用额外证据和人工流程。

不能为了处理简单退出请求索取身份证扫描件，若系统原本没有这种高敏数据。若确需额外材料，限定用途、访问和短期删除，并说明无法验证时的申诉路径。

请求状态对外不泄露某邮箱是否存在账号。客服和管理员界面实行最小权限、双人审批或分级复核，敏感导出有完整审计。

### 十五、第三方处理方也是生命周期的一部分

供应商台账记录处理目的、数据类别、角色、子处理方、地区、保留、删除能力、安全措施、事件通知和退出迁移。前端 SDK 可能在页面初始化时即采集数据，不能等用户点击功能才认为发生处理。

合同承诺要落实到技术配置：关闭供应商默认训练、缩短日志保留、选择区域、限制 API key、使用租户隔离、建立删除接口和验证回执。没有可执行 API 时定义工单与人工确认时限。

退出供应商时不仅停止新流量，还要导出必要数据、删除历史副本、撤销密钥和 SDK、更新清单与告知。供应商声称“已删除”需要可审计确认，重要流程定期抽样演练。

### 十六、AI 产品需要拆开输入、记忆、训练与评估

用户为获得一次回答提交内容，不自动等于同意长期记忆、训练通用模型、人工评审或营销分析。每个目的单独定义数据、选择、期限和接收方。

向量 embedding、提示缓存、反馈数据和安全审核样本都进入数据地图。若训练集无法逐条删除，需要在收集前说明并建立合适依据、隔离与排除机制；不能上线后才说模型参数无法回滚。

最小化还包括上下文构建：只发送完成当前任务所需片段，去掉无关字段和隐藏元数据，限制工具可访问资源。隐私控制与 token 成本、延迟和模型质量可以共同优化。

### 十七、用不变量把政策变成工程控制

为每个处理活动定义不变量：未启用可选诊断时网络中没有诊断事件；撤回后新事件在入口被拒绝；超过保留期的数据不可从主库和索引检索；删除完成后供应商回执齐全；导出只能由已验证主体下载。

测试使用合成用户和可追踪标记，沿真实数据流查询主库、缓存、索引、对象和供应商沙箱。故意让某个删除消费者失败，验证重试、告警和最终一致；故意恢复旧备份，验证 tombstone 阻止复活。

生产仪表盘关注未分类字段、过期数据、删除积压、撤回后事件、供应商超时和异常管理员访问。指标只有 owner、阈值和处置流程时才是控制证据。

### 十八、适用性不确定时工程师应停止推断

隐私规则取决于用户、处理者角色、地区、数据类型、规模、行业和具体目的。工程师可以识别事实、实现已确认控制、保存证据和发现冲突，但不应替代律师给出最终适用结论。

升级单至少包含产品事实、数据流、主体与地区、处理方、数量、期限、当前假设、候选控制、发布时间和负责人。法务结论返回后记录版本和条件，转为配置与测试。

法规、合同或产品事实变化时重新评估。过去的复核不能永久覆盖新供应商、新模型、新用途和新地区；发布闸门应让未知状态显式失败，而不是默认放行。

### 学完后应能说明

你应能以处理活动画出完整数据生命周期，区分目的限制、最小化、分类、同意、撤回、保留和各种用户权利；能设计跨主库、缓存、索引、备份与供应商的删除/导出工作流，并用负向实验验证控制；也能明确工程事实与法律适用判断的边界，在不确定时提供足够证据并阻断高风险发布。

# AI Code Review、风险证据与人工责任知识点讲义

## AIDEV-04 AI Code Review 与风险分级

AI 可以很快浏览大量 diff、搜索相似模式并提出遗漏，但它既不了解所有业务不变量，也可能引用不存在的 API、忽略变更外上下文或把风格偏好夸成严重缺陷。可靠的 AI Code Review 把模型当作高吞吐的假设生成器，把代码、运行证据、需求和责任人当作判定依据。评审的结果不是评论数量，而是高风险变化被发现、真实问题被修复、误报被解释且合并责任始终清楚。

### 学习前先确认

- 直接前置：[AIDEV-03 AI 生成代码的验证金字塔](../chinese-guides/aidev-03-ai-generated-code-verification.md#aidev-03)用于理解独立测试预言和证据闭环；[CAREER-05 代码评审、风险沟通与责任边界](../chinese-guides/career-05-code-review-risk-communication.md#career-05)用于理解普通代码评审的上下文、评论质量和合入责任。两者分别提供验证方法与协作基础。

### 一、Review Hypothesis 是待证伪判断

**评审假设（Review Hypothesis）**描述某段变化在特定输入和状态下可能违反某条合同。它包含文件位置、触发前提、执行路径、期望、可能实际结果和需要观察的证据。AI 输出首先处于 hypothesis 状态，不能直接标为 bug。

“这里可能有竞态”信息不足；“用户连续保存 A、B，A 响应较晚并覆盖 B；观察最终版本与请求序列”才可验证。评审者运行最小复现、读取调用者与测试、核对 API 文档，然后标记 confirmed、rejected、needs-context 或 accepted-risk。

同一模式在不同语境风险不同。未取消请求在搜索建议中可能只是浪费，在自动付款中可能写入过期金额。模型相似度不能替代业务对象、状态机和权限边界。

### 二、先理解变更意图和边界

评审从需求、非目标、基线行为、部署方式和变更清单开始。先看文件级结构、公共接口、数据流和新增依赖，再逐行读实现。没有意图时，AI 容易把刻意的兼容行为当错误，或忽略未修改文件中的隐含调用者。

检查 diff 是否包含意外生成文件、锁文件漂移、配置、数据库迁移、权限和遥测变化。新增一个前端按钮可能对应后端授权、审计和错误恢复；仅评审组件模板会漏掉真正风险。删除代码也需确认旧入口、导入和运行配置已清理。

大型变更拆成可独立理解的部分。纯重构与功能修改分离，协议与消费者分阶段但保持每个提交可运行。AI 上下文越大不一定越好，显式模块边界和问题清单比无差别上传仓库更可靠。

### 三、Trigger Path 把评论连到真实执行

**触发路径（Trigger Path）**是从可控输入或系统状态，经具体分支与边界，到可观察错误或影响的因果链。安全、并发、资源和兼容性问题必须能说明路径，不能只因出现某个关键词就升级风险。

例如发现 `postMessage(..., '*')`，先确认消息含什么、目标窗口是谁、攻击者能否控制接收或发送端、是否校验 origin/source、最终能触发什么动作。只有通配符不自动等于最高危；但若敏感 token 被发往不受控窗口，触发和影响都明确。

路径证据可来自测试、最小脚本、Network、trace、类型与控制流、规范或生产数据。行号只是入口，不是证明。修复后沿同一路径复验失败，并验证合法路径仍工作。

### 四、Risk Severity 分开影响、可能性与证据

**风险级别（Risk Severity）**由影响、可触发性、暴露范围、现有补偿控制、检测/恢复能力和证据强度共同决定。严重性不是模型置信度，也不是代码风格。可以使用 P0–P3，但团队必须定义每级的业务含义和响应时限。

P0 通常表示正在或极可能造成广泛资金、权限、数据或服务灾难，需要停止发布；P1 是可明确触发的高影响缺陷；P2 是范围受限或有缓解的真实问题；P3 是低影响维护、清晰度或非阻断建议。证据不足的高影响线索应标“待调查”，而不是假装已确认 P0。

同一问题在发布前后处理不同，但事实级别不应为赶进度随意降低。接受风险要记录 owner、原因、期限、监测和退出条件。格式、命名与个人偏好默认不是高危，除非能证明造成解析、兼容或安全后果。

### 五、按风险面系统扫描而不靠关键词

认证授权：检查主体、租户、资源与动作是否在服务端判定，缓存和批量接口是否越权。输入输出：检查运行时校验、注入、编码、错误泄露和不可信内容传播。状态与并发：检查迟到响应、重复提交、版本冲突、取消和未知结果。

资源生命周期：订阅、Observer、ObjectURL、流、文件句柄、计时器和子进程是否释放。错误恢复：异常是否被吞、错误分类是否准确、回滚和重试是否重复副作用。可访问性：语义、名称、焦点、键盘、动态状态和错误提示是否保持。

依赖与供应链：新增包是否必要、来源和 lockfile 是否改变、安装脚本和许可证是否审计。性能：是否出现 N+1、无限列表、主线程长任务、大对象保留和缓存失效。每一类都以该变更实际触达的边界为准，不生成泛化评论填数量。

### 六、幻觉 API 与过时知识要单独核验

AI 可能建议不存在的函数、错误参数、过期安全选项或另一版本的框架行为。凡涉及外部 API，检查仓库锁定版本、类型定义、官方文档和最小运行结果。能编译也不证明运行时环境支持，类型包可能与真实依赖漂移。

模型引用的 CVE、许可证和浏览器支持具有时间性，应保存查询日期与来源。无法核验的说法不进入阻断评论。不要因 AI 给出漂亮代码就直接粘贴修复；补丁仍需经过相同评审、测试和依赖审计。

组织可维护“常见幻觉清单”，但不能把过去误报永久排除。版本变化后重新验证。规则的目标是提升证据效率，不是让模型在某些目录免审。

### 七、并发评审要画事件序列

并发问题通常不在单行。画出请求 A/B、状态版本、取消、服务器写入和 UI 提交顺序，寻找迟到覆盖、重复副作用与丢失更新。仅说“加 debounce”可能减少请求，却不解决已经在途的旧写入。

前端保存可携带资源版本或幂等键，服务端做条件写入；响应只在仍对应当前 intent/version 时更新界面。取消是资源优化，不等于服务端没有执行。遇到网络未知结果要查询操作状态而非盲目重发。

测试使用可控延迟和确定性调度制造 A 先发后回、B 后发先回、重复点击、卸载后回调和服务端冲突。随机循环偶尔失败不是良好证据，固定序列才能复验修复。

### 八、资源泄漏需要所有权与释放证明

发现 `createObjectURL`、事件监听、Observer、stream、Worker 或订阅时，先确定谁创建、谁持有、何时失效、谁释放。组件卸载不是唯一边界；文件替换、请求取消、页面隐藏和错误分支也可能结束所有权。

内存快照和计数器应在相同操作序列前后比较，区分缓存与无法到达却仍被引用的泄漏。AI 能提示缺少 `revokeObjectURL`，但人工要确认 URL 是否仍用于下载或图片解码，过早释放也会造成错误。

修复采用集中生命周期、幂等 cleanup 和明确状态。测试重复进入离开页面、替换资源、异常中断和快速交互，确认句柄回到基线且功能未提前失效。

### 九、可访问性不是“最后跑一次扫描”

AI 能发现没有 label、可点击 div 或明显颜色问题，但动态焦点、读屏公告和业务错误恢复需要真实交互验证。审查新增控件是否使用原生语义，名称是否稳定，键盘顺序是否合理，弹层关闭后焦点是否返回。

自动扫描覆盖确定规则，组件测试模拟键盘和可访问查询，浏览器与辅助技术验证复杂流程。截图像素正确不代表可访问，DOM 有 ARIA 也不代表行为正确。修复不能只加属性而保留错误交互模型。

评审评论说明受影响用户和任务，例如“保存失败后焦点丢到 body，键盘用户无法找到错误并重试”，比“缺少 focus”更可行动。

### 十、误报处理是评审质量的一部分

拒绝 AI 评论时记录原因：路径不可达、已有服务端控制、版本不适用、测试证明行为正确、或只是风格偏好。不要只点“忽略”，否则同类噪声无法校准。待上下文问题指派 owner 和所需证据。

误报率按风险类别、模型/提示版本和仓库区域观察。降低噪声不能以漏掉高风险为代价；可采用两阶段流程，先广泛生成假设，再用确定性工具和人工筛选。模型自评“高置信”只用于排序待查，不用于合并门禁。

历史已确认问题与误报组成回放集。更新规则后比较召回、精确、复核时间和严重性偏差。数据集保留真实上下文并去敏，避免只收集容易样例。

### 十一、评论要让作者可以行动和复验

一条高质量评论包含优先级、位置、触发、影响、证据和期望合同；可以提出最小方向，但不必替作者完成设计。区分阻断、建议和提问，语气针对代码而非个人。多个同根因问题可合并，避免复制十条模板。

修复建议不能扩大范围或删除保护。若提出 `try/catch`，说明怎样保持错误可见与状态一致；若提出权限检查，明确必须在服务端按对象核验；若提出依赖替换，附当前版本与兼容依据。

作者回应采用已修复、不同意并给证据、接受风险、需要讨论等明确状态。对话结论写回代码、测试或 ADR，不能只留在评论线程后失去上下文。

### 十二、Human Accountability 不可委派给模型

**人工责任（Human Accountability）**表示具备权限和上下文的人对风险接受、合并与发布负责。AI 可以建议、分类和生成测试，但不能成为 CODEOWNER、批准例外或在无人知情时合入自己的修复。

责任人核对评审范围、复现关键问题、确认测试预言独立、处理误报与未决风险。高风险模块需要领域或安全 owner；模型不能用更多轮自我评审替代独立人审。紧急合并也记录批准人、临时控制与复查期限。

评审系统保留谁提供 AI 建议、谁确认、谁修改、谁批准和使用了哪个版本。责任不是追责工具，而是确保出现不确定性时有人能做决定、停止发布和组织恢复。

### 十三、把 AI 评审嵌入而不堵塞交付

先以 diff 与变更清单做快速扫描，高风险触发更深上下文与测试；低风险文档/格式变化走轻量路径。AI 分析可并行，但合并门禁只读取已确认状态。超时或服务不可用时有人工退化流程，不让外部模型成为唯一发布单点。

敏感仓库只发送允许的最小上下文，外部服务条款、留存和地区符合组织政策。秘密扫描和脱敏在发送前执行。AI 评论正文也可能暴露漏洞与用户数据，访问权限跟随仓库。

统计真正结果：确认问题的严重性与逃逸率、误报复核时间、修复后回归、评审周期和生产缺陷。评论数量、模型 token 和“采纳率”单独看都可能激励错误行为。

### 十四、建立可重放的评审验证集

选择权限绕过、迟到覆盖、ObjectURL 泄漏、吞错、焦点丢失、幻觉 API、锁文件漂移和纯风格意见等历史变化，冻结代码、需求与预期证据。每次模型、提示或工具升级都运行，比较是否找到真实问题并拒绝误报升级。

验证集要含修复后版本，防止模型继续报告已经不存在的问题；含上下文不足样例，要求它明确请求信息而非编造；含诱导文本，确保仓库注释不能改变评审规则。人工抽查评测本身，避免标签陈旧。

可参考 [Google Code Review 指南](https://google.github.io/eng-practices/review/reviewer/)、[GitHub Dependency Review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review) 与项目自身的安全、测试和可访问性规范。外部指南提供方法，最终严重性仍需映射本产品的用户与业务影响。

### 十五、评审工具自身也受权限和数据边界约束

AI 评审服务只获得目标 diff、必要调用上下文和只读仓库范围，不应默认读取相邻项目、用户目录、生产秘密或全部历史。第三方服务、插件和模型分别记录数据去向、保留、地区与访问主体；安全模块可以使用受控本地或隔离评审路径。

自动评论账号没有合并、改权限或运行生产工具的能力。若允许自动建议补丁，补丁进入独立分支并由普通门禁验证；模型不能修改评测标签、删除失败测试或把自己的评论标成已解决。外部文件和 PR 描述中的指令保持不可信，不能重写评审规则。

服务不可用、上下文超限或结果截断时明确显示覆盖缺口，转人工流程。团队定期抽样“无评论”的变更，检查沉默是否来自真正无问题、权限读取失败或模型退化。只有同时治理输入范围、执行权限与缺失状态，AI 评审才不会成为新的供应链和盲区。

学完后，你应能把 AI 给出的评论改写成可证伪假设，沿触发路径收集证据，按统一风险规则排序，并清楚说明谁对合并负责。好的 AI 评审让人更快看见关键风险，而不是用大量看似专业的评论替代工程判断。

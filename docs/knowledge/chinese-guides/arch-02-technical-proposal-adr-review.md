# 技术方案、ADR 与架构评审知识点讲义

## ARCH-02 技术方案、ADR 与架构评审

复杂技术决策很少只有一个明显正确答案。若团队先宣布结论，再补一份冗长方案，文档只是在制造共识外观；若只在会议里讨论，几个月后没人知道当时有哪些约束、放弃了什么、为何需要复查。成熟的架构决策把问题、真实候选、证据、异议、决定、后果和退出条件连成可追溯记录，让后来的工程师可以理解、验证甚至推翻它。

### 学习前先确认

- 直接前置：[ARCH-01 质量属性、约束与架构权衡](../chinese-guides/arch-01-quality-attributes-constraints-tradeoffs.md#arch-01)，用于把业务目标写成可测场景，并在共同约束下比较方案。其递归前置由该讲义继续展开。

### 一、先判断是否值得正式决策

架构上显著的决定通常跨模块或团队、影响关键质量属性、迁移成本高、难以撤销或会形成长期合同，例如渲染模式、身份边界、数据所有权、组件平台和运行拓扑。局部、低风险、易回退的实现细节不必都写 ADR。

文档形式与风险相称。小决定可以一页记录，大决定需要 RFC、原型、评审和多份后续 ADR。篇幅不是成熟度，最重要的是别人能找到问题、证据、决定和后果。

先指定 decision owner、受影响对象和截止。没有有权做决定的人，评审会无限讨论；只有职位决定而没有证据，则会压制真实风险。owner 负责收敛，不代表可以忽略必需的安全、法律或业务责任人。

### 二、问题陈述不偷偷包含答案

“我们需要迁移到微前端”已经把方案写进问题。更好的陈述是：“三支团队发布互相阻塞，过去季度平均等待多少小时；需要在不破坏统一身份与性能预算下提高独立交付。”这样候选可以包括流程、模块化、平台或微前端。

写清当前行为、用户与业务影响、范围、非目标、约束和成功/失败指标。把事实、假设和偏好分开，并链接原始数据。若问题规模未验证，先做发现，而不是设计庞大解法。

非目标用于控制范围，但不能藏风险。例如“不处理无障碍”若方案改变公共组件，就不是合法非目标。范围边界也要说明与相邻系统的接口和责任。

### 三、Decision Driver 连接业务与技术

**决策驱动因素（Decision Driver）**是能区分候选、来自目标或约束并有优先级的条件，例如核心任务成功率、恢复时间、数据地区、发布独立性、包体、成本和团队能力。它不是所有人都同意的口号。

每个 driver 写来源、度量、最低门槛和权重/优先关系。硬约束先淘汰不可行方案，软目标用于比较。权重由承担结果的人确认，工程师解释技术后果。权重相近且证据不确定时，不要用精确总分制造确定性。

驱动因素随环境变化。把流量、价格、组织和供应商假设写进记录，设复查触发器。一个结论只在其 driver 有效时成立。

### 四、至少保留包含现状的真实候选

候选通常包括维持现状/局部修复、渐进方案和更彻底方案。每个方案都必须在给定约束下真实可行，不能把反对项写成故意糟糕的稻草人。若只有一个可行方案，说明约束为何已排除其他项。

描述候选的运行机制、影响边界、迁移、运维、失败和退出，不只列优点缺点。相同框架换不同供应商可能不是独立架构候选；相同目标下改变边界、所有权或一致性策略才可能产生实质差异。

允许组合方案，但避免把目标方案不断吸收其他方案优点而不承担复杂度。组合后的接口、owner 和新风险重新评估。

### 五、Evidence Matrix 让比较使用同一把尺

**证据矩阵（Evidence Matrix）**按同一组 driver 列出每个候选的实测、估算、推断与未知。每个单元链接来源、版本和误差，使结论可以被复核。空白不是零风险，而是尚未知道。

高风险假设用最小原型、容量测试、故障演练、用户研究或迁移 spike 验证。原型要复刻决定性约束，例如真实身份、缓存、低端设备和运维，而不是只做顺畅 happy path。一次 benchmark 不能外推所有流量。

外部案例用于产生假设，不是直接证据。另一家公司选择某技术，不说明你的团队、数据和成本相同。供应商 benchmark 记录配置和限制，并在可行时用自己的工作负载复验。

### 六、Architecture Decision Record 保留决定历史

**架构决策记录（Architecture Decision Record）**是对一个架构上显著决定的追加式记录，包含状态、上下文、候选、决定、理由、后果、风险、owner 和复查。接受后不悄悄改写历史；变化时新建 ADR 并标记 supersedes/superseded-by。

一份 ADR 聚焦一个决定。RFC 可以探索更大方案，多个 ADR 分别记录数据所有权、渲染、认证或迁移策略。链接保持关系，但不要把整套系统塞进一份永远未完成的文档。

状态可为 proposed、accepted、rejected、deprecated、superseded。Rejected 方案同样有价值，防止新成员在相同约束下重复争论；若约束变化，可以新记录重新评估。

### 七、Dissent Record 保护重要异议

**异议记录（Dissent Record）**保存反对意见、依据、影响范围、回应和未解决状态。评审目标不是消灭不同意见，而是确认重要风险被理解、由谁承担、如何监测。职位和多数投票不能让技术事实消失。

异议具体到场景：“方案在读屏焦点恢复上没有验证，可能阻断结算”，比“我不喜欢这个框架”有用。owner 可以在未知仍存在时决定前进，但要记录风险接受、停止阈值和补偿实验。

心理安全影响证据质量。会前允许异步评论，会议中先复述反方最强论点，结论后公开未决项。反对者不需要为证明全部后果承担无限工作，但应提供可检查线索。

### 八、评审会议围绕未知和权衡

把背景和矩阵提前发出，会议不逐页朗读。先确认问题与 driver，再检查候选是否真实、证据是否可比、高风险未知是否有实验，最后由 owner 收敛决定或列出缺失输入。

邀请产品、运维、安全、隐私、无障碍、数据和受影响团队中真正承担后果的人。所有人参加所有评审会造成疲劳，可按风险选择必需角色，并保留异步入口。

会议纪要记录决定、异议、行动、owner、截止和下一门槛。讨论热烈或全员点头不是验证，行动项必须回到矩阵和 ADR。

### 九、面向不同受众保持同一事实

给业务负责人说明用户结果、成本、期限、风险和可逆性；给工程团队说明边界、合同、迁移、观测和操作。两份说明可以详略不同，但不能对一方隐藏关键代价或把未知包装成确定。

图示表达组件/上下文、数据流、部署和时序中的必要视角，并配文字解释边界与责任。一个大框图不能回答所有问题。图与 ADR 版本同步，避免过期图继续驱动实现。

非技术说明避免只说“重构”和“技术债”，要连接收入、风险、交付和用户任务；技术说明也不能丢失业务 driver，否则实现会局部优化。

### 十、决定必须附带后果和责任

记录积极与消极后果、短期与长期成本、新增能力、放弃能力、团队学习和运维负担。决定采用某服务也意味着接受其配额、故障、价格与退出路径；采用自建则接受持续 owner 和值班。

将决定转为边界、任务和验收：接口、数据 owner、部署单位、质量预算、兼容期和监测。没有实现连接的 ADR 只是档案。反过来，代码中出现的新架构决定也应补记录。

关键风险有责任人和到期，不把“团队”当 owner。owner 变更时显式交接，离职不会让决策无人维护。

### 十一、迁移与回滚是方案的一部分

描述从现状到目标的垂直切片、兼容层、数据策略、发布门槛、观测和旧路径删除。若只描述最终架构，团队可能在危险的中间态停留数年。迁移期间的双运行成本进入比较。

每阶段独立提供用户价值或风险降低，并能停止。回滚说明代码、配置、数据和外部副作用如何处理；“Git revert”不能撤销已迁移数据或发送通知。不可逆步骤需备份、演练或更高审批。

退出条件不仅是失败回滚，也包括何时放弃候选、何时下线旧系统。兼容层有删除日期与使用遥测，防止过渡变永久。

### 十二、低置信度决定用小赌注推进

有时必须在证据不足时决定。记录置信度、不确定来源和能最快获得信息的可逆步骤。先限制用户、流量、数据或期限，设置停止阈值，而不是一次押上全系统。

原型代码不默认进入生产；若进入，要补质量、owner 和删除计划。实验结果若推翻目标方案，应允许改变结论，不能因已投入而继续。沉没成本不是 driver。

对于高影响不可逆选择，延迟决定和收集证据可能更便宜；对于快速可逆选择，过度评审本身也是成本。流程与风险相称。

### 十三、复查决定而不是祭拜文档

复查触发器包括指标越界、流量/数据增长、供应商价格或条款、法规、团队能力、依赖停止维护和新候选成熟。定期日期只是一种兜底。监测要能映射到原 driver。

复查结果可以保持、调整、替代或废弃，创建新 ADR 连接历史。比较实际结果与预测，校准团队估算。决策正确但执行失败，与原假设错误要分开分析。

ADR 索引按领域、状态和关系可搜索。过期文档明确标记，不删除历史；入口指向当前有效决定。

### 十四、用反例检验决策机制

尝试推翻每个高风险假设：性能方案在冷缓存和故障下如何，身份方案遇到跨租户如何，组件平台在 Vue/React 与读屏下如何，供应商退出怎样导出。只验证目标方案正常路径会形成确认偏误。

证据还必须带有适用窗口。一次容量测试只证明当时的代码、数据规模、运行拓扑和负载模型；供应商报价只在对应地区、合同与日期下成立；团队能力评估也会随人员和工具变化。ADR 应为关键证据记录采集日期、环境、版本、样本与复验触发条件。复查时若前提已经变化，就重新验证或降低结论置信度，不能继续引用一张过期截图。这样做不是追求永远正确，而是让团队知道当前决定究竟依赖哪些仍然有效的事实。

让独立评审者从 ADR 找到原始约束与实验并重跑关键证据。若无法回答“在什么条件下这项决定应被推翻”，说明退出边界不清。若候选没有现状或真实替代，说明比较不成立。

可参考 [Microsoft 的 ADR 指南](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record) 与 [Google 工程评审实践](https://google.github.io/eng-practices/review/) 了解记录和评审方法。模板只是起点，项目证据、责任与复查才决定质量。

### 十五、区分 RFC、ADR、设计说明与运行手册

RFC 用于在决定前探索问题、候选和反馈；ADR 在收敛后记录一个显著决定及后果；设计说明把决定细化为组件、接口、数据和失败处理；运行手册说明生产如何观测和恢复。它们可以相互链接，但不能用一份文档承担所有生命周期。

RFC 结束时明确 accepted、rejected 或 superseded，避免草案被当现行标准。ADR 指向最终证据和后续实现，设计变化若推翻原 driver 则回到新决策。运行中的事实反过来更新复查，而不是悄悄改写旧记录。

文档入口维护当前状态和 owner，历史可搜索。新成员先能找到“现在遵循什么”，再按需理解过去，避免在数十份互相冲突的方案中猜。

### 十六、评审过程本身也需要服务级别

定义何种风险需要哪些 reviewer、预读多久、何时给反馈、何时由 owner 收敛。无限等待会让团队绕过架构评审，过度快速则让关键角色来不及发现问题。紧急决定使用缩短流程，但保留风险、批准和补审期限。

追踪从提案到决定的 lead time、因缺上下文往返次数、决定后重大返工和未按期复查，而不是文档数量。慢可能因为方案风险高，也可能因为责任不清，要用具体阻塞分析。

建立小、中、大三档评审路径，给团队明确预期。模板字段允许“不适用并说明”，避免为了完整填充无意义内容。

### 十七、发现证据冲突时不求平均

性能原型、用户研究、安全评估和运维经验可能指向不同候选。先检查它们是否使用同一场景、版本和分母，再判断冲突来自测量误差、样本差异或真实质量权衡。不能把两个不兼容结论简单取平均。

真实权衡交给 driver 优先级与有权责任人；测量冲突设计区分实验；无法及时解决则降低范围、选择可逆步骤并设置停止条件。记录为何采用某证据、为何暂不采用另一证据，让未来新信息可重开决定。

评审结束前由非作者复述问题、决定、最大代价和推翻条件。若复述与作者理解不同，先修正文档再进入执行，避免团队带着不同合同开工。

学完后，你应能主持一次从问题、driver、候选、证据到决定的评审，保留反对意见和未知，把结果写成追加式 ADR，并给出迁移、回滚与复查条件。好的架构文档不会阻止未来改变，而是让未来改变知道自己在推翻什么、为什么。

# 让下一位工程师看懂这次技术决定

## ARCH-02 技术方案、ADR 与架构评审

两支团队都要维护订单表单。有人提议统一框架，有人建议只统一组件合同，还有人认为先修好发布流程就够了。会议最后说“先试试第二个”，两个月后大家却分别理解成试验、正式标准和迁移命令。

这不是少写了一份长文档，而是没有把问题、证据和决定分清。本篇围绕这次虚构的组件协作决策，说明如何提出真实候选、处理异议、记录 ADR，并让实现和未来复查使用同一份事实。读完应能解释当前决定为什么成立，以及什么新证据足以重新打开讨论。

### 学习前先确认

- 直接前置：[ARCH-01 质量属性、约束与架构权衡](../chinese-guides/arch-01-quality-attributes-constraints-tradeoffs.md#arch-01)。先把“更快、更稳定”改写成有环境与度量的质量场景。

### 一、把问题写成允许出现不同答案的句子

“需要把所有页面迁到框架 B”已经包含答案。先描述现象：“同一表单规则在两个应用重复实现，最近三次规则调整有两次出现差异；我们希望减少返工，同时保持现有输入和键盘操作。”这样候选才可能包括修复规则归属、统一合同、统一组件或更换框架。

本篇的次数、工时和阈值都是教学合成数据，不是 Career Atlas 的项目测量。真实提案应链接需求、事故或变更记录，分别写事实、推测与偏好。例如“修改了六个文件”是观察；“因为框架不同才返工”是待验证解释；“我更熟悉 B”是会影响成本的背景。三者不应在正文里悄悄合成因果结论。

问题陈述还要说明影响谁、目前怎样完成任务、成功条件和本次范围。若只改组件合同，可以不重写订单服务；但表单改变后仍需验证原有可访问性，不能把会被本次改动影响的责任列为非目标。范围用于控制工作，不用于藏住后果。

不是每个变量命名都要正式评审。跨团队接口、数据所有权、渲染与部署、难以撤回的供应商选择通常值得记录；局部且容易恢复的实现细节，可以在普通代码评审中说明。记录成本应随影响增加，文档页数不表达风险大小。

### 二、用决策驱动因素区分候选

**决策驱动因素（Decision Driver）**是来自目标或约束、足以改变选择的条件。组件例子的驱动因素可能是规则一致性、核心表单任务、修改周期、迁移窗口和维护责任。“先进”“生态好”还不能直接比较，需要变成当前产品可以观察的要求。

先分硬门槛与比较目标。键盘用户必须能完成提交、不得跨租户读取数据，可以是不可违反的门槛；减少维护工时属于在合格候选之间比较的收益。权重只能帮助比较可接受的代价，不能让性能高分抵消权限失败。相关基础见 [ARCH-01 的候选门槛](../chinese-guides/arch-01-quality-attributes-constraints-tradeoffs.md#六在通过底线的候选中比较成本)。

对每个驱动因素写来源、判断方法和负责解释的人。产品负责人说明哪种返工最影响用户，表单维护者说明当前实现边界，无障碍负责人说明核心操作如何验收。技术决策 owner 负责收敛选择，但不能替其他有法定或组织职责的人擅自接受其边界风险。

至少保留真实的替代。在本例中，A 是维持框架并集中规则修复；B 是共享规则与接口，两个界面各自适配；C 是统一一套界面实现并逐页迁移。三案都需要达到共同门槛。如果 C 在窗口内根本无法完成，就应说明为何不可行，不能为了凑三列假装它是可立即采用的候选。考试中的三案要求也不意味着所有小决定都必须制造三个选项。

### 三、证据矩阵记录比较依据，而不替人投票

**证据矩阵（Evidence Matrix）**把相同驱动因素与各候选的证据放在一起。一个格子可以是实测、估算、推断或未知，但必须让读者看得出差别。下面是合成记录，用来练习推理；数字没有证明任何框架天生更好。

| 同一表单场景 | A：局部治理 | B：合同与适配器 | C：统一实现 |
| --- | --- | --- | --- |
| 键盘操作 | 当前样例通过 | 草稿原型未验证焦点恢复 | 新原型通过，旧入口未验证 |
| 修改一条规则 | 估算 2～4 小时 | 一次原型 1.5 小时 | 一次原型 1 小时 |
| 迁移成本 | 估算 1～2 天 | 估算 4～8 天 | 估算 4～8 周 |
| 运行与升级 owner | 已明确 | 两适配器的共同责任待定 | 新运行栈责任待确认 |

不能把 C 的“一小时”与 A 的估算直接当成长期效率差距。先确认任务是否相同、是否包含评审与发布、实现者熟悉度、投入时间及原型质量。若 B 缺焦点验证，最有价值的下一步可能是半天的小实验，而不是继续争论生态排名。

证据应绑定场景、版本、采集日期、原始结果与适用范围。下面完整离线程序演示“通过但版本过期”为什么仍不能作为当前批准依据。保存为 `decision-evidence.mjs`，用 Node.js 22 执行 `node decision-evidence.mjs`；输入与时间均为合成数据，无外部请求。

```js example=arch02-evidence
const current = { scenario: 'order-form-v2', build: 'candidate-b-r4' };
const required = ['keyboard', 'tenant-isolation'];
function readiness(records) {
  const matching = records.filter(row => row.scenario === current.scenario
    && row.build === current.build);
  if (matching.some(row => required.includes(row.check) && row.result === 'fail')) {
    return '停止：当前门槛失败';
  }
  const missing = required.filter(check => !matching.some(row =>
    row.check === check && row.result === 'pass'));
  return missing.length ? `补证据：${missing.join('、')}` : '可进入人工决策';
}
const records = [
  { ...current, check: 'keyboard', result: 'pass', build: 'candidate-b-r3' },
  { ...current, check: 'tenant-isolation', result: 'pass' },
];
console.log(readiness(records)); // => 补证据：keyboard
records.push({ ...current, check: 'keyboard', result: 'pass' });
console.log(readiness(records)); // => 可进入人工决策
records.push({ ...current, check: 'keyboard', result: 'fail' });
console.log(readiness(records)); // => 停止：当前门槛失败
```

旧构建的键盘结果没有被删除，只是不适用于新构建。当前版本又出现失败时，程序不会用另一条通过把它平均掉；需要调查两份证据的样本和环境，或明确哪份已被新的证据替代。真实系统还要校验证据来源与状态，这个函数不证明记录内容真实。

输出“可进入人工决策”也不等于正式批准。程序只检查两项教学门槛，不能替负责人判断迁移成本、团队能力和未决事项。结构化记录帮助发现缺口，不应伪装成万能架构评分器。

### 四、异议要变成场景、行动与决定边界

**异议记录（Dissent Record）**保留不同意见、依据、影响范围、回应与未解决状态。例如“原型关闭弹窗后焦点落到页面顶端，键盘用户需重新导航；扩大试点前必须验证返回位置”，比“我不认可这个组件平台”更容易处理。

先判断分歧属于事实、价值排序还是权限边界。事实冲突需要可区分的实验；成本与期限冲突需要承担后果的人取舍；组织规定的硬门槛失败不能由多数投票消除。若无障碍负责人报告可复现的阻断，技术 owner 应暂停相关范围并安排修复或替代，而不是只在纪要末尾写“已知风险”。

对于软目标的不确定性，可以选择更小、可恢复的试点。记录谁接受剩余风险、限制哪些用户或功能、何时停止、缺什么证据。不要把同意试点写成同意全面推广，也不要要求反对者独自完成无限调查才能被听见。

一次有效的评审可以按这样的顺序进行：会前阅读问题和矩阵；会上先确认共同条件，集中讨论高影响未知；最后决定继续试验、接受、拒绝或延后，并给下一步负责人和日期。角色按风险邀请，避免所有人每次都参会。响应期限可以由团队约定，例如两个工作日内说明是否需要更多输入，不能把无人回应解释为批准。

意见不必完全一致，但结论要能被其他人准确复述。可请非作者说明“选择了什么、适用范围、最大代价、何时重开”。若复述不同，先修正记录。向非技术受众可以减少实现细节，不能删掉同一决定中的重要风险。

### 五、一份 ADR 只回答一个显著决定

**架构决策记录（Architecture Decision Record）**简称 ADR，保存决定发生时的上下文、候选、选择和后果。它帮助后来的维护者知道系统为何成为现在这样。RFC 用于征求意见和探索，设计说明落实组件与接口，运行手册讲如何观测和恢复；四者互相链接，不应把一份巨型草案同时当成全部文件。

下面是一份完整的教学记录，可保存为 `adr-001-form-contract.md` 阅读和修改，不需要运行工具。状态和编号是示例团队约定，不是统一协议。所有人名、日期后的检查结果及工时均为虚构；它演示记录范围，不代表本站发起了真实迁移。

> **ADR-001：先共享订单规则合同，再保留两套界面适配**
>
> 状态：接受有限试点；日期：2026-10-08；决策 owner：组件负责人林宁。
>
> 问题：两个应用重复维护订单规则，合成基线中的三次变更出现两次差异。
>
> 范围：一个内部订单编辑切片；暂不改变订单写入服务与身份来源。
>
> 候选：A 局部治理，B 合同加适配器，C 统一界面实现；三案比较见本节前的合成矩阵。
>
> 决定：采用 B 进行限期原型试验；尚未批准生产扩大或组织统一框架。
>
> 理由：有机会集中规则，同时保持当前两支团队的交付路径；最大未知是焦点恢复与共同维护成本。
>
> 后果：短期多维护一个合同和两套适配器；修改合同需要兼容检查。
>
> 异议：无障碍评审要求补焦点证据；运维要求明确失败归属。两项在扩大前仍是阻断条件。
>
> 下一步：林宁安排候选原型，周澄独立验证键盘任务；试验后共同比较完整变更时间。
>
> 停止：发生输入丢失、越权或无法恢复旧入口即暂停；不以截止日期替代门槛。
>
> 复查：两周后，或任何硬门槛失败时提前复查；若维护收益无法确认，保留 A 并归档试验。
>
> 退出：原型与临时开关删除后关闭试点；正式采用需要后续 ADR 和真实证据。

这份记录接受的是“限定试验”，因此允许关键未知尚待验证。若状态改为“正式扩大”，同样的未知就需要相应证据，不能只修改一个状态词。正式项目还应为证据和任务提供真实链接；教学记录没有伪造不存在的报告地址。

一份包含渲染、身份、数据所有权和迁移方式的大方案，可以由 RFC 总览，再拆成多份 ADR。拆分依据是独立决定，不是为了增加文档数量。几个决定相互依赖时，应明确哪个成立后另一个才可执行。

### 六、让记录状态与当前规则一致

提案可能经历 proposed、accepted、rejected、superseded 等状态，但名称及审批者由组织约定。draft 不应被新成员误当成现行标准，rejected 也值得保留，因为它解释了同一条件下为什么没有采用某案。

已经接受的记录应保留历史内容。后续事实推翻决定时，建立新 ADR，指明它替代哪一份；索引或状态元数据可以追加“已被 ADR-009 替代”，不要把旧理由悄悄改成今天的理由。错别字修正可按团队规范注明，但实质性选择变化必须能追溯。

当前入口要让读者先找到有效决定，再顺着关系看历史。仅将所有文件按创建日期堆在目录里，很容易出现新旧记录互相冲突。索引应包含主题、状态、owner 和替代关系；不需要因此建设另一套复杂平台，仓库文档和正常评审通常已经足够。

更换 owner 时同步更新维护入口与未决任务，历史批准者仍按当时事实保留。某人离职不会自动让旧决定失效，但可能让它依赖的维护能力改变，触发新的评估。

### 七、把选择落实到安全的中间状态

方案不能只描述最终架构。例子中，两套界面如何使用合同、旧消费者怎样读取新错误码、哪个模块拥有草稿、取消后谁停止请求，都决定了迁移中间态能否运行。每一步应产生可用增量或可判断的证据，并有停止点。

在设计说明中把 ADR 转成具体边界：接口版本、数据 owner、发布单元、质量预算、支持期限和旧路径删除条件。运行手册再明确回退路由、恢复制品、处理缓存与在途动作的方法。回滚代码无法撤销已经确认的订单或发出的通知，需要另外的幂等、对账和补偿方案。

这也是为什么迁移成本必须进入候选比较。B 可能免于一次性框架重写，却需要双运行和兼容层；若这个中间态长期没有 owner，收益可能被额外维护吃掉。详细的写入权威与恢复机制见 [ARCH-03](../chinese-guides/arch-03-progressive-migration-strangler-compatibility.md#五写迁移先确定谁有权确认结果)。

验证按风险选择。只改一条局部规则，不必重复整个系统业务测试；改变输入所有权或身份合同，则要让这些风险进入原型。原型源码也不自动成为生产代码，正式接入前仍需补齐依赖、错误、资源释放与维护责任。

### 八、复查的是假设与结果，不是文档是否写完

复查触发器来自驱动因素：规则变更频率增加、维护时间未降低、支持期结束、团队能力变化、供应商条件改变，或核心场景出现失败。固定日期只是防止遗忘的兜底。若前提没有变化且证据仍有效，不需要机械重复整套评审。

复查时先比较预测与实际，再判断是选择假设错误、实现没有遵守决定，还是运行环境改变。三者对应不同动作：重选方案、修执行或更新约束。不能因为实施不完整，就立即把整个技术方向归为失败；也不能因为投入已经很多，就坚持被证据推翻的目标。

评审过程本身也有成本。观察从提出问题到给出可行动决定的等待、缺上下文导致的往返、重大返工与过期未决项。文件数量或全票通过不能证明流程有效。紧急决定可以缩短讨论，但需要明确范围、责任和事后复查时间，不能让“紧急”成为永久绕过。

向业务说明时，可以说“我们先用一个切片验证是否减少规则返工，成本上限是多少，什么时候停止”；向工程团队补充合同和恢复细节。两份表达的事实应相同。委派与跨团队推进怎样让决定真正发生，见 [LEAD-01](../chinese-guides/lead-01-technical-roadmap-delegation-influence.md#四委派时把结果权限和停止条件一起交出去)。

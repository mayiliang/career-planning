# 调试知识点讲义

## DEBUG-01 系统化调试、证据与因果定位

调试不是快速猜中某一行，而是用最小成本缩小原因范围，并让修复在相同机制再次出现时仍然有效。经验丰富的工程师也会猜错；差别在于他们把观察、假设、实验和结论分开，主动寻找能推翻自己判断的证据，而不是不断改代码直到现象暂时消失。

### 学习前先确认

本讲不要求其他站内前置。JavaScript 异步、浏览器网络和 Git 工具会作为例子出现，但正文会解释调试所需的概念；需要深入某个机制时再沿相关知识点学习，不必预先读完一套工具说明。

### 一、先把现象写成可比较事实

“页面有问题”“有时很慢”不能直接指导实验。高质量现象描述至少包含：精确输入、环境、预期、实际、第一次出现时间、发生比例、影响范围和可观察证据。

例如“搜索错乱”可改为：在同一账号连续输入 `a` 和 `ab`，第二个响应先返回时，界面随后被第一个响应覆盖；10 次约出现 3 次，生产版本发生、本地慢速模拟可复现。这样的描述已经提示需要记录请求身份和提交顺序，但仍没有把“竞态”写成既定根因。

**复现（reproduction）**不是重复点击直到偶然看到，而是一组别人能按相同条件执行的步骤。若不能稳定复现，就先统计发生条件和差异，不要用一次成功或失败宣判修复有效。

### 二、最小复现保留因果所需条件

**最小可复现用例（minimal reproducible example）**要移除与现象无关的页面、请求和数据，同时保留触发问题的时序、状态与环境。最小并不等于代码最短；删掉真实缓存层后竞态消失，说明缓存可能是必要条件，不能为了好看继续删。

缩小范围可沿输入、时间、组件、网络、版本和账号逐维进行。每次只改变一个维度，并记录现象是否随之变化。把生产数据复制到本地前必须脱敏和最小化；无法复制时，用结构相同的合成数据重建机制。

### 三、建立系统模型再列假设

先画出输入经过哪些边界到达可见结果：事件处理器、状态更新、请求层、缓存、服务端、存储、构建制品。故障可能发生在任何边，也可能是多个正确局部组合后的错误顺序。

假设应可证伪。例如：

- 请求 A 晚于 B 完成且缺少最新身份守卫；
- 页面加载了旧 HTML 引用的新旧混合 chunk；
- Source Map 与实际执行制品不配套；
- 接口返回正确，但渲染用到了旧闭包状态。

“异步有问题”“缓存玄学”不是合格假设。每项都应写出：若为真预计观察到什么，看到什么会推翻它，成本最低的区分实验是什么。

### 四、用信息增益安排实验顺序

优先做能同时排除最多候选、风险最低且不会破坏现场的检查。版本和资源散列可以先把“代码不一致”与“同制品运行错误”分开；受控 HIT/MISS 对照可以判断缓存是否影响正文；请求时间线可以区分发送、响应和 UI 提交。

不要同时升级依赖、清缓存和重写状态逻辑。多个变量一起变化时，现象消失也无法知道哪个动作有效，副作用还可能掩盖真正原因。生产故障需要先安全缓解时，也应把缓解与根因结论分开记录。

### 五、观察工具本身会改变系统

暂停断点会冻结主线程，可能让超时、竞态和连接行为发生变化。这类加入观察后消失或改变的故障常称**观察者效应缺陷（Heisenbug）**。应根据问题选择低干扰工具：高频异步顺序适合 logpoint 或结构化日志；未知 DOM 修改者适合 DOM 变化断点；吞掉的异常适合捕获/未捕获异常暂停。

条件断点表达式和日志点也会执行代码，不能调用有副作用的函数。录制性能、网络限速和覆盖率同样可能增加开销，所以要保存“未开启工具”和“开启工具”的对照，并避免把工具造成的时序当产品事实。

### 六、调用栈只是当前路径

同步调用栈显示如何到达暂停位置，最顶帧是错误被观察的位置，不保证是根因。异步栈可把 Promise、timer、事件与调度来源关联，帮助回答“谁启动了这项工作”。

查看作用域时区分局部变量、闭包捕获、模块状态和全局状态。两个回调可能分别捕获旧值，也可能共同读取一个后来变化的对象。直接在控制台改值可以作为实验，但不能把现象消失写成修复证据。

页面、iframe、Worker 和 Service Worker 具有不同执行上下文。日志来自哪个全局、请求由哪个上下文发起、断点是否设在真实执行脚本，都要明确。错误上下文中看到的同名变量没有证明力。

### 七、网络问题要分发送、传输、响应和消费

网络面板应记录 URL、方法、开始与完成时间、initiator、状态、重定向、缓存来源、响应头和请求身份。200 只表示协议层得到成功响应，不表示业务数据正确，也不表示 UI 使用了该响应。

`X-Cache: HIT` 只说明某层报告命中，不能单独证明缓存错误。需要知道是浏览器缓存、Service Worker、CDN 还是服务端缓存，cache key 是否包含必要维度，HIT 与受控 revalidate/MISS 的正文散列是否不同。

`networkidle` 也不是通用“页面完成”定义：长轮询、埋点和流式连接可能一直存在。调试和测试都应等待与业务目标对应的信号，例如特定响应、可访问状态或 DOM 内容。

### 八、存储与缓存有不同生命周期

Cookie、Local Storage、Session Storage、IndexedDB、Cache Storage 和 Service Worker 注册各自有作用域与生命周期。清空全部数据只能证明某个持久状态参与了问题，不能定位哪一层或为什么。

使用窄对照：只换账号、不换版本；只禁用 Service Worker、不删 IndexedDB；只修改缓存 key 对应输入。记录前后值和来源。涉及身份或业务数据时，只采集必要字段并脱敏，调试便利不能越过隐私与授权边界。

### 九、Source Map 必须与执行制品配对

**源代码映射（source map）**把生成代码位置映射回编写源码。浏览器执行的仍是部署后的生成代码；本地最新源码或另一次构建的 map 即使文件名相同，也可能指向错误行。

可靠流程是记录 release、脚本 URL、内容散列和生成位置，再取得同一构建产物及 map，验证 manifest 或构建 ID，最后检查映射语句、局部变量和调用语义是否一致。Pretty Print 只是格式化生成代码，不是恢复原始源码。

生产 map 可能包含源码和内部路径，应按安全策略私有上传、控制访问和保留期。映射正确只证明“异常位置对应这段源码”，仍需证据说明它为何收到错误输入或为何在错误时机执行。

### 十、日志要描述状态转换而不是堆文本

结构化日志可记录时间、release、route、requestId、sequence、phase、duration、status 和 errorCode。对竞态，`start → resolve → commit/drop` 比三行“进入函数”更有信息量。

**关联 ID（correlation ID）**让浏览器、网关和服务端记录同一事务；trace 把多个 span 组成端到端时间线。采样会影响可见性，低频严重错误需单独保留策略。所有日志在采集前去除令牌、Cookie、完整查询词和不必要的个人数据，不能把脱敏推迟到导出之后。

### 十一、性能问题先确定口径

“页面慢”可能来自网络等待、主线程长任务、布局抖动、内存压力或过多渲染。先定义测量起止点、设备、数据量、缓存状态和统计量。平均值可能掩盖尾部问题，开发机器结果也不能代表用户现场。

Performance trace 用于时间和线程归因，内存快照用于对象保留，框架 Profiler 用于组件更新；三者回答不同问题。看到函数耗时高还要判断它是否位于关键路径、调用次数和输入规模，不能只优化火焰图中最宽的一块。

### 十二、版本定位需要确定性判定

`git blame` 说明一行最后由哪个提交修改，可用于寻找上下文，不证明该作者或提交造成故障。移动代码、共享依赖和更早数据变更都可能是根因。

`git bisect` 在已知 good 与 bad 之间二分，前提是每个提交都有确定性判定。测试若十次中随机失败一次，二分会给出看似精确的错误提交。先固定依赖、数据、时序和环境；无法构建的提交应按工具约定跳过；完成后恢复原工作状态。

二分找到 first bad commit 后仍要阅读变化、证明机制并建立回归测试。时间相关不自动等于因果相关。

### 十三、最小修复关闭已证明的机制

修复应针对证据支持的因果边：旧请求覆盖新请求，就在提交状态前检查请求身份，并让取消作为资源优化；资源版本错配，就修 manifest、缓存 key 和原子发布；错误 map 则修制品关联和错误平台配置。

不要顺便重写整个请求层或升级框架。过大修改会引入新变量，使“修复有效”难以归因。若架构债务确实需要后续治理，单独记录范围、风险和验证，不与紧急最小修复混在一起。

### 十四、回归验证覆盖机制边界

回归测试要让旧实现稳定失败、新实现稳定通过。竞态需覆盖 A 慢 B 快、A 快 B 慢、取消未生效和组件卸载；缓存需覆盖旧入口与新 chunk、HIT/MISS 和回退；布局需覆盖长文本、缩放和目标视口。

除自动测试外，还要在修复实际运行环境检查版本、资源和监控。一次手工刷新成功不足以关闭问题。记录观察窗口和仍未排除的风险，使后续异常能判断是复发还是新机制。

### 十五、生产缓解、根因分析和长期改进是三层工作

生产影响扩大时，可以先回滚、关闭开关、限流或降级，目标是恢复用户任务。缓解成功不证明根因，也不保证数据完整。保留时间线、版本、日志和必要现场后，再进行假设实验。

根因分析解释直接触发与系统条件；长期改进可能包括检测、隔离、发布和恢复能力。把“操作失误”当终点会遗漏为什么单次动作能产生大范围影响、为何门禁未拦截、为何恢复困难。

### 十六、形成可复核调试记录

一份有效记录包括：现象与环境、复现率、系统模型、假设矩阵、实验变量、原始证据、排除项、最小修复、回归结果和观察窗口。事实与推断分栏，失败实验也保留，因为它们缩小了范围。

记录不是为了展示工具截图，而是让另一位工程师能复查结论，并在相似问题发生时重用方法。无法说明证据如何推翻其他候选时，结论仍应标为暂定。

### 进阶：用因果图而不是单一“根因”

复杂故障可以画有向因果图：发布改变资源映射，旧 HTML 缓存继续引用被删除 chunk，错误恢复又无限刷新。每条边写证据和反事实——若保留旧 chunk，是否仍失败；若恢复不循环，用户影响是否降低。这样能区分触发、放大和恢复缺口。

多个条件可能共同充分，任一单独存在都不出错。把最后修改的一行称为唯一根因会遗漏其他防线。修复优先选择能切断高风险路径且容易验证的边，并为其他促成因素安排独立改进。

### 进阶：低频故障需要统计而不是故事

故障率从 1% 降到一次未见，不能凭少量运行宣布消失。根据基线频率选择样本量和观察窗口，保存每次输入与环境。A/B 或分批发布要确认分组没有设备、区域和版本偏差。

日志缺失也不是“没有发生”。采样、客户端关闭、上报失败和隐私过滤都会影响可见性。用独立信号交叉验证，如用户任务、服务日志和客户端错误。先评估观测管线的覆盖，再根据零事件下结论。

对于无法稳定复现的问题，可增加低风险诊断字段和保护性守卫，但必须设置数据最小化、成本与移除条件。永久保留海量调试日志会形成隐私和性能债务。

### 进阶：并发与内存故障需要观察时间关系

并发缺陷取决于事件顺序，而不只是输入值。先标出任务创建、队列、锁、取消、超时和状态提交的时间点，再通过可控制调度、延迟注入或虚拟时钟放大窗口。随意加入日志可能改变调度，让竞态暂时消失；因此日志只证明带有该观察条件的运行。稳定回归应控制顺序或断言不变量，而不是依赖“多跑几百次偶尔复现”。

内存持续增长也要区分活对象、可回收对象和回收时机。比较相同用户任务完成并触发可比回收后的 heap snapshot，沿 retaining path 找到谁仍持有对象。单次快照很大可能只是缓存或尚未回收；只看进程总内存又会混入原生缓冲、图形资源和分配器策略。修复后用重复任务的稳态曲线与功能结果共同验证。

浏览器主线程卡顿可能来自长任务、布局、脚本或垃圾回收。性能录制给出相关时间片，源代码与输入实验才建立因果。将问题按 CPU、等待、内存和渲染资源分类，可以避免看到某个醒目的函数就过早优化。

### 学完后应能说明

你应能把模糊故障改写成可复现现象，建立可证伪假设并按信息增益安排单变量实验；能区分调用栈、网络、缓存、Source Map、日志和 Git 历史各自能证明什么；也能将生产缓解、根因结论和长期改进分开，用最小修复与稳定回归关闭已经证明的机制。

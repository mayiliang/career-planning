# 持续交付与发布恢复知识点讲义

## ENG-06 CI/CD、制品晋级、发布与回滚

把代码送到生产环境不是“运行一条部署命令”，而是一条把不确定变更逐步转化为可验证制品、受控流量和可恢复业务状态的证据链。高级工程师关心的不只是流水线是否绿色，还要回答：被测试的究竟是不是后来上线的那一份制品，配置和数据库能否与新旧版本共存，出现异常时怎样停止扩大影响，以及回滚命令执行后用户任务是否真的恢复。本讲从提交进入流水线开始，逐层建立交付、晋级、发布和恢复模型。

### 一、CI 与 CD 解决的是不同阶段的不确定性

**持续集成（Continuous Integration）**要求开发者频繁把小变更合入共同主线，并由自动化检查尽早发现组合问题。它的关键不是服务器会跑测试，而是每次判断都绑定明确提交、依赖锁文件、工具版本和输入数据；同一个提交重跑时应能解释差异。格式、静态类型、单元、集成、契约、安全、许可证、内容结构和生产构建可以组成分层门禁，但每一层都要说明阻止的风险，不能为了“检查多”而堆叠重复任务。

**持续交付（Continuous Delivery）**把已经验证的候选版本保持在可部署状态，并让它经过测试、预发布、生产等环境。持续部署则进一步允许满足策略后自动进入生产。两者的差异在最后一次生产变更是否还需要人工决策，而不是有没有流水线。高风险系统可以持续交付但保留审批；低风险内容服务也可以自动发布，只要停止条件和回滚路径足够可靠。

流水线绿色只说明预先定义的检查通过。它不能证明需求正确、生产数据分布一致、第三方稳定或用户任务没有退化。因此交付系统必须保存“已证明什么”和“尚未证明什么”，发布后的现场观察才是证据链下一段。

### 二、一次流水线运行必须有不可混淆的身份

触发源至少区分拉取请求、主线提交、标签、手动重跑和定时任务。拉取请求中的代码可能来自不可信分支，不能直接获得生产密钥；主线构建要记录提交 SHA、仓库状态、依赖锁文件摘要、构建器版本和工作流版本。只显示人类可读版本号而不保存不可变身份，会让同名版本在不同时间指向不同内容。

并发策略要与业务含义一致。一个分支的新提交可以取消尚未完成的旧验证，但已经开始写入共享测试环境或执行数据库步骤的任务不能被粗暴终止。重复运行应产生新的运行 ID，同时继续指向同一输入提交；如果结果不同，必须能追到外部依赖、缓存或非确定测试，而不能覆盖第一次证据。

流水线自身也是生产代码。工作流、第三方 action、runner 镜像和脚本需要评审与版本固定；来自 PR 的脚本不应在带密钥的高权限上下文执行。日志要记录必要证据，但命令回显、异常对象和构建产物不得泄露 token、证书或用户数据。

### 三、构建一次，晋级同一份制品

**不可变制品（Immutable Artifact）**是内容一旦发布就不再原地改写、能用摘要唯一识别的交付单元。前端制品不只是 JS 和 CSS，还包括入口 HTML、静态图片、运行时配置模式、知识库内容、数据库迁移说明和版本清单。容器镜像、压缩包或静态目录都可以是制品，关键是它们有明确边界和可验证摘要。

正确路径是一次构建产生候选制品，后续环境只晋级同一摘要。若测试环境和生产环境分别重新构建，依赖下载、环境变量、时间戳和工具版本都可能改变输出，测试证明就不再指向生产对象。环境差异应通过运行时配置、部署参数或独立密钥注入表达，而不是修改已经验证的代码包。

制品仓库负责存放、读取权限、保留期限和版本状态。晋级记录包含源提交、制品摘要、生成流水线、通过的门禁和目标环境。撤回一个有问题的版本应改变其可部署状态，而不是删除全部证据；保留最近稳定版本和它引用的旧静态资源，才能支持真正回滚。

### 四、缓存和复现不能污染正确性

依赖缓存、构建缓存和测试缓存可以缩短反馈，但缓存键必须包含真正影响结果的输入，例如锁文件、运行时版本、平台、构建配置和源码摘要。缓存缺项会把另一个分支或旧工具链的输出伪装成本次结果。读取缓存后仍要验证关键元数据；缓存不可用时应回到较慢但正确的路径。

可复现构建不是要求每个字节在任何机器上天然相同，而是先消除不必要的时间、随机数、绝对路径和未锁定下载，再解释仍存在的平台差异。对于必须包含生成时间的清单，可以把时间从主体摘要中分离。最重要的是能从提交和构建定义重建等价制品，并验证公开结果与记录一致。

不要缓存权限或秘密。凭据只在需要它的阶段短时注入，构建前端包时尤其要确认所谓环境变量不会被打进浏览器可下载代码。产物扫描应搜索密钥模式、源码映射、调试端点和不应公开的配置，并把发现当成发布阻断而非日志警告。

### 五、质量门禁要按风险分层

快速门禁应在开发者等待期间返回高价值反馈，例如格式、类型、关键单元与契约测试；较慢的浏览器、性能、安全和完整构建可以并行或在合入后继续。层次设计的目标是尽早失败并保留最终覆盖，不是把所有工作串成漫长单线。相同检查只运行一次并复用结果，避免不同脚本给出矛盾口径。

必需检查名称要稳定，分支保护引用的是语义清晰的汇总结果。矩阵任务中某个平台失败时，汇总门禁必须失败；跳过任务要明确是“不适用”还是“未执行”。允许临时豁免时，需要风险说明、批准人、期限和补偿检查，不能让管理员绕过成为日常路径。

测试不稳定性不能通过无限重试掩盖。重试可以帮助收集证据，但首次失败仍要计入质量数据；隔离测试要有负责人和恢复期限。发布前至少确认关键用户路径、接口兼容、迁移兼容、制品完整性和部署配置语法，具体阈值由系统风险决定。

### 六、环境和密钥是受控边界

开发、测试、预发布和生产环境表达不同信任与数据边界。环境保护可以限制允许发布的分支、要求审批、设置等待窗口，并在批准后才暴露该环境的密钥。审批者看到的应是制品摘要、变更范围、已通过证据、未解决风险和发布计划，而不是只有一个绿色按钮。

密钥应使用短期凭据或工作负载身份，范围只覆盖当前环境和所需动作。自托管 runner 与宿主共享网络和磁盘时不能假设每次任务完全隔离；来自不可信代码的作业不应接触生产网络。密钥轮换、撤回和使用审计与部署流程同等重要。

配置变化也必须版本化。运行时开关、反向代理规则、知识库和策略文件可能不改应用源码，却会改变用户行为。它们要经过审阅、验证和制品标识，不能在生产控制台悄悄修改后没有可追踪记录。

### 七、数据库与配置要跨版本兼容

应用回滚常被数据库不可逆变化阻断。expand/contract 先增加新旧版本都能接受的字段或结构，应用过渡期同时读写兼容格式，确认旧版本不再运行后才删除旧结构。重命名字段通常要经历新增、双写/回填、切读、停止旧写和清理，而不是一次迁移直接替换。

数据回填与结构迁移要分离。大批量回填限速、可暂停、可重复，并记录进度；请求路径不能假设所有历史行已经完成。新版本在灰度期必须能处理未回填数据，旧版本也不能被新写入立刻破坏。若变更确实不可逆，发布计划应采用向前修复而非虚假的一键回滚承诺。

配置模式同样需要兼容窗口。新增枚举、权限动作或事件字段时，旧消费者应忽略未知字段或进入安全失败；删除值之前先观察使用量。发布评审应明确代码回退、配置回退和数据恢复是三种不同动作。

### 八、功能开关把发布与启用分开

功能开关允许代码已部署但只对内部、少量租户或指定用户启用。开关评估必须有稳定主体、默认值和服务端权限边界；前端隐藏不能代替授权。开关服务不可用时选择安全默认，不能随机把半成品开放给全部用户。

开关适合控制曝光和快速停用，不适合长期维护两套产品。每个开关记录 owner、创建原因、目标人群、过期日期和删除条件。旧分支持续存在会增加测试组合、缓存键和数据库兼容负担，最后比发布本身更危险。

启用开关也属于一次变更，要绑定指标和审计。若新代码已经部署但开关未开，技术健康只能证明暗置代码未破坏公共路径；真正业务验证要在小流量启用后进行。

### 九、选择发布策略要看可隔离程度

蓝绿发布准备两套可切换环境，适合快速切换与清晰回退，但数据库、队列和外部副作用仍可能共享，不能因为流量入口可切换就假设所有状态可逆。滚动发布逐实例替换，资源利用率好，但新旧版本会共存，接口和数据必须兼容。

**金丝雀发布（Canary Release）**先让一小部分真实流量进入新版本，再按阶段扩大。分流单位应稳定，例如租户或用户，而不是让同一会话随机跨版本。低流量阶段要有足够样本和关键业务探针；只看总体错误率可能掩盖特定设备、地区或高价值任务的失败。

发布策略不是成熟度等级。小型静态站点可能用原子切换和旧资源保留就足够；状态复杂系统需要分阶段、影子验证或双写观察。选择依据是故障隔离、状态兼容、观测能力、恢复时间和成本，不是追逐流行术语。

### 十、停止条件必须在发布前定义

每个阶段先写进入条件、观察窗口、扩大条件和停止条件。技术信号包括错误率、延迟、资源、崩溃和依赖失败；用户任务信号包括登录、搜索、下单、保存和导出；数据完整性信号包括重复写、漏写、队列积压和对账差异。三类信号互补，不能用 CPU 正常替代业务正确。

阈值要考虑基线和样本。一次偶发错误不一定停止，低流量下零错误也不证明安全；可以使用绝对严重事件、相对基线退化和最小样本共同判断。发布控制器自动停止扩大流量，人负责处理证据模糊或业务影响重大的决策。

监控失明本身应是停止条件。若关键指标延迟、日志关联丢失或告警管道异常，继续扩大等于在没有仪表的情况下加速。发布事件应标注版本和阶段，让观察系统能比较发布前后而不是凭记忆猜测。

### 十一、前端发布有入口与旧 chunk 的特殊风险

入口 HTML 经常变化并引用带内容哈希的 JS/CSS。哈希资源可以长期不可变缓存，HTML 应短缓存或重新验证。若切换新 HTML 后立即删除上一版资源，仍打开旧标签页或缓存旧入口的用户会请求不存在的 chunk，出现白屏或动态导入失败。

安全做法是保留兼容窗口内的旧资源，记录每版资源清单，并对 chunk 加载失败提供受控刷新。刷新前要保护未提交输入，不能无限重载。Service Worker、CDN、浏览器 HTTP 缓存和应用数据缓存是不同层，回滚时分别确认它们指向的版本。

运行时配置应有版本并与前端兼容。新入口读取旧配置、新代码访问旧 API、旧标签页调用新 API 都应在发布矩阵中验证。只在无缓存新浏览器打开首页，无法证明真实用户路径安全。

### 十二、回滚是决策与恢复过程

回滚计划先定义可回退对象、目标版本、负责人、授权、最大决策时间和无法回退的数据步骤。触发后先冻结继续发布和开关扩大，保存现场证据，再执行最小恢复动作。对于配置错误可能只需回退配置；对于局部功能可关闭开关；对于代码回归才切换制品。

命令返回成功不等于恢复。要重新检查健康、核心用户任务、错误和延迟、数据对账、缓存命中、队列和第三方调用，并在约定观察窗内保持稳定。若用户已经产生错误数据，还需要补偿、通知或人工处理，不能用旧版本覆盖事实。

回滚失败时需要向前修复路线。准备可访问的上一稳定制品、独立控制面和最小运维手册，避免事故中依赖已经损坏的应用页面。定期演练才会暴露凭据过期、脚本漂移、旧资源被清理和负责人缺席。

### 十三、审计与复盘形成下一次门禁

一次发布记录源提交、制品摘要、环境、配置版本、迁移、批准、分流阶段、指标决策、事件和最终状态。审计不是为了增加表格，而是让团队能回答“谁基于什么证据把哪一份内容交给了哪些用户”。记录应自动产生，敏感值只保存引用或摘要。

事故复盘把时间线、影响、检测、控制失效、恢复和后续行动连接起来，不以寻找个人替代系统修复。若根因是缺少旧 chunk，行动项可能是保留策略和回归测试；若告警太晚，就修改 SLO 和发布观察窗。行动项必须有 owner、期限和可验证完成条件。

发布频率、失败率、恢复时间和变更前置时间可以反映交付系统，但指标会被团队规模和变更类型影响。不要为提高频率拆出无意义发布，也不要把回滚次数隐藏成热修复。指标用于发现系统瓶颈，不用于惩罚个人。

### 十四、验证一条交付链是否成立

选择一个真实小变更，从 PR 开始保存每个不可变身份：提交、依赖、构建、制品摘要、环境配置和发布事件。证明生产使用的是测试过的摘要；模拟门禁失败、环境审批拒绝、金丝雀指标越界、旧 HTML 请求旧 chunk、配置不兼容和数据库回退受阻。每个故障都要有停止、恢复和复验记录。

至少做一次从稳定版本发布、逐步扩大、触发回滚到业务恢复的演练。比较发布前后核心任务和数据完整性，而不只看进程健康。再尝试重建同一提交，核对制品内容和来源差异；对无法复现部分写出原因与控制。

学完后，你应能设计一条把可信提交变成不可变制品、把同一制品逐环境晋级的流水线；能够为配置和数据库建立兼容窗口，为蓝绿、滚动或金丝雀发布定义停止条件；并能解释为什么部署成功、回滚成功和用户任务恢复是三种不同证据。继续查证可参考 [GitHub Actions 工作流机制](https://docs.github.com/zh/actions/about-github-actions/understanding-github-actions)、[GitHub 部署环境](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments)与[不可变发布](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)。

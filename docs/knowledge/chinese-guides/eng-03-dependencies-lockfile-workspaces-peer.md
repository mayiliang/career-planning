# 工程化知识点讲义

## ENG-03 依赖解析、Lockfile、Workspace 与 Peer Dependency

`package.json` 写的是版本意图，实际安装结果还取决于注册表元数据、解析器规则、平台、锁文件和包管理器版本。项目在一台机器上能运行，不等于任何干净环境都能得到同一依赖图。要治理依赖，必须区分声明、解析、物理布局和运行时身份，而不是在冲突时删除 lockfile 重新抽签。

### 学习前先确认

本讲不要求其他站内前置。能阅读 JSON 和运行包管理命令即可开始；语义化版本、依赖类型、锁文件、工作空间和对等依赖都会从机制解释。

### 一、manifest 表达直接依赖意图

包清单通常包含名称、版本、入口、exports、脚本、运行约束和依赖声明。依赖字段表达责任：

- `dependencies` 是包运行时需要并随消费者安装的依赖；
- `devDependencies` 支撑开发、构建和测试；
- `peerDependencies` 要求宿主提供兼容实例；
- `optionalDependencies` 安装失败时允许包按合同降级。

字段不是“线上会不会看到这个文件”的精确分类。前端构建会把 devDependency 中的构建工具用于生成产物，却不会把工具本身送到浏览器；一个依赖若被源码 import，即使错误写进 devDependencies，本地完整安装可能正常，生产只装 dependencies 时则失败。

### 二、语义化版本描述兼容承诺

**语义化版本（semantic versioning）**用 MAJOR.MINOR.PATCH 表达公共 API 兼容意图：破坏性变化提升 major，兼容功能提升 minor，兼容修复提升 patch。它是发布者合同，不是数学证明；实际包可能错误发布破坏性 patch。

范围如 `^1.2.3`、`~1.2.3` 和精确版本允许解析器选择不同集合。范围越宽越能取得修复，也增加未来解析变化；范围越窄越稳定，却可能阻塞安全更新。应用和库的策略不同：应用依靠 lockfile 固定部署，库还要给消费者留合理兼容区间。

预发布版本、0.x 兼容和多入口 exports 需要按当前规范与包实际合同判断，不能把所有 `^` 都理解成“随便升级”。

### 三、lockfile 固定的是解析结果

**锁文件（lockfile）**记录直接与传递依赖的具体版本、来源、完整性及依赖关系。它把“版本范围 + 注册表当时信息 + 解析规则”得到的结果保存下来，使后续冻结安装不再重新选择。

锁文件应进入版本控制并随 manifest 一起评审。手工编辑容易破坏关联；删除它会允许整棵图重新解析，可能同时升级许多间接包，让原问题更难定位。正确修复是明确更新目标依赖、查看 lockfile diff，并在干净环境验证。

锁文件格式与包管理器版本也属于输入。项目可通过 `packageManager` 和运行时版本文件声明工具，CI 使用 frozen lockfile 拒绝清单与锁文件不一致。

### 四、可重复安装不只看 lockfile

相同 lockfile 仍可能受注册表可用性、被撤回制品、平台可选包、安装脚本、原生编译和环境变量影响。真正的可重复性需要：锁定工具版本、受控注册表、完整性校验、干净安装、可审计缓存和受限脚本。

缓存命中只说明本地已有内容，不证明内容可信或安装逻辑可重复。CI 应能在没有 `node_modules` 的环境完成冻结安装；离线模式只有在所需制品都已可信缓存时才成立。

包的安装脚本可以执行任意代码，是供应链边界。应按项目策略批准构建脚本、最小化权限，并在更新时审查新增脚本和来源。

### 五、依赖图与 node_modules 布局不是一回事

逻辑图说明包依赖谁；物理布局说明文件放在哪里、通过硬链接或符号链接怎样可见。不同包管理器采用扁平、嵌套或内容寻址存储，但代码不应依赖偶然提升。

**幽灵依赖（phantom dependency）**指包没有声明某依赖，却因上层提升而暂时可以 import。换包管理器、更新图或独立发布后就会失败。严格布局能早期暴露这种边界错误；修复是由实际使用者声明依赖，而不是继续提高 hoist 范围。

重复物理副本也不一定代表逻辑错误。不同 peer 组合可能需要不同实例；但 React 等单例型运行时重复会破坏 context 或 Hook 身份，需要追查解析路径。

### 六、peer dependency 描述宿主协作

**对等依赖（peer dependency）**常用于插件、组件库和框架适配器：包需要与宿主使用同一份框架实例，并声明可兼容的版本范围。它不是“安装失败就随便忽略”的警告。

例如组件库应把 React 声明为 peer，并在开发依赖中提供一份用于自身测试。若把 React 打入库产物，消费者可能同时加载两份。peer 范围过窄会阻塞兼容版本，过宽则承诺未验证行为。

处理冲突时找出每个消费者要求的范围、是否真需要共享单例、哪个包尚未支持目标版本。可以升级、降级、替换或分隔运行环境；强行忽略只把解析问题推迟到运行时。

### 七、optional peer 与能力降级要显式

插件可能只在启用某功能时需要一个 peer，可通过元数据标记为 optional。optional 不等于调用时可以静默崩溃；运行时应检测能力并给出明确错误或降级路径。

平台相关 optionalDependency 也要验证目标平台未安装时的行为。日志应区分“按设计未启用”和“安装失败导致能力缺失”，否则运维会把正常降级当故障或反过来。

### 八、workspace 建立仓库内包边界

**工作空间（workspace）**把多个包置于一个仓库和依赖图中。根目录定义成员，包仍各有自己的 manifest、入口和责任。`workspace:` 协议可以要求依赖必须解析到本地成员，避免名称相同却意外从注册表下载。

```json
{
  "dependencies": {
    "@atlas/shared": "workspace:*"
  }
}
```

workspace 不等于所有包可以互相引用源码。公共包仍应通过 exports 暴露合同，并单独构建、测试或发布。循环 workspace 依赖会破坏拓扑执行与初始化，应通过职责拆分解决，而不是关闭警告。

### 九、monorepo 的任务图来自包依赖图

递归构建应先构建依赖再构建消费者；测试可按受影响包运行，但需要包含传递消费者。仅根据修改文件目录选择测试会漏掉公共类型、配置和生成物的影响。

任务缓存的 key 至少考虑源码、配置、锁文件、工具版本和相关环境。缓存命中后仍应能说明复用了哪个输入集合；若隐含环境未入 key，旧成功结果会伪装成当前验证。

并行执行要隔离端口、数据库和临时目录。包依赖无环不代表运行资源不会竞争。

### 十、override 是受治理的临时或全局决定

override/resolution 可以强制传递依赖使用某版本，常用于紧急漏洞、错误版本或统一实例。它改变整棵图，不应只因为安装警告难看而添加。

每条 override 记录原因、受影响路径、兼容验证、owner 和删除条件。上游修复后主动移除并重新解析。强制一个不满足调用方范围的版本可能编译成功却运行失败，必须覆盖实际调用路径。

patch 工具对第三方包的本地补丁也需要来源、diff、测试和升级策略，不能成为永久隐藏 fork。

### 十一、依赖更新按风险而非数字大小处理

major 变更通常风险高，但一个被广泛执行的 patch、安装脚本变化或构建器更新也可能高风险。更新前看发布说明、来源、维护状态、脚本、许可和调用范围；更新后检查 lockfile 实际改变的包数和重复实例。

批量更新能提高效率，却会降低归因。底层框架、构建工具和类型包之间有关联时可作为一组；互不相关的更新分开，便于审查和回退。

自动依赖 PR 应有频率、分组、测试和人工批准策略，不能让“机器人创建了 PR”冒充供应链治理。

### 十二、发布 workspace 包需要显式版本合同

内部包发布时，`workspace:` 范围通常转换为普通版本范围。要决定哪些包独立版本、哪些联动发布、变更如何生成 changelog，以及消费者何时升级。

发布前从打包结果检查包含文件、exports、类型、许可证和依赖字段，再在临时消费者安装 tarball。仓库内源码别名会绕过真正打包边界，不能作为发布证明。

版本号只描述兼容承诺；弃用周期、迁移说明和双版本支持窗口同样影响消费者。

### 十三、供应链证据连接来源与产物

完整性哈希验证下载内容未在传输中变化，但不能证明发布者可信或包没有恶意逻辑。可结合注册表来源限制、签名/证明、制品清单、漏洞扫描和最小权限安装。

扫描结果要区分可达风险、开发工具与生产运行，并记录处置决定。无漏洞报告不表示安全，过期高危也不能因“只是传递依赖”自动忽略。

敏感仓库应控制令牌范围、禁止在日志输出 registry credential，并防止依赖混淆：私有名称、scope、注册表映射和发布权限要一致。

### 十四、排查安装差异从图开始

当本地通过、CI 失败时，依次比较 Node 与包管理器版本、lockfile 状态、平台、注册表、安装脚本、环境变量和缓存。使用依赖树或 why 命令追踪某版本为何出现，不要只在 `node_modules` 手工删除目录。

peer 冲突关注宿主组合；幽灵依赖关注声明所有权；重复版本关注范围与解析条件；完整性失败关注来源与缓存。给不同失败贴对标签，修复才能落在正确层。

### 十五、建立依赖治理的可复核基线

项目应能在干净目录冻结安装，输出一致依赖图，运行构建和关键测试。记录工具版本、锁文件散列、批准脚本、registry 和 override。定期从零验证，避免长期只在热缓存与遗留 `node_modules` 上工作。

依赖变更的完成条件包括清单与 lockfile 一致、消费者运行、重复单例检查、供应链扫描和可回退性，而不是安装命令退出 0。

### 进阶：平台条件和 exports 影响同一包的身份

包可以通过 `exports` 为 import/require、browser/node 和开发/生产暴露不同入口。解析器根据条件选择，深路径若未导出就不属于公共合同。直接引用 `pkg/dist/internal.js` 可能在一次发布后失效，也绕过类型和平台分支。

不同工具若条件集合不一致，测试和构建会加载不同实现。记录 resolver、conditions 和目标平台，并在库发布时验证每个承诺入口。条件导出两边必须语义兼容，不能让 browser 版本悄悄省略安全校验。

### 进阶：Catalog 与集中版本不取消包责任

workspace 可集中常用版本范围，减少重复更新，但每个包仍应声明自己真正使用的依赖。集中 catalog 是维护工具，不是让所有包隐式获得根依赖。更新共享版本时沿消费者图运行测试，并检查 peer 组合。

内部包边界还需 lint 或发布测试防止源码越界。TypeScript path alias 可以让编译通过，却不保证 Node、测试和打包器解析相同，也不自动生成正确发布依赖。

### 进阶：许可与维护状态属于依赖风险

依赖选择不仅看漏洞。检查许可证是否适合分发，维护者与发布频率是否健康，包是否被弃用，是否有可替代标准 API。小功能引入大型无人维护依赖会增加长期升级和安全成本。

自动生成 SBOM 可列出组件和版本，但需要关联实际制品与环境。开发依赖、可选平台包和打包进浏览器的代码风险不同，处置时说明可达性与用途，不能只按扫描总数排名。

### 进阶：安装脚本与包来源属于执行边界

依赖安装可能执行 lifecycle script，获得当前用户与 CI 的文件、网络和环境权限。审查新依赖时不仅看它导出的 API，也看安装脚本、预编译二进制的下载来源和失败回退。生产流水线采用最小权限、批准脚本清单与隔离缓存；禁止脚本后还要验证所需原生制品是否以可信方式提供。

同名同版本包通常被假定不可变，但 registry、镜像和代理仍是供应链参与者。锁文件的完整性字段验证取得的归档是否符合解析记录，却不说明维护者账号未被接管。固定 registry、保存来源与签名/证明，并对高风险更新查看发布差异和维护权变化。

依赖删除也要验证不可达。清单中移除直接项后，它可能仍由传递路径存在，或其代码已复制进仓库和制品。使用依赖图解释剩余路径，重新构建并检查产物。治理的目标是控制实际执行内容，而不是让 `package.json` 看起来简短。

### 学完后应能说明

你应能区分 manifest 版本意图、lockfile 解析结果、逻辑依赖图和物理布局，解释 peer dependency 为什么由宿主提供，以及 workspace 协议如何保护本地包边界。面对幽灵依赖、peer 冲突、override 或缓存差异时，应能定位责任并在干净环境证明可重复安装，而不是删除锁文件碰运气。

# 需求与交付证据知识点讲义

## BIZ-08 需求到验收的可追踪性

大型项目失败往往不是“没人写需求”或“没人写测试”，而是需求、业务规则、设计决定、实现、测试和上线证据各自存在，却无法回答彼此保护了什么。需求改变后，团队靠记忆搜索文件；测试失败时，不知道违反哪条用户价值；上线后又无法证明真正验收了关键约束。本讲把这些制品连接成可双向反查、能随变更维护的证据网络。

### 学习前先确认

- 直接前置：[BIZ-01 业务对象、关系与统一语言](../chinese-guides/biz-01-domain-objects-relations-ubiquitous-language.md#biz-01)。本讲用统一业务语言、对象身份、规则和边界拆解需求。
- 直接前置：[ENG-05 ESLint、类型检查、测试与 CI 质量门禁](../chinese-guides/eng-05-quality-gates-lint-types-tests-ci.md#eng-05)。本讲假定你理解检查应对应风险并产生稳定、可行动的证据。

### 一、可追踪不是堆链接，而是记录关系

**可追踪性（Traceability）**让一个业务目标可以沿着规则、设计、实现、验证和运行证据前进，也能从代码、测试、缺陷和事故反向找到原始理由。链接只有在说明关系类型时才有意义：implements、verifies、decides、supersedes、affected-by 与 evidence-for 表达的责任不同。

Issue、PR、Wiki、代码注释和测试报告只是载体。把所有 URL 放进一页不等于有追踪链；真正有用的链能回答“这段校验实现哪条规则”“这条规则有哪些正反例”“若删除该接口会影响哪些用户任务”“本次发布用什么证据证明仍满足”。

可追踪不是为了让文档无限增长，而是降低变更与审计时重新考古的成本。风险低的展示文案可以轻量记录，高风险授权、资金、隐私和兼容规则需要更完整证据。

### 二、先把模糊需求拆成目标、规则与约束

“做一个好用的审批功能”无法直接验收。先写用户/业务目标，再拆成可判断的业务规则、数据定义、权限、异常和非功能约束。例如：导师可在提交后七天内批准；申请人与批准人不得相同；超期进入 EXPIRED；直接 API 调用也必须拒绝。

规则使用稳定 ID 和统一术语。ID 不承载会频繁变化的标题或文件路径，例如 `APR-DELEGATE-01` 比 `page3-button` 稳定。正文记录来源、owner、状态、版本/生效时间和替代关系。删除规则时标记 superseded，而不是抹去历史。

需求来源可能互相冲突：法规、合同、产品说明、客服口径和旧实现不能默认同权。记录冲突与裁决人，必要时用 ADR 保存备选、决定和后果。尚未决定的事项显式列为 open question，不能由开发者默默猜成规则。

### 三、验收标准必须可观察且包含反例

**验收标准（Acceptance Criteria）**描述在给定前提和输入下，可观察到什么结果。它不是实现步骤，也不应写成“代码写完、测试通过”。好的标准同时覆盖正例、边界和拒绝：谁在何状态做什么，服务端事实与用户反馈分别如何变化。

例：“已提交六天、当前导师且非申请人时，批准返回新版本并显示批准人；第八天或申请人自行批准时，服务端不改变对象，返回稳定拒绝码，页面保留上下文并说明原因。”这里的时间、身份、状态和不变事实都可验证。

非功能要求也要操作化。“快”需要设备/网络条件、指标和阈值；“安全”要列威胁与控制；“易用”要写代表任务、目标用户、完成标准和错误容忍。阈值来源、测量窗口和例外责任一起记录。

### 四、正向追踪保证每条承诺都有落点

**正向追踪（Forward Traceability）**从目标和规则走到设计决定、接口/界面、实现、测试、验收与监控。它发现“写在需求里却无人实现/验证”的遗漏，也帮助规划最小范围。

一条链可以是：目标 `APR-GOAL-1` → 规则 `APR-EXPIRE-7D` → 状态转移/ADR → API guard 与页面状态 → 单元/集成/端到端测试 → 发布运行 ID → 过期拒绝指标。每个节点只链接自己真正承担的部分，避免一份巨大测试被宣称覆盖全部需求。

实现可能有多个落点：前端提供早期提示，服务端保护最终边界，后台任务处理超时，监控发现异常。追踪矩阵要显示各自责任，而不是只链接一个页面文件。

### 五、反向追踪解释代码和证据为何存在

**反向追踪（Backward Traceability）**从实现、测试、缺陷或运行告警返回需求来源。它发现没有业务理由的功能、过时分支和“为了测试而测试”的制品。代码评审者看到一个特殊 412 处理，应能找到对应并发规则与验收标准。

每个关键测试名称或元数据引用规则 ID；实现中的复杂分支可引用 ADR/规则，而不是复制全文。构建制品记录提交、规则基线、测试运行和环境。事故报告把影响回连到被违反的规则，修复再链接新增/强化的测试。

反向链也支持删除。若一个功能没有活跃目标、调用者、规则或运行使用证据，团队可以评估退役；但“没有链接”也可能是追踪缺失，先与 owner 核实，不能自动删除。

### 六、追踪矩阵要小而可维护

矩阵列可包含规则 ID、来源、owner、状态、设计、实现、正例、反例、测试、验收证据、监控和最近复核。不是每格都填 URL；可用仓库路径、测试 ID、仪表盘查询或制品摘要。关键是引用稳定且可自动检查存在性。

按能力或业务流程拆矩阵，不要把整个系统放入一张几千列的表。跨域规则通过 ID 关联。生成视图可以汇总，但事实来源应尽量靠近负责团队和代码，避免复制后漂移。

设置完成定义：高风险规则必须有 owner、至少一个拒绝例、服务端执行点、自动化测试与当前发布证据；低风险规则可能只需实现和人工验收。要求与风险成比例。

### 七、设计决定记录“为什么这样做”

需求说明想达到的结果，ADR 记录在约束下选择了哪种方案、有哪些备选和后果。它避免后来只看到实现，误以为偶然代码结构就是不可改变的业务规则。

ADR 引用相关规则 ID，设计变化产生新 ADR 并标记 supersedes。不要覆写旧决定到看不出历史；也不要把每个变量名都写 ADR。适合记录边界、协议、数据所有权、迁移、权限和不可逆平台选择。

验证方案同样是设计的一部分：哪层使用模型/性质测试，哪层用契约或端到端，哪些无法自动化需要人工观察。若规则无法以任何方式观察，先重写规则，而不是制造一个无意义的“passed”。

### 八、变更从规则 diff 推导影响范围

需求变化时先比较规则：新增、修改、废止，还是仅澄清文案。再沿正向链收集受影响设计、接口、数据、页面、测试、监控、文档与迁移。沿反向链检查是否还有旧实现和消费者依赖被遗漏。

例如“拒绝原因从始终必填改为合规命中时必填”影响状态守卫、DTO Schema、表单条件、旧草稿迁移、测试数据、报表和审计；不影响七天过期，但仍需回归相邻路径。影响清单明确 changed/verified/not-applicable 及理由。

不要因为改动看起来是一个字段就跳过兼容分析。旧客户端、历史数据、导出、消息消费者和缓存可能仍依赖旧语义。发布计划记录 expand—migrate—contract 阶段和删除条件。

### 九、AI 参与不能替代来源与责任

AI 可以根据规则生成候选测试、搜索引用和汇总 diff，但模型输出不是需求来源，也不能自行决定歧义。提示上下文引用稳定规则与文件，生成结果由 owner 审阅，并保存实际执行证据而非对话中的“看起来正确”。

防止 AI 为满足现有测试反向修改规则：规则变化必须有来源和批准；测试失败先判断实现错、测试错还是规则已变。自动生成大量链接也会制造噪音，只有能够验证存在且关系真实的链接进入矩阵。

敏感需求与日志遵守最小披露，外部工具不应获得不必要的客户数据。AI 代码的来源与安全验证由专门工程知识处理，本讲只规定它必须落入同一追踪链。

### 十、测试覆盖率不等于需求覆盖率

代码覆盖率说明哪些结构被执行，不说明断言是否对应业务承诺。需求覆盖需要从规则到测试的映射，以及测试预言真正检查结果。一个没有断言的高覆盖用例不能成为验收证据。

每条关键规则至少有允许与拒绝观察；边界规则使用冻结时间、身份、版本和明确输入，避免依赖当前日期或共享环境。跨层规则可由多个测试共同证明，但要说明各自保护什么，不能把同一用例重复计数成多份独立证据。

测试报告带运行 ID、提交、环境、时间和结果。截图可以辅助说明，单独截图没有输入、版本和可复跑步骤时证据很弱。生产验证要与发布制品摘要关联。

### 十一、验收是对合同的独立判定

开发自测、测试环境验证、产品验收和生产确认回答不同问题。验收人根据事先定义标准和真实风险判定，不应只听实现者演示快乐路径。未通过项记录规则 ID、实际结果、证据和处理决定。

验收环境与生产有差异时显式写出，如身份提供方、数据规模、浏览器或网络。无法在测试环境证明的生产约束，需要灰度、开关、监控和回滚条件。验收通过也不意味着未来发布永久有效，每次相关变更都生成新证据。

人工验收适合文案理解、复杂视觉和业务判断；可重复的权限、时间、版本和错误语义应自动化。两者组合，而不是把所有责任交给一次手工点击。

### 十二、非功能需求要进入相同链条

性能规则关联用户路径、设备/网络、数据规模、指标、预算与性能测试；可访问性规则关联语义/键盘实现、自动检查和人工读屏；安全规则关联威胁、服务端控制、攻击反例和审计；隐私规则关联数据字段、目的、留存和删除验证。

“页面三秒内打开”要说明冷/热缓存、哪个分位、从何时到何时。“支持键盘”要列完整任务与焦点恢复。“日志可观测”要列关联字段和告警响应。模糊形容词不能直接成为通过标准。

非功能约束常跨多个能力，使用共享规则 ID 并明确 owner。某个页面通过并不证明整个系统符合，采样范围和例外必须记录。

### 十三、生产证据让追踪链闭环

上线后用监控、日志、审计和用户任务结果确认真实行为。规则 ID 可以进入结构化日志/指标标签，但注意标签基数；高价值拒绝记录策略版本和原因。发布记录连接制品摘要、迁移、开关、测试运行与观测窗口。

如果生产告警发现七天规则异常，从告警反向定位规则、实现与最近变更；修复后增加反例测试并更新证据。事故不是追踪链之外的临时事件，而是对合同缺口的反馈。

证据有保留和访问控制。客户数据、密钥和敏感日志不能因“审计”无限保留；保存必要摘要、脱敏样本与受控查询，记录谁访问和何时删除。

### 十四、自动化检查连接完整性而非伪造内容

CI 可以检查关键规则 ID 格式、引用目标存在、废止规则没有新实现引用、测试报告包含提交与运行 ID、知识库链接可打开。它无法自动判断一条测试是否真的验证规则，需要评审与抽样运行。

建立 orphan 报告：没有测试的活跃高风险规则、没有规则的复杂实现、没有 owner 的失败验收、过期 ADR 和长期未复核的证据。报告先作为诊断，规则清晰后再决定门禁，避免误报使团队习惯忽略。

可视化图适合影响分析，但底层仍是可版本控制的稳定关系。工具迁移时可导出标准字段，不让追踪信息锁死在无人维护的平台。

### 十五、常见反例与适用边界

- 需求只有长篇描述，没有稳定规则 ID、owner 和反例。
- PR 写“完成需求”，却无法从测试或代码回到具体规则。
- 用代码覆盖率、截图数量或链接数量冒充需求覆盖。
- 需求改变只改页面，未分析 API、历史数据、消费者和监控。
- 为迎合现有实现悄悄改验收标准，历史决定被覆盖。
- 追踪矩阵过度细化到每行代码，维护成本超过风险价值。

小型探索原型可以用轻量目标清单和决定日志，不必建设重型 ALM；一旦能力涉及多人、跨系统、监管、高风险或长期维护，就应提升链条完整度。

### 十六、学完后应能说明

你应能把模糊需求拆成稳定规则和可观察验收标准，建立正向与反向关系；用矩阵与 ADR 记录责任和决定；从规则 diff 推导实现、数据、测试与发布影响；区分代码覆盖和需求覆盖；并让生产告警、事故与下一次修复重新回到同一证据链。

继续查证可参考 [NASA Systems Engineering Handbook 的需求管理章节](https://www.nasa.gov/reference/systems-engineering-handbook/) 与 [W3C 可访问性评估方法](https://www.w3.org/WAI/test-evaluate/)。

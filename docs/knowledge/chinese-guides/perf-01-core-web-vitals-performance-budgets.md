# Web 体验指标与性能预算知识点讲义

## PERF-01 Core Web Vitals 与性能预算

性能工程不是把页面分数调绿，而是用稳定口径判断用户何时看到主要内容、操作何时得到下一帧反馈、页面是否发生意外移动，并把这些体验约束转化为设计、开发和发布决策。Core Web Vitals 提供共同语言，却不会自动说明根因，也不能覆盖所有业务任务。本讲从字段分布、指标生命周期和归因入手，建立实验室复现、性能预算、回归门禁和持续改进的方法。

### 学习前先确认

- 直接前置：[OBS-01 前端可观测性、SLO、告警与隐私边界](../chinese-guides/obs-01-frontend-observability-slo-alerting-privacy.md#obs-01)。字段性能依赖路由、版本、采样、分位数和用户任务口径，必须先理解这些观测边界。

### 一、Core Web Vitals 是体验信号而非总分

当前核心指标由 LCP、INP 和 CLS 组成，分别观察主要内容出现、交互响应与视觉稳定。它们覆盖加载、响应和稳定三个重要维度，但不直接衡量业务成功、可访问性、内容正确、动画流畅、崩溃和长期内存。因此“全部通过”只说明这三个维度达到给定阈值，不能推出产品体验全面优秀。

每个指标都依赖一次页面访问的生命周期。硬导航与 SPA 软导航的边界、页面进入后台、往返缓存恢复和预渲染激活会改变数据归属。采集实现必须记录导航类型和口径版本，不能把不同生命周期的数字混在同一趋势里。

指标值是观测结果，不是根因。LCP 慢可能来自服务器、资源发现、下载、解码或渲染；INP 慢可能来自输入延迟、处理或呈现；CLS 可能来自无尺寸资源、字体或动态插入。优化前先把值分解到可验证阶段。

### 二、LCP 观察最大主要内容何时呈现

**最大内容绘制（Largest Contentful Paint）**记录视口中合格的最大内容元素完成绘制的时刻，常见候选是主图、海报、文本块或背景图。候选可能在加载过程中变化，因此不能看到第一条 LCP 条目就立即上报最终值；页面隐藏或用户交互等生命周期边界需要正确收尾。

LCP 可分为首字节之前、资源加载延迟、资源加载时长和元素渲染延迟。服务器慢影响第一段；图片藏在客户端脚本后才发现会增加加载延迟；图片过大增加下载；主线程阻塞或样式未就绪使下载完成后仍无法绘制。四段要求不同修复，盲目给所有图片 preload 可能争抢带宽反而更慢。

首先确认候选元素确实代表主要内容。骨架屏或占位图很早绘制不等于真实内容可用；把重要文本延迟到客户端请求会推后发现。图片提供正确尺寸、现代格式和高优先级之前，要先保证它能从初始 HTML 或服务器输出中及时发现。

### 三、INP 衡量交互直到下一帧的整体延迟

**交互到下一次绘制（Interaction to Next Paint）**观察用户点击、触摸或键盘交互，从最早事件开始到浏览器呈现下一帧的延迟，并在一次访问中关注接近最慢的代表性交互。它不是单个事件处理器用时，也不等于所有动画持续时间。

一次交互可分为输入延迟、处理时长和呈现延迟。主线程在执行别的任务时，事件先等待；多个监听器和同步计算占用处理阶段；样式、布局、绘制和下一帧等待进入呈现阶段。只优化事件回调而忽略此前长任务或随后布局，可能看不到改善。

反馈要尽早可见，但不能用虚假成功掩盖工作。可以在状态更新后把重计算切片、延后非关键任务或交给 Worker；也要减少 DOM 数量和同步布局。不要把所有工作简单包进 `setTimeout`，那只是改变队列位置，仍可能阻塞下一次交互。

### 四、CLS 关注非用户预期的布局移动

**累积布局偏移（Cumulative Layout Shift）**累计一次访问中非用户近期输入导致的可见元素位移，通过影响范围与移动距离估计干扰。页面长并不自动产生高 CLS，正常滚动也不计入；问题是用户准备点击或阅读时内容突然移动。

图片、广告、嵌入内容和异步组件应预留尺寸或稳定容器。字体切换可改变字形尺寸，需要合适回退字体和加载策略。顶部插入横幅会推动全部内容，应在初始布局留位，或使用不会改变文档流的呈现方式。

用户交互后的变化存在短暂排除窗口，但不能滥用。点击“展开”导致预期布局变化通常不算意外；几秒后异步广告挤压内容仍会计入。优化要保留功能和清晰反馈，不能为了数字固定所有高度导致内容裁切。

### 五、字段数据要看分布和样本条件

官方阈值通常以页面或来源的第 75 分位判断：LCP 2.5 秒以内、INP 200 毫秒以内、CLS 0.1 以内属于良好区间。p75 表示至少四分之三访问不超过该值，不是“最慢 25% 的平均”。平均值会被极快或极慢样本拉动，难以表达大多数用户是否达到目标。

分组至少考虑页面类型、设备类别和网络，但每次细分都减少样本。样本不足时显示区间或等待更长窗口，不要用个位数访问判断发布。机器人、内部流量、预渲染和异常生命周期是否包含要写入数据合同。

整体 p75 改善可能掩盖低端设备恶化，因为流量构成改变。比较前后要控制版本、路由和用户群，并同时观察分布与样本量。隐私要求下避免用稳定设备指纹追踪个人，只保留决策需要的粗粒度条件。

### 六、实验室与字段数据组成定位闭环

字段数据回答真实影响在哪里，实验室在固定浏览器、设备、节流、数据和操作下提供可重复诊断。Lighthouse、Performance 面板和自动化脚本各有模型；工具版本和评分权重会变化，所以报告必须记录版本和条件。

一次实验室结果波动很大。冷缓存与热缓存、CPU 背景负载、扩展、服务端状态和页面随机内容都会影响数字。至少多次运行，报告中位数或分布，并保留原始结果。实验室无法自然产生足够多真实交互，INP 往往需要明确脚本或现场数据。

从 RUM 找到退化路由和候选元素，再在实验室重现相同资源、任务和环境；修改后同条件 A/B，最后在小流量字段数据确认。任何环节无法复现都应保留不确定性，不要把相关改动包装成因果结论。

### 七、Lighthouse 分数是加权诊断界面

Lighthouse 性能分数由一组实验室指标按当前版本权重映射而来。工具升级、环境和指标分布都可能改变分数；相同分数也可能由完全不同瓶颈构成。分数适合快速发现回归和交流，不应成为唯一 SLO 或供应商合同。

审计建议提供机会，但不理解全部业务约束。删除第三方脚本可能提升性能却破坏支付；延后主内容会改变测量而伤害用户。每项建议都要回到网络、主线程和布局证据，并在修复后验证功能与关键用户任务。

自动门禁中固定 Lighthouse 版本、设备和网络，保存报告而不是只保存分数。阈值既可以约束核心指标，也可以约束资源体积和请求数；允许合理波动但阻止显著回归。字段目标仍由 RUM 单独判断。

### 八、性能预算把目标放到设计和构建阶段

**性能预算（Performance Budget）**是对体验指标、资源和架构成本预先设置的约束。体验预算可写 p75 LCP、INP、CLS；资源预算可写关键 JS、图片、字体、第三方字节和请求数；过程预算可限制主线程长任务或关键请求链。只有阈值、条件、测量方式、负责人和超标动作完整时，它才是工程合同。

预算应按页面和用户群设置。营销首页、数据后台和编辑器具有不同内容与交互；统一 200KB 预算可能对一种页面过宽、对另一种不现实。先测基线和用户价值，再决定逐步目标，不能用当前很差的数值直接当永久预算。

新功能消费预算需要显式取舍。增加富文本编辑器可能有合理价值，但要说明延迟加载、路由隔离和低端设备影响；第三方标签必须有 owner、用途、加载条件和退出标准。预算超标不能用修改阈值静默解决。

### 九、资源预算与体验预算互相约束

更少 JS 通常降低解析和执行成本，但字节相同的代码可能有不同主线程开销。图片字节影响 LCP，但发现时机和优先级同样重要。资源预算是可在构建时稳定检查的领先指标，体验预算是最终结果，两者不能互相替代。

按初始路由、异步 chunk 和共享依赖拆开统计。压缩后传输大小、未压缩解析大小和源映射属于不同指标；不能只报告 gzip 后数字忽略浏览器执行。重复依赖、错误模块边界和全量 locale 会使用户下载不需要的内容。

第三方资源的代码不在仓库也会进入用户主线程和网络。预算把它们计入，并测量失败、超时和阻塞。把第三方标成“不可控”后排除，只会让报表漂亮而真实体验继续变差。

### 十、诊断 LCP 要沿资源发现链前进

先确认服务器响应和 HTML 到达时间，再看候选资源由 HTML、CSS 还是 JS 发现。初始文档中的 `<img>` 通常比组件挂载后生成 URL 更早；CSS 背景图要等样式表下载解析。跨源资源可能需要 preconnect，真正关键且晚发现的资源才适合 preload。

检查 `srcset`、尺寸和压缩，避免移动设备下载巨大图片。预加载必须与实际请求的 URL、类型、跨源属性一致，否则会重复下载。资源到达后仍慢，查看解码、主线程、隐藏样式和动画延迟。

修复后核对候选没有被意外换成次要大元素，也没有牺牲图片清晰度或布局。字段数据按页面和设备确认，不能仅凭网络瀑布缩短就结束。

### 十一、诊断 INP 要拆开输入、处理与呈现

录制具体慢交互，定位事件前主线程任务、事件监听器、框架更新、样式布局和下一帧。输入延迟高时先减少此前长任务；处理高时优化算法、数据规模和工作分片；呈现高时检查 DOM、样式和同步布局。

交互频率和设备决定方案。一次点击的重计算可用 Worker 或分片，连续输入还需要取消过期工作、合并更新和避免每键全量渲染。虚拟列表降低 DOM，但其测量和焦点管理也可能制造新成本，必须验证结果与可访问性。

不要只看最慢一次调用栈。INP 是访问级指标，需要测试不同交互并观察长尾。修复一个按钮后，路由切换或输入框可能成为新瓶颈；预算应覆盖关键任务而非单个演示路径。

### 十二、诊断 CLS 要保留会话时间线

布局偏移条目带受影响节点和时间，结合截图、网络和 DOM 变化判断来源。首屏图片无尺寸、字体替换、同意横幅、错误提示和无限列表插入是常见原因。按会话窗口聚合时要保留最大窗口，而不是把全部页面时长简单相加。

为异步内容预留的空间应接近实际范围；固定过大空白也伤害体验。使用 `aspect-ratio`、尺寸属性、稳定骨架和内容占位，动态提示尽量出现在已有区域。动画使用 transform 不会触发布局，但仍要尊重减少动态偏好。

测试慢网络、字体失败、广告不同尺寸、错误状态和 200% 文字缩放。只在理想内容下无偏移，不能证明组件在真实输入中稳定。

### 十三、性能门禁要防止误判和指标投机

CI 中运行固定场景，保存原始报告、版本和基线。阈值可以采用硬上限与相对回归结合：超过用户底线立即失败，小幅波动通过多次测量判断。共享 runner 噪声较大时，资源预算和可重复 trace 可以先作为稳定门禁，真实设备实验另行验证。

禁止通过隐藏内容、延后埋点、排除慢用户或改变测量边界让数字变好。优化后检查功能、可访问性、数据正确和第三方任务。若指标改善只是因为用户不再能完成慢操作，那是产品故障。

例外需要 owner、理由、到期和偿还计划。持续报告预算消费趋势，比临近上线才收到红灯更能指导设计。每次工具和阈值更新要用历史样本校准，避免规则变化制造虚假回归。

### 十四、建立持续性能治理

仪表盘按版本、路由、设备和网络显示 LCP、INP、CLS 分布、样本与口径。发布事件叠加在趋势上，预算越界连接负责人和候选归因。定期检查数据采集成本、隐私字段和浏览器支持，旧适配及时删除。

选一个真实页面，先在 RUM 识别最差用户群，再固定实验室条件重现慢首图、长交互和布局移动。分别记录指标阶段、根因证据、最小修复和同条件复测；之后通过小流量确认字段 p75，没有足够样本时明确等待。

学完后，你应能解释三项 Core Web Vitals 的生命周期与限制，区分字段分布、实验室诊断和 Lighthouse 分数；能把指标拆成可验证阶段，设计体验、资源和过程预算，并建立不会牺牲功能或通过改变口径取巧的发布门禁。继续查证可参考 [web.dev Core Web Vitals](https://web.dev/articles/vitals?hl=zh-cn)、[指标阈值说明](https://web.dev/articles/defining-core-web-vitals-thresholds)与 [Chrome Performance 面板](https://developer.chrome.com/docs/devtools/performance/overview)。

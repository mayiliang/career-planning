# 07–09 内容审计中文讲义

本讲义补足 07–09 中没有可靠中文原始资料的概念；每节可脱离外链完成学习。术语以稳定的浏览器、Node.js 和开放规范行为为准；实现或标准版本变化时，应以题目给定版本和对应发布说明复核，不能把版本号本身当作能力证据。

## MEDIA-01

**定义与机制。**播放链路把媒体容器中的音视频轨道解复用、解码，再按时间戳送至渲染或音频设备。MSE 让脚本向 `SourceBuffer` 追加分段；追加队列必须等待 `updateend`，否则会抛错或造成缓冲无序。WebCodecs 是更底层的 `VideoDecoder`/`AudioDecoder` 队列：输入 `Encoded*Chunk`，输出帧；`decodeQueueSize` 上升时暂停取片，帧用完即 `close()`。能力探测只回答“此设备在这些配置下可能平滑、节能播放”，不能保证 DRM 许可、网络或内容可用。EME 仅管理受保护内容的密钥会话，不替代鉴权、授权与审计。

**例子与反例。**点播页可在缓冲低水位拉取 4 秒分片、成功追加后再拉下一片，并根据带宽/丢帧切换清晰度；直播页还要限定目标延迟。反例是同时 `appendBuffer` 两段、将每一帧永久保留在画布、或把“支持 H.264”当作播放一定成功。DRM、自动播放、画中画、字幕与音频描述都有用户代理、权限和可访问性边界，失败时应给出可理解的静态提示或较低码率流。

**验证练习。**输入为一个含两档码率、一个不支持编码配置的 fixture；输出为缓冲/队列状态表和降级选择。断言：追加串行、队列有上限、所有帧释放；模拟许可证失败、网络中断和能力不支持，确认不重试风暴且可恢复到可播放的替代流。

## COMP-01

**定义与机制。**组件契约先定义职责，再定义输入、输出和可组合方式：数据用值或受限对象传入，用户意图用事件传出，内容扩展用插槽/children，外观扩展用有限的语义变体。每一个 prop 必须说明默认值、互斥关系、可访问语义和兼容承诺；组件内部状态不得泄露为调用方必须理解的 DOM 细节。组合优先于不断增加布尔开关，因为组合能让状态和语义保持局部。

**例子与反例。**`Dialog` 可接受 `open`、`onOpenChange`、标题和操作区插槽，并承诺焦点进入、Escape 关闭和焦点归还；触发器若不是按钮，也必须承担等价键盘语义。反例是 `isLarge/isSmall/isPrimary/isDanger` 同时存在，或暴露 `setOverlayZIndex` 让使用方依赖实现。不能只凭视觉截图认定契约正确：读屏顺序、键盘路径、禁用状态和嵌套组件才是边界。

**验证练习。**输入为一页组件 API 草案和三个使用场景；输出为 API 表、互斥规则及可运行示例。检查 happy path、键盘打开/关闭、非法组合被类型或运行时拒绝、升级后旧调用仍按声明工作；记录一个刻意被拒绝的布尔参数，说明为何改为组合。

## DS-01

**定义与机制。**Token 是可发布的设计决策而不是散落的 CSS 值。原始 token 表示色阶、间距等物理值；语义 token 表示 `color.text.default` 等用途；组件 token 只在组件内映射语义 token。主题切换只替换同一语义层的值，构建阶段把 token 编译为 CSS 变量、原生值或 JSON，同时保存来源、版本与弃用信息。对比度、字号和动效还需要针对目标背景和状态验证，不能只看 token 名称。

**例子与反例。**深色主题将 `color.surface`、`color.text.default` 一起替换，按钮读取语义 token 而非写死 `#1677ff`。反例是产品 A 把 `blue-6` 直接写进组件、产品 B 重新定义同名 token，导致主题切换和跨端输出不一致。Token 不应承担布局业务逻辑；无法表达的局部差异应显式成为组件变体。

**验证练习。**输入为浅深两套原始值与三条语义映射；输出为编译后的变量和变更 diff。检查同一组件在两主题不出现未解析变量、关键文字与背景达到题设对比度、删除 token 会在构建时报出所有引用点；将一次破坏性重命名标为 major 或提供别名迁移。

## COMP-03

**定义与机制。**组件发布的证据链是“契约文档—可运行示例—自动测试—版本记录”。文档说明输入、输出、可访问行为和已知限制；示例使用公开 API，避免复制内部实现；交互、视觉与无障碍测试各自覆盖不同风险。版本号按兼容性表达：新增兼容能力为 minor，修复为 patch，删除/改变公开行为为 major 或先弃用；变更日志必须写明影响、迁移和回退方法。

**例子与反例。**把 `onSelect(id)` 改为 `onSelect({id,label})` 即使页面能运行也是公开契约破坏，应保留旧适配层或发布 major，并给迁移例子。反例是只改截图、示例仍调用旧参数，或以“新增组件数量”代替采用价值。多框架封装只要承诺同一交互，就要在每个承诺的运行时留下测试证据。

**验证练习。**输入为上个版本 API、拟发布 diff 和消费者示例；输出为文档页、变更日志条目、兼容性分类和测试结果。检查示例可执行、公开类型和文档一致、键盘和读屏回归通过；故意删除一个 prop，验证发布检查会阻止未标 major 的破坏性变更。

## PLATFORM-01

**定义与机制。**配置化页面把“允许变化的页面数据”写为 schema，把“可信的渲染器与业务动作”留在代码。流程为读取版本化 schema、校验结构、白名单解析组件/字段、计算受限表达式、渲染、收集数据，再用同一或服务端 schema 校验输出。组件注册表只能暴露固定组件和属性；表达式不能取得全局对象、网络能力或任意函数。迁移把旧 schema 显式变换到新版本，并保留可定位的错误路径。

**例子与反例。**订单页 schema 可以声明 `TextInput`、必填规则和“国家为 CN 时显示省份”；渲染器把它映射到已注册组件。反例是 schema 内直接写 JavaScript、把权限判断只放前端、或校验失败仍提交原数据。配置适合可枚举的表单/展示差异，不适合把复杂工作流、付款副作用或未知 UI 当字符串执行。

**验证练习。**输入为有效 schema、未知组件、循环联动和旧版 schema fixture；输出为页面、规范化数据及每个错误的 JSON 路径。检查未知组件拒绝、联动稳定收敛、服务端再次校验、迁移前后语义一致；记录一次沙箱越权尝试被拦截的证据。

## PLATFORM-02

**定义与机制。**微前端是独立交付单元通过宿主协议组合，而不是把多个应用并排加载。先按团队边界、独立发布需求和故障域决定是否拆分；每个子应用声明路由前缀、初始化/卸载、样式隔离、消息 schema、共享依赖版本和降级页。宿主负责装载、超时、错误边界和回滚，子应用在卸载时清除监听器、定时器和挂载节点。通信使用有版本的事件或请求协议，禁止共享任意全局可变状态。

**例子与反例。**宿主在 `/billing/*` 按清单加载账单子应用；版本不兼容时显示静态账单入口并上报。反例是把全站状态对象暴露给所有子应用、共享 React 单例却不锁版本、或把 iframe/模块加载成功误认为业务可用。若团队不能独立部署或协议频繁同步变化，模块化单体通常成本更低。

**验证练习。**输入为两个版本不同的子应用、故障清单和发布清单；输出为装载时序、协议定义、兼容矩阵和回滚记录。检查路由、样式和错误隔离；模拟远程入口超时、共享依赖冲突与子应用崩溃，确认宿主仍可导航且旧版本可恢复。

## PLATFORM-03

**定义与机制。**物料平台把组件从“可发布包”治理为“可发现、可采用、可退出的产品”。登记内容至少有所有者、适用场景、API、质量门禁、版本状态和迁移窗口；目录和示例解决发现，类型/视觉/无障碍/安全检查解决准入，使用遥测和 Issue 分类验证是否真正减少重复实现。采用率必须有分母（目标项目或可替换调用数）与时间窗，不能只报下载量。

**例子与反例。**平台发现三个相同日期选择器后，选定一个物料，提供迁移 codemod，连续两版跟踪替换率与缺陷率。反例是强制接入但不支持例外、废弃包仍被新项目选用、或因“发了 20 个组件”宣布成功。治理不能替代业务负责人：平台要公开升级成本和退出条件。

**验证练习。**输入为物料清单、项目调用样本和 Issue 数据；输出为登记卡、门禁结果、采用率分母/分子及淘汰计划。检查新物料无所有者或无示例时不能发布，模拟一个高下载低实际引用物料不被误判为成功，审阅迁移后重复代码是否下降。

**实施顺序与失败处理。**先为候选物料指定产品所有者和维护 SLA，再把 API、可访问行为、性能预算、支持的运行时以及不支持的场景写进登记卡；随后用可复现的示例和自动门禁发布试用版。试用期同时收集安装、实际引用、迁移失败、工单和绕行实现，按项目/版本/时间窗计算采用率。若迁移成本高于重复实现节省，或维护者无法在承诺窗口修复，平台应暂停推广、公布替代物料和退出日期，而不是用强制升级掩盖失败。验收时随机抽样两个已登记项目：从锁文件和代码引用复算分子，从目标项目名单复算分母；再删除一个声明为废弃的物料入口，确认目录、模板和脚手架均不会再推荐它。

## MOBILE-01

**定义与机制。**跨平台原生前端由 JavaScript/声明式 UI 与平台渲染、原生模块协作；桥接/JSI 类接口把值、调用和回调跨线程传递。每项原生能力都要定义权限申请时机、前后台恢复、深链入口、失败回调和资源释放。发布链路从构建产物、签名、隐私声明、商店审核到崩溃符号和灰度回滚；OTA 只能更新允许热替换的代码和资源，不能绕过原生权限或二进制兼容边界。

**例子与反例。**扫描页在用户点击后请求相机权限，进入后台时暂停预览，返回时重新确认权限和会话；缺少权限时显示设置入口。反例是启动即申请所有权限、把大图逐帧跨桥传递、或把要求原生升级的 API 改动通过 OTA 强推。平台差异必须由能力检测和可见降级处理，而非假定两端完全一致。

**验证练习。**输入为相机、推送、深链三种能力矩阵；输出为生命周期状态图、权限文案、故障回退和发布清单。检查首次拒绝、永久拒绝、冷启动深链、后台恢复和旧二进制打开新配置；通过启动时间、内存、崩溃率和关键操作完成率验证，不只看模拟器。

## NODE-04

**定义与机制。**BFF 的一次请求共享一个绝对截止时间和取消信号：浏览器断开、上游超时或进程停止任一发生，都向尚未完成的下游 I/O 传播取消。输入在边界校验并建立认证/追踪上下文；聚合读取可并发但受并发上限，写入用幂等键和明确重试策略。流式响应必须在 `write()` 返回 `false` 时等待 `drain`；响应提交后只记录/终止流，不能再次写 JSON 错误。诊断事件只补充日志、指标和追踪，不能成为业务正确性的唯一通道。

**例子与反例。**`GET /dashboard` 并发读取账户和消息，800ms 总预算内把剩余时间分给下游；客户取消时两个 fetch 都 abort。反例是每层各自 1 秒导致总耗时失控、对非幂等写入无限重试、或 SIGTERM 后仍接收连接。健康检查必须区分“进程活着”和“可接流量”。

**验证练习。**输入为两个可延迟/失败的下游和一个中断的客户端；输出为带 request id 的响应、时序日志、指标和优雅停机记录。检查取消传播、429/503 的结构化错误、背压、重复写入去重、SIGTERM 后停止接新请求并在上限内退出。

## NODE-03

**定义与机制。**CLI 契约把 argv、环境变量和配置文件解析成已校验的命令对象，并明确优先级；正常机器结果走 stdout，诊断走 stderr，退出码表达成功、用法错误、运行失败或被信号中断。交互模式可询问确认，CI 模式必须由 flag 完全驱动；`--dry-run` 输出将执行的不可逆操作却不改变状态。结构化 JSON 输出与人类输出应有固定 schema/字段，不混入进度条。

**例子与反例。**`atlas import --file a.json --format json --dry-run` 输出计划并返回 0；未知选项返回用法错误且不写文件。反例是把错误日志写 stdout 破坏管道、解析失败仍返回 0、或 Ctrl+C 时直接 `process.exit()` 截断清理。密钥不应出现在 help、日志或 dry-run 输出中。

**验证练习。**输入为有效/无效参数、环境配置和 SIGINT；输出为 stdout、stderr、退出码及文件副作用清单。检查配置优先级、子命令 help、JSON 可解析、dry-run 零副作用、无效参数/取消分别得到可预期退出码与清理证据。

## API-01

**定义与机制。**规范化先解析 YAML/JSON 为保留来源位置的文档树，再识别 OpenAPI 版本与 schema 方言，解析本地/远程 `$ref` 并维护访问栈防循环，最后产出统一的路径、操作、参数、请求体、响应和 schema 中间表示。解析与业务设计分离：缺少 `operationId`、冲突参数或不支持的动态引用要成为带文件路径和指针的诊断，而不是悄悄猜测。示例是样本，不是无条件类型定义；overlay/多文件合并需规定顺序和覆盖规则。

**例子与反例。**输入根文件引用 `models/user.yaml`，规范化输出 `GET /users/{id}` 的参数和 200 schema；若 `User` 间接引用自身，报告循环链而非栈溢出。反例是把 `example: 1` 推断成唯一允许值、把相同路径不同方法覆盖、或允许任意 URL 远程引用造成 SSRF。规范化不负责决定业务字段是否合理。

**验证练习。**输入至少 20 个固定 fixture，含多文件、错误缩进、缺 `operationId`、多 content type、循环和被禁止远程引用；输出为稳定中间表示与定位诊断。检查同一输入字节级稳定、错误精确到文件/路径、diff 区分破坏性与非破坏性变更。

## API-02

**定义与机制。**代码生成以 API-01 的规范化中间表示为唯一输入：先给 schema 建立稳定标识和命名表，再生成类型/服务 AST 或等价结构，处理保留字、同名和循环引用，最后格式化、写入受管目录并 typecheck。确定性要求相同输入得到相同字节；增量更新只覆盖受管文件，手写扩展位于受管目录外或显式保留区。生成器不推断未在 schema 中表达的业务语义。

**例子与反例。**`user-id` 变为 `userId`，若与已有字段冲突则以稳定规则加后缀并在清单记录；删除 schema 字段会产生可审阅 diff。反例是按对象遍历顺序随机输出、直接拼字符串造成转义漏洞、覆盖用户手写服务实现，或 typecheck 失败仍写入“成功”。格式化工具只是最后一步，不能修复错误 AST。

**验证练习。**输入为含保留字、同名、nullable、循环引用及 schema 改动的 fixture；输出为受管 types/service、manifest、diff 和 typecheck 结果。检查重复运行零 diff、手写扩展未变、冲突命名可预测；注入非法标识和不支持 schema 后必须失败且不留下半写文件。

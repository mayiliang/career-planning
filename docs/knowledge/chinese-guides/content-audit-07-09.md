# 07–09 内容审计中文讲义

本讲义补足 07–09 中没有可靠中文原始资料的概念；每节可脱离外链完成学习。术语以稳定的浏览器、Node.js 和开放规范行为为准；实现或标准版本变化时，应以题目给定版本和对应发布说明复核，不能把版本号本身当作能力证据。

## 二轮使用与验收口径

本轮为每个知识点补齐“定义/机制—实现路径—不适用或失败边界—故障注入—证据”的最小闭环。实施前记录浏览器、Node、容器或 SDK 的**实际版本**、设备/网络条件和 feature detection 结果；不把某一版本号、单次运行或单张截图当作通过证据。每个练习至少保留输入 fixture、操作步骤、关键日志或 trace、预期/实际、修复后的同条件复测。外链用于查证 API 细节；本讲义不声称替代厂商发布说明，也不把未在当前环境实测的兼容性写成事实。

## MEDIA-01

**定义与机制。**播放链路把媒体容器中的音视频轨道解复用、解码，再按时间戳送至渲染或音频设备。MSE 让脚本向 `SourceBuffer` 追加分段；追加队列必须等待 `updateend`，否则会抛错或造成缓冲无序。WebCodecs 是更底层的 `VideoDecoder`/`AudioDecoder` 队列：输入 `Encoded*Chunk`，输出帧；`decodeQueueSize` 上升时暂停取片，帧用完即 `close()`。能力探测只回答“此设备在这些配置下可能平滑、节能播放”，不能保证 DRM 许可、网络或内容可用。EME 仅管理受保护内容的密钥会话，不替代鉴权、授权与审计。

**例子与反例。**点播页可在缓冲低水位拉取 4 秒分片、成功追加后再拉下一片，并根据带宽/丢帧切换清晰度；直播页还要限定目标延迟。反例是同时 `appendBuffer` 两段、将每一帧永久保留在画布、或把“支持 H.264”当作播放一定成功。DRM、自动播放、画中画、字幕与音频描述都有用户代理、权限和可访问性边界，失败时应给出可理解的静态提示或较低码率流。

**验证练习。**输入为一个含两档码率、一个不支持编码配置的 fixture；输出为缓冲/队列状态表和降级选择。断言：追加串行、队列有上限、所有帧释放；模拟许可证失败、网络中断和能力不支持，确认不重试风暴且可恢复到可播放的替代流。

## COMP-01

**定义与机制。**组件契约先定义职责，再定义输入、输出和可组合方式：数据用值或受限对象传入，用户意图用事件传出，内容扩展用插槽/children，外观扩展用有限的语义变体。每一个 prop 必须说明默认值、互斥关系、可访问语义和兼容承诺；组件内部状态不得泄露为调用方必须理解的 DOM 细节。组合优先于不断增加布尔开关，因为组合能让状态和语义保持局部。

**例子与反例。**`Dialog` 可接受 `open`、`onOpenChange`、标题和操作区插槽，并承诺焦点进入、Escape 关闭和焦点归还；触发器若不是按钮，也必须承担等价键盘语义。反例是 `isLarge/isSmall/isPrimary/isDanger` 同时存在，或暴露 `setOverlayZIndex` 让使用方依赖实现。不能只凭视觉截图认定契约正确：读屏顺序、键盘路径、禁用状态和嵌套组件才是边界。

**验证练习。**输入为一页组件 API 草案和三个使用场景；输出为 API 表、互斥规则及可运行示例。检查 happy path、键盘打开/关闭、非法组合被类型或运行时拒绝、升级后旧调用仍按声明工作；记录一个刻意被拒绝的布尔参数，说明为何改为组合。

## DS-01

**定义与机制。**Token 是可发布的设计决策而不是散落的 CSS 值。原始 token 表示色阶、间距等物理值；语义 token 表示 `color.text.default` 等用途；组件 token 只在组件内映射语义 token。主题切换只替换同一语义层的值，构建阶段把 token 编译为 CSS 变量、原生值或 JSON，同时保存来源、版本与弃用信息。对比度、字号和动效还需要针对目标背景和状态验证，不能只看 token 名称。

**例子与反例。**深色主题将 `color.surface`、`color.text.default` 一起替换，按钮读取语义 token 而非写死 `#1677ff`。反例是产品 A 把 `blue-6` 直接写进组件、产品 B 重新定义同名 token，导致主题切换和跨端输出不一致。Token 不应承担布局业务逻辑；无法表达的局部差异应显式成为组件变体。

**验证练习。**输入为浅深两套原始值与三条语义映射；输出为编译后的变量和变更 diff。检查同一组件在两主题不出现未解析变量、关键文字与背景达到题设对比度、删除 token 会在构建时报出所有引用点；将一次破坏性重命名标为 major 或提供别名迁移。

## COMP-03

**定义与机制。**组件发布的证据链是“契约文档—可运行示例—自动测试—版本记录”。文档说明输入、输出、可访问行为和已知限制；示例使用公开 API，避免复制内部实现；交互、视觉与无障碍测试各自覆盖不同风险。版本号按兼容性表达：新增兼容能力为 minor，修复为 patch，删除/改变公开行为为 major 或先弃用；变更日志必须写明影响、迁移和回退方法。

**例子与反例。**把 `onSelect(id)` 改为 `onSelect({id,label})` 即使页面能运行也是公开契约破坏，应保留旧适配层或发布 major，并给迁移例子。反例是只改截图、示例仍调用旧参数，或以“新增组件数量”代替采用价值。多框架封装只要承诺同一交互，就要在每个承诺的运行时留下测试证据。

**验证练习。**输入为上个版本 API、拟发布 diff 和消费者示例；输出为文档页、变更日志条目、兼容性分类和测试结果。检查示例可执行、公开类型和文档一致、键盘和读屏回归通过；故意删除一个 prop，验证发布检查会阻止未标 major 的破坏性变更。

**发布路径与故障注入。**发布前由 CI 从公开类型生成 API 清单，逐项比对文档、示例与行为测试；再在隔离消费者项目安装候选包，执行构建、键盘流程和升级脚本。适用场景是有多个消费者、公开契约或长期维护责任的组件；一次性页面内部组件不必伪装成可独立发布的包。模拟“类型仍兼容但焦点行为改变”“示例依赖未导出内部符号”“补丁版本删除默认值”三种变更，分别要求阻断、标记 major 或给兼容适配层。验收证据包括版本前后 API diff、消费者升级日志、弃用告警命中数、回滚版本和保留期截止日；复测需使用干净锁文件重装，只有发布成功而没有消费者复测不能证明治理有效。发生线上回滚时，还应保存触发阈值、受影响消费者版本、回滚包的完整性校验、恢复后关键交互回归和后续修复版本的关联记录；不能以“已重新发布”替代回滚链路证据。

## PLATFORM-01

**定义与机制。**配置化页面把“允许变化的页面数据”写为 schema，把“可信的渲染器与业务动作”留在代码。流程为读取版本化 schema、校验结构、白名单解析组件/字段、计算受限表达式、渲染、收集数据，再用同一或服务端 schema 校验输出。组件注册表只能暴露固定组件和属性；表达式不能取得全局对象、网络能力或任意函数。迁移把旧 schema 显式变换到新版本，并保留可定位的错误路径。

**例子与反例。**订单页 schema 可以声明 `TextInput`、必填规则和“国家为 CN 时显示省份”；渲染器把它映射到已注册组件。反例是 schema 内直接写 JavaScript、把权限判断只放前端、或校验失败仍提交原数据。配置适合可枚举的表单/展示差异，不适合把复杂工作流、付款副作用或未知 UI 当字符串执行。

**验证练习。**输入为有效 schema、未知组件、循环联动和旧版 schema fixture；输出为页面、规范化数据及每个错误的 JSON 路径。检查未知组件拒绝、联动稳定收敛、服务端再次校验、迁移前后语义一致；记录一次沙箱越权尝试被拦截的证据。

**实现路径与失败证据。**把 schema 按“解析—结构校验—版本迁移—白名单解析—受限联动—渲染—提交复验”逐段记录输入和输出；表达式只读取当前表单白名单字段，不能访问网络、全局对象或任意函数。它适合字段、展示和校验可枚举的差异，不适合审批流、支付或跨服务事务等副作用编排。补充 fixture：旧版本缺字段、迁移后默认值冲突、两个字段循环写入、客户端绕过必填和未知组件名。验收必须给出 JSON Pointer 诊断、迁移前后值快照、服务端拒绝记录和限制表达式的拒绝日志；把 JSON `eval` 成功渲染不是可接受实现。

## PLATFORM-02

**定义与机制。**微前端是独立交付单元通过宿主协议组合，而不是把多个应用并排加载。先按团队边界、独立发布需求和故障域决定是否拆分；每个子应用声明路由前缀、初始化/卸载、样式隔离、消息 schema、共享依赖版本和降级页。宿主负责装载、超时、错误边界和回滚，子应用在卸载时清除监听器、定时器和挂载节点。通信使用有版本的事件或请求协议，禁止共享任意全局可变状态。

**例子与反例。**宿主在 `/billing/*` 按清单加载账单子应用；版本不兼容时显示静态账单入口并上报。反例是把全站状态对象暴露给所有子应用、共享 React 单例却不锁版本、或把 iframe/模块加载成功误认为业务可用。若团队不能独立部署或协议频繁同步变化，模块化单体通常成本更低。

**验证练习。**输入为两个版本不同的子应用、故障清单和发布清单；输出为装载时序、协议定义、兼容矩阵和回滚记录。检查路由、样式和错误隔离；模拟远程入口超时、共享依赖冲突与子应用崩溃，确认宿主仍可导航且旧版本可恢复。

## PLATFORM-03

**定义与机制。**物料平台把组件从“可发布包”治理为“可发现、可采用、可退出的产品”。登记内容至少有所有者、适用场景、API、质量门禁、版本状态和迁移窗口；目录和示例解决发现，类型/视觉/无障碍/安全检查解决准入，使用遥测和 Issue 分类验证是否真正减少重复实现。采用率必须有分母（目标项目或可替换调用数）与时间窗，不能只报下载量。

**例子与反例。**平台发现三个相同日期选择器后，选定一个物料，提供迁移 codemod，连续两版跟踪替换率与缺陷率。反例是强制接入但不支持例外、废弃包仍被新项目选用、或因“发了 20 个组件”宣布成功。治理不能替代业务负责人：平台要公开升级成本和退出条件。

**验证练习。**输入为物料清单、项目调用样本和 Issue 数据；输出为登记卡、门禁结果、采用率分母/分子及淘汰计划。检查新物料无所有者或无示例时不能发布，模拟一个高下载低实际引用物料不被误判为成功，审阅迁移后重复代码是否下降。

**实施顺序与失败处理。**先为候选物料指定产品所有者和维护 SLA，再把 API、可访问行为、性能预算、支持的运行时以及不支持的场景写进登记卡；随后用可复现的示例和自动门禁发布试用版。试用期同时收集安装、实际引用、迁移失败、工单和绕行实现，按项目/版本/时间窗计算采用率。若迁移成本高于重复实现节省，或维护者无法在承诺窗口修复，平台应暂停推广、公布替代物料和退出日期，而不是用强制升级掩盖失败。验收时随机抽样两个已登记项目：从锁文件和代码引用复算分子，从目标项目名单复算分母；再删除一个声明为废弃的物料入口，确认目录、模板和脚手架均不会再推荐它。

**量化示例与反例。**假设目标项目 20 个，其中 8 个存在可替换日期选择器调用；迁移 5 个项目只能报告“可替换调用采用率 5/8”，不能报告“平台已覆盖 5/20”或只报下载量。适用于重复模式、维护责任和升级窗口可被统一治理的组织；对迭代极快且没有稳定共同需求的小团队，强制平台反而增加等待与绕行。注入无人认领、无可运行示例、高下载低引用、废弃版本仍被脚手架推荐和 SLA 超时，门禁应分别拒绝发布、拒绝成功判定或停止推广。验收保存目标分母来源、代码搜索规则、版本时间窗、Issue 分类和下一次复算日期，防止指标随口径变化失真。

## MOBILE-01

**定义与机制。**跨平台原生前端由 JavaScript/声明式 UI 与平台渲染、原生模块协作；桥接/JSI 类接口把值、调用和回调跨线程传递。每项原生能力都要定义权限申请时机、前后台恢复、深链入口、失败回调和资源释放。发布链路从构建产物、签名、隐私声明、商店审核到崩溃符号和灰度回滚；OTA 只能更新允许热替换的代码和资源，不能绕过原生权限或二进制兼容边界。

**例子与反例。**扫描页在用户点击后请求相机权限，进入后台时暂停预览，返回时重新确认权限和会话；缺少权限时显示设置入口。反例是启动即申请所有权限、把大图逐帧跨桥传递、或把要求原生升级的 API 改动通过 OTA 强推。平台差异必须由能力检测和可见降级处理，而非假定两端完全一致。

**验证练习。**输入为相机、推送、深链三种能力矩阵；输出为生命周期状态图、权限文案、故障回退和发布清单。检查首次拒绝、永久拒绝、冷启动深链、后台恢复和旧二进制打开新配置；通过启动时间、内存、崩溃率和关键操作完成率验证，不只看模拟器。

**版本边界与发布证据。**原生二进制、JS 包、服务端配置和商店版本必须各自标识兼容范围；旧二进制调用新配置时先走能力协商，不支持则保持旧路径或显示升级提示。适用跨平台的前提是共享的业务体验大于原生差异成本；相机实时处理、系统级后台任务或严格合规能力若无法稳定桥接，应拆出原生实现而不是把失败隐藏在 JS 层。演练 OTA 回滚、签名/完整性失败、灰度崩溃率超阈值、推送冷启动与深链参数伪造，输出版本矩阵、回滚决策、符号化崩溃摘要和真机性能基线。验收要求能从用户版本、原生版本、JS bundle 标识和请求 trace 还原一次故障，且密钥、设备标识和精确位置不出现在崩溃或调试日志中。

## NODE-04

**定义与机制。**BFF 的一次请求共享一个绝对截止时间和取消信号：浏览器断开、上游超时或进程停止任一发生，都向尚未完成的下游 I/O 传播取消。输入在边界校验并建立认证/追踪上下文；聚合读取可并发但受并发上限，写入用幂等键和明确重试策略。流式响应必须在 `write()` 返回 `false` 时等待 `drain`；响应提交后只记录/终止流，不能再次写 JSON 错误。诊断事件只补充日志、指标和追踪，不能成为业务正确性的唯一通道。

**例子与反例。**`GET /dashboard` 并发读取账户和消息，800ms 总预算内把剩余时间分给下游；客户取消时两个 fetch 都 abort。反例是每层各自 1 秒导致总耗时失控、对非幂等写入无限重试、或 SIGTERM 后仍接收连接。健康检查必须区分“进程活着”和“可接流量”。

**验证练习。**输入为两个可延迟/失败的下游和一个中断的客户端；输出为带 request id 的响应、时序日志、指标和优雅停机记录。检查取消传播、429/503 的结构化错误、背压、重复写入去重、SIGTERM 后停止接新请求并在上限内退出。

## NODE-03

**定义与机制。**CLI 契约把 argv、环境变量和配置文件解析成已校验的命令对象，并明确优先级；正常机器结果走 stdout，诊断走 stderr，退出码表达成功、用法错误、运行失败或被信号中断。交互模式可询问确认，CI 模式必须由 flag 完全驱动；`--dry-run` 输出将执行的不可逆操作却不改变状态。结构化 JSON 输出与人类输出应有固定 schema/字段，不混入进度条。

**例子与反例。**`atlas import --file a.json --format json --dry-run` 输出计划并返回 0；未知选项返回用法错误且不写文件。反例是把错误日志写 stdout 破坏管道、解析失败仍返回 0、或 Ctrl+C 时直接 `process.exit()` 截断清理。密钥不应出现在 help、日志或 dry-run 输出中。

**验证练习。**输入为有效/无效参数、环境配置和 SIGINT；输出为 stdout、stderr、退出码及文件副作用清单。检查配置优先级、子命令 help、JSON 可解析、dry-run 零副作用、无效参数/取消分别得到可预期退出码与清理证据。

## API-01

**定义与机制。**规范化先解析 YAML/JSON 为保留来源位置的文档树，再识别 OpenAPI 版本与 schema 方言，解析本地/远程 `$ref` 并维护访问栈防循环，最后产出统一的路径、操作、参数、请求体、响应和 schema 中间表示。解析与业务设计分离：缺少 `operationId`、冲突参数或不支持的动态引用要成为带文件路径和指针的诊断，而不是悄悄猜测。示例是样本，不是无条件类型定义；overlay/多文件合并需规定顺序和覆盖规则。

**例子与反例。**输入根文件引用 `models/user.yaml`，规范化输出 `GET /users/{id}` 的参数和 200 schema；若 `User` 间接引用自身，报告循环链而非栈溢出。反例是把 `example: 1` 推断成唯一允许值、把相同路径不同方法覆盖、或允许任意 URL 远程引用造成 SSRF。规范化不负责决定业务字段是否合理。

**验证练习。**输入至少 20 个固定 fixture，含多文件、错误缩进、缺 `operationId`、多 content type、循环和被禁止远程引用；输出为稳定中间表示与定位诊断。检查同一输入字节级稳定、错误精确到文件/路径、diff 区分破坏性与非破坏性变更。

**解析路径与反例。**读取器先限定根目录和允许的引用协议，再以文件 URL 加 JSON Pointer 组成访问栈；解析成功后才进入版本/方言分派和规范化，任何一步失败都返回可定位诊断而不返回部分“可用”模型。它适合需要稳定查询、diff 或生成输入的规范工具；业务评审不能把解析器接受某字段理解为接口设计合理。补充输入：相对引用逃出根目录、同名 schema 覆盖、YAML 锚点展开过大、`oneOf` 无判别条件和远程 URL 重定向。验收保存每个 fixture 的 IR 摘要、错误代码、文件/指针、允许或拒绝理由及重复运行散列，证明循环和异常输入不会栈溢出、SSRF 或悄悄丢字段。

## API-02

**定义与机制。**代码生成以 API-01 的规范化中间表示为唯一输入：先给 schema 建立稳定标识和命名表，再生成类型/服务 AST 或等价结构，处理保留字、同名和循环引用，最后格式化、写入受管目录并 typecheck。确定性要求相同输入得到相同字节；增量更新只覆盖受管文件，手写扩展位于受管目录外或显式保留区。生成器不推断未在 schema 中表达的业务语义。

**适用场景与失败边界。**它适合接口数量多、消费者多且规范可作为共同事实来源的场景；小型、一次性的接口不应为生成器引入比手写代码更高的维护成本。生成范围必须显式声明：`oneOf`、鉴权流程、日期格式或厂商扩展若不能无损表达，应生成诊断和受控扩展点，不能静默降级为 `any`。写盘前在临时目录完成格式化与 typecheck，再原子替换受管目录；任一校验失败就保留旧产物、清理临时文件并返回失败，避免把半写代码交给调用方。

**例子与反例。**`user-id` 变为 `userId`，若与已有字段冲突则以稳定规则加后缀并在清单记录；删除 schema 字段会产生可审阅 diff。反例是按对象遍历顺序随机输出、直接拼字符串造成转义漏洞、覆盖用户手写服务实现，或 typecheck 失败仍写入“成功”。格式化工具只是最后一步，不能修复错误 AST。

**验证练习。**输入为含保留字、同名、nullable、循环引用及 schema 改动的 fixture；输出为受管 types/service、manifest、diff 和 typecheck 结果。检查重复运行零 diff、手写扩展未变、冲突命名可预测；注入非法标识和不支持 schema 后必须失败且不留下半写文件。

**生成路径与验收。**生成器按“稳定排序的 IR—命名表—受限 AST/模板—格式化—临时目录 typecheck—原子发布”执行，并把每个 schema 标识到文件/导出的映射写进 manifest。适合重复的、规范可表达的客户端契约；遇到无法无损表达的鉴权流程、厂商扩展或联合类型时，应停在诊断/扩展点，不能编造 `any`。注入格式化失败、磁盘空间不足、typecheck 失败、手写文件同名和第二次生成；验收记录临时目录清理、旧产物哈希、发布前后 diff、typecheck 命令和 manifest。只有生成了文件但没有证明无半写、零 diff 与消费者编译通过，不能算确定性生成。

## PERF-01

**定义与测量。**Core Web Vitals 是面向一次页面访问体验的 LCP、INP、CLS；字段数据应按页面、设备和网络分组看 75 分位，实验室结果只是在设定节流下的可重复诊断，不能替代真实用户分布。性能预算要写成可执行的阈值：路由、设备/网络、指标分位、样本量/观察窗与超标处置，且同时记录资源体积和关键请求数，避免只优化分数。

**实现与反例。**先以 RUM 找出退化路由，再用 Lighthouse/trace 复现实验室瓶颈；例如首屏图是 LCP 候选时，比较图像发现、下载、解码和渲染时刻，而不是盲目预加载全部图片。反例是把平均值当通过、把第三方脚本排除在体验外，或为改善实验室分数延迟真实可交互内容。

**验证练习。**为一个页面建立“慢 4G/中端设备”和“真实用户”两张基线表；注入慢首图、长点击处理和异步内容位移。提交 LCP/INP/CLS 的候选归因、预算门禁结果及同条件复测；若字段样本不足，明确标为“不可下结论”，不得伪造改善百分比。

## PERF-02

**机制与路径。**瀑布图先区分排队、DNS/连接、TTFB、下载和解析；缓存策略由资源可变性决定，带内容哈希的静态资源可长期缓存，HTML/API 则需验证或短缓存。`preload` 只用于浏览器尚未会及时发现且确实关键的资源；推测加载仅限无副作用、高意图导航。bfcache 是整页冻结/恢复，不等于 HTTP 缓存，恢复时仍需处理陈旧状态。

**失败边界。**给全部图片 preload、预渲染写操作页、用 `unload` 阻断 bfcache、或把用户 A 的认证响应复用给用户 B 都是错误优化。缓存命中不是成功本身：还要看过期内容、重复下载、内存和取消率。

**验证练习。**导出一次优化前后 HAR，列出每个关键资源的发现者、优先级、缓存头和字节数；注入过期内容、错误版本、导航取消和登录态切换。验收同时给出命中/浪费、关键路径时长、bfcache 恢复与业务正确性的证据。

## PERF-03

**机制与归因。**输入事件先进入主线程任务，脚本可能触发样式计算、布局、绘制和合成；渲染只能在任务让出后发生。长任务表示主线程连续占用过久，却不能单独证明交互体验；结合 trace、Long Animation Frame、INP 和 `PerformanceObserver` 才能判断是脚本、强制布局、绘制还是观测开销。

**实现与反例。**把可拆分计算切片到多个任务或 Worker，并在写样式后批量读/写以减少强制同步布局。反例是仅把代码包进 `setTimeout`、把大量 DOM 访问搬到每帧，或高频上报所有性能条目造成第二个长任务。

**验证练习。**录制一次筛选卡顿，输出 flame chart 截图、任务名称、调用栈和受影响帧；故意加入 120ms 计算与读写交错，分别修复。现场观测须有采样率、上限与 `disconnect()`，复测须证明行为和结果未变。

## PERF-04

**机制与定位。**泄漏不是“内存曾变大”，而是本应失活的对象仍从 GC root 可达。对同一操作进行热身、重复 N 次、强制或等待 GC 后比较堆快照；以 retaining path 识别是监听器、闭包、缓存、定时器、`Blob` URL、媒体轨道还是 detached DOM 持有引用。

**实现与反例。**组件挂载时登记资源，卸载时移除监听、取消定时器、停止轨道并 `revokeObjectURL`；缓存需要容量/TTL 和逐出策略。反例是只调用 GC、只比较单次快照，或在清理时误关闭共享资源。

**验证练习。**提供打开/关闭弹窗或播放器 20 次的脚本、三次快照和增长曲线；注入未解绑 listener 与未释放对象 URL。通过条件是修复后可达对象数量在重复操作中稳定，并附 retaining path、清理代码路径和回归记录。

## H5-01

**机制与选择。**布局 viewport、视觉 viewport、DPR 与 CSS 像素不是同一概念；页面应以可伸缩布局、`min/max` 约束和内容驱动高度适配宽度。安全区使用 `env(safe-area-inset-*)` 作为可为零的环境值，不能按设备型号写死。软键盘、横竖屏与地址栏变化会改变可见区域，应在实际视口变化后重新布置关键控件。

**失败边界与验证。**反例是固定 `100vh` 遮住底部按钮、用 `vw` 给正文定字号、禁止缩放掩盖排版问题。交付 320、375、430px，横屏及 200% 字体缩放的截图/录屏与 DOM 尺寸；检查无横向滚动、焦点元素可见、安全区内操作区可点。记录浏览器和设备版本，未测设备只标“待验证”。

## H5-02

**机制与实现。**优先用 Pointer Events 统一鼠标/触摸/笔，手势识别后应释放或取消 pointer capture；仅在确需阻止默认滚动时使用非 passive 监听。软键盘出现时读取 `visualViewport` 的变化并将当前输入框滚入可见区；`overscroll-behavior` 只限制指定容器的滚动链，不应把整页滚动锁死。

**故障注入与证据。**构造弹窗内滚动、底层页面滚动、长表单和横向滑块：注入快速双击、手势中断、键盘弹出、pointercancel 与组件卸载。提交 iOS/Android 或可靠等效环境的事件日志、滚动位置和录像；键盘、Escape/关闭按钮和屏幕阅读器操作仍须完成同一任务。

## HYBRID-01

**机制与边界。**容器能力链应为“环境识别—向服务端申请当前 URL 的短期配置/签名—SDK 配置—ready/error—能力调用—普通 H5 回退”。厂商签名材料和长期凭证不进入前端；每个能力先做可用性检测，并把厂商返回值归一化为本地状态。普通浏览器、企业微信与钉钉是三种独立运行环境，不能用 UA 猜测替代实际 ready/error。

**验证练习。**为定位或文件选择实现适配器，记录容器名、SDK 版本、配置结果、能力检测和匿名错误码。注入签名过期、URL 不匹配、网络离线、能力缺失和用户取消；验收是错误可定位且浏览器回退仍完成核心任务，而不是“SDK 已加载”。

## H5-03

**机制与隐私。**定位只能在明确用户动作与目的说明后请求；一次请求与 `watchPosition` 的超时、最大缓存时间、精度和清理策略不同。地图 SDK 是异步外部资源：加载、实例、覆盖物、事件和销毁须成对管理；坐标系转换、公开前端 key 与服务端 secret 也需分开建模。

**验证练习。**实现“定位—展示地址—手工输入回退”的状态机，含 prompt/granted/denied、超时、低精度、后台恢复和地图加载失败。保留权限拒绝、清除 watch、`destroy`/监听释放及地址文本回退的日志；不得把用户精确位置写入普通调试日志。

## H5-04

**三种数据路径。**服务端代理上传是“浏览器—业务服务—对象存储”：浏览器不取得存储凭据，服务端可在流中执行限额、内容嗅探、病毒扫描或合规判断，但会承担全部入口带宽、背压、超时和扩容成本，服务端实现不得把整文件读入内存。单次直传是业务服务签发限定对象键、方法、大小/类型条件与短有效期的授权，浏览器一次 `PUT` 到存储；它减少业务服务带宽，适合尺寸可控且中断后可整体重传的文件，却没有分片级恢复。分片直传先由业务服务创建上传意图/分片会话，再逐片授权、上传和记录服务端已确认的 part，最后由可信服务校验清单并发起完成；它适合大文件和不稳定网络，但增加签名刷新、并发、重复 part、遗留分片、存储费用和完成幂等复杂度。三者共用业务 `intentId`、不可由客户端选择的对象归属和最终确认状态，不能把“对象存储返回成功”直接当成业务记录成功。

**信任、成本与选择。**浏览器的 `File.type`、文件名、对象键、散列和“已完成”声明都不可信；服务端至少复核实际大小、允许的内容特征、对象归属、校验和/ETag 的厂商语义及上传意图状态。需要同步检查敏感内容、文件较小或不能向客户端开放存储端点时选代理；文件中等、网络稳定且可整体重试可选单次直传；超出单次重传预算或需要断点时选分片。短期签名只缩短泄露窗口，不替代最小范围、CORS、速率限制和审计。成本记录应至少含业务服务入口/出口字节、存储请求数、未完成分片占用、浏览器峰值内存、失败重传字节和恢复时间，不能只比较“是否上传成功”。

**统一状态机与切换。**客户端状态为 `created → authorizing → uploading → verifying → committed`，取消进入 `aborting/aborted`，可重试失败进入 `paused`；每次动作带 `intentId` 和幂等键。刷新恢复必须先查询服务端确认的模式、对象与已收 part，不能只信本地进度。存储不可用时不能盲目把正在上传的流切到代理：先停止新 part，查询完成状态；结果明确未完成才中止/登记原会话清理，并由服务端按文件限额、扫描要求和容量策略签发新的代理会话。若完成结果不确定，保持 `verifying` 并对账，避免同一业务意图生成两个对象。代理容量不足、合规不允许或文件超过代理上限时，应保留待重试状态并说明恢复时间，而不是承诺必定切换。

**可复现实验。**为同一份 64 MiB 或大于项目内存预算的固定 fixture 实现统一 `UploadTransport`：`proxy` 路径以流和背压经过测试服务；`direct` 路径取得一次性短期授权后单次上传；`multipart` 路径按固定块切 `Blob.slice()`、限制并发、逐片登记并由服务端完成。测试服务提供上传意图、授权、查询状态、完成/中止和对象复核端点；对象存储可用本地兼容服务或可控 mock，但必须标注 mock 不证明真实厂商兼容。每种路径记录浏览器峰值内存、服务端入站字节、请求数、总耗时、重传字节、最终散列和唯一业务记录，证明选择依据与数据流一致。

**故障注入与验收。**分别注入代理消费者变慢/连接中断、单次直传 CORS/签名过期/存储 `503`、分片乱序/重复/丢失/刷新页，以及“完成请求超时但服务端可能已提交”的不确定结果。再模拟存储持续不可用：满足代理策略的 fixture 建立新代理会话，不满足的停在可恢复队列；两者都要清理旧分片且不能重复落业务记录。输出三条时序、上传意图与分片清单、授权范围、并发/内存上限、迁移决策、对象复核和清理任务；断言取消后不再发请求、失败不产生半提交记录、完成可幂等重放，客户端 MIME/路径/完成声明均未被当作安全依据。

## MEDIA-02

**采集与轨道状态。**采集必须由明确用户操作触发，并在开始前说明来源、用途、传输对象和保留时间。`MediaStreamTrack` 的 `mute/unmute` 表示暂时没有媒体，`ended` 表示来源终止，`stop()` 是本端主动释放；屏幕共享还可能被浏览器 UI 直接停止。设备切换应先取得并验证新轨道，再用 `replaceTrack` 或等价切换并停止旧轨道，不能同时占用旧硬件。页面隐藏不是自动同意继续采集的理由，产品需明确暂停、继续或结束策略。

**从轨道到受控录制。**`MediaRecorder` 消费 `MediaStream`，按 `timeslice` 或 `requestData()` 产生 `Blob`；时间片不是精确媒体分段或关键帧保证，因此每片要另记会话、递增序号、单调采集时间、MIME/codec 和大小，不能仅靠回调到达时间排序。录制状态机至少包含 `idle → requesting → recording ↔ paused → stopping → stopped/error`；停止时先阻止新操作，等待最后一次 `dataavailable` 与 `stop`，再完成清单、关闭对象 URL 和轨道。片队列必须有字节/时长上限与背压策略：可暂停录制、停止并提示保存，或在仅允许低价值预览时明确丢弃；不得无限积累 Blob。MIME 支持通过运行时探测，unsupported 时退到可用格式或禁用录制，不伪造文件扩展名。

**实时传输与服务端处理。**WebRTC 适合需要拥塞控制、抖动缓冲和双向低延迟媒体的会议；MediaRecorder 分片上传适合可容忍秒级批次的录制/转写；AudioWorklet 适合音量计、轻量 PCM 预处理或需要自定义帧的路径，但实时线程中不能做网络、JSON、大对象分配或重计算。自定义 PCM/编码片传服务端时要带序号、源时钟、采样率/声道和取消标识，并给发送队列上限；服务端断线后不得把全部历史音频无界追赶。服务端实时处理可集中模型、审核和跨端一致性，却增加原始媒体出端、网络依赖、成本和数据保留责任；本地处理隐私更好但受设备能力、模型体积和兼容性限制。选择必须同时记录延迟目标、质量目标、设备预算、网络预算与隐私依据。

**字幕时序与质量面板。**转写结果使用 `{ segmentId, startMs, endMs, revision, final, text }` 对齐采集源时钟；相同 segment 的高 revision 替换临时文本，`final` 后的改写需有显式更正策略，乱序/重复响应按 id 与 revision 去重。播放器当前时间不能直接替代采集时间，设备切换、暂停和重连要记录时间基准偏移。字幕视图提供开启/关闭、键盘可达和可读对比度，临时结果不应高频轰炸读屏实时区域。质量面板至少显示端到端字幕延迟、未决分段数、音频队列字节/时长、丢弃片、网络 RTT/丢包或 WebRTC 状态、轨道静音/结束、Recorder 错误；有标注参考文本时才计算字错率，没有真值只能报告延迟、覆盖和人工抽查，不能把服务返回文本当“准确率 100%”。

**隐私、失败与降级。**权限拒绝、设备拔出、用户停止共享、网络断开、服务端限流、字幕过期和页面隐藏都要进入显式状态；撤权/停止从轨道传播到 Recorder、PeerConnection、Worklet、上传队列和字幕请求。日志只保留会话/轨道的随机标识、状态和聚合指标，不写原始音频、字幕全文、设备 label 或屏幕内容；保存/上传需遵守同意与删除期限。实时处理失败时可保留经用户同意的本地录制待上传、切到纯文字沟通或关闭字幕，不能在未告知时改送另一服务。

**可复现实验与证据。**实现摄像头或屏幕二选一的会议/录制切片：显式授权后建立轨道；以 1 秒左右 timeslice 生成带序号的录制片；一条路径通过 WebRTC 测试对端实时传输，另一条把录制片送入可控转写服务。测试服务按脚本返回延迟、乱序、重复的 interim/final 字幕，使界面可验证 revision、时间轴和质量面板；它只能证明协议与 UI，不能冒充真实转写质量。注入拒绝、拔设备、浏览器停止共享、Recorder 不支持/报错、片队列超限、ICE 失败、服务断连、字幕乱序/迟到、页面隐藏和 Worklet 过载。提交权限/轨道/录制/传输/字幕时序、队列上限、质量面板截图或日志、停止后的资源快照及同条件复测；验收旧轨道、Recorder、PeerConnection、Worklet、对象 URL 和未决请求全部释放。

## COMP-02

**机制与实现。**一个交互值在任一时刻只能有一个权威所有者：受控模式由 `value` 与变更回调驱动，非受控模式只以初始值建内部状态。不要在渲染时把 props 无条件复制进 state；模式切换应被禁止或给出开发期告警。命令式句柄只暴露无法自然表达为 props 的能力，如 `focus()`，不暴露内部 DOM 或状态机。

**验证练习。**以选择器实现受控、非受控、外部 reset、异步保存、表单重挂载与 `focus()`；记录每次事件顺序。注入父级延迟回写、默认值变化和受控/非受控切换，证明无回滚闪烁、循环更新或双源竞态；通过 DOM 测试和键盘焦点回归验收。

## EMBED-01

**决策与协议。**npm/ESM 适合可共享构建链的可信宿主；Web Component 隔离 DOM 接口；脚本注入成本低但全局冲突风险高；iframe 隔离最强但通信、性能和第三方存储成本最高。无论形态，都需要版本化初始化参数、幂等 mount/unmount、资源预算与错误回调。跨窗消息必须同时校验 `origin`、消息版本/schema 与会话/nonce，不能以 `*` 代替目标来源。

**验证练习。**以两个宿主加载同一部件，注入重复初始化、样式污染、伪造消息、租户切换和 iframe 加载超时。输出形态选择矩阵、消息 schema、CSP/权限清单和销毁后资源快照；验收一个宿主故障不读取另一租户数据，且静态回退可使用。

## RUNTIME-01

**定义与能力授予。**受限宿主是“页面代码不能直接拥有全部平台能力，必须经宿主声明、用户授权或策略授予后调用”的运行环境。普通网页依赖浏览器标准 API；MV3 扩展由 manifest、运行时权限和 host 权限授予能力；小程序由逻辑层/渲染层及宿主 Bridge 暴露白名单能力；企业托管浏览器、IDE 面板和受限 WebView 则由宿主配置、注入桥或消息协议决定能力。应用代码不能靠检查某个全局变量就信任宿主，应经适配层读取带版本的 capability 清单，并在每次敏感调用时再次校验权限、调用方、参数和当前生命周期状态。能力探测只说明“当前可请求或可调用”，不代表用户已经授权，也不保证下一次调用仍可用。

**执行上下文与生命周期。**普通网页的 DOM、脚本和存储通常随页面导航、冻结或销毁变化，网络受同源、CORS 和 CSP 约束。MV3 内容脚本与页面处于隔离执行世界，后台 service worker 可在空闲时被回收；关键状态必须先持久化，事件处理器必须可重复注册且幂等恢复。小程序的逻辑层、渲染层和宿主原生层经序列化消息协作，页面隐藏、卸载、进程回收或分包更新都可能中断异步调用。受限 WebView/IDE 面板的 Web 内容与宿主进程也不是同一信任域：桥只在特定面板、会话和版本中有效，面板重载、宿主升级或企业策略变更后必须重新握手。任何宿主都不得把内存单例、永驻后台或固定初始化顺序当作契约。

**适配合同。**业务层只依赖 `HostAdapter` 一类窄接口，例如 `getContext()`、`loadState()`、`saveState()`、`request()` 和 `openExternal()`；接口返回 `{ ok, value, errorCode, retryable }`，并声明能力名、协议版本和取消语义。普通网页适配器用 `location`、标准存储、`fetch` 和普通链接；扩展适配器通过经过验证的消息调用后台存储或网络能力；小程序/WebView 适配器经白名单 Bridge 请求宿主。Bridge 消息至少带协议版本、会话标识、唯一请求号、动作和经 Schema 校验的 payload；接收方还要验证来源窗口/发送者、允许动作、响应关联和超时，不能接受网页伪造的“宿主成功”消息。网络代理只允许登记的目标和方法，认证材料留在有权上下文；存储按命名空间和 schema 版本隔离，升级采用“读取旧版—校验—迁移副本—原子切换”，失败时保留旧数据。

**适用、不适用与降级。**只有标准 Web 无法满足且宿主能力的收益足以承担权限、审核、更新和兼容成本时，才选择扩展、小程序或 WebView。信息展示、表单和普通导航优先标准 Web；不应为获取更宽权限而包装受限容器。每项特有能力都要定义标准 Web 或人工替代：没有宿主存储时退到会话内状态或导出文件，没有宿主导航时显示普通链接/复制地址，没有网络代理时给出可重试提示而不是绕过策略。宿主禁用、能力撤回或协议版本过高必须返回稳定错误，并停止继续调用；不能静默失败、无限重试或降级成更宽权限。

**可复现实验。**实现“读取当前宿主上下文、保存主题偏好并打开帮助页”这一业务切片，业务代码只调用同一 `HostAdapter`。提供三套可运行实现：普通网页直接使用标准 API；MV3 扩展由内容脚本经消息访问可回收的后台和扩展存储；第三套选择小程序开发工具或一个受限 WebView 合同测试器。合同测试器可用父页面加载沙箱 iframe，通过固定 `postMessage` 协议模拟宿主握手、能力清单、隐藏/恢复、销毁和重载，因此没有厂商环境也能复现协议行为，但报告必须明确它是合同模拟而非真机兼容证明。另列普通网页、MV3、小程序、WebView/IDE 的执行上下文、生命周期、权限、存储、网络、更新和降级矩阵；未实际运行的宿主标为“设计验证”，不得写成已兼容。

**故障注入与证据。**一是终止 MV3 service worker 或重载宿主，验证内存状态丢失后能从带版本存储恢复且事件不会重复注册；二是从错误 origin/会话发送未知动作、重复请求号和畸形 payload，验证 Bridge 全部拒绝并留下脱敏原因；三是撤回 `openExternal` 或网络能力，验证业务收到 `UNSUPPORTED` 并走普通链接/手动操作；四是放入 v1、损坏版和未来版状态，验证 v1 可迁移、损坏版隔离、未来版拒绝且旧数据仍可回滚；五是模拟企业策略或宿主设置禁用，验证适配器释放订阅、停止后台工作并显示标准 Web 降级。提交能力矩阵、协议 Schema、三套实现或合同测试、权限提示、消息/生命周期时序、迁移前后快照、拒绝日志和同条件复测。只有扩展 happy path、只有 capability 检测截图，或把模拟器结果当成真实小程序/WebView 兼容证据都不能通过。

## RUNTIME-02

**能力授予链。**桌面容器的 renderer 视为不可信：Electron 通过隔离的 preload 暴露窄 API，Tauri 通过 capability/command 白名单授权。每次文件、通知、深链或外链操作都要校验调用方、参数、允许路径和输出；远程内容、宽泛 IPC 与直接 Node 集成会穿透这条边界。更新包的签名、版本、失败回退与崩溃日志脱敏同样是交付的一部分。

**验证练习。**实现“选择受限目录文件并显示通知”的最小桥接，注入 `../` 路径、未知 IPC、远程导航、深链畸形参数与更新签名失败。提交 allowlist、拒绝记录、隔离配置、更新回退演练；验收 renderer 没有系统能力，失败不泄露本地路径或密钥。

## NODE-01

**机制与测量。**Node 的 timer、pending callback、poll、check 等阶段与微任务调度共同决定回调时机；`process.nextTick()` 在不受控制时可饿死 I/O，Promise 微任务也会延后后续阶段。不要背诵绝对顺序：timer/immediate 与 I/O 的可观察顺序取决于调用位置和运行环境，应以可重复脚本与当前 Node 版本实测。

**实现与验证。**用 `monitorEventLoopDelay` 或等价延迟直方图记录 P50/P99，在 CPU 循环和同步文件读取下对照吞吐/延迟。把可分割工作切片，或把纯 CPU 任务放入 worker，并明确消息复制成本和取消路径。注入 nextTick 递归、慢 CPU 任务和 worker 异常；验收 I/O 仍获调度、P99 有改善且结果顺序/数据一致。

## NODE-02

**机制与实现。**Stream 的背压来自写端 `write()` 返回值与 `drain`，正确组合应使用 `pipeline()` 使错误、关闭和取消沿链传播。Buffer 是二进制视图而不是无限容器；大文件要流式解析或分块处理。原子替换通常写入同目录临时文件、完成 fsync/关闭后 rename，并在失败分支清理临时文件；平台差异必须在当前部署环境验证。

**故障注入与验收。**以大 YAML/JSON fixture 运行，记录峰值 RSS、吞吐、错误 `cause` 和文件状态；注入读取权限错误、磁盘满、解析错误、Abort 和下游提前关闭。通过条件是 pipeline 失败后所有句柄关闭、旧目标未被半写覆盖、成功文件可重新读取校验，且错误包含操作和路径上下文但不泄露敏感内容。

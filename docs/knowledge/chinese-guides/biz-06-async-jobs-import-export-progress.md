# 异步业务任务知识点讲义

## BIZ-06 异步任务、导入导出与进度

导入十万行数据、生成报表、媒体转码和批量审批无法在一次短请求中可靠完成。把 HTTP 超时调得更长，只会让代理、浏览器、进程重启和用户刷新更容易切断观察路径。正确模型是把“请求创建任务”与“任务持续执行”拆成两个生命周期，用稳定任务身份、显式状态、可恢复查询和有边界的取消连接它们。本讲从任务协议一直讲到进度、结果领取、部分成功和运维治理。

### 一、长任务必须拥有独立身份与状态

**长时间运行操作（Long Running Operation）**在创建请求结束后继续存在。服务端接受任务后返回稳定 `taskId`、初始状态、查询地址和建议重试时间。HTTP 202 表示请求已接受处理，不表示业务已成功；若输入同步校验就失败，应立即返回明确拒绝，不必创建注定失败的任务。

任务至少区分 QUEUED、RUNNING、SUCCEEDED、FAILED、CANCEL_REQUESTED、CANCELLED 和 EXPIRED。PAUSED、WAITING_FOR_INPUT 或 PARTIALLY_SUCCEEDED 是否需要，取决于业务是否真的存在这些阶段。状态不是页面动画，而是进程崩溃、断线和重启后仍可查询的事实。

任务记录保存发起主体、租户、业务意图 ID、输入摘要、当前状态、版本、进度、结果引用、错误类别和时间。执行进程不能只在内存里持有这些数据，否则重启后客户端有 taskId 却查不到任何事实。

### 二、创建任务需要去重一次业务意图

用户双击、浏览器重试或代理重放可能多次创建相同任务。客户端为一次意图生成稳定 key，服务端以主体、业务类型和规范化输入摘要原子占位。同键同输入返回已有 taskId，同键不同输入拒绝，防止一个 key 被误复用。

按钮禁用与防抖只能减少普通误触，无法抵御多标签页、网络重试和脚本调用。去重记录的保留期要覆盖实际重试和任务恢复窗口；已完成任务重复创建时，是返回旧结果还是创建新任务，要由业务合同明确。

如果创建响应丢失，客户端先用意图 key 查询，而不是生成新 key。服务端也要能区分“尚未创建”“正在创建”“已创建但未开始”和“已完成”，避免并发首次请求各自创建一份工作。

### 三、任务队列不是无限缓冲区

队列把接收流量与执行容量解耦，却不能创造容量。提交速度长期大于处理速度时，等待时间和存储必然增长。入口需要配额、最大队列、租户公平性、优先级和拒绝策略，并向用户返回预计等待或明确过载。

worker 领取任务时要有租约或可见性超时，崩溃后任务能再次可见；重复执行由幂等步骤和状态版本吸收。心跳过于宽松会延迟恢复，过短又可能把慢任务误判为死亡。领取、续租和完成更新必须原子比较所有者与版本。

大任务应拆成可重试分片并保存检查点，但分片边界不能破坏业务原子性。例如导入可按行验证并汇总错误，资金结算则可能需要更强事务与人工恢复。分片并行度要受下游数据库和第三方限额约束。

### 四、进度必须来自可解释的工作量

进度条需要可靠分子与分母。文件共有 10,000 行，已验证 4,000 行可以显示 40%；“正在调用不确定耗时的外部服务”没有可靠分母，应显示不确定进度、阶段、已用时间和可取消性，而不是虚构 80%。

多阶段任务可给阶段权重，但权重必须来自测量并允许版本化。读取、校验、写入、生成报告的成本不同，简单平均会在 90% 停很久。进度通常单调不减；若重新扫描导致总量变化，应解释重新估算，而非突然倒退。

进度更新频率也有成本。每处理一行写数据库会压垮存储，按时间或批量节流更合适。UI 将高频更新合并到合理帧率，并把百分比与“已处理/总数、当前阶段、失败数”一起呈现。

### 五、轮询需要退避、可见性与终止条件

**轮询（Polling）**是客户端周期查询任务快照。它兼容普通 HTTP 和代理，适合更新不极高的任务。服务端可返回 `Retry-After` 或建议间隔；客户端加入指数退避与抖动，避免大量页面在整秒同时请求。

轮询只在有观察者、页面可见或业务确需后台更新时运行。进入终态立即停止；网络失败与任务失败分开，断网恢复后先查当前状态。页面刷新从持久化 taskId 或任务列表恢复，不能重新提交创建命令。

慢响应可能与下一轮重叠。保持同一时刻最多一个查询，或给响应带任务版本并丢弃旧版本。401/403 表示身份/权限变化，不应无限重试；404 需要区分从未存在、已过保留期和无权隐藏。

### 六、推送减少等待，但查询仍是恢复真相

**推送（Push）**可用 SSE、WebSocket 或其他消息通道通知状态变化，降低轮询延迟与请求量。推送消息包含 taskId、版本、状态与事件 ID；客户端只接受版本更新的消息，并将其合并到对应任务。

连接会断开、消息可能重复或错过，因此推送不能是唯一事实来源。重连携带游标，发现缺口时查询任务快照；页面初始进入也先查询，再订阅增量。没有恢复协议的“实时”只是在网络正常时看起来流畅。

传输选型看方向、规模、代理和兼容要求。任务进度通常服务器单向更新，SSE 或普通轮询足够；不要为了一个百分比引入复杂双向协议。实时协议可靠性由 REALTIME-01 深入。

### 七、取消浏览器请求不等于取消业务任务

**取消（Cancellation）**是一种协作协议。AbortController 可以停止当前 fetch 或流读取，却无法自动撤销已经被服务端接受的导入。业务取消需要显式命令，例如 `POST /tasks/{id}:cancel`，服务端把状态改为 CANCEL_REQUESTED，执行器在安全检查点停止并最终进入 CANCELLED。

取消与完成会竞争。若任务已不可逆地完成，取消可能返回“已完成”而不是伪装撤回；若正在写入，系统决定回滚、保留部分成功或执行补偿。UI 以服务端最终状态为准，不能点击取消后立刻删除所有证据。

任务内部把取消信号传到子步骤，停止新工作并清理临时资源。某些外部调用无法取消，则标记等待结果并丢弃不再需要的响应，或进入补偿路径。取消超时要可观察并允许人工介入。

### 八、重试策略取决于失败类别与副作用

临时网络错误、限流和可重试依赖失败采用有上限退避，并遵守 Retry-After。输入错误、权限拒绝和确定性业务冲突不自动重试。未知结果先查询幂等记录或外部状态，再决定恢复，不能盲目重复有副作用步骤。

每个步骤要么幂等，要么保存完成标记和输出。任务整体重启时从检查点恢复，而不是从头重复发送邮件、扣款或创建文件。对第三方 API 使用稳定请求 key，并记录对方响应 ID。

超过重试预算进入明确失败或待人工处理，不要永久占用队列。死信记录输入引用、错误类别、尝试次数和恢复操作；敏感原始输入按留存策略保护，不能为了排错无限保存。

### 九、导入是解析、校验与写入三条边界

上传文件先限制大小、类型与解压上限，保存为不可执行的受控对象；任务逐步解析，区分文件结构错误、行级格式错误和业务冲突。不要一次把巨大文件读入内存，也不要用扩展名相信真实格式。

校验报告保留行号、字段、稳定错误码和用户可理解说明。部分成功策略由业务决定：全有或全无适合强一致批次；允许正确行写入时，结果必须列出成功、失败和未处理行，重试只包含未确认部分。

导入与现有数据并发时使用版本、唯一约束与幂等键。预览不是提交保证：预览后到实际写入之间数据可能变化，因此提交阶段再次验证关键不变量，并说明冲突。

### 十、导出要保护快照、权限与文件生命周期

导出任务保存筛选、字段、排序、请求者和快照语义。若数据持续变化，要明确导出反映创建时快照还是逐页读取的时间区间。直接把前端当前表格行当导出源，会漏页并绕过服务端权限。

结果文件放在受控存储，领取时再次验证用户与租户。短期签名 URL 或下载 token 需要过期、单对象范围和安全文件名；URL 不应进入公开日志。权限撤回后是否仍可领取旧文件，要按数据敏感度制定并执行。

文件过期进入 EXPIRED，UI 提供重新生成而不是继续使用失效地址。删除临时文件、失败残留和旧报告由独立清理任务完成，并有容量与审计指标。

### 十一、页面要呈现完整生命周期和恢复路径

任务中心比单个弹窗更可靠：用户可离开当前页、刷新或稍后回来查看。每项显示业务名称、创建时间、状态、阶段、进度、失败摘要、结果有效期和允许动作。状态文案不能只用颜色，焦点与读屏区域在重要变化时适度通知。

加载、空、离线、权限不足、部分成功和结果过期都要有下一步。取消前说明已完成部分是否保留；失败后保留错误报告；刷新后恢复同一任务。并行任务按租户和用户隔离，切换账号时清除旧缓存与订阅。

不要用频繁 toast 汇报每个百分点，也不要在后台任务尚未确认时显示“完成”。页面关闭不是取消意图；若用户确实要停止，必须操作明确取消命令。

### 十二、观测与容量治理

关键指标包括创建率、排队时间、执行时间、完成/失败/取消率、重试次数、租约恢复、每租户在途量、队列年龄、进度停滞和结果文件容量。只看平均执行时间会隐藏少量卡住任务，需观察分位与最老任务。

每个任务用 taskId 关联创建请求、队列消息、worker 日志、外部调用和结果文件。状态变化写审计事件，避免日志只有“job failed”。敏感输入和下载 token 脱敏，权限拒绝也保留可安全诊断的规则标识。

容量保护在入口完成：当队列接近预算时拒绝低优先任务或延后调度，不能无限接受后让所有任务超时。发布新 worker 前验证旧任务 Schema 和检查点兼容，滚动升级期间不同版本不能互相破坏。

### 十三、验证故障而不仅是成功动画

构造确定性时钟和假执行器，测试状态机合法边、重复创建、worker 崩溃重领、进度节流、终态停止轮询、推送缺口后查询、断网恢复、取消/完成竞态、结果过期和账号切换。验证服务端记录与 UI 同时一致。

对导入测试巨大文件、坏编码、压缩炸弹、行级错误、唯一冲突和部分成功；对导出测试权限撤回、筛选快照、文件过期与清理。负载测试逐步增加提交率，找到队列稳定点与拒绝行为。

保存可复核时间线：意图 key、taskId、每个状态版本、执行所有者、请求次数、最终结果和清理记录。若刷新产生新任务、终态仍轮询、Abort 后服务器继续而 UI 说已取消，测试应明确失败。

### 十四、常见反例与适用边界

- 用一个超长 HTTP 请求等待所有工作完成。
- 收到 202 就显示成功，或随意伪造线性进度。
- 页面刷新重新创建任务，双击只靠禁用按钮。
- 固定一秒无限轮询，终态、后台和离线仍不停止。
- 把 AbortSignal 当作服务端取消，取消后隐藏真实结果。
- 重试整个任务并重复外部副作用，没有检查点与幂等。

几十毫秒即可完成、没有独立恢复价值的操作不必任务化。任务系统增加队列、状态、清理和运维成本，只有工作显著超出普通请求预算、需要异步调度或必须跨刷新恢复时才值得引入。

任务 Schema 与执行代码也要兼容滚动升级。旧 worker 可能领取新服务创建的任务，新 worker 也可能恢复旧检查点；任务记录带 schemaVersion，发布前验证双向读取与迁移。不能理解的版本安全暂停并告警，不能猜测字段默认值后继续产生副作用。删除旧字段前确认队列、重试和归档中已没有旧版本任务。

### 十五、学完后应能说明

你应能设计任务创建、查询、推送、取消和结果领取合同；解释 taskId 与意图 key 的不同；给出可信进度与退避轮询；处理 worker 崩溃、断线、重复、部分成功和权限撤回；并用状态时间线、队列指标与故障测试证明任务可以恢复而不会重复副作用。

继续查证可参考 [MDN AbortController](https://developer.mozilla.org/zh-CN/docs/Web/API/AbortController) 与 [RFC 9110 的 202 Accepted 语义](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted)。

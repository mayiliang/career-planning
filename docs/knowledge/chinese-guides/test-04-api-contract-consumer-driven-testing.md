# 接口兼容验证知识点讲义

## TEST-04 API 契约兼容与消费者驱动契约测试

接口规范存在不代表消费者不会被破坏。提供者可能仍返回合法 JSON，却删除某个旧客户端依赖的错误码；protobuf 仍可解码，却复用了字段号；最新版 Web 通过，仍在线的移动端却无法处理新枚举。契约测试的价值是把真实消费者依赖变成可执行、可归属、可在提供者发布前验证的证据。本讲覆盖 HTTP、gRPC-Web 与异步消息，并明确契约测试与 Schema、集成测试和端到端测试的分工。

### 一、先明确契约测试要阻止什么

契约测试阻止独立发布的消费者与提供者对同一交互产生不同理解。它关心消费者真实发送的请求和依赖的响应/错误，提供者在受控状态下能否满足。它不证明整个用户任务完成、权限绝对安全、性能足够，也不替代服务内部单元测试。

适用条件包括多客户端独立发布、移动旧版本长期存续、跨团队 API、第三方集成或异步消息 Schema 演进。单体内部同一编译单元的纯函数通常用类型和单元测试即可；为了时髦给每个内部调用建 broker，只会增加维护成本。

### 二、消费者驱动从真实依赖出发

**消费者驱动契约（Consumer Driven Contract）**由消费者描述自己需要的交互，而不是让提供者猜测所有可能使用。消费者测试在隔离的 mock provider 上执行真实客户端代码，生成请求、匹配规则与预期响应；契约随后由真实提供者验证。

契约只包含消费者依赖的字段，避免把整个响应精确快照成脆弱合同。值匹配和类型/模式匹配要区分：ID 可接受任意符合格式值，状态可能只接受已知集合，错误码则需要精确语义。过度宽松会漏破坏，过度精确会把无关字段顺序变成门禁。

消费者名称、版本/分支、owner 和环境必须稳定。匿名契约无法通知迁移，也无法判断旧版本何时可删除。发布契约时关联提交和构建，不能由开发机随手上传覆盖主线事实。

### 三、Provider State 建立确定可重放前提

**提供者状态（Provider State）**描述交互发生前服务端需要满足的业务前提，例如“订单 42 存在且待审批”“用户没有该租户权限”。验证器通过状态处理器准备最小数据，再执行契约请求。

状态名称使用业务语言，不写“数据库第 3 行”。准备过程必须确定、隔离、可重复和幂等，不能依赖共享测试环境恰好存在的数据。每个验证运行使用独立租户/事务或可清理 fixture，避免并行互相污染。

状态处理器不是绕过生产逻辑的秘密后门。它只负责准备前提，不应修改契约响应或直接伪造被测 handler。敏感生产数据不得复制；时间、随机 ID 和外部服务用受控输入。

### 四、契约文件连接消费者测试与提供者验证

消费者侧先执行客户端调用，验证自己能正确消费 mock 响应，并生成契约。提供者侧加载同一契约、建立状态、向真实接口发送请求、比较响应，失败输出具体交互、状态和差异。两边都要运行，单独生成 pact 不产生保护。

契约制品不可人工编辑为通过。它关联消费者提交并在 CI 发布，提供者验证结果再关联自身版本。签名或制品摘要防止门禁验证的契约与实际发布契约不同。

请求匹配包括方法、路径、查询、头、认证上下文和 body；响应包括状态、必要头、body 与错误。认证 token 可由验证环境动态注入，但消费者对身份/租户字段的依赖仍应表达。

### 五、Broker 管理版本矩阵与发布判断

**Pact Broker**或同类契约仓库存储消费者版本、契约、提供者验证和部署环境关系。它的关键不是网页列表，而是回答“这个消费者版本与这个提供者版本是否验证过”“现在能否安全部署”。

can-i-deploy 类判断必须基于即将发布的真实版本和仍在运行/将运行的消费者集合。只验证主分支最新版本会遗漏生产旧客户端；永久验证所有历史版本又不可持续。团队要记录部署、退役和支持窗口。

Broker 失败时发布策略要保守但可恢复：使用已签名的近期结果、明确例外审批或阻断，而不是默认跳过。契约分支、标签和环境选择规则进入代码评审，避免通过错误标签只选到一个消费者。

### 六、HTTP 契约不仅比较 JSON 字段

HTTP 交互还包含状态码、Content-Type、缓存、分页、条件请求、重试和错误语义。消费者依赖 404 `ORDER_NOT_FOUND` 与 403 的区别时，提供者把两者统一为 200+null 就是破坏，即便 body Schema 仍允许 null。

匹配查询参数时注意编码、重复项和顺序语义；头只纳入消费者真正依赖项，避免 Date/requestId 造成脆弱比较。分页契约表达游标存在、稳定错误与空页，不把某次具体 ID 列表写死。

文件下载、流式响应和 SSE 需要验证头、首段、事件结构、终止与错误。只验证能建立连接不足以证明消费者能处理流尾失败或取消。

### 七、OpenAPI/JSON Schema 与 CDC 互补

提供者驱动 Schema 说明接口允许的完整形状，适合生成、文档、静态 lint 和 breaking diff；消费者契约说明哪些允许形状被真实客户端依赖。Schema 允许新增可选字段，CDC 可证明旧消费者确实不受影响；CDC 未覆盖的新接口仍需要 Schema 和提供者测试。

Schema diff 工具只能按规则猜测破坏性。例如删除 optional 字段在规范上可能允许，但某消费者实际读取；新增枚举在开放 Schema 中合法，却让旧 switch 崩溃。把 diff 与消费者验证、使用度量和弃用计划结合。

规范文件也要从真实实现验证，防止文档与运行时漂移。代码生成成功只证明语法可处理，不证明业务错误、默认值和权限语义正确。

### 八、向后兼容需要真实发布窗口

**向后兼容（Backward Compatibility）**通常指新提供者继续满足旧消费者；滚动发布还需要新消费者对旧提供者的兼容。建立消费者×提供者版本矩阵，标出生产、预发布与已退役组合。

兼容变更优先增加可选字段、保留旧语义和双写/双读。删除、重命名、收窄输入、改变默认、状态码或错误类别通常破坏。弃用流程包含使用发现、owner 通知、替代方案、截止、生产零使用证据和最终移除验证。

不能因为 Web 可即时更新就忽略旧 chunk、离线页面和缓存；移动/桌面客户端窗口更长。支持窗口来自产品与发布现实，不由测试工具自动决定。

### 九、Protobuf 与 gRPC-Web 有独特兼容规则

protobuf 字段号是线上的稳定身份。删除字段后把编号和名称保留为 reserved，不能复用给新含义。改变字段类型、oneof、map 或 repeated 可能在二进制或语义上破坏；未知字段可保留，不代表消费者理解新状态。

枚举首值与未知枚举处理需要按语言/生成器验证。旧客户端收到新数值时必须有安全策略，不能默认为成功。gRPC status、details 与 trailing metadata 都可能是消费者合同；只比较消息 body 会漏掉流尾错误。

gRPC-Web 还经过代理与浏览器适配。契约验证应覆盖实际代理模式、unary/streaming 支持、取消、压缩和 header 暴露。原生 gRPC 提供者测试通过不代表浏览器链完整。

### 十、异步消息契约验证生产者与消费者两面

事件契约包含类型、版本、eventId、对象 ID、发生时间、payload、顺序/分区与重复语义。生产者测试证明真实代码生成符合 Schema 的消息，消费者测试证明处理代表消息及未知字段，并验证业务效果与幂等。

消息没有同步 Provider State 请求，但仍需确定业务前提和处理环境。重复、乱序、缺口、毒消息与旧 Schema 都要进入测试。把一份 JSON fixture 能 parse 当作契约通过，会漏掉 ack、重试和状态变化。

事件是已发生事实，重命名类型或改变字段含义可能比新增字段更危险。新旧消费者并存时使用可兼容 Schema、版本路由或迁移事件，不能原地改历史语义。

### 十一、多消费者时防止最强或最弱者代表全部

Web、移动、批处理和合作伙伴可能依赖不同字段与错误。提供者验证逐份契约并输出消费者版本；一个最新 Web 成功不能代表移动。相反，不能把所有消费者需求合并成一份超大契约，否则无法知道谁阻止了变更。

重复交互可由 broker 去重展示，但 ownership 保持独立。若两个消费者对同一字段期待矛盾，先回到业务合同裁决，不应让 mock 各自返回不同世界。可以在迁移窗口提供兼容适配，再推动统一。

提供者团队需要查看消费热点和弃用 owner；消费者团队负责保持契约最小、及时发布和退役版本。没有双方责任，契约仓库会变成过期垃圾场。

### 十二、门禁设计要防止假通过

CI 顺序通常是消费者测试→发布契约→提供者验证→发布判断。提供者代码、状态处理器或契约变化都会触发验证。失败阻断相关制品，而不是允许手工点“绿”覆盖；紧急例外有 owner、期限、风险和回滚。

假通过常见来源：测试请求没经过真实路由、验证环境使用 mock 下游绕过关键转换、只选择最新标签、Provider State 吞掉异常、匹配器过宽或结果未关联发布 digest。定期故意注入破坏性变更，确认门禁真的红。

不稳定契约不能简单设为非阻断。先隔离状态、冻结时间、移除无关精确值、修复并行数据；仍无法确定时缩小交互，并由更合适集成测试承担。

### 十三、失败输出必须支持最小修复

报告指出消费者、版本、交互描述、Provider State、期望与实际差异、提供者版本和重放命令。对 Schema/proto 同时给出 diff；对流保存安全的帧与状态摘要。不能只报“contract failed”。

修复选择可能是恢复兼容输出、在适配层双支持、更新消费者并等待退役，或经业务批准发布新版本。不能为了让测试过而放宽匹配器，除非消费者代码也证明不依赖该字段。

每次失败回到具体合同语义。若契约错误，应由消费者 owner 更新并说明依据；提供者不能单方面重写消费者期待。

### 十四、验证证据与生产观测闭环

保存契约摘要、消费者/提供者提交、验证运行、状态准备日志和发布判断。生产记录各客户端版本、弃用字段使用和错误分布，帮助决定旧合同何时可删除。

契约通过后仍监控未知枚举、Schema 校验失败、代理异常和客户端错误。生产反馈发现遗漏时，先增加最小消费者用例，再修复提供者，避免同类回归。

敏感 payload 不进入 broker；使用最小合成值和脱敏日志。契约仓库访问、保留与删除按组织安全策略治理。

### 十五、常见反例与适用边界

- 共享一个由提供者维护的 mock，消费者没有自己的可执行期待。
- 只验证最新客户端、快乐路径或 200 body。
- 把 OpenAPI/proto diff、代码生成或能解码当作完整兼容证明。
- Provider State 依赖共享脏数据，失败后直接重跑直到绿。
- 契约精确快照所有字段，任何无关变化都阻断；或匹配过宽什么都通过。
- Broker 结果不关联实际发布版本，门禁查询了错误组合。

契约测试保护服务边界的兼容，不覆盖业务模型正确性、授权、性能、完整 UI 流程和生产容量。把它放在测试金字塔中恰当位置，才能既快速又可信。

### 十六、学完后应能说明

你应能识别消费者并写最小交互契约，建立可重复 Provider State，在提供者侧验证真实实现；解释 Broker 的版本矩阵和发布判断；区分 Schema 与 CDC；处理 HTTP、protobuf/gRPC-Web 和消息兼容；并通过故意删除字段、复用编号、改变错误与提前结束流证明门禁会阻止真实破坏。

继续查证可参考 [Pact 官方文档](https://docs.pact.io/) 与 [Protocol Buffers 更新消息类型指南](https://protobuf.dev/programming-guides/proto3/#updating)。

# PRECS-01 输入规模、基本操作与增长趋势

## PRECS-01

十条记录时很快，一万条记录时却很慢，最先要问的不是“电脑为什么变慢”，而是“记录变多之后，程序多做了哪些事”。这份短文从数次数开始，为复杂度讲义准备一个直观起点。

### 先说清楚什么东西变多了

**输入规模（input size）**是用来描述输入大小的量。字母 `n` 常被用作它的代号，但不天然等于数组长度。

对名单逐人点名，`n` 可以是人数；在文本中查词，可能要分别考虑文本长度和关键词长度；处理依赖关系时，既要看节点数，也要看连线数。相同的十个人，可以只有九条上下级关系，也可以有几十条互相关注关系，处理关系的工作量会不同。

如果程序接收订单表和用户表，就可以让 `n` 表示订单数，`m` 表示用户数。保留两个量的好处是：订单增加而用户没变时，你仍能说明成本为什么变化。把所有东西都叫 `n`，反而会把问题藏起来。

### 用一个小例子数清楚工作量

下面统计正数，同时记录做了多少次数值比较。计数器只用于帮助观察，实际业务不一定需要保留。

```js example=precs01-count
function countPositive(values) {
  let positive = 0;
  let comparisons = 0;
  for (const value of values) {
    comparisons++;
    if (value > 0) positive++;
  }
  return { positive, comparisons };
}
console.log(JSON.stringify(countPositive([-2, 0, 3, 5]))); // => {"positive":2,"comparisons":4}
console.log(JSON.stringify(countPositive([1, 2, 3, 4, 5, 6, 7, 8]))); // => {"positive":8,"comparisons":8}
```

第一组有四项，其中两个正数，但比较了四次。第二组有八项，比较了八次。答案里的正数数量不是这里的工作量；为了得到答案检查了多少项，才是我们在数的东西。

选出的代表性动作叫**基本操作（basic operation）**。这里选数值比较，查找字符串时可能选字符比较。选哪个动作，要看它能不能代表主要成本。一次“处理记录”若内部还会扫描全部用户，就不能把它当成永远只花固定时间的一小步。

### 把规模翻倍看看会发生什么

下面先用整数计数，不谈毫秒。每一种情况都假设其他条件保持不变。

| 做法 | 4 项输入 | 8 项输入 | 变化 |
| --- | --- | --- | --- |
| 每项检查一次 | 4 次 | 8 次 | 两倍 |
| 每项都与全部项比较，包括自己和反向配对 | 16 次 | 64 次 | 四倍 |
| 每轮把候选数量减半，直到剩一项 | 2 轮 | 3 轮 | 只多一轮 |
| 直接读取一个已知下标 | 1 次读取 | 1 次读取 | 次数不变 |

“每项与全部项比较”与“不重复地选两项比较”不是同一个任务。四项不重复配对只有六对，八项有二十八对。分析之前先说清楚算法实际做什么，再数次数，不能看到两层循环就直接套一个精确数字。

规模增大时工作量呈现的变化，就是增长趋势。把范围减半的过程增长很慢：候选数翻倍，只需要多排除一轮。完整遍历则必须看过新增的每一项。

### 次数不直接等于毫秒

十次数字比较和十次大图片解码的耗时不会相同。即使都是数组处理，创建新对象、访问内存和垃圾回收也会影响实际速度。操作次数帮助我们解释增长方式，不能代替目标电脑上的实际观察。

反过来，一次计时很快，也无法说明数据扩大后仍然快。后台任务、浏览器优化和输入分布都会影响结果。刚开始分析时，不必先写一套庞大的性能测试：明确输入规模，数出主要重复动作，再用少量有代表性的输入看看预测是否成立，就能排除很多错误判断。

例如“八项比四项快”可能只是这次测量太短、受到噪声影响；它不能推翻完整遍历需要检查所有项这一事实。关于增长的推导与某次计时，回答的是两个层次的问题。

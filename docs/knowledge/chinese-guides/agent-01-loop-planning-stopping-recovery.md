# Agent 循环、规划、停止与恢复知识点讲义

## AGENT-01 Agent 循环、规划、停止条件与失败恢复

Agent 不是“让模型一直思考直到完成”的提示词，而是一个由应用控制的状态机：接收目标，观察可信状态，提出下一步，执行允许的动作，再依据真实结果决定继续、等待、恢复或停止。高级工程能力体现在边界和失败语义，而不在循环次数。没有预算、停止条件、幂等和检查点的 Agent，会把模型的不确定性扩大成重复副作用、无限成本和无法解释的半完成任务。

### 学习前先确认

- 直接前置：[AIAPP-04 工具调用、执行语义与结果 UI](../chinese-guides/aiapp-04-tool-calling-execution-result-ui.md#aiapp-04)，用于理解参数验证、副作用、幂等和未知结果。间接前置不重复列出。

### 一、Agent Loop 是受控状态机

**Agent 循环（Agent Loop）**是应用在目标、观察、决策、动作和结果之间推进任务的受控过程。每轮都具有 runId、stepId、输入状态、预算、允许动作和终态，模型只生成候选决策，编排器决定候选是否可执行。

典型状态包括 queued、observing、deciding、awaiting_approval、executing、waiting_external、recovering、completed、failed 和 cancelled。迁移由明确事件触发，不能依赖助手文本里出现“完成了”。状态机保存谁在何时依据什么证据做了迁移。

前端从事件和状态渲染进度；服务端掌握事实。刷新后根据持久状态恢复，而不是重新发送原提示让模型猜此前做了什么。

### 二、观察必须区分事实与推断

观察来自用户输入、数据库、工具结果、环境快照和已确认中间产物。每项带来源、时间、版本、权限与可信度。模型之前的总结是派生内容，不能替代实际工具状态。

在开始新一步前重新读取会变化的关键事实，例如文件版本、订单状态、当前权限和任务取消标记。缓存可用于性能，但必须定义一致性和失效；执行前检查比在提示中提醒“注意最新状态”可靠。

工具返回失败、超时和未知结果是不同事实。未知不等于未执行，应先查询或对账，再决定是否重试。

### 三、Planner 产生可检查的下一步

**规划器（Planner）**把当前目标和观察转换为一个或多个候选步骤，并说明前置条件、期望效果、风险、所需能力和完成证据。它可以由模型、规则或二者组合实现，但输出必须结构化并经过验证。

计划不是一次生成后永久照做。环境变化、工具失败或用户修改目标时需要重规划；已经完成的事实和副作用进入新状态，不能从头重放。短任务可逐步决定，长任务可先给里程碑再细化最近一步，以减少过期规划。

并行只用于相互独立且结果可合并的步骤。共享资源、顺序依赖和额度竞争需显式建模；“模型认为可以并行”不足以绕过锁或事务。

### 四、执行器守住能力和参数边界

规划输出只是提议。执行器按服务端身份校验工具白名单、资源范围、参数 Schema、风险等级、审批凭证、并发与额度。模型提供的 tenantId、ownerId 或“已获授权”字段都不能决定权限。

读操作也可能泄露敏感数据，写操作还要处理幂等、补偿和未知结果。每个副作用步骤使用稳定 operationId；同一逻辑步骤重试时复用，用户明确发起新动作时生成新 ID。

执行结果保存原始状态码、业务回执、资源版本和脱敏摘要。模型获得最小必要结果，前端展示用户能核验的证据。

### 五、Stop Condition 由程序判定

**停止条件（Stop Condition）**是编排器可验证的终止规则，包括目标完成、无法继续、等待用户、预算耗尽、策略拒绝、取消或安全熔断。它不能只依赖模型说“任务已完成”。

完成条件应对应可观察断言，例如文件存在且校验通过、审批记录已生成、所有必需子任务到达终态。某些知识型任务没有唯一正确答案，则用覆盖标准、来源完整性和用户确认作为完成证据。

设最大步骤、token、时间、成本、同类失败和连续无进展次数。预算耗尽返回部分成果、未完成项和安全恢复入口，不把 `max_steps` 包装成成功。

### 六、无进展检测阻止空转

循环可能不断调用同一工具、重复读取相同页面或重写同一计划。为每步计算状态指纹、目标距离或新证据量；连续多轮状态不变且动作相同，触发重规划、换策略或停止。

不要只比较自然语言，它会换措辞却没有进展。比较资源版本、任务状态、已解决约束、工具结果类别和产物哈希。等待外部系统时进入 waiting_external，并使用明确唤醒事件，而非频繁空轮询。

循环检测也要识别 A→B→A 的状态振荡。把近期状态/动作摘要放入编排器规则，而不是指望模型记住自己重复了。

### 七、Checkpoint 保存可恢复边界

**检查点（Checkpoint）**是在安全边界持久保存的任务状态，包含目标版本、已确认事实、已完成步骤、外部回执、待审批项、预算、下一可执行位置和代码/策略版本。它让进程崩溃后继续，而不是重新演绎历史。

检查点在副作用提交前后分别记录意图和回执。恢复时先对账 pending 操作：已完成则吸收结果，未执行且可安全重试才继续，未知则转人工或查询。不能把模型输出缓存当事务日志。

版本迁移要明确。旧检查点与新工作流不兼容时使用适配器、只读恢复或请求用户重新确认，不能按新字段默认值偷偷执行。

### 八、失败分类决定恢复策略

把失败分为输入无效、权限拒绝、资源冲突、瞬时依赖故障、速率限制、业务终态失败、未知结果和策略阻断。每类有重试资格、退避、补偿、用户消息和观测指标。

瞬时失败可指数退避并加入抖动，尊重服务端重试时间；参数错误应修正或询问，不能原样重试。权限拒绝不靠换措辞绕过。业务冲突重新观察并规划。未知副作用先查询幂等状态。

恢复策略自身有预算，避免“修复失败的修复”无限嵌套。无法自动恢复时保留可复制诊断、当前检查点和下一步选择。

### 九、补偿不是通用回滚

外部动作往往无法事务回滚。发送邮件、付款或发布内容即使有撤回接口，也不等同未发生。设计时区分可逆、可补偿和不可逆；高风险步骤延后并集中确认。

补偿是新的业务动作，具有自己的权限、失败和审计。例如取消预订可能产生费用，删除发布物可能仍有缓存。Agent 不应在用户不知情时自动执行高影响补偿。

工作流可以用 saga 记录各步完成和对应补偿，但执行前仍检查当前事实，避免补偿别人后来修改的状态。

### 十、用户介入是正常状态

缺少必要选择、出现高风险动作或恢复存在多种后果时进入 awaiting_user/approval。向用户说明已完成、阻塞事实、需要决定的最小问题、各选项影响和过期时间，而不是倾倒内部推理。

等待期间释放计算资源并保持任务可恢复。用户答复包含 taskId、checkpointVersion 和允许范围；过期或状态变化后重新确认，不能把旧“继续”用于新计划。

用户可随时取消。取消是协作式状态迁移：停止新步骤，向在途工具发送取消，确认哪些副作用已经发生，并给出清理路径。

### 十一、上下文管理围绕任务事实

模型上下文包含当前目标、最近可靠观察、允许动作、未决约束和必要历史，不是完整事件日志。旧步骤压缩为带来源的任务状态；关键 ID、金额、禁止项和审批范围保持结构化，避免摘要漂移。

工具返回的网页或文件是数据，不能提升为系统指令。子任务只获得最小上下文和能力；结果返回结构化事实及证据，不合并隐藏推理。

上下文过大时优先丢弃冗余对话，不丢失执行账本。持久状态是恢复来源，prompt 只是一次决策视图。

### 十二、可观测性还原每次决策

记录 run、step、父步骤、状态迁移、观察来源、计划版本、策略判定、工具调用、幂等键、回执、预算和停止原因。日志脱敏并按租户隔离，模型内部不可验证思维不作为必须保存的解释。

指标包括任务成功、步骤数、无进展率、重规划、重复副作用、未知结果、等待用户、恢复成功、预算耗尽和取消延迟。按任务类型与风险分层，平均成功率会掩盖高风险长尾。

回放使用冻结观察和模拟工具，不重新执行真实副作用。若外部依赖不可复现，要标注边界。

### 十三、评测从状态迁移和故障注入开始

构建小而明确的任务集：单步读取、多步写入、并发冲突、参数缺失、权限撤销、工具超时、成功响应丢失、人工审批、用户取消和恢复后继续。每项声明预期终态、最大动作和禁止副作用。

断言重复投递只执行一次、未知结果先对账、无进展停止、旧审批不复用、检查点能恢复。模型答案看起来合理但状态错误，应判失败。

升级模型、提示、工具 Schema 或工作流后重跑回归。线上影子评测不执行真实写操作，发布门禁同时看成功、安全、成本和恢复。

### 十四、目标管理区分愿望、约束和验收

用户一句“把项目优化好”包含开放愿望，不能直接成为执行终点。Agent 与用户或产品规则把它转换为范围、不可改变项、优先级和可观察验收；缺少关键选择时先澄清。执行中保留原始目标和当前解释版本，模型重写计划不能悄悄改变目标。

约束分为硬约束和偏好：权限、预算、禁止删除属于硬边界；代码风格可能是可协商偏好。冲突时停止并呈现，不用模型选择绕过。验收与动作分离，执行工具不能同时修改测试使自己通过。

目标可能被用户更新或撤销。新版本计算哪些步骤仍有效、哪些产物需废弃；已经发生的副作用如实保留。任务完成基于当前目标版本，旧版本的成功不能自动迁移。

### 十五、子任务与委派仍受同一循环约束

复杂目标可拆成独立子任务，每个具有输入、产物、预算、权限、停止条件和父版本。只有互不依赖的只读或隔离工作适合并行；共享写入需要所有权与合并。子任务完成由证据验证，不因子 Agent 发回“done”就接受。

委派能力是父能力的子集，限制深度和数量。返回内容是不可信候选，协调者验证来源、Schema、版本和副作用。子任务失败只阻塞依赖节点，不盲目重跑已成功的兄弟节点。

即使当前实现只有一个 Agent，用任务信封表达边界也能减少上下文漂移；未来扩展多 Agent 时不需重写业务状态。

### 十六、确定性工作流与 Agent 可以组合

稳定、可枚举的步骤优先使用普通代码、规则和工作流引擎；模型用于理解非结构输入、提出候选或处理难以枚举的分支。规划后可把已确认步骤编译成确定性执行图，减少每步都调用模型。

若某一步只有一个合法动作，就不需要模型“决定”。把 Agent 限制在真正需要判断的节点，系统更便宜、易测且安全。失败恢复也优先走确定性规则，规则无法裁决才重新规划或求助人。

### 十七、先可靠再增加自主性

从一个目标、少量只读工具、明确终态开始。加入持久状态和可观察结果后，再支持副作用、审批、长任务和并行。每增加一种能力，就补充失败分类、预算、检查点与评测。

设计一个 Agent 前，写出目标 Schema、可信观察源、允许动作、每个动作的副作用/幂等/查询方法、状态图、完成断言、预算和人工入口。任何字段若只能由模型自然语言决定，都要问能否改为服务端事实或结构化候选。随后在每个提交边界杀死进程并恢复，确认不会重复执行。

还要证明错误不会被漂亮回答掩盖：工具权限撤销后停止，外部响应丢失后对账，状态无进展后终止，用户取消后报告真实副作用，验收失败后不写 completed。把这些不变量做成自动测试和生产告警，模型/提示/工具升级都重跑。

若普通工作流能完成目标，优先使用它；只有输入或分支确实需要语言推理时才引入模型，并把其自由度限制在可验证候选内。自主性应由可靠证据逐步扩大，而不是一次性打开全部工具。

生产运行还要提供全局和按工具的紧急停止、版本回滚、任务隔离和只读诊断。停止开关由可信控制面维护，Agent 无权关闭；触发后阻止新副作用，保留观察和导出证据，逐项对账在途操作。恢复服务前先修复策略或工具，再由小流量验证。

对于长期 Agent，定期检查原目标是否仍有效、用户是否仍有权限、资源是否已被外部改变和预算是否仍合理。等待状态用事件唤醒而不是模型空转；超过有效期就请求用户重新确认或安全终止。

每种终态都返回结构化完成报告：采用的目标版本、已完成与未完成、外部回执、费用、已知不确定性和可继续入口。这样上层系统和用户不必从自然语言猜任务是否真正结束。

运行手册应说明如何暂停单个任务、禁用单个工具、查询 operation、重建检查点和联系人工；没有这些操作面的 Agent 很难在生产事故中安全处置。

学完后，你应能把 Agent 描述为可审计状态机，区分观察、计划和执行，定义程序化停止条件、无进展检测、检查点与恢复策略，并解释为何“多循环几轮”不能替代权限、幂等和完成证据。

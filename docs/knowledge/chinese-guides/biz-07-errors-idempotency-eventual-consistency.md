# 分布式业务一致性知识点讲义

## BIZ-07 异常边界、幂等与一致性

浏览器发出写请求后连接超时，客户端无法从“没有收到响应”推断服务端是否执行。代理可能重试，消息队列可能重复投递，两个用户可能同时修改同一对象，跨服务更新也不可能永远依赖一个数据库事务。高级工程的关键不是承诺“绝不失败”，而是识别确定成功、确定拒绝和未知结果，给每种状态设计可重放证据、幂等处理、冲突保护与补偿。本讲建立这套端到端恢复模型。

### 学习前先确认

- 直接前置：[BIZ-02 状态机与业务不变量](../chinese-guides/biz-02-state-machines-business-invariants.md#biz-02)。本讲用状态机、版本、不变量和持久化中间态表达恢复过程。
- 直接前置：[BIZ-04 API 契约、DTO 与前端模型](../chinese-guides/biz-04-api-contract-dto-frontend-model.md#biz-04)。本讲假定你能区分传输失败、业务拒绝、稳定错误码和未知枚举。

### 一、失败分类决定下一步，不能统一成“出错了”

输入不合法可由用户修正；未认证需要重新认证；无权需要申请或退出；状态冲突要刷新当前事实；限流和暂时依赖故障可以受控重试；网络超时可能是未知结果；永久内部错误需要支持介入。错误类型不同，恢复动作完全不同。

客户端至少维护 `idle/pending/succeeded/rejected/unknown`，其中 rejected 表示服务端明确没有接受业务动作，unknown 表示可能已经生效但证据未返回。把 timeout 显示成“操作失败，请重试”会诱导重复扣款或创建。

服务端错误合同包含稳定 code、公开 message、可重试提示、对象版本和 requestId。日志记录内部原因与关联标识，响应不泄露堆栈、SQL 和敏感数据。错误文案可以迭代，程序判断不应依赖文案。

### 二、幂等定义的是业务效果，不是相同响应字节

幂等表示同一次意图重复执行，最终业务效果与执行一次相同。GET、PUT 等 HTTP 方法有协议上的幂等语义，但具体业务仍可能错误实现副作用；POST 也可以借助稳定意图标识实现业务幂等。响应时间、requestId 或当前展示字段可以不同，不影响核心效果相同。

**幂等键（Idempotency Key）**由客户端为一次业务意图生成，所有不确定重试沿用同一键。服务端将键与主体、租户、操作类型和规范化载荷摘要绑定；同键同载荷返回已有状态，同键不同载荷拒绝。键不是随机“每次请求 ID”，换键就代表新意图。

记录至少有 PROCESSING、SUCCEEDED、REJECTED 与必要响应引用。首次占位必须原子，避免两个并发请求都认为键不存在。保留期覆盖客户端、代理和消息可能重试的最长窗口；过期策略与用户重新发起的语义明确。

### 三、未知结果先查询，再决定是否重放

写请求在服务端提交后响应丢失，客户端进入 unknown。若接口提供按幂等键或业务意图查询，先查账本；查到成功就收敛 UI，查到明确拒绝可修正，仍处理中则等待。只有确认未执行或协议保证同键安全时才重放。

没有查询接口的高价值写入很难可靠恢复。可以返回操作资源 URL、在业务对象上保存 lastOperation，或提供事件流。仅凭本地“请求已发送”不能作为服务端事实，前端也不应永久显示加载。

支持人员需要同一关联链：客户端意图 key、网关 requestId、服务端事务、消息 eventId 和外部提供方 ID。没有这条链，人工只能凭时间和金额猜测是否重复。

### 四、条件请求保护并发版本

**条件请求（Conditional Request）**让写入只在资源仍符合客户端前提时发生。读取获得 ETag 或 version，更新携带 If-Match；当前版本不一致时服务端返回 412/409，不执行覆盖。它解决两个不同意图同时修改造成的 lost update。

条件请求与幂等键解决不同问题：同一个付款意图重试需要幂等；两个编辑者各自提交不同内容需要版本冲突。一个新幂等键仍可能基于旧版本，旧键也不能授权当前状态不允许的动作。

冲突响应返回当前版本和安全差异信息，客户端保留草稿并重新判断。字段编辑可以三方合并，状态命令通常刷新后要求用户重新确认。服务端版本比较与写入必须原子，先查再写两次请求仍会竞态。

### 五、唯一约束与事务是服务端最后防线

幂等键的唯一索引、业务自然键和版本条件应由存储原子保证。仅在进程内 Map 或“先 select 再 insert”无法抵御多实例并发。状态变更、幂等结果、审计事件和 outbox 若属于同一事实边界，应在同一事务提交。

事务失败意味着其中任何一步都不应对外可见；提交成功后响应失败属于未知结果。代码要把这两类区分。捕获唯一冲突时读取已有记录并比较载荷，而不是无条件当成功。

长事务会持锁并扩大故障面。跨外部系统不可能纳入本地 ACID 事务，需要状态机和可靠消息协调。不要用分布式锁掩盖错误对象边界，锁本身还有过期、脑裂和所有权问题。

### 六、Outbox 解决状态已写但消息未发

应用若先更新订单再发送消息，中途崩溃会让下游永远不知道；先发消息再提交订单则可能通知不存在的事实。Transactional Outbox 把业务状态与待发送事件在同一数据库事务写入，独立发布器稍后发送并标记。

发布器可能在发送成功、标记之前崩溃，因此消息仍可能重复。消费者用 eventId 幂等，且按对象版本拒绝旧事件覆盖新状态。Outbox 提供至少一次传递与可恢复证据，不自动提供全局恰好一次。

监控未发布最老年龄、重试次数和死信；保留策略不能早于所有消费者恢复窗口。事件 Schema 与业务状态版本一起演进，敏感内容最小化。

### 七、最终一致性必须有截止、查询和用户语义

**最终一致性（Eventual Consistency）**表示没有新更新时，各副本在某个条件下收敛。它不是“迟早会好”的借口。设计必须说明哪些视图暂时旧、正常延迟预算、如何检测偏差、超过截止怎样补偿或告警、用户看到什么。

例如订单已支付但搜索索引稍后更新，详情可读主存储显示最新事实，列表标记“同步中”；若十分钟仍未收敛，后台对账重放事件并告警。对于余额或权限等高风险事实，不应让陈旧副本决定关键写入。

读取自己写入可通过路由主存储、版本令牌或短期会话覆盖实现。界面不要在一个区域显示成功、另一区域无任何解释地显示旧值。展示“正在同步”并提供刷新/查询，让暂时差异可理解。

### 八、补偿是新业务动作，不是时间倒流

**补偿（Compensation）**在原副作用已经发生后执行反向或修正业务动作，例如退款、释放预留、撤销积分。它有自己的权限、幂等键、失败和审计，不保证把世界恢复到从未发生的状态：邮件已被阅读、汇率已变化、库存可能被他人占用。

Saga 把跨服务流程拆成步骤及对应补偿。编排式由中心状态机决定下一步，可观察但中心复杂；协同式由事件驱动，耦合较松但全局路径难追踪。无论形式，都要持久化流程实例、当前步骤、尝试和截止时间。

补偿也会超时和重复。先查询原步骤和补偿意图，使用稳定 key，失败进入重试或人工处理。不要因补偿失败就重复原动作，也不要用数据库手工改状态掩盖外部事实。

### 九、重试需要预算、退避与副作用知识

自动重试只用于被分类为暂时、且操作幂等或有去重保护的失败。采用指数退避、随机抖动、最大尝试和总时间预算，遵守服务端 Retry-After。大量客户端同步立即重试会形成雪崩。

重试发生在哪一层要明确。SDK、网关、服务和任务队列都重试时，3×3×3 会放大为 27 次。选择拥有足够语义的一层，向下传递 attempt 与 key，并让上层知道结果仍未知。

熔断器可在依赖持续失败时快速拒绝，限流保护容量，超时限制等待；它们不证明业务未执行。恢复探测和半开策略要有指标，不能把所有错误永久熔断。

### 十、消息处理要区分传输与业务语义

消息 broker 的确认表示传输系统接收或消费者处理到某阶段，不等同业务恰好一次。消费者在事务中记录 eventId 与业务变更，重复消息返回已处理；处理失败不确认或进入受控重试。

顺序只在协议承诺的分区/流内成立。对同一对象带 sequence/version，缺口时暂停、查询快照或补洞；不同对象不必全局排序。旧事件到达时不得回滚新状态。

毒消息是确定性无法处理的输入，永久重试会阻塞队列。经过有限尝试进入死信，保留 Schema 版本、错误和恢复工具；修复后重放仍需幂等。权限和隐私规则也适用于死信存储。

### 十一、界面应呈现确定性与恢复责任

pending 显示操作正在确认且防止误触；unknown 明确“尚未确认结果”，提供查询或稍后查看；conflict 保留输入并展示新事实；partially completed 列出已成功与未处理项。不要把所有状态压成 spinner/toast。

用户重复点击时，界面关联同一意图而不是生成多个独立卡片。刷新和换设备后从服务端操作记录恢复。高价值动作提供可复制的业务参考号，但不暴露内部敏感 ID。

撤销若只是短期延迟提交，可以在窗口内取消；若原动作已生效，则撤销触发补偿。文案必须区分，避免用户以为世界已瞬间回滚。

### 十二、对账是跨系统一致性的最后闭环

即使在线流程设计正确，未知故障和人工操作仍会造成偏差。周期性对账按稳定业务键比较本系统、支付方、消息日志和下游结果，分类缺失、重复、金额不符与状态不符，并生成可审计修复任务。

对账脚本也要幂等、限速和最小权限。自动修复只处理规则明确、风险低的差异；高价值异常进入人工审批。修复后再次对账，不能只修改一张表就关闭事件。

指标包括 unknown 停留时间、幂等命中/冲突、412 比例、outbox 年龄、死信、补偿失败和对账差异。告警连接具体恢复手册，而不是只有错误数量。

### 十三、验证用故障矩阵证明收敛

为每个写操作注入：请求到达前断线、提交前崩溃、提交后响应前断线、重复并发、旧版本、消息发送前后崩溃、重复/乱序消息、依赖超时和补偿失败。记录业务行数、版本、幂等表、outbox、下游效果与 UI。

性质测试可以表达“相同 key 重放任意次只产生一个业务效果”“对象版本单调增加”“不同租户 key 不共享”“旧事件不能回退状态”。集成测试证明数据库原子约束，端到端测试证明用户不会因 unknown 被诱导产生新意图。

负载与混沌测试要有安全边界，先在隔离环境用可清理数据；结论附带时间线和版本。只看最终页面“好像一样”不足以证明没有重复副作用。

### 十四、常见反例与适用边界

- 504/网络错误直接判定写入失败，重试时生成新业务意图。
- 用按钮禁用代替服务端幂等，用幂等键代替版本检查。
- 幂等记录只存在单进程内，或同键不同载荷仍复用结果。
- 宣称 broker、事务或框架提供“恰好一次”，没有业务效果证据。
- 最终一致没有延迟预算、查询、补洞、补偿和用户提示。
- 补偿失败后手工改库，却不核对外部副作用。

纯读取和本地无副作用计算通常不需要完整恢复协议，但仍要处理缓存与取消。越接近资金、库存、权限和不可逆外部动作，越需要稳定意图、状态查询、审计和对账。

时间也是一致性输入。幂等保留期、租约、退避和补偿截止应使用单调计时或可信服务端时间；客户端时钟只用于展示。跨区域系统不能假设两个节点时间完全相同，排序优先使用对象版本、序列或数据库提交标记。测试冻结时钟并覆盖恰好到期、跨时区和夏令时边界，避免同一意图在边界两侧被当成两次新操作。

恢复工具的每次人工决定也写入同一审计链，并要求再次对账确认修复真的收敛。

### 十五、学完后应能说明

你应能把错误分成可修正、可重试、冲突与未知结果；设计幂等记录和条件写入；解释 outbox、至少一次投递、最终一致与补偿的边界；为 UI 提供明确恢复状态；并用故障注入、性质测试和对账证明重复、乱序、崩溃后系统仍收敛到一个可解释事实。

继续查证可参考 [RFC 9110 幂等方法](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods) 和 [RFC 9110 条件请求](https://www.rfc-editor.org/rfc/rfc9110.html#name-conditional-requests)。

# 职业表达知识点讲义

## CAREER-04 从用户影响走到恢复与复盘

告警消失了，用户却仍然打不开统计面板；回滚命令成功了，旧页面还是请求一个已经被删除的文件。这些情况说明：执行了操作，和恢复了用户任务，是两件需要分别确认的事。

事故响应要在不完整的信息下协调行动，先降低当前影响，再继续弄清原因。复盘则把当时的条件、证据和决定保存下来，改变下一次的处理能力。这篇用一份完整的模拟记录，连接这两个过程。

### 学习前先确认

- 直接前置：[DEBUG-01 用证据缩小问题](../chinese-guides/debug-01-systematic-debugging-evidence-causality.md#debug-01)。本讲直接使用事实与假设分离、单变量观察和版本定位。

**下文 INC-DEMO-12、版本 v41/v42、时刻与角色都是教学模拟，不代表当前系统发生过事故。** 练习只进行桌面推演，不要求在生产环境注入故障。先读到当时的证据，再决定下一步，避免拿事后已知答案评价最初判断。

### 用用户任务描述事故而不是复述告警

本例的背景是：资料工作台的统计代码按需加载。10:00 发布 v42；有些用户仍开着 v41 页面，直到点击统计时才请求 v41 对应的 JS 文件。

10:05，前端错误告警出现。此时一个合格的初始事件卡可以写成：

| 字段 | 10:05 时已知内容 |
| --- | --- |
| 事件 | INC-DEMO-12，旧页面打开统计失败 |
| 发现来源 | 前端资源加载告警与一条支持反馈 |
| 已知影响 | 已确认一名保持旧页面的用户无法打开统计；列表读取暂未发现异常 |
| 范围未知 | 是否影响所有旧页面、是否有保存问题、是否所有区域都受影响 |
| 近期变化 | 10:00 发布 v42，尚未确认与故障的因果关系 |
| 当前动作 | 核对页面版本、失败资源和对应响应，暂缓非必要发布 |

“全站故障”超出了现有证据，“只有一个用户受影响”也超出了证据：确认了一例不等于总体只有一例。初始描述可以不完整，但必须让已知与未知分开。

**严重度（severity）**决定协调规模、升级和更新频率。没有所有公司的统一数字规则。本例把“部分已登录用户的统计任务不可用”作为当前范围，由值班约定决定级别；若随后发现保存丢失或影响范围扩大，再记录理由并升级，不为了守住最初标签缩小影响。

### 分配角色以减少互相干扰的操作

小事故不一定需要很多人，但需要有人明确负责协调、执行、沟通和记录。一个人可以兼任，责任不能消失。

| 角色 | 本例的主要工作 | 容易混淆的边界 |
| --- | --- | --- |
| 协调负责人，也称 incident commander | 确认当前目标、分配动作、决定升级与交接 | 不必亲自执行每条命令 |
| 操作负责人 | 核对文件与版本、提出并执行缓解、报告观察 | 不在他人未知时同时改变多个变量 |
| 沟通负责人 | 更新用户影响、替代路径和下一更新时间 | 不把猜测原因写成定论 |
| 记录负责人 | 保存时间、动作、执行者、结果与来源 | 不只保留群聊中的最后结论 |

例如前端负责人说“我来回滚”，发布负责人同时说“我先清缓存”，两者叠加会让恢复原因和副作用都难判断。协调者应先确认一个动作的对象、可逆性和观察信号；可以并行读取证据，但可能互相影响的变更需要安排先后。

建立一个事件文档与主要协调入口，关联监控、版本和现场。新的领域专家加入后先获得当前摘要；多个告警是否属于同一事件，要看共同依赖的证据，不因时间接近就强行合并。独立事件可以分别指挥，争用人员时再协调资源。

### 先保存会被后续操作改变的证据

旧页面一旦刷新，现场可能变成 v42，原先请求 v41 文件的情况就消失了。因此本例先保存页面版本、失败资源路径、响应状态和触发步骤，再考虑操作。

| 观察 | 当时可以写下的事实 | 尚不能下的结论 |
| --- | --- | --- |
| 保持打开的 v41 页面请求 v41 统计文件得到 404 | 该入口当时无法取得指定资源 | 所有 CDN 节点都丢失文件 |
| 新打开的 v42 页面可进入统计 | 新页面路径在这次观察中正常 | 所有新用户功能都正常 |
| 资料 API 请求仍返回预期结果 | 被检查的接口路径正常 | 数据整体完整、所有写入都正确 |
| 发布脚本包含旧文件清理步骤 | 存在可能相关的变化 | 这个步骤一定造成全部影响 |

实际记录还应带时区、版本标识和来源。客户端时钟与服务端日志可能有偏差；顺序不清楚时先标待校准，不把近似时间拼成精确的因果链。

保存证据不等于广泛复制日志。使用能证明问题的最少字段，移除 Cookie、令牌和用户输入；公开说明可以引用“旧页面请求历史资源返回 404”，不需要暴露内部路径与私人记录。

### 比较缓解动作时同时看收益和代价

**缓解（mitigation）**先减少当前影响，不要求已经完整解释根因。本例在 10:10 获得进一步证据：v41 资源在来源存储中被清理，历史制品仍完整保留。此时可以比较：

| 候选动作 | 可能作用 | 本例必须核对的代价 |
| --- | --- | --- |
| 让新入口回到 v41 | 新打开页面改用旧版本 | 若 v41 文件仍缺失，新入口也可能失败 |
| 恢复缺失的 v41 原始资源 | 已打开旧页面可以继续请求它需要的文件 | 必须来自对应制品，核对内容摘要、访问路径与缓存响应 |
| 通知所有用户刷新 | 部分页面可能转到 v42 | 可能丢失未保存草稿，且把恢复责任推给用户 |
| 清空所有缓存 | 可能改变缓存命中 | 不会凭空恢复来源存储中的文件，还可能增加负载 |

本例选择恢复经核对的 v41 原始资源，同时保留 v42。这是已知条件下的决定，不是所有前端事故的通用答案。恢复后还要核对曾缓存 404 的路径是否继续返回错误，按目标范围处理缓存，不能假定“源站有文件了”就代表所有访问已恢复。

恢复旧文件也不是把新代码改名成旧 hash。文件名与内容对应关系必须成立，否则缓存和依赖可能继续混用。版本与旧资源共存的机制见 [ENG-02](../chinese-guides/eng-02-dev-production-environments-assets-cache.md#发布新版本时旧页面仍可能需要旧文件)。

每个操作记录预期信号与停止条件。例如恢复后目标路径仍 404，先查分发与响应链，不继续盲目重试全局操作；若出现新的写入异常，优先扩大影响调查，不能只盯统计页面。

### 用事实时间线保留决定发生时的信息

以下是本例完整的模拟记录。10:02 的最早失败时刻来自后来回查，不能写成值班者当时就已经知道。

| 时刻，统一为 UTC+08:00 | 事件与依据 | 当时的决定或状态 |
| --- | --- | --- |
| 10:00 | 发布记录显示 v42 生效 | 常规发布结束 |
| 10:02 | 后续回查定位到最早一条可确认的 v41 资源失败 | 当时尚未告警；不是完整总体影响起点的证明 |
| 10:05 | 告警与支持反馈 | 开始核对用户影响 |
| 10:07 | 旧页面复现，v42 对照正常 | 建立事件角色，暂停非必要发布 |
| 10:10 | 制品与存储清单对照确认 v41 资源被清理 | 选择恢复历史资源，保留现场 |
| 10:12 | 对应原始文件恢复，记录摘要与操作结果 | 开始核对分发与用户任务 |
| 10:16 | 保持打开的旧页面和新页面均完成统计路径，目标错误指标回落 | 进入恢复观察 |
| 10:26 | 约定观察窗口内关键路径与指标保持稳定，保存抽查无异常 | 确认已核对范围恢复，复盘与后续动作继续 |

这种时间线同时保留事实、证据和决定。若后来发现 10:01 已有失败，可以追加修订依据；不要不留说明地覆盖旧的认知。因果图和用户影响区间也随证据更新。

### 状态更新先回答用户此刻关心什么

内部协作需要候选假设和操作细节；用户需要知道哪些功能受影响、正在处理什么、是否需要自己操作、何时会有下一条消息。

下面是本例 10:10 可用的**模拟状态说明**，仅供学习写法：

> 我们确认部分保持旧页面的用户无法打开统计面板，正在恢复相关历史资源。暂未发现资料列表受同一问题影响，保存功能仍在核对中。请先保留当前页面和未保存内容；我们将在 10:20 前更新进展。

这段话承诺下次更新时间，没有编造恢复时间。即使到 10:20 尚未恢复，也应该按承诺说明已完成动作和剩余问题。根因未知不妨碍报告用户影响；外部供应商说已恢复，也不能替代自己的关键任务核对。

若确实需要用户重新登录或刷新，应先说明未保存内容如何处理，并提供适用范围。不能把“用户刷新后好了”当作服务已经恢复的全部依据。对外更新应由明确角色负责，避免不同人员同时给出互相矛盾的解释。

### 恢复确认要穿过三个观察层次

本例的恢复记录不能只写“复制文件成功”。至少需要把下面三层连接起来：

1. **技术状态**：对应版本文件可访问，内容与历史制品一致；目标错误率在有请求的窗口内恢复。无流量时没有错误，不算恢复证据。
2. **用户任务**：保持旧页面的用户路径与新打开页面都能进入统计；失败后的反馈与重试也符合预期。
3. **数据与范围**：抽查读写结果，核对是否存在未知提交或草稿损失；注明样本与仍未覆盖的范围。

本例中“保存抽查无异常”只支持被抽查的路径，不能自动变成“没有任何数据损失”。若事故涉及写操作，可能需要按业务记录核对不变量、重复提交和补偿；涉及备份时，应在隔离环境实际恢复并验证数据，而不只是看到备份文件存在。

恢复后保留观察窗口、指标与负责人。缓解、恢复、根因修复和事件关闭可以采用团队约定的状态，但必须说明每个状态需要什么证据。用户功能恢复了，长期修复还未完成，这两个事实可以同时成立。

浏览器检查与真实持久化分别证明什么，可回到 [TEST-03](../chinese-guides/test-03-e2e-visual-regression-isolation-flakiness.md#端到端先说明穿过哪些真实边界)。

### 复盘解释条件组合而不止寻找最后一个人

**无责复盘（blameless postmortem）**把当时可用的信息、工具和约束放回分析中。它不免除行动项责任，也不把“人犯了错”作为分析终点。

本例的因果解释可以分成四部分：发布清理是触发；清理规则没有考虑旧页面的延迟加载，是促成条件；发布检查只打开新页面，是检测缺口；历史制品保留且恢复路径可用，是帮助缓解的条件。

“发布者不够认真”无法说明为什么规则允许删除仍会被请求的资源。“加强测试”也不够具体，因为团队可能再加十条新页面用例，仍然漏掉旧页面。要寻找的是哪些条件使错误容易发生、难被发现或难以恢复。

恢复资源后现象消失是有价值的证据；为了确认机制，还可以在隔离环境重现“旧页面保持打开 → 发布清理 → 延迟请求失败”。不要在生产反复制造故障来追求漂亮的因果证明。对应架构需保留事故时版本，参见 [CAREER-02](../chinese-guides/career-02-architecture-diagrams-boundaries-adrs.md#迁移过程也需要可阅读的中间态)。

### 行动项需要能判断完成的结果

一项有效的改进应说明改变什么、谁负责、何时验收、如何证明，以及暂未完成期间的残余风险。下面的负责人和期限也属于模拟安排。

| 行动 | 模拟责任与期限 | 验收证据 |
| --- | --- | --- |
| 调整历史资源清理策略 | 发布负责人，下次发布前 | 记录保留条件与清理依据；旧页面所需文件在约定支持窗口内可取 |
| 增加跨版本关键路径 | 前端负责人，下次发布前 | 保持旧页面后发布，再触发延迟功能；被清理的故障对照失败，修复后通过 |
| 补充资源恢复手册 | 值班负责人，本周内 | 另一名值班者可在隔离环境按手册找到制品、核对摘要并恢复访问 |
| 改善版本维度告警 | 可观测性负责人，两周内 | 能区分页面版本与失败资源；告警有真实任务与流量依据 |

不要凭空定“永久保留所有文件”，也不要只写“保留两天就够”。资源保留窗口要结合页面存活、缓存、支持范围、容量和恢复约定决定。临时人工保护可以先落地，长期策略另有负责人。

优先处理最能减少复发或缩短恢复的少量动作。每项都做成大平台，会让事故复盘变成新的积压。跨团队行动需要对方接受责任，不能单方面把名字写进表里就宣布闭环。

### 事故时长先定义起点终点再计算

“恢复用了多久”可能从首次用户影响、告警、响应开始或执行操作开始计时。本例能精确算出记录中的差值，却不能据此推断完整用户群的真实影响时长。

```js example=career04-duration
const at = (time) => Date.parse(`2026-09-12T${time}:00+08:00`);
const minutes = (start, end) => (at(end) - at(start)) / 60000;
console.log(minutes('10:02', '10:05'));
// => 3
console.log(minutes('10:05', '10:16'));
// => 11
console.log(minutes('10:02', '10:16'));
// => 14
console.log(minutes('10:16', '10:26'));
// => 10
```

这里依次是记录中的首次失败到告警、告警到进入恢复观察、首次失败到进入恢复观察、恢复观察窗口。确认时间是 10:26，不应悄悄替换 10:16 以得到想要的指标。团队使用 MTTR 等缩写时，也要先写清定义和统计人群。

指标用于发现检测、召集、判断、执行或验证哪个环节最慢，不应用于惩罚更早报告问题的人。少量事故的平均数可能很不稳定；还要关注相似故障复发、行动项有效性和近失事件，而不只看一条下降曲线。统计口径可继续读 [CAREER-01](../chinese-guides/career-01-project-evidence-causal-storytelling.md#数字先写口径再计算比例)。

### 交接与演练要减少对某个人的依赖

交接包至少包含当前影响、已做动作及结果、开放假设、下一步、禁止重复的风险操作和联系入口。接班人复述后再接管，比一句“看群记录”更可靠；长时间事故也需要休息与轮换。

平时用桌面推演检查角色、权限和信息流，用隔离环境验证具体恢复步骤。自动回滚或扩容还需要触发条件、动作上限、冷却、审计和停止方式；执行返回成功后仍要核对用户结果。模拟监控缺失或部分成功，才能看到自动化是否会在错误信号下扩大影响。

近失事件同样值得轻量记录。例如旧资源即将被清理，但人工提前发现：用户没有受影响，不代表防线已经可靠。按潜在影响安排改进，不必把每个小告警写成长篇复盘。

涉及安全、隐私或证据保全时，由相应负责人进入专门流程；不要凭一般恢复经验销毁日志或随意轮换所有凭据。本讲不制定法定通知期限。AI 可以整理去敏时间线与候选缺口，但不能据缺失日志补造事实、擅自执行恢复或对外发布消息。

### 让复盘进入下一次真实变更

复盘文档可以按影响、事实时间线、缓解、恢复依据、条件分析、行动与未知组织。技术细节面向需要它的人，对外版本聚焦用户影响和已实施改进，不展示私人输入或内部敏感信息。

当清理策略的 PR 出现时，评审者应能沿事件记录找到原来遗漏的条件；当行动项标为完成时，应能看到对应验证，而不只是“手册已写”。具体评审表达见 [CAREER-05](../chinese-guides/career-05-code-review-risk-communication.md#评论要把触发条件与修改请求连起来)。

复盘的价值来自下一次决策发生变化：旧页面被纳入检查，恢复入口能由其他人执行，风险在发布前被看见。没有资源或不再适用的行动项也应明确决定，不能长期静默挂起。

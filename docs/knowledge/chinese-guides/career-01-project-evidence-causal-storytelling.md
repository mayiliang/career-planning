# 职业表达知识点讲义

## CAREER-01 把项目经历讲成有依据的判断

“负责 React 项目开发，使用 TypeScript，优化性能 40%。”这句话看起来完整，听者却很难知道：什么变快了，40% 怎样算，你具体负责哪一步，结果有没有其他解释。

项目表达的任务，是让不在现场的人理解问题、判断和证据。它不要求每个项目都有惊人的指标，也不要求把所有工作包装成个人主导。这篇用一组明确标注的模拟材料，演示从零散记录到简历、口头陈述和深入追问的整理过程。

### 学习前先确认

本讲没有硬性前置。可以先读例子，再选择一个自己真实参与的项目练习。定义、证据强弱、指标口径和个人贡献都会在正文解释。

**本篇所有“资料后台 A”的事件、数字、角色和编号均为教学模拟，不来自当前项目的实测业绩，也不是可直接套用的个人经历。** 示例中的资料编号只用于互相回指；整理自己的项目时，要替换成真实、允许使用的材料。没有材料支持的字段保留未知，不补造内容。

### 先说清谁遇到了什么问题

项目背景不需要从公司历史讲起。先让听者知道用户、任务和阻碍，再说明为什么值得处理。

下面两句话涉及同一个模拟项目：

| 表述 | 听者能得到什么 |
| --- | --- |
| 使用 React、Vite 和代码分割优化后台 | 知道工具名称，不知道问题发生在哪里 |
| 运营人员每天从资料列表进入工作台，首屏同时下载了只有打开统计面板才会使用的图表代码 | 知道受影响任务和一个可调查的机制 |

第二句话还不是因果结论。“同时下载图表代码”需要网络记录或构建图支持；它也不自动证明图表代码造成了全部等待。先把问题写成可观察现象，再说明如何判断原因，顺序才不会倒过来。

如果任务原本是统一技术栈，就如实写组织目标和迁移约束；不要事后编出一场不存在的用户事故。小型个人项目也可以围绕一个明确能力目标展开，例如“验证保存失败后草稿能否恢复”，不需要虚构日活用户来增加分量。

### 用资料台账把回忆与证据分开

**证据链（evidence chain）**把一个主张连接到支持它的材料以及材料的限制。先收集事实，再决定最后讲什么，避免为了保住一句漂亮的话反过来挑材料。

以下是贯穿本讲的完整模拟材料摘要：

| 编号 | 模拟材料内容 | 它能支持什么 | 不能独自支持什么 |
| --- | --- | --- | --- |
| E1 | 需求记录：运营反馈首次进入资料列表等待明显；两周内交付，可改前端，不能更换业务后端 | 当时的问题、范围与期限 | 等待的唯一根因 |
| E2 | 网络与模块图记录：统计依赖处于首屏静态可达集合，尚未打开统计面板已加载 | 候选机制与优化位置 | 真实用户体验改善幅度 |
| E3 | 评审记录：比较整体重写、预加载、按需拆分；决定先拆统计模块并保留失败恢复 | 候选方案、理由与参与者 | 决定一定正确 |
| E4 | 同入口、同工具与配置下，两份构建清单统计的首屏静态可达 JS gzip 总大小为 1200 KiB 与 720 KiB | 按这个口径减少了 480 KiB，即 40% | 所有资源、所有路由或所有用户都快 40% |
| E5 | 前端 PR、评审与交付记录：小林调查模块关系、参与方案比较，实现拆分、加载失败反馈和验证；同事完成发布配置检查 | 个人动作与交接点 | 小林独立完成整个项目 |
| E6 | 发布前后各一周，同一路由的用户监控显示 p75 LCP 为 3.4 s 与 2.5 s；同期有 CDN 调整，用户网络分布也变化 | 观察窗口内指标随发布发生变化 | 0.9 s 全部由前端拆分造成 |
| E7 | 实验记录：直接预加载没有减少首屏所需字节，团队停止该尝试 | 假设如何被证据修正 | 所有预加载方案都无效 |
| E8 | 发布前本地运行记录：统计面板按需出现；模拟资源故障有恢复提示；未评估转化率 | 验证过的行为与未验证范围 | 已提升转化率或完成所有生产风险验证 |

台账中的“不能证明”不是额外道歉，而是决定措辞的重要信息。PR 证明改过代码，发布记录证明它进入某个版本，用户监控描述某段时间的观测；不同材料不要互相替代。

整理自己的台账时可以加上实际日期、链接、版本、所有者和公开范围。尚未找到来源的内容标为“个人回忆，待核对”，不要给模糊记忆补一个精确时间戳。材料越贴近当时现场，越容易减少事后重构故事的偏差。

### 时间线先检查故事能否成立

按先后关系排列模拟材料，得到：问题记录 E1 → 机制调查 E2 → 方案评审与失败尝试 E3/E7 → 实现与构建对照 E4/E5 → 发布 → 用户观测 E6。E8 是发布前的本地行为核对，不能写成已经完成生产巡检。

一条简单时间线就能发现很多问题。假如后来找到的记录显示 LCP 已在前端拆分发布之前改善，就必须撤回“拆分带来这次改善”的原说法，再核对 CDN 调整、采样窗口和版本信息。不能为了故事顺畅，把变化时间悄悄挪到发布以后。

这里还要区分提交时间和实际发布：提交可能很早，灰度可能很晚；用户访问的也可能是旧页面或旧资源。版本到访问的连接可以参考 [ENG-02](../chinese-guides/eng-02-dev-production-environments-assets-cache.md#发布新版本时旧页面仍可能需要旧文件)。

发现矛盾后，先保留冲突材料，列出可能解释，再缩小结论。如果不能确认准确时间，可以写“参与了该阶段实现，现有资料不足以确认它与指标变化的先后关系”。承认依据不足比继续维护一个无法成立的因果顺序更可靠。

### 约束和备选方案让技术选择有解释力

方案好不好，要放回当时的限制。模拟案例只有两周，可以改前端，却不能重写业务服务；团队还需要确保统计功能仍能访问。这些条件使“小范围拆分并补加载反馈”成为可讨论的选择。

| 模拟候选 | 可能收益 | 成本或未解决的问题 | 当时的决定 |
| --- | --- | --- | --- |
| 整体重写工作台 | 可重新设计大量边界 | 范围超出两周期限，回归面大 | 暂不采用 |
| 提前预加载统计代码 | 可能缩短之后打开统计的等待 | 未减少首屏字节，不符合当前首要问题 | 按 E7 停止该尝试 |
| 统计模块按需加载 | 减少首屏静态可达代码 | 增加首次打开等待与失败处理 | 采用并核对相关行为 |

这里不能说“按需加载永远优于预加载”。如果统计面板是多数用户进入后的第一步，两种方案的价值就可能改变。表达取舍时说明谁先受益、代价落在哪里、什么信号会让你重新选择。

重要决定可以整理成简短 **ADR**：背景、候选、决定、理由、后果和回顾条件。它帮助表达当时如何判断，不是替决定盖一个永久正确的章。架构表达的完整组织方法可继续查 [CAREER-02](../chinese-guides/career-02-architecture-diagrams-boundaries-adrs.md#career-02)。

### 个人贡献用动作和交接点说明

“参与”“负责”“推动”“主导”包含不同强度的主张。先写清实际做过的动作，再选择合适动词，不要先挑最有分量的词。

在模拟案例中，小林可以说明自己检查模块图、实现动态导入、补加载失败反馈并完成构建对照；发布配置由同事核对，CDN 调整由另一团队完成。团队指标应写成团队观察到的结果，再解释自己的工作在哪个环节产生作用。

| 含糊表达 | 更容易核对的表达（动作须有自己的记录支持） |
| --- | --- |
| 我主导了性能全面优化 | 我负责统计模块拆分与前端验证，参与发布方案评审 |
| 我推动了多个团队合作 | 我整理请求与版本证据，组织前端和发布负责人确认接口及资源保留窗口 |
| 我解决了所有线上问题 | 我修复了这类资源加载失败的反馈，并验证列出的成功与故障路径 |

“推动”应能说出改变了什么：共同事实变清楚、接口责任确认、候选方案被比较、某个阻塞有了负责人和截止时间。会议数量或消息数量不能直接证明推动效果。

提交署名也不等于设计的全部所有权，评审意见和结对工作同样重要。若不同阶段角色变化，按时间说明；若后续指标由别人继续优化取得，不把后来的数字算到自己的交付阶段。

### 数字先写口径再计算比例

模拟材料 E4 的 40% 是文件大小减少比例，计算方式为 `(1200 - 720) / 1200`。它没有测量页面总下载、用户等待或业务转化。表达时保留“首屏静态可达 JS”“gzip”“同入口”的范围，不能缩成含义不明的“性能提升 40%”。

```js example=career01-artifact-ratio
const beforeKiB = 1200;
const afterKiB = 720;
console.log(beforeKiB - afterKiB);
// => 480
console.log(((beforeKiB - afterKiB) / beforeKiB * 100).toFixed(1) + '%');
// => 40.0%
```

数字还需要定义、样本、窗口和来源。错误率以请求、会话还是用户为分母，构建时间是否热缓存，p75 按什么人群采样，都可能改变结论。不要把平均数、分位数、实验室数据和真实用户数据混成一条趋势。

再看一组独立的模拟计数：前期 100 次操作中失败 5 次，后期 50 次中失败 2 次。失败次数减少 60%，却不等于失败率减少 60%。

```js example=career01-rate-denominator
const before = 5 / 100;
const after = 2 / 50;
console.log(`${(before * 100).toFixed(1)}% → ${(after * 100).toFixed(1)}%`);
// => 5.0% → 4.0%
console.log(((before - after) * 100).toFixed(1) + ' 个百分点');
// => 1.0 个百分点
console.log(((before - after) / before * 100).toFixed(1) + '%');
// => 20.0%
```

这是算术示例，样本很小，不能凭这几个计数证明总体风险已经下降。相对变化与百分点变化都能用，但要明确分母，并避免从简单前后对比跳到统计或因果结论。

没有可靠数字时，写可观察变化也有价值。例如“保存失败后保留草稿并提供重试；组件和浏览器路径分别验证”，比编造“满意度提升 30%”更可信。验证实际停在哪里，参见 [TEST-03](../chinese-guides/test-03-e2e-visual-regression-isolation-flakiness.md#端到端先说明穿过哪些真实边界)。

### 相关贡献与因果不要用同一种语气

发布后指标改善，首先是一个时间上的相关观察。**因果（causality）**进一步主张：某个动作使结果发生变化。**反事实（counterfactual）**则问：如果没有做这个动作，结果会怎样。

模拟案例 E4 有明确机制与受控构建对照，可以支持“拆分减少了该口径下的首屏字节”。E6 的 LCP 同期还受 CDN 和用户网络分布影响，证据不足以把全部 0.9 s 改善归给拆分，更不能据此推断转化率。

| 证据状态 | 合适的表达强度 |
| --- | --- |
| 只有个人回忆 | 我记得当时有这个现象，具体幅度尚未核对 |
| 当时记录确认动作发生 | 我完成了拆分和相关验证 |
| 相同输入的受控对照支持机制 | 对照显示该入口的首屏静态可达字节减少 |
| 发布前后观察，同时存在其他变化 | 发布后指标改善，前端拆分可能有贡献，无法单独归因 |
| 有可靠对照并核对关键假设 | 在这些实验条件下，结果支持该动作的影响 |

分组实验、渐进发布或回退对照可以增强判断，但各自有适用假设与限制。没有对照并不意味着经历不能写，只意味着要使用与证据匹配的语气。计划阶段的预测收益，也不能在结项时自动变成已取得结果。

不要给证据机械排一个从“截图最弱”到“监控最强”的统一榜单。监控适合描述用户分布，代码差异适合确认实现，受控运行适合解释机制；证据强弱首先取决于它是否回答当前主张。

### 同一事实可以压缩成不同长度

**STAR** 将背景、任务、行动与结果组织成便于听者跟随的顺序。它解决表达顺序，不会自动补齐证据。下面都来自前面的模拟台账，不能当作自己的简历事实直接使用。

**模拟简历版本：**

> 面向资料工作台的首屏加载问题，负责统计模块按需拆分与加载失败恢复；在同入口、同构建口径下，将首屏静态可达 JS 的 gzip 总大小从 1200 KiB 减至 720 KiB，并核对统计打开与故障反馈路径。

这个短版只使用 E1、E2、E4、E5、E8 支持的内容，没有借 E6 宣称全部真实用户收益。如果空间不够，宁可删掉次要技术名词，也保留指标定义和个人动作。

**模拟口头版本：**

> 资料工作台的用户主要先处理列表，统计功能并不是每次都会打开，但原先统计依赖已经在首屏加载。我们只有两周，不能重写后端，所以我先检查网络和模块关系，再比较预加载与按需拆分。预加载没有解决首屏字节的问题，最终采用统计模块按需加载，并补上加载失败后的提示。
>
> 我负责前端实现和验证，发布配置由同事配合核对。相同构建口径下，首屏静态可达 JS 的 gzip 总大小从 1200 KiB 降至 720 KiB。发布后用户监控也有改善，但同期还有 CDN 调整和网络分布变化，我不能把全部 LCP 改善归给这项工作。我的直接证据是构建清单、请求变化、行为验证和对应 PR。

更长的陈述可以在这条主线上展开候选方案、一次失败尝试、观察条件和下一步实验，而不是把技术栈全部塞进去。把时长当作信息预算：短版交代问题和贡献，追问再打开机制与附件。并不存在说够某个分钟数就一定有说服力的规则。

### 追问时沿机制展开而不是新增事实

深度来自能把现象、机制、动作和证据连起来。模拟案例可以按这个顺序回答：静态可达关系为什么导致提前下载 → 动态导入怎样改变加载边界 → manifest 和 Network 如何核对 → 哪些样式和错误路径仍要保留。机制详见 [ENG-01](../chinese-guides/eng-01-module-graph-build-output-source-maps.md#chunk-的边界要到浏览器里观察)。

| 追问 | 基于同一模拟材料可以怎样回答 |
| --- | --- |
| 为什么不直接换框架 | 当时主要问题是统计依赖进入首屏，期限与后端边界不支持整体重写，E3 记录了比较 |
| 怎么证明不是只改了截图 | E4 有构建清单口径，E8 有打开与故障行为；截图只补充当时外观 |
| LCP 改善全是你做的吗 | 不能这样判断，E6 明确存在 CDN 与人群变化 |
| 如果多数用户立刻打开统计呢 | 当时没有这份人群证据；需要测首次打开等待，再比较预加载与拆分成本 |
| 如果结果没有改善，还能写什么 | 可以说明被排除的假设、停止决定、保留下来的可复现观察方法 |

“当时未验证，我会这样补证据”是合理回答。不要把现在的推演说成过去真实发生过的实验。对方提出替代方案时，先确认约束是否相同；如果当时确实判断错了，说明错误假设如何被发现，而不是把每个选择都辩护成最佳。

### 失败尝试事故与协作都可以形成主线

失败尝试的价值在于改变了判断。模拟 E7 说明某种预加载没有解决当前目标，所以团队停止投入；它不能被写成“预加载技术没有价值”。保留当时假设、观察和停止标准，听者才能看出你怎样更新认识。

事故故事则先讲用户影响、发现、缓解、恢复验证，再说明触发原因、促成条件和检测缺口。不要把通宵时长当成主要贡献，也不要把复杂系统问题归结为某位同事不认真。修好一个异常页面还需核对相关数据与任务，不能只看监控回绿。更完整的事故组织可参考 [CAREER-04](../chinese-guides/career-04-incident-response-postmortem-learning.md#career-04)。

跨团队故事可以围绕词义、接口、所有权和节奏如何对齐展开。例如前端与发布团队对“上线完成”的理解不同，你提供了新旧资源需要共存的请求证据，促成保留窗口和负责人确认。采用别人的方案也能体现协作判断，价值不在于自己的意见赢了。

被取消或没有上线的项目仍可说明目标、验证、停止和可复用结论。不要把失败重新命名成胜利，也不必因为没有漂亮终点就抹掉有依据的工程动作。

### 给不同听者调整信息层次

招聘方通常先需要知道问题、范围和个人角色；技术交流继续关注机制、取舍和可维护性；未来同事还会关心交接、恢复和协作。核心事实保持一致，改变的是展开顺序和术语密度。

可以为每个项目建立一个“能力—主张—证据”索引：调试能力连接假设与证伪记录，架构能力连接候选与后果，协作能力连接接口和决定，可靠性连接恢复与检查。一次回答选最相关的一条主线，不让一个项目承担所有能力证明。

附件也要围绕问题。模块图帮助解释依赖，时间线帮助检查先后，指标表帮助核对口径；每份附件写清它支持哪条主张、来自哪个版本、有哪些限制。材料越多，越需要索引，否则听者只能自己从文件堆里找结论。

作品集可以保留问题说明、关键决策、可运行示例、验证结果和边界。在线演示失效时，静态说明和复现步骤仍有用。个人练习、合成数据与团队生产项目都可以展示，但必须清楚标注各自身份，不混用规模或用户数字。

### 事实源保持一份表达可以有多种

不要分别维护几份互相漂移的“项目真相”。简历短句、口头陈述和深挖材料都从同一台账提取；后来发现口径错了，应同时修正引用它的版本。

下面是可填写的台账字段说明，不是要求你补齐每个数字：

| 字段 | 填写内容 | 没有材料时怎样处理 |
| --- | --- | --- |
| 项目与范围 | 真实系统、时间阶段、允许描述的边界 | 使用可公开的代称，保留内部对应关系的授权边界 |
| 问题与约束 | 当时已知现象、用户、期限、可改范围 | 标出来源不明的回忆 |
| 我的动作 | 调查、决定、实现、验证、交接 | 不把参与扩大为独立负责 |
| 结果与口径 | 实际观察、单位、分母、样本、版本 | 使用定性证据，或直接写尚未测量 |
| 证据索引 | 能定位的记录、PR、报告、审阅结果 | 列待查项，不伪造链接 |
| 其他解释 | 同期变化、环境、样本偏差、未知 | 降低因果表述强度 |
| 后续决定 | 保留、停止、补测、回顾条件 | 区分计划和已经完成 |

在项目进行中及时记录，比结束很久后只凭记忆回顾更容易保留真实的失败与共同贡献。版本记录与 PR 说明的写法可连接 [GIT-03](../chinese-guides/git-03-commits-remotes-pr-worktrees-collaboration.md#pr-帮助别人完成一次有依据的决定)。

### 可公开范围和 AI 整理都服从事实边界

表达经历不要求带出公司的代码、客户日志、账号或内部文件。可以用允许公开的机制说明、匿名结构图和自己重建的合成示例。删除姓名不一定足够脱敏，比例、时间和路径也可能暴露业务信息；使用材料前确认其公开范围。

不能展示原件时，可以说明证据类型和内部核对方式，不暗示可以违规提供。推荐人能否确认职责，也需要事先征得其同意，不能把别人变成未经许可的背书。

AI 可以压缩文字、按证据编号整理、发现缺口和模拟追问，但不能替你创造经历。可以给它一条明确工作要求：“只使用台账已有事实；所有数字回指标编号；未知保留未知；区分个人动作与团队结果。”接着逐句检查它有没有把“参与”改成“主导”、把“同期改善”改成“直接带来”。

最终自查不必追求华丽：每项重要主张能否指出来源，指标是否说清口径，贡献是否有交接点，反证出现时是否会调整结论。如果这些问题能清楚回答，表达就已经有了稳固的基础。

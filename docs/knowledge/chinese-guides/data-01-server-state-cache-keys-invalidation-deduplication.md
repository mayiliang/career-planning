# 客户端远端数据管理知识点讲义

## DATA-01 Server State、缓存键、失效与请求去重

订单列表、用户资料和权限快照属于远端系统拥有的事实。浏览器只能保存某时刻的副本，这份副本会陈旧、可能因权限变化失效，也会受到网络延迟、乱序和重试影响。把它和输入框、弹窗开关或 URL 状态混在一个全局 store 中，团队就必须手工重造缓存、去重与恢复。本讲从数据所有权出发，建立与具体 React/Vue 库无关的 Server State 模型。

示例会围绕同一订单的列表、详情、不同租户与游标分页展开：通过缓存快照、请求时间线和身份切换实验，观察键遗漏、迟到响应、去重和定向失效如何影响用户看到的事实。

### 学习前先确认

- 直接前置：[NET-01 浏览器网络协议、Fetch 与请求可靠性](../chinese-guides/net-01-browser-network-fetch-reliability.md#net-01)。本讲直接使用 HTTP 缓存、AbortSignal、请求竞态、身份、租户和响应归属。

### 一、先按所有权和生命周期分类状态

**服务器状态（Server State）**由远端权威拥有，客户端异步读取并缓存副本。它带来源、更新时间、权限、错误和同步状态。客户端状态由当前应用拥有，如面板开关、未提交筛选草稿；URL 状态用于可分享导航；表单草稿有独立编辑生命周期。

分类不按“是否放进 store”，而按谁能改变和如何恢复。订单可能被其他用户更新，刷新可从服务端重建；弹窗开关不会被服务器改变；搜索词若需要可分享应进 URL。错放会导致把服务端副本当永久事实，或把临时 UI 状态不必要地持久化和同步。

### 二、查询状态不只是 data/loading/error

查询同时有数据状态和请求状态。可能已有陈旧数据且后台 fetching，也可能从未成功而 pending，或者上次成功数据仍可显示但刷新失败。用一个 `isLoading` 会让界面在后台刷新时清空可用内容。

记录 status、fetchStatus、dataUpdatedAt、error、failureCount 和查询键。界面决定首次骨架、后台刷新提示、陈旧标记和错误恢复。取消不等于错误，禁用查询也不等于加载完成。

成功响应还需运行时校验和领域映射；HTTP 200 但 Schema 错误不能进入缓存。错误分类决定是否重试、重新认证、刷新权限或让用户修正输入。

### 三、完整查询键描述远端副本身份

**查询键（Query Key）**应包含所有改变响应内容的输入：资源类型、稳定 ID、租户/用户、筛选、排序、游标、语言、权限视图和必要 Schema 版本。查询函数依赖的变量遗漏在键外，会让不同请求错误共享缓存。

键使用稳定、可序列化结构并集中构造。对象字段顺序、Date、函数和临时引用不应造成偶然新键。筛选先规范化：默认值显式、集合排序、空字符串与缺失语义统一；否则语义相同的查询无法去重。

不要把 token 明文放入键和日志。身份维度可用安全 session/tenant 标识，并在切换时清理。若缓存实例严格限定单会话，仍需证明旧响应不会在新身份后提交。

### 四、新鲜、陈旧与垃圾回收是三件事

**新鲜时间（Stale Time）**描述数据在多久内可被视为无需自动重取；陈旧表示允许触发刷新，不等同不能显示。垃圾回收时间描述无观察者的缓存保留多久，与业务新鲜度不同。轮询间隔又是主动更新频率，不能混成一个数字。

时效来自业务：国家列表可长时间新鲜，库存可能数秒，权限撤回可能要求立即失效。默认值随库版本变化，项目应显式记录关键查询策略。`staleTime=Infinity` 只适合由可靠事件失效或真正不可变数据，否则会永久显示旧事实。

重新聚焦、联网、组件挂载和路由进入是否刷新，需与新鲜策略协调。开发者切换 DevTools 造成重复请求不一定是 bug；先查看配置和时间线。

### 五、请求去重共享同一在途工作

多个组件同时观察同一完整键时，可以复用一个 in-flight Promise，减少重复请求。去重范围只限语义完全相同的查询；不同租户、筛选或权限不能为了省请求合并。

共享请求的取消需要观察者语义：一个组件离开不一定取消仍被其他组件需要的请求；全部观察者离开或键变化时可 Abort。服务端已经收到的读取仍可能完成，但客户端丢弃无归属响应。

去重不是服务端幂等，也不解决写入重复。缓存库的批处理窗口和 retry 可能影响网络数量，验证时记录真实 HAR 与键，而不是凭组件渲染次数推断请求数。

### 六、竞态控制以响应归属为中心

用户快速从筛选 A 切到 B，A 的慢响应后到。正确做法是键分别存储，当前视图只订阅 B；若手写状态，则 Abort A 或比较 request/navigation ID。不能只靠“最后完成者覆盖”。

租户/账号切换更严格：先阻止旧请求提交，断开订阅，清除私有缓存，再建立新会话。响应携带旧 session 时即使键碰巧相同也不显示。预取、后台刷新和持久化缓存都纳入隔离。

删除对象后迟到详情可能复活。使用对象版本、墓碑/失效状态和请求取消，成功删除使详情与相关列表失效，旧版本响应不能清除删除事实。

### 七、缓存失效比缓存写入更重要

**缓存失效（Cache Invalidation）**在已知副本可能过时时标记陈旧并按策略重取。写入成功后，从业务影响图列出对象详情、所属列表、聚合统计和权限，而不是无脑清空全部缓存或只改当前页面。

精确 `setQueryData` 适合服务端返回完整权威对象，能立即更新；不确定所有派生时先更新直接详情并失效相关集合。局部响应不能整体替换详情。失效粒度过宽制造请求风暴，过窄留下矛盾视图。

事件/SSE 可按实体 tag 失效，但事件会丢失，重连和定期校正仍需。时间陈旧、用户动作、权限变更、部署 Schema 更新和显式刷新都是失效来源。

### 八、列表、详情和分页需要结构化关系

列表键包含筛选、排序和分页。详情更新后，哪些列表受影响取决于对象是否仍符合条件；可以更新已缓存页或失效前缀。不要假设对象始终留在原页，状态/排序改变会移动位置。

游标分页把页参数与筛选放入同一键/分页状态，下一页游标来自服务端，不按数组长度猜。后台重取多页时防止重复或跳项，服务端提供稳定排序与快照语义。

无限列表可以保留前页显示并加载下一页，错误只影响相应动作。权限撤回或对象删除要从所有页移除；预取的下一页也属于私有缓存。

### 九、重试只针对暂时且安全的读取失败

网络暂时错误、部分 5xx 和限流可有限退避；400/401/403/404 通常不应默认三次重试。遵守 Retry-After，加入抖动并设置总预算。页面卸载与用户取消不计业务失败。

失败时若有旧数据，可以显示并标记刷新失败；首次无数据则给错误与重试。重试按钮应触发同一键，不能重置整个应用。离线时暂停，恢复后按新鲜/权限策略重取。

服务端读取也可能昂贵，客户端库的默认重试会放大事故。生产指标按状态码、attempt 和键前缀观察，避免每层同时重试。

### 十、预取是提前承担成本与权限

预取在用户可能访问前获取数据，提高导航速度。只预取高概率、可取消、成本可控且当前有权的数据。鼠标瞬间 hover、移动网络或省流模式下要克制；敏感详情不要因为列表可见就全部下载。

预取使用与正式查询完全相同的键和 mapper，进入页面才能命中。不同参数或身份维度遗漏会让预取既浪费又串数据。预取错误通常静默记录，真正进入页面时仍提供错误 UI。

SSR 预取与 hydration 也一样：只把当前用户必要查询序列化，带更新时间，客户端恢复为对应键，并避免立刻无意义重取。

### 十一、SSR Hydration 要防止时间与身份错配

服务端查询缓存是请求级，不应跨用户复用私有 QueryClient。序列化数据做 XSS 安全转义和运行时校验，记录 dataUpdatedAt；客户端使用相同键、版本与时钟策略。

服务端新鲜策略和客户端不同会导致 hydration 后立刻 refetch 或长期陈旧。明确服务器预取目的：减少首屏等待还是提供完整快照。错误是否序列化、重定向和状态码由路由层决定。

CDN/框架缓存可能位于 Query 缓存之外，必须同时审查。客户端正确分租户不能修复服务器把用户 A HTML 缓给 B。

### 十二、持久化缓存需要版本、配额和隐私

把查询缓存存入 IndexedDB/localStorage 可改善重开体验，但扩大数据留存。只持久化允许离线保存的字段，按用户/租户命名空间，加 schemaVersion、最大年龄、容量与迁移。登出、撤权和版本不兼容时清除。

持久化副本启动时先显示陈旧标记并后台验证；不能因离线缓存存在就跳过权限。敏感数据加密在同源脚本被攻破时保护有限，更重要是最小化、短留存和 XSS 防护。

恢复失败安全丢弃缓存，不能让坏 JSON 阻止应用启动。迁移代码也要测试旧版本和中断。

### 十三、写入与查询缓存通过影响图连接

Mutation 保存自身 pending/success/error 和变量，不应被当查询。开始前可取消受影响读取，成功后用权威响应更新/失效，失败保留用户输入。乐观更新、离线 outbox 与冲突由 DATA-02 详细处理。

建立 mutation→query 影响图或集中 key factory，避免每个组件手写字符串。新增查询时审查哪些写入使它陈旧，新增写入时审查所有派生。审计记录能从一次写入追到失效范围。

客户端缓存正确不替代服务端事务和幂等。它只管理远端副本的展示与重新获取。

### 十四、观测要能发现错键与过度刷新

开发工具展示键、观察者、fresh/stale、更新时间、请求与失效。生产采样命中率、请求去重、取消、失败、重试、数据年龄和 payload；按查询类别控制基数，不记录敏感完整键。

重复请求可能来自错键、不稳定参数、过短新鲜期或重新挂载；陈旧数据可能来自漏失效、长 stale、事件断线或错误缓存层。用 trace 从 UI 动作→mutation→失效→refetch→渲染串联。

命中率高不一定好，可能长期命中错误数据；请求少也不一定正确。指标必须与时效、权限和任务成功一起解释。

### 十五、验证矩阵覆盖身份、参数和网络

准备两个用户、两个租户、两种筛选、两页游标和一个详情。验证完整键不会串数据；相同键并发只有一个请求；切筛选/租户时旧响应不闪现；写入只更新相关列表与详情；登出后私有缓存和预取清除。

再注入慢响应、乱序、取消、刷新失败、离线恢复、权限撤回、对象删除、持久化旧 Schema 和 SSR hydration。保存键表、状态图、HAR、缓存快照和最终 UI 断言。不要用 `clear()` 让测试绿，因为它掩盖失效设计。

库升级时复跑默认重试、stale/gc、取消、SSR 与 query key 行为，记录版本。通用原理稳定，具体选项名和默认值会变化。

### 十六、常见反例与适用边界

- 所有订单列表都用 `['orders']`，遗漏租户、筛选和游标。
- 用一个全局 loading，后台刷新清空已有内容。
- 写入后清空全部缓存，或只改当前组件不失效其他投影。
- 登出只删 token，保留查询、预取、持久化和在途响应。
- 把客户端去重当作写入幂等，或把长期 stale 当授权缓存。
- 只看组件渲染次数，不检查真实请求与响应归属。

一次性页面的一次读取可以直接 fetch，不必引入完整缓存库；多组件复用、导航、分页、刷新和写入出现后，显式查询模型会显著降低隐式状态。

批量预取需要容量边界。鼠标经过就预取所有详情会挤掉真正使用的数据，并在蜂窝网络消耗流量。按命中概率、数据大小和用户网络选择，取消已无意义的预取；预取结果仍遵守身份隔离与失效规则。

所有缓存策略都要由真实访问与错误数据复核。

### 十七、学完后应能说明

你应能按所有权区分远端/客户端/URL/草稿状态；构造包含所有依赖的查询键；解释 fresh、stale、gc 与轮询；设计去重、取消和竞态归属；从写入影响图精确失效；隔离身份与持久化；并用多用户、多参数、乱序、SSR 和撤权证据证明缓存既不串数据也不过度请求。

继续查证可参考 [TanStack Query Query Keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)、[QueryClient](https://tanstack.com/query/latest/docs/reference/QueryClient) 与所用框架适配器的当前版本文档。

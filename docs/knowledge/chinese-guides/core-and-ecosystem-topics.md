# 核心与生态主题中文伴读

更新时间：2026-07-29

本讲义覆盖“已有中文主资料，但仍保留英文标准、规范或项目原文用于版本核验”的知识点。中文资料和本讲义构成必读内容；知识点后标注的英文原文为可选核验材料，不作为独立首考题源。若版本化英文规范发生变化，应先更新中文讲义和考核范围，再要求学习者掌握新内容。

## WEB-03

现代 CSS 架构的目标是让样式作用域、覆盖顺序和组件适配可预测。容器查询根据组件所在容器而不是整个视口响应，级联层显式排列 reset、基础、组件和覆盖层，设计令牌则把颜色、间距、字体和状态语义从具体选择器中抽离。

实践时应以组件在不同容器中的表现验证边界，并为不支持的新特性提供可用降级。不要用大量 `!important`、无限提高选择器权重或复制断点来掩盖层叠关系不清。

## SEC-01

XSS 的核心是不可信数据进入了可执行上下文；防御要按 HTML、属性、URL、CSS、JavaScript 等输出位置采用正确编码，并尽量避免危险 DOM API。CSRF 利用浏览器自动携带凭据，因此需要 SameSite、CSRF Token、来源验证和正确的请求语义。

前端鉴权只负责交互提示，最终授权必须由服务端执行。Token、Cookie、CSP、输入校验和输出编码解决的问题不同，不能用其中一个替代全部安全控制。

## SEC-03

WebAuthn 使用站点绑定的公钥凭证完成抗钓鱼认证，服务端生成一次性 challenge 并验证 RP ID、origin、签名计数和凭证状态。Passkey 是可发现、可能跨设备同步的 WebAuthn 凭证体验，不等于“把密码保存到浏览器”。

界面必须处理创建、登录、条件式 UI、取消、设备不可用和账号恢复。前端 API 成功只表示本地凭证操作完成，不能在服务端验证前显示最终登录成功。

## TS-07

TypeScript 类型只在编译阶段存在，网络响应、存储数据和用户输入仍需运行时校验。接口契约应把成功数据和错误数据建模为可区分结构，并在系统边界完成解析，而不是在每个组件中零散断言。

Schema 与静态类型要避免双份漂移，可从同一来源生成或通过契约测试保持一致。`as` 不能证明数据真实，捕获异常后也不能假设它一定是 `Error`。

## TS-08

业务类型建模应让非法状态难以表示。使用可辨识联合表达互斥状态，用品牌类型或封装构造过程区分格式相同但语义不同的 ID、金额和时间，并用穷尽检查保证新增状态得到处理。

权限类型只能提升开发体验，不能替代服务端授权。避免一个包含大量可选字段的“万能对象”；它往往允许互相矛盾的字段组合，并把错误推迟到运行时。

## REACT-08

错误边界捕获其子树渲染和生命周期中的错误，并渲染可恢复 UI；它不自动捕获事件处理、任意异步回调或服务端错误。异步 UI 还需要区分加载、空数据、业务拒绝、网络失败、取消和重试。

恢复策略应保持用户输入、提供明确下一步并记录可定位信息。不要用一个全屏“系统异常”吞掉所有错误，也不要在重试时重复提交有副作用的请求。

## UMI-04

Umi Max Access 可集中声明权限判断，再用于页面、菜单和按钮展示。页面路由、按钮可见性和数据范围是不同层次，隐藏按钮不能阻止直接调用接口，真正授权和数据过滤仍必须在服务端执行。

权限初始化要有加载、失败和刷新状态，并防止旧账号权限残留。复杂规则应输入明确的用户、资源和上下文，而不是散落在模板里的字符串角色比较。

## ANTD-04

移动业务组件首先要适应触控、窄屏、软键盘、安全区和不稳定网络，而不是把桌面组件等比例缩小。表单、列表、日期选择、上传和弹层应保持可达的触控目标、清楚的进行中与失败状态，并让滚动容器和焦点行为可预测。

主题定制应优先使用组件公开的 CSS 变量和设计令牌，并在浅色、深色、横竖屏及动态字号下验收。不要依赖内部类名覆盖，也不要让固定高度弹层被键盘遮挡；遇到复杂桌面交互时，应重新设计移动任务流而非机械复刻。

## BIZ-01

业务建模从统一语言开始：产品、研发和数据对实体、值对象、事件、状态和规则使用一致术语。对象边界由业务身份、生命周期和不变量决定，不应机械照搬数据库表或接口 JSON。

先画出对象关系、所有权和变化原因，再决定前端 Store、表单和接口模型。一个模型同时服务列表、编辑、统计和权限通常会出现大量无意义可选字段，应按使用场景建立读写模型。

## BIZ-02

状态机用有限状态、事件、转移、守卫和动作表达业务生命周期，不变量则说明无论经过何种路径都必须成立的规则。显式模型能发现“不允许的跳转”和并发下的冲突。

不要把状态机退化成一个枚举加任意赋值，也不要为简单开关引入过重框架。验证应覆盖每个允许转移、拒绝转移、重复事件、超时和恢复路径。

## BIZ-03

RBAC 根据角色授予权限，ABAC 还结合主体、资源、动作和环境属性。前端可以依据权限结果组织界面，但不能自行推断数据权限，也不能把菜单配置当作授权策略。

设计时明确默认拒绝、权限继承、资源所有权、租户隔离和审计。权限缓存要有用户和租户维度，账号切换后必须失效，服务端返回 403 时应按真实拒绝处理而不是自动重试。

## BIZ-04

API 契约定义输入输出和兼容承诺，DTO 适合传输，前端领域模型适合交互与业务推导。二者可以映射但不应默认等同，否则后端字段变化会直接污染整个界面。

需要明确缺失与 `null`、时间和时区、金额单位、枚举扩展、分页、错误结构和版本策略。生成类型能减少拼写错误，但不能替代运行时校验与语义转换。

## BIZ-05

同一业务对象在新建、列表、详情和编辑页面中应共享身份、状态和权限语义，但每个页面可以拥有适合任务的投影。保存后需要定义本地数据、列表缓存和详情缓存如何同步。

表单初始值不是永久真相；处理服务端回填、并发编辑、校验错误、取消和重置时要避免覆盖用户输入。不要让每个页面各自维护一套状态枚举和格式化规则。

## BIZ-06

长任务通常采用提交、返回任务 ID、查询或订阅进度、完成后下载结果的协议。前端需要区分排队、运行、成功、失败、取消和过期，并在刷新后恢复任务状态。

进度值必须有真实语义，未知进度应使用不确定状态而不是伪造百分比。轮询要有退避和停止条件，下载凭证要短期、一次性或受权限保护。

## BIZ-07

幂等表示同一操作重复执行不会产生额外业务效果，不等于返回内容永远相同。GET、PUT、DELETE 等 HTTP 方法有规范语义，但具体业务仍需幂等键、版本号或唯一约束保护。

异常处理要区分可重试、不可重试、冲突、超时和结果未知。超时后直接再次创建订单可能重复扣款；应先查询原请求结果或携带稳定幂等键。

## BIZ-08

可追踪性把需求、设计、接口、实现、测试、发布和验收连接起来，使每项交付都能回答“为什么做、如何验证、谁确认”。它不要求重复抄写内容，而是保存稳定引用和状态。

验收标准应以可观察行为描述正常、异常和边界路径。提交记录、PR 和测试报告要能回到需求；范围变化时同步更新验收而不是只修改代码。

## ENG-01

构建工具从入口建立模块图，解析导入、转换源码、拆分 Chunk 并生成带哈希的产物。开发服务器侧重快速反馈和 HMR，生产构建侧重兼容目标、压缩、缓存和可观测产物。

分析包体时先识别入口、共享依赖、动态导入和重复模块，再根据实际加载路径优化。Tree-shaking 依赖静态 ESM 和正确的副作用声明，不能只看源码是否写了 `import`。

## ENG-07

Vite 8 以 Rolldown 作为生产构建核心并依赖 Oxc 生态提升解析和转换性能。迁移应对比插件 API、产物语义、CSS、Worker、SSR、Source Map 和浏览器目标，而不是只比较构建耗时。

先建立旧版本基线和回归样本，再逐项处理不兼容插件。性能提升不能以丢失错误信息、Source Map 或兼容性为代价，迁移必须保留可回滚版本。

## ENG-03

lockfile 固定依赖解析结果，Workspace 管理多包边界和本地链接，包管理器的幽灵依赖、提升策略和严格性会影响代码在 CI 与发布包中的表现。

仓库必须固定包管理器版本并在 CI 使用冻结 lockfile。内部依赖使用明确版本策略，避免任意 `*`；更新依赖要审查变更、执行测试并保留回滚。

## ENG-05

格式化解决风格一致，Lint 发现规则问题，Typecheck 验证静态类型，测试验证行为，它们不能互相替代。提交门禁应快速、确定并与 CI 一致，较慢的全量验证可以分层运行。

规则需要说明风险和修复方式，不能不断增加无价值告警。禁止通过全局关闭规则、滥用 `any` 或跳过 Hook 来追求“绿灯”。

## OBS-01

RUM 从真实用户环境采集加载、交互、错误和业务体验；实验室数据适合复现，二者需要结合。OpenTelemetry 用 Trace、Metric、Log 和上下文传播连接前端请求与后端处理。

采集前定义事件、采样、版本和用户同意，避免记录输入内容、Token 和个人数据。指标必须能关联发布版本、页面、设备与网络条件，否则平均值很难指导修复。

## PERF-05

体验质量不仅是速度分数，还包括键盘可用性、文本缩放、焦点、对比度、减少动态效果和辅助技术语义。性能优化不能通过移除标签、延迟关键反馈或破坏可访问树换取。

应将自动扫描、人工键盘检查、屏幕阅读器抽查和真实设备性能一起纳入验收。Lighthouse 是线索，不是单独的通过凭证。

## COMP-01

组件职责由一个稳定任务和清晰状态模型定义。API 需要表达受控/非受控状态、默认值、事件、组合、可访问语义和逃生口，不应暴露页面内部结构。

优先使用组合而不是不断增加布尔属性。复杂组件要画出状态与事件，验证键盘、焦点、异步和错误路径；只有视觉复用而无行为一致性的部分不一定应该抽成组件。

## DS-01

Design Token 用语义名称连接设计决策与实现，如背景、文本、间距和状态，而不是简单保存一组颜色值。基础令牌可映射到语义令牌，再由组件令牌表达局部用途。

主题切换需要处理继承、对比度、组件状态和运行时更新。令牌变化属于公共契约，应版本化并做视觉回归，避免组件直接引用品牌色数值。

## PLATFORM-01

配置化页面把字段、布局、校验、权限和动作描述为受控 Schema，再由渲染器映射到有限组件。Schema 必须版本化、可校验，并明确哪些能力可配置、哪些必须编码实现。

禁止把任意表达式、HTML 或脚本塞进配置。复杂交互如果需要大量条件和逃生字段，应回到正常组件开发；配置平台的价值是稳定重复场景，不是替代所有前端代码。

## PLATFORM-02

微前端适合组织边界、发布节奏和运行隔离确实独立的系统。需要明确路由、认证、依赖、样式、通信、错误、监控和回滚契约；技术拆分不能解决不清晰的业务所有权。

通信优先使用稳定事件或 API，避免直接读写其他应用内部 Store。共享依赖要有版本策略，首屏性能和故障隔离必须用真实数据验证。

## NODE-03

CLI 的契约包括参数、帮助、标准输入输出、错误流、退出码、配置优先级和中断行为。成功输出应便于人阅读或机器解析，错误信息需要说明原因、位置和恢复方式。

参数解析后仍需业务校验；取消和信号要清理临时资源。不要以交互式提示作为唯一入口，也不要在错误时仍返回 0。

## API-02

代码生成器先把外部规范解析成稳定内部模型，再执行命名、类型映射、模板或 AST 输出。这样能把输入差异、业务策略和打印格式分开测试。

生成结果要确定、幂等、可格式化并包含来源说明。保留无法安全表达的 Schema 警告，避免静默退化为 `any`；用快照、解析、类型检查和编译验证产物。

## AI-01

AI 辅助研发适合生成候选、解释、搜索和机械改写，但输出必须经过规格、类型、测试、安全和人工评审。验证深度应随改动影响面、数据敏感度和可逆性提高。

记录模型提供的假设和未验证部分，不要把流畅解释当作证据。评估应比较任务成功、返工、缺陷和时间，而不是生成代码量。

## CAREER-01

项目复盘要从背景、目标、约束、关键问题、方案选择、个人行动、量化结果和反思形成完整证据链。STAR 只是组织结构，不能用来包装无法验证的夸大结果。

区分团队成果和个人贡献，并说明取舍与失败。数据应有口径和来源；无法量化时用可复核的交付、风险下降或用户反馈支撑。

## CAREER-05

代码评审关注正确性、设计、可读性、测试、安全和长期维护。评论应指出具体位置、风险、依据和建议，并区分阻塞问题、建议和个人偏好。

推动技术决策要倾听约束、记录异议、用实验和数据降低分歧。目标是团队形成更好决策能力，而不是由资深人员赢得每次讨论。

## CAREER-06

面试和教学表达先判断受众，再用问题、机制、例子、边界和验证组织内容。高级表达不仅给出结论，还能解释为什么、什么时候不适用以及如何发现失败。

演示和文章要有可运行证据、清晰图示和反馈迭代。影响力来自他人能够理解、复用并改进方案，而不是术语密度或发布数量。

## AIAPP-01

模型 API 的关键参数包括模型、消息、上下文窗口、输出上限、温度和停止条件。上下文不是越长越好，需要为系统规则、用户输入、检索内容、工具结果和输出预留预算。

服务端负责密钥、限流和策略，前端只接收受控结果。模型版本、采样参数和 Prompt 必须记录，超长输入、截断、拒绝和供应商故障要有明确处理。

## AIAPP-02

流式生成需要区分网络字节、SSE 事件、模型增量和最终消息。前端应增量解析结构化事件、批量更新 UI、支持取消，并在结束时确认完整状态。

不能假设每个网络块都对应完整字符或 JSON。处理断线、重复事件、部分结果、Markdown 未闭合和工具调用切换，同时避免每个 Token 都触发昂贵渲染。

## AIAPP-03

结构化输出先要求模型按约定格式生成，再用运行时 Schema 校验字段、类型、枚举和业务约束。合法 JSON 不等于业务有效，校验失败不能被自动当作成功。

可进行有限次数的修复重试，但要保留原始结果和错误原因。高风险结论需要人工复核，并为截断、空响应和供应商不支持提供降级。

## AIAPP-04

Tool Calling 由模型提出工具名和参数，应用负责校验、授权、确认、执行和返回结果。模型不能直接获得系统权限，也不能决定绕过审批。

前端要展示待确认、执行中、成功、失败和可重试状态，并保留参数与结果来源。副作用工具使用幂等键和最小权限，未知工具或错误参数必须拒绝。

## AIAPP-05

Generative UI 应基于版本化消息块协议渲染 text、citation、tool call、result 和 artifact，而不是执行模型生成的任意 HTML 或组件代码。未知消息块要安全降级。

流式更新和持久化需要稳定 ID、顺序和完成状态。刷新后应恢复执行进度，组件只接受经过 Schema 校验的数据。

## AIAPP-06

RAG 包含切分、索引、检索、重排、生成和引用验证。前端需要展示来源、段落、时间和冲突，明确区分“没有资料”“相关度低”和“来源不一致”。

检索内容仍是不可信数据，不能把其中指令提升为系统指令。评估集要测召回、相关性、引用正确性和无答案处理，而不只看回答是否流畅。

## AIAPP-10

AI 产品 UX 要说明系统能力和限制，并让用户可以取消、编辑、重试、查看来源和接管。等待、低置信、拒绝、工具失败和人工升级都应有明确状态。

不要用拟人化和伪精确置信度制造过度信任。高风险结果必须可核验、可撤销并说明责任边界。

## AGENT-06

长任务需要显式任务句柄、状态、进度、取消、恢复和幂等语义。Tasks 扩展的能力必须先协商，Client 不能假设任意 Server 都支持。

任务状态存储独立于连接生命周期，重复更新和网络重试不能重复副作用。进度事件有序且可恢复，终态之后拒绝非法转移。

## AGENT-09

Agent 可观测性要记录目标、步骤、工具、模型、Token、审批、错误和最终结果，并通过 Trace Context 串联 Host、Client、Server 与下游服务。日志内容要脱敏并限制保留。

回放应依赖版本化输入输出和工具结果，而不是重新执行有副作用操作。指标关注成功率、失败类型、人工介入、成本和循环长度，不能只统计调用次数。

## WEBAI-02

WebGPU 通过 Adapter、Device、Queue、Buffer、Texture 和 Pipeline 暴露 GPU 计算与渲染。设备能力、限制和丢失都必须检测，不应假设桌面独显环境。

本地推理要管理数据布局、显存、批次、预热和回收，并提供 WebGL、WASM 或云端降级。性能测试同时观察端到端延迟、内存和设备覆盖。

## WEBAI-03

WebAssembly 提供接近原生的可移植执行环境，SIMD 可并行处理向量数据，但 JavaScript 与 WASM 边界复制、内存增长和初始化也有成本。

将热点计算而不是整个应用盲目迁移。基准测试应包含冷启动、稳态、数据传输和不支持 SIMD 的降级，并避免阻塞主线程。

## WEBAI-04

Worker 把 CPU 密集任务移出主线程，通过结构化克隆、Transferable 或共享内存通信。消息协议需要 ID、类型、取消、错误和版本，避免无法追踪的字符串事件。

Worker 不是无限并行，线程数量、内存和序列化成本都会影响性能。UI 更新仍回到主线程，应批量回传进度并正确终止资源。

## WEBAI-06

本地 Embedding 流程包含模型加载、文本预处理、向量生成、存储、相似度检索和版本管理。不同模型或归一化方式生成的向量不能直接混用。

索引要绑定模型版本和数据权限，敏感文本不应因“本地处理”就无限保留。用中文和业务样本评估召回、延迟、存储和无结果场景。

## WEBAI-10

本地 AI 优化同时关注启动、首 Token、吞吐、内存、能耗、热降频和交互响应。高性能设备上的平均值不能代表移动端或辅助技术用户。

推理过程提供进度、取消、降级和减少动态效果支持。任务过重时应降低模型、批次或转向云端，而不是长期占满主线程和电池。

## AIDEV-02

Context Engineering 决定模型能看到哪些目标、代码、约束、工具和历史。上下文应最小充分、来源可追溯并按任务更新，避免把整个仓库和秘密一次性注入。

仓库指令说明构建、测试、风格、安全和禁止事项；冲突时要有优先级。过期文档、生成文件和无关日志会降低准确率，应通过资源 URI、缓存和摘要管理。

## AIDEV-03

AI 生成代码需要从静态检查、单元测试、组件/集成测试、端到端测试到人工评审逐层验证。验证组合取决于风险，不是每个改动都运行同样流程。

测试应针对规格和边界，而不是复述生成实现。高风险代码加入安全、性能、迁移和回滚验证，不能因代码“看起来合理”跳过执行。

## AIDEV-05

Agentic Coding 要把任务隔离在明确工作树或分支，限制可修改范围并持续检查 diff。Agent 获得最小权限，不应同时处理无关用户改动。

每个阶段保留可验证产物，合并前运行测试和人工审查。出现目标变化、范围外修改或危险操作时暂停，而不是用重置覆盖现场。

## AIDEV-09

设计稿到代码需要把布局、令牌、状态、响应式和组件语义转成可维护实现。视觉相似不是唯一目标，还要验证键盘、可访问性、内容扩展和真实数据。

视觉回归使用稳定视口、字体、数据和阈值，并人工判断有意义差异。不要用绝对定位和截图背景换取单一尺寸像素一致。

## DEPLOY-01

Nginx 常用于静态资源、反向代理、TLS 终止和缓存控制。HTML 通常短缓存或协商缓存，带内容哈希的静态资源可以长缓存 immutable，二者策略不能颠倒。

代理配置要正确传递 Host、协议和客户端信息，并设置超时、体积限制和安全头。SPA fallback 只处理前端路由，不能把 API 404 重写成 HTML。

## DEPLOY-02

CI/CD 从可信源码构建可追溯制品，经测试、安全扫描、环境审批和部署策略进入生产。一次构建的同一 digest 应在环境间晋级，避免每个环境重新产生不同镜像。

灰度发布需定义流量、观察窗口、健康指标和自动回滚。部署成功不等于业务健康，复盘要连接变更、指标、告警和用户影响。

## RENDER-01

SPA、SSR、SSG 和 ISR 的选择取决于内容时效、个性化、SEO、缓存、交互和部署约束。一个应用可以按路由混合策略，不必全局二选一。

比较时同时计算 TTFB、HTML 可见时间、注水成本、数据一致性和运维复杂度。预渲染不是永久静态，缓存失效和错误恢复仍需设计。

## RENDER-02

RSC 在服务端执行并把可序列化结果传给客户端组件，Streaming 允许 HTML 分段到达，Suspense 划分等待边界，Hydration 为已有 HTML 绑定交互。它们解决不同层次问题。

服务端与客户端边界要避免泄露密钥、传递不可序列化值和重复获取。流式错误、注水不一致、客户端导航和缓存必须纳入测试。

## DATA-02

乐观更新在服务端确认前先修改界面，需要保存旧快照、生成幂等请求并在失败时回滚。并发写入时单一快照可能过期，应结合版本、冲突响应或重新获取。

离线突变队列必须持久化顺序、用户身份和重试状态，账号切换时隔离。并非所有操作适合乐观处理，高风险和不可逆动作应等待确认。

## COLLAB-01

WebRTC 负责点对点媒体或数据通道，仍需要信令和 STUN/TURN。CRDT 通过可合并操作处理并发编辑，但不自动解决权限、业务不变量和历史保留。

协作系统要定义文档身份、参与者、离线合并、意识状态、撤销和恢复。网络分区、重复消息和版本升级必须通过多客户端测试验证。

## GRAPHICS-02

WebGL/WebGPU 渲染管线把顶点、纹理、Uniform/Buffer 和 Shader 组合为 GPU 命令。性能来自批处理、减少状态切换、合理数据布局和资源复用，不只是把代码交给 GPU。

资源要在生命周期结束时释放，并处理 context/device lost。高分屏尺寸、颜色空间、兼容性和无障碍替代内容同样属于交付范围。

## ANALYTICS-01

埋点模型先定义业务事件、触发时机、主体、对象、属性和版本，再实现采集。事件名和字段要稳定，客户端与服务端事件需要可关联但避免重复计数。

数据质量通过 Schema 校验、采样检查、漏斗守恒和发布对比监控。个人数据、自由文本和稳定标识必须最小化并遵守同意与留存规则。

## I18N-01

国际化把文案、复数、插值、日期数字和方向从组件逻辑中抽离。翻译键应表达语义，不能把完整句子拆成无法重排的碎片，也不要拼接不同语言片段。

界面要测试文本膨胀、RTL、字体、换行和键盘顺序。图标方向、布局逻辑属性和可访问名称需要随语言正确变化。

## I18N-02

时间点应使用明确时区或 UTC 传输，展示时依据用户和业务时区格式化。日历日期、墙上时间和绝对时间是不同数据类型，不能都用一个无时区字符串表示。

使用 Intl 处理数字、货币、相对时间和排序，并测试 DST、跨日和非公历地区。金额同时保存数值、币种和精度，不能直接对格式化字符串计算。

## IDENTITY-01

Cookie 可由浏览器自动携带，Session 通常把状态保存在服务端，Bearer Token 则由持有者证明访问权。选择取决于威胁模型和部署边界，不是“Token 一定更现代”。

使用 Secure、HttpOnly、SameSite、短期访问凭证、刷新轮换和可靠退出。前端存储不能消除 XSS 风险，多设备会话与撤销必须由服务端维护。

## PRIVACY-02

跨区域合规先做数据分类、处理目的、存储位置、接收方和传输路径盘点，再决定本地化、脱敏、同意、合同和访问控制。前端 SDK 和埋点常是隐蔽跨境来源。

工程控制包括地区配置、字段最小化、日志过滤、下载审计和用户权利入口。法律条文随地区变化，产品方案需由专业合规人员复核，技术文档不能替代法律意见。

## ARCH-01

架构质量属性包括性能、可靠性、安全、可维护性、可访问性和成本，需要写成可测场景：在什么刺激下、系统处于何状态、期望什么响应。抽象的“高性能高可用”无法评审。

架构决策是在约束下权衡，不存在同时最大化所有属性的方案。高风险假设通过原型、容量测试和故障演练验证，并保留决策与后果。

## ARCH-03

渐进迁移先建立现状基线和边界，再按可独立交付的切片替换旧系统。Strangler 模式通过路由或适配层把流量逐步转向新实现，直到旧能力可以安全删除。

兼容层必须有退出条件，双写要处理顺序、失败和对账。每个阶段都保留监控、回滚和数据迁移策略，避免长期运行两个事实来源。

## ARCH-04

技术债按影响、利息、风险和修复成本管理，而不是把所有旧代码都视为债务。依赖升级需要所有者、支持周期、弃用信息、兼容测试和升级窗口。

制定预算和退出标准，优先处理安全、不可恢复故障和阻塞交付的债务。只创建永不关闭的债务清单不会改善系统。

## BACKEND-03

对象存储适合大文件和静态对象，前端常通过短期预签名 URL 直传或下载。分片上传需要 upload ID、分片编号、校验、完成和取消协议，并支持断点恢复。

服务端仍要验证权限、类型、大小、摘要和病毒扫描。CDN 缓存键、私有内容、失效和成本必须明确，预签名 URL 不应长期暴露。

## CLOUD-01

Serverless 关注按请求执行和平台托管，容器封装运行环境，Kubernetes 编排 Pod、Deployment、Service 和 Ingress。前端高级工程师需要理解交付边界，不必取代平台工程师。

部署必须配置健康检查、资源、密钥、伸缩和滚动策略。平台抽象不能消除冷启动、网络、状态和成本，选择应依据负载和组织能力。

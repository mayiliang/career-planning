# 核心与生态主题中文伴读

更新时间：2026-07-29

本讲义覆盖“已有中文主资料，但仍保留英文标准、规范或项目原文用于版本核验”的知识点。中文资料和本讲义构成必读内容；知识点后标注的英文原文为可选核验材料，不属于必读资料，也不进入首考资料定位题。若版本化英文规范发生变化，应先更新中文讲义和考核范围，再要求学习者掌握新内容。

## GIT-01

Git 的仓库不是“文件版本列表”，而是由 blob、tree、commit 和 tag 组成的内容寻址对象图。工作区保存当前文件，暂存区保存下一次提交的树快照，分支和 `HEAD` 是指向提交的引用；理解这四层后，`add`、`commit`、`restore`、`reset` 和 `revert` 的差异可以从状态变化推导出来。

恢复操作必须先判断改动位于工作区、索引、本地提交还是已发布历史。未发布历史可通过引用和 reflog 找回，已发布错误通常应追加 revert；`reset --hard` 会覆盖工作区和索引，不能在未取证或存在他人修改时使用。敏感信息进入历史后还涉及历史重写、凭据轮换和协作者同步，删除当前文件并不足够。

## GIT-02

分支本质上是可移动的提交引用。fast-forward 只移动引用，三方合并基于两个分支和共同祖先生成双父提交，rebase 则把一组补丁重新应用到新基线并产生新提交；因此即使文件内容相同，提交身份和历史拓扑也可能不同。

解决冲突的目标是恢复业务语义，不是机械删除冲突标记。应先确认共同祖先和双方意图，再编辑、测试并检查差异；对已经共享的提交随意 rebase 或强推会让其他人的引用失效。merge、rebase、squash 和 cherry-pick 应根据审计、回滚、发布与协作约束选择，而不是追求一种固定历史形状。

## GIT-03

可协作的提交应保持单一目的、包含必要测试，并能独立审查和回滚。远端跟踪引用记录上次 fetch 所见状态，pull 只是获取后再执行集成策略；PR 将提交图、检查、评审和需求证据连接起来，但平台按钮不会改变 Git 对象和引用的基本机制。

多 Agent 并行开发应为每个任务分配明确文件边界、分支和 worktree。多个 worktree 共享对象数据库但拥有独立工作区与索引，仍可能在最终集成时产生语义冲突；因此必须记录任务归属、提交顺序和验证结果，保留用户已有修改，并在集成前检查脏状态、过期基线、生成文件与跨任务依赖。

## WEB-03

现代 CSS 架构的目标是让样式作用域、覆盖顺序和组件适配可预测。容器查询根据组件所在容器而不是整个视口响应，级联层显式排列 reset、基础、组件和覆盖层，设计令牌则把颜色、间距、字体和状态语义从具体选择器中抽离。

`@scope` 限制选择器匹配范围但不会创建安全隔离，嵌套仍需关注特异性；逻辑属性让布局适配 writing-mode，`content-visibility` 可跳过屏外渲染但不能破坏搜索、焦点和无障碍树。Anchor Positioning 让浮层相对锚点定位并定义回退位置，Scroll-driven Animations 用滚动/视图时间线驱动进度；两者都要提供不支持时的静态布局或轻量脚本路径。

设计令牌分原始值、语义用途和组件别名，主题切换不能把品牌值直接散落到组件。现代颜色、`color-mix()` 和相对颜色要验证对比度、强制颜色和打印。所有动画尊重 `prefers-reduced-motion`，滚动增强不应成为读取内容或操作控件的必要条件。

实践以组件在不同容器、视口、writing-mode、缩放和浏览器中的表现验证边界，并根据 Baseline 与真实用户流量选择上线目标。不要用大量 `!important`、无限提高选择器权重、复制断点或只支持最新版浏览器来掩盖架构问题。

## SEC-01

XSS 的核心是不可信数据进入了可执行上下文；防御要按 HTML、属性、URL、CSS、JavaScript 等输出位置采用正确编码，并尽量避免危险 DOM API。CSRF 利用浏览器自动携带凭据，因此需要 SameSite、CSRF Token、来源验证和正确的请求语义。

DOM Clobbering 利用带 `id`/`name` 的元素影响命名属性访问或隐式全局引用，使代码取得攻击者控制的节点/字符串。安全代码不从 `window.foo` 或可被命名元素覆盖的属性取得配置，使用显式查询、类型/实例检查和可信配置源；CSP 能降低部分结果，但不能修复错误引用。

Prototype Pollution 让攻击者控制 `__proto__`、`constructor`、`prototype` 等路径，把属性写进共享原型并影响授权、配置或 DOM sink。解析和深合并使用键白名单、拒绝危险路径、无原型对象或 Map，校验后再读取；冻结内建对象只能作为特定环境的补充控制。测试必须验证污染前后无共享对象被改变。

前端鉴权只负责交互提示，最终授权必须由服务端执行。Token、Cookie、CSP、输入校验、输出编码和安全对象合并解决的问题不同，不能用其中一个替代全部控制。安全审计追踪数据从入口、转换到 sink/授权决策的完整路径，而不是只尝试常见 Payload。

## SEC-03

WebAuthn 使用站点绑定的公钥凭证完成抗钓鱼认证，服务端生成一次性 challenge 并验证 RP ID、origin、签名计数和凭证状态。Passkey 是可发现、可能跨设备同步的 WebAuthn 凭证体验，不等于“把密码保存到浏览器”。

界面必须处理创建、登录、条件式 UI、取消、设备不可用和账号恢复。前端 API 成功只表示本地凭证操作完成，不能在服务端验证前显示最终登录成功。

## SEC-04

跨源隔离不是单一响应头，而是浏览上下文、资源准入和能力授权的组合。`Cross-Origin-Opener-Policy: same-origin` 把顶层页面与不可信弹窗分离，`Cross-Origin-Embedder-Policy: require-corp` 要求跨源资源通过 CORS 或 CORP 明确授权；两者满足并通过浏览器检查后，`crossOriginIsolated` 才可能为真，SharedArrayBuffer 等高风险能力才可用。

COEP 会暴露历史上被忽略的第三方资源问题：图片、字体、脚本、Worker、Wasm、iframe 和 CDN 都要逐项确认 CORS/CORP。迁移应先盘点资源与弹窗/OAuth 流程，在报告或测试环境验证，再设置强制策略；不能遇到阻断就关闭隔离。

iframe 的 `sandbox` 控制脚本、表单、导航、弹窗和源能力，`allow`/Permissions Policy 控制摄像头、麦克风、剪贴板和实验性工具等特性。能力只授予完成任务所需的最小来源；跨源嵌入默认不应继承顶层页全部能力。

`postMessage` 必须校验 `event.origin`、`event.source`、协议版本和运行时 Schema，发送时使用精确 `targetOrigin`。消息中的 URL、HTML、命令和工具参数仍是不可信输入；来源匹配不代表业务授权成立。

跨站信息泄露可能利用窗口引用、错误/加载差异、缓存、资源尺寸或时序推断用户状态。敏感响应采用正确的 Cookie、缓存、CORP/COEP、内容类型和统一错误边界，避免让跨源页面通过可观察差异探测身份。点击劫持则通过恶意嵌入诱导用户操作，优先用 CSP `frame-ancestors` 限制允许的父页面，并让高风险动作再次展示主体、影响和确认。

验收应自动检查响应头、`crossOriginIsolated`、第三方资源加载、弹窗/登录、iframe 权限和消息伪造，并提供不支持隔离或第三方无法配合时的降级路径。

## TS-07

TypeScript 类型只在编译阶段存在，网络响应、存储数据和用户输入仍需运行时校验。接口契约应把成功数据和错误数据建模为可区分结构，并在系统边界完成解析，而不是在每个组件中零散断言。

Schema 与静态类型要避免双份漂移，可从同一来源生成或通过契约测试保持一致。`as` 不能证明数据真实，捕获异常后也不能假设它一定是 `Error`。

## TS-08

业务类型建模应让非法状态难以表示。使用可辨识联合表达互斥状态，用品牌类型或封装构造过程区分格式相同但语义不同的 ID、金额和时间，并用穷尽检查保证新增状态得到处理。

权限类型只能提升开发体验，不能替代服务端授权。避免一个包含大量可选字段的“万能对象”；它往往允许互相矛盾的字段组合，并把错误推迟到运行时。

## REACT-08

错误边界捕获其子树渲染和生命周期中的错误，并渲染可恢复 UI；它不自动捕获事件处理、任意异步回调或服务端错误。异步 UI 还需要区分加载、空数据、业务拒绝、网络失败、取消和重试。

恢复策略应保持用户输入、提供明确下一步并记录可定位信息。不要用一个全屏“系统异常”吞掉所有错误，也不要在重试时重复提交有副作用的请求。

## UMI-04

Umi Max Access 可集中声明权限判断，再用于页面、菜单和按钮展示。页面路由、按钮可见性和数据范围是不同层次，隐藏按钮不能阻止直接调用接口，真正授权和数据过滤仍必须在服务端执行。

权限初始化要有加载、失败和刷新状态，并防止旧账号权限残留。复杂规则应输入明确的用户、资源和上下文，而不是散落在模板里的字符串角色比较。

## ANTD-04

移动业务组件首先要适应触控、窄屏、软键盘、安全区和不稳定网络，而不是把桌面组件等比例缩小。表单、列表、日期选择、上传和弹层应保持可达的触控目标、清楚的进行中与失败状态，并让滚动容器和焦点行为可预测。

主题定制应优先使用组件公开的 CSS 变量和设计令牌，并在浅色、深色、横竖屏及动态字号下验收。不要依赖内部类名覆盖，也不要让固定高度弹层被键盘遮挡；遇到复杂桌面交互时，应重新设计移动任务流而非机械复刻。

## BIZ-01

业务建模从统一语言开始：产品、研发和数据对实体、值对象、事件、状态和规则使用一致术语。对象边界由业务身份、生命周期和不变量决定，不应机械照搬数据库表或接口 JSON。

先画出对象关系、所有权和变化原因，再决定前端 Store、表单和接口模型。一个模型同时服务列表、编辑、统计和权限通常会出现大量无意义可选字段，应按使用场景建立读写模型。

## BIZ-02

状态机用有限状态、事件、转移、守卫和动作表达业务生命周期，不变量则说明无论经过何种路径都必须成立的规则。显式模型能发现“不允许的跳转”和并发下的冲突。

不要把状态机退化成一个枚举加任意赋值，也不要为简单开关引入过重框架。验证应覆盖每个允许转移、拒绝转移、重复事件、超时和恢复路径。

## BIZ-03

RBAC 根据角色授予权限，ABAC 还结合主体、资源、动作和环境属性。前端可以依据权限结果组织界面，但不能自行推断数据权限，也不能把菜单配置当作授权策略。

设计时明确默认拒绝、权限继承、资源所有权、租户隔离和审计。权限缓存要有用户和租户维度，账号切换后必须失效，服务端返回 403 时应按真实拒绝处理而不是自动重试。

## BIZ-04

API 契约定义输入输出和兼容承诺，DTO 适合传输，前端领域模型适合交互与业务推导。二者可以映射但不应默认等同，否则后端字段变化会直接污染整个界面。

需要明确缺失与 `null`、时间和时区、金额单位、枚举扩展、分页、错误结构和版本策略。生成类型能减少拼写错误，但不能替代运行时校验与语义转换。

OpenAPI 3.2 文档要显式识别规范版本和 JSON Schema 方言，覆盖多媒体类型、流式响应、Webhook 与安全方案。兼容性按消费者方向判断：新增可选字段、删除响应字段、收窄枚举、改变空值和错误语义的风险不同。DTO 到领域/UI 模型的防腐层应集中处理未知值、版本迁移和降级。

Protocol Buffers 用稳定字段编号编码数据，字段名不是线上身份；删除字段后应 `reserved` 编号和名称，不能复用。未知字段通常可以转发，但业务层仍需处理未知枚举与缺省值。生成代码只说明编解码规则一致，不能证明字段业务含义、授权和服务端约束正确。变更必须用新旧客户端和服务端组成兼容矩阵，而不是只重生成最新版。

gRPC-Web 让浏览器经代理访问 gRPC 服务，受浏览器传输、代理、CORS 和流式模式限制。前端要把 gRPC status、metadata、取消和流结束映射为领域错误与可恢复 UI，不能把 HTTP 200 当成 RPC 成功。无论 JSON 还是二进制协议，DTO 都停留在传输边界，时间、金额、空值、身份和状态应在防腐层转成前端领域模型。

## BIZ-05

同一业务对象在新建、列表、详情和编辑页面中应共享身份、状态和权限语义，但每个页面可以拥有适合任务的投影。保存后需要定义本地数据、列表缓存和详情缓存如何同步。

表单初始值不是永久真相；处理服务端回填、并发编辑、校验错误、取消和重置时要避免覆盖用户输入。不要让每个页面各自维护一套状态枚举和格式化规则。

## BIZ-06

长任务通常采用提交、返回任务 ID、查询或订阅进度、完成后下载结果的协议。前端需要区分排队、运行、成功、失败、取消和过期，并在刷新后恢复任务状态。

进度值必须有真实语义，未知进度应使用不确定状态而不是伪造百分比。轮询要有退避和停止条件，下载凭证要短期、一次性或受权限保护。

## BIZ-07

幂等表示同一操作重复执行不会产生额外业务效果，不等于返回内容永远相同。GET、PUT、DELETE 等 HTTP 方法有规范语义，但具体业务仍需幂等键、版本号或唯一约束保护。

异常处理要区分可重试、不可重试、冲突、超时和结果未知。超时后直接再次创建订单可能重复扣款；应先查询原请求结果或携带稳定幂等键。

## BIZ-08

可追踪性把需求、设计、接口、实现、测试、发布和验收连接起来，使每项交付都能回答“为什么做、如何验证、谁确认”。它不要求重复抄写内容，而是保存稳定引用和状态。

验收标准应以可观察行为描述正常、异常和边界路径。提交记录、PR 和测试报告要能回到需求；范围变化时同步更新验收而不是只修改代码。

## ENG-01

构建工具从入口建立模块图，解析导入、转换源码、拆分 Chunk 并生成带哈希的产物。开发服务器侧重快速反馈和 HMR，生产构建侧重兼容目标、压缩、缓存和可观测产物。

分析包体时先识别入口、共享依赖、动态导入和重复模块，再根据实际加载路径优化。Tree-shaking 依赖静态 ESM 和正确的副作用声明，不能只看源码是否写了 `import`。

## ENG-07

Vite 8 以 Rolldown 作为生产构建核心并依赖 Oxc 生态提升解析和转换性能。迁移应对比插件 API、产物语义、CSS、Worker、SSR、Source Map 和浏览器目标，而不是只比较构建耗时。

先建立旧版本基线和回归样本，再逐项处理不兼容插件。性能提升不能以丢失错误信息、Source Map 或兼容性为代价，迁移必须保留可回滚版本。

## ENG-03

lockfile 固定依赖解析结果，Workspace 管理多包边界和本地链接，包管理器的幽灵依赖、提升策略和严格性会影响代码在 CI 与发布包中的表现。

仓库必须固定包管理器版本并在 CI 使用冻结 lockfile。内部依赖使用明确版本策略，避免任意 `*`；更新依赖要审查变更、执行测试并保留回滚。

## ENG-05

格式化解决风格一致，Lint 发现规则问题，Typecheck 验证静态类型，测试验证行为，它们不能互相替代。提交门禁应快速、确定并与 CI 一致，较慢的全量验证可以分层运行。

规则需要说明风险和修复方式，不能不断增加无价值告警。禁止通过全局关闭规则、滥用 `any` 或跳过 Hook 来追求“绿灯”。

## OBS-01

RUM 从真实用户环境采集加载、交互、错误和业务体验；实验室数据适合复现，二者需要结合。OpenTelemetry 用 Trace、Metric、Log 和上下文传播连接前端请求与后端处理。

传统 Core Web Vitals 以硬导航划分页面生命周期，SPA 路由会让多个页面体验落在同一文档。Soft Navigations 提议用用户交互、可见内容变化和 URL 更新识别软导航，并用 `navigationId` 将 paint、event 和 layout shift 等条目归属到正确导航。API 支持状态快速变化且并非全平台基线，生产必须能力检测；不支持时使用路由事件和底层 Performance 条目的启发式口径，并明确它与标准口径不可直接混算。

采集前定义事件、导航边界、采样、版本和用户同意，避免记录输入内容、Token 和个人数据。观察条目可能延迟到达，应以导航 ID/时间边界正确 finalize 前一路由并重置当前路由指标，避免重复和串页。指标关联发布版本、页面、设备、网络与后端 trace，且记录口径版本，否则平均值很难指导修复或比较。

可运维的告警必须指向用户症状、严重度判断输入和明确 owner。症状告警用于发现影响，原因告警辅助定位；去重、抑制、升级和运行手册可防止值班被噪声淹没。事故中保存告警、版本、Trace、决策和恢复时间线，恢复后在约定窗口持续观察核心用户任务与数据完整性。复盘行动项进入可追踪台账，只有完成验收并证明风险下降才关闭。

## COMP-01

组件职责由一个稳定任务和清晰状态模型定义。API 需要表达受控/非受控状态、默认值、事件、组合、可访问语义和逃生口，不应暴露页面内部结构。

优先使用组合而不是不断增加布尔属性。复杂组件要画出状态与事件，验证键盘、焦点、异步和错误路径；只有视觉复用而无行为一致性的部分不一定应该抽成组件。

## DS-01

Design Token 用语义名称连接设计决策与实现，如背景、文本、间距和状态，而不是简单保存一组颜色值。基础令牌可映射到语义令牌，再由组件令牌表达局部用途。

主题切换需要处理继承、对比度、组件状态和运行时更新。令牌变化属于公共契约，应版本化并做视觉回归，避免组件直接引用品牌色数值。

## PLATFORM-01

配置化页面把字段、布局、校验、权限和动作描述为受控 Schema，再由渲染器映射到有限组件。Schema 必须版本化、可校验，并明确哪些能力可配置、哪些必须编码实现。

禁止把任意表达式、HTML 或脚本塞进配置。复杂交互如果需要大量条件和逃生字段，应回到正常组件开发；配置平台的价值是稳定重复场景，不是替代所有前端代码。

## PLATFORM-02

微前端适合组织边界、发布节奏和运行隔离确实独立的系统。需要明确路由、认证、依赖、样式、通信、错误、监控和回滚契约；技术拆分不能解决不清晰的业务所有权。

通信优先使用稳定事件或 API，避免直接读写其他应用内部 Store。共享依赖要有版本策略，首屏性能和故障隔离必须用真实数据验证。

## NODE-03

CLI 的契约包括参数、帮助、标准输入输出、错误流、退出码、配置优先级和中断行为。成功输出应便于人阅读或机器解析，错误信息需要说明原因、位置和恢复方式。

参数解析后仍需业务校验；取消和信号要清理临时资源。不要以交互式提示作为唯一入口，也不要在错误时仍返回 0。

CLI 还要把人类交互与脚本协议分开：正常数据写 stdout，诊断写 stderr，退出码稳定表达结果。配置优先级、`--help`、非交互模式、JSON 输出、dry-run、SIGINT 清理和危险操作确认必须可测试；不能用彩色提示或交互选择阻断 CI，也不能在部分失败时仍返回成功码。

## API-02

代码生成器先把外部规范解析成稳定内部模型，再执行命名、类型映射、模板或 AST 输出。这样能把输入差异、业务策略和打印格式分开测试。

生成结果要确定、幂等、可格式化并包含来源说明。保留无法安全表达的 Schema 警告，避免静默退化为 `any`；用快照、解析、类型检查和编译验证产物。

## CAREER-01

项目复盘要从背景、目标、约束、关键问题、方案选择、个人行动、量化结果和反思形成完整证据链。STAR 只是组织结构，不能用来包装无法验证的夸大结果。

区分团队成果和个人贡献，并说明取舍与失败。数据应有口径和来源；无法量化时用可复核的交付、风险下降或用户反馈支撑。

项目复盘应从约束和基线出发，说明自己负责的决策、备选方案、验证过程和可量化结果。STAR 只是组织结构，结果必须能回到提交、测试、指标或用户证据；团队成果要清楚区分个人贡献，不用技术名词堆砌掩盖问题规模、权衡和遗留风险。

## CAREER-05

代码评审关注正确性、设计、可读性、测试、安全和长期维护。评论应指出具体位置、风险、依据和建议，并区分阻塞问题、建议和个人偏好。

推动技术决策要倾听约束、记录异议、用实验和数据降低分歧。目标是团队形成更好决策能力，而不是由资深人员赢得每次讨论。

评审意见按阻断、建议、疑问和表扬区分强度，指向具体风险并给出可执行理由。推动技术变化要识别受影响者、迁移成本、试点指标和退出条件；争议先复述对方约束，再用实验或 ADR 收敛。合并并不代表推动结束，还要跟踪采用、缺陷和后续清理。

## CAREER-06

面试和教学表达先判断受众，再用问题、机制、例子、边界和验证组织内容。高级表达不仅给出结论，还能解释为什么、什么时候不适用以及如何发现失败。

演示和文章要有可运行证据、清晰图示和反馈迭代。影响力来自他人能够理解、复用并改进方案，而不是术语密度或发布数量。

## AIAPP-01

模型 API 的关键参数包括模型、消息、上下文窗口、输出上限、温度和停止条件。上下文不是越长越好，需要为系统规则、用户输入、检索内容、工具结果和输出预留预算。

服务端负责密钥、限流和策略，前端只接收受控结果。模型版本、采样参数和 Prompt 必须记录，超长输入、截断、拒绝和供应商故障要有明确处理。

## AIAPP-02

流式生成需要区分网络字节、SSE 事件、模型增量和最终消息。前端应增量解析结构化事件、批量更新 UI、支持取消，并在结束时确认完整状态。

不能假设每个网络块都对应完整字符或 JSON。处理断线、重复事件、部分结果、Markdown 未闭合和工具调用切换，同时避免每个 Token 都触发昂贵渲染。

## AIAPP-03

结构化输出先要求模型按约定格式生成，再用运行时 Schema 校验字段、类型、枚举和业务约束。合法 JSON 不等于业务有效，校验失败不能被自动当作成功。

可进行有限次数的修复重试，但要保留原始结果和错误原因。高风险结论需要人工复核，并为截断、空响应和供应商不支持提供降级。

结构化输出先定义运行时 Schema、版本、允许的未知值和失败策略，再请求模型生成。流式 JSON 可能尚未闭合，解析和渲染应按完整边界提交；Schema 通过也不证明业务语义正确，高风险字段仍需权限、范围和人工确认。失败时保留原始诊断但不向用户泄露敏感提示。

## AIAPP-04

Tool Calling 由模型提出工具名和参数，应用负责校验、授权、确认、执行和返回结果。模型不能直接获得系统权限，也不能决定绕过审批。

前端要展示待确认、执行中、成功、失败和可重试状态，并保留参数与结果来源。副作用工具使用幂等键和最小权限，未知工具或错误参数必须拒绝。

工具调用把模型建议变成真实副作用。前端要展示工具名称、参数摘要、权限、预计影响、执行状态和结果，区分模型请求、用户批准、服务端执行与结果呈现。重复事件、取消后迟到结果、结果未知和工具错误必须有幂等与恢复；模型给出的参数永远是待校验输入。

## AIAPP-05

Generative UI 应基于版本化消息块协议渲染 text、citation、tool call、result 和 artifact，而不是执行模型生成的任意 HTML 或组件代码。每种块都要有稳定 ID、版本、状态和运行时 Schema；组件注册表只允许映射到应用预先审核的实现，未知块显示可理解的文本降级。

流式更新要处理部分字段、乱序、重复事件、取消和最终完成，持久化则保存消息、工具调用和 UI 状态的可恢复快照。恢复后不能重复执行已有副作用，也不能假设旧版本客户端理解所有新字段。

MCP Apps 是核心 MCP 之外的可选扩展。工具通过元数据关联 `ui://` UI Resource，Host 获取资源后放进沙箱 iframe；App 与 Host 通过 `postMessage` 承载的 JSON-RPC 通信，可接收工具结果或按 Host 授权调用能力。扩展能力必须先协商，不支持时仍要返回有意义的文本或结构化结果。

沙箱是信任边界：App 不能读取宿主 DOM、Cookie、本地存储或任意导航父页面。Host 要校验消息来源、协议版本和 Schema，限制工具、外链和网络权限并应用 CSP；App 不能把 Host 传来的数据当可信 HTML。可访问名称、键盘操作、焦点返回、尺寸变化和加载/错误状态也属于协议体验的一部分。

验收时同时测试普通消息块和 MCP App：未知版本能否降级，恶意 HTML 是否被拒绝，伪造消息是否无法越权，权限撤销后调用是否停止，刷新是否保持状态，以及不支持扩展的客户端是否仍能完成核心任务。

## AIAPP-06

RAG 包含切分、索引、检索、重排、生成和引用验证。前端需要展示来源、段落、时间和冲突，明确区分“没有资料”“相关度低”和“来源不一致”。

检索内容仍是不可信数据，不能把其中指令提升为系统指令。评估集要测召回、相关性、引用正确性和无答案处理，而不只看回答是否流畅。

RAG 的引用必须从检索结果中的稳定文档、片段和版本生成，不能让模型自由编造 URL。切分、索引、过滤、召回、重排和答案合成各有独立指标；没有证据时应拒答或说明不确定。权限和租户过滤在检索前执行，删除/更新需要传播到索引、缓存与引用。

## AIAPP-09

AI 成本账本应从供应商响应中的实际 usage 出发，区分输入、输出、思考、缓存创建/命中、图片/音频和工具等计量单位，并绑定模型、版本、地域、租户、用户、功能、请求和价格快照。预估 Token 只用于调用前保护，结算以后端返回和账单为准；价格会变化，考核和预算使用带生效日期的冻结价格表，不能把文档当前价格写死为业务常量。

限流控制单位时间的 RPM、TPM 或并发，不限制累计花费；预算控制单任务、用户、租户、日/月的累计消耗。两者都应在服务端原子执行并设置软预警、硬上限、保留额度和应急流程。浏览器计数只能改善体验，不能成为费用防线；高并发下“先查余额再扣减”会竞态超支，应使用原子预留、结算和退款/释放。

缓存分为字节/响应缓存、语义缓存和供应商上下文缓存。缓存键至少包含租户与授权、模型/版本、系统提示、工具/Schema、参数、数据版本和安全策略；个性化、时间敏感或高风险任务不应盲目共享。命中后仍要执行授权、内容安全和新鲜度检查，记录来源与有效期，能按用户删除；供应商缓存的命中和计价规则必须按版本核验。

失败要区分 429、可重试 5xx、连接/首字节/总时限超时、客户端取消、永久参数/权限错误和“请求可能已执行但结果未知”。退避遵守 `Retry-After`，使用指数增长、随机抖动、单次上限和总重试预算；写操作依赖幂等键与状态查询，不能对未知结果无脑重放。熔断、并发隔离和 fallback 还要验证输出 Schema、语义质量、隐私区域和成本，不是换一个模型名即可。

上线指标把成功率、限流率、超时、重试放大、缓存命中、Token、单位成功任务成本、预算拒绝和账单差异放在同一视图。异常用量需要告警和归因，日志不保存完整提示、密钥或个人数据。可靠性和成本共同定义 SLO：降低费用不能以失败、质量下降或把负担转移给用户为代价。

## AIAPP-10

AI 产品 UX 要说明系统能力和限制，并让用户可以取消、编辑、重试、查看来源和接管。等待、低置信、拒绝、工具失败和人工升级都应有明确状态。

不要用拟人化和伪精确置信度制造过度信任。高风险结果必须可核验、可撤销并说明责任边界。

信任体验要求用户知道系统正在做什么、依据什么、会影响什么并能接管。生成中可取消，修改可预览/撤销，自动执行按风险分级；置信度不能伪造精确概率。错误、拒绝、超时和部分成功给出恢复动作，重要决定保留来源与人工确认，不用拟人文案掩盖系统边界。

## AIAPP-12

AI 会话至少包含显示给用户的 UI 消息、送给模型的模型消息、工具执行事件和派生的摘要/记忆。它们的生命周期和可信度不同：UI 消息可包含组件状态，模型消息应经过安全转换，工具结果必须保留来源，摘要只是可重建的派生数据，不能冒充原始记录。

持久化以服务端生成的会话 ID、消息 ID、租户/用户授权和幂等追加为基础。刷新、断线重试、并发标签页、重新生成和从历史分支继续，都可能产生重复或覆盖；应使用版本、序号或乐观并发控制，并把授权验证放在服务端而不是接受客户端传来的 userId。

上下文组装是受预算约束的选择问题。系统指令、当前任务、最近消息、工具状态和检索片段应有明确优先级。滑动窗口会遗忘早期约束，摘要会产生漂移，因此要保留关键事实/约束的结构化表示，记录摘要来源与版本，并用回归样本验证压缩前后行为。

验收覆盖跨租户读取、并发写入、刷新重放、摘要丢约束、分支/重试和删除未传播。更长上下文只扩大一次请求的可见范围，不等于长期记忆；长期记忆的写入、召回、冲突、投毒和用户遗忘权由 `AIAPP-13` 独立治理。

## AGENT-06

长任务需要显式任务句柄、状态、进度、取消、恢复和幂等语义。Tasks 扩展的能力必须先协商，Client 不能假设任意 Server 都支持。

任务状态存储独立于连接生命周期，重复更新和网络重试不能重复副作用。进度事件有序且可恢复，终态之后拒绝非法转移。

长任务以稳定 task id 表示，状态转换、进度、产物、取消和过期可查询。重复创建使用幂等键，客户端刷新后从服务端恢复，而非依赖内存连接；取消可能只是请求，需继续观察真实终态。部分产物、超时、重试和人工审批都要显式建模，避免把“连接断开”误判为失败。

## AGENT-09

Agent 可观测性要记录目标、步骤、工具、模型、Token、审批、错误和最终结果，并通过 Trace Context 串联 Host、Client、Server 与下游服务。日志内容要脱敏并限制保留。

结构化事件至少包含 trace/span、协议请求 ID、会话/任务、模型和工具版本、开始结束时间、状态与错误分类。日志、指标和追踪各有职责：日志保留离散上下文，指标观察总体趋势，追踪连接一次执行链路；不能把整段 Prompt 或工具结果无差别写入三套系统。

脱敏应在采集前进行，Secret、Token、个人数据和文件内容采用字段白名单、摘要或受控引用。采样、访问控制、区域和保留期限按数据敏感度定义，调试模式也不能绕过生产隐私规则。

回放依赖版本化输入输出、决策与工具结果，默认只读展示时间线，绝不重新执行有副作用操作。若需要重跑评估，应进入隔离环境、替换真实工具并使用新的关联 ID，避免被误认为原始执行。

指标关注任务成功、失败类型、人工介入、工具选错、循环长度、延迟、Token、成本和恢复率，不能只统计调用次数。可观测性验收要能从一次用户问题追到具体失败步骤，也能从聚合异常定位受影响版本。

## WEBAI-02

WebGPU 通过 Adapter、Device、Queue、Buffer、Texture 和 Pipeline 暴露 GPU 计算与渲染。设备能力、限制和丢失都必须检测，不应假设桌面独显环境。

本地推理要管理数据布局、显存、批次、预热和回收，并提供 WebGL、WASM 或云端降级。性能测试同时观察端到端延迟、内存和设备覆盖。

## WASM-01

WebAssembly 是可移植的低层字节码与执行模型，不是 JavaScript 的“更快语法”。浏览器先获取并验证模块，再编译、实例化并把显式 imports 连接到宿主；exports 才能被 JavaScript 调用。Module 可复用已编译代码，Instance 持有绑定后的运行状态，线性 Memory 是按页增长的字节数组，Table 保存可间接引用的函数或对象。沙箱限制模块直接访问宿主，但被导入的网络、文件或业务能力仍需单独授权和校验。

JavaScript 与 Wasm 之间只有明确的 ABI。数字可直接传递，字符串、数组和结构体通常要编码进线性内存并传入指针与长度；调用双方必须约定布局、所有权、分配、释放和错误。大量细碎跨边界调用、重复编码和复制可能抵消计算收益。`memory.grow()` 可能让旧的 JavaScript TypedArray 视图失效，语言绑定生成的句柄也必须在成功、异常和取消路径释放。

加载路径应采用 `instantiateStreaming` 或缓存后的 Module，并处理 MIME、网络、验证、编译、链接和运行时错误。构建产物包含 `.wasm`、JavaScript 胶水、类型、Worker 和调试映射，需固定工具链、审查来源、预算体积并验证 CDN/缓存。浏览器 DevTools、source map、语言工具和性能面板用于定位宿主调用、热点、内存增长和未释放对象；优化前同时记录下载、编译、预热、稳态、内存和正确性。

SIMD 适合数据并行，线程依赖 SharedArrayBuffer、Atomics 与跨源隔离，并必须有单线程路径。是否使用 Wasm 由计算密度、已有原生库、包体、启动、设备和维护成本共同决定；DOM 密集、业务编排或大量小调用通常更适合 JavaScript。WebGPU 面向 GPU 并行计算，Wasm 面向 CPU/可移植原生代码，两者可以组合但性能必须实测。

WebAssembly 3.0 是当前核心规范基线；具体引擎仍需特性检测。WASI 为非浏览器宿主提供能力接口，Component Model/WIT 解决组件级接口和语言互操作，但其可用性取决于运行时、工具链和版本。它们不是浏览器原生通用 API，生产设计需标注成熟度、兼容矩阵和回退，不得借“组件”名义绕过宿主能力边界。

## WEBAI-03

WebAssembly 提供接近原生的可移植执行环境，SIMD 可并行处理向量数据，但 JavaScript 与 WASM 边界复制、内存增长和初始化也有成本。

将热点计算而不是整个应用盲目迁移。基准测试应包含冷启动、稳态、数据传输和不支持 SIMD 的降级，并避免阻塞主线程。

## WEBAI-04

Worker 把 CPU 密集任务移出主线程，通过结构化克隆、Transferable 或共享内存通信。消息协议需要 ID、类型、取消、错误和版本，避免无法追踪的字符串事件。

Dedicated Worker 属于创建它的上下文，SharedWorker 可被同源多个上下文连接，Service Worker 管理网络/后台事件，Worklet 运行受约束的渲染或音频工作；选择取决于生命周期和能力，不是名称越“共享”越高级。OffscreenCanvas 能把部分 Canvas 工作转移到 Worker，但 DOM、最终 UI 状态和多数交互仍受主线程协调。

结构化克隆复制逻辑数据，Transferable 转移 ArrayBuffer 等资源后原发送方视图会 detached；SharedArrayBuffer 让多个线程访问同一内存，必须通过 Atomics、状态机和不变量同步。`Atomics.waitAsync` 避免在不能阻塞的线程同步等待，但仍需处理丢通知、取消和终止；共享内存依赖跨源隔离并必须有非共享降级。

Worker 不是无限并行，线程数量、内存、启动、序列化和同步都会影响性能。协议包含请求/任务 ID、Schema 版本、优先级、进度、背压、取消、错误与结束，组件销毁时中止任务并忽略迟到结果。测试同时观察主线程响应、总完成时间、复制字节、峰值内存、线程崩溃/重启和正确性。

## WEBAI-05

模型不是单个匿名文件，而是一组带版本的制品：权重分片、分词器、配置、运行时代码和许可证。可信清单记录名称、模型/格式版本、每个文件大小和内容摘要、兼容运行时、总空间与可选签名。摘要只能发现内容变化，清单签名或受控 HTTPS 来源才建立来源信任；下载成功、长度一致和缓存命中都不能替代验证。

大文件先写入带会话和版本的临时区域，按 Range/分片记录完成状态、ETag/摘要和重试，再在全部校验与最小加载测试通过后原子更新 active pointer。旧版本在兼容窗口保留，激活失败恢复旧指针；临时、失败、过期和孤儿分片有垃圾回收。多标签页通过锁或领导者协议避免重复下载，Service Worker 与模型清单版本必须协调，不能让新代码加载旧格式或反之。

Cache API 适合 Request/Response 语义，IndexedDB 适合事务元数据，OPFS 适合较大的私有文件和顺序/随机访问；实际选择还受浏览器、Worker、性能和工具链支持影响。使用 `navigator.storage.estimate()` 评估空间，按价值请求持久化并接受拒绝或驱逐。存储不是永久保证或可信密钥库，模型清单、业务授权和用户数据仍需独立保护。

状态机覆盖未下载、下载中、暂停/失败、待校验、待激活、可用、过期、回滚和删除。UI 展示体积、网络、耗时、版本、进度、失败原因和删除入口；取消要中止网络并回收临时文件。故障测试包括断网、进程关闭、摘要失败、空间不足、驱逐、清单更新、多标签竞争和旧 Service Worker，不能用“清空全部缓存”作为唯一恢复策略。

## WEBAI-06

本地 Embedding 流程包含模型加载、文本预处理、向量生成、存储、相似度检索和版本管理。不同模型或归一化方式生成的向量不能直接混用。

索引要绑定模型版本和数据权限，敏感文本不应因“本地处理”就无限保留。用中文和业务样本评估召回、延迟、存储和无结果场景。

本地语义搜索要把模型版本、分词/归一化、向量维度、距离度量和索引版本绑定。文档更新与删除必须同步重建或增量维护，Worker 防止推理阻塞主线程；至少用带相关性标注的查询集评估 recall/precision 类指标，并处理冷启动、内存、持久化和模型升级。

## WEBAI-07

多模态模型输入的前端职责从用户选择或授权开始，而不是从“拿到 Blob”开始。相机、麦克风和屏幕仅在用户理解用途并主动操作后请求，显示正在采集的状态，设备切换和拒绝可恢复；停止、取消、页面隐藏或任务结束时关闭轨道、Reader、Frame、编码器和对象 URL。

输入标准化先检查文件头/解码结果而非只信扩展名和 MIME，限制文件数、尺寸、像素、时长、帧率、采样率和批次。图片处理方向与颜色，视频按任务抽帧或分段，音频降采样并保留必要时间信息；WebCodecs 只在需要帧级控制且设备支持时使用，队列有上限、背压和 `close()`，否则退回媒体元素、Canvas、普通文件或服务端处理。

本地预处理或推理不自动等于隐私安全：原始媒体可能写入缓存、日志、崩溃报告或跨源 Worker，设备标识和 EXIF/地理位置等元数据也会泄露。设计应最小采集、尽早裁剪/降采样/清理元数据，明确显示哪些内容会上传、发送前确认、传输加密、设置留存与删除，并让本地/云端路由可解释。

结果体验包含预览、进度、取消、重试、部分失败、低端设备降级和可访问替代。图片提供文字说明，音频提供转写，视频提供字幕或摘要。测试覆盖权限永久拒绝、设备消失、格式损坏、后台限流、内存压力、重复提交和删除传播；专业播放、MSE、DRM、ABR 与 AudioWorklet 的深度由 `MEDIA-01` 承担。

## WEBAI-10

本地 AI 优化同时关注启动、首 Token、吞吐、内存、能耗、热降频和交互响应。高性能设备上的平均值不能代表移动端或辅助技术用户。

推理过程提供进度、取消、降级和减少动态效果支持。任务过重时应降低模型、批次或转向云端，而不是长期占满主线程和电池。

本地 AI 的预算同时包含模型下载、冷启动、首 token、稳态吞吐、主线程长任务、内存/显存和功耗代理。低端设备、后台限流和热降频会改变结果，应按设备档位测量并允许暂停、量化、小模型或云端降级。状态通过可访问文本表达，动画尊重 reduced-motion。

## AIDEV-02

Context Engineering 决定模型能看到哪些目标、代码、约束、工具和历史。上下文应最小充分、来源可追溯并按任务更新，避免把整个仓库和秘密一次性注入。

仓库指令说明构建、测试、风格、安全和禁止事项；冲突时要有优先级。过期文档、生成文件和无关日志会降低准确率，应通过资源 URI、缓存和摘要管理。

## AIDEV-03

AI 生成代码需要从静态检查、单元测试、组件/集成测试、端到端测试到人工评审逐层验证。验证组合取决于风险，不是每个改动都运行同样流程。

测试应针对规格和边界，而不是复述生成实现。高风险代码加入安全、性能、迁移和回滚验证，不能因代码“看起来合理”跳过执行。

属性测试从业务不变量生成大量输入，并把失败收缩为最小反例；变异测试故意改变实现，检查现有断言能否发现有意义的错误；fuzz 关注解析器、协议和工具入口在异常输入下是否崩溃、泄漏或超限，并设置资源上限和可重放种子。差分测试比较新旧实现或独立实现，蜕变测试在缺少精确答案时验证输入变换与输出关系。这些方法都依赖可信预言，不能把同一模型生成的实现和期望互相证明。

验证证据要降低相关失败：类型生成和契约测试可能共享同一错误 Schema，AI 生成的单元测试可能复制实现假设，视觉快照也可能把错误界面固化。高风险验收至少组合来源不同的证据，例如独立业务样例、运行时 Schema、属性/变异、真实浏览器任务与人工评审，并把失败归因到规格、实现、测试或预言。修复不能靠删除断言、过度 mock 或扩大截图阈值。

## AIDEV-09

设计稿到代码需要把布局、令牌、状态、响应式和组件语义转成可维护实现。视觉相似不是唯一目标，还要验证键盘、可访问性、内容扩展和真实数据。

视觉回归使用稳定视口、字体、数据和阈值，并人工判断有意义差异。不要用绝对定位和截图背景换取单一尺寸像素一致。

视觉验收的基准环境固定浏览器、视口、DPR、字体、数据和动画状态，并把设计 Token、响应式断点、加载/空/错/权限状态纳入用例。像素 diff 需要阈值和人工解释；还要检查语义、键盘、缩放、RTL 与动态内容，不能用绝对定位或整图背景换取单一截图相似。

## DEPLOY-01

Nginx 常用于静态资源、反向代理、TLS 终止和缓存控制。HTML 通常短缓存或协商缓存，带内容哈希的静态资源可以长缓存 immutable，二者策略不能颠倒。

代理配置要正确传递 Host、协议和客户端信息，并设置超时、体积限制和安全头。SPA fallback 只处理前端路由，不能把 API 404 重写成 HTML。

## RENDER-01

SPA、SSR、SSG 和 ISR 的选择取决于内容时效、个性化、SEO、缓存、交互和部署约束。一个应用可以按路由混合策略，不必全局二选一。

比较时同时计算 TTFB、HTML 可见时间、注水成本、数据一致性和运维复杂度。预渲染不是永久静态，缓存失效和错误恢复仍需设计。

渲染决策要按路由和用户任务记录数据新鲜度、个性化、缓存、SEO、TTFB、可交互时间与运维成本。SSR/SSG 失败时定义状态码和降级，客户端导航保持同一数据契约；缓存键、失效和用户身份不能混淆。用真实网络与服务端故障验证，而非只比较首屏截图。

## RENDER-02

RSC 在服务端执行并把可序列化结果传给客户端组件，Streaming 允许 HTML 分段到达，Suspense 划分等待边界，Hydration 为已有 HTML 绑定交互。它们解决不同层次问题。

服务端与客户端边界要避免泄露密钥、传递不可序列化值和重复获取。流式错误、注水不一致、客户端导航和缓存必须纳入测试。

## DATA-02

乐观更新在服务端确认前先修改界面，需要保存旧快照、生成幂等请求并在失败时回滚。并发写入时单一快照可能过期，应结合版本、冲突响应或重新获取。

离线突变队列必须持久化顺序、用户身份和重试状态，账号切换时隔离。并非所有操作适合乐观处理，高风险和不可逆动作应等待确认。

离线队列记录用户/租户、操作 id、基版本、重试次数和创建时间；上传允许重复但必须幂等。409 或版本冲突要回到领域规则，呈现本地与远端差异供合并，不能一律最后写入覆盖。注销、账号切换和删除数据时同步清理队列，重连采用上限退避。

## COLLAB-01

WebRTC 负责点对点媒体或数据通道，仍需要信令和 STUN/TURN。CRDT 通过可合并操作处理并发编辑，但不自动解决权限、业务不变量和历史保留。

协作系统要定义文档身份、参与者、离线合并、意识状态、撤销和恢复。网络分区、重复消息和版本升级必须通过多客户端测试验证。

CRDT 收敛不等于业务正确：文档 Schema、权限、最大消息、历史压缩和撤销范围仍需服务端约束。信令不承载长期文档真相，ICE 失败应转 TURN 或服务端通道；多客户端测试覆盖离线并发、重复/乱序更新、版本升级和恶意大消息，并验证最终状态及审计。

## GRAPHICS-02

WebGL/WebGPU 渲染管线把顶点、纹理、Uniform/Buffer 和 Shader 组合为 GPU 命令。性能来自批处理、减少状态切换、合理数据布局和资源复用，不只是把代码交给 GPU。

资源要在生命周期结束时释放，并处理 context/device lost。高分屏尺寸、颜色空间、兼容性和无障碍替代内容同样属于交付范围。

## ANALYTICS-01

埋点模型先定义业务事件、触发时机、主体、对象、属性和版本，再实现采集。事件名和字段要稳定，客户端与服务端事件需要可关联但避免重复计数。

数据质量通过 Schema 校验、采样检查、漏斗守恒和发布对比监控。个人数据、自由文本和稳定标识必须最小化并遵守同意与留存规则。

事件字典为名称、属性类型、触发时机、身份/租户、版本和 owner 建立单一口径。客户端批量、离线和重试会产生重复或乱序，服务端需校验和去重；漏斗/留存必须能从原始事件重算。采样、同意、删除和敏感字段策略在采集前确定，异常质量自动告警。

## I18N-01

国际化把文案、复数、插值、日期数字和方向从组件逻辑中抽离。翻译键应表达语义，不能把完整句子拆成无法重排的碎片，也不要拼接不同语言片段。

界面要测试文本膨胀、RTL、字体、换行和键盘顺序。图标方向、布局逻辑属性和可访问名称需要随语言正确变化。

可翻译 UI 不拼接句子，复数、性别、语序和插值由本地化消息处理；`lang` 与 `dir` 分别描述语言和方向。CSS 采用逻辑属性，图标只在有方向语义时镜像。伪本地化、RTL、长文本、缺失键和字体回退进入自动/人工验收，禁止把机器翻译当工程完成证据。

## I18N-02

时间点应使用明确时区或 UTC 传输，展示时依据用户和业务时区格式化。日历日期、墙上时间和绝对时间是不同数据类型，不能都用一个无时区字符串表示。

使用 Intl 处理数字、货币、相对时间和排序，并测试 DST、跨日和非公历地区。金额同时保存数值、币种和精度，不能直接对格式化字符串计算。

Temporal 用不同类型表达 `Instant`、纯日期/时间、带时区时间和 Duration，避免传统 `Date` 把多个概念混在一起。把墙上时间转换成具体时刻时必须决定 DST 缺失或重复时刻的消歧策略；Duration 的比较与舍入还需要相对起点。生产使用前检测运行时支持，polyfill 不能改变传输契约。

## IDENTITY-01

Cookie 可由浏览器自动携带，Session 通常把状态保存在服务端，Bearer Token 则由持有者证明访问权。选择取决于威胁模型和部署边界，不是“Token 一定更现代”。使用 Secure、HttpOnly、SameSite、短期访问凭证、刷新轮换和可靠退出；前端存储不能消除 XSS 风险，多设备会话与撤销必须由服务端维护。

浏览器正在按顶层站点分区第三方存储。CHIPS 的 `Partitioned` Cookie 在“嵌入来源 + 顶层站点”分区中保存，适合每个嵌入站点独立状态，不能用来恢复跨站共享身份。它仍需 Secure，并继续遵守最小化和 SameSite 等约束。

Immediate UI 尝试在明确登录动作后立即提供本地可用的 Passkey 或受管密码；调用前检测 `PublicKeyCredential.getClientCapabilities()` 的 `immediateGet`，无凭证、不支持、私密模式或用户取消时通常以 `NotAllowedError` 进入标准登录，不应显示成账户不存在。它截至 2026-07-29 仅由 Chrome 支持，属于渐进增强，不能替代服务端 challenge、凭证验证、账号恢复或其他浏览器路径。

Storage Access API 用于在嵌入上下文中、经过用户动作和浏览器策略后申请访问未分区 Cookie；它不是默认绕过第三方 Cookie 限制的开关。请求前先判断是否真的需要共享身份，拒绝后提供跳转顶层登录、一次性授权码或人工流程。

FedCM 把联合身份的部分交互交给浏览器，能够减少跨站跟踪和第三方 Cookie 依赖，但实现与兼容仍在演进。应采用能力检测和渐进增强，保留标准 OAuth/OIDC 顶层重定向或弹窗回退，不能把实验 API 作为唯一登录入口。

Digital Credentials API 让用户经浏览器或系统中介选择并出示可验证凭证，涉及持有者、发行方、验证方、选择性披露和用户同意。它目前只作为成熟度标注的观察项：不得把草案行为当跨浏览器承诺，也不得把数字凭证等同于应用会话；不支持时必须回退到现有身份和人工核验流程。

验收覆盖顶层登录、跨站 iframe、第三方 Cookie 禁用、不同顶层站点分区、权限拒绝、退出/吊销和不支持新 API。禁止用浏览器指纹或隐藏跳转绕开用户的隐私选择。

## PRIVACY-02

跨区域合规先做数据分类、处理目的、存储位置、接收方和传输路径盘点，再决定本地化、脱敏、同意、合同和访问控制。前端 SDK 和埋点常是隐蔽跨境来源。

工程控制包括地区配置、字段最小化、日志过滤、下载审计和用户权利入口。法律条文随地区变化，产品方案需由专业合规人员复核，技术文档不能替代法律意见。

## ARCH-01

架构质量属性包括性能、可靠性、安全、可维护性、可访问性和成本，需要写成可测场景：在什么刺激下、系统处于何状态、期望什么响应。抽象的“高性能高可用”无法评审。

架构决策是在约束下权衡，不存在同时最大化所有属性的方案。高风险假设通过原型、容量测试和故障演练验证，并保留决策与后果。

质量属性必须可度量，例如延迟分位数、可用性、恢复目标、数据一致性、安全边界和可维护成本；架构图把用户任务映射到组件、数据、信任和故障传播。方案比较记录约束、假设和验证，不能以流行技术或抽象层数量证明架构先进。

## ARCH-03

渐进迁移先建立现状基线和边界，再按可独立交付的切片替换旧系统。Strangler 模式通过路由或适配层把流量逐步转向新实现，直到旧能力可以安全删除。

兼容层必须有退出条件，双写要处理顺序、失败和对账。每个阶段都保留监控、回滚和数据迁移策略，避免长期运行两个事实来源。

渐进迁移先建立兼容缝、流量/功能切片和新旧双向回退，定义每阶段入口、数据所有权、观测指标和删除旧路径条件。双写与双读必须处理顺序、补偿和差异审计；迁移完成以旧依赖删除和指标稳定为准，而不是新代码已经上线。

## ARCH-04

技术债按影响、利息、风险和修复成本管理，而不是把所有旧代码都视为债务。依赖升级需要所有者、支持周期、弃用信息、兼容测试和升级窗口。

制定预算和退出标准，优先处理安全、不可恢复故障和阻塞交付的债务。只创建永不关闭的债务清单不会改善系统。

技术债条目要说明受影响能力、风险、证据、继续拖延的成本、解决选项和 owner。用风险×概率×影响与机会成本排序，绑定业务或平台路线；治理既包含偿还，也可接受、隔离或淘汰。完成后验证缺陷、交付时间或运维成本下降，不能用重构代码量证明价值。

## BACKEND-03

对象存储适合大文件和静态对象，前端常通过短期预签名 URL 直传或下载。分片上传需要 upload ID、分片编号、校验、完成和取消协议，并支持断点恢复。

服务端仍要验证权限、类型、大小、摘要和病毒扫描。CDN 缓存键、私有内容、失效和成本必须明确，预签名 URL 不应长期暴露。

## CLOUD-01

Serverless 关注按请求执行和平台托管，容器封装运行环境，Kubernetes 编排 Pod、Deployment、Service 和 Ingress。前端高级工程师需要理解交付边界，不必取代平台工程师。

部署必须配置健康检查、资源、密钥、伸缩和滚动策略。平台抽象不能消除冷启动、网络、状态和成本，选择应依据负载和组织能力。

## CS-01

复杂度描述输入规模变化时，时间或空间成本的增长趋势。分析先定义规模 `n`、基本操作和最坏/平均/摊还条件，再讨论 `O(1)`、`O(log n)`、`O(n)`、`O(n log n)`。Big-O 忽略常数和低阶项，不能替代真实设备上的延迟、内存和主线程测量。

基准要覆盖多个数量级，固定输入生成和环境，区分预热、缓存、GC、网络与序列化影响，并报告分布而非只报最快值。出现拐点时检查算法退化、无界缓存、数据复制和浏览器资源限制。

工程决策不仅问“能否算完”，还问是否阻塞交互、峰值内存是否可接受、是否能取消、是否值得在客户端执行。分块和 Worker 改善响应性但不减少总计算量；服务端聚合会引入网络、权限和一致性成本。

## CS-02

数组适合连续遍历与随机访问，Map/Set 适合身份查找和去重，队列适合调度，堆适合动态 Top-K，树适合层级，图适合依赖与关系。选择由访问、插入、删除、顺序、内存和键语义共同决定，不能把所有问题都转成数组扫描。

算法模式覆盖稳定排序和比较器、二分的闭开区间、双指针/滑动窗口、递归与显式栈、DFS/BFS、拓扑排序、贪心和动态规划。每个实现都应写出不变量、终止条件、复杂度与退化输入，而不是背诵代码形状。

测试覆盖空输入、重复、非法键、环、极深树和极端规模。属性测试可验证排序有序且保持多重集合、拓扑结果满足每条依赖、去重满足幂等；示例通过不代表一般正确。

## CS-03

大数据 UI 的第一步是减少工作：稳定索引、增量更新、避免重复排序/格式化、虚拟化不可见内容。随后再选择分块、迭代器、Streams、Worker、TypedArray、Transferable 或服务端计算。

Worker 能释放主线程，但结构化克隆、消息数量、Transferable 所有权、结果合并和销毁都可能形成新瓶颈。协议要支持批量、背压、进度、取消、错误和版本；组件卸载后必须终止任务并释放引用。

缓存要有键、容量、淘汰、失效和命中率证据。无界 Map、重复对象图和完整中间结果会放大 GC；流式处理应控制并发和峰值内存，不能把全部块重新汇总后才渲染。

验收比较主线程、Worker 与服务端方案的交互延迟、吞吐、复制/网络成本和内存峰值，并在设备能力不足时降级。只证明十万条数据最终处理完成，不等于具备前端大数据能力。

## DEBUG-01

系统化调试从“现象、期望、最小复现、时间线和环境”开始。先固定版本、账号、数据、网络和浏览器，再收集 Console、Network、Performance、源映射、服务端日志和发布信息；没有证据就修改代码会制造新的变量。

JavaScript 调试要理解断点、条件断点、日志点、调用栈、作用域、闭包、事件监听器、异步堆栈和异常暂停。Source Map 把产物位置映射回源码，但必须与当前制品严格对应，并避免把包含敏感源代码的映射无控制地公开。

浏览器问题常跨越事件循环、渲染、缓存和网络。排查竞态时记录请求开始/取消/完成及状态写入顺序；排查白屏时区分资源加载、语法/运行时错误、路由、CSP 和 hydration；排查“本地正常”时对比环境变量、构建目标、缓存、Cookie、代理和区域依赖。

生产诊断采用关联 ID、版本号、结构化错误、采样和脱敏。Git bisect 可在可重复的好/坏判定下定位引入提交；若判定脚本不稳定，二分结果也不可信。修复后要添加能在更低层捕获问题的回归测试或监控，而非只保存一次临时操作。

合格记录应包含预期、实际、至少三个可证伪假设、每步证据、根因、最小修复、回归验证和后续预防。重启、清缓存或扩大超时只能作为实验，不能自动等同根因。

## WEB-05

Web Components 由 Custom Elements、Shadow DOM、HTML Template/Slot 和相关生命周期组成，目标是在浏览器原生层建立可复用组件边界。自定义元素名称包含连字符，构造函数保持轻量，连接/断开和属性变化在对应生命周期中处理。

Shadow DOM 提供 DOM 与样式封装，但不是安全沙箱。外部脚本仍可持有引用，继承属性、CSS 自定义属性和事件仍可能跨边界；样式通过 `:host`、part 和语义令牌开放受控扩展，不能依赖消费者穿透内部选择器。

属性是字符串化声明接口，Property 可以承载运行时值，二者需要明确反射与默认策略。事件是跨框架通信的稳定方式，要决定 `bubbles`、`composed` 和 `cancelable`，避免把内部实现对象直接泄露。Slot 负责内容组合，并需处理备用内容和 slotchange。

与 React、Vue 或其他框架互操作时验证布尔属性、对象 Property、事件命名、服务端渲染、hydration、表单参与和类型声明。复杂表单控件可研究 ElementInternals，但必须保留标签、错误、焦点和提交语义。

验收需要在纯 HTML 和至少两个框架宿主中运行，检查升级前内容、重复连接、销毁清理、键盘/屏幕阅读器、主题覆盖和无 Shadow DOM/不支持特性的降级。Web Components 适合稳定跨框架边界，不应替代应用内部所有普通组件。

## NET-01

浏览器访问 URL 时通常经历 URL 解析、DNS、连接建立、TLS、HTTP 请求、服务端处理、响应传输与缓存判定。HTTP/2 复用一条连接上的流，HTTP/3 基于 QUIC 降低传输层队头阻塞；协议版本、连接复用和优先级由浏览器与服务端协商，页面脚本不能把它们当固定事实。

HTTP 缓存区分浏览器私有/共享缓存、强缓存和验证缓存。`Cache-Control` 描述新鲜度和存储策略，ETag/Last-Modified 支持条件请求；带哈希静态资源适合长期不可变缓存，HTML 和接口需依据更新、一致性、隐私及授权设计。Service Worker Cache 与 HTTP Cache 是不同层，不应混为一谈。

Cookie 具有 Domain、Path、Expires/Max-Age、Secure、HttpOnly 和 SameSite 等属性，并可能随请求自动携带。CORS 是浏览器对跨源读取的控制，不是服务端授权；预检验证方法和请求头，成功返回 CORS 头也不能证明调用者有业务权限。

Network 面板要从队列、DNS、连接、SSL、TTFB、内容下载、优先级、发起方、缓存来源和响应头建立证据。慢请求可能来自服务器、丢包、连接竞争、资源优先级或主线程消费；只看总耗时无法定位。

设计与验收要覆盖缓存命中/验证/失效、离线和弱网、重试与幂等、重定向、跨域凭据、证书错误、HTTP/2/3 降级和旧资源兼容。优化前记录瀑布图、协议、命中状态和真实用户分布，避免以一次本机快照代替结论。

## UX-01

交互设计从用户目标、上下文和任务流开始。先画出入口、关键决策、系统反馈、退出和恢复，再设计页面；仅交付静态“正常态”无法覆盖加载、空、部分成功、校验失败、权限拒绝、网络中断、并发冲突和长任务。

状态体验要回答系统正在做什么、发生了什么、用户还能做什么。即时操作提供就近反馈，耗时操作显示真实进度或不确定状态；破坏性动作说明影响并提供合适确认或撤销。错误文案应指出问题、保留输入并给出可执行恢复路径。

可用性验证不是询问“喜欢吗”，而是给代表用户完成代表任务，记录完成率、耗时、错误、求助和主观负担。五个样例能发现常见问题但不能代表统计结论；高风险或多群体产品需要更系统的招募、无障碍参与和定量数据。

信息架构、视觉层级、内容设计和微交互共同影响理解。组件一致性服务于学习迁移，但不能以统一为由增加任务步骤。骨架屏、动画和乐观更新要遵循真实性，避免制造虚假进度、意外跳动或不可逆误操作。

验收至少覆盖端到端任务流、键盘和辅助技术、窄屏/触控、慢网、错误恢复和用户测试记录。输出应包括问题严重度、证据、修复方案与复测结果，而不仅是设计稿。

## RUNTIME-01

浏览器扩展位于页面与浏览器高权限能力之间。Manifest V3 把 permissions、host permissions、content script、后台 service worker、消息、存储和 web-accessible resources 显式化；权限应按任务申请，不能默认全域。

后台 worker 可能休眠或重启，关键状态必须持久化且操作幂等。content script 与页面脚本处在不同执行世界，但页面仍可控制 DOM 和输入；跨边界消息要验证发送者、tab/frame、来源、Schema 与业务授权。

企业策略、浏览器版本、商店审核和 IDE/WebView 容器会禁用部分能力。验收覆盖权限拒绝、worker 重启、升级迁移、恶意页面消息和普通 Web 降级。

## RUNTIME-02

Electron 由 main、renderer 和 preload 构成。Renderer 默认按不可信网页处理，通过 `contextIsolation` 和白名单 preload API 使用系统能力；禁止广泛 Node 集成、任意 IPC、危险远程导航和可执行远程代码。

Tauri 通过 Rust command、capability 和窗口/来源配置限制系统能力。两类容器都要校验调用者、参数、路径、URL 与返回数据，文件路径归一化并限制根目录，外链交给系统浏览器。

代码签名、公证、自动更新、深链、协议注册、崩溃报告和企业分发属于功能的一部分。更新包要验证、支持版本迁移和回滚；Secret 不打入前端包，遥测遵守最小化与同意。

## MOBILE-01

React Native/Expo 不是“把网页换一套标签”。新架构通过 JSI、Fabric 和 TurboModules 连接 JavaScript、原生模块与 UI 渲染；线程、同步/异步调用、序列化和原生对象生命周期都会影响正确性与性能。WebView Bridge、小程序 JSBridge 和原生模块应分别建模，不能混为一谈。

移动应用随时经历冷启动、前台、后台、挂起、系统回收和恢复。网络请求、定时器、媒体、定位和编辑状态要跟随生命周期暂停/恢复；权限包含未决定、允许、拒绝、永久拒绝和系统设置变化，拒绝必须有可用替代路径。

深链与推送是外部不可信入口，要验证 Scheme/Universal Link/App Link、参数、登录态和导航权限。敏感凭证使用平台安全存储；相册、摄像头、定位、蓝牙和通知按需申请并说明用途。

OTA 只更新与已安装原生二进制兼容的 JS/资源，不能绕过商店审核或调用不存在的原生 API。维护原生版本—JS bundle—Schema 兼容矩阵、灰度、签名、回滚和强制升级边界；崩溃符号、启动、内存、列表帧率和包体需要生产监控。

选择 Web、PWA、Hybrid、React Native/Expo、Flutter 或原生开发应由能力、体验、团队、发布和长期维护约束决定。完整掌握要求能设计边界和交付闭环，不要求深入实现所有 iOS/Android 原生细节。

## SEO-01

搜索可发现性是发现、抓取、渲染、索引和结果呈现的链路。技术 SEO 的目标是让搜索引擎稳定访问并理解公开内容，不保证排名；内容质量、站点信誉、竞争和搜索系统变化仍会影响结果。

HTTP 200 应返回真实内容，永久/临时迁移使用合适重定向，缺失页返回 404/410，避免软 404 和重定向链。robots.txt 控制抓取，不保证移出索引；`noindex` 控制索引但页面必须可抓取到该指令。canonical 用于表达首选重复 URL，不是强制重定向或隐藏错误架构的万能开关。

sitemap 列出希望发现的规范 URL，并与站内链接、状态码、canonical 和多语言 `hreflang` 保持一致。参数、筛选、排序和分页要避免生成无限 URL 空间；重要页面应有可抓取的语义链接，而不是只有点击脚本才能到达。

JavaScript 站点要保证关键标题、正文、链接和元信息在搜索引擎可执行路径中可用。SSR、SSG、CSR 和流式渲染各有部署与缓存取舍，选择要以内容更新、个性化、可恢复和真实抓取证据判断。结构化数据必须与用户看到的内容一致，并通过 Schema 与富媒体结果工具校验。

发布前自动检查标题、canonical、robots、sitemap、状态码、结构化数据和孤儿页；发布后结合服务日志、Search Console 的网址检查、抓取/索引覆盖与搜索展现观察。索引变化存在延迟，应记录发布日期和版本，避免把短期波动直接归因于单一改动。

AI 搜索仍依赖可抓取、可索引、对用户有价值的公开内容，不存在能保证被 AI 回答引用的专用 Schema。测量可结合搜索引荐、落地页、转化、服务日志和 Search Console，但来源标记与产品界面会变化，无法归因的流量不能包装成确定结论。

## AIAPP-11

实时多模态交互把麦克风、摄像头或屏幕媒体经浏览器采集，通过 WebRTC 或 WebSocket 发送给实时模型，并把音频、文本、工具事件和状态增量返回。WebRTC 适合实时媒体与网络适应，WebSocket 更易控制自定义消息；选择取决于供应商协议、延迟、代理兼容和运维能力。

采集必须在用户动作后请求权限，并持续显示录制、静音和共享对象。音频链路涉及采样率、声道、编码、回声消除、降噪、自动增益和重采样；格式不匹配会造成速度、音高、延迟或识别问题。模型长期密钥不能下发浏览器，应由服务端签发短期、最小权限会话凭证。

VAD 用于判断说话开始/结束，barge-in 则允许用户在系统播放时打断。打断必须停止旧音频缓冲、取消或标记旧生成、保留已确认上下文，并避免把扬声器输出重新送入麦克风。过度灵敏会误打断，过度迟钝会让对话显得僵硬，需要以真实噪声环境测量。

界面同时呈现连接、聆听、思考、调用工具、播放、被打断、重连和失败状态，提供实时字幕、键盘、静音、结束会话和切换文本。断线恢复要区分可续接会话与重新开始，处理事件序号、重复消息和工具副作用幂等。

隐私上明确采集目的、传输对象、保存期限和删除方式，不默认保存原始音视频。质量指标包括首音频时间、端到端延迟、打断延迟、转写错误、断线率、任务成功和单会话成本；无字幕、无文本降级或弱网不可恢复都不能算完成。

## WEBAGENT-01

浏览器 Agent 可以通过视觉/DOM 模拟点击和输入，也可以调用网页显式暴露的结构化工具。WebMCP 的目标是让页面以命令式 JavaScript API 或声明式 HTML 表单标注注册工具，提供名称、描述、JSON Schema 和当前页面状态，从而减少脆弱的界面猜测。

WebMCP 与 MCP/MCP Apps 不同：MCP Server 是 Agent Host 可连接的远程或本地能力；MCP App 是工具返回并由 Host 沙箱承载的 UI；WebMCP 是已打开网页向浏览器 Agent 暴露页面内操作。三者的发现位置、凭证、执行上下文、生命周期和用户可见性不同。

工具应在适用页面状态注册、失效时注销，名称和描述准确且不重叠。输入必须运行时校验，副作用幂等；购买、发送、删除和授权等高风险动作在页面中展示影响并要求用户确认，完成后同步更新可见 UI。

安全依赖稳定来源、`tools` Permissions Policy、跨源 iframe 显式授权和正常业务鉴权。Agent 不能因为调用了页面工具就绕过权限、CSRF、防欺诈或速率限制；页面内容、工具描述和模型参数都可能是不可信输入。

截至 2026-07-29，WebMCP 是 Chrome 149 Origin Trial 中的拟议标准。生产设计必须做能力检测，把它当渐进增强；没有 API、页面关闭或浏览器不支持时，语义 HTML、键盘、屏幕阅读器和人工操作流程仍能完成任务。

## ENG-06

CI 从受控提交构建并运行格式、类型、测试、安全和内容检查；CD 将通过验证的不可变制品逐环境晋级。构建一次能减少环境漂移，镜像和静态包使用 digest、签名、SBOM 与来源记录，而不是依赖可变 `latest` 标签。

Registry 管理制品身份、权限、保留和漏洞状态。密钥在运行或流水线受控阶段注入，不写入源码、日志、镜像层或浏览器包。配置和数据库迁移要向前/向后兼容，使新旧版本在灰度和回滚窗口内能共存。

部署前定义 readiness/liveness、启动超时、SLO 和关键业务探针。金丝雀或蓝绿发布逐步扩大流量，以错误率、延迟、核心转化和资源指标决定继续或停止；功能开关可以降低发布风险，但不能替代授权，也必须有清理期限。

回滚需要明确触发阈值、责任人、目标时间和验证步骤。前端还要处理 HTML 与旧 chunk、Service Worker、CDN 和 API 版本不一致；内容、知识库、配置和代码都属于制品输入，变更后必须重新构建并留下版本标识。

发布后记录版本、变更、批准、制品摘要、指标和事件。事故复盘关注时间线、影响、控制为何失效、修复与预防，不以寻找个人责任代替系统改进；恢复演练和回滚成功证据比文档中写有“可回滚”更可信。

回滚命令成功不等于业务恢复。发布策略要预先定义技术 SLO、核心用户任务和数据完整性三类停止/恢复条件；涉及数据库或配置时采用 expand/contract，使新旧版本在灰度和回滚窗口兼容。恢复后保持变更冻结并观察约定时长，确认错误、延迟、缓存、队列和关键转化稳定，再关闭事件；行动项必须有 owner、期限和验收证据。

## JS-07

可迭代对象通过 `Symbol.iterator` 返回迭代器；迭代器的 `next()` 返回 `{ value, done }`。生成器把状态机写成可暂停函数，但消费方提前结束时仍要通过 `return()` 或 `finally` 完成清理。异步迭代把每一步变成 Promise，适合流式分页，却不自动提供背压、取消和资源释放。

`Proxy` 拦截对象基本操作，`Reflect` 提供与内部操作相近的默认转发。代理必须遵守不可配置属性、不可扩展对象等不变量，并会改变身份、调试和性能特征，因此只应用在明确边界。资源管理要覆盖成功、异常、取消和重复释放；惰性序列也必须证明会终止。

## PERF-03

主线程按任务执行脚本，在渲染机会中完成样式、布局、绘制和合成。Long Task 观察超过阈值的单个任务；Long Animation Frame 观察完整渲染帧，因此能发现多个短任务、渲染工作合计造成的卡顿，并提供更细的脚本归因。两者与 INP 相关，但不能相互替代或单凭一项完成根因判断。

实验室使用 Performance trace 复现并查看调用栈、布局和绘制；现场使用 `PerformanceObserver` 订阅受支持的条目，设置采样、缓冲上限、隐私脱敏与清理。功能检测失败时退回 longtask、事件耗时和关键业务计时。优化可采用分片、调度、减少布局、Worker 或降低渲染量，并以相同任务的正确性与前后数据验收。

## H5-03

原生 `<audio>`/`<video>` 负责通用加载与播放。前端处理 `preload`、`poster`、字幕轨、自动播放限制、错误、seek、后台切换和资源释放；专业编码、MSE、DRM 与低延迟媒体进入 `MEDIA-01`。Geolocation 只能在安全上下文和用户授权下使用，选项在精度、耗电与等待时间之间取舍；浏览器接口没有统一取消方法时，可用业务状态忽略迟到结果，但仍要处理超时、权限永久拒绝、坐标精度和隐私说明。

地图 SDK 是第三方高权限脚本。Key 可按厂商设计公开但必须限制域名、配额和能力，服务端 Secret/签名密钥绝不进入浏览器。异步加载需处理重复加载、版本、插件、错误和 CSP，覆盖物、事件和地图实例在卸载时销毁。坐标系转换必须明确来源/目标并有样例验证；地图不可用时以地址、坐标文本、列表或外部导航链接保留核心任务，不能让单一厂商决定业务数据模型。

浏览器上传前检查数量、大小和可解码内容，但服务端仍需重新验证类型、权限和对象键。业务服务端签发短期、最小目录/类型/大小的 Policy、预签名 URL 或 STS，浏览器直传对象存储，完成后由服务端依据可信回调或主动查询确认；永久 AccessKey、任意 Bucket 权限和客户端自报完成都不可信。CORS、内容处置、恶意文件扫描、生命周期和 CDN 访问是端到端边界。

大文件使用初始化—上传 Part—完成的状态机，保存 upload ID、分片号、大小和 ETag/摘要；限制并发、单片重试与总预算，支持暂停/恢复、取消和签名过期刷新。完成请求幂等并校验全部分片，失败/取消/过期任务清理遗留分片。进度以已确认字节计算而不是简单累加尝试量，测试弱网、刷新、重复回调、乱序完成、空间/配额和跨账号访问。

## MEDIA-01

媒体文件的容器负责组织音视频轨道、时间信息和元数据，编码格式负责压缩单条轨道；浏览器支持某个编码并不代表支持任意容器、参数或硬件路径。采集/网络输入到播放通常经过解封装、解码、同步、处理、渲染，录制或导出则反向经过编码和封装。前端必须先探测类型、配置、分辨率、帧率和设备能力，再选择原生媒体元素、MSE、WebCodecs、WebRTC 或服务端转码。

WebCodecs 提供 Video/AudioEncoder、Decoder、Frame 和 EncodedChunk 等低层对象，不负责容器解析、网络协议或 UI。时间戳、duration、关键帧和编码配置必须一致；`decodeQueueSize`/`encodeQueueSize` 等队列信号用于背压，不能无限喂入帧。Frame、AudioData 和 Chunk 可能持有稀缺底层资源，转移、克隆和 `close()` 的所有权要明确，成功、错误、取消和组件卸载都要释放。

MSE 通过 MediaSource 和 SourceBuffer 把分段媒体追加给媒体元素，是 DASH/HLS 等自适应播放实现的基础之一。追加、删除和切换受更新时间、时间范围、配额与编码连续性约束；播放器要控制前后缓冲、处理 seek、清理旧片段，并以吞吐、缓冲、码率和设备能力选择清晰度。EME 只定义浏览器与内容解密模块的交互，许可证、身份、密钥策略和内容授权仍属于 DRM/服务端系统，不能在前端复制密钥或绕过授权。

MediaStream/WebRTC 负责实时轨道和传输，AudioWorklet 在音频渲染线程执行低延迟处理；Worklet 代码必须小而确定，主线程通过消息传递参数。实时管线处理设备切换、静音、回声/噪声策略、断线、后台限流、时钟漂移和音画同步。录制、预览和处理停止后关闭媒体轨、Worklet 节点、编码器、对象 URL 和缓冲，避免相机指示灯、内存或硬件资源残留。

摄像头、麦克风和屏幕捕获必须由清晰用户意图触发。设备标签和完整枚举常在授权后才可用；约束协商失败、永久拒绝、设备拔出、系统停止共享会分别表现为错误或轨道 `ended`/`mute`，界面要区分并提供恢复。热切换时先建立新轨道并替换发送者/预览，再停止旧轨道；取消、导航和卸载路径都要关闭硬件。屏幕共享指示和停止入口由浏览器控制，应用不得伪造或规避。

Region Capture 只在支持的环境中裁剪已共享标签页区域，句柄和目标元素都可能失效；Picture-in-Picture 也受用户激活、文档状态和平台能力限制。两者必须能力检测并保留普通共享/内嵌播放路径。系统音频、窗口选择和移动端支持差异很大，兼容矩阵应记录真实设备、授权状态、前后台和切换结果，而不是根据 API 是否存在推断可用。

质量不能只看“能播放”。至少观察启动时间、卡顿率、码率/清晰度切换、掉帧、音画同步、直播延迟、内存和功耗代理，并在目标设备、弱网和后台/前台切换下复验。提供字幕、转写、音频描述或等价文本，播放器支持键盘、可见焦点和减少动态效果。权限按需请求，原始媒体、设备标识和元数据遵循最小采集、明确上传与可删除原则。

## BROWSER-01

浏览器将文档解析成 DOM/CSSOM，生成渲染树并经历样式、布局、绘制和合成。属性变化落在哪一阶段决定成本；读写布局属性交错可能触发同步布局。事件从捕获到目标再冒泡，委托利用传播处理动态节点，但监听器、AbortSignal 和组件销毁必须形成清理闭环。

Cookie 会随匹配请求发送，适合服务端会话标识而非大数据；Web Storage 是同步字符串键值存储，主线程与容量边界明显；IndexedDB 是异步、事务化、可索引的结构化数据库。三者均不是可信安全区，敏感数据、跨标签一致性、版本升级、失败回滚和浏览器驱逐都需单独设计。

## BROWSER-02

Intersection、Resize、Mutation 和 Performance Observer 用浏览器已掌握的变化信号替代高频轮询。观察器回调仍会占用主线程，必须控制观测范围、批量处理并断开订阅。`requestAnimationFrame` 对齐视觉帧，空闲回调只适合可推迟工作，后台页面会被限流，任何调度都不能依赖固定时间必然执行。

`scheduler.postTask()` 可按 user-blocking、user-visible、background 排优先级，并用 AbortSignal/TaskController 取消或调整；`scheduler.yield()` 把长函数的 continuation 放回有优先级的任务队列。它们不是 Baseline，需特性检测并退回基于任务的分片。优先级表达用户价值，不是让任务立刻执行；过多 yield 会增加开销，连续高优先级任务会让后台工作饥饿，因此同时比较交互延迟、总完成时间和公平性。

页面会经历 visible、hidden、frozen、resumed、terminated 等状态，BFCache 还可能让页面在不重载的情况下恢复。保存动作应幂等，不能只依赖卸载事件。BroadcastChannel 用于同源广播，SharedWorker 可维护共享进程内状态，Web Locks 可协调互斥任务；消息仍需版本、来源语义、去重、超时、领导者租约和无支持时的降级。

## SEC-05

编码只改变表示，摘要用于完整性指纹，HMAC 证明共享密钥持有者，数字签名证明私钥持有者，对称/非对称加密保护机密性。Web Crypto 的算法名、用途、IV/nonce、哈希和密钥参数必须匹配；不能用 `Math.random()` 生成安全随机数，也不能自行设计密码算法。

密钥生命周期包括生成、导入、派生、存储、使用、轮换、撤销、备份和销毁。浏览器中的脚本受 XSS、扩展、日志和设备控制者影响，因此前端密钥不能自动成为服务端信任根。高价值根密钥与最终授权留在受控服务端或 KMS/HSM，前端仅持最小用途、短期或不可提取材料。

## TEST-01

测试预言说明给定输入或状态下什么才算正确。示例测试覆盖已知场景，属性测试从不变量生成输入并收缩失败；变异测试通过改变条件、边界和返回值衡量断言是否真正约束行为；结构化 fuzz 让解析器和协议入口面对异常但受限的输入；差分测试比较独立实现，蜕变测试验证输入变换后输出应保持的关系。选择方法取决于风险，行覆盖率只能说明代码被执行，不能说明结果被正确判断。

替身要按语义区分：stub 提供固定响应，spy 记录调用，fake 用简化实现工作，mock 预设交互期望。替身越靠近内部实现，重构耦合和“测试共谋”风险越高。时间、随机数、网络、文件和并发要可控制并在每次测试后恢复；生成器不能复制被测算法，fuzz 设置输入/时间/内存上限并保存种子，差分前确认参考实现可信。失败样本进入回归集，存活变异体要分类为等价、不可达或真实测试缺口。

## TEST-04

API 契约不仅是字段形状，还包括 HTTP 语义、错误、空值、枚举、顺序、分页、幂等、事件和版本。规范优先从 OpenAPI/Schema 生成验证与类型；消费者驱动契约则记录实际消费者依赖，并在提供者流水线用确定的 Provider State 验证。Mock 只能模拟约定，不能证明真实提供者兼容。

兼容性要分别判断请求与响应：提供者删除响应字段、收窄枚举或改变错误语义通常会破坏消费者；新增可选字段是否安全取决于消费者是否拒绝未知字段。契约版本、验证结果、弃用期限和使用方矩阵必须可追踪，发布闸门失败时应阻止或灰度隔离不兼容变更。

Protocol Buffers 的兼容身份是字段编号；删除后应保留编号与名称，不能改变同一编号的语义或随意收窄类型。未知字段、未知枚举、默认值以及是否保留未知数据需要新旧运行时实测。gRPC-Web 还引入代理、CORS、metadata、RPC status、取消和 unary/server-streaming 边界，HTTP 状态或成功解码不能单独证明 RPC 与业务成功。

契约门禁至少验证当前提供者对已部署消费者和候选消费者的矩阵。Provider State 必须确定、隔离并可重复建立；Schema/proto diff 只是风险分类输入，最终还需真实提供者验证。消息契约同时检查 key、顺序、重复、幂等和失败语义。生成的 Mock、类型或客户端都源自同一契约，不能作为独立兼容证据。

## PWA-02

Web App Manifest 描述应用名称、图标、启动 URL、作用域、显示模式和主题等安装元数据，但安装入口和资格由浏览器/平台决定。快捷方式、文件/协议处理、启动处理等能力必须先检测再增强，未安装用户仍应获得完整网页功能。

Share Target 把系统分享面板中的文本、URL 或文件作为导航/表单输入交给 PWA。Manifest 中的 action、method、enctype 和参数名必须与接收端一致；所有输入都不可信，要限制文件数量、大小和可解码类型，清理临时数据，校验 URL，并在执行上传、发布或发送前展示预览与确认。请求使用幂等键处理操作系统重复投递，未安装或不支持的平台保留粘贴、文件选择和普通 Web Share 等路径。

推送订阅由浏览器推送服务、应用服务和 Service Worker 协作；订阅端点与密钥属于敏感数据，需要更新、注销和服务端清理。通知权限只能在用户理解价值并主动操作后请求。后台事件有时间与资源限制，通知点击深链需校验，拒绝或不支持时应提供站内通知等替代路径。

## WEBAI-11

WebNN 以操作数和算子构建计算图，再由实现映射到可用的 CPU、GPU 或 NPU 后端。设备偏好不是硬件保证，算子、数据类型、形状和布局支持会随实现变化。图构建/编译、输入复制、预热和缓存均可能主导短任务延迟。

工程上用统一运行时适配 WebNN、WebGPU、Wasm 和云端，先做能力检测，再进行正确性误差、冷启动、稳态延迟、吞吐、内存、功耗代理与隐私比较。实验性或不支持的环境必须安全降级，不能因本地推理后端缺失阻断核心功能。

## AIAPP-13

长期记忆不是保存全部聊天，而是对候选事实进行有目的的写入、检索、更新和遗忘。记忆应记录来源、主体、置信度、有效期、版本和允许用途；用户明确陈述、系统推断、任务结果和偏好不能混成同一可信等级。冲突时保留证据并请求确认，不让一次错误自动强化。

记忆会扩大 Agent 的持续影响面：网页或工具可投毒记忆，错误偏好会跨会话复用，跨 Agent 共享会形成级联。写入需门控，检索需权限与租户过滤，影响决策时需可审计。用户能够查看、纠正、关闭、导出和删除；删除要传播到索引、缓存、摘要、备份策略和下游副本。

## AIMEDIA-01

生成式媒体前端处理输入文件、参考素材、异步任务、变体、局部重做、预览、审核、导出和发布。大文件要限制类型与尺寸、支持取消/分片并避免把原始内容写入日志。对象 URL、Canvas、MediaStream 和录制轨道都有生命周期，完成或取消后应释放。

生成结果不是天然可发布资产。每个制品需关联输入授权、模型/参数版本、生成时间、来源与审核状态，并处理版权、肖像、敏感内容和隐私。图片提供替代文本，视频提供字幕，音频提供转写；队列幂等、刷新恢复、格式兼容、存储/CDN 留存和单任务成本均要观测。

## SUSTAIN-01

可持续性评估先定义功能单位和系统边界，例如“一次成功完成的任务”，并包含设备、网络、数据中心与数据留存。传输字节、CPU/GPU/NPU 时间、内存峰值、设备温度、延迟和云成本可作能耗代理，但不能直接宣称为精确碳排；地区电力、硬件制造和测量误差必须披露。

优化包括减少无用功能与请求、压缩媒体、延长缓存、控制 JavaScript、避免持续轮询、支持低端设备，以及按任务在本地小模型和云模型间路由。还要防止反弹效应：单次更便宜可能诱发更多调用和更长留存。验收同时检查性能、可访问性、隐私、可靠性、硬件寿命和总使用量。

## NODE-04

生产 BFF 的第一条边界是：它不是“把几个接口拼起来”的控制器，而是一个同时管理 HTTP 生命周期、下游资源和用户截止时间的服务。请求到达后要先建立 request/trace id、认证上下文、运行时 Schema 与总截止时间，再把剩余时间和 `AbortSignal` 传给每个下游；客户端断开、截止时间到达或进程开始排空时，应取消仍在进行的网络、文件和流式工作。连接超时、首字节超时、空闲超时和整个业务截止时间不是同一个值，不能只设置一个框架 `timeout` 就宣称完成保护。

聚合请求要设置并发上限与过载策略。读取只有在错误可恢复、操作允许重试且仍有剩余预算时才能采用指数退避和抖动；写入重试还必须有幂等键、去重存储和结果复用。流式响应一旦提交状态与响应头，后续错误就不能改写成普通 JSON 错误，因此要定义流内错误或主动终止协议，并尊重 `write()` 返回值和 drain 信号。认证令牌只向确有需要的下游传递，Cookie 场景还要同时处理 SameSite、CSRF、CORS 与可信来源，不能把浏览器已登录等同于请求已授权。

运行服务需要可验证的关闭与可观测性。存活检查只证明进程能运行，就绪检查决定能否接流量；依赖短暂故障不应让存活检查触发重启风暴。收到 SIGTERM 后先标记未就绪并停止接收新连接，再等待在途请求、关闭 keep-alive/连接池和后台任务，超过上限才强制退出。日志、指标和追踪至少能回答“哪个请求、花在哪一段、为什么失败、是否重试、是否取消”，并持续观察事件循环延迟、句柄数、内存、连接池等待、下游延迟、错误率与限流。框架可以减少样板代码，但不会自动给出正确的截止时间、幂等、背压、授权或优雅停机。

## EMBED-01

嵌入式前端首先要选择信任与隔离模型。npm/ESM SDK 与宿主共享 JavaScript、DOM 和构建环境，集成深但冲突面最大；Web Component 能封装生命周期和部分样式，却不是安全沙箱；脚本注入适合无构建接入，但必须控制全局符号、重复加载与供应链；iframe 以独立文档提供最强的运行隔离，代价是通信、认证、尺寸、无障碍与 SEO 更复杂。选择依据应包含宿主是否可信、是否能改构建、是否需要共享 DOM、发布是否独立、CSP 是否允许、故障是否必须隔离，而不是只按团队偏好选技术。

公共契约包括初始化参数、方法、事件、错误、销毁语义和协议版本。挂载要幂等，同页多实例不能共享可变租户状态；销毁必须释放监听器、观察器、计时器、对象 URL、网络任务和节点。CSS 使用命名空间、Shadow DOM 或 iframe 边界，不能依赖全局 reset。跨窗口消息要固定 `targetOrigin`，接收端同时校验 `event.origin`、`event.source`、一次性 nonce 与运行时 Schema；`postMessage('*')`、只检查消息 `type` 或把长期访问令牌放入 URL 都会扩大接管风险。iframe 的 `sandbox` 和 Permissions Policy 按实际能力逐项开放，CSP 与 SRI 用于限制代码来源，但不能替代应用层授权。

多租户隔离必须贯穿配置、令牌、缓存键、网络请求、遥测和错误报告，任何默认单例都要检查是否会串租户。第三方 Cookie、存储分区、广告拦截器或宿主 CSP 可能让认证和资源加载失败，所以需要短期令牌交换、明确降级与宿主诊断信息。发布时记录宿主版本、SDK/协议版本和租户灰度，先兼容旧消费者再移除字段；出现故障能按租户或版本关闭并回滚。验收至少在两个技术栈不同、CSP 不同的宿主中覆盖重复加载、旧版本、慢网、卸载重挂、伪造消息和宿主异常，证明部件既不会污染宿主，也不会让宿主获得超出契约的能力。

## LOCALFIRST-01

本地优先不是“有网时请求、没网时缓存”的同义词，而是把本地持久化数据视为用户交互的主副本：一次编辑先在本地事务中完成，再异步同步；网络只影响新鲜度，不阻断基本读写。IndexedDB 适合结构化对象、索引和事务，OPFS 适合源私有的大文件与低层文件访问，SQLite Wasm 可提供关系查询但会增加 Worker、锁、持久化后端与兼容复杂度。选型必须同时考虑查询模型、数据量、迁移、并发、导出、浏览器支持和团队运维能力，不能因熟悉 SQL 就默认引入数据库运行时。

可靠同步通常以本地业务事务和变更日志/outbox 同写开始。每条变更带稳定操作 id、实体/基版本、顺序或因果信息与租户身份；上传可以重复，服务端以幂等键确认；拉取以游标断点续传，应用远端变更后再推进游标。删除需要墓碑和保留期，否则离线旧副本会把记录“复活”。字段级合并、人工冲突界面、CRDT 或服务端串行各有适用边界，单纯按客户端时间戳最后写入会受时钟漂移影响并静默覆盖语义冲突。日志压缩与快照必须确保仍可从已确认位置重建状态。

浏览器存储并非永久磁盘：配额、逐出、私密模式、用户清理、升级中断和实现缺陷都可能使数据不可用。应用要估算用量、请求持久化但不依赖其必然成功，提供空间预警、可理解的清理、加密边界与可移植导出。Schema 升级放在版本事务中，较大迁移要可分批、可恢复并阻止不兼容旧页面继续写入。多标签写入可用 Web Locks、BroadcastChannel 或领导者租约协调，但仍要处理持有者崩溃和消息重复。故障演练应覆盖磁盘满、逐出、数据库损坏、迁移中断、离线数日、乱序/重复同步和服务端回滚，并用空环境导入恢复证明用户真正拥有可恢复的数据。

## EDITOR-01

复杂编辑器必须把“文档数据”和“浏览器显示”分开。文档模型或 AST 是可校验、可序列化、可迁移的内容真相，DOM 只是当前视图；一次输入、格式化、粘贴或 AI 改写都应转成带选择区前后状态的事务，再由事务更新模型、DOM 和撤销栈。Selection/Range 指向易变化的 DOM 边界，重渲染、虚拟化和远端协作都会让它失效，因此要把位置映射为文档路径、稳定节点 id 或相对锚点，并在无法恢复时明确提示，而不是悄悄把光标移到末尾。

IME 是编辑器正确性的硬门槛。中文、日文、韩文等输入会在 `compositionstart` 到 `compositionend` 之间多次产生组合态事件，`beforeinput`/`input` 的顺序和可取消性还存在浏览器差异。组合期间不能把 Enter、Backspace 或临时文本当成最终命令，也不应由框架重渲染替换编辑宿主。撤销分组要贴合用户意图：一次连续输入、一次粘贴或一次 AI 接受通常各自成为事务；剪贴板输入先解析为受支持的 AST，再对 HTML、URL 与文件做白名单净化和大小限制，不能把不可信 HTML 直接插入 DOM。

AI 创作不是把流式文本不断写进当前光标。发起请求时要保存稳定范围、原文版本和请求 id；结果以局部 diff 或候选事务显示，用户可以逐段接受、拒绝、取消并查看来源。若用户在等待期间修改了同一区域，旧结果必须重新基线、转为冲突候选或失效，绝不能静默覆盖。提示词与上传内容经过敏感信息边界，日志只记录必要元数据；失败、断网、取消和部分生成后仍能恢复原文。性能验收应区分输入到显示延迟、事务应用、布局/绘制和序列化，并对大文档采用增量计算或可视区域渲染，同时保留屏幕阅读器与键盘可访问的文档结构。

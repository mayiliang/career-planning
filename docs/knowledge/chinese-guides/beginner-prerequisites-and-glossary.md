# 初学者前置知识与术语讲义

## PRIMER-00 初学者前置知识与术语讲义

这是一份给初级前端工程师使用的“阅读桥梁”。它不替代任何知识点的主讲义，也不单独作为掌握挑战题源；它只负责解释主讲义中为了准确表达而必须出现、但初学者可能尚未系统学习的概念。

阅读时请保留中文译名和英文原名。例如第一次遇到“运行时（Runtime）”，不要只背中文或只背英文，要能把它和“代码正在实际执行的阶段”联系起来。不同团队的中文译法可能不同，英文原名是查阅报错、文档和源码时更稳定的定位词。

::: note 使用边界
如果某个术语只是实现参考，而不是当前知识点的学习目标，你只需理解它在当前例子中的职责，不需要顺着它扩展学习整套工具。挑战仍以知识点页面明确列出的资料、输入、交付物和通过标准为准。
:::

### 先学会判断：这是目标、前置还是实现细节

看到陌生词时，先把它放入下面三类之一：

| 类别 | 判断问题 | 应该学到什么程度 |
| --- | --- | --- |
| 当前目标（Learning Objective） | 不理解它，是否就无法解释本知识点的核心机制？ | 理解定义、机制、边界、反例和验证方法 |
| 前置知识（Prerequisite） | 它是否是讲解当前目标必须使用的基础语言？ | 理解到能读懂例子、报错和数据流 |
| 实现细节（Implementation Detail） | 换一个库、平台或工具后，核心机制是否仍然成立？ | 知道它在例子中的职责和替代边界即可 |

例如学习“组件测试”时，断言（Assertion）和测试夹具（Test Fixture）属于前置知识；某个具体测试库的某个辅助函数通常只是实现细节。学习“服务端渲染”时，服务端渲染（Server-Side Rendering, SSR）是当前目标，某个云平台的部署按钮不是。

验证方法：读完一个知识点后，用三列写下“当前目标 / 必要前置 / 可替换实现”。如果无法解释为什么某项能被替换，说明你可能把工具名误当成了机制。

### 代码从文本到运行：源代码、编译、构建与运行时

**源代码（Source Code）**是开发者直接编辑的文本，例如 `.ts`、`.vue` 或 `.css` 文件。它不一定能被目标浏览器或服务器直接执行。

**编译期（Compile Time）**是编译器分析和转换代码的阶段。类型检查、语法转换和部分静态优化常发生在这里。编译期错误通常意味着“程序还没有开始运行，工具已经发现结构或类型不成立”。

**构建期（Build Time）**是把源代码、依赖和资源加工成可部署产物的阶段。构建可能包含编译、打包、压缩、代码分割和生成资源清单。构建期和编译期常有重叠，但“构建”更强调形成完整交付物的流水线。

**运行时（Runtime）**是代码正在真实环境中执行的阶段。用户点击按钮、浏览器发请求、服务端读取数据库，都属于运行时行为。类型检查通过不代表运行时一定正确，因为网络、权限、输入和环境状态只有执行时才出现。

**产物（Artifact）**是构建或流程产生、可被保存和交付的结果，例如 JavaScript bundle、Source Map、测试报告、容器镜像或部署包。产物必须能追溯到源代码版本和构建配置，否则出现故障时很难复现。

```text
源代码 Source Code
  → 编译 Compile
  → 构建 Build
  → 产物 Artifact
  → 部署 Deploy
  → 运行 Runtime
```

常见反例：开发环境能运行，就直接断言生产构建正确。开发服务器可能替你处理了路径、热更新和回退，而生产环境使用的是真实构建产物。验证时至少要运行一次生产构建并检查最终产物。

### 模块、依赖、包管理器和打包器

**模块（Module）**是一段具有明确导入和导出边界的代码。ECMAScript 模块（ECMAScript Modules, ESM）使用 `import` / `export`；CommonJS 模块（CommonJS, CJS）常使用 `require` / `module.exports`。两者的加载语义和工具兼容边界不同，不能只改文件后缀就当作完成转换。

**依赖（Dependency）**是当前代码运行、构建或测试时需要的外部包。直接依赖（Direct Dependency）由当前项目显式声明；传递依赖（Transitive Dependency）是依赖的依赖。生产依赖（Production Dependency）与开发依赖（Development Dependency）的区别在于部署运行时是否需要，而不是“这个包由谁写”。

**包管理器（Package Manager）**负责解析版本约束、下载包并记录依赖图，例如 npm、pnpm。锁文件（Lockfile）记录实际解析结果，使另一台机器能够复现相同依赖组合。只看 `package.json` 而不检查锁文件，可能漏掉真实安装的受影响版本。

**打包器（Bundler）**从入口开始遍历模块图（Module Graph），把代码和资源组合成浏览器可加载的产物。代码分割（Code Splitting）会把产物拆成多个块（Chunk）；摇树优化（Tree Shaking）会尝试移除未使用且可安全判定无副作用的导出。

**转译（Transpilation）**把一种源码语法转换成另一种相近层级的语法，例如把较新的 JavaScript 语法转换为旧浏览器能够解析的形式。**垫片（Polyfill）**则在运行时补充目标环境缺少的 API。转译能解决“语法不认识”，但不自动补齐“API 不存在”。

验证方法：从一个入口文件追踪到最终 chunk，记录模块为什么被包含；再删除一个未使用导出并比较产物。如果产物没有变化，检查副作用声明、动态导入和分析报告，而不是直接断言 Tree Shaking 失效。

### 数据、类型、Schema 与序列化

**类型（Type）**描述一个值允许具有什么结构和操作。静态类型（Static Type）在程序运行前由工具检查；运行时校验（Runtime Validation）检查真实输入。TypeScript 类型在编译后通常不会自动保留，因此来自网络、文件或用户的未知数据仍需要运行时校验。

**模式（Schema）**是对数据结构、字段约束和关系的机器可读描述，例如 JSON Schema。Schema 可以驱动校验、文档或代码生成，但它仍需要版本治理；随意删除字段或改变含义会破坏旧消费者。

**序列化（Serialization）**把内存中的数据转换为可存储或传输的形式，例如 JSON 字符串；**反序列化（Deserialization）**把它恢复为程序可处理的数据。函数、循环引用、`Date`、`Map` 等对象不一定能用普通 JSON 无损表示。

**数据传输对象（Data Transfer Object, DTO）**是跨边界传输数据的结构。它不等于领域对象（Domain Object），也不应直接决定页面文案和业务规则。前端常需要把 DTO 转换为展示模型（View Model）。

```ts
type UserDto = { id: string; status: 'A' | 'D' };
type UserView = { id: string; statusLabel: '正常' | '停用' };

function toUserView(input: UserDto): UserView {
  return { id: input.id, statusLabel: input.status === 'A' ? '正常' : '停用' };
}
```

失败反例：为了省事，把任何非空 `status` 都显示成“正常”。类型可能合法，业务语义却错误。验证时要使用至少一个正常值、一个边界值和一个非法输入，并分别保留类型检查与运行时校验证据。

### 状态、副作用、幂等与竞态

**状态（State）**是系统在某个时刻会影响后续行为的信息。**状态机（State Machine）**用有限状态、事件和允许的转移表达行为约束，例如订单只能从“待支付”进入“已支付”或“已取消”，不能从“已取消”直接进入“已发货”。

**副作用（Side Effect）**是函数除返回值外对外部世界产生的可观察影响，例如写入存储、修改 DOM、发网络请求或记录日志。纯函数（Pure Function）在相同输入下返回相同输出，并且没有外部副作用，因此更容易测试。

**幂等性（Idempotency）**表示同一个操作执行一次和重复执行多次，系统最终效果一致。它不等于“函数只能调用一次”，也不保证每次响应文本完全相同。支付、任务创建和重试常通过幂等键（Idempotency Key）避免重复副作用。

**竞态条件（Race Condition）**是结果依赖多个异步操作完成顺序的缺陷。例如用户快速切换 A、B 两个筛选条件，A 请求较慢却最后返回，覆盖了 B 的新结果。取消信号（Cancellation Signal）可以停止一部分工作，但“浏览器不再等待响应”不代表服务端事务一定回滚。

验证方法：人为让旧请求比新请求晚完成，观察旧响应能否覆盖新状态；再加入请求序号、取消或状态检查，使用同一时间顺序重放回归。

### 调用栈、事件循环与异步任务

**调用栈（Call Stack）**记录当前正在执行的函数及其调用关系。栈顶函数执行完才会返回上一层。无限递归会导致栈溢出（Stack Overflow）。

**事件循环（Event Loop）**协调同步代码、任务队列和渲染时机。Promise 回调通常进入微任务（Microtask）队列；定时器、输入事件等通常作为任务（Task）处理。微任务会在当前同步代码结束后、进入下一个任务前清空，因此大量连续微任务也可能推迟渲染。

**并发（Concurrency）**表示多个任务在重叠时间内推进；**并行（Parallelism）**表示多个任务在同一时刻由不同执行资源真正运行。JavaScript 主线程上的异步 I/O 可以形成并发，但这不等于所有 JavaScript 都在多个 CPU 核上并行执行。

```js
console.log('同步');
Promise.resolve().then(() => console.log('微任务'));
setTimeout(() => console.log('任务'), 0);
```

预期顺序通常是“同步 → 微任务 → 任务”。如果只背顺序而不能解释队列和检查点，就很难排查长任务、界面卡顿或异步状态覆盖。

### API、协议、请求与响应

**应用程序接口（Application Programming Interface, API）**是不同代码单元之间约定的交互边界。API 不只指 HTTP 地址；函数签名、浏览器能力和组件属性也都是 API。

**协议（Protocol）**规定参与方如何组织消息、转换状态和处理错误。HTTP（Hypertext Transfer Protocol，超文本传输协议）使用请求（Request）与响应（Response）交换消息。方法、状态码、请求头（Header）和响应体（Body）各自承担不同语义。

**契约（Contract）**是调用双方都必须遵守的可验证约定，包括字段、状态码、顺序、错误与兼容规则。接口返回 HTTP 200 不代表业务一定成功；还要看业务状态、数据约束和副作用是否成立。

**超时（Timeout）**限制等待时间；**重试（Retry）**在特定失败后再次执行；**退避（Backoff）**逐步拉长重试间隔；**熔断器（Circuit Breaker）**在连续失败时暂时阻止新请求，避免拖垮依赖。不可幂等的写操作不能在没有幂等策略时盲目重试。

验证方法：至少覆盖成功、业务拒绝、超时、重复请求、响应乱序和服务端已执行但客户端断开六类情况。

### 浏览器同源、Cookie、Session 与 Token

**源（Origin）**由协议、主机和端口共同确定。**同源策略（Same-Origin Policy）**限制一个源读取另一个源的敏感数据。跨源资源共享（Cross-Origin Resource Sharing, CORS）通过响应头声明哪些跨源读取被允许；它不是身份认证，也不能阻止攻击者直接向服务器发送请求。

**Cookie（浏览器 Cookie）**是浏览器按域和路径等规则自动携带的小段数据。`HttpOnly` 可阻止脚本读取，`Secure` 要求安全连接，`SameSite` 影响跨站携带策略。Cookie 是存储/传输机制，不等于登录状态本身。

**会话（Session）**通常表示服务端保存的登录上下文，浏览器持有会话标识。**持有者令牌（Bearer Token）**是谁拿到谁就能使用的凭据，因此必须限制存储、传输、有效期和权限。刷新令牌（Refresh Token）用于换取新的短期访问令牌（Access Token），仍需要轮换、吊销和重放防护。

**跨站脚本（Cross-Site Scripting, XSS）**让攻击脚本进入可信页面执行；**跨站请求伪造（Cross-Site Request Forgery, CSRF）**利用浏览器自动携带凭据发起用户未授权的请求。两者攻击数据流不同，不能用同一个开关笼统解决。

验证方法：画出“凭据从哪里产生、存在哪里、何时自动发送、服务端如何验证、退出后如何失效”的完整生命周期，再测试脚本注入、跨站请求、过期和多设备退出。

### 测试语言：Fixture、Assertion、Mock 与 Oracle

**测试夹具（Test Fixture）**是为了稳定复现测试场景而准备的输入、环境和初始状态。好的 fixture 是固定、最小、可版本化的；“随便找一条线上数据”不是可靠 fixture。

**断言（Assertion）**声明预期必须成立，例如“状态码等于 403”或“列表只有一项”。**测试预言机（Test Oracle）**是判断结果正确与否的依据，可能是明确规则、参考实现、快照或人工确认的黄金数据。

**模拟对象（Mock）**通常带有预设交互期望；**桩（Stub）**提供固定响应；**间谍（Spy）**记录真实或包装函数的调用。不同工具对这些词的实现可能不同，但都不应替代对最终可观察行为的验证。

**单元测试（Unit Test）**聚焦小单元；**集成测试（Integration Test）**检查多个模块协作；**端到端测试（End-to-End Test, E2E）**从用户入口验证完整关键路径。层级越高不代表一定越好：高层测试更接近真实行为，但通常更慢、定位失败更困难。

**回归测试（Regression Test）**用于保证修复过的问题不再出现。**快照测试（Snapshot Test）**把输出与已确认快照比较；如果团队在不了解差异时直接更新快照，它就失去了预言机价值。

验证方法：先让测试在缺陷存在时失败，再修复并看它通过。一个从未见过失败的测试，不能证明它真的能捕获目标问题。

### 结构化代码：AST、静态分析与代码转换

**抽象语法树（Abstract Syntax Tree, AST）**把源代码表示为结构化树。节点表达变量声明、调用、条件等语义结构，而不是单纯字符位置。格式化、Lint、编译和 Codemod 常基于 AST 工作。

**静态分析（Static Analysis）**在不真正执行程序的情况下分析代码，适合发现类型、控制流、依赖和规则问题；它无法完整知道网络响应、用户权限和运行环境。

**代码修改器（Codemod）**按结构批量转换代码。可靠 Codemod 应满足幂等（重复执行不继续改变结果）、保留语义、能处理边界输入，并提供修改前后测试和回滚方式。

失败反例：用正则批量替换所有同名文本，却误改字符串、注释和不同作用域变量。验证时要加入同名但不同语义的反例，并比较 AST 或运行测试。

### 工程交付：CLI、环境变量、CI/CD 与回滚

**命令行界面（Command-Line Interface, CLI）**通过文本命令操作工具。命令的退出码（Exit Code）用于告诉调用方成功或失败；只看控制台有没有红字并不可靠。

**环境变量（Environment Variable）**由运行环境提供配置。它适合注入端口、模式和外部地址，但敏感信息仍需专门的密钥管理与最小权限；把密钥打进前端产物后，环境变量名称再隐蔽也无法保密。

**持续集成（Continuous Integration, CI）**在变更合入前自动执行检查；**持续交付/持续部署（Continuous Delivery / Continuous Deployment, CD）**负责把通过门禁的制品推进到环境。CI/CD 的核心是可重复的门禁和制品晋级，不是某个网站上的按钮。

**部署（Deployment）**把已构建制品投放到运行环境；**回滚（Rollback）**恢复到已知可用版本；**前滚修复（Roll Forward）**发布新修复版本。回滚方案只有在真实或等价环境演练并留下时间、版本和健康证据后才可信。

### 容器、镜像、反向代理与端口

**容器（Container）**是受隔离约束的进程及其文件系统和资源视图。它不是完整虚拟机，也不会自动提供安全边界。**容器镜像（Container Image）**是创建容器所用的只读分层模板；镜像标签可能移动，摘要（Digest）才稳定指向具体内容。

**端口（Port）**用于区分同一主机上的网络服务。服务监听 `127.0.0.1` 通常只接受本机连接；监听 `0.0.0.0` 表示在所有可用网络接口接受连接，是否能从外部访问还取决于防火墙和网络规则。

**反向代理（Reverse Proxy）**位于客户端与应用服务之间，负责 TLS 终止、路由、缓存、限流或负载均衡。它不能替代应用自身的身份鉴别和资源授权。

验证方法：从外部入口沿“域名 → TLS → 代理 → 应用端口 → 下游依赖”逐跳记录地址、身份和失败响应；不要因为容器内部能访问就断言公网路径正确。

### 可观测性：Log、Metric、Trace、SLO

**日志（Log）**记录离散事件；**指标（Metric）**记录可聚合的数值时间序列；**追踪（Trace）**通过跨度（Span）串起一次请求跨服务的路径。三者互补，不能用大量文本日志替代所有可观测性设计。

**服务等级指标（Service Level Indicator, SLI）**是被测量的可靠性指标；**服务等级目标（Service Level Objective, SLO）**是目标区间；**服务等级协议（Service Level Agreement, SLA）**通常是带外部承诺和后果的协议。把内部 SLO 直接称为 SLA 可能产生错误承诺。

**关联标识（Correlation ID）**帮助把同一次请求在不同组件中的日志关联起来。它应可追踪但不应直接包含身份证号、令牌等敏感数据。

验证方法：注入一次可控失败，确认能从用户现象定位到指标变化、追踪路径和必要日志，并验证日志脱敏和保留期限。

### AI 基础词：Model、Inference、Token 与 Context

**模型（Model）**是从数据中训练得到、用于执行预测或生成任务的参数化系统。模型名称并不足以描述真实能力；版本、提供商配置、上下文限制和部署方式都会影响结果。

**推理（Inference）**是使用已训练模型处理输入并产生输出的过程。推理延迟、成本和可用能力可能随模型版本变化。

**词元（Token）**是模型处理文本时使用的分割单位，不等于汉字、英文单词或字节。**上下文窗口（Context Window）**限制一次请求可被模型共同处理的 token 数量。把文档塞进窗口不代表模型能够可靠使用其中每个事实。

**提示词（Prompt）**是给模型的输入指令和上下文。系统提示词（System Prompt）设置高层规则，用户提示词（User Prompt）描述具体请求；不可信文档中的提示词注入（Prompt Injection）可能试图改变既定规则。

**幻觉（Hallucination）**是模型生成看似合理但无充分依据的内容。降低幻觉需要来源约束、工具验证、结构校验和人工复核，不能只要求模型“不要编造”。

### AI 检索与执行：Embedding、RAG、Tool Calling、Agent 与 MCP

**嵌入（Embedding）**把内容映射为向量，使系统能够按语义相近程度检索。向量数据库（Vector Database）负责存储、索引和查询向量；相似不等于事实正确，也不等于用户有权读取。

**检索增强生成（Retrieval-Augmented Generation, RAG）**在生成前检索外部资料，并把相关片段提供给模型。完整 RAG 链路包括切分、索引、召回、重排、权限过滤、引用和评估。只接入向量数据库不等于完成了 RAG。

**工具调用（Tool Calling）**让模型输出结构化调用意图，由应用校验参数、执行真实工具并返回结果。模型不应直接获得无限权限；执行层需要模式校验、授权、超时、幂等和审计。

**智能体（Agent）**是在目标、状态和停止条件约束下，循环观察、决策和行动的系统。一次模型调用不是 Agent；无限循环调用工具也不是合格 Agent。必须有停止、取消、恢复、预算和人工审批边界。

**模型上下文协议（Model Context Protocol, MCP）**是连接 AI 应用与资源、提示词和工具的协议。资源（Resources）、提示词（Prompts）和工具（Tools）职责不同；协议连接成功不等于调用已获业务授权。

**人在回路（Human in the Loop, HITL）**要求在高风险或不可逆动作前由人确认。确认界面必须展示将执行的真实对象、影响和参数，不能只放一个含糊的“同意”按钮。

验证方法：对工具参数注入越权对象、重复请求、超时和用户拒绝，检查系统是否默认拒绝、保留审计并能安全恢复。

### AI 质量与安全：Eval、Guardrail、Grounding 与 Provenance

**评估（Evaluation, Eval）**用固定数据集、指标和判定规则测量 AI 系统质量。离线评估（Offline Eval）适合可重复对比；线上评估（Online Eval）观察真实流量，但需要隐私、分流和风险控制。

**护栏（Guardrail）**是输入、输出或执行环节的限制机制，例如敏感信息检测、模式校验和危险动作阻断。护栏会误报和漏报，不能替代权限系统或人工复核。

**依据约束（Grounding）**要求回答建立在指定资料或工具结果上。**来源追踪（Provenance）**记录内容、数据或模型输出来自哪里、经过哪些转换。引用存在不代表引用真的支持结论，仍要检查语义对应关系。

**内容凭证（Content Credentials）**用于携带媒体来源和编辑历史等可验证信息。凭证缺失不自动证明内容伪造，凭证存在也不自动证明内容真实；验证必须检查签名、信任链和处理历史。

### 如何阅读挑战中的“固定输入、最小产出、受限排错”

**固定输入（Fixed Input）**让不同学习者面对同一可复现场景。例如指定 JSON、代码仓库状态、网络响应和浏览器尺寸。不要擅自把固定输入替换为熟悉项目，否则评分失去一致边界。

**最小产出（Minimum Deliverable）**是证明掌握所需的最小交付物，不是让你顺手重构整个系统。题目要求一个状态机和三条测试时，额外换框架既不加分，还可能掩盖核心证据。

**受限排错（Constrained Debugging）**会限制候选根因、可用证据或允许修改的范围，目的是检查你能否通过证伪缩小问题，而不是靠大面积重写碰运气。

**可复核证据（Reviewable Evidence）**是第三方能重新检查的产物，例如测试输出、日志、截图、性能记录、依赖树和变更 diff。“我试过了，没问题”不是证据。

可以使用下面的答题骨架：

```markdown
1. 机制：输入如何经过关键步骤变成输出。
2. 边界：哪些条件下成立，哪些条件下不成立。
3. 产出：题目要求的最小文件、图、实现或记录。
4. 失败：如何稳定复现，候选根因如何逐个证伪。
5. 证据：别人使用什么命令、数据和观察点可以复核。
```

### 最终自检：陌生术语是否真的被理解

对每个重要术语完成以下检查：

- 能同时说出中文译名和英文原名。
- 能用一句不依赖该术语本身的话解释它是什么。
- 能指出它在当前知识点中属于目标、前置还是实现细节。
- 能给出一个正确例子和一个失败反例。
- 能说明用什么观察、日志、测试或产物验证判断。
- 能说出一个“不需要继续展开学习”的边界，防止无目的超纲。

如果其中两项做不到，先回到对应小节完成一个最小实验，再继续主讲义。初学者真正需要的不是一次记住所有名词，而是建立“遇到新词 → 确定职责 → 运行例子 → 触发失败 → 保存证据”的稳定学习方法。

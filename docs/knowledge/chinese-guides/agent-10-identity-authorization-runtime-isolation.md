# Agent 身份、授权、工具权限与运行隔离知识点讲义

## AGENT-10 Agent 身份、授权、工具权限与运行隔离

Agent 能读懂一句“帮我处理发票”，不代表它拥有读取所有发票、修改付款信息或把数据发往任意网站的权力。身份回答“谁在请求”，授权回答“此刻能对哪个对象做什么”，委派回答“用户把哪部分能力临时交给系统”，运行隔离则确保即使模型、工具或外部内容出错，也无法越过文件、网络、时间和预算边界。这些控制必须由确定性系统执行，不能托付给提示词。

### 学习前先确认

- 直接前置：[MCP-01 Server、Tools、Resources、Prompts 与 Schema](../chinese-guides/mcp-01-server-tools-resources-prompts-schema.md#mcp-01)用于理解协议调用边界；[IDENTITY-02 OAuth、OIDC、PKCE 与安全验证](../chinese-guides/identity-02-oauth-oidc-pkce-security.md#identity-02)用于理解授权码、token、issuer、audience 与客户端安全。两条路径分别承担协议与身份基础。

### 一、区分用户、Agent、Client、Server 和下游服务

一次调用可能包含登录用户、代表应用的 Client、执行计划的 Agent、暴露工具的 MCP Server 和真正保存数据的下游 API。它们是不同安全主体。把它们统称“AI”会让审计无法回答谁发起、谁决定、谁执行、凭谁的权限。

用户身份通常来自认证会话；Client 有自己的注册与重定向边界；MCP Server 是受保护资源；下游服务有独立 audience 与策略；Agent 只是使用受限能力完成目标的执行单元。模型输出不是身份凭据，模型声称“管理员已允许”也不会改变任何策略。

每一跳记录主体、租户、会话、客户端和授权来源的不可混淆标识。浏览器传来的 `isAdmin`、工具参数中的 ownerId 和外部文档里的授权语句都属于不可信数据，服务端必须从受信上下文重新取得事实。

### 二、Delegated Authority 必须缩小而不能放大

**委派权限（Delegated Authority）**是用户或服务把明确范围、期限与用途内的能力交给 Agent。它不等于共享用户全部会话，也不等于 Agent 获得长期自身权限。子任务和下游调用的权限必须是上游授权、当前任务与组织策略的交集。

委派记录包含授权人、受托主体、目标资源、动作、目的、有效期、最大深度、预算和撤销句柄。二次委派只能继续缩小，并保留完整链路。若某一步无法证明权限从何而来，默认拒绝。

服务账号适合系统自身的后台职责，不应用来悄悄扩大用户动作。Agent 同时拥有服务身份和用户委派时，策略明确选择哪一种；不能在用户权限不足时自动切到高权限服务账号完成任务。

### 三、Audience Binding 阻止 token 跨服务复用

**受众绑定（Audience Binding）**确保 access token 只被签发给并接受于特定资源。Client 在授权和换 token 时声明 MCP Server 的 canonical resource，Server 验证签名、issuer、audience、过期与 scope；发给其他 API 的 token 即使真实有效，也不能用于当前 Server。

MCP Server 若需要调用第三方 API，应作为独立 OAuth Client 获取面向该下游的 token，而不是把收到的用户 token 原样透传。透传会造成 confused deputy：下游误以为中间服务已经正确验证并代表用户，权限边界被混合。

多授权服务器环境还要防 authorization server mix-up。Client 根据受保护资源元数据发现授权服务器，校验返回的 issuer，并把 state、PKCE verifier、redirect URI 和发起会话绑定。只验证 code 存在而不验证来源，会把攻击者服务器的响应送到错误 token endpoint。

### 四、OAuth 流程中的每个值都有绑定对象

`state` 绑定浏览器发起流程并防 CSRF，PKCE 把 authorization code 绑定发起 Client，`nonce` 在 OIDC 中绑定 ID Token，redirect URI 精确匹配返回位置，issuer 标识授权服务器，audience/resource 标识目标资源，scope 限制能力。它们不能互相替代。

公共 Client 不应保存 client secret；桌面与 CLI 回调遵守已注册的 localhost 或自定义方案规则。动态注册和 Client ID Metadata Document 解决发现与注册问题，不会自动证明调用者可信。注册元数据、redirect URI 和软件声明仍需验证。

access token 短期保存于安全进程，refresh token 采用轮换和重用检测。token 不进入 URL、前端包、Prompt、工具描述和普通日志。登出、权限变化和安全事件触发撤销与缓存失效。

### 五、Least Privilege 落到每个工具与资源

**最小权限（Least Privilege）**不是给整个 Agent 一个粗粒度 `admin` scope，而是按工具、动作、对象与条件映射最小能力。`invoices.read` 不允许退款，`files.write:/exports` 不允许覆盖配置，读取一条客户记录不意味着可搜索全租户。

策略输入来自受信身份、规范化参数、资源当前属性、租户、时间、设备或风险状态。先做参数 Schema 和规范化，再做授权，避免 `../`、大小写、Unicode、重定向或别名绕过允许范围。执行前再次读取资源版本，防止授权后对象归属变化。

工具发现也按权限裁剪，但隐藏工具不能代替执行时授权。列表缓存可能过期，旧 Client 可能手工调用，模型也可能猜出名称。每次调用都由 Server 判定，并返回不泄露资源存在性的稳定拒绝。

### 六、审批授权的是具体动作快照

高风险工具在执行前展示规范化动作、对象、影响、数据目的、费用和可撤销性。用户批准绑定 tool、参数哈希、资源版本、主体、有效期和一次性 nonce。后续修改收件人、金额或文件后必须重新批准。

“允许这个 Agent”不是无限授权；“继续”也只对当前可见上下文有效。批量动作要展示数量和范围，超出阈值拆分或提升审批级别。自动审批策略也有 owner、条件、审计、到期和紧急停用。

服务端验证审批 token，前端勾选状态不是证据。批准后执行仍可能因资源变化、撤销或策略更新被拒绝。界面应把“已批准”“已提交”“结果未知”和“已完成”区分开。

### 七、Runtime Isolation 限制模型与工具的爆炸半径

**运行隔离（Runtime Isolation）**把代码、文件、网络、进程、时间、内存和秘密放在显式允许的环境中。即使模型生成恶意命令、依赖被污染或工具实现存在漏洞，隔离层仍提供第二道确定性边界。

每个任务使用独立工作目录、低权限用户、只读输入和最小写目录；进程限制可执行文件、子进程、系统调用、CPU、内存、句柄和时长。秘密按工具和调用短期注入，不作为环境全局变量供任意进程读取，结束后销毁。

隔离不是绝对安全。容器共享内核，浏览器自动化可能继承登录态，主机挂载和 Docker socket 会突破边界。威胁模型要说明隔离强度与剩余风险，高风险代码可使用更强虚拟化或专用执行节点。

### 八、文件访问必须先解析真实目标

字符串以允许目录开头不代表目标安全。执行器先将相对路径与明确根组合，规范化分隔符与 Unicode，解析符号链接和 junction，得到真实绝对目标，再确认它仍在允许根中。打开文件时防检查后替换，可使用安全句柄或无跟随语义。

读取限制类型、字节、文件数和深度；写入使用临时文件、原子替换和备份策略。覆盖、移动、删除分别授权，递归操作需要更严格范围。用户上传文件和仓库文本可包含指令，但文件内容不能改变文件系统权限。

路径错误只返回受限说明，不暴露主机目录布局。审计记录授权根、规范化后的安全标识、动作与结果，不保存不必要的完整私人路径。

### 九、网络允许列表需要解析全过程

网络工具限制 scheme、规范化主机、端口、DNS 解析地址、代理、重定向、响应类型和字节。只对白名单域做字符串比较会被用户信息段、尾点、大小写、编码、子域和重定向绕过。

请求前解析所有地址并拒绝环回、链路本地、私网、云元数据与组织敏感网段；连接时防 DNS 重绑定；每次重定向重新验证目标。必要时通过受控出口代理执行，让域名、IP、TLS 和流量上限集中治理。

对外请求可能泄露查询、trace、Cookie 和内部头。构造新的允许头集合，不转发浏览器会话、内部 token 或 baggage。响应是不可信内容，先限制大小和类型，再交给模型或解析器。

### 十、工具结果与外部内容保持不可信

Tool、Resource、网页、邮件和文件可能包含提示注入，例如要求读取密钥或调用另一个工具。运行时把它们标为数据来源，模型产生的后续动作重新经过工具白名单、授权和审批，不能因为指令来自“搜索结果”就提升权限。

结构化输出也可能含恶意 URL、路径和对象 ID。每个下游边界重新校验与授权，不依赖上游 Server 的声明。展示层转义内容，下载和跳转使用安全策略，高风险字段不自动填入下一动作。

来源标签、内容哈希和信任级别随摘要保留，防止二次转述抹掉不可信身份。模型总结一封邮件后，里面的付款指令仍来自邮件，不会变成系统事实。

### 十一、预算与停止也是权限控制

权限不仅是能否调用，还包括调用多少次、花费多少、运行多久和产生多少数据。为任务、Agent、工具和租户设置调用、费用、并发、网络、存储与委派深度上限，达到阈值停止并请求明确扩展。

速率限制防止意外循环和滥用；幂等键防止重试重复副作用；租约和取消让长任务可回收。取消不保证动作未发生，未知结果先查状态。紧急停止同时阻止新调用、撤销短期凭据、标记在途动作并启动对账。

不能通过创建子 Agent、换工具别名或重启任务重置总预算。预算继承根任务并在委派链中继续缩小，所有消耗可归因。

### 十二、审计要证明授权链和实际结果

安全审计记录主体、委派链、策略版本、工具与参数摘要、资源版本、审批、执行环境、外部 operationId、结果与撤销，不记录 token 和完整敏感参数。记录采用追加语义、完整性保护和受控访问。

拒绝同样重要：错误 audience、scope 不足、路径逃逸、内网 URL、审批过期、预算耗尽和 token 撤销都要有稳定事件。大量相同拒绝可能表示攻击，也可能表示客户端版本错误，需要关联发布和主体分析。

审计中的 `success` 只能来自业务结果验证，不能因为进程退出码为零。对于外部调用，记录提交与确认分开；结果未知保持未知直到对账。

### 十三、撤销必须传播到缓存和在途任务

撤销 token 后，Server 不能继续信任本地长期缓存。短期缓存有主体、audience、策略版本和过期；高风险动作执行前做在线或等价的新鲜度检查。在途长任务定期续租与重授权，不能拿启动时权限跑数小时。

用户收回某个目录、工具或第三方连接时，更新发现集合、停止新步骤、通知相关执行器并处理在途副作用。已取得的数据按保留政策删除或隔离。撤销失败本身需要告警和人工处置。

员工离职、设备丢失和供应商事故通过演练验证：谁能触发停用、多久生效、哪些任务受影响、如何对账。没有演练的“支持撤销”往往只覆盖正常登录。

### 十四、用越权矩阵验证系统

测试合法读取之外，还要覆盖错误 issuer/audience、过期和撤销 token、scope 扩大、跨租户对象、二次委派超深、路径穿越、符号链接、私网与重定向、恶意 Resource、重复幂等键、审批参数变化和紧急停止。

每个用例断言拒绝发生在哪一层、没有副作用、日志不含秘密、错误信息不泄露对象，并且后续合法调用不被污染。对文件与网络使用真实规范化和解析环境，纯字符串单测不足以证明边界。

截至 2026-09，应以 [MCP 2026-07-28 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)、[MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) 和 [OAuth 2.0 Security Best Current Practice RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) 核验协议要求。规范版本变化时，更新兼容矩阵和拒绝测试，而不是只改 SDK。

学完后，你应能画出从用户登录、委派、token 校验、逐工具授权、审批到隔离执行和撤销的完整链路，并解释每一层阻止什么攻击。安全 Agent 不是一个“懂得拒绝”的模型，而是一组即使模型判断错误也无法越权的确定性边界。

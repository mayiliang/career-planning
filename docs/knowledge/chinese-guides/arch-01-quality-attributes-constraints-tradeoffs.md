# 质量属性、业务约束与架构权衡知识点讲义

## ARCH-01 质量属性、约束与架构权衡

架构不是技术名词清单，也不是把性能、可靠性、安全和成本都写成“越高越好”。一个方案只有在明确业务任务、环境、负载、失败和组织约束下才有意义。高级工程师把模糊愿望改写成可验证质量场景，识别属性之间的冲突，用最小实验推翻高风险假设，并把剩余风险、责任人与复查条件留给未来，而不是宣布一个永远正确的“最佳架构”。

### 学习前先确认

- 直接前置：[BIZ-08 需求、验收与证据追踪](../chinese-guides/biz-08-requirement-acceptance-traceability.md#biz-08)用于把业务目标转成可验收合同；[OBS-01 前端可观测性、SLO、告警与隐私](../chinese-guides/obs-01-frontend-observability-slo-alerting-privacy.md#obs-01)用于理解指标、分位数和生产反馈。两者分别承担需求与测量基础。

### 一、Quality Attribute 描述系统如何表现

**质量属性（Quality Attribute）**描述系统在特定条件下提供功能的方式，例如性能、可靠性、安全、可用性、可访问性、可演进性、互操作、可观测性和成本。它们不同于“支持登录”这类功能需求，却决定功能在真实压力和变化中是否可用。

属性必须联系用户与业务。结算页 p95、辅助技术完成率、故障恢复、权限隔离和月成本都能影响同一任务。只写“高性能、高可用、安全”没有主体、刺激和阈值，任何方案都可以口头声称满足。

质量属性不是彼此独立的滑块。缓存可降低延迟却返回旧权限，多区域可提高容灾却增加成本和一致性复杂度，严格安全检查可能增加路径延迟但降低灾难风险。架构工作就是显式管理这些关系。

### 二、约束先于方案

约束包括发布日期、预算、法规地区、既有合同、团队技能、数据驻留、设备、供应商、组织边界和不可停机窗口。约束不是偏好；违反它的候选即使技术漂亮也不可行。偏好可以在证据下调整。

建立约束清单，标记来源、owner、强制程度、有效期和验证方式。区分事实、假设与选择，例如“客户合同要求数据留在地区”是约束，“只有供应商 A 能做到”是待验证假设，“团队更熟悉框架 X”是组织现状。

约束会冲突。预算不足以同时支撑多区、最高吞吐和零运维时，必须与决策人调整目标、范围或风险接受，不能在文档中同时承诺互斥结果。

### 三、Quality Attribute Scenario 让愿望可证伪

**质量属性场景（Quality Attribute Scenario）**通常包含刺激源、刺激、环境、受影响制品、期望响应和度量。它把“页面要快”改写为“促销峰值、冷缓存、目标移动设备上，结算关键内容 p75 LCP 不高于某阈值且失败可恢复”。

可靠性场景要说明依赖如何失败、多久发现、怎样降级和恢复；安全场景说明攻击主体、资源、拒绝与审计；可演进性场景说明哪类需求变化、允许修改范围和交付时间；可访问性场景说明用户、辅助技术与任务成功。

每个度量有采集位置、时间窗口、分位数/分母和误差。平均延迟会掩盖尾部，服务 uptime 不等于用户任务成功，测试环境结果不等于生产分布。不可测目标只能标假设，不能进入完成定义。

### 四、先建立基线再谈改进

在现状上测相同场景：正常与峰值、冷/热缓存、主要设备、依赖故障和恢复。记录版本、数据量、流量形状、环境、原始结果和成本。没有基线，“提升 50%”和“足够稳定”都无法解释。

基线应覆盖用户结果和系统资源。页面快但支付失败、服务器省钱但低端设备崩溃，都不是整体改进。将指标连接到业务任务，并观察错误类别、排队、CPU/内存、下游限流和人工运维。

数据不足时明确未知与采集计划。不要把测试机单次结果填成生产承诺。基线也有有效期，流量、功能和价格变化后需更新。

### 五、Architecture Tradeoff 是有代价的选择

**架构权衡（Architecture Tradeoff）**是在约束下选择某些质量收益并承担明确代价。每个候选写因果假设：采用什么机制，会在哪个场景改善什么指标，又会增加什么风险、复杂度和长期成本。

例如边缘缓存可能改善静态与公共内容延迟，但个性化缓存键、失效和地区合规更复杂；客户端本地计算减少服务器成本，却增加包体、设备差异和数据暴露；强一致写简化用户理解，却牺牲可用性或延迟。

比较必须使用同一组场景与约束，包含维持现状。为目标方案定制指标、把其他方案写成稻草人不是评审。权重由业务责任人确认，架构师说明技术后果。

### 六、容量模型找到拐点而不是单个数字

估算用户、请求、数据增长、并发、峰谷、缓存命中、外部配额和资源单位成本。把平均和峰值分开，考虑突发、重试放大和后台任务。模型先用于发现敏感变量，不追求虚假的小数精度。

容量实验逐步提升负载，观察延迟分位、错误、队列、连接池、内存、GC 和下游。找到第一个饱和点及传播路径；“2 万并发通过”不说明 4 万，也不说明请求形状相同。测试生成器本身也需验证不成为瓶颈。

把结果映射回扩容、限流、降级和成本。超过预算时选择削峰、缓存、分层服务或降低非核心目标，并记录用户影响。

### 七、故障场景验证恢复而非只验证报错

模拟实例、区域、DNS、身份、数据库、第三方和网络故障，观察检测、隔离、降级、数据一致性、恢复和沟通。故障注入有安全范围、停止条件与责任人，先在隔离/预发布，再逐步生产。

成功不是“系统返回错误”，而是核心任务按场景保持或以明确方式降级，恢复时间和数据损失满足目标，告警能指向原因。故障时关闭鉴权或返回旧租户缓存，即使可用性提高也不可接受。

演练记录时间线、自动/人工步骤、未达目标和改进。灾备文档未实际演练不能证明可恢复，备份存在也不证明可还原。

### 八、安全和隐私质量属性要进主设计

识别资产、主体、信任边界、滥用路径、最小权限、加密、保留和事件响应。安全不是上线前扫描，隐私不是条款页；二者影响数据模型、缓存、日志、地区和供应商选择。

建立可测试场景：跨租户 ID 被拒且不泄露存在性；撤销后短期内所有入口失效；删除请求覆盖主存储、索引和备份策略；日志不保存密钥与完整个人数据。记录剩余风险和监测。

控制也有可用性成本，需设计恢复与支持流程。过严且无法完成合法任务会诱发绕过；合理方案在不降低边界的前提下提供明确授权和申诉路径。

### 九、可访问性和兼容性属于架构约束

语义、焦点、键盘、缩放、语言和浏览器支持会影响组件、渲染、设计系统和测试架构。若等到页面完成再补，基础组件和数据流可能已阻碍修复。把关键任务与目标辅助技术写进质量场景。

第三方组件、Canvas、高度定制控件和微前端都可能扩大可访问性与兼容成本。原型要验证真实任务，而不仅截图。降级路径和支持矩阵也是架构产物。

指标包含自动规则、人工任务完成与用户反馈。自动扫描零错误不是完整证据，像素一致也不是兼容目标。

### 十、可演进性用变化场景衡量

列出高概率变化：新增租户规则、替换模型、修改支付供应商、框架升级、数据地区扩展。预测需要改哪些组件、多少团队、是否停机、怎样兼容和回滚。边界清晰、合同稳定和自动测试降低变化成本。

抽象不是越多越可演进。为未知未来建立通用平台会增加今天复杂度；只对已识别变化点设置适配层，并有使用量和删除条件。错误抽象要允许拆除。

通过一次演练或小原型验证变化成本，例如替换一个供应商、升级一个协议或迁移一个垂直切片。文档声称“解耦”不如实际 diff 和交付时间可靠。

### 十一、总拥有成本包含组织与迁移

计算云资源、第三方费用、开发、值班、培训、审计、测试、双运行、事故和退出成本。便宜的服务若需要大量人工恢复，或低初始成本产生不可迁移数据，长期可能更贵。

成本模型写价格日期、流量、折扣、增长和敏感性范围。避免用当前免费额度预测生产，也不把已投入成本自动当继续选择的理由。迁移期间新旧系统并行是显著成本。

将成本与已验证用户结果联系。削减日志可能省存储却延长事故，降低模型质量可能增加人工返工。优化目标是约束内价值，而非单项账单最低。

### 十二、风险登记连接假设与动作

风险项包含事件、概率、影响、触发信号、owner、缓解、应急、到期和剩余风险。假设则包含可证伪预测、验证方法与截止。二者不能混成一列“注意事项”。

优先验证高影响且高不确定项。已有稳定数据的低风险细节不必做昂贵原型；一个会决定方案可行性的权限、容量或团队能力假设应最先实验。失败结果同样有价值，可淘汰候选。

评审后未解决项不会消失。进入路线图与监测，触发阈值到达时重新决策。风险接受由有权承担后果的人签署。

### 十三、Fitness Function 持续检验关键属性

**适应度函数（Fitness Function）**是持续检测架构质量约束的自动或半自动检查，例如包体预算、依赖方向、跨租户拒绝、接口兼容、故障恢复时间和成本上限。它把一次评审的结论延伸到后续变化。

不是所有属性都能完全自动化。团队技能、运维复杂度和用户可理解性需要演练、评审或调研；仍应有固定节奏和证据。自动指标也要防代理失真，单纯追求覆盖率可能删除有价值测试。

适应度函数有 owner、阈值来源、误差、运行频率和失败处理。架构决策改变时同步更新；不能为了让 CI 变绿静默调宽预算。

### 十四、形成可复查的架构结论

最终产物包含业务目标、约束、质量场景、基线、候选、实验、权衡、决定、反对意见、风险、迁移/回滚、指标、owner 和复查触发器。面向非技术受众说明收益、代价和不确定性，面向工程团队提供可执行边界。

决定有期限。当流量翻倍、供应商价格改变、法规或团队能力变化，重新运行关键实验。过去正确的架构可能不再适合，这不是失败，而是约束改变后的正常演进。

可参考 [Azure Well-Architected 架构师原则](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/checklist) 理解从业务结果与约束出发的方法，但不要套用支柱名称代替项目质量场景。真正证据来自你的用户、系统和可重跑实验。

### 十五、用敏感性分析识别真正的决策变量

容量和成本模型中的并发、命中率、增长、故障概率与人工恢复时间都不精确。不要只计算一组“最可能”数字；在合理上下界内逐个改变变量，观察哪个变化会让候选越过质量或预算门槛。最敏感的变量优先测量、监控或通过合同限制。

例如缓存命中率从 90% 降到 60% 可能让下游配额立即耗尽，而服务器单价上涨 10% 只轻微影响总成本，那么应先验证缓存分布和降级，而不是花大量时间谈采购。若结论只有在一个非常窄的理想区间成立，就必须降低置信度或选择更稳健方案。

敏感性结果还帮助设计触发器：流量、价格或错误率达到什么水平必须扩容、降级或重做决定。架构因此从静态图变成可监测的运行假设。

### 十六、处理多个质量属性的最低门槛与优化目标

先定义不能违反的底线，例如跨租户隔离、法定地区、核心无障碍任务和最大数据损失；再在满足底线的候选中优化延迟、成本或交付。用加权总分把安全底线与少量性能收益相抵消，会产生危险结论。

对于无法同时达到的软目标，记录优先顺序和补偿控制。移动低端设备与桌面、正常与灾难环境可能使用不同预算，但同一用户承诺不能互相矛盾。局部团队的开发速度也不能把运维、客服和其他团队的成本外部化。

评审时用场景逐条走查候选，明确满足、部分满足、未知或不满足。Unknown 不按中间分数处理，而要进入实验或风险接受。这样可防止表格分数精确却没有证据。

### 十七、架构边界应使失败局部化

模块、服务、队列和团队边界的价值之一，是限制变化和故障传播。对每个候选追踪一次输入错误、依赖超时、权限撤销和配置发布会穿过哪些边界，谁检测、谁恢复。边界过细会增加网络与协调，过粗会扩大爆炸半径。

用故障域、部署域、数据 owner 和权限域检查边界是否一致。一个独立部署服务仍共享数据库超级账号，并没有真正隔离；一个单体内清晰模块也可能提供良好变化边界。技术形态不是质量结论。

边界变化后重复容量、故障和团队协作实验，确认收益没有被额外调用、序列化、缓存和 on-call 复杂度抵消。

学完后，你应能把模糊质量愿望写成场景，建立容量、故障、安全、可访问和成本实验，在同一约束下比较真实候选，并说明选择牺牲了什么。架构能力不是预测所有未来，而是让重要假设尽早可证伪、让变化发生时有复查和退出路径。

# 在相同约束下，怎样选择架构

## ARCH-01 质量属性、约束与架构权衡

一次登录系统评审里，有人建议多区域部署，有人建议加缓存，还有人主张先保持单区域。每个人都说自己的方案“更快、更稳定”，却没人说明要承受多少请求、哪种故障必须恢复，以及团队能承担多少成本。

架构选择需要先把这些话变成可检验的条件。本篇用一个虚构的企业工作台贯穿质量场景、容量、故障、成本与变化实验。你会看到同一个方案在什么输入下成立、改变哪个条件就不再成立，以及如何把尚未证实的假设留在决策中。

### 学习前先确认

- 直接前置：[BIZ-08 需求、验收与证据追踪](../chinese-guides/biz-08-requirement-acceptance-traceability.md#biz-08)。知道用户目标、验收条件与实现决定要分开。
- 直接前置：[OBS-01 前端可观测性、SLO、告警与隐私](../chinese-guides/obs-01-frontend-observability-slo-alerting-privacy.md#obs-01)。理解度量位置、分母、时间窗口与生产证据。

### 一、功能说明做什么，质量属性说明怎样做到

“用户可以登录”描述功能。两万在线用户同时工作时登录是否仍可用，身份服务超时后用户能否恢复，跨租户数据是否被拒绝，则描述系统在具体条件下的表现。**质量属性（Quality Attribute）**就是性能、可靠性、安全、可访问性、可演进性等方面的行为特征。

属性名称不能直接用来验收。“高可用”可能指服务进程存活，也可能指用户能完成登录；二者并不相同。首页返回 200，但身份接口持续失败，服务器监控看起来正常，用户任务却不可用。先说明受影响的人和任务，再选指标，才不会优化错误目标。

本篇的虚构约束是：工作台有 2 万在线会话；登录峰值可能达到平时三倍；目标 p95 为 800 ms；月度运行预算 8 万元；时间型可用性目标 99.9%；需要考虑单区域中断 15 分钟。它们还不是完整要求，例如“在线会话”没有说明请求频率，“800 ms”没有说明从哪里开始计时。下一步就是补齐含义。

约束要写来源与可协商程度。客户合同中的地区要求是硬边界；“只能选择供应商 A”可能只是待验证假设；“团队熟悉当前技术”是会影响交付与值班成本的事实。偏好可以调整，硬约束不能靠另一个维度的高分抵消。确实冲突时，需要与有权决策的人调整范围、期限或预算。

### 二、把更快更稳定写成可以被推翻的场景

**质量属性场景（Quality Attribute Scenario）**通常写清刺激源、刺激、环境、受影响对象、期望响应和响应度量。这不是为了增加表格，而是为了让两个人测试同一件事。只写“响应 800 ms”时，一个人可能计网关时间，另一个人计从点击到页面可操作的时间。

以登录为例：组织用户在工作日上午集中点击登录；目标桌面浏览器、规定网络条件、冷会话且峰值请求速率下；登录入口、身份服务与前端受到影响；用户获得明确成功或可恢复错误；从点击到确认进入工作台的 p95 不高于 800 ms，并单独报告失败率、样本数和时间窗口。重定向与外部身份交互是否计入，必须明确，不能为了指标好看临时移出范围。

| 属性 | 刺激与环境 | 可观察的响应和门槛示例 |
| --- | --- | --- |
| 可靠性 | 单区域中断，已有与新会话同时存在 | 检测、切换、重新验证与恢复各有期限；说明哪些任务暂不可用 |
| 安全 | 租户 A 的有效会话请求租户 B 的对象 | 拒绝访问，不返回对象内容；按既定策略处理存在性信息 |
| 可访问性 | 用户仅用键盘，在目标桌面浏览器操作 | 可进入、纠错和完成登录，焦点不丢、不被遮挡 |
| 可演进性 | 替换身份供应商 | 改动限制在已列边界，旧会话迁移有可执行方案 |
| 成本 | 规定月流量与保留量，含故障预留 | 运行费用不越预算，同时列出尚未计入的人力与迁移 |

表中的门槛需由项目具体化，不能把“各有期限”原样当成验收标准。性能通常需要分位数与错误共同判断；可访问性需要真实任务观察；安全则有不能被平均掉的拒绝要求。给每项附上证据入口与负责人，未知就写未知。

一次需求变化后，场景也要跟着版本化。若原本只支持桌面，却改为低端移动设备，原先的性能与交互证据不能原样复用。兼容支持范围怎样落地，见 [COMPAT-01](../chinese-guides/compat-01-baseline-progressive-enhancement-device-testing.md#一先承诺任务再确定支持范围)。

### 三、先记录基线，再选择值得比较的候选

基线是现有系统在相同场景下的实际表现。固定构建、数据量、流量形状、设备与网络，分别观察正常、峰值、冷缓存和依赖失败。保留延迟分布、失败类型、排队、CPU、内存、连接池和下游限流，才能说明瓶颈在哪里。

不要只有一个“提升 50%”的数字。若改动前用了冷缓存，改动后用了热缓存，比较不成立；若只删除慢请求再计算 p95，就隐藏了任务失败。服务端响应更快但浏览器初始化变慢，也未必改善从点击到可操作的时间。证据必须绑定当前构建和度量口径，见 [BIZ-08](../chinese-guides/biz-08-requirement-acceptance-traceability.md#八证据要对应这次规则和这次构建)。

**架构权衡（Architecture Tradeoff）**是在相同约束下取得某种收益，并承担另一种代价。本例可以比较维持现状并优化瓶颈、单区域加公共配置缓存、增加备用区域三个候选。每个都写因果链，不把候选简单命名为“传统”和“先进”。

公共配置缓存可能减少回源请求，但引入过期与失效；备用区域可能改善区域故障恢复，但需要复制、路由、切换权限和额外维护。缓存登录权限或租户数据更涉及撤销和隔离，不应为了降低延迟直接复用公共缓存策略。对候选使用同一组场景，才看得清收益和代价。

维持现状也是候选。若用户瓶颈来自前端重复初始化，增加区域可能几乎不改变端到端体验，却增加值班责任。先找会改变选择的证据，再决定是否引入昂贵机制。

### 四、把在线人数换算成负载，观察哪个假设最敏感

“2 万并发”可能指在线会话、在途请求或同时占用连接，三者单位不同。假设 2 万在线会话平均每分钟产生一次公共配置读取，平时约为 333 次/秒；峰值系数为 3 时约为 1000 次/秒。这只是根据行为假设得到的到达率，不是压测结果。

下面模拟公共配置的回源，**不缓存登录令牌或授权判断**。假定源服务预算为每秒 300 次，请求命中缓存就不回源。保存为 `capacity.mjs`，用 Node.js 22 运行 `node capacity.mjs`。没有真实服务、定时器或付费调用。

```js example=arch01-capacity
function estimate(sessions, hitRate) {
  const requestsPerSessionPerMinute = 1;
  const peakFactor = 3;
  const arrivals = sessions / 60 * requestsPerSessionPerMinute * peakFactor;
  const origin = Math.round(arrivals * (1 - hitRate));
  return `${sessions} 会话，命中 ${hitRate * 100}%：回源 ${origin}/s，${origin <= 300 ? '未越预算' : '超过预算'}`;
}
for (const sessions of [20000, 40000]) {
  for (const hitRate of [0.9, 0.6]) console.log(estimate(sessions, hitRate));
}
// => 20000 会话，命中 90%：回源 100/s，未越预算
// => 20000 会话，命中 60%：回源 400/s，超过预算
// => 40000 会话，命中 90%：回源 200/s，未越预算
// => 40000 会话，命中 60%：回源 800/s，超过预算
```

人数不变，只把命中率从 90% 降到 60%，回源就从 100 增至 400 次/秒。未命中比例由 10% 变为 40%，所以是四倍，不是增加三成。缓存重启、过期集中、不同租户键分布都会影响命中率，不能只取一个理想百分比。

这叫敏感性分析：改变一个不确定输入，观察结论何时越界。本例中，命中率的变化足以改变容量结论，应该优先验证；人数翻倍也要重算。但模型没有排队、重试、批量请求、背景任务和扩容延迟，不能由“未越预算”推出 p95 必然达标。

在稳定、边界一致的系统中，平均在途量可用平均到达率乘平均停留时间帮助估算；不能把在线会话数直接带入，也不能把 p95 代替平均值。接近饱和时，队列可能显著放大尾延迟。需要逐步提高实际负载，观察第一处饱和、错误、重试与下游配额，而不是一次打满服务器后只记录“通过”。

真实容量实验应固定请求内容、认证与缓存分布，确保压测发生器不是瓶颈，同时设停止阈值和隔离环境。先测高价值路径以及冷缓存、回源放大等风险条件；模型用于选择实验，实验再更新模型。不要把这里的合成数字抄成生产容量证明。

### 五、故障预算与恢复演练需要相同口径

时间型可用性 99.9% 若按 30 天、全天连续服务计算，允许不可用时间为 43.2 分钟。它不是“每次都能中断 43.2 分钟”，而是这个统计窗口内的总预算。一个持续 15 分钟、导致目标服务完全不可用的区域故障，就使用约三分之一预算。

下面只做算术推演，保存为 `availability.mjs`，用 Node.js 22 执行。所有数值都是教学条件，没有实际故障注入。

```js example=arch01-availability
const windowMinutes = 30 * 24 * 60;
const target = 0.999;
const budget = windowMinutes * (1 - target);
const outageMinutes = 15;
console.log(budget.toFixed(1)); // => 43.2
console.log((outageMinutes / budget * 100).toFixed(1) + '%'); // => 34.7%
console.log((budget - outageMinutes).toFixed(1)); // => 28.2
```

如果项目用请求成功比例作为 SLI，不能直接套这份分钟预算：同样 15 分钟发生在低流量与高峰，失败请求占比可能不同。可用性定义、排除项和统计窗口需事先确定；不能在事故后临时排除最差区间。用户任务与遥测分母的说明见 [OBS-01](../chinese-guides/obs-01-frontend-observability-slo-alerting-privacy.md#obs-01)。

恢复目标也有不同维度。RTO 描述计划允许的恢复时长，RPO 描述可接受的数据丢失时间范围；它们不是同一个指标，也不等于真实已达到。备用区域存在，不代表路由、身份、密钥、数据库和操作人员都能完成切换。

一个合成演练时间线可以是：t=0 断开测试区域，t=20s 检测，t=50s 完成流量切换，t=90s 用户重新验证成功，t=120s 对账完成。应分别记录什么阶段核心任务可用、什么阶段仍存在未知结果。若只测到负载均衡切换，就不能宣布用户 50 秒完成恢复。

恢复中的重试和重复操作尤其重要。请求超时可能已提交，恢复后应查询或用同一业务幂等键重试；临时关闭鉴权、复用其他租户缓存都不是可接受的“可用性修复”。故障域、数据权限域和部署域要一起检查：独立服务共用一个数据库超级账号，仍可能共同失败或越权。

### 六、在通过底线的候选中比较成本

给性能、安全和成本加权打分看似客观，却可能让“跨租户泄露”被“便宜且快”抵消。先判断硬性门槛，再在满足门槛的候选之间比较软目标。未知不是中间分数，应进入验证或明确的风险决策。

下面用虚构候选演示顺序，保存为 `candidates.mjs` 并用 Node.js 22 运行。p95 与成本数字是合成输入，不是实测与报价；安全字段只是外部证据状态，程序没有验证隔离。

```js example=arch01-candidates
const candidates = [
  { name: '共享缓存', isolated: false, p95: 250, monthly: 30000 },
  { name: '单区优化', isolated: true, p95: 720, monthly: 60000 },
  { name: '备用区域', isolated: null, p95: 760, monthly: 78000 },
];
function evaluate(item) {
  if (item.isolated === false) return '淘汰：隔离底线失败';
  if (item.isolated !== true) return '待验证：隔离证据缺失';
  if (item.p95 > 800 || item.monthly > 80000) return '不满足当前预算';
  return '保留候选：继续验证故障与迁移';
}
for (const candidate of candidates) console.log(`${candidate.name}：${evaluate(candidate)}`);
// => 共享缓存：淘汰：隔离底线失败
// => 单区优化：保留候选：继续验证故障与迁移
// => 备用区域：待验证：隔离证据缺失
```

第一项最快最便宜，仍被淘汰；第三项没有失败证据，也不能被写成已满足。第二项只是留下继续调查，不是已经选定，因为恢复、可访问性和迁移还没检查。把月成本改为 90000 后，即使延迟达标，也不再满足当前约束。

月成本要说明口径。计算、存储、网络、日志、供应商配额和备用资源属于常见运行费用；开发、培训、值班、审计、迁移双运行与退出成本影响总拥有成本。两者可以分列，但不能为了候选好看只报其中一部分。价格、折扣、汇率与用量具有时间性，应使用实际报价日期，本例 8 万仅为教学预算。

对费用做范围估算比小数点精确更诚实。若流量、保留期或缓存命中变差，哪个项先突破预算？如果每月便宜一万元，却要额外两人长期值班，组织成本可能更高。已经投入的成本也不应自动成为继续方案的理由，应比较从今天起的增量收益、迁移代价和风险。

### 七、变化实验检验边界是否真的有用

“可扩展”“解耦”都需要变化场景。例如把身份供应商从 A 换到 B，应该改哪些模块、触及哪些团队、怎样处理旧会话、能否逐步切换？小型原型可以揭示第三方类型是否渗透业务、错误码是否绑定供应商、回调与账号关联是否难以迁移。

一次变化实验应选真实可能发生的窄切片：替换测试环境中的一个适配器，保持业务接口和验收条件，记录实际 diff、耗时与未处理部分。只在架构图上画出接口，不证明实现可以替换；把所有调用套进万能抽象，也可能增加当前复杂度而没有降低迁移成本。

边界还影响故障传播。队列可以缓冲突发，但增加积压、重复处理和延迟；拆成服务可独立部署，但增加调用、身份与运维；单体中清晰模块也能限制变化范围。需要追踪一次错误输入、超时、撤销和配置变更会到哪里停止，不能从技术形态直接推导质量高低。

安全、隐私与可访问性要进入原型。缓存键要验证租户与权限；日志要验证不采集秘密；删除要覆盖索引与保留策略；登录弹窗要验证键盘焦点、错误反馈和缩放。自动扫描可以发现一部分问题，不能替代真实用户任务。越早发现基础组件不支持这些条件，返工范围越小。

同时考虑团队边界。方案若需要每次发版协调五个团队，或只有一人理解恢复流程，就有组织可演进性风险。记录需要的知识、值班能力、移交和培训，而不是把这些成本留给未来同事。

### 八、把最高风险的假设转成持续检查

优先验证影响大且不确定的假设。本例中“缓存命中不低于 90%”“备用区域能在期限内恢复”“组织能维护两套配置”都可能决定候选是否可行；字体阴影的差异通常不会改变架构选择。用最小实验尽早淘汰错误假设，比在选定方案后补证明更有效。

风险登记要连接动作：事件是什么、影响谁、触发信号是什么、谁调查、何时完成、如何缓解和应急。已经证实不满足的条件不应继续写成含糊的“存在风险”；证据未知则标明何时补齐。接受剩余风险需要有权承担后果的人决定。

**适应度函数（Fitness Function）**把重要架构约束变成持续检查，例如构建体积预算、依赖方向、跨租户拒绝、接口兼容、恢复时间和单位任务成本。它可以是自动检查，也可以是定期演练；关键是与具体质量场景相连，并规定失败后怎么办。

检查代理指标也会失真。包体没变不能证明初始化更快，测试覆盖率提高不能证明故障可恢复。每项应说明度量口径、阈值依据、误差、运行频率与 owner。只有真实约束变化、完成评审后才调整门槛，不能为了当前 PR 变绿而静默放宽预算。

比如缓存命中在代表流量中低于预计值，触发回源容量复测；新增地区触发数据处理与恢复审查；供应商变更触发价格和可替换性复核。日常检查通过后不需要无理由重复全部实验，新增失败或场景变化才扩展验证。

### 九、让未来的人知道为什么作出这个决定

一份可复查结论至少包含业务任务、约束来源、质量场景、现状基线、候选、关键证据、选择代价、未决项、迁移恢复办法和复查触发器。记录反对意见与尚未证实的假设，有助于后续读者理解方案在哪些条件下成立。

例如结论可以是：“暂采用单区优化；在当前测试条件下延迟达标，区域故障恢复仍待演练；在完成恢复目标验证前，不把新可用性目标对外承诺。若回源超过已验证预算或客户新增地区要求，重新比较备用区域。”这比“最佳实践是多区域”更能指导下一步行动。

迁移需要状态连续性。灰度期间新旧版本如何读写相同数据，旧会话怎样处理，停止迁移时怎样恢复，数据库或协议变化是否向后兼容，都属于选择成本。回滚代码不一定回滚已经写入的数据；实验应说明可逆部分与只能修复或对账的部分。

架构结论因此是一组有证据、有限定条件的工作假设。条件改变后重新选择并不意味着过去判断失败；真正危险的是条件已经改变，却仍用旧测试和旧预算宣称同样的质量保证。

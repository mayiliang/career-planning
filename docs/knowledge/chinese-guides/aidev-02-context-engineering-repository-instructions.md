# AI 上下文治理知识点讲义

## AIDEV-02 Context Engineering 与仓库指令

编码代理看到的不是整个真实世界，而是当前推理时被放进上下文的有限信息：系统规则、仓库指令、任务规格、代码片段、工具说明、命令输出和历史摘要。上下文治理的目标不是“尽量多塞”，而是在有限窗口中持续选择最相关、最新、可信、可追踪且允许披露的事实，并让过期信息能够失效。

### 学习前先确认

- 直接前置：[AIDEV-01 AI 协作规格上下文与代理执行闭环](../chinese-guides/aidev-01-specification-controlled-agent-loop.md#aidev-01)。本讲直接使用任务包、工具边界、检查点、停止条件和证据闭环；上下文是执行合同的一部分，不是独立的提示技巧。

### 一、上下文工程管理的是模型此刻能依据的状态

**上下文工程（Context Engineering）**是选择、组织、更新和验证模型在一次推理中可见信息的工程。它包含提示，但范围更大：系统指令、工具定义、检索结果、代码、运行输出、记忆和历史压缩都会改变行为。

模型窗口有限，即使长度足够，无关内容、相互冲突的旧版本和重复信息也会稀释关键约束。目标应是“最小充分”：少到每一项都能说明用途，多到关键决定有事实依据。这个集合会随任务阶段变化——定位问题需要地图和日志，修改阶段需要局部代码与合同，验证阶段需要命令、失败输出和验收项。

### 二、先建立仓库地图，再按任务下钻

仓库地图描述包、入口、领域边界、公共接口、生成物、测试位置和常用命令。它不是复制目录树，而是帮助代理从任务词汇定位可信来源。例如“结算校验”应能找到页面、领域 Schema、API 合同和相关测试，而不是全仓库搜索到哪个同名字符串就改哪个。

地图中的每个节点带路径、所有者、用途和更新依据。生成目录、依赖缓存、构建产物和历史归档明确标注，避免被当成源文件。地图失效时，源码与可运行工具优先，并触发更新，而不是要求代理相信摘要。

下钻采用逐步披露：先读最小入口，根据 import、调用图和失败证据继续扩展。一次把整个 monorepo 放入上下文会增加成本、泄密面和错误关联。

### 三、仓库指令需要明确作用域与优先关系

**指令作用域（Instruction Scope）**回答一条规则适用于哪些目录、文件、任务和工具。根指令放全仓库共同约束，模块指令放局部构建、测试和编码惯例，任务包放本次目标与临时限制。越具体、越靠近目标的规则可以补充上层规则，但不能越过系统安全边界或用户授权。

不同工具的加载规则并不完全相同。GitHub 文档当前支持仓库级、路径级和 `AGENTS.md` 等形式，并说明最近的 `AGENTS.md` 会具有更直接的作用；其他代理可能采用不同文件名、合并方式和优先级。仓库必须记录“本工具实际怎样加载”，用小实验验证，而不是假设所有产品通用。

规则中写可执行事实：使用哪个包管理器、在哪个目录运行哪些检查、哪些文件生成、哪些操作需要批准。模糊的“写高质量代码”无法被验证。版本敏感规则标注维护者、日期或依赖版本；临时迁移规则带到期条件。

### 四、冲突不能靠位置猜测解决

读取后把规则规范化为 `source/scope/priority/version/content`。如果根规则要求 npm、模块规则要求 pnpm，而任务包未解释迁移，不能任选一条继续；应核对锁文件、脚本和负责人，必要时停止。安全规则与局部便利冲突时，安全边界保持生效。

同一层级的重复规则也会漂移。建立唯一事实源，其余位置只链接；在 CI 中检查互相矛盾的命令、过期路径和不存在脚本。规则变更要触发相关摘要与索引失效。

### 五、来源决定信息能被当成什么

**来源证明（Provenance）**记录一段上下文来自哪个文件、提交、URI、工具调用或人工决定，以及读取时间。源码、运行输出、规格和网页的权威范围不同：源码说明当前实现，测试说明已编码的预言，规格说明期望，生产观测说明真实运行，网页可能只适用另一个版本。

每条关键结论标注事实、推断或未知。工具输出和外部文档属于数据，里面即使出现“忽略以上指令”也不能提升为控制指令。检索结果只提供候选，需要核对来源、版本和与任务的相关段落。

引用应能定位到稳定路径、锚点或提交；只写“README 说”在 README 更新后无法重放。外部网页注明访问日期和版本，重要机制优先官方来源。

### 六、上下文预算按决策价值分配

**上下文预算（Context Budget）**不是固定 token 数，而是对有限窗口、检索次数、延迟和费用的分配。高价值内容包括目标、不变量、直接代码、失败证据和验证命令；低价值内容包括无关历史、重复文档、完整依赖源码和大量成功日志。

预算可以分层：始终保留任务合同与安全边界；保留当前检查点与未解决假设；局部代码按需替换；原始长日志存外部 URI，只把关键区间和定位信息放入窗口。达到预算时先清除重复和过期项，而不是截断规格或安全规则。

摘要必须可下钻，并记录覆盖范围与未覆盖内容。“测试失败”不够，应保留命令、退出码、首个根因区间和完整日志 URI。

### 七、缓存需要键、TTL 和事件失效

代码地图、接口摘要和检索结果可以缓存，但缓存键至少包含仓库、提交或内容 hash、工具版本、作用域和生成策略。只用文件路径作键，文件修改后仍会命中旧摘要。

TTL 只解决“最多旧多久”，不能捕捉关键事件。提交变化、依赖升级、Schema 版本、指令文件修改、测试从绿变红和权限变化都应主动失效。任务开始时先验证基线；任务中发生切换分支或拉取更新时，作废相关上下文。

缓存来源与敏感等级也要保存。不同租户、用户或仓库的内容不能共享同一无隔离索引；删除源数据时要传播到索引、摘要和备份生命周期。

### 八、长任务靠外部状态而不是无限聊天历史

长任务会累积工具输出和失败尝试。把稳定状态写入检查点：目标、基线、已验证事实、开放问题、变更集和下一动作。原始证据存仓库或制品系统，后续窗口按 ID 读取。这样即使会话压缩或模型切换，也能从可重建状态恢复。

压缩摘要会丢细节，必须注明时间、范围和不确定性。恢复时核对工作区、分支、依赖和服务是否仍与摘要一致。对关键安全决定和用户批准，保留原文或结构化记录，不让多轮摘要改变含义。

### 九、敏感信息先在检索前排除

最小化不是在模型输出后再脱敏。索引和读取阶段就排除 `.env`、密钥、个人数据、生产转储和无授权仓库；必要信息以短期、只读、字段级方式提供。路径名也可能泄露客户或项目，需要按分类处理。

日志进入上下文前移除令牌、Cookie、请求正文和个人标识，并保留可关联的安全 ID。外部检索不能带内部源码或客户数据作为查询。模型供应商、区域、保留和训练设置按组织政策核验，不能只依赖 UI 默认值。

如果任务确实需要敏感数据，先确认目的、最小字段、访问者、处理位置、保存和删除；无法满足时使用合成数据或停止升级。

### 十、检索质量要用真实任务评估

建立一组覆盖不同模块和失败类型的代表任务，记录完成任务所需的金标准来源。运行上下文选择器，测量关键来源召回、无关内容比例、过期命中、敏感泄露、读取成本和最终任务结果。只看向量相似度不能证明模型获得了正确事实。

对照“无地图、只有全局指令”“地图加局部指令”“加入缓存摘要”等配置。失败时分类：未检索到、检索错版本、优先级错误、摘要失真、内容太长、权限过宽或模型未遵循。改进一个机制后用同一任务集复跑，防止为单个例子过拟合。

### 十一、上下文变化本身也需要可观测

每次代理运行记录加载了哪些指令、检索了哪些资源、命中哪个版本、为什么纳入或排除、消耗多少预算、哪些缓存命中或失效。不要记录敏感正文，可记录分类、hash 和 URI。

当结果异常时，先比较“模型看到什么”，再比较“模型如何推断”。两个运行代码相同但上下文版本不同，结果差异不应被归因于随机性。上下文构建器也要有单元、集成和安全测试。

### 十二、用漂移实验验证治理闭环

选一个模块修复任务，准备根指令、局部指令、接口合同、失败用例和验证命令。第一次运行建立基线；随后修改接口但保留旧摘要、移动测试路径、让局部规则与根规则冲突，并在候选日志中混入伪指令和令牌。

期望系统能因内容 hash 或事件作废旧摘要，发现冲突后停止，继续从新路径找到测试，把伪指令视为数据，并在进入上下文前清除令牌。保存每轮加载清单、缓存决定、预算、最终证据和泄露扫描。若只有最终代码正确，却无法说明用了哪些事实，治理仍不合格。

### 十三、上下文构建可以写成可测试的选择流程

先固定不可丢弃集合：目标、授权、安全规则、基线和验收。再根据任务实体检索候选，按作用域、版本、权威性、相关度和敏感策略过滤；对冲突项保留双方并标记待决；最后在预算内去重、排序和压缩。每次选择输出原因码，而不是只返回一段拼好的文本。

选择器的单元测试覆盖作用域匹配、最近规则、提交变化、权限隔离和预算截断；集成测试用真实仓库任务验证关键来源仍在。修改排序算法或 embedding 模型时，先跑固定评估集比较，而不是直接用新索引覆盖旧结果。

如果预算不足以同时保留安全规则与任务代码，正确动作是拆小任务或换外部引用，不是压缩掉安全边界。

### 十四、代码搜索、语义检索和图检索各有盲区

精确搜索适合错误码、符号和路径，语义检索适合概念近义，import/调用图适合结构依赖，运行 trace 适合真实路径。单一向量搜索会漏掉短符号和版本关系，也可能把概念相似但无调用关系的模块混在一起。

检索计划随问题组合工具：从错误日志精确定位入口，沿调用图找边界，再用语义检索补文档。候选必须经内容和版本核验。动态加载、代码生成、反射和配置路由会让静态图不完整，应在地图上标记并用运行证据补充。

### 十五、文档与代码不一致时需要裁决规则

“源码优先”不是万能答案：源码说明现状，已批准规格可能说明它正是错误。应按问题区分权威：期望行为看有效规格和领域决定；当前实现看代码与运行；构建方式看锁文件和实际脚本；安全授权看系统/组织策略。

发现不一致时记录双方版本、差异和影响，停止依赖该事实的写操作。由适当负责人裁决后，同时更新源与派生摘要。不要静默选择更方便修改的一方。

### 十六、上下文供应链也需要安全与许可治理

索引器、MCP 服务、网页抓取和第三方知识库都有权限与依赖风险。连接器只获得完成检索所需的只读范围，返回结果保留来源和租户，工具升级经过版本与安全审查。外部内容的许可、保留和再分发限制也影响能否长期缓存。

对检索服务做提示注入、跨租户、恶意文件、超大结果和删除传播测试。停用数据源后撤销凭据并清除派生索引；不能因为模型上下文不可见就忘记后台仍保存副本。

### 十七、成本和延迟是质量约束的一部分

每次读取整个仓库会拖慢反馈并增加费用，过度摘要又会降低正确性。记录检索次数、读取字节、上下文 token、缓存命中和端到端时间，与任务成功和缺陷一起分析。优化应减少无价值内容，不是把可重放证据删掉。

交互式小修需要秒级入口和渐进下钻；长迁移可在后台建立更完整索引。缓存预热只针对活跃、低敏且版本稳定的资料。性能退化时先定位是检索、排序、模型还是工具等待，避免盲目缩短所有上下文。

### 十八、上下文输出要让执行者看见不确定性

构建结果除了内容，还应给出缺失项、冲突项、低置信来源和未读取范围。模型知道“没有读取支付服务实现”比收到一个看似完整的摘要更安全；评审者也能判断结论边界。

对事实使用可定位引用，对推断写明依据，对未知提出能缩小范围的下一步。若关键未知会改变实现方向，暂停写入；若只是低风险细节，可采用已批准默认值并记录。把不确定性结构化，能避免后续摘要把“可能”压缩成“确定”。

### 常见误解

- 更大的上下文窗口不会消除过期、冲突和不相关信息。
- 仓库指令不是文档装饰，必须验证工具实际加载和优先方式。
- 摘要不是事实源；它可以被源码、规格和运行证据作废。
- 向量相似不等于版本正确、权限允许或任务相关。
- 缓存有 TTL 不等于能响应提交、Schema 和权限变化。

### 学完后应能说明

你应能为一个真实仓库建立可维护地图和分层指令，给关键上下文标记来源、作用域、版本与敏感等级，按任务阶段分配预算，设计缓存键和事件失效，利用代表任务测量检索质量，并在冲突、漂移或泄密风险出现时停止执行而不是继续猜测。

# AI 结构化输出与运行时校验知识点讲义

## AIAPP-03 结构化输出与 Schema 校验

让模型返回 JSON 只是把自然语言的不确定性装进了看似规整的括号。它可能语法损坏、字段缺失、枚举越界，也可能每个字段都符合类型却违反业务权限。可维护系统必须把模型结果视为不可信候选，经过解析、结构、语义、授权和状态验证后，才能成为页面数据或业务动作。高级工程师关注的不是“怎样让模型更听话”，而是任何模型、版本和异常输入都无法越过确定性边界。

### 学习前先确认

- 直接前置：[AIAPP-01 模型接口、指令与上下文边界](../chinese-guides/aiapp-01-model-interface-instructions-context-boundaries.md#aiapp-01)，用于理解模型响应、结束原因、能力协商和供应商适配；[TS-07 运行时契约、校验与错误模型](../chinese-guides/ts-07-runtime-contracts-validation-error-models.md#ts-07)，用于区分静态类型与运行时事实。两条路径分别承担模型边界与程序校验，没有互相包含。

### 一、结构化输出解决的是接口形状

**结构化输出（Structured Output）**是让生成结果遵循应用声明的数据形状，并在运行时验证后再消费。它适合表单草稿、分类结果、工具参数、抽取记录和可渲染消息块，因为这些消费者需要稳定字段而不是一段任意文字。

结构化不等于真实、完整或有权。`{"role":"admin"}` 可以是合法 JSON，也能通过字符串类型检查，却不代表当前主体拥有管理员角色。评分 `101` 可能符合 number，却超出业务范围。每一层只证明一件事：解析证明语法，Schema 证明形状，业务规则证明领域约束，授权证明主体可以影响对象。

先写消费者需要的最小数据，而不是把数据库模型、供应商响应或未来设想全部暴露给模型。字段越多，模型越容易制造矛盾，迁移和隐私面也越大。派生字段由确定程序计算，身份、租户、价格和权限从受信系统读取，不让模型填写。

### 二、Schema 是可执行合同

**运行时模式（Runtime Schema）**是在真实值进入程序时检查类型、必填项、枚举、格式、组合和额外字段策略的可执行合同。TypeScript 的接口会在编译后消失，类型断言 `as Result` 只是告诉编译器相信开发者，不能改变网络字节。

Schema 应有明确版本、所有者和消费者。字符串可继续约束长度、正规化和格式；数组限制数量与元素；对象决定是否拒绝未知字段；判别联合用稳定 `kind` 区分形态。日期最好先保留为经验证的 ISO 字符串，再由确定代码解析时区，不让 `Date` 构造器替你猜。

严格拒绝未知关键字段有助于发现供应商或提示漂移；兼容扩展区可以保留明确命名的元数据。全局使用“自动剥离所有未知字段”会掩盖版本不一致，全局使用“全部接受”又可能把危险字段传到下游。策略应按边界选择并记录。

### 三、从字节到可信对象要逐层收敛

响应首先受大小、超时和内容类型限制，再解码为文本。非流式 JSON 只有在结束原因表明完整、字节解码成功且整体闭合后才解析；流式数据不能对每个碎片调用 `JSON.parse`，因为 UTF-8 字符、转义序列和对象都可能跨块。

解析结果类型是 `unknown`。通过 Schema 后得到“结构有效候选”，再进入领域校验：日期先后、金额上下限、引用存在、字段组合、对象版本和状态机转移。最后在服务端使用认证上下文核验租户与权限。只有这些层全部通过，结果才进入内部可信类型。

每次转换保留关联 ID、Schema 版本、模型与提示版本、结束原因和错误类别。不要在普通日志保存完整提示或敏感候选；诊断可记录字段路径、期望类型、实际类别、长度和脱敏摘要。

### 四、语义校验不能塞进一句 refine

**语义校验（Semantic Validation）**检查数据是否在当前领域、身份和时间点成立。它经常需要数据库、权限服务或状态机，因此不应伪装成纯 JSON Schema。Schema 可要求 `amount` 是非负数，业务层才知道订单剩余额度、币种精度和审批阈值。

把结构与语义错误分开，用户和恢复策略才准确。`items` 缺失可以请求模型重新给出结构；订单属于另一租户必须直接拒绝，不能把租户 ID 放回提示让模型“修正”；记录版本过期需要重新读取事实，而不是润色结果。

跨字段不变量要集中在领域层，例如结束时间晚于开始时间、选了退款动作就必须有订单和原因、引用 ID 必须来自本次允许集合。若同一规则散落在提示、前端和执行器，迟早会出现一处放行。

### 五、把失败建模为状态而不是异常字符串

一条结果可以经历 `candidate → decoded → parsed → schema_valid → policy_valid → accepted`，也可以进入 `truncated`、`malformed`、`unsupported_version`、`schema_invalid`、`policy_denied`、`stale` 或 `needs_review`。这些状态决定是否重试、请求用户输入、降级为文本或停止。

错误对象包含稳定代码、可公开说明、内部字段路径和可否修复。不要把校验库的原始堆栈、内部 Schema 或敏感值直接发给模型和用户。前端展示“缺少截止日期，可补充后再试”，而不是 `invalid_type at result.tasks[0].dueAt`；诊断台仍能通过请求 ID 找到细节。

空响应、模型拒绝和长度截断不是同一种“JSON 错误”。拒绝内容应作为明确响应块呈现，截断可让用户缩小任务或继续生成，空响应可能按供应商暂态错误处理。混成解析失败会诱发错误重试。

### 六、修复是一条受限的新生成链

**修复预算（Repair Budget）**规定一次候选最多允许多少次结构修复、消耗多少时间和费用，以及哪些错误根本不可修复。修复只处理形状，不应改变原始业务结论、提升权限或替模型补造证据。

给修复调用提供原始候选的受控片段、失败字段和目标 Schema，不把秘密或内部策略全量回传。修复结果从头经过解析、Schema、语义和授权，不能因为“这是第二次”跳过检查。达到上限后转人工输入、普通文本或明确失败。

可修复的例子是枚举大小写或缺少可从原文提取的字段；不可自动修复的例子是越权对象、相互冲突的金额、缺少来源或内容安全阻断。把所有失败都交给模型重写，可能把可诊断错误变成流畅伪造。

### 七、结构化输出能力需要在调用前协商

供应商可能提供严格 Schema、JSON mode、工具参数 Schema 或仅靠提示约束的 JSON。它们保证强度不同。应用合同声明需要“语法 JSON”还是“服务端强制指定 Schema”；适配器无法满足必需能力时拒绝或选择显式降级，不能把弱能力标成严格模式。

供应商特有字段留在适配层。内部 Schema 才是应用真相，供应商 Schema 是一次映射。映射器要测试不支持的关键字、深度限制、枚举数量、递归引用和可空语义；自动删减 Schema 后若改变约束，应判为能力不等价。

即使服务端声称强制 Schema，应用仍校验响应。网络代理、SDK bug、版本变化和宽松语义都可能返回意外值；而且供应商无法理解你的租户、库存或审批规则。

### 八、版本演进要区分读兼容与写兼容

新增可选字段通常对旧消费者读兼容，新增必填字段则需要新版本或迁移。改变枚举含义、单位和默认值往往是破坏性变化，即使 JSON 形状没变。Schema 版本应跟随结果保存，让历史数据可解释。

读路径可以接受 v1/v2 并迁移到内部当前模型；写路径只产生明确版本。迁移是确定函数，有输入输出样本和失败状态，不能让模型临时“把旧 JSON 改成新 JSON”后覆盖原记录。未知未来版本应停止或只读降级。

发布新 Schema 时先运行历史回放和双写观察，确认旧客户端、安全策略和存储都能处理；再灰度切换提示与模型。回滚要同时恢复 Schema、提示、解析器和消费者，不能只换模型名。

### 九、流式结构需要提交边界

流式文本可以逐字展示，结构对象则应在完整边界提交。可以流式传送多个独立 JSONL 事件、带长度的帧或具有明确 start/delta/end 的字段，但不能把尚未闭合的对象当最终值触发渲染或副作用。

增量界面可以展示“正在生成第 2 项”的临时态，稳定 ID 和序号用于合并；只有完整项通过校验后成为已确认块。终态到达后拒绝迟到事件，断线时保留已确认项并把未完成项标为 incomplete。

尤其不能逐块净化或逐块 Schema 校验后直接拼接执行，因为危险字符串和字段可以跨块组成。最终组合还要重新经过整体校验。

### 十、不要把 Schema 变成提示泄露面

发送给模型的 Schema 可能暴露内部字段、权限名称或业务规则。只提供生成所需的公共合同；内部主键、审批令牌、风险阈值和秘密不进入 Schema 描述。服务端在结果上补充受信元数据，而不是请模型回显。

错误反馈也要最小化。告诉模型“字段 role 不允许由生成结果设置”比返回完整权限表安全。外部用户看到的失败说明与内部诊断分层，避免攻击者通过反复试错枚举 Schema 和策略。

模型产生的字符串进入 HTML、URL、SQL 或工具时还要按最终解释器处理。结构化输出不是 XSS、SSRF 或命令注入的防护替代品。

### 十一、测试从控制失效和组合错误开始

基础样本覆盖合法、空、截断、超长、额外字段、缺失字段、错误类型、未知枚举、深层嵌套和旧版本。领域样本覆盖范围、状态冲突、跨租户、引用缺失、时间竞争和权限撤销。组合样本故意让 Schema 通过但授权失败，或让修复成功却版本过期。

断言不仅看错误码，还看副作用调用次数为零、旧有效数据未被覆盖、日志不含秘密、用户能恢复、相同输入可回放。用属性测试生成边界值，用变异测试确认删除某个校验会导致用例失败，防止“测试全部绿色但断言从未保护规则”。

生产指标按 Schema/模型/提示版本统计接受、修复、拒绝、人工升级、字段失败分布、延迟和成本。接受率突然升高也可能意味着校验被放宽，不应只对失败率告警。

### 十二、复合对象要把局部错误定位给人

真实输出常是树形对象：报告包含章节，章节包含主张和引用，引用又包含来源与范围。若只返回“Schema 校验失败”，开发者和用户都不知道哪一处需要修正。校验结果应使用稳定 error code、JSON Pointer/字段路径、期望类型、实际类别和可公开说明；日志保留候选版本与 Schema 版本，界面只展示安全且可行动的信息。

数组需要同时验证元素、长度、唯一性和跨元素约束。例如引用 ID 不能重复，主张引用的 sourceId 必须存在，百分比之和可能需等于 100。不要为了让解析通过就删除失败元素，否则原本要求五项的结果会悄悄缩成四项。局部容错必须是产品合同的一部分，并明确哪些字段可缺省、哪些错误使整份结果不可用。

国际化也属于数据合同：日期、货币、locale、时区和自然语言文本分开保存。模型生成的“2026/9/1”不能在不知道地区时直接解析成业务日期。服务端统一规范化，展示层按用户 locale 格式化，原始候选继续可追溯。

### 十三、形成稳定的结构化边界

为一个真实输出画出字节、解码、解析、Schema、语义、授权、呈现或执行的完整链。逐层写输入、能证明的事实、失败状态和负责人；再用版本升级、截断、越权和修复耗尽证明任何一层失效都不会把候选冒充事实。

上线清单还应包含 Schema owner、兼容窗口、失败样本留存、监控字段和回滚路径。消费者不得绕过统一解析器直接断言字段，批处理、缓存和消息队列也使用同一版本合同。只有每个消费入口都拒绝未经验证的候选，边界才真正闭合。

监控按 Schema 版本和字段路径聚合失败，突然升高时可快速定位供应商、提示或消费者变更，而不需要先翻阅用户原文。

学完后，你应能解释为什么“返回 JSON”“TypeScript 有类型”和“供应商支持 Schema”都不足以建立信任；能设计版本化运行时合同、错误状态、有限修复和迁移；能让页面与服务端只消费已经通过相应边界的数据。DeepSeek 的 [JSON Output 官方说明](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)可用于核验具体接口约束，但厂商能力不替代本讲的通用验证链。

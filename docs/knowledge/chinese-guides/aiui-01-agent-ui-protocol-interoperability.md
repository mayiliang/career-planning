# Agent UI 协议与互操作知识点讲义

## AIUI-01 Agent UI 协议与 MCP Apps 互操作实现

Agent 前端不再只接收一段文本：它可能接收运行生命周期、工具调用、共享状态、声明式界面或隔离应用。AG-UI、A2UI 与 MCP Apps 分别解决不同层次的问题，名称相似却不能互换。高级前端要能识别协议负责什么、状态归谁、能力怎样协商、版本如何降级，并通过内部适配层避免业务组件被某个快速演进的协议绑死。

### 学习前先确认

- 直接前置：[AIAPP-05 Generative UI 视图模型与宿主边界](../chinese-guides/aiapp-05-generative-ui-view-model-host-safety.md#aiapp-05)，用于理解受信组件、视图状态与隔离宿主；[AIAPP-02 流式响应、SSE 与增量渲染](../chinese-guides/aiapp-02-streaming-sse-incremental-rendering.md#aiapp-02)，用于理解事件流、断线、顺序和终态。两份资料共享更早模型接口，但彼此不包含。

### 一、先按层次区分协议

AG-UI 主要连接 Agent 运行时与用户应用，表达 run、消息、工具和状态事件；A2UI 主要让 Agent 用受限 JSON 流描述 surface、组件和数据模型；MCP Apps 让 MCP Tool 关联可交互 UI 资源，在宿主隔离环境中通过桥接通信。一个系统可以组合三者，也可以只使用其中一个。

不要按营销名称推断能力。事件协议不自动提供声明式组件，声明式 UI 不自动提供可靠传输，MCP Tool 可用不代表宿主支持 Apps 扩展。每层都要单独协商、验证和降级。

建立分层图：底层传输负责字节和连接；运行事件负责生命周期与状态；视图描述负责可渲染结构；宿主扩展负责隔离资源和能力桥；业务服务负责身份、授权和事实。把它们混成一个“Agent SDK”会让故障与安全责任无法定位。

### 二、Event Protocol 表达可归约的运行事实

**事件协议（Event Protocol）**用类型化、可排序的事件描述运行开始、消息增量、工具调用、状态快照和终态。事件是状态变化证据，不是随意日志字符串。客户端根据事件归约 UI，重连后用快照或水位线恢复。

AG-UI 官方架构以事件驱动、双向且传输无关为核心，提供生命周期、消息、工具、状态和扩展事件。标准事件并不等于网络天然可靠：应用仍需 runId、messageId、toolCallId、顺序约束、重复处理和终态封闭。

`RAW` 或自定义事件不能成为绕过 Schema 的通道。适配器保存来源和原始类型，只把明确支持的语义映射到内部事件；未知事件可记录并忽略，不能直接传给业务组件执行。

### 三、A2UI 描述 surface 而不是代码

A2UI v0.9 家族以 JSON 流创建 surface、更新组件、更新数据模型和删除 surface，组件来自 catalog。当前官方页面建议生产关注 v0.9.1，并把 v1.0 标为 candidate；因此实现必须锁定版本并在发布时复核，不能把“v0.9”当永久事实。

宿主按 catalog 验证组件、属性、绑定路径和动作。UI 结构与数据模型分离，允许逐步建立组件并更新数据；未到达的引用显示占位。模型生成仍需严格校验，因为 prompt-first 描述不会自动变成可信对象。

客户端能力声明支持的 catalog 与函数，服务端只在交集里生成。未知 catalog、组件或函数采用文本/结构化降级，不能动态下载任意实现。数据绑定只在 surface 范围内工作，不读取宿主对象。

### 四、MCP Apps 是可选宿主扩展

MCP Apps 通过 Tool 元数据关联预声明 UI Resource，宿主把 HTML 应用放入沙箱 iframe，并用受控桥接传递工具结果、主题、尺寸和允许调用。它不是核心 MCP 的必备能力，不支持的客户端仍应得到有意义的文本 Tool 结果。

UI 资源的 URI、媒体类型、CSP 和权限由规范与宿主政策约束。来源是 MCP Server 不等于完全可信；App 只能通过协商的能力调用 Tool 或请求宿主服务，不能直接读取聊天、令牌或跨域网络。

宿主必须验证来源、实例、消息 Schema、请求 ID 和当前授权。App 卸载或会话切换后撤销能力。工具执行事实仍由 MCP Server 或业务服务提供，iframe 自己显示“成功”不能改变 Host 状态。

### 五、Capability Matrix 先于适配代码

**能力矩阵（Capability Matrix）**逐项记录协议版本、事件类型、状态所有者、组件 catalog、输入事件、媒体、工具、恢复、安全边界和降级。它让团队看到交集与不可映射差异，而不是用一个 `supportsUI` 布尔值掩盖。

能力有必需与可选。当前功能若必须编辑表单，而宿主只支持文本，就应切换到链接或人工流程；若只是图表可视化，可以降级为表格。任何降级都要保持事实、来源和关键动作边界。

矩阵带来源、核验日期和实现版本。协议页是 living document 或 candidate 时，发布构建锁定 Schema/SDK 版本，自动契约测试验证真实宿主，不依据网页标题猜支持。

### 六、Protocol Adapter 建立内部防腐层

**协议适配器（Protocol Adapter）**把外部事件、surface 或桥接消息转换成应用内部的版本化运行事件和视图模型，并把内部用户动作映射回协议允许形式。它负责结构、版本、顺序和能力差异，不负责替服务端授权。

内部最小事件可以包含 session/run ID、event ID、sequence、kind、entity ID、payload、source、schemaVersion 和 terminal。视图模型由 AIAPP-05 负责，工具事实由 AIAPP-04 负责；适配器只连接它们。

不要追求无损映射。AG-UI 状态 delta、A2UI data model 和 MCP App 私有状态有不同所有权；无法保持语义时保存可观察扩展并降级。静默丢掉确认或终态会制造错误事实。

### 七、顺序、重复和重连需要明确策略

同一实体事件按协议定义的顺序归约；没有全局序号时使用 run、message 或 toolCall 局部顺序。重复 ID 幂等忽略，序号缺口进入等待或快照重同步，终态后拒绝迟到增量。

网络传输可能保持到达顺序，却无法避免应用重放、恢复和多来源合并。客户端不能仅靠数组 append。快照覆盖对应版本的旧状态，delta 必须有基线；基线缺失时请求新快照或安全重建。

重连保存最后确认水位线和用户草稿。协议不支持续传时显示未完成并重新开始新 run，不能把两次 run 的 token 拼成一个回答。

### 八、状态所有权必须一目了然

区分服务端运行状态、共享业务状态、客户端视图状态、用户未提交输入和隔离 App 本地状态。只有拥有者能发布权威更新；其他层发送提议或派生视图。模型不能通过 state delta 改变权限或数据库事实。

双向共享状态需要版本或 JSON Patch 基线、冲突策略和字段权限。客户端编辑与 Agent 更新同一字段时，按所有权、版本和用户确认解决，不使用“最后到达者获胜”覆盖输入。

持久化选择可恢复的事实与用户数据，临时动画和派生布局不必保存。调试 trace 记录事件与归约版本，但遵循隐私最小化。

### 九、协议版本要锁定、协商和迁移

编译期类型不能证明远端版本。握手或能力元数据取得对端声明，校验 Schema 后选择双方交集。无交集给出明确错误；未知可选字段忽略并记录，未知关键语义停止。

版本升级先运行旧客户端/新服务端、新客户端/旧服务端和双新组合。适配器可短期双栈，但要有流量阈值、期限、监控和删除条件，避免永远背负旧协议。

living document、draft、candidate 和 stable 要在资料和代码中区分。生产不能只引用 `latest`，应锁定可复现的 Schema、SDK 和测试快照。

### 十、Graceful Degradation 保持任务可完成

**优雅降级（Graceful Degradation）**是在能力缺失或版本不兼容时保留核心信息与安全路径，而不是伪装支持或整页崩溃。降级顺序可从交互组件到只读结构、数据表、文本摘要，再到可解释的外部人工入口。

降级不能改变权限。宿主不支持确认组件时，高风险工具不是“默认同意”，而是停止或跳转到可信确认页。缺少流式支持可以等完整结果，缺少自定义组件可以显示文本，缺少来源展示则不能把内容标成已核验。

用户应知道当前是降级模式、失去什么、怎样恢复。遥测记录能力缺失和任务影响，为是否继续维护兼容层提供依据。

### 十一、跨 origin 与桥接消息按不可信输入处理

验证精确 origin、source、协议版本、nonce、实例 ID 和消息 Schema，不使用 `*` 或只看事件 type。App 发来的工具请求仍经过 Host 能力和服务端授权；Host 发给 App 的敏感数据按最小必要字段裁剪。

桥接限制速率、消息大小、允许方法和并发。销毁实例后拒绝旧消息，导航到新 origin 时旧能力失效。CSP 与 sandbox 防止直接访问，但不能替代消息授权。

协议事件也可能包含用户或网页文本，渲染时按最终上下文编码。标准协议不是可信内容证书。

### 十二、可观测性记录结构化事实而非隐藏推理

一次运行关联 transport、协议与版本、能力快照、适配器版本、run、message、tool、surface、App 实例和错误类别。日志保存事件元数据与脱敏摘要，不需要公开模型内部思维。

指标包括握手失败、未知事件、序号缺口、重放、快照恢复、组件降级、桥接拒绝、用户恢复和版本分布。按协议层定位，不把所有失败都叫“Agent 出错”。

用户可见进度来自生命周期和真实工具状态；没有事件证据时显示等待或未知，不用动画编造阶段。

### 十三、兼容测试必须跨三个维度

为每种协议准备正常、旧版、未知字段、未知组件、缺能力、乱序、重复、断线、伪造 origin 和权限撤销。至少用支持完整组件、只支持文本和不支持扩展的三类宿主。

断言内部状态一致、写工具不重复、能力不足不越权、纯文本仍可完成核心任务。截图验证表现，事件/权限/网络记录验证语义；只跑通官方 happy path 不足以证明互操作。

性能还要覆盖高频 delta、巨大 surface、多个 App、桥接风暴和销毁资源。适配器不能因未知事件累计无限队列。

### 十四、互操作还要统一语义而非只翻译字段

两个协议都出现 `message`、`tool` 或 `state`，不代表含义相同。适配前写出内部不变量：谁分配 ID、delta 是否可重放、终态能否再更新、动作由谁授权、surface 销毁是否取消任务。无法无损映射的能力显式标为 partial/unsupported，不用相似字段硬凑。

例如事件协议报告工具已完成，而 UI surface 仍保留旧的“执行中”按钮，适配器要以服务端事实结束交互并拒绝重复动作；surface 的本地表单草稿不能反向改写任务终态。跨层一致性由关联 ID、版本和状态归约规则保证。

维护一组协议中立的 golden traces，同一轨迹分别经过各适配器，比较最终内部状态、权限决策和降级 UI。这样升级某个 SDK 时，团队验证的是产品语义没有漂移，而不只是类型检查通过。

### 十五、形成协议可替换的产品架构

先定义产品需要的内部事件、视图和动作，再用能力矩阵选择协议组合。适配器隔离变化，宿主掌握组件和权限，服务端掌握业务事实；每层都能独立测试和降级。

协议选择记录产品所需能力、当前实现版本、缺失语义、降级方式、迁移负责人和退出条件。升级不是替换依赖版本后结束，还要重放 golden traces、检查权限和旧任务恢复，并在生产观察版本分布。

学完后，你应能说明 AG-UI、A2UI 与 MCP Apps 的职责差异与组合方式，建立能力矩阵、协议适配、版本迁移和安全桥接，并在不支持新能力时保持可读、可控的任务路径。实现前应复核 [AG-UI 架构](https://docs.ag-ui.com/concepts/architecture)、[A2UI 当前规范族](https://a2ui.org/specification/v0.9-a2ui/)与 [MCP Apps 官方说明](https://modelcontextprotocol.io/extensions/apps/overview)，因为这些协议仍在演进。
